# 08. Decide: which ADRs carry over

Type: grilling
Status: resolved
Blocked by: 06, 07
Labels: wayfinder:grilling
Map: ../map.md

## Question

For each of the old map's ADRs, `.scratch/next-foundation-specs/adr/0001` to `0046` with their dated notes, decide whether it is carried over, adapted, or abandoned for Yeti, with the reason. Examples:

- rendering modes (0008);
- the browser testing stack (0018);
- WCAG 2.2 AA enforcement (0022);
- the release policy (0045);
- Sass packaging (0012);
- the class rule (0039);
- Variant input types (0040);
- each plugin-specific record.

## How to work it

AFK grilling against the research tickets and the decisions of [Decide: which standing preferences and user rulings carry over](07-decide-inherited-preferences-and-rulings.md) and [Decide: the browser target](06-decide-browser-target.md). Each carried-over ADR is copied into `adr/` here with a new number and an `Inherited from` line. Each adapted one is rewritten with what changed. Each abandoned one gets one line in this ticket's Answer. Plugin-specific records (Reveal, Orbit, Tabs, menus) are only adapted when [Decide: the spec list](11-decide-spec-list.md) keeps a Yeti counterpart; until then they are marked pending.

### Questions asked and answered

Both sides of each question were played against the sources; the answer recorded is the one the evidence supported.

1. **May a plugin-specific record with no Yeti counterpart at all be abandoned now?** No. The ticket keeps plugin-specific records pending until the spec list keeps a counterpart, and the spec list may still add shared-utility specs. Each pending row records the expected verdict instead, so ticket 11's follow-up is mechanical. Against: Interchange, Toggler, and Equalizer have no Yeti item, so the wait buys nothing. For: the rule is the ticket's own, and waiting costs one table edit.
2. **Do the superseded records (0010, 0034) wait too?** No. They were superseded in the old bundle itself, so their verdict follows the old bundle's own history, not the spec list.
3. **Is the Anchored pane's positioning (0002) a shared utility to keep or a Foundation port to drop?** Drop. Its own text named native `popover` plus anchor positioning as the upgrade "when the browser target moves", and the target moved ([ADR 0002](../adr/0002-browser-target-baseline-2025.md)), which also decided that Yeti's guarded fallbacks stand. Checked in `dropdown.css:44-58`.
4. **Does Yeti have breakpoints for a Breakpoint service to mirror?** No. Checked in `migrating.md:111` and `responsive.md:29-33`, and by searching `src/` for `matchMedia` (one hit, `hover.js:14`, a pointer query) and for viewport `@media` queries (none outside `prefers-*`, `hover`, and `pointer`).
5. **Which clauses of the rendering-modes contract survive Yeti?** All but two kinds: the click-handler activation clause (replaced by the platform's opening attributes, measured in ticket 18) and the breakpoint clauses (no breakpoints). Two clauses are new, from ticket 18's and ticket 20's measurements: no reliance on Yeti modules' load-time setup, and `withI18nSupport()` wherever `i18n` is used.
6. **Is the button's no-`click`-on-`<a>` rule button-specific?** Its decision is; its reason is Angular's dispatcher (checked in `dispatcher.ts:127-140`), and Yeti has many link items (breadcrumbs, pagination, nav, toc). So the general rule moves into ADR 0011 now and the button row stays pending.
7. **With the platform resolving `commandfor` by id, is a typed reference still worth having?** Yes. The platform needs ids, but a consumer typing them gets no compile error for a typo; a reference costs nothing at run time and the directive writes the id. Against: an id string reaches across templates where a reference does not. Recorded as the reopening condition in ADR 0013.
8. **Do generated ids threaten hydration now that they appear in platform attributes?** Possibly, across hydration boundaries. CDK's `_IdGenerator` keeps counters in module state (checked, `id-generator.ts:18`), so server and client ids can differ; a pair that hydrates in one pass is consistent. Inferred, not measured, which is why the old one-hydration-boundary rule keeps a new reason in ADR 0011 clause 7.
9. **Does the old registry's light-dismiss model still need code?** Only its focus rule, plus the tooltip's Escape. Yeti's comment says the top layer, light dismiss, Escape, and the expanded state "are all the browser's" (`dropdown.css:1-4`, checked), while ticket 17 measured the dropdown staying open on focus-out and the APG's disclosure example closes on `focusout` (`disclosureMenu.js:87-92`, checked).
10. **Where do Yeti's `validate.js` and `frozen.js` sit among the test layers?** Neither is a layer. `bin/build.js` imports and runs the validator on every build (`build.js:9`, `:34`, checked); `frozen.js` compares two git refs and exits 1 on a break (`frozen.js:1-12`, checked), which makes it a pin-move check. The third addition, an attribute-and-value check, is a package test in the node-level layer, so the Milestones deferral of checks does not reach it.
11. **Without Sass, what replaces the compile-time contrast check?** A play-function assertion from computed styles: Yeti's tokens are runtime, so a story's computed colours are the defaults a consumer sees. Against: the old record rejected runtime contrast checks because colours vary by theme. That objection was to a check in consumers' pages, not to a test of the package's own stories.
12. **Is a Yeti pin move a dependency update or a release-policy event?** A release-policy event, classed by what changes. A frozen-surface break removes or renames the package's own public values, which the carried policy reserves for an Angular major; an additive move breaks nobody. Raising Yeti's browser target waits for an Angular major, as Angular's own browser support does (`versions.md:75-77`, checked). Changes to what Yeti leaves unfrozen are not settled by the sources (`### Triage`).
13. **Is a later-milestone import-check spec worth keeping at all, as ticket 07 asked?** Yes as the answer, while the spec list decides whether this map writes it. The user deferred checks and never withdrew them ("family/peer/parent/similar checks should be specced but deferred like missing import checks", old ticket 158), and under ADR 0003 a forgotten import is worse than before: the element gets no class at all.
14. **Can the class prefix be decided from sources?** No. The user is choosing it (the orchestrator's message, with the user's words quoted in ADR 0012). What is independent of the letters is recorded: a prefix exists, `Nfs` goes, tokens are camelCase `...Token`, and class names must not equal a Yeti type name, because Yeti generates `Yeti`-plus-vocabulary types (`gen-types.js:18`, checked).

**Open item 1: pin moves that change only unfrozen surface.** Yeti freezes names, not values: public token defaults, private tokens, and generated file text may change at any commit (`src/guides/stability.md:19`, `:26-28`, read at `f52d1e8b9`: "Their default values may still be tuned"; "so may we, before `7.0.0`, where a measurement says a default is wrong"). A pin move can therefore change every consumer's colours or spacing without touching the package's API. The carried policy reserves breaking changes, removals, and platform-feature upgrades that change what consumers see for an Angular major. The option the user chose in the old bundle phrased it as "a behaviour-changing platform upgrade lands only in a major" (old ticket 141, the orchestrator's option text), written for the package's own adoption of a platform feature (its example was a Dropdown pane moving to native popover), with no Yeti case in view. Both readings are defensible, and they lead to different work for ticket 12: one holds such moves for up to six months, the other lets them ship in any release.

- (a) Allowed in any release, with a changelog entry naming the visible change, because Yeti declares those values unfrozen and a consumer can keep any default by setting the token ([ADR 0004](../adr/0004-yeti-tokens-are-a-consumer-stylesheet-surface.md)).
- (b) Held to an Angular major, like a visible platform upgrade, so a routine update never changes what a page looks like.
- (c) Split by kind: (a) for colour and spacing values, (b) for anything a spec's stories or the contract check show as a layout change.

Recommendation, for the user to accept or refuse: (a), because the clause's subject was the package's own platform choices, and (b) would hold Yeti's design fixes behind Angular's calendar. Until the user answers, [ADR 0017](../adr/0017-release-policy-with-a-pinned-yeti.md) plans no such move into a release.

**Open item 2: the class prefix.** The user's words and the orchestrator's unapproved recommendation are quoted in [ADR 0012](../adr/0012-class-prefix-and-token-naming.md). Nothing in this ticket depends on the letters; the specs write `<Prefix>` and `<prefix>` until the user rules.
