# Map: ngx-yeti-specs

Label: wayfinder:map
Branch: wayfinder
Created: 2026-10-01

## Destination

One published spec (via `/to-spec`) for each Yeti component, layout, recipe, and utility family that the spec-list decision keeps, plus a building-blocks map and a ledger (`ledger.md`) of every standards, accessibility, and Angular Aria, CDK, or Material feature the package adds that Yeti itself lacks. Each spec describes the Angular directives (preferred) or component of a new Angular package that wraps Yeti, Foundation's version 7 (`yeti-css`). The building-blocks map records which Angular, CDK, Aria, or native platform primitive each one is built on. [Decide: the spec list](issues/11-decide-spec-list.md) keeps 53: one spec per item of Yeti's manifest (49), named as Yeti names it, and 4 shared-utility specs (navigation-close, fragment-links, events, generated-ids). The map is done when all specs exist under `specs/`, every carried-over requirement, ADR, decision, and principle from `.scratch/next-foundation-specs/` has been triaged and recorded here, and the consistency review has passed.

## Notes

### Domain

Yeti (https://github.com/foundation/yeti, `develop` branch; docs at https://www.foundationcss.com/yeti/) is the successor to Foundation for Sites. Its README describes "a CSS-first, native, zero-build layout and styling framework": one stylesheet, no Sass, cascade layers, container queries, runtime `--yeti-*` tokens, and optional JavaScript modules. Its README says it targets Baseline 2025, and its stability guide (`src/guides/stability.md`) lists what `7.0.0-beta` froze. The Angular package wraps Yeti's CSS and attribute contract and replaces or complements its optional JavaScript; which of those it does is decided here.

The user ruled Yeti's FSL-1.1-MIT licence compatible with this package as a free and open-source MIT project ([ADR 0001](adr/0001-yeti-licence-compatible-with-mit-package.md)). Yeti's announcement (foundation/yeti#15554) says of `develop`, "unstable until the beta. Do not build on it yet." The user ruled on readiness, verbatim: "Readiness: We will spec and build against a specific commit of `foundation/yeti`'s `develop` branch." Which commit, how the pin moves, and how the package depends on unpublished Yeti are decided in [Decide: which Yeti version the specs target, and how the package tracks it](issues/12-decide-yeti-version-policy.md).

### Standing rulings (the user's own messages to the orchestrator, 2026-10-01)

- Browser target: "26. Browser baseline: For this project, accept Yeti's Baseline 2025 or the least common denominator browser set/baseline supporting browser/CSS features Yeti relies on." [Decide: the browser target](issues/06-decide-browser-target.md) chooses between the two.
- Components for styles: "28. If using Angular components with styles/styleUrl(s) can be used for lazy-loading/unloading component-specific styles and to pass requirements and bugs Angular's leave-animation guard and Beasties critical CSS, that's a valid reason to use components instead of directives where applicable." This relaxes the old map's "directive over component" preference for this map, wherever a component's `styleUrl` is what makes lazy styles meet the requirements. [Decide: which standing preferences and user rulings carry over](issues/07-decide-inherited-preferences-and-rulings.md) and [Decide: how component styles load and unload](issues/13-decide-style-loading.md) apply it.
- Deployment URLs: "29. `deployUrl`/`--deploy-url` is unsupported/to-be-removed as per https://angular.dev/tools/cli/build-system-migration#manual-migration-to-the-new-application-builder so we don't need to support it. Only `baseHref`/`--base-href`/`<base href>` should be supported." No spec supports or tests `deployUrl`.
- Hydration features: "We must not forget about support for `withEventReplay()`, `provideClientHydration()`, [incremental hydration](https://angular.dev/guide/incremental-hydration), and `withI18nSupport()`." Every spec states how its directives or components behave under each of these, and [Prototype: Yeti under SSR, hydration, `@defer`, event replay, and `animate.enter` and `animate.leave`](issues/18-prototype-yeti-rendering-modes.md) measures them.
- Building Yeti: "31. As written in Yeti's documentation, it is expected that in this alpha stage, the consumer must run npm build in the repo and `esbuild` locally to use their CSS (and JS). If we need to compile it, we can use an `@nx/*` plugin/executor to automate this process. Note that Nx 24 was just released and removes all/most executors, replacing them with inferred task plugins. Read its docs and README on building, consuming, and customizing/theming it." The user then pointed at https://nx.dev/blog/look-mum-no-executors. The orchestrator read it on 2026-10-01: the post (dated 2026-09-29) says Nx v24 "ships in a few weeks", and npm's `latest` is still 23.2.1. v24 removes the deprecated built-in executors, among them `@nx/vite:*`, `@nx/vitest:test`, `@nx/storybook:*`, `@nx/playwright:playwright`, `@nx/eslint:lint`, and `@nx/jest:jest`, in favour of inferred-task plugins. It keeps `nx:run-commands`, the `@nx/js` build executors, `@nx/esbuild:esbuild`, and every `@nx/angular` executor. So the specs plan on inferred tasks for testing and linting, and [Decide: which Yeti version the specs target, and how the package tracks it](issues/12-decide-yeti-version-policy.md) chooses how Yeti gets built, from what [Prototype: building, consuming, and theming Yeti from a pinned commit with Nx](issues/22-prototype-building-and-consuming-yeti-with-nx.md) measured. Asked about trying Nx 24 and whether 23.3.0-beta.7 becomes it, the orchestrator found on 2026-10-01 that it does not. Nx 21, 22, and 23 each began their own `X.0.0-beta.0` line 3 to 13 weeks before release, while the previous major's minor betas shipped as that minor. No 24.x exists on npm. nrwl/nx's `next-major` branch is 0 commits ahead of master, and the removal is in open draft PRs such as #37160 (read on 2026-10-01 from the npm registry's `nx` document and GitHub's compare and pull-request pages). Until `24.0.0-beta.0` appears, prototypes stay on Nx 23.2 and are made v24-ready by construction: `nx g infer-targets`, and no target on v24's removal list. The orchestrator recommended this plan, and the user approved it, verbatim: "41. Approve recommendation." So it is a ruling.
- Accessibility and parity ledger: "36. Every accessibility/browser spec feature (including WHATWG, WAI-ARIA, WCAG, ARIA APG, and so on) added that isn't supported by Yeti itself must be documented in a ledger or something like that, for example to keep track of which accessibilty checks that is compliant because of ngx-yeti, not because of Yeti itself. The same goes for features added inspired by or for feature parity/overlap with Angular Aria/CDK/Material." The bundle keeps `ledger.md`; every spec adds its rows, and [Decide: the building-blocks map for every ngx-yeti item](issues/25-decide-building-blocks-map.md) sets its format.
- Angular Aria and CDK first: "37. Make sure we utilize Angular Aria and CDK where possible to replace Yeti's JavaScript modules and comply with accessibility standards and best practices."
- Building-blocks audit: "38. Make a building blocks audit for every component going into ngx-yeti like we did for Foundation for Sites v6.9 components going into ngx-foundation-sites." [Decide: the building-blocks map for every ngx-yeti item](issues/25-decide-building-blocks-map.md) is that audit.
- Zoneless: "43. All specs must support zoneless." Every directive, component, and service works under zoneless change detection, and each spec's tests run zoneless. [Prototype: Yeti under SSR, hydration, `@defer`, event replay, and `animate.enter` and `animate.leave`](issues/18-prototype-yeti-rendering-modes.md) found that a plain field written from a Yeti event listener does not refresh the view zoneless, while a signal does.
- Upstream bugs: "44. Keep a ledger of upstream bugs found and whether they have been verified and have a minimal reproducible example. Accessibility issues go in the accessibility ledger." The bundle keeps [upstream-bugs.md](upstream-bugs.md) for Yeti, Angular, and other upstreams, and `ledger.md` holds accessibility issues. No upstream report is filed without the user's confirmation.
- `data-*` attributes: "42. Audit Yeti's `data-*` attributes and determine how each will be mapped/managed by ngx-yeti." [Decide: how the package maps each of Yeti's `data-*` attributes](issues/26-decide-yeti-data-attributes-mapping.md) does the audit.
- Package name: "Our new package name, replacing "ngx-foundation-sites" will be "ngx-yeti"". The orchestrator checked on 2026-10-01 that `ngx-yeti` is unclaimed on npm (the registry returns 404). The user also wrote that the old prefix must go: "The project shorthand/prefix should no longer be "nfs" which was short for "ngx-foundation-sites". We need something else. I considered "yeti" but it might clash with the actual Yeti. I'm open to suggestions." The prefix is open until the user chooses; specs and prototypes write `nfs` nowhere new.
- Prefix (2026-10-02): asked where a plain `yeti` prefix would clash, the user approved the orchestrator's recommendation and added a TypeScript rule, verbatim: "Prefix: Approve recommendation. Use an `NgxYeti` TypeScript naming prefix where collisions cannot be avoided." So:
  - `yeti` is used for Angular-side names: selectors (`[yetiCard]`, `<yeti-demo>`), `exportAs`, DI tokens, provider functions (`provideYeti()`), and entry points (`ngx-yeti/card`).
  - `ngx-yeti` is used wherever the package writes into Yeti's runtime namespaces: custom properties (`--ngx-yeti-*`), cascade layers (`@layer ngx-yeti`, after `yeti`), and data attributes (`data-ngx-yeti-*`). The package dispatches no DOM events of its own, because Yeti owns `yeti:*`.
  - TypeScript names take `Yeti` (`YetiCard`), and `NgxYeti` where a `Yeti` name collides with one Yeti's `yeti.d.ts` exports. Five item names collide today: `YetiColumns`, `YetiAttention`, `YetiEnter`, `YetiLift`, and `YetiPrint`. Input value types reuse Yeti's own exported vocabulary types rather than redeclaring them.
  - [Decide: the glossary](issues/10-decide-glossary.md) records the rule.
- Package CSS for accessibility (2026-10-02): asked whether the package may add CSS of its own where Yeti's CSS fails WCAG 2.2 AA (the forced-colours case), the user answered, verbatim: "Accessibility CSS: Yes." This settles the `OPEN FOR HUMAN` item of [Decide: which standing preferences and user rulings carry over](issues/07-decide-inherited-preferences-and-rulings.md) as its option (a). The package adds one small documented rule per gap, in its own `ngx-yeti` layer above Yeti's. Each rule is built from CDK's high-contrast mixin and Material's per-control rules and written against state hooks, not Yeti's internals, and each is a row in [ledger.md](ledger.md).
- Vendoring (2026-10-02): asked whether the licence ruling covers shipping Yeti's built files inside the package, the user answered, verbatim: "Vendoring: Yes, but if possible don't bundle Yeti's CSS in our package. Try to find a way to let the consumer". The message was cut off; the user then completed it, verbatim: "Vendoring: Try to find a way to let the consumer bring a build." So redistributing Yeti's files is allowed, but the package looks for a way to let the consumer bring their own build of Yeti, rather than bundling Yeti's CSS. [Decide: how component styles load and unload](issues/13-decide-style-loading.md) and ADR 0006 apply it.
- Pin moves that change only unfrozen defaults (2026-10-02): asked whether such a move waits for an Angular major, the user chose "(a) Any release (Recommended)". It may land in any release, with a changelog entry naming the visible change ([ADR 0017](adr/0017-release-policy-with-a-pinned-yeti.md)).
- Version format (2026-10-02): the user wrote, verbatim:
  > We will use a prerelease 0.x versioning scheme. Maybe something like the Angular DevKit-inspired version we considered/decided for the ngx-foundation-sites map combined with the Yeti commit SHA we're pinning, for example in the format 0.x.y-<yeti-commit-sha>.

  > Additionally, the N should indicate breaking changes because 2202 indicates the Angular version supported, for example 0.2202.0001+yeti.<sha>, then 0.2202.0002+yeti.<sha> or 0.2202.0100+yeti.<sha> for breaking changes. Is something like this possible?

  > Could we include something like "yeti-7-<sha>", "yeti-7-0-<sha>", or "yeti-70-<sha>"?

  > To clarify, what I want is a prerelease versioning scheme that indicate the Yeti version and commit SHA pinned, the Angular major.minor version supported as well as whether the release contains breaking changes compared to the previous release. If there's a format that supports a conventional semver prerelease scheme for indicating breaking changes, let me know.

  Shown that semver has no breaking-change convention for prerelease tags and forbids leading zeros (`0.2202.0001` is invalid), the user chose "Breaking in minor + build metadata (Recommended)". The format is `0.<Angular major><Angular minor, two digits><breaking counter, two digits>.<patch>+yeti.<Yeti version>.<Yeti commit SHA>`, for example `0.220200.0+yeti.7.0.0-alpha.0.f52d1e8`. A breaking release bumps the counter, `^0.220200.0` does not match `0.220201.0`, and everything else bumps the patch. The 0.x major marks the package as a prerelease (semver item 4). [ADR 0017](adr/0017-release-policy-with-a-pinned-yeti.md) records it, and [Research: whether the npm registry keeps a version's build metadata](issues/28-research-npm-build-metadata.md) checks the `+` suffix before the first publish.

### Inherited preferences and rulings (decided 2026-10-01, [Decide: which standing preferences and user rulings carry over](issues/07-decide-inherited-preferences-and-rulings.md))

Each record below was triaged from `.scratch/next-foundation-specs/`; that bundle binds nothing, and these lines are what binds. The ticket's table holds the per-record reason and the nine abandoned records. Where a line adapts a user ruling, the ruling's own words are quoted and the adaptation is this map's, not the user's.

- **Directives first.** Every Yeti item is attribute directives on the markup the consumer writes. A component only where a part needs generated structure, or where a `styleUrl` is what makes lazy styles meet the requirements under the user's standing ruling 28 ([ADR 0003](adr/0003-directives-set-yetis-class-attributes-and-markers.md); adapted from the old [ADR 0001](../next-foundation-specs/adr/0001-directive-first-with-named-exceptions.md)).
- **Composition over subclassing.** The package reuses and extends behaviour through `hostDirectives` and directives placed beside each other, and never asks a consumer to extend a package class (the user's rule, 2026-09-27, carried over as it reads).
- **Implementation order.** Native platform feature, then `@angular/aria`, then `@angular/cdk`, then custom Angular. Each spec says which level it stopped at and why. Most Yeti items stop at level 1, because Yeti is platform-first; the user's standing ruling 37 sets levels 2 and 3 for what the platform leaves. Where this repository's `AGENTS.md` puts `@angular/aria` first, this order wins: replacing a working native element with an Aria pattern would change Yeti's semantics.
- **The contract the package manages.** One class per item, bound as a static host class; every `data-*` attribute and marker set from a typed input; every `yeti:*` event an `output()`, because a template cannot bind a colon-named event; state left native, except state that changes before or after hydration, which is Angular's; and the platform's opening attributes (`popovertarget`, `commandfor`, `command`, `popover`) rendered with generated ids so they work before any script. A consumer writes elements and directive attributes, and no Yeti class or attribute ([ADR 0003](adr/0003-directives-set-yetis-class-attributes-and-markers.md); adapted from the old [ADR 0039](../next-foundation-specs/adr/0039-directives-manage-every-foundation-class.md), the user's class rule of 2026-09-27).
- **Typed values.** Each input's type is a closed union of its vocabulary's values, from Yeti's frozen `schema/vocabulary.json`; a misspelt value fails to compile. No registry, no declaration merging, no generator, no sync check: Yeti has no setting that generates a value ([ADR 0005](adr/0005-closed-unions-from-yetis-vocabularies.md); adapted from the old [ADR 0040](../next-foundation-specs/adr/0040-variant-input-types.md)).
- **Input naming.** From Yeti's attribute and marker names in camelCase (`data-variant` to `variant`). An input named like an HTML presentational attribute keeps that name and its directive owns what the static attribute renders, stated per spec as output, removed, insertion, or inert (carried over from [ticket 139](../next-foundation-specs/issues/139-decide-inputs-named-like-presentational-attributes.md)). Every directive and component has an `exportAs` (the user's ruling, 2026-09-29, carried over). A class-name prefix and the camelCase `...Token` form for injection tokens carry; the prefix itself is set with the glossary.
- **State and reactivity.** Signals for state, `model()` for two-way state, `linkedSignal` for derived-but-writable, OnPush, zoneless-safe, SSR-safe.
- **Tokens.** Yeti's `--yeti-*` tokens are a consumer stylesheet surface, not a per-component input contract: each spec names the tokens its item reads and how a consumer sets them, and the package offers no input per token and no theme provider. Two exceptions: a token a Yeti module writes as state becomes a host style binding from a `computed` (`--yeti-range-value`), and a spec may expose one derived token as an input where its API needs it, saying why. The package does not ship or wrap Yeti's theme files ([ADR 0004](adr/0004-yeti-tokens-are-a-consumer-stylesheet-surface.md); adapted from the old map's runtime-theming exclusion).
- **Accessibility.** Every directive and component meets WCAG 2.2 AA, follows the matching WAI-ARIA APG pattern, and is axe-clean on the stated rule set; never a recommendation. Each spec names the criteria its item touches and how each is met. Every gap the package closes that Yeti leaves open is a row in `ledger.md` (the user's standing ruling 36). How far the package may add CSS of its own where Yeti's CSS is what fails is `OPEN FOR HUMAN` (ticket 07, `### Triage`).
- **Animation.** No `@angular/animations` and no JavaScript-timed animation. Yeti's own CSS transitions, `@starting-style`, and `enter` utility do the work; `animate.enter` and `animate.leave` where an element enters or leaves the DOM, in the class form only, because a function-form `(animate.leave)` listener anywhere keeps a component's styles loaded (angular/angular#66244).
- **Rendering modes.** Every directive and component is specified for `@defer` with its hydrate triggers, SSR, prerendering, full and incremental hydration, event replay, and `withI18nSupport()`. Each spec states its server output, what it must not touch before hydration, which events replay, and how it behaves in a deferred and a `hydrate never` block.
- **Lazy styles.** A library-wide requirement, carried over from the user's ruling of 2026-10-01: a first-milestone directive or component loads its item's styles when its first instance renders and unloads them after the last. The unit is one of Yeti's 49 part files rather than a Sass export mixin's output, and a library `styleUrl` is no longer ruled out. The mechanism, the exceptions, and what the consumer writes are [Decide: how component styles load and unload](issues/13-decide-style-loading.md)'s.
- **The always-loaded group.** Yeti's layer statement, tokens, reset, base files, and `layouts/attributes.css` are loaded globally and are not specified: they style bare HTML and declare every token, and 40 of the 49 part files render differently without them. No directive manages them; a spec that relies on one of their rules cites it.
- **Testing.** Four layers: story play functions with interaction tests, a browser-level layer, a node-level layer with the SSR smoke, and Playwright e2e. Three additions for Yeti, which the testing decision places: Yeti's own `bin/validate.js` and `bin/frozen.js` against the pinned commit, an attribute-and-value check against the built manifest, and testing at the target's floor browsers ([Research: testing at the browser floor](issues/27-research-testing-at-the-browser-floor.md)).
- **Release policy.** The Angular devkit's version scheme, `0.<Angular major><Angular minor, two digits>.<patch>`; breaking changes, removals, and consumer-visible platform upgrades only when the Angular major changes; one Angular major of deprecation before a removal, with `@deprecated`, a changelog entry, and a migration where one can be written; migrations as Nx migrations first, reused for `ng update` (the user's ruling, 2026-09-28, carried over). What a Yeti pin move does to the version is settled by [Decide: which ADRs carry over](issues/08-decide-inherited-adrs.md) and [Decide: which Yeti version the specs target](issues/12-decide-yeti-version-policy.md). The version format was replaced on 2026-10-02 (Standing rulings, Version format).
- **Milestones.** Every check is specified but planned and implemented in a later milestone of the implementing repository; no other spec depends on one, names one, or links to a deferred spec, and each states the rule a check enforced as documented usage. The user's reasons, 2026-09-29: "all checks should be deferred to a later milestone because at the core of it, this is an issue Angular should correct, not 3rd-party Angular component libraries", and "I want to keep the initial milestone simpler and smaller in scope". Entry points export directive classes and no import arrays (the user's ruling, 2026-09-28). Which checks Yeti leaves worth deferring at all is settled by [ticket 08](issues/08-decide-inherited-adrs.md) and [ticket 09](issues/09-decide-inherited-principles-and-building-blocks.md).
- **Scope shape.** Being CSS-only never excludes an item: an Angular directive is the Angular-native way to use a UI component even when all it adds is a class, typed inputs, and generated ids (the user's ruling, 2026-09-27). One spec per item of Yeti's own manifest, which is also its docs page; [Decide: the spec list](issues/11-decide-spec-list.md) reconciles the 49 items against 50 docs pages and 72 sitemap URLs. An item the first milestone leaves out relies on the consumer's loaded stylesheet rather than on a spec, in the shape of the user's later-milestone ruling of 2026-09-30. A mechanism Yeti itself has replaced is out of scope, as the Float and Flex Grids were for Foundation.
- **Design criteria.** Each directive or component is the best combination of: Yeti's CSS, attribute contract, and manifest (its `a11y` and `support` blocks included); the APG, WAI-ARIA, WHATWG HTML, and platform features; Angular Aria and CDK; Material-equivalent accessibility and API shape for the nearest Material component; and modern DI patterns.
- **Spec shape.** A `/to-spec` spec whose Implementation Decisions and Further Notes carry the API-design subsections, with two substitutions: the class mapping becomes a contract mapping (class, each attribute and marker with its input and type, each event with its output, each token the spec names), and the Sass subsection becomes the part file and how it loads. The `foundation-api-design` skill is one input the user called an early sketch; this bundle's ADRs and the user's rulings outrank it.
- **Precedence.** `architecture-guide.md` restates these records as testable principles and ranks below all of them; a conflict is settled by the record, never by the guide. This repository's `AGENTS.md` is one design-criteria input, neither a source nor a constraint, and its component code is not a source either. Spec Kit is not used.

## Decisions so far

- [Decide: whether Yeti's licence and readiness allow this package](issues/15-decide-yeti-licence-and-readiness.md) -- the user ruled FSL-1.1-MIT compatible with the package as a free and open-source MIT project ([ADR 0001](adr/0001-yeti-licence-compatible-with-mit-package.md)); readiness moved to the Yeti version decision.
- [Research: Foundation's `llms.txt` and `llms-full.txt` as sources for this map](issues/14-research-foundationcss-llms-txt.md) -- Yeti's own `/yeti/llms.txt` and `/yeti/llms-full.txt` match the repository's generated copies and list all 49 items; the domain-root pair covers other tools, and the MCP server the README mentions does not exist.
- [Research: inventory of Yeti's components, layouts, recipes, utilities, and contract](issues/02-research-yeti-inventory.md) -- 49 items (17 layouts, 3 recipes, 22 components, 7 utilities), 297 tokens, and 10 optional modules; eight old specs have no counterpart per the migration guide, and 16 Yeti items are new.
- [Research: Yeti's JavaScript modules and what Angular adds](issues/03-research-yeti-javascript-and-angular.md) -- 760 lines across ten optional modules, and most items need types only; a template cannot bind a `yeti:`-prefixed event, and `validate.js` never runs on a form under an Angular form directive.
- [Research: Angular 22's browser baseline against what Yeti expects](issues/01-research-browser-baseline-vs-yeti.md) -- Angular 22 implies Chrome, Edge, and Firefox 119 and Safari 17; Yeti implies Chrome and Edge 141, Firefox 145, and Safari 26.2. 33 Yeti features fall outside Angular's set and 27 are unguarded, `light-dark()` and invoker commands among them (per web-features data).
- [Research: Yeti's styling model, and loading component styles lazily](issues/04-research-yeti-styles-and-lazy-loading.md) -- on static light-scheme pages, each of the 49 part files loads alone beside Yeti's always-loaded group (one earlier difference on the demo pages was not reproduced or explained). Most of the old map's constraints disappear; Angular's leave-animation guard remains, and the library's own `styleUrl` per part passed except for that leak.
- [Research: binding Yeti's `yeti:*` events in Angular templates](issues/16-research-yeti-events-in-angular-templates.md) -- the compiler rejects `(yeti:close)`; an aliasing event manager plugin, a re-dispatcher, and a directive `output()` all work (measured in Chromium only), with different typing and upkeep, and none replays events.
- [Research: what `validate.js` does, and replacing it with Angular Signal Forms](issues/19-research-yeti-validate-and-signal-forms.md) -- `validate.js` only surfaces the browser's own constraint validation; under `FormRoot` or reactive forms it never runs, and with a bare `[formField]` it runs only on constraints the DOM knows (measured in three engines). Angular sets neither `aria-invalid` nor `aria-describedby`, so the package must.
- [Prototype: Yeti as a dependency from GitHub at a pinned commit](issues/21-prototype-yeti-as-github-dependency.md) -- a plain git dependency installs without `dist/`, because Yeti ignores it and has no `prepare` script; a packed tarball, a submodule, a fetch-and-build script, and a git dependency on a commit that adds `prepare` all pass `npm ci` and `ng build`.
- [Prototype: Yeti's modules in a single-page Angular app](issues/20-prototype-yeti-in-single-page-apps.md) -- all three inferred failures are real in three engines: modules miss every route, bare `#id` links reload the page, and shell overlays stay open across navigation. Owner directives, closing on navigation, and a fragment interceptor fix them.
- [Research: Yeti against WHATWG, WAI-ARIA, the APG, and Angular Aria, CDK, and Material patterns](issues/17-research-yeti-accessibility-and-standards.md) -- axe finds no WCAG 2.2 AA violation on the 49 examples in three engines (five need a manual contrast check), and focus rings are present at every stop, with contrast measured on one control. Eight behaviour deviations, no `forced-colors` support among them, each map to an Angular building block.
- [Prototype: Yeti under SSR, hydration, `@defer`, event replay, and `animate.enter` and `animate.leave`](issues/18-prototype-yeti-rendering-modes.md) -- every item works without JavaScript, but hydration rewrites static attributes over pre-load state, `i18n` components need `withI18nSupport()`, client-rendered `@defer` content misses Yeti's module setup, and `hydrate never` blocks lose their `styleUrl` styles (eight SSR builds, three engines).
- [Prototype: building, consuming, and theming Yeti from a pinned commit with Nx](issues/22-prototype-building-and-consuming-yeti-with-nx.md) -- a small local `createNodes` plugin running Yeti's `bin/build.js` through `nx:run-commands` caches `dist/` on Nx 23.2.1, with no target v24 removes; theming is tokens on `:root`.
- [Research: Yeti's cascade layers and stylesheet order, for lazy loading](issues/23-research-yeti-layers-and-import-order.md) -- `layers.css` fixes Yeti's layer order once, and every insertion method matched full Yeti in three engines through unload and reload, apart from one order-dependent tie and stale computed styles on 2 to 7 pages in Chromium and WebKit (engine invalidation, inferred).
- [Prototype: the package beside Tailwind v4 in one Angular application](issues/24-prototype-ngx-yeti-with-tailwind-v4.md) -- measured in three engines: with Tailwind first, Yeti beats every utility; with Yeti first, Tailwind's preflight beats Yeti. One shared order, `@layer theme, base, yeti, components, utilities;`, lets utilities win over Yeti and Yeti over preflight, or the preflight can be left out. Either needs `@source not inline('container');`, because Tailwind otherwise generates `.container` over Yeti's container. It is set in the consumer's global stylesheet, which component styles cannot do. Lazy loading and unloading behaved in every order.
- [Decide: the browser target](issues/06-decide-browser-target.md) -- the user chose Yeti's Baseline 2025 (Chrome and Edge 141, Firefox 145, Safari 26.2) over the lowest common set, which differed only in Chrome, Edge, and Firefox ([ADR 0002](adr/0002-browser-target-baseline-2025.md)).
- [Task: carry the old map's Yeti findings into this bundle](issues/05-task-carry-yeti-findings-from-old-map.md) -- the old map's Yeti research is copied to [research/yeti-foundation-7.md](research/yeti-foundation-7.md), with its origin, and the five tickets it partly answers have a note; this bundle's later research holds where they differ.
- [Decide: which standing preferences and user rulings carry over](issues/07-decide-inherited-preferences-and-rulings.md) -- of 42 old preferences and rulings, 14 carry over, 19 are adapted, and 9 are abandoned; the kept ones are in the Notes. Directives set Yeti's class, attributes, and markers from closed-union inputs ([ADR 0003](adr/0003-directives-set-yetis-class-attributes-and-markers.md), [ADR 0005](adr/0005-closed-unions-from-yetis-vocabularies.md)), and tokens stay a consumer stylesheet surface ([ADR 0004](adr/0004-yeti-tokens-are-a-consumer-stylesheet-surface.md)). Whether the package may add CSS where Yeti's fails WCAG 2.2 AA is OPEN FOR HUMAN.
- [Decide: which Yeti version the specs target, and how the package tracks it](issues/12-decide-yeti-version-policy.md) -- the first pin is `f52d1e8b9`; it moves only for a reason (an upstream fix, a needed addition, a beta tag or npm release), behind a gate of `bin/frozen.js`, a diff of what it skips, and the package's tests. The workspace builds Yeti's source at the pin with a cached Nx task, and the published package ships Yeti's built files with its licence ([ADR 0006](adr/0006-yeti-pinned-develop-commit-vendored-and-gated.md)). The user then allowed that redistribution but asked for a way to let the consumer bring their own build of Yeti (Standing rulings, Vendoring).
- [Research: testing at the browser floor (Chrome and Edge 141, Firefox 145, Safari 26.2)](issues/27-research-testing-at-the-browser-floor.md) -- Playwright 1.56.x bundles Chromium 141 at the floor (checked by the orchestrator), and runs Vitest 4.1 browser mode. No release bundles Firefox 145, and no Playwright WebKit matches Safari 26.2. Chrome for Testing 141 works through `executablePath`. Stock Firefox 145 works only through Playwright 1.57's `moz-firefox` channel, or through the WebdriverIO provider, which also pinned Chrome 141 but ignored an Edge pin. A Yeti dialog probe passed at every floor engine and failed below it. GitHub's macOS images carry Safari 26.5 to 27.0, not 26.2. None of nine projects runs a CI matrix at its floor; they hold it with static checks.
- [Decide: the spec list](issues/11-decide-spec-list.md) -- 53 specs: one per item of Yeti's manifest (49), named as Yeti names them, and four shared-utility specs (navigation-close, fragment-links, events, generated-ids). All three of the user's sources list the same 49 items; the extra docs page is the tokens page, and the extra sitemap URLs are guides, examples, and the root. Every item is directives except `demo`, a component.
- [Decide: which ADRs carry over](issues/08-decide-inherited-adrs.md) -- of the old map's 46 ADRs, 24 are adapted and 22 abandoned, none carried over as is. ADRs 0010 to 0018 set class-form animation, the rendering-modes contract, naming (with the user's prefix ruling), parts naming targets by reference, the test layers, WCAG 2.2 AA enforcement, light dismiss, the release policy under a pinned Yeti, and no import arrays. ADRs 0019 to 0025 make `nav` and `dropdown` disclosure navigation rather than Aria menus, take field validity from Angular forms, make the dialog a directive on the native `<dialog>`, give the button no listeners, split fragment links by who owns the link, keep carousel slides non-`inert` in server HTML, and have the toc find its headings from its links. The user ruled the one open item: a pin move that changes only unfrozen defaults may ship in any release.
- [Decide: which architecture principles and building-blocks rules carry over](issues/09-decide-inherited-principles-and-building-blocks.md) -- all 26 old principles carry over (10) or are adapted (16), with four new ones in [architecture-guide.md](architecture-guide.md). The cross-cutting part of [building-blocks.md](building-blocks.md) is written. All five old shared utilities are abandoned, because the platform replaces them: invoker commands and `popover` for Triggers, `popover` with Yeti's guarded anchor positioning for the Anchored pane, and container queries for the Breakpoint service. The package replaces all of Yeti's optional modules ([ADR 0040](adr/0040-package-replaces-yetis-optional-modules.md)).
- [Decide: the glossary](issues/10-decide-glossary.md) -- [CONTEXT.md](CONTEXT.md) defines 79 terms, each with an origin and an `_Avoid_` list: 26 in Yeti's own words, 13 carried over, 17 adapted or renamed, and the rest new to this map. Overloaded words are settled: an **Item** is any of the 49 manifest entries, a **Component item** is Yeti's `component` kind, and an **Angular component** is Angular's. **Module** means only Yeti's optional JavaScript files. "Family" is retired, and the loading unit is the **Part file**. [ADR 0080](adr/0080-yeti-prefix-ngx-yeti-runtime-names-ngxyeti-on-collision.md) records the prefix ruling with its five `NgxYeti` names. The `pfx` stand-in is replaced in the architecture guide and the building-blocks map.
- [Decide: how the package maps each of Yeti's `data-*` attributes](issues/26-decide-yeti-data-attributes-mapping.md) -- 168 rows, each a declaration in the manifest (132 attributes, 36 markers). By [ADR 0070](adr/0070-where-a-yeti-attribute-sits-decides-its-mapping.md), where a declaration sits decides its mapping. An attribute of the item's own element is a typed input on the root directive (127 rows). A child marker is an input on the child directive (19). A part marker is the part directive's static attribute (11). An any-element marker or a utility attribute is a selector-named input (10). `enter`'s `data-once` is the only state Angular owns. Nothing is left to the consumer. One item is OPEN FOR HUMAN: whether those 10 inputs take the selector's name (`yetiPaint="primary"`) or the input-naming record's (`paint`).
- [Research: whether the npm registry keeps a version's build metadata](issues/28-research-npm-build-metadata.md) -- no. `npm publish` runs `semver.clean`, so `0.220200.0+yeti.7.0.0-alpha.0.f52d1e8` is published as `0.220200.0` (read, and measured with `npm publish --dry-run`). Only the tarball's own `package.json` keeps the suffix; `npm view`, the lockfile, and `npm ls` show the core version. `ng update` and `nx migrate` compare with semver, which ignores build metadata (read). A prerelease tag survives publish, and `npm publish --tag latest` accepts one (measured by the orchestrator, dry run). The live registry was not queried.
