# Vitest browser mode stays the browser-level layer; Playwright component tests enter only as the e2e layer's way of opening stories

The map required a working Playwright component test solution for Angular 22.2 and, if one was found, a decision on whether it replaces Vitest Browser for browser-level tests. The [Prototype: Playwright component tests mounting CSF stories from @storybook/angular-vite](../issues/40-playwright-component-testing-prototype.md) found one: Playwright 1.63's built-in `mount(storyId, props?)` fixture over the static `@storybook/angular-vite` build, with about 150 lines of project-owned gallery code, mounts the same CSF stories in Chromium, Firefox, and WebKit; none of the three community adapter packages works next to Playwright 1.63. We decided that Playwright component tests do not replace Vitest browser mode, and do not become a fifth layer either. The four layers of the map's Testing rule stay, with one stack each: story play functions run through `@storybook/addon-vitest` (`nx test-storybook`); the browser-level layer is Vitest browser mode under the Angular unit-test builder (`nx test`, Chromium headless, TestBed over a bare test host component, no stories mounted); the node-level layer is the same `nx test` run, holding pure-logic specs and the `<name>.ssr.spec.ts` server-render smoke through one shared `renderServer()` helper, with a separate `test-node` project only for a server path that depends on the DOM adapter; and the Playwright e2e layer runs against two served targets, the static Storybook build (opened through `mount(storyId)` with `embed=true`, so the story's play function does not run again) and a prerendered fixture app with one route per plugin. Why: the two stacks answer different questions and neither can do the other's job. From Node, a Playwright test sees only the page: no TestBed, no DI override, no `DeferBlockBehavior.Manual`, no `Directionality` double, no dispatch of a replay-shaped event, no dev-mode warning capture, no coverage (`research/playwright-component-testing.md` section 6). What Playwright adds, real engines other than Chromium, real input events, and a whole browser context, is exactly what the e2e layer already provides, and it comes at a mount cost of one navigation plus one Storybook boot (0.5 to 1 s in Chromium, 3 to 21 s in the emulated Firefox and WebKit here; 23 tests took 2 min 29 s in three engines against 6.8 s for the Vitest Browser run of the same stories). Putting the mount fixture inside the e2e layer keeps the 26 specs' test tables the same whether or not the gallery survives, because e2e tests address stories by Story id and assert through locators, and the gallery is one file.

## Considered options

- Playwright component tests replace Vitest browser mode as the browser-level layer: rejected. Every TestBed-only case in the published specs (the Breakpoint service's fake `MediaMatcher` and `TransferState` seeding, the Triggers' `skipSelf` resolution and replay-safe dispatch, the Button's dev-mode warnings and RouterLink provider) would need a story-level equivalent that Storybook args cannot express, and the run would be ten times slower per test.
- Both, as separate layers (a fifth "component test" layer next to e2e): rejected. Its content would be either a copy of a play function (already run by layer 1 through the same Storybook build) or an engine-specific assertion that belongs in e2e. A layer with no case of its own is a layer nobody fills.
- Vitest Browser only, with Playwright e2e opening stories by URL (`/iframe.html?id=<story-id>&viewMode=story`, the tooling baseline's original layer 3): the fallback, not the choice. It stays one mechanical rewrite away: replace `await mount(id, props)` with `page.goto` on the public URL (`&args=` for props) and drop `update()`. It is what the library falls back to if the gallery can no longer depend on Storybook preview internals (`__STORYBOOK_PREVIEW__`, `storeInitializationPromise`, `teardownRender`, and the channel event names). The gallery on those internals is adopted (triage in the [Decide the browser testing stack: Playwright component tests, Vitest Browser, or both](../issues/41-browser-testing-stack-decision.md) ticket); the fallback is `page.goto` on the public iframe URL, and asking Storybook for a public API stays human-only.
- Portable stories (`composeStory`) inside the browser-level layer, so Vitest Browser specs mount CSF stories: rejected as a rule. It works under the builder with three workarounds (`STORYBOOK_ANGULAR_OPTIONS`, CSS module typings, a type cast over the untyped `composeStory`), but a spec that only replays a play function duplicates layer 1, and the interaction cases belong to the story.
- A jsdom default for `nx test`, with `--browsers` only for browser-level specs: rejected. The directives are DOM, focus, and ARIA behaviour that jsdom does not implement, and the server-render smoke passes in browser mode too, so one run in Chromium covers layers 2 and 3.

## Consequences

- Each spec's Testing Decisions names the same four layers with the wording fixed in the [Decide the browser testing stack: Playwright component tests, Vitest Browser, or both](../issues/41-browser-testing-stack-decision.md) answer; the consistency review rewrites the stack-neutral specs mechanically.
- Play functions are the single home of interaction tests. Layer 4's Storybook half never re-runs them (`embed=true`) and asserts only what needs a real engine, real key presses, or a browser context (viewport, media emulation, history, storage, reload) on the same Story ids. Layer 2 mounts no story and runs no axe.
- Axe runs per story through `@storybook/addon-a11y` with `parameters.a11y.test = 'error'` in layer 1, on one rule set for every layer that runs axe: `runOnly` tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, `best-practice` (the user's WCAG 2.2 AA rule; naming `wcag22aa` is what turns on axe-core's `target-size` rule, which ships disabled). Layer 1 in CI is the enforcing gate: every story renders Foundation's CSS as the consumer compiles it, so a Foundation default that fails 2.2 AA fails the story that shows it before merge, and the answer is a settings override or a library rule, never a silenced rule. The same addon report reaches layer 4 through `storyFinished`, so a violation rejects `mount()`; `@axe-core/playwright` with the same tags runs only on states no play function reaches and on the fixture app's JavaScript-disabled page.
- Server HTML is asserted in layer 3; a replay-shaped event in layer 2; real hydration, event replay with the main bundle held back, hydrate triggers, and first paint without JavaScript in layer 4's fixture half.
- The one file on Storybook preview internals, `.storybook/playwright-gallery.ts` plus the `previewHead` stub in `main.ts`, lives in the library's Storybook directory and is owned by the e2e project's tests. A Storybook change breaks that file, not the specs.
- The static Storybook build runs Angular in production mode, so layer 4 sees no development-mode checks; those stay in layers 1 and 2.
- Every Playwright browser on the development machine is an x64 binary under Windows-on-Arm emulation; the three-engine runs are for CI, and `-- --project=chromium` is the local default. Linux CI and real Safari are unproven until the new repository's first CI run.
