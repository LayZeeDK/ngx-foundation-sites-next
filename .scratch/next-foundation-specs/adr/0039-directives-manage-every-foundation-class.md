# Directives manage every Foundation and library class; the consumer writes none

The user ruled on 2026-09-27 that being CSS-only never excludes a Foundation for Sites component or variant from scope, because an Angular directive or component is the Angular-native way to use a UI component even when all it does is add a CSS class. Answering the questions of [Triage the out-of-scope Foundation components and variants](../issues/79-triage-out-of-scope-components-and-variants.md) the same day, the user set the rule this record carries: "Generally, consumers should not write any CSS classes for any of our components/directives. All Foundation for Sites and NFS classes are managed by the Angular components/directives." Until then the consumer wrote Foundation's markup, classes included, and a directive added behaviour to it ([ADR 0001](0001-directive-first-with-named-exceptions.md)); Variant classes stayed consumer-written ([ADR 0010](0010-button-variant-classes-stay-classes.md)); and the CSS-only components other than Button, the layout systems, and the utility families had no directives at all.

We decided the class rule: consumers write Foundation's elements and the library's directive attributes, and no Foundation or NFS class. Every Structural class is bound by its directive, one attribute directive per Structural class, with a component only where Foundation generates structure (ADR 0001's exceptions); every Variant class is set by a typed input, typed as [Decide: typed Variant inputs over open Sass maps](../issues/81-decide-typed-variant-inputs-open-sass-maps.md) rules; every State class is a host binding. The rule covers every Plugin, every CSS-only component, Foundation's layout systems (XY Grid, and the legacy Float Grid and Flex Grid), and its utility families (Prototyping Utilities, Flexbox Utilities, Visibility Classes, Float Classes, Typography Helpers), each of which gets directives. Each directive also owns the ARIA, `type` default, or development-mode and compile-time check that its documented markup lacks for WCAG 2.2 AA ([ADR 0022](0022-wcag-2-2-aa-enforcement.md)), because Foundation's own examples fail it ([research/out-of-scope-triage.md](../research/out-of-scope-triage.md)): every Progress Bar example has no accessible name (axe `aria-progressbar-name`), the Input Group example has an unlabelled field (axe `label`), the docs menu icon has no name, the Switch off track is about 1.6:1 on white, and the Badge and Label `alert` colour is 4.499:1 with white. Foundation's base element styles (Global Styles, Typography Base) and every element Foundation styles only by tag (`table` itself, `select`, checkboxes, radios, text inputs, bare `fieldset` and `legend`, native `<progress>` and `<meter>`) get no directive: there is no class to manage, and the spec of the docs page that shows such an element documents it.

## Considered options

- Markup only: the CSS-only components, layout systems, and utility families keep Foundation's markup with no directive, as the map's Out of scope held for every CSS-only component except Button until 2026-09-27. Overruled by the user: being CSS-only is no reason to leave a component without its Angular-native form.
- Consumer-written Variant classes, with an input only where the directive's behaviour depends on the state (ADR 0010), which the triage's judge recommended for its single spelling, its lack of a collision rule against a static class, and its lack of a union type claiming to list an open Sass map; and its narrower form, typed inputs only for the closed sets Foundation's Sass fixes (`stacked`, `stack`, `vertical`, `full`, `hollow`). Rejected by the user, who chose typed inputs for every family: sizes, colours, fills, and every modifier. ADR 0010's objections to typed inputs (open value sets, custom palette colours and sizes, classes that exist only under a Sass setting such as `.solid`, runtime defaults that could fight the Sass settings) pass to [Decide: typed Variant inputs over open Sass maps](../issues/81-decide-typed-variant-inputs-open-sass-maps.md), with consumer-side TypeScript `namespace` or `module` augmentation (declaration merging) ruled out by the user.
- No directives for the layout systems and utility families, recorded as Utility classes the consumer writes: the triage's recommendation, because no directive there adds a role, a name, a state, or a check, their classes are generated per breakpoint and column count, and typed source-ordering and hiding inputs would make a 1.3.2 hazard look supported. Overruled by the user: they get directives, the legacy Float Grid and Flex Grid included (legacy since Foundation 6.4 and disabled by default), and the ordering hazard (1.3.2, 2.4.3) passes to their specs.

## Consequences

- Every one of the 26 published specs changes its consumer markup and is re-run under the rule by a ticket of its own, from [Re-run: Accordion spec under the class rule](../issues/107-rerun-accordion-class-rule.md) to [Re-run: Nested menu (shared utility) spec under the class rule](../issues/132-rerun-nested-menu-class-rule.md), each waiting on [Decide: typed Variant inputs over open Sass maps](../issues/81-decide-typed-variant-inputs-open-sass-maps.md). The Structural classes those specs left as markup because they carry no behaviour (the Orbit wrapper, controls, figure, image, and caption; `.slider-fill`; `.off-canvas-wrapper`; `.submenu-toggle-text`; the close buttons of Off-canvas, Reveal, and Toggler) gain directives there.
- One spec per Foundation docs page: 25 new spec tickets, from [Spec: Button Group](../issues/82-spec-button-group.md) to [Spec: Typography Helpers](../issues/106-spec-typography-helpers.md), bring the destination to 51 specs. [Consistency review: the class-rule wave](../issues/133-consistency-review-class-rule-wave.md) checks that no consumer-written Foundation or NFS class remains in any spec's examples.
- Consumer markup keeps the element structure of Foundation's docs and carries directive attributes where the docs carry classes: `<div class="reveal">` becomes `<dialog nfsReveal>`. Host bindings render on the server (building-blocks 1.11, decision 1), so the server HTML still carries every Foundation class, and Foundation's CSS styles the first paint and every dehydrated block.
- Each spec's CSS class mapping (building-blocks 1.14) has a row for every Structural class with the directive that binds it, every Variant class with its typed input, and every State class with its host binding. Stories follow the rule ([storybook-conventions.md](../storybook-conventions.md)).
- A CSS-only component, layout system, or utility family that needs custom CSS or compile-time checks gets an `nfs-<entry point>` Library mixin ([ADR 0012](0012-sass-packaging.md), dated note).
- Class names passed as input values (user decision, 2026-09-27): no Foundation or NFS class name appears in consumer code, not even as an input value: an input that selects a library class takes a typed name (a Motion input takes `'fade-in'`, never `'nfs-fade-in'`), and the directive maps it to its class, applying it with `animate.enter` and `animate.leave` where the element enters or leaves the DOM and with a State class on a persistent element otherwise (building-blocks 1.6); inputs that apply the consumer's own classes stay (the Toggler's class mode toggling an application class, the Tooltip's `templateClasses` for application classes), because the rule is about the library's classes. The Motion class inputs (`animationIn`, `animationOut`, `animate`), the Toggler's class-mode `toggler`, and the Tooltip's `templateClasses` are revised by their specs' re-run tickets under this rule.
- ADR 0001's directive-first rule and its three component exceptions stand; its consequence that consumers write Foundation's markup carries a dated qualifier. ADR 0010 is superseded.
