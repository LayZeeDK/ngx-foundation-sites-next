# The Nested menu root commits every Menu mode swap in its own render callback, and ResponsiveMenu starts every instance from the Server breakpoint's mode

The [Spec: Nested menu (shared utility)](../issues/56-spec-nested-menu.md) lets the root's `mode` follow the function ResponsiveMenu passes to `drive()` directly, so a breakpoint change re-renders every class map in change detection, and its swap rule then prunes the Open path in a later `afterRenderEffect` that reads `document.activeElement`. For one change-detection pass the page therefore shows the new mode over submenus the swap is about to close; in the case the [Prototype: Nested menu directive family with breakpoint mode switching](../issues/50-prototype-nested-menu.md) measured as F3 (a dropdown submenu open, focus on its toggle, a swap into drilldown), that pass puts the focused toggle inside an `invisible` level, and without pruning focus fell to `body` in Chromium, Firefox, and WebKit. Whether an engine moves focus off a hidden control within the same task, or only at its next rendering update, is not something the library should depend on, and building-blocks 1.5 names the two safe places to record focus around a swap: the change-detection code that removes nodes, or the render callback that itself commits the swap. [ADR 0014](0014-breakpoint-service-first-render-handoff.md) and [ADR 0032](0032-responsive-accordion-tabs-instance-first-render.md) kept the Breakpoint service's handoff for consumers that "change classes on the same nodes, so their focus survives a first-render change"; the F3 measurement shows a class swap can hide the focused node too, and a swap into dropdown can leave an overlay open from a pre-opened section. We decided that `NfsMenuRoot` keeps the displayed Menu mode separate from the driven one: the displayed `mode` takes the driven function's value on its first read and afterwards changes only in the root's swap `afterRenderEffect`, whose `earlyRead` reads the driven mode, `document.activeElement`, and the DOM order of the open submenus while the old mode's classes are still on the page, and whose `write` sets the displayed mode and applies the pruning together, so no render shows the new mode over an unpruned Open path. And we decided that ResponsiveMenu drives the root with the mode its rules give at the Server breakpoint until its own first render callback, then with the live breakpoint's, so every instance, deferred and client-created ones included, hydrates or first renders as the server would send it and every change of mode, the first included, goes through that one callback. `drive()`'s signature does not change.

## Considered options

- The Nested menu spec as written (mode follows the driven function; pruning in a later callback): rejected, because it relies on engines not moving focus off a control hidden for one pass, and on no earlier `earlyRead` callback forcing style in between, which would also start transitions from the intermediate state.
  - 2026-09-26 (consistency review): the [Prototype: ResponsiveMenu swap committed in the Nested menu root's render callback](../issues/71-prototype-responsive-menu-swap-commit.md) measured the intermediate pass this option produces (case F3: one pass with `drilldown` on the root over the still-open submenu, in all three engines), and focus survived that pass in Chromium, Firefox, and WebKit, even behind an `earlyRead` callback that forces style and layout. The option stays rejected on this record's own ground: the library does not depend on when an engine moves focus off a hidden control. The same prototype confirmed the decision itself, with one correction to the keep rule (entering drilldown closes the submenu whose own row, toggle or Hybrid link, holds focus), now in the Nested menu and Responsive Menu specs.
- The Breakpoint service's handoff for the first render, as ADR 0032 expected for class-swapping consumers: rejected for ResponsiveMenu. An instance first rendered after the service went live (a `@defer (hydrate on ...)` block, a routed layout created after a navigation, an `@if`) would start in the live mode without passing the swap rule, so a pre-opened current section (Foundation's `is-active`, or an `expanded` bound from Router state) would open a dropdown overlay on a desktop page, and deferred blocks would be re-classed during their own hydration.
- Recording the focused control continuously from `focusin`/`focusout` on the root, a host that survives every swap, and restoring it after the swap: not adopted as the design, because recording does not prevent the pass in which the focused control is hidden, and whether an engine fires `focusout` when it moves focus off a hidden control varies. Kept as the named fallback if the prototype shows the commit in one callback missing a focus case.

## Consequences

- A client-created ResponsiveMenu renders twice in its first tick (the Server breakpoint's mode, then the live one); the first is never painted. ADR 0032's note that other consumers keep focus through a first-render class change no longer describes ResponsiveMenu.
- The Nested menu spec's `mode` and `drive()` rows, its swap rule, its render hooks table, and its ResponsiveMenu rendering-modes bullet change; the swap rule also closes every submenu when a swap enters dropdown mode with focus outside the menu.
- Building-blocks 1.11 decision 8 lists ResponsiveMenu, like ResponsiveAccordionTabs, among the plugins whose blocks hydrate as sent.
- A pre-hydration click replays onto a node the swap kept, so it is applied once in the live mode, unlike ResponsiveAccordionTabs, whose swap removes the clicked control.
- 2026-09-28 ([Re-run: Nested menu (shared utility) spec under the class rule](../issues/132-rerun-nested-menu-class-rule.md)): a section open at first paint is now only a bound `expanded`; the static `is-active` seed named in the second considered option is gone (building-blocks 1.4). The option's rejection stands on the `expanded` case.
