# Variant inputs are closed unions over library registries that a declaration file generated from the consumer's Sass extends

[ADR 0039](0039-directives-manage-every-foundation-class.md) has every Variant class set by a typed input, and it passed ADR 0010's objection to that on to a decision. Many Variant names come from Sass settings the consumer changes (palettes, size and ratio maps, `$breakpoint-classes`, counts), so a type the library ships on its own either rejects the names the consumer's Sass adds or accepts typos. The user wants a misspelt palette or size name to fail to compile. The user prefers directive composition over subclassing. On 2026-09-27 the user allowed consumer-side declaration merging of library-declared interfaces once a probe confirmed it, while a tsconfig `paths` remap and anything that writes into `node_modules` stay vetoed.

We decided, through the panel and the second research round in [Decide: typed Variant inputs over open Sass maps](../issues/81-decide-typed-variant-inputs-open-sass-maps.md):
- **Closed types.** Every Variant input's type is closed. A Closed Variant family is Foundation's fixed names, or a boolean whose transform accepts only booleans, the bare attribute, `"true"`, and `"false"`. An Open Variant family is Foundation's default names combined with a Variant registry, through MUI's true/false union (`name: true` adds a name, `name: false` removes a default, and a count's registry holds `count`), chained where Foundation's Sass defaults chain. A Variant registry is an empty interface the library declares once per Sass setting in its primary entry point `ngx-foundation-sites`, such as `NfsButtonPaletteOverrides` for `$button-palette`.
- **The declaration file.** The consumer's Variant declaration file, `src/nfs-variants.d.ts` in each application's own source tree, augments the registries. The library's Nx generator, exposed as an Angular CLI schematic, writes it from the Variant properties in the application's compiled global stylesheet. The Sass stays the source; a hand-written file is supported.
- **Keeping it in step.** An Nx task sync generator keeps the file in step before builds, serves, and tests, with `nx sync:check` as its own CI step. An Angular CLI Architect builder rewrites the file, or fails CI in its `check` configuration.
- **Runtime checks.** A runtime check configured in the style of NgRx's `runtimeChecks` runs every check in development builds unless the consumer opts one out, and runs none in production unless the consumer opts one in.
- **Responsive Variants.** A responsive Variant is the family's own input taking a Breakpoint query or a Breakpoint rules object over Class breakpoints, never one input per breakpoint and never a class-name string.
- **Defaults.** Every Variant input defaults to setting no class, so the consumer's Sass default is the look.

Why:
- Declaration merging does everything the user's ideal asks. Measured with `ngc` 22.2 strict templates over a real ng-packagr 22.2 package:
  - a misspelt name fails with the compiler's suggestion (TS2820), and so does a Foundation class name passed as a value;
  - a declared custom name compiles and is offered by the editor, and a removed name fails;
  - each application program keeps its own names, and a program that lacks the file fails closed.
- No other route reaches that result. No provider, wherever it is registered, reaches the template type check. A consumer subclass loses its providers, selector, and `exportAs`, and the user has ruled subclassing out. The registry is therefore the one closed-by-default type a consumer can extend without per-directive code.
- The compiled Sass stays the source of truth, where Foundation documents its customisation, and the generator and the runtime check both read the same Variant properties.

## Considered options

- Foundation's default names plus `(string & {})`, with a development check (this decision's first draft): superseded. A typo compiles, and a Foundation class name such as `hide` passes as a value, against ADR 0039's follow-up decision on class names in input values.
- A closed union with no registry: rejected. It fails the `purple` and `xlarge` that Foundation's docs teach consumers to add, and its only escapes are `$any()` or turning attribute checking off for the whole project.
- Consumer subclasses of exported abstract generic bases: rejected by the user's composition rule. Measured, a subclass inherits no `providers`, selector, or `exportAs`, so a child that finds its parent through an optional token silently stands alone. It cannot retype an input a library directive hosts through `hostDirectives`, and a library shared by several Nx applications cannot import an application's subclass.
- Consumer directives placed beside or around the library directive (a narrowing directive on the same selector, generated with import lists, or a consumer directive hosting the library directive through `hostDirectives`): not adopted. A typo fails, but only in components that use the consumer's directive; one that imports the library directive directly falls back to the library's type. The editor offers the consumer's names only when the library input is aliased away. The cost is one directive per family or per library directive. Once the registry closes the library's own type, they add nothing.
- A generic directive that infers the names from a palette bound on the same element: rejected. It needs an extra binding on every element and checks nothing when it is omitted, and the editor offers nothing.
- A provider, or a typed theme constant as the source of the names: not adopted. No provider reaches the template type check. A constant that drives the augmentation works, but without `as const` every name compiles, and it adds a second list beside the Sass.
- TypeScript or design tokens as the source, with the Sass map generated: not adopted. The types never go stale, but the staleness moves to the generated Sass partial, where no compiler sees it, and Foundation's documented settings workflow is replaced by a file of colour values in TypeScript or JSON.
- A tsconfig `paths` remap of a library type module, and a generator that writes into the installed package: vetoed by the user.
- An angular-eslint template rule, or a stand-alone check over Angular's `TemplateTypeChecker`: not adopted. Both check only literal values, which the registry-typed input already rejects at compile time. Both add library API and upkeep, and the user sees no way to feed them from the Sass.
- Regenerating the file inside the build (a builder that wraps `@angular/build:application`, or an esbuild plugin): not adopted. The application builder has no hook inside its Sass compile, code plugins never see that compile, and a wrapper would have to carry every option of the application builder across its releases. A committed file needs a drift check, not a rewrite on every build.
- One options object with a tri-state per check, or NgRx's own production rule that forces every check off: not adopted. Every caller of a single function would ship the checker, and the user wants a production opt-in. Only the production provider function references the checker, so a consumer who does not call it ships none of it (measured: 87 bytes for the shape, against 895 once installed).
- `booleanAttribute` for boolean Variant inputs: rejected. Its parameter is `unknown`, so `dropdown="flase"` compiles and sets the class.

## Consequences

- Input names, in this order: a Foundation `data-*` Option that names the family (`revealOn`, `inCanvasOn`, `hideFor`); the hosted `@angular/aria` directive's name for the concept (`orientation`); one enum input per set of mutually exclusive names, named for its dimension (`color`, `size`, `fill`, `ratio`); a boolean named after its class (`expanded`, `arrowOnly`). A responsive form takes the input that remains once the breakpoint and any `only` or `down` are removed from Foundation's class template, and a `<words>-for-<bp>` class keeps Foundation's words (`stackedFor`). Building-blocks 1.4 carries the full rule.
- The library declares every Variant input with explicit type arguments that name exported aliases, and its build asserts that each emitted write type in the typings names its alias. The reason: declaration emit printed a count input whose type was inferred as the resolved default range, freezing Foundation's defaults where no declaration can reach them. The read type of a count printed resolved even with an explicit argument.
- The Variant registries and the shared Variant types live in the primary entry point. Secondary entry points use them as types only, which adds no runtime import (measured in the FESM bundle), so per-plugin `@defer` splitting is untouched.
- Every TypeScript program that type-checks templates must include the declaration file. The Angular CLI and Nx application templates include `src/**/*.ts`, and the spec templates include `src/**/*.d.ts`. A program without the file rejects the consumer's own names: it fails closed. A shared Nx library's own type check, tests, and stories need a file of their own, and a program that includes several applications' files merges them.
- The file must be a module, with an `import` in it. Otherwise its `declare module` block is an ambient module that replaces the library's types. A consumer who wants open typing for one setting declares an index signature in that registry.
- Nx: no task runs a sync generator when `CI` is set, so `nx sync:check` must be its own CI step. A local non-interactive run (a git hook, an agent shell) stops when the workspace is out of sync. `nx serve` syncs once at start, and the dev server re-checked templates only after the first change to the declaration file, so the docs tell consumers to restart the server after a change of Sass keys.
- Angular CLI: nothing reruns under a bare `ng build` or `ng serve`. npm `pre` scripts are an optional stand-in, and `ng run <app>:nfs-variants:check` is the CI step. The schematic, as an Nx generator converted with `convertNxGenerator`, needs `nx` installed as a development dependency. The check builder is a plain Architect builder and needs only `@angular-devkit/architect`.
- The runtime check has three checks, `strictVariantNames`, `strictVariantProperties`, and `strictBreakpointSync` (ADR 0005's drift check). `provideNfsRuntimeChecks(...)` opts checks out in development and provides nothing in production. `provideNfsProductionRuntimeChecks(...)`, with an optional `report` callback, is the only production code path that references the checker. The checks run only in the browser, after the first render, because the server has no computed style. Under declaration merging they report drift between the declaration file and the compiled CSS, a missing Library mixin include, and values that bypass the type.
- Each Library mixin of an entry point with an Open Variant family writes the Variant properties (`--nfs-<setting>` lists on `:root`), and `nfs-breakpoint-properties` also writes `--nfs-breakpoint-classes` ([ADR 0012](0012-sass-packaging.md), dated note).
- An element Foundation styles by tag gets a directive once Foundation gives it a Variant class: native `<progress>` and `<table>` (ADR 0039, dated note).
- Behaviour Options keep the open `NfsBreakpointName`; Variant inputs use the closed `NfsClassBreakpoint`.
- Reopened if a supported toolchain cannot see the declaration file in a way the CI check does not catch (Vitest under Angular's unit-test builder and `@storybook/angular-vite` are not measured), or if a TypeScript release stops merging interfaces into modules resolved through package `exports`.
- 2026-09-27 ([Re-run: Button spec under the class rule](../issues/128-rerun-button-class-rule.md)): an empty Variant property and a missing one read the same, the empty string, through `getPropertyValue` (measured in Chromium 153, Firefox 155, and WebKit 26.6), so `strictVariantProperties` decides that an include is missing only from properties its mixin never leaves empty on Foundation's defaults, never from a flag-gated one. Sass interpolates a `map-keys()` list with commas, so each mixin joins the names with `space`.
- 2026-09-27 ([Spec: Button Group](../issues/82-spec-button-group.md)): a Variant property has one writer. An entry point whose Open Variant families loop over another entry point's settings reads that entry point's properties and writes none, because a second writer would keep the property present while the first include is missing and hide it from `strictVariantProperties`.
- 2026-09-27 ([Spec: Variant declaration tooling](../issues/136-spec-variant-declaration-tooling.md)): the tooling is specified. The sync generator is registered on each covered project's own targets with Nx's `"..."` array spread, not through `targetDefaults` keyed by executor, because Nx uses the executor key alone when it exists and would drop a workspace's defaults keyed by target name. The declaration file is compared with the Sass by meaning, so formatting and hand-written layout never count as drift, and the tooling rewrites only a file it generated. A shared library whose own programs use names the defaults lack gets a declaration file of its own, from a named application build target or stylesheet; the tooling never builds a program that merges several applications' files, whose conflicting counts `skipLibCheck: true` hides.
- 2026-09-28 ([Spec: Progress Bar](../issues/95-spec-progress-bar.md)): the one-writer rule has one exception, a setting no entry point owns. `nfs-callout` and `nfs-progress-bar` both write `--nfs-foundation-palette`, with the same value, because each loops over `$foundation-palette` and an application may include either alone. `strictVariantProperties` therefore cannot report a missing `nfs-progress-bar` while `nfs-callout` is present; a presence property that is not a Variant property would close that gap and is not adopted.
- 2026-09-28 ([Re-run: Off-canvas spec under the class rule](../issues/117-rerun-off-canvas-class-rule.md)): the Defaults rule presumes that the Sass settings give an element a look with no Variant class. Where they do not, because Foundation's docs require one of the family's classes and no setting names a default (the Off-canvas panel's `.position-<side>`), the Variant input is required, so there is no unset state and still no runtime default that sets a class.
- 2026-09-28 ([Prototype: Variant declaration tooling in real Nx and Angular CLI workspaces](../issues/137-prototype-variant-declaration-tooling.md)): the dev server kept its template diagnostics after the declaration file changed because `@angular/build` recomputes template diagnostics only for files TypeScript's builder reports as affected, and a module augmentation that nothing imports affects only itself; its first rewrite was re-checked only because the first incremental rebuild replaces the placeholder type-check shims. The generated file therefore ends with an empty `declare global {}`, which makes every rewrite reach the template diagnostics under `ng serve` and `nx serve`; the restart advice applies only to a hand-written file without it. On the reopening condition: Vitest under `@angular/build:unit-test` and `@nx/angular:unit-test`, in jsdom and in browser mode, sees the file and fails closed without it; `@storybook/angular-vite` checks no template or story types in any mode, so Storybook neither sees nor needs the file, and a type check of its TypeScript configuration does. Neither reopens this decision.
