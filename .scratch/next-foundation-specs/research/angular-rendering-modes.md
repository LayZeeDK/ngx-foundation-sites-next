## 0. Corrections to earlier research

- `angular-22-api-survey.md` says incremental hydration "needs `provideClientHydration(withIncrementalHydration())`". In 22.x that is out of date. `provideClientHydration()` turns incremental hydration on by default unless `withNoIncrementalHydration()` is passed (`NG/packages/platform-browser/src/hydration.ts:289-291`); `withIncrementalHydration()` is `@deprecated Since v22.0.0 ... Intent to remove in v24` (`hydration.ts:146-151`); `withNoIncrementalHydration()` is `@publicApi 22.0` (`hydration.ts:153-161`). The guide agrees (`NG/adev/src/content/guide/incremental-hydration.md:15-39`).
- Consequence the guides do not state together: the internal incremental-hydration provider list starts with `withEventReplay()` (`NG/packages/core/src/hydration/api.ts:343-346`, "Enabling incremental hydration also enables event replay for the entire app"). So in 22.x a plain `provideClientHydration()` enables event replay too. The platform-server spec confirms it: the "event replay is not enabled" case has to pass `withNoIncrementalHydration()` to get HTML without `jsaction` attributes (`NG/packages/platform-server/test/event_replay_spec.ts:704-720`). `hydration.md:64-74` still describes `withEventReplay()` as an opt-in; treat event replay as on by default for every SSR consumer.

## 1. SSR and prerendering

### What runs on the server

- The server bootstraps the same application with `provideServerRendering()` (platform-server version: `NG/packages/platform-server/src/provide_server.ts`, which sets `globalThis.ngServerMode = true` if undefined and adds `PLATFORM_SERVER_PROVIDERS`). The `@angular/ssr` version wraps it and takes features: `provideServerRendering(withRoutes(serverRoutes))`, `withAppShell(Component)`, and an options object with `maxResponseBodySize` (`NG/adev/src/content/guide/ssr.md:54-80, 425-441`).
- Server platform providers: `DOCUMENT` from a domino document, `PLATFORM_ID` = `'server'`, `ServerEventManagerPlugin`, `ViewportScroller` = `NullViewportScroller` (`NG/packages/platform-server/src/server.ts:48-81`). `DominoAdapter.supportsDOMEvents = false` (`domino_adapter.ts:50`). Template and host listeners are still attached to domino elements (`server_events.ts`, `supports()` returns true for every event) but nothing ever dispatches them.
- Runs on the server: constructors, field initializers, `inject()`, `input()`/`model()` defaults and bound values, `computed`, `linkedSignal`, `effect` (no server guard in `NG/packages/core/src/render3/reactivity/effect.ts`), `ngOnInit`/`ngOnChanges`/`ngAfterViewInit`, template rendering, and every `host` binding (class, style, attribute, property). Host bindings are therefore the only way a directive's state reaches the server HTML.
- Does not run on the server:
  - `afterNextRender`, `afterEveryRender` return `NOOP_AFTER_RENDER_REF` when `ngServerMode` is set (`NG/packages/core/src/render3/after_render/hooks.ts:227-228, 401-402`); `afterRenderEffect` likewise (`NG/packages/core/src/render3/reactivity/after_render_effect.ts:419-420`, doc line 351 "run on browser platforms only"). Guide: "Render callbacks never run during server-side rendering or build-time pre-rendering" (`NG/adev/src/content/guide/components/dom-apis.md:44`).
  - `animate.enter` / `animate.leave`: the `animateEnter` instruction returns early under `ngServerMode` (`NG/packages/core/src/render3/instructions/animation.ts:63-65`; `NG/packages/core/src/animation/utils.ts:30-34`). No enter classes appear in server HTML.
  - `@defer` triggers and prefetching (see section 5).
- No layout exists on the server. Domino has no layout engine, no `IntersectionObserver` ("unsupported in Domino", `NG/packages/platform-server/test/incremental_hydration_spec.ts:1117-1120`), no `ResizeObserver`, no `matchMedia`. `window` is not a Node global; `inject(DOCUMENT).defaultView` is domino's window object, which exists but lacks those APIs. CDK's `MediaMatcher` returns `matches: false` for every query on the server (`angular-cdk-inventory.md`, layout section).

### Stability and `PendingTasks`

- The server serializes only after `await applicationRef.whenStable()` (`NG/packages/platform-server/src/utils.ts:300-303` for `renderModule`, `:370-373` for `renderApplication`). Anything that keeps the app unstable delays or blocks the response.
- `PendingTasks.add(): () => void` is stable (`@publicApi 20.0`, `NG/packages/core/src/pending_tasks.ts:40-50`); `PendingTasks.run(fn)` is `@developerPreview 19.0` (`pending_tasks.ts:74`); `pendingUntilEvent()` is `@developerPreview 20.0` (`NG/packages/core/rxjs-interop/src/pending_until_event.ts:12-21`). Use them only for async work whose result must be in the server HTML. A directive library has almost none (Interchange partial loading is the one candidate).
- Zone.js apps: pending macrotasks (a `setInterval`, a long `setTimeout`) keep the zone unstable (`NG/adev/src/content/guide/hydration.md:173-175`), so an interval started during server rendering in a zone-based consumer never lets `whenStable()` resolve. Zoneless apps track only `PendingTasks`. A library that must work for both starts timers only inside `afterNextRender` (never runs on the server) and, on the client, outside the Angular zone (`NgZone.runOutsideAngular`, harmless when zoneless). The client side matters too: hydration cleanup and event replay both wait for `appRef.whenStable()` (`NG/packages/core/src/hydration/api.ts:278-296`; `NG/packages/core/src/hydration/event_replay.ts:163`), so a client-side interval inside the zone delays replay of every pre-hydration click. `provideStabilityDebugging()` is included in dev mode by `provideClientHydration` (`hydration.ts:284`).

### Render modes per route (`@angular/ssr`)

- `ServerRoute[]` with `renderMode: RenderMode.Server | RenderMode.Client | RenderMode.Prerender` in `app.routes.server.ts` (`ssr.md:27-90`). Prerender options: `getPrerenderParams()` (build time, `inject()` only synchronously), `fallback: PrerenderFallback.Server` (default) `| Client | None` (`ssr.md:164-235`). `outputMode: 'static'` gives a server-less fully prerendered build (`ssr.md:393-415`). Headers and `status` per route (`ssr.md:134-152`).
- `RenderMode.Client` routes are served with a `ngcm` attribute on `<body>` and hydration is skipped without a warning (`api.ts:166-181, 230-245`). So one library must behave in three ways within one app: plain CSR, SSR plus hydration, and prerender plus hydration. Prerender is SSR at build time: same rules, plus `REQUEST`, `RESPONSE_INIT`, `REQUEST_CONTEXT` are `null` (`ssr.md:358-391`) and nothing per-user or per-viewport is knowable.
- Server-side providers configured with `useValue` persist across requests in a long-lived server (`ssr.md:266-271`). The same is true of module-level state: CDK's `_IdGenerator` keeps a module-global counter map (`NGC/src/cdk/a11y/id-generator.ts:18, 38-47`), so server-generated IDs keep counting across requests.

### `provideClientHydration` features (22.2)

From `NG/packages/platform-browser/src/hydration.ts`: `withNoHttpTransferCache()`, `withHttpTransferCacheOptions(options)`, `withI18nSupport()` (`@publicApi 20.0`), `withEventReplay()`, `withIncrementalHydration()` (deprecated, default on), `withNoIncrementalHydration()` (`@publicApi 22.0`). `provideClientHydration()` must also be in the server providers; without it the client logs NG0505 and falls back to destroy and re-render (`api.ts:227-245`; `hydration.md:52`).

### What a library must do to stay SSR-safe

- Read `document` only through `inject(DOCUMENT)` from `@angular/core` (survey section "Hydration and SSR constraints"). Never touch `window`, `navigator`, `location`, `matchMedia`, `getComputedStyle`, `getBoundingClientRect`, `focus()`, `scrollIntoView()` outside a render callback.
- Put every browser-only read or write in `afterNextRender` (once) or `afterRenderEffect` (reactive). These are the library's platform check: they skip the server without any `isPlatformBrowser` call.
- Services that must behave differently per platform: the guide prefers per-platform providers over `isPlatformBrowser` (`ssr.md:262, 273-332`), but a library cannot require the consumer to register a server provider. For library services, keep lazy browser access behind `afterNextRender` or CDK `Platform.isBrowser` (`NGC/src/cdk/platform/platform.ts:39-41`, derived from `PLATFORM_ID`), which is what CDK and Material do. Never branch a template on the platform (`ssr.md:264`; `hydration.md:214-216`).
- Do not read `globalThis.ngServerMode`. Its declaration says "internal Angular flag (not a public API)" (`NG/packages/core/src/util/ng_server_mode.ts:9-21`).
- Do not write the DOM in `effect()`: effects run on the server, and a write there lands in the serialized HTML without Angular knowing about it.

## 2. Hydration

### Structure rules

- Server HTML and client DOM must have the same node structure, including whitespace text and comment nodes; the HTML "must not be altered between the server and the client" (`hydration.md:97-103`). Direct DOM manipulation (`appendChild`, moving or detaching nodes, `innerHTML`, `outerHTML`, querying and inserting into `document`) is the main cause of failure (`hydration.md:105-111`).
- What the client actually checks: node type and tag name. `validateMatchingNode` compares `nodeType` and `tagName` only (`NG/packages/core/src/hydration/error_handling.ts:59-72`); `locateOrCreateElementNodeImpl` claims the next node by position (`NG/packages/core/src/render3/instructions/element.ts:331-375`). Attributes, classes, inline styles and property values are not compared. Static attributes are re-applied on the claimed node (`NG/packages/core/src/render3/instructions/shared.ts:596-599`) and bindings run in the first update pass. Consequence for a class-toggling directive: a class or `aria-*` value that differs between server and client is not an error; the first client pass rewrites it, but the user sees the server value until hydration (a flash or layout shift). Source reading for the rewrite of a `[class.x]` binding whose server value was true and client value is false; not covered by a test found here.
- Valid HTML only: `<table>` needs `<tbody>`, no `<div>` in `<p>`, no nested `<a>` (`hydration.md:113-125`). `preserveWhitespaces` must match between server and client builds (`hydration.md:127-133`).
- Error codes (`NG/packages/core/src/errors.ts:83-92`): NG0500 node mismatch, NG0501 missing siblings, NG0502 missing node, NG0503 DOM nodes created outside Angular passed as projectable nodes to `createComponent` (`error_handling.ts:198-215`), NG0504 `ngSkipHydration` on a non-component host, NG0505 missing annotations, NG0506 not stable within 10 s (`api.ts:85`), NG0507 SSR integrity marker comment removed (for example by a CDN), NG0508 incremental hydration misconfigured, NG0509 missing node on path.

### Control flow and content projection

- `@if`, `@switch`, `@for` views are serialized with a template id and count (`NG/packages/core/src/hydration/views.ts`, `locateDehydratedViewsInContainer`). On the client a view is reused only when the first dehydrated view's template id matches (`hasMatchingDehydratedView`); otherwise the container's dehydrated views are removed and the branch is created fresh (`findMatchingDehydratedViewImpl`, `removeStaleDehydratedBranch`). A branch that differs between server and client is therefore not an error, only a re-render at that spot (and a shift).
- Unclaimed dehydrated views (for example extra `@for` items the client no longer has) are removed only after the app is stable, and render hooks are scheduled again afterwards "because the hydration cleanup alters the DOM" (`api.ts:278-296`). So the first `afterNextRender` after bootstrap can still see stale server nodes. Measure through Angular queries (`viewChildren`, `contentChildren`, `ElementRef`), not `querySelectorAll`.
- Content projection: "Angular always instantiates and creates DOM nodes for content rendered to a `<ng-content>` placeholder, even if that placeholder is hidden"; do not wrap `<ng-content>` in `@if`/`@for`/`@switch` (`NG/adev/src/content/guide/components/content-projection.md:77-80`). Nodes that are instantiated but not attached at serialization time are recorded as disconnected and created fresh on the client (`NG/packages/core/src/hydration/interfaces.ts:97-105`). Material's `mat-tab-group` projects `<ng-content/>` only on the server to keep structure aligned (`angular-material-reference.md` 0.3).

### Things that silently turn hydration off for a component

- `ngSkipHydration`: an attribute or static host binding (`host: {ngSkipHydration: 'true'}`) on a component host; the component and its children are destroyed and re-rendered (`hydration.md:147-171`). It is valid only on component hosts; on any other node Angular throws NG0504 ("Please move the `ngSkipHydration` attribute to the component host element", `error_handling.ts:219-233`). A directive has no escape hatch at all: every directive in this library must be hydration-clean by construction.
- Components whose view contains i18n blocks are skipped unless the app passes `withI18nSupport()` (`hydration.md:195-212`), and components with `ViewEncapsulation.ShadowDom` or `ExperimentalIsolatedShadowDom` are always skipped because domino has no shadow DOM (`NG/packages/core/src/hydration/annotate.ts:824-835`). Skipped components are not serialized, so their elements never get `jsaction` attributes (those are set inside `serializeLView`, `annotate.ts:729-740`) and pre-hydration events inside them are not replayed. Library components must not use Shadow DOM encapsulation.

### How a directive defers DOM writes until after hydration

- Express first-paint state as `host` bindings computed from signals (`[class.is-active]`, `[attr.aria-expanded]`, `[attr.hidden]`, `[style.--x]`). These render on the server and are rewritten, not mismatched, on the client.
- Everything that reads layout or touches nodes outside the host goes into `afterNextRender` or `afterRenderEffect`, using the `earlyRead` / `write` / `mixedReadWrite` / `read` phases; phases run in that order across all registered sequences (`NG/packages/core/src/render3/after_render/manager.ts:71-100`). Both APIs warn that "Components are not guaranteed to be hydrated before the callback runs" (`hooks.ts:99-104`; `NG/adev/src/content/guide/signals/effect.md:203-207`). In practice this means: the directive's own host node is claimed before its render callback runs, but nodes inside a still-dehydrated `@defer` block (section 3) and stale server views (above) may be present.
- Third-party DOM scripts: defer them with `afterNextRender` (`hydration.md:222-224`).
- Never move server-rendered nodes (Foundation Reveal appends its overlay to `<body>`, Tooltip and Dropdown attach panes to `<body>`). Render in place, use the top layer (`<dialog>.showModal()` moves nothing in the DOM), or create the floating node on the client only (CDK overlay after an interaction).

## 3. Incremental hydration

### Syntax and triggers

- A `hydrate` trigger makes the server render the block's main template instead of `@placeholder`; on the client the block's code stays unloaded and the DOM stays dehydrated until a hydrate trigger fires (`incremental-hydration.md:41-43`). Several triggers are OR-ed with `;` (`:49`).
- `hydrate on idle` (optional ms timeout), `hydrate on viewport` (IntersectionObserver), `hydrate on interaction` (`click`, `keydown`), `hydrate on hover` (`mouseover`, `focusin`; the list in code is `['mouseenter', 'mouseover', 'focusin']`, `NG/packages/core/primitives/defer/src/triggers.ts:25-28`, but `mouseenter` is not a replayable type, see section 4), `hydrate on immediate`, `hydrate on timer(500ms)`, `hydrate when expr`, `hydrate never` (`incremental-hydration.md:53-185`).
- Parameters: `hydrate on interaction` and `hydrate on hover` take no parameters; `hydrate on viewport` takes at most one, an options object literal without `root` and without a `trigger` key (`NG/packages/compiler/src/render3/r3_deferred_triggers.ts:635-643, 669-670, 704-718`). So hydrate interaction and hover triggers always watch the block's own root elements, which get `jsaction` attributes on the server (`annotate.ts:893-915`).
- `hydrate when` only fires while its block is the top-most dehydrated block, because the expression lives in the parent (`incremental-hydration.md:166-168`).
- `hydrate never` keeps the block static on initial load, blocks every hydrate trigger in its subtree (`:170-185`), and its elements get no `jsaction` attributes, so events in it are never replayed (asserted in `NG/packages/platform-server/test/incremental_hydration_spec.ts:2147-2196`).
- Regular and hydrate triggers are mutually exclusive per render: on the server regular triggers are attached only when incremental hydration is off or the block has no hydrate triggers; on the client a server-rendered block with hydrate triggers ignores its regular triggers (`NG/packages/core/src/defer/triggering.ts:612-661`). Regular triggers apply to later client-side renders, for example after a route change (`incremental-hydration.md:187-199`), so `@placeholder` is still needed (`:224-226`).

### Nesting and order

- Hydrating any block hydrates every dehydrated ancestor first, top-down (`incremental-hydration.md:201-218`; queue built by `getParentBlockHydrationQueue` in `triggering.ts:374-429`).
- Per block: load its dependencies, wait one render (`afterNextRender`), then resolve (`triggering.ts:456-477, 578-583`). After the last block resolves, the pending task is removed, queued events are replayed, and dehydrated leftovers are cleaned after stability (`triggering.ts:483-528`).

### What a dehydrated block is

- Server HTML with no Angular behind it: component and directive classes inside the block have not been constructed, host bindings keep their server values, and no listeners exist except the `jsaction` delegation on `document.body`. CSS-only and native-element behaviour works (`:hover` styles, `<details>` toggling, form controls); nothing driven by the directive does.
- A parent outside the block sees none of the block's children: content queries (`contentChildren`) and registration into a parent-owned collection (Aria's `SortedCollection.register`, `NGC/src/aria/private/utils/collection.ts:30-36`) only happen when the child is constructed. A Tabs or Accordion parent whose items sit in a dehydrated block has an empty item list and broken keyboard navigation until that block hydrates. Rule: one composite widget (container plus its items, trigger plus its target) belongs inside one hydration boundary; a `@defer` boundary wraps the whole widget, never part of it.
- An interaction on any element inside the block that has a replayable template or host listener hydrates the block, whatever its hydrate trigger (idle, viewport, timer, when): such elements carry `jsaction="click:;"` plus `ngb="d<N>"` (`NG/packages/core/src/event_delegation_utils.ts:25-47`; asserted at `incremental_hydration_spec.ts:2190`), and a replay whose target carries `ngb` calls `triggerHydrationFromBlockName` (`event_replay.ts:280-298`).

### What a directive inside a hydrate block may assume after hydration

- Its constructor, inputs, `ngOnInit` and first render all happen during the block's hydration render; its `afterNextRender` callbacks registered in that render run in the same after-render pass that the hydration queue awaits (`triggering.ts:470-477`; hooks registered during change detection join the current pass, `manager.ts:125-142`). Then queued events are replayed (`triggering.ts:496-499`). Source reading: the replayed event therefore sees state set in constructors, `computed`, `linkedSignal`, host bindings and that first `afterNextRender`, but not state set by later async work.
- `animate.enter` has no hydration guard in the `animateEnter` instruction / `runEnterAnimation` (`animation.ts:60-94, 96-160`). Source reading, untested here: an element present in the server HTML that carries `animate.enter` may play its enter animation when it is hydrated (full or incremental). Needs a prototype before Reveal, OffCanvas or Orbit specs rely on either outcome.

## 4. Event replay

### Mechanism

1. Server: `annotateForHydration` walks every serialized view and collects, per element, the event names of its DOM listeners (`collectDomEventsInfo`, `event_replay.ts:230-273`), then writes `jsaction="click:;keydown:;"` on those elements (`annotate.ts:729-740`). If any replayable type was found, platform-server inserts `window.__jsaction_bootstrap(document.body, "<appId>", [bubble types], [capture types])` right after the inline `<script id="ng-event-dispatch-contract">` (`NG/packages/platform-server/src/utils.ts:44, 111-124, 159-188`). The CLI build inlines that contract script; `@angular/core/event-dispatch-contract.min.js` is the published file (`NG/packages/core/package.json` exports). Without it in the document, no replay script is emitted (`utils.ts:170`).
2. Browser before hydration: the early contract listens on `document.body` for the collected types (capture phase for capture types) and queues event infos; it does not call `preventDefault` (`NG/packages/core/primitives/event-dispatch/src/earlyeventcontract.ts`, `createEarlyJsactionData`, `addEvents`). Native default actions happen: links navigate, `<details>` toggles, checkboxes flip, forms submit, focus moves.
3. Browser after hydration: listeners are stashed per element as they are created (`event_replay.ts:98-131`). After `appRef.whenStable()` the queue is replayed through a JSAction `EventDispatcher` (`event_replay.ts:163-224`), `jsaction` attributes are removed (`event_delegation_utils.ts:84-91`), and the contract is cleaned up, except that with incremental hydration it stays alive for dehydrated blocks until app destroy (`event_replay.ts:184-192`).

### Which events replay

- Replayable bubble types (`NG/packages/core/primitives/event-dispatch/src/event_type.ts:295-355`): `click`, `dblclick`, `auxclick`, `contextmenu`, `focusin`, `focusout`, `keydown`, `keyup`, `keypress`, `mouseover`, `mouseout`, `mousedown`, `mouseup`, `wheel`, `pointerdown`, `pointermove`, `pointerup`, `pointercancel`, `pointerover`, `pointerout`, `gotpointercapture`, `lostpointercapture`, `touchstart`, `touchmove`, `touchend`, `touchcancel`, `submit`, `change`, `input`, `beforeinput`, `select`, `compositionstart`/`update`/`end`, `copy`, `cut`, `paste`, `drag*`, `drop`, `ended`, `loadedmetadata`, `pagehide`, `pageshow`, `visibilitychange`, `beforematch`.
- Replayable capture types (`event_type.ts:358-364`), dispatched only when the listener element is the event target (`event_dispatcher.ts:88-94`): `focus`, `blur`, `error`, `load`, `toggle`. `toggle` covers `<details>` and popovers.
- Not replayed: `mouseenter`, `mouseleave`, `pointerenter`, `pointerleave` (special mouse types, `event_type.ts:287-292`; test "should not replay mouse events", `event_replay_spec.ts:687-702`), `scroll`, `resize`, `animation*`, `transition*` (also excluded from listener cleanup bookkeeping, `NG/packages/core/src/render3/view/listeners.ts:186, 202-204`), and any custom event type (for example Foundation-style `open.zf.reveal` or a `CustomEvent`).
- Only listeners declared in templates or in `host` metadata replay. The server finds them through `tView.cleanup` (`event_replay.ts:236-270`), where outputs are excluded (`isDomEvent`, `event_replay.ts:258-265`) and listeners added in code (`Renderer2.listen`, `addEventListener`, a CDK service) are never recorded. Directive host listeners are included: they are registered on the host element's view, and the stash function explicitly handles host listeners on `<ng-container>` hosts (`event_replay.ts:114-119`).
- Global targets do not replay: `(document:click)`, `(window:click)`, `(body:click)` host listeners get a target-getter instead of an element index (`listeners.ts:187-189`), so no element gets `jsaction`; the three platform-server tests assert the spy is not called (`event_replay_spec.ts:310-427`). A document-level Escape handler or outside-click handler sees nothing from before hydration.

### Replay semantics a handler must respect

- Replayed events have `event.eventPhase === 101` (`EventPhase.REPLAY`, `NG/packages/core/primitives/event-dispatch/src/event_dispatcher.ts:29-31`). `event.target` and `currentTarget` are patched to the original elements; bubbling to ancestor listeners and `stopPropagation` are emulated (`event_dispatcher.ts:83-117`; tests at `event_replay_spec.ts:537-641`).
- `event.preventDefault()` during replay calls the original and then throws `preventDefault called during event replay`; `event.composedPath()` throws (`event_dispatcher.ts:121-138`; asserted in `NG/packages/core/primitives/event-dispatch/test/event_dispatcher_test.ts:87-109`). Angular's listener wrapper catches the throw and reports it to `ErrorHandler` (`listeners.ts` `executeListenerWithErrorHandling`), so any statement after `preventDefault()` in that handler is skipped. A listener that returns `false` makes Angular call `preventDefault()` for it (`listeners.ts:91-92`; `NG/packages/platform-browser/src/dom/dom_renderer.ts:531-534`), with the same result. Aria's `KeyboardEventManager` defaults `preventDefault: true` and calls it after the handler (`NGC/src/aria/private/behaviors/event-manager/keyboard-event-manager.ts:34`, `event-manager.ts:66-80`): source reading, a replayed arrow key in an Aria tab list changes state and then logs this error. `EventPhase` is exported from `@angular/core/primitives/event-dispatch`, whose README says "not a public API" (`NG/packages/core/primitives/event-dispatch/README.md:3-5`).
- An event that a real listener already handled after the component hydrated is not replayed again (`event_delegation_utils.ts:100-130`; test `event_replay_spec.ts:94-138`, issue #67328). Replay skips elements no longer connected (`invokeListeners`, `isConnected`).
- Anchors: for live events inside a still-dehydrated block (the contract is alive under incremental hydration), the JSAction `Dispatcher` calls `preventDefault()` on a `click` whose action element is an `<a>` before dispatching (`NG/packages/core/primitives/event-dispatch/src/dispatcher.ts:79-86, 127-140`). Source reading: a hash link with a `(click)` listener inside a dehydrated block does not follow its `href` natively; the replayed handler must perform the navigation or scroll itself. Outside dehydrated blocks (initial full-hydration window) the early contract lets the native navigation happen and replays the handler afterwards.
- Transient user activation has usually expired by the time of replay. APIs that require it (fullscreen, clipboard write, `window.open`) may fail from a replayed handler. `showModal()` and `focus()` do not require activation.

### Worked cases

- Click on a not-yet-hydrated Reveal open button (full hydration): the browser does its default (nothing for a `type="button"`), the click is queued, the app hydrates, and after `whenStable()` the button's `(click)` host or template listener runs with `eventPhase === 101`. If the handler reads a signal set in the directive constructor or first `afterNextRender`, that state exists. If it looks up a target by id through a registry that the target fills in its own `afterNextRender` or later, check the order; if the target sits in a dehydrated `@defer` block, it does not exist yet and the open is lost unless the trigger and target share a hydration boundary or the registry queues requests.
- Click on a Dropdown button: same as above. The pane opening after replay runs positioning in `afterNextRender`/`afterRenderEffect`, which works because layout exists by then. The outside-click closer (document listener, not replayed) cannot close from a pre-hydration click, which is correct.
- Keyboard: `keydown` on a focused tab or menu item replays. Handlers must change state first and call `preventDefault()` last, or skip it when `event.eventPhase === 101`, or the state change is lost or an error is logged.
- Hover and focus: `mouseover`/`focusin` replay late, possibly after the pointer or focus has moved on. Handlers for hover or focus-opened UI (Tooltip, hover DropdownMenu) should re-check live state (`el.matches(':hover')`, `el.matches(':focus-visible')`, `document.activeElement`) or use non-replayed `pointerenter`/`pointerleave` for opening.

## 5. `@defer`

### Rules (beyond the survey)

- Deferred dependencies: standalone only, and not referenced outside the block in the same file or in a `viewChild` query, otherwise they are eager (`NG/adev/src/content/guide/templates/defer.md:17-28`). Placeholder, loading and error block dependencies are eager (`:62, 90, 109`). `@placeholder (minimum 500ms)`, `@loading (after 100ms; minimum 1s)`; timers for `@loading` start when loading is triggered (`:64-105`).
- `on viewport`, `on interaction` and `on hover` with no reference watch the placeholder, which must then have a single root element (`:189, 230, 253`). `on viewport({trigger: ref, rootMargin, threshold})` passes IntersectionObserver options except `root` (`:208-224`). `when` is one-time (`:310`). `prefetch on ...` loads code only (`:312-333`); prefetch never runs on the server (`triggering.ts:619`).
- On the server without hydrate triggers, a block renders `@placeholder` (or nothing) and its triggers are not invoked; the client hydrates the placeholder and activates triggers (`defer.md:379-383`). With a hydrate trigger, the main content renders on the server (section 3).
- HMR fetches every deferred chunk eagerly (`defer.md:375-377`); test deferred behaviour with `--no-hmr`.
- Accessibility: placeholder-to-content swaps are not announced unless wrapped in a live region (`defer.md:426-447`).

### DI, queries and projection inside a deferred block

- DI: a component inside `@defer` inside another component's content resolves providers of that host component and of the declaring component; the platform-server-free test "should provide access to tokens from a parent component" shows `<parent-cmp> @defer { <child-cmp/> } </parent-cmp>` injecting both (`NG/packages/core/test/acceptance/defer_spec.ts:4825-4870`). NgModule providers pulled in by deferred dependencies go into a new environment injector chained under the parent (`NG/packages/core/src/defer/rendering.ts:79-125`). The optional `skipSelf` parent-token pattern in this repo's AGENTS.md keeps working across a consumer's `@defer`.
- Queries: each sub-block is a separate view; a `viewChildren` query sees the placeholder, loading, and main instances in turn (`defer_spec.ts:1418-1484`). A parent's `contentChildren` sees deferred children only once the main block has rendered (and, under incremental hydration, hydrated).
- `<ng-content>` inside a `@defer` block projects normally (`defer_spec.ts:1486-1540`), but it defers no code: projected content belongs to the consumer's template and is instantiated whether or not the slot renders (`content-projection.md:77-80`).

### Library lazy content: `@defer` versus `ng-template`

- `@defer` splits code. It belongs in the consumer's template, around heavy content the consumer puts inside an accordion panel, tab panel, Orbit slide or Reveal. The library cannot choose hydrate triggers for consumers and has no heavy dependencies of its own to split, so library templates should not contain `@defer`.
- `ng-template` content directives (Material `matExpansionPanelContent`, Aria `ngAccordionContent` / `ngTabContent`) delay instantiation, not code. How the view is created decides SSR output:
  - Aria's `DeferredContent` creates the view in an `afterRenderEffect({write})` (`NGC/src/aria/private/deferred-content/deferred-content.ts:56-71`), and `AccordionPanel`/`TabPanel` set `contentVisible` in another `afterRenderEffect` (`NGC/src/aria/accordion/accordion-panel.ts:84-89`; `NGC/src/aria/tabs/tab-panel.ts:96-100`). Neither runs on the server, so an initially open Aria accordion panel or selected Aria tab panel is empty in the server HTML and pops in after hydration (layout shift, content missing for crawlers and no-JS users). Aria's accordion group and tab list also start their `SortedCollection` observer and default-state logic only in render callbacks (`accordion-group.ts:114-116`; `tab-list.ts:133-149`).
  - A template-driven view created during change detection (`@if (expanded()) { <ng-container [ngTemplateOutlet]="content" /> }` in a library component template, or a structural directive that creates its view synchronously in a `computed`-driven path) renders on the server when the initial state is open and hydrates normally.
  - Plain projected content toggled with `hidden`/`inert`/a Foundation state class renders on the server in every state; it is the SSR-safest option when laziness is not needed.
- Rule for specs: any panel the consumer can mark open by default must render its content on the server. A spec that adopts an Aria pattern with `DeferredContent` must either accept client-only content (documented) or supply content through projection instead of the Aria `ng-template` directive.

### Testing deferred blocks

- `TestBed.configureTestingModule({deferBlockBehavior: DeferBlockBehavior.Manual})`; default is `DeferBlockBehavior.Playthrough` (`NG/packages/core/src/defer/interfaces.ts:320-332`). `await fixture.getDeferBlocks()` returns `DeferBlockFixture[]`; `await block.render(DeferBlockState.Placeholder | Loading | Complete | Error)`; nested blocks through `block.getDeferBlocks()` (`NG/packages/core/testing/src/defer.ts:25-66`). `TestBed.compileComponents()` is required when `@defer` is used (`NG/adev/src/content/guide/testing/components-basics.md:87`; `utility-apis.md:57`). TestBed renders client-side only; hydrate triggers cannot be exercised there.

## 7. Library implications

### Rules every spec applies

1. Server HTML is the first paint and must be correct without JavaScript: every state visible at first paint comes from `host` bindings on signal state (`[class.is-active]`, `[class.is-open]`, `[attr.aria-expanded]`, `[attr.aria-selected]`, `[attr.hidden]`, `[attr.inert]`, `[style.--nfs-*]`), never from render callbacks.
2. Foundation's CSS hides closed things by default (`.dropdown-pane` `display: none; visibility: hidden` until `.is-open`, `.is-opening` shows it invisibly for measuring, `FS/scss/components/_dropdown.scss:41-67`; `.reveal` and `.reveal-overlay` `display: none`, `_reveal.scss:58-77`; `.tabs-panel` shown only with `.is-active`, `_tabs.scss:131-140`). `.accordion-content` is `display: none` with no class rule that shows it (`_accordion.scss:125-136`; Foundation's JavaScript writes inline display), so an accordion open at first paint needs a host style or attribute binding or a documented library rule.
3. Measure only in `afterRenderEffect` `earlyRead`/`read` and write in `write`, or use `ResizeObserver`/`IntersectionObserver` created in `afterNextRender`. Nothing measured exists on the server; the server renders the unmeasured state.
4. No DOM structure changes outside templates: no `appendChild`, no moving nodes to `<body>`, no `innerHTML`. Structure the plugin used to inject (Drilldown back buttons, Nest submenu toggles, Orbit bullets) is template-owned.
5. Focus, scroll and timers only in render callbacks; timers outside the Angular zone; nothing that keeps the app unstable.
6. Event listeners that must replay are template or `host` listeners on elements (not `document:`/`window:` targets, not `Renderer2.listen`). Handlers do their state change before any `preventDefault()`, and skip `preventDefault()` on replay. Hover and focus handlers re-check live state.
7. A widget's container and its items, and a trigger and its target, share one hydration boundary; document that a consumer `@defer` must wrap the whole widget.
8. Generated IDs are fine only where every reference to them is also a binding: `_IdGenerator.getId(prefix, true)` adds a per-process random infix (`id-generator.ts:24, 47`), so server and client IDs differ and are rewritten at hydration. Deep links (Tabs and Accordion hash, Magellan targets) use consumer-supplied stable IDs.
9. Breakpoint-dependent state cannot be known on the server. Decide per spec which breakpoint the server renders (Foundation is mobile-first, so `small`), and note that CDK `MediaMatcher` answers `false` to every query on the server, including `small`'s `(min-width: 0)`, so the library breakpoint service must define its server answer itself. Prefer CSS media queries and Foundation visibility classes for anything visible at first paint.
10. No Shadow DOM encapsulation and no `ngSkipHydration` in library components; directives cannot use `ngSkipHydration` at all.
11. `hydrate never` blocks stay static forever on initial load: a widget there works only as far as its server HTML and native elements work.

- Whether `animate.enter` replays on server-rendered nodes at hydration (source shows no guard). Needs a prototype before Reveal, OffCanvas, Toggler and Orbit animation specs commit.

- Whether the new repo gets an SSR fixture app (Nx Angular application with `@angular/ssr` prerender plus Playwright) as a fourth test seam; the tooling ticket did not plan one.
- Whether Aria-based Accordion and Tabs specs accept client-only panel content from Aria's `DeferredContent`.
