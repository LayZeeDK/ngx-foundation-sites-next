# Out-of-scope triage, second pass: lens 2, adversarial scope and Foundation fidelity

Model: Opus 5.5

Lens 2 of three for [Triage: out-of-scope items across the specs](../issues/138-triage-out-of-scope-across-specs.md), step 2. It reads the rows of [out-of-scope-exclusions-2.md](out-of-scope-exclusions-2.md) by their ids, and it reads the verdicts of [Triage the out-of-scope Foundation components and variants](../issues/79-triage-out-of-scope-components-and-variants.md) in [out-of-scope-triage.md](out-of-scope-triage.md). The lens attacks in both directions. First, for each exclusion it asks whether Foundation for Sites 6.9 documents or styles the item, so that leaving it out breaks fidelity. Second, for each case another lens may make for inclusion, it asks whether the item brings in something the Destination does not cover: application behaviour, jQuery or DOM plumbing, a dependency, or a feature Foundation lacks.

Path prefixes: `docs/`, `scss/`, and `js/` are in the Foundation 6.9.0 clone (`d:/projects/github/foundation/foundation-sites`, `v6.9.0-1-g337be7a8d`); `NC/` is `d:/projects/github/angular/components` at 22.2.x; `APG/` is `d:/projects/github/w3c/aria-practices`. Bundle paths are relative to EFFORT. The contrast ratios below were recomputed with the exact WCAG relative-luminance formula against `$body-background` (`#fefefe`).

## Result

This lens gives a verdict on all 417 new rows and on every re-checked row that a later ruling bears on. It finds no fails and two partly verdicts. The partly verdicts cover three rows: `forms-4` together with the re-checked `button-3`, and `input-1`. Every other row holds. The specs of the class-rule wave checked Foundation's Sass, docs, and JavaScript closely. Every claim of the form "Foundation generates no such class" or "Foundation has no such Option" that I tested against the clone is true; the tested claims are the ones cited in H2c, H6, H7, H8, H10b, and the table. Nine rows hold with a stated reason that is wrong, missing, or stale. The section that lists them also records the wrong reason behind the first partly verdict.

## Cases for inclusion I expect and reject

- **A Router-driven breadcrumb trail or a breadcrumb service (breadcrumbs-1).** It brings in route data and a route-data key, which is application state (P15). Foundation's markup is the consumer's.
- **Aria's `Toolbar` on a Button Group, or on a Top Bar (button-group-3, top-bar-8).** It brings in a roving tab stop and a key table that Foundation never had, and a role with no spec that needs it (ADR 0004's reasoning). A consumer who needs a toolbar can write Aria's directives beside `nfsButtonGroup`, which is composition, not a library change.
- **Selection or a group-level `disabled` on the Button Group (button-group-4, button-group-5).** This is Material's toggle group. Foundation's group only cascades looks (`scss/components/_button-group.scss:215-244`, cited by [Triage the out-of-scope Foundation components and variants](../issues/79-triage-out-of-scope-components-and-variants.md)).
- **Default roles, default names, and live roles (H4).** Foundation supplies none of them. Each would make one element's semantics the default for every use, and under ADR 0045 it could be reversed only at an Angular major.
- **Components with slots for Card, Media Object, Table, Thumbnail, Switch, Responsive Embed, and form fields (H2a).** Each brings in generated structure, against ADR 0001. A data-driven table brings in a data source (CDK's `CdkTable`).
- **A page-window helper for Pagination (pagination-1).** This is application logic. As a pure function it is additive later, which ADR 0045 allows in any release.
- **Indeterminate progress, slider ticks, a value badge, a slider colour, and stacked bars (H2b).** Foundation has no look for any of them.
- **A `checked` model on the Switch (switch-2).** It adds a second value source beside the native control and Angular Forms (P20).
- **Schematics, watch modes, and builder wrappers for the Variant declaration file (H19).** Each brings in toolchain code that ADR 0040 weighed and did not adopt.

## Rows whose stated reason is wrong, missing, or stale; the verdict holds

- **abide-10.** As written, the bullet excludes radio groups, checkbox groups with a minimum count, `select`, and `textarea`. The spec covers each of them (`specs/abide.md:18`, `:159`, `:497`, `:643-646`). What stays out is any other control kind that the prototype did not design. The bullet should name that residue, not the covered kinds.
- **tabs-16.** The spec drops a Foundation key binding with no reason ("no longer switch tabs", `specs/tabs.md:753`). The reason is APG `tabs-pattern.html:116` and the hosted Aria Tabs (`NC/src/aria/private/tabs/tabs.ts:159-172`), under H7.
- **progress-bar-6.** The bullet gives no reason, but the Animation section does (`specs/progress-bar.md:317`). Foundation's partial declares no transition, and a transition would show a value the ARIA attributes no longer carry. The bullet should cite that section.
- **equalizer-12.** The reason quoted in the row, "building-blocks 1.4 has no start events", covers only the pre events. The per-row pre and post events are dropped because the row heights are the `equalized` payload (`specs/equalizer.md:93-94`).
- **anchored-pane-9.** The row gives no reason. The reason is ADR 0024: the Light dismiss registry replaces the `closeme` broadcast and the shared `click.zf.dropdown` namespace.
- **menu-7.** The row's reason, "a consumer attribute", covers only `role="list"`. The `ol` half holds because no menu in `docs/pages` is an `ol`.
- **bb-1.** The rule's list in ADR 0039's body names native `<progress>` and `table`. ADR 0039's own dated note and ADR 0040 later gave both elements directives, and gave the form `label` one too. The rule holds only while Foundation gives the element no class, as that note says.
- **variant-declaration-tooling-4.** The bullet reads as ruling out `ng update` and `nx migrate` migrations in general. ADR 0045, recorded later the same day, decides that the library's migrations are Nx migrations reused as `ng update` migrations, and that a removed or renamed public API gets one wherever a migration can be written. The bullet holds for the declaration file, because the sync generator rewrites a file it generated. It should say that it covers the file only. It should also say that a renamed registry interface follows ADR 0045's deprecation rule, because a hand-written file (ADR 0040) keeps using the old name.
- **forms-4 and button-3.** "Until a fix for WCAG 2.2 AA 2.4.7 exists" is wrong for the sibling-after and nested markup forms (first table row).
- **dropdown-menu-23 (re-checked, DM19).** The evidence paraphrase "consumer-written" is stale. The spec's own reason is current: `aria-current`, per ADR 0042 (`specs/dropdown-menu.md:134`).

## ADR 0045 and the impact ratings

ADR 0045 moves no verdict, but it changes impact, and the judge may want to apply that consistently.

- An exclusion whose later reversal is additive is LOW impact, because such a change can ship in any release for an Angular minor: a new host, input, directive, opt-in check, or recipe. Examples are forms-4, H2d, and H5.
- An exclusion whose reversal changes a default is harder to reverse, because after the first release it waits for an Angular major. That covers a default role, name, or live role (H4), a new required setting or compile error (input-1), and a Library mixin rule that changes Foundation's rendering at rest (H6). These are the rows to settle before the first release.

## For the user

Nothing from this lens has to go to the user. Neither partly verdict is HIGH impact with NOT-HIGH confidence. input-1 extends the compile-time checks to one base-element colour. That is a small policy step past the map's base-styles line. The judge may choose to mention it to the user, but the triage quadrant does not require it.
