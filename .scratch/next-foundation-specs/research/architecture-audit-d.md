# Architecture audit: group d

Group: d. Specs audited: `specs/nested-menu.md`, `specs/off-canvas.md`, `specs/orbit.md`, `specs/pagination.md`, `specs/progress-bar.md`, `specs/prototyping-utilities.md`, `specs/responsive-accordion-tabs.md`, `specs/responsive-embed.md`, `specs/responsive-menu.md`. Guide version: `architecture-guide.md`, last dated change 2026-09-28. Date of this audit: 2026-09-29.

Each spec was read in full (Problem Statement through Further Notes) and checked against every principle P1-P26 from the spec's class mapping, hierarchy and DI shape, API, ARIA and keyboard tables, rendered HTML, rendering modes, Sass subsection, and Testing Decisions, per the guide's own audit instructions. ADR 0044, ADR 0045, ADR 0046, and `specs/forgotten-import-checks.md` were read first, as the ticket requires, and every multi-directive spec in this group was checked for its In-family check lines, parent token descriptions, and `strictParents` effect statements by that rule.

## Summary of the one cross-cutting cause

Eight of the nine specs in this group predate [ADR 0046](../adr/0046-forgotten-imports-caught-by-checks.md) (2026-09-28) in one shared respect: none states that its directives or components call `nfsDirectiveCheck`, none lists the per-part In-family check line the shared [Spec: forgotten-import checks (shared utility)](../issues/150-spec-forgotten-import-checks.md) requires of a spec with more than one directive, and the two families in this group that appear in that spec's eight-family `strictParents` table (Nested menu, Orbit, Pagination) never state the `strictParents` effect on their optional parent injections. A mechanical search of every spec in this group, and of every published spec, for `nfsDirectiveCheck`, `strictParents`, and `In-family` returns matches in only three files in the whole corpus: `specs/breakpoint-service.md`, `specs/accordion.md`, and `specs/forgotten-import-checks.md` itself -- none of them in this group. This is recorded once per affected spec below, under P24, because P24 is the lowest-numbered principle each falls short of (each spec's own ad hoc development checks for copied classes, missing includes, and placement already meet P23's substance; it is specifically the ADR 0046 mechanism that is absent).

The ninth spec, `specs/responsive-accordion-tabs.md`, is the one exception: its two declarables (an element-selector component and an `ng-template`-hosted directive) are both explicitly out of `nfsDirectiveCheck`'s scope by `forgotten-import-checks.md`'s own text ("element-selector components are the compiler's"; a directive whose host is `ng-template` or `ng-container` "calls nothing... only the static check can see it"), so its silence on the mechanism is correct, not a gap.

## GUIDE PROBLEM (from this spec)

P17's rule text says hidden in-DOM content gets `inert` "except the cases building-blocks 1.10 lists (dialogs and top-layer elements, the closed Off-canvas panel, the Tooltip tip)". This spec's hidden Drilldown ancestor levels (a level that still contains the currently open descendant level) use Foundation's `invisible` (`visibility: hidden`) instead, and the spec's own Design decision D9 explicitly rejects `inert` on the hidden parent level as the alternative not taken, "because `inert` on an ancestor blocks the open level" (an inert ancestor cannot be selectively released for one live descendant; `inert` is inherited through the whole subtree). This is a real, unavoidable fifth case for any nested slide-over disclosure widget that neither building-blocks 1.10's four-item exception list nor the guide's P17 rule text names, so a spec built correctly here still reads as falling short of P17's literal text. This is offered as a guide gap, not a spec defect: the fix belongs in P17's exception list (or in building-blocks 1.10), not in `nested-menu.md`.

## GUIDE PROBLEM (from this spec)

P18's rule text ("one Library mixin per Foundation export mixin that needs custom CSS, checks, or Variant properties, named after it and included after it") is written as an unconditional per-export-mixin rule, with only a multi-mixin precedent cited (Top Bar/Title Bar/Menu icon, which still runs in the same direction: more mixins, not fewer). It states no exception for a utility family whose many export mixins each need only a Variant-property write and share one Library mixin covering the whole family -- yet this spec's own decision (Utility directive rule, clause 7: the entry point's one `nfs-<entry point>` mixin writes the Variant properties and checks for every export mixin in the family) is exactly the shape ADR 0044's Consequences ratify for this spec, Float Classes, and Typography Helpers. Since an ADR outranks the guide, this is not a finding against `prototyping-utilities.md`, but it is a real, recorded conflict between P18 and ADR 0044 that the guide's "Conflicts between the research and recorded decisions" section (which lists only three conflicts) omits. Evidence: `architecture-guide.md` P18 rule text versus `specs/prototyping-utilities.md`'s Utility directive rule clause 7 and its Sass subsection (one mixin covering eighteen export mixins), and `adr/0044-utility-directive-rule.md`'s Consequences bullet naming Float Classes and Typography Helpers as following "this shape."

## `specs/responsive-accordion-tabs.md`

No finding: this spec is the one exception to the group's P24 gap. Its two declarables are both out of `nfsDirectiveCheck`'s scope by `forgotten-import-checks.md`'s own text: `NfsResponsiveAccordionTabs` has an element selector (`nfs-responsive-accordion-tabs`), and "element-selector components are the compiler's" (a forgotten one already gets Angular's NG8001); `NfsResponsiveAccordionTabsPanel`'s host is `ng-template[nfsResponsiveAccordionTabsPanel]`, and "a directive or component whose host is an `ng-template` or `ng-container`... calls nothing: the DOM holds no element for it, so only the static check can see it." ## Guide problems

Two are recorded above, under `specs/nested-menu.md` and `specs/prototyping-utilities.md`. Both are offered as guide gaps rather than spec defects: P17's `inert` exception list has no line for a hidden ancestor level of a nested disclosure that still contains a visible, open descendant (a structural necessity of any Drilldown-shaped widget, not an error in how `nested-menu.md` is written); and P18's one-mixin-per-export-mixin rule has no exception for the one-mixin-per-utility-family shape ADR 0044 ratifies for standalone utility families, which the guide's Conflicts section does not list among its three recorded conflicts.

## Principles checked hardest across the whole group, yielding no further findings

Beyond P24 and the two guide problems above, this group concentrates the library's disclosure menus, an Aria-hosted carousel, a listener-free item family, a value-only meter family, a flat utility family, the one element-selector component, a CSS-only wrapper directive, and a thin swap-driving consumer, and close reading turned up no further shortfall in: P1 (directive-versus-component boundary across every spec, including the two accepted exceptions); P5 (native element choices -- `<button>` triggers, no `<dialog>` for Off-canvas, `<input type=range>` not used here but the same discipline applied to every other native choice); P6/P8 (hostDirectives limits in Nested menu, Orbit, and Responsive Menu, all matching already-accepted patterns the guide itself cites); P9 (utility-family input shapes in Prototyping Utilities and the shared-name nesting rule in Nested menu); P11 (one source per state, checked in every spec that has state: Nested menu, Off-canvas, Pagination, Progress Bar, Orbit, Responsive Menu); P16 (native-first implementation levels and the CDK pieces Off-canvas and Nested menu use); P17/WCAG tables (contrast and target-size compile-time checks in every spec that has visible state); P19 (animation via State classes, never `animate.enter`/`animate.leave`, in Nested menu, Off-canvas, and the deliberate Orbit exception); P21 (no library strings, checked hardest in Orbit, Pagination, Progress Bar, and Responsive Accordion Tabs' recorded exception); and P22 (entry-point boundaries and type-only token imports across the group).
