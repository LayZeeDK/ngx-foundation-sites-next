# Loading and unloading family styles from directives in Angular 22.2

Ticket: [Research: loading and unloading component styles from directives in Angular 22.2](../issues/182-research-lazy-style-loading-from-directives.md), for [Decide: how first-milestone directives load and unload their family styles](../issues/185-decide-lazy-family-styles.md). Model: Opus 5.5, with a Sonnet 5.5 sweep of other libraries' packages and of the `@layer` data (sections 6 and 7), spot-checked against the extracted files.

This file decides nothing. It lists the mechanisms that let a directive load its family's CSS when the first instance renders and remove it when the last is destroyed, what each costs, where the CSS can come from so the consumer's Foundation settings apply, and what remains unknown.

## 1. Options at a glance

| M3 | A `<link>` to a non-injected global style bundle (`inject: false`), counted by `SharedStylesHost.addStyles([], [url])` | yes (measured); critical CSS copied by Beasties stays (3.4) | yes, as a `<link>` (measured) | a separate, unhashed `.css` file (measured) | yes (measured) | yes, `ɵSharedStylesHost` |

## 2. Why a directive needs a carrier

- `@Directive` metadata has no `styles` or `styleUrl`; only `Component` adds them (`NG/packages/core/src/metadata/directives.ts:113`, `:544`, `:583`, `:594`, `:620`).
- A component cannot be a host directive: `Host directive ${type.name} cannot be a component.` (`NG/packages/core/src/render3/features/host_directives_feature.ts:289-290`, error code 310 at `NG/packages/core/src/errors.ts:61`). So a directive cannot borrow a component's styles through `hostDirectives`.
- Styles enter the document only when Angular creates a renderer for a component that has them (section 3). A directive therefore gets styles either by creating a component (M1, M1', M2) or by writing to the document itself (M3, M3', M4).

## 3. `SharedStylesHost`, `REMOVE_STYLES_ON_COMPONENT_DESTROY`, and the rendering modes

### 3.1 How styles are counted

- `SharedStylesHost` keeps two maps: inline styles keyed by their full text, and external styles keyed by URL, each with a usage count and the elements it created (`NG/packages/platform-browser/src/dom/shared_styles_host.ts:114`, `:120`, `:28-31`). `addUsage` increments an existing record or creates one element per style host (`:159-182`); `removeUsage` decrements and removes the elements when the count reaches 0 (`:184-200`). The host is application-scoped: `SHARED_STYLES_HOST` is provided with `useClass: SharedStylesHost` (`NG/packages/platform-browser/src/browser.ts:276-278`), and `ngOnDestroy` removes everything (`shared_styles_host.ts:202-207`).
- Every component view gets its own `createRenderer` call (`NG/packages/core/src/render3/view/construction.ts:247`). `DomRendererFactory2` caches one renderer per component type (`NG/packages/platform-browser/src/dom/dom_renderer.ts:220-288`) but calls `applyStyles()` (that is, `addStyles`) on every `createRenderer` for `None` and `Emulated` (`dom_renderer.ts:208-215`, `:675-677`, `:715-722`). When a component view is destroyed, core calls its renderer's `destroy()` (`NG/packages/core/src/render3/node_manipulation.ts:360-363`), which calls `removeStyles` (`dom_renderer.ts:679-686`). So the count is per component instance, not per type.
- `REMOVE_STYLES_ON_COMPONENT_DESTROY` defaults to `true` (`dom_renderer.ts:58-74`). With `false`, `destroy()` returns before `removeStyles` (`:680-682`) and styles stay once added.
- The style host is `document.head` for components in the document, or the shadow root (`NG/packages/core/src/render3/component_ref.ts:345-350`, `getStyleHost` at `:532-544`). New elements are appended (`shared_styles_host.ts:239-252`), so a lazily added style lands after everything already in `<head>` (measured: after the global `styles-*.css` link).

### 3.2 What `ViewEncapsulation.None` changes

- `None` uses `NoneEncapsulationDomRenderer` with no selector shimming (`dom_renderer.ts:647-687`, `default:` branch at `:270-281`); `Emulated` passes a component id and shims the text (`:689-715`, `shimStylesContent` at `:670`). Counting and removal are the same for both.
- Because records are keyed by text, two different `None` components with identical CSS share one `<style>` and one count. Measured: a second carrier type compiled from the same `.scss` added no element; an `Emulated` carrier from the same file added a second `<style>` (`measure.mjs` scenario T).
- Measured: a real `None` component's `<style>` is added when it renders and removed when it is destroyed (scenario P). The ticket's question whether `SharedStylesHost` removes a `None` component's styles on destroy: it does.

### 3.3 Two measured gaps in the count

1. **Leave animations stop removal and leak the count.** `NoneEncapsulationDomRenderer.destroy()` calls `removeStyles` only when `allLeavingAnimations.size === 0` (`dom_renderer.ts:683-685`). The set is application-wide (`NG/packages/core/src/animation/longest_animation.ts:171`): any `animate.leave` in progress adds its view (`NG/packages/core/src/render3/instructions/animation.ts:288`, `:416`; `NG/packages/core/src/render3/node_animations.ts:81`) and removes it when done (`node_animations.ts:181`, `:186`). There is no retry, so the decrement is lost, not delayed. Measured (scenario L1b): a callout inside an element with `animate.leave` was destroyed; 1.5 s after the leave ended the callout `<style>` was still in `<head>` with no callout on the page, and after one more add and remove it was still there (the count stayed at 1). Measured (scenario L2): the last callout destroyed while an unrelated element's leave animation ran also kept its `<style>` for good. The guard came from `857675fedb` ("delays removal of stylesheets when the element registry is present", fixing angular/angular#62942, "Stylesheet pruning causes removal of animate.leave classes before animation can happen"), reworked to the global set by `4924108630` (#63450).
2. **Dehydrated instances are not counted.** With incremental hydration, a block that has not hydrated has server DOM but no client component, so no usage. Measured (scenario S): the server `<style>` was reused at hydration (no element removed or re-added), and when the last hydrated callout was destroyed the `<style>` was removed while the dehydrated `#deferred-hydrate` callout was still on the page; its `padding-top` fell from 44 px to 0. Hydrating it (a click) re-added the style.

### 3.4 Server rendering, hydration, `@defer`, and event replay

- On the server every element the host adds gets `ng-app-id="<APP_ID>"` (`shared_styles_host.ts:245-248`). On the client the constructor finds `style[ng-app-id]` and `link[ng-app-id]` in `<head>`, strips the attribute, and records each with usage 0 (`:65-92`, `:135-136`); `addUsage` then reuses the element (`:168-174`; the `ng-style-reused` attribute is set in dev mode only). Links are keyed by the file name after the last `/` (`:80-85`). No other hydration code touches styles: `ng-app-id` appears only in that file under `NG/packages`, and the transfer-state script is `<APP_ID>-state` (`NG/packages/core/src/transfer_state.ts:166`) and carries no styles.
- A usage-0 record that no client component ever claims is never removed until the app is destroyed (inferred from `removeUsage` running only through `removeStyles`).
- Measured server HTML (`D:/tmp/nfs-research-182/ssr2.html`): carrier styles appear as `<style ng-app-id="ng">` for M1 and for M1' (the server waited for the dynamic import through `PendingTasks`); the M3 link appears as `<link rel="stylesheet" href="nfs-reveal-family.css" ng-app-id="ng" media="print" data-beasties-media="all">` plus a `<noscript>` copy. The rewrite to `media="print"` is Beasties critical-CSS inlining, which `@angular/ssr` runs on rendered pages (`SSR/fesm2022/ssr.mjs:1121-1162`, `preload: 'media-script'` at `:1152`), controlled by `optimization.styles.inlineCritical` (`BUILD/src/builders/application/schema.json:243`).
- Beasties also copied the reveal overlay's critical rules from `nfs-reveal-family.css` into the first, unmanaged `<style>` (measured). That element has no `ng-app-id`, so it is never removed: after the last overlay was destroyed and its `<link>` removed, a new `.reveal-overlay` element still computed the consumer's `rgba(255, 0, 0, 0.45)` (scenario R). The same would apply to any family that M3 serves and that is on the first page.
- `@defer` without a hydrate trigger: the server renders the placeholder only; the block's styles are added when it renders on the client (measured, scenario D). With `hydrate on interaction`, the server renders the content and its styles, and they stay in place, unclaimed, until the block hydrates (measured, scenario S) or until the gap in 3.3 item 2 removes them.
- Event replay: no code path links replayed events to styles. A replayed click that hydrates a block creates its components and so adds usage like any other render (measured for the hydrate-on-interaction block; inferred for replay in general).
- Prerendering uses the same server rendering, so the same rules hold (inferred, not built).

## 4. CDK's `_CdkPrivateStyleLoader` and its callers

- The service keeps a `WeakMap` from `ApplicationRef` to the loader types and their `ComponentRef`s (`COMP/src/cdk/private/style-loader.ts:21-30`). `load(type)` creates the component once per application with `createComponent(loader, {environmentInjector})` and never attaches it to a view or the DOM (`:46-68`). The only cleanup destroys the refs when the application is destroyed (`:57-60`). The created component's renderer applies its `None` styles once and is never destroyed, so the styles stay for the application's life. The commits that introduced it say why: overlay, ripple, and text-field styles had needed a manual global include, and the loader removed that step (`df21d2b09`, `855ed4948`, `ad18e6d74`). They state no reason for never unloading; the loader components hold small structural styles shared by many components (inferred).
- Loader components are hidden `None` components with a `styleUrl` and an empty template: `_VisuallyHiddenLoader` (`COMP/src/cdk/private/visually-hidden/visually-hidden.ts:15-21`), `_StructuralStylesLoader` (`COMP/src/material/core/focus-indicators/structural-styles.ts:15-21`), `_CdkOverlayStyleLoader` (`COMP/src/cdk/overlay/overlay-container.ts:15-19`), `_CdkTextFieldStyleLoader` (`COMP/src/cdk/text-field/text-field-style-loader.ts:14-18`), `_ResetsLoader` (`COMP/src/cdk/drag-drop/drag-drop-registry.ts:45-50`), `_MatRippleStylesLoader` (`COMP/src/material/core/ripple/ripple-renderer.ts:64-68`), `_MatBadgeStyleLoader` (`COMP/src/material/badge/badge.ts:69-73`).
- Callers: CDK a11y (`aria-describer.ts:55`, `focus-trap.ts:390`, `live-announcer.ts:278`), overlay (`overlay.ts:55`, `overlay-container.ts:96`), text-field (`autosize.ts:130-131`, `autofill.ts:77`), drag-drop (`drag-drop-registry.ts:158`); Material badge (`badge.ts:171-173`), button (`button-base.ts:159`), button-toggle (`:677`), checkbox (`:239`), chips (`chip.ts:257-259`, `chip-action.ts:86`), datepicker (`calendar.ts:73`, `calendar-body.ts:233`, `datepicker-base.ts:189`, `month-view.ts:221`), expansion (`expansion-panel-header.ts:68`), list (`list-base.ts:181`), menu (`menu-item.ts:88`), option (`option.ts:140-142`), radio (`:598`), ripple (`ripple-renderer.ts:125`), slide-toggle (`:210`), slider (`:417`), sort (`sort-header.ts:121`), stepper (`step-header.ts:88-90`), tabs (`tab.ts:141`, `tab-nav-bar.ts:339`). All paths under `COMP/src/cdk/` or `COMP/src/material/`.
- `MatBadge` is a directive (`selector: '[matBadge]'`, `COMP/src/material/badge/badge.ts:76-77`) that loads its whole family stylesheet, `badge.css`, this way: the closest prior art to this library's case. Its CSS is compiled when Material is built, and consumer theming reaches it at run time through CSS custom properties (`token-utils.slot` returns `var(--...)` with fallbacks, `COMP/src/material/core/tokens/_token-utils.scss:7-11`, `:50-66`; used in `COMP/src/material/badge/badge.scss:4`, `:10`, `:31`). Foundation's settings are Sass globals resolved at compile time (ADR 0012), so this route does not carry them.
- Material's breaking-change notes for the move record the cascade cost: "The overlay stays [styles] are now loaded slightly later than before which can change their specificity" (`df21d2b09`) and the same for ripples (`855ed4948`).
- A reference-counted variant needs (inferred from 3.1 and 3.3): one carrier per directive instance instead of per application (M1), or a count per family in a service that creates the carrier at 0 to 1 and destroys it at 1 to 0. Either way, removal through the carrier's renderer is subject to the global leave-animation guard (3.3 item 1), so a variant that must unload after `animate.leave` either delays the carrier's destroy until the host element's own animations have finished and no others run, or counts and removes outside the renderer (through `ɵSharedStylesHost.removeStyles`, which has no guard, `shared_styles_host.ts:151-157`, or its own elements as in M3'). It also needs to count server-rendered, not-yet-hydrated instances, or keep a family's styles while any dehydrated block that uses it remains (3.3 item 2). How to detect either from a directive is not established here.

## 5. Where the CSS comes from

### 5.1 Library-compiled CSS (the ADR 0012 constraint)

- A published library's component styles are compiled when the library is built and ship as strings in the partial declaration: for example `styles: [".mat-focus-indicator {..."]` inside `ɵɵngDeclareComponent` (`PRIOR/@angular__material/package/fesm2022/_structural-styles-chunk.mjs:13`, `:22`). The consumer's `stylePreprocessorOptions` never reach them. This is ADR 0012's reason: such CSS renders Foundation's defaults ([ADR 0012](../adr/0012-sass-packaging.md)).

### 5.2 A carrier component in the consumer's project (M1, M1')

- The application builder compiles component stylesheets with the project's `stylePreprocessorOptions.includePaths` (`BUILD/src/builders/application/setup-bundling.js:80-93`), passed to Dart Sass as `loadPaths` (`BUILD/src/tools/esbuild/stylesheets/sass-language.js:164`). Foundation's docs have the consumer import a settings file before Foundation (`FDN/docs/pages/sass.md:79-87`; `FDN/scss/foundation.scss:18-20`).
- Measured: a carrier in the probe app, `@Component({styleUrl: './callout-styles.scss', encapsulation: None, template: ''})` with `@import 'settings'; @import 'foundation-sites/scss/foundation'; @include foundation-callout;` and `includePaths: ["src/foundation-settings"]`, compiled to `.callout{...padding:2.75rem...}` from the consumer's `$callout-sizes` (Foundation's default is `1rem`; `FDN/scss/components/_callout.scss:53` reads `map-get($callout-sizes, default)`). The production output held only the family's rules, no normalize or banner (the Badge chunk is 642 bytes). Ticket 183 left open "how an application build would give each family file the same settings": `includePaths` plus one `@import 'settings'` per family file does it.
- The library registers carriers through a provider (the probe used `provideNfsFamilyStyles({callout: CalloutStyles, ...})` and an `InjectionToken`, `PROBE/src/app/app.config.ts`, `PROBE/src/lib/family-styles.ts`). A generator in the consumer's workspace, like the Variant declaration file generator of [ADR 0040](../adr/0040-variant-input-types.md), could write the carriers and the provider call (not built).
- First paint and chunks: M1 puts each carrier's CSS string in the bundle that imports the provider, here `main-*.js` (measured), so the bytes load eagerly and only the insertion is lazy. M1' maps a family to `() => import('./badge-styles').then(m => m.BadgeStyles)`; the builder emitted `chunk-SNL6UJWX.js` named `badge-styles` as a lazy chunk (measured), the server waited for it through `PendingTasks.run` and put the `<style>` in the HTML (measured), the client fetched the chunk at hydration and reused the server `<style>` (measured, `measure-lazy.mjs`). On a client-only first render the element appears before the chunk resolves, so at least one frame is unstyled (inferred; not measured on a cold network). The probe needed a `destroyed` flag so a directive destroyed before the import resolved does not create its carrier.
- What a consumer writes: the settings file on `includePaths` (or a relative import in the generated file), the generated carriers, and the provider call, rerun when it adds a family.

### 5.3 Non-injected global style bundles and a `<link>` (M3, M3')

- `styles` entries accept `{input, bundleName, inject}` with `inject` defaulting to `true` (`BUILD/src/builders/application/schema.json:121-147`). A non-injected entry is named after `bundleName` or the file name (`BUILD/src/builders/application/options.js:408-413`) and its output name has no hash (`bundles: '[name]'`, `BUILD/src/tools/esbuild/global-styles.js:43-48`); global entries also get `includePaths` (`:49`). Measured: with `outputHashing: all`, `{input: 'src/lazy/nfs-reveal-family.scss', bundleName: 'nfs-reveal-family', inject: false}` produced `dist/app/browser/nfs-reveal-family.css` (1.54 kB), listed by the builder under "Lazy chunk files", with the consumer's `$reveal-overlay-background` applied.
- Through the private `ɵSharedStylesHost` (exported at `NG/packages/platform-browser/src/private_export.ts:15`), `addStyles([], ['nfs-reveal-family.css'])` and `removeStyles` give a counted `<link>` with SSR output and hydration reuse (measured, scenario R). Two costs measured: the URL must equal the file-name key that `addServerStyles` derives (`shared_styles_host.ts:80-85`), because `'/nfs-reveal-family.css'` and `'nfs-reveal-family.css'` produced two `<link>` elements for the same file; and Beasties' unmanaged copy of the critical rules stays after unload (3.4). `removeStyles` here has no leave-animation guard, so it removes at once even while an element leaves (inferred from `shared_styles_host.ts:151-157`).
- M3' would do the same with public APIs: a root service that counts per family, inserts `<link rel="stylesheet">` into `document.head` (on the server too), adopts a server-rendered link on the client, and removes it after the count reaches 0 and any leave animation has finished (inferred, not built). CSP: `SharedStylesHost` copies `CSP_NONCE` onto every element (`shared_styles_host.ts:240-243`); M3' would have to as well (inferred).
- On the client, a newly inserted `<link>` applies only after the file loads. In the probe the re-inserted link had its sheet by the first animation frame, from the cache (measured); a cold fetch is not measured, so the unstyled interval for a family first used after navigation is unknown.
- What a consumer writes: one `styles` entry per family in `angular.json` or `project.json`, with `inject: false` and a `bundleName` the library knows; a generator could add them (not built). `bundleName` must match `^[\w\-.]*$` (`schema.json:134-137`).

### 5.4 Other sources

- Constructable stylesheets (M4): web-features `constructed-stylesheets` is Baseline high since 2025-09-27 (support Chrome 73, Edge 79, Firefox 101, Safari 16.4), so widely available on 2026-05-07 (`PRIOR/web-features/package/data.json`, version 3.40.0). Adopted sheets live outside the DOM, so server HTML cannot carry them and the first paint after SSR would lack the family (inferred). PrimeNG uses them only to mirror styles into shadow roots (`PRIOR/primeng/package/fesm2022/primeng-usestyle.mjs:62-75`).
- `externalRuntimeStyles`, which turns component styles into `<link>` URLs (`getExternalStyles`, `dom_renderer.ts:672`), is set only by the dev server for component style hot replacement (`BUILD/src/builders/dev-server/vite/index.js:145`); it is not a production option.

## 6. Cascade order and `@layer`

- Lazily added styles land in runtime order. Measured: after a family's `<style>` was removed and re-added it moved behind the M3 `<link>` in `<head>` (scenario S, `S_afterHydratingDeferred`). Ticket 183 measured the one first-milestone pair where order changes the computed style, `foundation-menu` before `foundation-drilldown-menu` and `foundation-dropdown-menu` (equal specificity), and Foundation's source order is `foundation-everything` (`FDN/scss/foundation.scss:80-150`).
- Baseline: web-features `cascade-layers` is Baseline high, low date 2022-03-14, high date 2024-09-14; support Chrome 99, Chrome Android 99, Edge 99, Firefox 97, Firefox Android 97, Safari 15.4, Safari iOS 15.4. Every browser of the map's core table (Chrome, Chrome Android, Edge, Firefox, Firefox Android 119; Safari and Safari iOS 17) is at or past those versions (`PRIOR/web-features/package/data.json`, version 3.40.0). `@import url() layer()` has the same dates and versions (BCD `css.at-rules.import.layer`, 8.1.3). There is no `layer` attribute on `<link>` or `<style>`: BCD's `html.elements.link` lists none, the HTML standard has no match, and Cascade 5 carries the open issue "Provide an attribute for assigning link or style elements to cascade layers?" (w3c/csswg-drafts#5853, section 6.4.1).
- The spec (https://drafts.csswg.org/css-cascade-5/): "Cascade layers are sorted by the order in which they first are declared" and "Unlayered rules are sorted later than any layered rules within the same parent layer" (section 6.4.3, `#layer-ordering`); an empty statement "allows a page to declare the order of its layers up front" (section 6.4.4.2, `#layer-empty`); "for normal rules the declaration whose cascade layer is latest in the layer order wins, and for important rules the declaration whose cascade layer is earliest wins", with unlayered declarations in an implicit final layer (section 6.1, `#cascade-sort`); "the layer order is global to the document" (section 6.4.3 note).
- Measured in Chromium 153, Firefox 155, and WebKit 26.6 (`measure-layer.mjs`), with `<style>@layer nfs.base, nfs.callout, nfs.button;</style>` first in `<head>`: two layered sheets appended in reverse of the declared order still resolved in declared order; an unlayered `div` rule beat a layered `.callout.primary`; a layered `!important` beat an unlayered `!important`; a layer name first seen in a later sheet sorted after the declared ones.
- So one order statement, placed before every lazily added sheet, fixes the order among layered family sheets whatever their insertion order. The statement has to come first in tree order (the spec orders by first declaration; inferred to mean document order of style sheets): Angular appends to `<head>`, and the global `styles-*.css` link came before every lazy style in the probe (measured), but Beasties put its inlined `<style>` ahead of that link (measured). Whether Beasties keeps an `@layer` statement from `styles.css` in its inlined copy, and so in first position, is not measured.
- A consumer's unlayered rule beats every layered library rule regardless of specificity (measured). That helps consumer overrides, and it also means Foundation's own unlayered global output wins against layered family rules: `foundation-global-styles` resets `button` to `padding: 0; border: 0; background: transparent` (`FDN/scss/_global.scss:223-231`) and typography sets `a { color: $anchor-color }` (`FDN/scss/typography/_base.scss:343-346`), which an unlayered tag rule would apply over a layered `.button` (inferred from the measured rule). Layered family CSS therefore needs the consumer's global Foundation output in an earlier layer too, or stays unlayered. Dart Sass 1.104.1 compiles `@layer nfs.callout { @include foundation-callout; }` to one `@layer nfs.callout{...}` block (measured); wrapping `foundation-global-styles` was not tried.
- `!important` reverses: Foundation's first-milestone families have few or none, and most of Foundation's `!important` sits in later-milestone utilities (`_visibility.scss` 16, `prototype/` 47, `_float.scss` 2) and in `_global.scss:218`, `:251`, `:255` (`.is-visible`, `.is-hidden`) (counted with `rg -c '!important'` under `FDN/scss`).

## 8. Open unknowns

- How a directive can tell that a server-rendered instance of its family is still dehydrated, so a counted mechanism does not remove styles under it (3.3 item 2), and whether this matters for families used only inside hydrate-triggered `@defer` blocks.
- How to time removal after `animate.leave` without the leak (3.3 item 1): whether a per-directive delay based on the host element's animations is enough while other leave animations run, and whether Angular plans to change the guard. No Angular issue was searched for the leak itself.
- Whether Beasties keeps an `@layer` order statement first, and whether `inlineCritical: false` is an acceptable consumer requirement for M3, which otherwise leaves critical rules behind after unload.
- The unstyled interval on a cold fetch for M1' and M3 when a family is first used after client navigation.
- Whether `foundation-global-styles` and `foundation-forms` compile and behave when wrapped in a layer, and what the consumer would write for that.
- The cost of M1's one hidden component view per directive instance on pages with many instances; not measured.
- The probe covered SSR with `RenderMode.Server` in Chromium only; prerendering, Firefox, and WebKit hydration were not run.
- Whether the Variant declaration generator, which reads `:root` properties from a compile of the global stylesheet, sees families moved into carriers or lazy bundles (also open in ticket 183).
