# Architecture audit: group a

Group: a. Specs audited: `specs/abide.md`, `specs/accordion.md`, `specs/accordion-menu.md`, `specs/anchored-pane.md`, `specs/badge.md`, `specs/breadcrumbs.md`, `specs/breakpoint-service.md`, `specs/button-group.md`, `specs/button.md`. Guide version: `architecture-guide.md`, last dated change 2026-09-28 (revised the same day after the critic's review). Date of this audit: 2026-09-29.

Each spec was read in full and checked against every principle P1-P26 from the spec's class mapping, hierarchy and DI shape, API, ARIA and keyboard tables, rendered HTML, rendering modes, Sass subsection, and Testing Decisions, per the guide's own audit instructions. ADR 0044, ADR 0045, ADR 0046, and `specs/forgotten-import-checks.md` were read first, and every spec in this group was checked for its `nfsDirectiveCheck` statement, its per-part In-family check lines where it defines more than one directive, its parent token descriptions, and, for Breadcrumbs specifically (one of the eight families named in the shared spec's `strictParents` table), its `strictParents` effect statement.

## Summary of the one cross-cutting cause

Seven of the nine specs in this group carry the same gap: none states that its directive(s) call `nfsDirectiveCheck`, and the multi-directive specs (Abide, Accordion) do not list, or do not fully list in the required one-line-per-part form, the In-family check lines ADR 0046 and `specs/forgotten-import-checks.md` (2026-09-28) require. A search of this group's nine specs for `nfsDirectiveCheck` and `strictParents` finds them only in `breakpoint-service.md` (the shared infrastructure spec that defines the mechanism) and, partially and in a non-conforming combined-paragraph form, in `accordion.md`. This is the same pattern a sibling group's audit (`research/architecture-audit-b.md`) independently found across all nine of its own specs: the gap is spec-currency (specs written or last revised before the shared checks spec landed), not a defect in the guide. It is recorded once per spec below, under P24, the lowest-numbered principle each falls short of.

The two specs with no finding, `anchored-pane.md` and `breakpoint-service.md`, define no attribute-selector directives of their own (Anchored pane is pure functions and one cross-instance service; Breakpoint service hosts the shared checks infrastructure other specs call), so P24's directive-check requirement does not bind them.

## Guide problems

The P24 rule itself (and the ticket's instruction to check every family spec against it) is sound, testable, and restates a recorded decision (ADR 0046); the cross-cutting gap above is spec-currency, not a defect in the guide. Four narrower ambiguities surfaced while auditing individual principles. None rises to "no spec could ever meet it", but each is capable of producing two different verdicts on the same spec text from two auditors:

1. P13's four-step Variant-input order ("a Foundation Option that names the family, then the hosted Aria input's name, then one enum..., then a boolean...") reads as either a per-input naming rule (pick whichever tier names one family) or a required declaration order across all of a directive's inputs. Under the second reading, `button-group.md`'s declared input order (`size, color, fill, expanded, stacked, stackedFor, noGaps`) interleaves an enum among booleans and would fail; under the first it passes cleanly. P14's own `NfsDropdownPane` Preferred example (`position, alignment, hover, hoverDelay, closeOnClick, and the rest`) also mixes enums and booleans with no visible grouping, which supports the first reading, but the guide never states which reading is intended. Evidence: architecture-guide.md P13 (Rule) and P14 (Preferred); `specs/button-group.md`'s API section input order.
2. P10's Rule and Preferred/Avoided examples are phrased entirely in directive and component terms (`input()`, `model()`, Variant transforms) and never say whether the "Shared service, function, token, or type" kind is inside its scope at all, even though the guide's own "The kind decides which principles apply" sentence implies some principles do not bind every kind. `breakpoint-service.md`'s plain, non-computed predicate methods (`atLeast`, `upTo`, `only`, `is`, `resolve`) would read as an Avoided form if P10 binds services, yet nothing in P10 says one way or the other. Evidence: architecture-guide.md P10 (Rule, Preferred, Avoided) and the "Kinds of building block" table's service row; `specs/breakpoint-service.md`'s API table and Design decision 5.
3. P26's focus baseline states "one tab stop per composite" as universal, but the real APG Accordion pattern (which `accordion.md` correctly follows, `tabindex="0"` on every title) does not use roving tabindex the way Tabs or Menu do -- every accordion header is independently Tab-reachable. Whether building-blocks 1.10's own "composite" language already excludes Accordion could not be confirmed without reading building-blocks.md directly; flagged for the judge rather than recorded as a finding against accordion.md. Evidence: architecture-guide.md P26 (Rule, "one tab stop per composite"); `specs/accordion.md`'s keyboard table (independently focusable titles).
4. P4's rule text ("A parent provides an `InjectionToken`... a child injects it") reads as universal for any parent/child cooperation, but the "Kinds of building block" table's Coordinating-directive entry defines coordination as registration-bearing ("children... register with the parent"). `breadcrumbs.md` documents a third shape -- an optional class-injection lookup that powers only a one-off development warning, with no token, no registration, no ordering -- and cites this as shared precedent with Menu and Pagination. The guide never states whether this reachability-only shape needs a lightweight token or is exempt from P4. Evidence: architecture-guide.md P4 (Rule) and the Coordinating-directive row; `specs/breadcrumbs.md`'s Hierarchy and DI shape section.

## Principles checked hardest but yielding no further findings in this group

P1/P2 (directive-not-component; one directive per Structural class: badge, button, button-group, accordion parts), P3 (no consumer-written class throughout), P5/P6 (native element choice; `NfsAccordionMenu`-style hosting of `NfsMenu`; Triggers written beside `nfsButton`, never hosted), P7/P8 (composition over inheritance; `hostDirectives` limits), P9 (input-name collisions: button's `size` versus the native attribute, button-group versus button on non-shared elements), P11 (state source of truth: `aria-current` in breadcrumbs per ADR 0042, `data-nfs-*` in accordion-menu per ADR 0033), P14 (every input traces to Foundation, Aria, the APG, WCAG, or Material, no target count), P16 (Implementation level: Aria and CDK rejections argued with evidence in accordion-menu, anchored-pane, button-group), P17 (WCAG 2.2 AA gates: button's 24px floor, breadcrumbs' and accordion-menu's exact-formula contrast checks), P18 (Sass mixins only, no runtime theming), P19 (animation via State classes and CSS only), P21 (no library strings; `Directionality` used narrowly), P22 (entry-point boundaries, type-only registry imports), P25 (DOM-first tests, no custom harnesses), P26 (member visibility, id generation, focus restoration).
