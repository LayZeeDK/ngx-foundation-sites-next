## 1. How this lens read the rows

Four questions per row, from the consumer's side of the library: would an Angular developer expect a directive, input, output, or method here; does the exclusion force the consumer to write a Foundation class, a DOM call, or a workaround that the class rule (ADR 0039) or the guide rules out; do Angular Aria, the CDK, or Material offer the equivalent; and what does bringing it in cost in API surface. The smallest API that removes a real gap wins; an exclusion whose only cost is one consumer attribute in the consumer's own namespace is not a gap.

Rulings applied that postdate many rows: ADR 0039 (consumers write no Foundation or NFS class, not even as an input value; inputs that take the consumer's own classes stay), ADR 0040 (typed Variant inputs over registries; a Variant input defaults to no class), ADR 0044 (utility families), ADR 0045 (additive API lands in a minor release, so "additive later" is a cheap and sound reason; a removal waits an Angular major; migrations are Nx migrations first, reused as `ng update` migrations), and the guide's P11 (one source per state; initial state is bound, never read from a static class), P14 (every Foundation Option is an input unless dropped with a listed reason), P20 (the native control carries the value), and P21 (no library strings, no name input for an element the consumer writes).

Every `new` row (417), the four `carried` rows, and every `re-checked` row that ADR 0039, 0040, 0041, 0042, 0043, 0044, 0045, or the guide bears on has a verdict below. Two rows fail in part; everything else holds. Nothing from this lens is HIGH impact with NOT HIGH confidence.

Under the class rule every Foundation container a pane might be bounded by (a card, a callout, a grid cell, the Off-canvas content) has its classes bound by a library directive, so `parentClass` always needs an application class the consumer adds for the lookup alone (`specs/dropdown.md:278`, D6 `:574`). ## 4. Rows whose stated reason is wrong, loose, or missing though the verdict holds

- abide-10: the bullet (`specs/abide.md:540`) lists `select`, `textarea`, radio groups, and checkbox groups as out of scope, but `NfsAbideInput`'s selector is `input[nfsAbideInput], textarea[nfsAbideInput], select[nfsAbideInput]` (`:217`), `aria-invalid` is rendered on `select` hosts (`:499`), and the keyboard table covers radios and checkboxes (`:361-363`). The exclusion is a test-coverage boundary ("beyond what the Prototype covered"), not an API gap; reword to "behaviour of those controls beyond the prototype's cases is untested, not unsupported", or the sentence reads as if a `<select>` in an Abide form has no error binding.
- breakpoint-service-17: "no consumer; `upTo` covers it" is loose. Foundation's `next(size)` returns the next breakpoint's name (`js/foundation.util.mediaQuery.js:226`) and `upTo` calls it (`:161`), so `upTo` does not cover `next`'s return value; the reason is that no directive or consumer needs the name. Holds on that reason.
- progress-bar-6: the Out of Scope bullet (`specs/progress-bar.md:394`) gives no reason; the Animation section has it: "a transition on `width` would show a value the ARIA attributes no longer carry" (`:317`). Cite it in the bullet (P14 asks each drop to carry its reason).
- responsive-accordion-tabs-9 (RAT8): the bullet (`:600`) gives no reason; `:496` has it (the component's state is `selected`, not tied to an animation in tabs mode; a consumer who needs `opened`/`closed` uses the Accordion directly). Cite it.
- reveal-11 (RV9): "not elaborated" at ticket 79 and still not. The reason: a Reveal is a `<dialog>` in the consumer's template, so navigating away from the route that declares it destroys it; Material's `closeOnNavigation` exists only because its dialogs live in an overlay outside the route. A Reveal declared in the application shell is closed by the consumer's own router event handler. Record it.
- Bullets marked "not elaborated" or "unelaborated" in the evidence whose reason exists elsewhere in the bundle and should be cited where the drop is listed (P14): responsive-menu-8 (RM3), dropdown-menu-6 (DM16), dropdown-menu-7 (DM17; the animation half's reason is D12, `specs/dropdown-menu.md:587`, and the close-reason half has none recorded), accordion-menu-7, accordion-menu-9, accordion-menu-10, accordion-menu-11, drilldown-menu-9, triggers-9 (D12 and D13), variant-declaration-tooling-6 (`:428`), variant-declaration-tooling-7, media-object-8 (D7).
- dropdown-11: the reason is right; add to D6 that under the class rule the bounding element is almost always library-classed, so the application class is the expected form, not the exception (section 2's note).
- prototyping-utilities-3: the reason is right; the bullet should say plainly that classes generated from a name added to `$prototype-sizing` cannot be set by any directive until the keyed input lands, since the class rule leaves the consumer no other way to write them.
- switch-14: the reason ("the library's switch markup needs none") is right but reads as if `.show-for-sr` were unsupported; cite D4 (the visible label replaces Foundation's hidden-text name, measured double naming).
- variant-declaration-tooling-4: the reason speaks only of the declaration file; section 2.

## 5. For the judge

- Nothing from this lens is HIGH impact with NOT HIGH confidence, so nothing goes to the user on this lens's account.
- Two verdicts touch shared records and should be confirmed by the judge rather than applied by a re-run alone: the migrations half of variant-declaration-tooling-4 records a home for `migrations.json` that ADR 0045 presumes and no spec names; input-1 adds a base-style setting to a Library mixin's check, which the map's base-styles line (`map.md:309`) does not forbid (no directive, no class) but which the Typography Helpers spec's Out of Scope bullet (`:413`) currently excludes by name.
- The five verdicts this lens is most sure of: variant-declaration-tooling-4 (migrations) fails in part; input-1 fails in part; abide-10 holds with a wrong-reading bullet; dropdown-11 holds; menu-5 holds (Foundation's own defect and deprecation, not a library choice).
