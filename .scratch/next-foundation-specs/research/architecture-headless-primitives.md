# Headless primitives and the web platform: what they say about directive and component architecture

Question: what design principles do the headless and primitive component libraries state for themselves, what does the web platform now provide, and how does each translate to an Angular library of directives and components over Foundation for Sites' CSS? ## 1. Headless separation of behaviour from imposed styling (draft P1, P8)

**Principle.** A component library's job is to supply accessible interaction and structure; the visual layer is left to (or handed to) something else.

**Evidence.** Radix: "Unstyled: Components ship without styles, giving you complete control over the look and feel" (`overview/introduction`). React Aria: "React Aria is style-free out of the box, allowing you to build custom designs... using any styling and animation solution" (`react-aria/index.html`); "React Aria does not include any styles by default" (`getting-started.html`). Headless UI: "Completely unstyled, fully accessible UI components" (`headlessui.com/`). Zag: "Headless: The machine APIs are completely unstyled and give you the control to use any styling solution you prefer" (`zagjs.com/overview/introduction`). Base UI ships components that render semantic markup and ARIA state but no CSS (implied throughout `base-ui.com/react/overview/accessibility`, which discusses only behaviour, focus and labelling, never appearance).

**Applies to an Angular 22.2 library over Foundation's CSS.** Directive-first is this effort's form of "headless": a directive attaches behaviour and ARIA attributes to an element the consumer already wrote, exactly as React Aria's hooks or Radix's unstyled parts attach behaviour to a DOM node without owning its class list. But the analogy inverts on styling: the five React libraries above leave visual design entirely to the consumer, while this library's standing preference is the opposite -- "Foundation CSS classes and state classes... are the styling contract... custom CSS only for what Foundation cannot express" (`../map.md`, Standing preferences). The library is headless about *behaviour* (no library ships its own visual language on top of Foundation) but opinionated about *styling* (Foundation's Sass is the one visual language, applied by the directive, not left open). That is a stronger contract than any of the five libraries offer their consumers, and the reason for it (Foundation's class-based contract, not a consumer choice) does not weaken the underlying principle: attach behaviour without inventing new structure.

**Strength.** Strong. Every fetched primary source states this as a first-listed feature, and it matches the map's existing "Foundation's Sass styles only, no Foundation JavaScript" domain note.

**Where it holds, needs a qualification, or conflicts.** Holds directly for P1 and P8. Qualification: "headless" in this effort means "no parallel styling system," not "no styling system" -- Foundation's classes are the mandatory style layer, which none of the five React libraries impose.

## 2. Compound parts as the anatomy of a coordinating component (draft P3, P6; APG anatomy)

**Principle.** A component that needs more than one element to work is modelled as a small set of named, individually-styleable parts, not one component with props for every variant.

**Evidence.** Radix Accordion's stated anatomy: `Accordion.Root > Accordion.Item > Accordion.Header > Accordion.Trigger`, plus `Accordion.Content` as a sibling of `Header` inside `Item` (`components/accordion`, "Anatomy"). React Aria's own tutorial states the rule directly: "Each React Aria component renders a single DOM element. Complex components like Select compose together multiple parts to build a complete pattern" (`getting-started.html`, "Build a component from scratch," step 1); its Select example composes `Select > Label + Button > SelectValue + Popover > ListBox > ListBoxItem`. Headless UI's Disclosure is `Disclosure > DisclosureButton + DisclosurePanel`, each "a default element that is sensible for that component" (`headlessui.com/react/disclosure`, "Rendering as different elements"). shadcn/ui states this as a house rule, not a per-component accident: "Every component uses a common, composable interface, making them predictable... If a component does not exist, we bring it in, make it composable, and adjust its style to match" (`ui.shadcn.com/docs`, "Composition").

The WAI-ARIA APG encodes the same anatomy at the specification level, as named roles with defined relationships rather than as an implementation detail of one library. Tabs: "the element that serves as the container for the set of tabs has role `tablist`... each element that serves as a tab has role `tab`... each element that contains the content panel for a tab has role `tabpanel`," linked by `aria-controls` (tab to panel) and `aria-labelledby` (panel to tab) (`content/patterns/tabs/tabs-pattern.html`, "WAI-ARIA Roles, States, and Properties"). Accordion: the header `button` element carries `aria-expanded` and `aria-controls` pointing at the panel (`content/patterns/accordion/accordion-pattern.html`, same section). Dialog (modal): the container carries `aria-modal="true"` and `aria-labelledby` pointing at a visible title (`content/patterns/dialog-modal/dialog-modal-pattern.html`). Menu button: the trigger carries `aria-haspopup` and `aria-expanded` (`content/patterns/menu-button/menu-button-pattern.html`). Every one of the five libraries' compound-part designs is a direct rendering of one of these APG anatomies; none invents its own part vocabulary.

**Applies to an Angular 22.2 library.** This is already the shape building-blocks.md records: a coordinating component (or a directive that hosts another directive) per part, joined by DI rather than props. Section 1.8 (Triggers) defines a shared `NfsOpenable` contract (`isOpen`, `id`, `triggerRole` as signals, plus `open()`/`close()`/`toggle()`) that any Trigger reaches through the lightweight `nfsOpenableToken` -- the Angular equivalent of Radix's `Accordion.Trigger` reading shared state from its nearest `Accordion.Item`, done through injection instead of React context. Section 1.9 records "Hosting a class directive": a directive whose element is always another component's structural class hosts that component's directive through `hostDirectives` (Accordion Menu, Drilldown and Dropdown Menu roots host `NfsMenu`), which is this effort's version of composing named parts without inventing a new element for each one.

**Strength.** Strong. Cross-library and cross-specification consensus (five component libraries and the APG itself), and it already matches recorded decisions in this repository, not just the draft.

**Where it holds, needs a qualification, or conflicts.** Holds for P3 and P6 without qualification. Extends P6's "one clearly defined responsibility" rule with a concrete anatomy source: where Foundation and the APG both name a part (tab/tablist/tabpanel, accordion header/panel, dialog title), that name is the one to give the directive or component, not a library-invented synonym.

## 3. In Angular, the `asChild` / `render` / `as` escape hatch has no equivalent problem to solve (new)

**Principle.** Radix, Base UI, Headless UI and Ark UI each ship a prop that changes which element a part renders, because in React a component owns the element it returns; Angular directives never have this problem, so the prop itself does not translate.

**Evidence.** Radix: "`asChild`... When set to `true`, Radix will not render a default DOM element, instead cloning the part's child and passing it the props and behavior required to make it functional... Your component must spread props... Your component must forward ref" (`guides/composition`). Base UI: "Use the `render` prop to compose a Base UI part with your own React components... The custom component must forward the `ref`, and spread all the received props" (`handbook/composition`). Headless UI: "`Disclosure` and its subcomponents each render a default element... Use the `as` prop to render the component as a different element... making sure your custom components forward refs" (`react/disclosure`, "Rendering as different elements"). Ark UI: "The `asChild` prop lets you integrate custom components, ensuring consistent styling and behavior" (`ark-ui.com/docs/guides/composition`, via WebFetch summary), with the same nested-Popover-Trigger-inside-a-custom-button example as Radix's.

The common cause named in every one of these four sources is the same: a React component decides its own root element and must be told, explicitly, to render someone else's element instead, and the consumer's replacement component must cooperate (accept and spread props, forward a ref) for the substitution to keep working.

**Applies to an Angular 22.2 library.** An Angular attribute directive never renders an element -- it attaches to whatever element the consumer already wrote (`<button nfsButton>`, `<a nfsButton>`). There is no default element to override and therefore no prop needed to override it; "changing the element type" (Radix's own first example, switching `Tooltip.Trigger` from `button` to `a`) is simply writing the directive on a different tag. `hostDirectives` covers the one case that remains -- a *component* that must always render another directive's behaviour on its own host, such as this effort's Accordion Menu hosting `NfsMenu` (`../building-blocks.md` 1.9) -- and that case has no prop-based equivalent in the surveyed libraries at all; it is closer to what those libraries do internally to compose one part's hook into another (React Aria's `useMenuTrigger` calling `useOverlayTrigger`) than to `asChild`.

**Strength.** Strong as a negative claim (four independent primary sources name the same React-specific cause), and it resolves a possible misreading of the draft: P1's "directive-first" is not "the Angular translation of `asChild`" -- directives make the entire category of problem `asChild` exists to solve not apply.

**Where it holds, needs a qualification, or conflicts.** No conflict. The one place a genuine analogue appears is content projection into a coordinating component (`<ng-content>` or a content-projected `ng-template`), where Angular's own DI rule -- "Angular resolves injection against the injector where the content is declared, not where it renders" (`adev/.../hierarchical-dependency-injection.md`, quoted in `research/di-and-composition-patterns.md` section 2) -- creates a different problem (projected content cannot see a parent's `viewProviders`) with a different, already-documented fix (`providers` instead of `viewProviders`, or an explicit injector on an `ngTemplateOutlet`), not `asChild`.

## 4. Controlled and uncontrolled state pairs translate directly to `model()` (draft P4)

**Principle.** A stateful part should work standalone (the library owns the state) and also accept external control (the consumer owns the state), through one prop pair, not two different APIs.

**Evidence.** Radix Accordion.Root: "Can be controlled or uncontrolled" (features list), with `value`/`onValueChange` (controlled) and `defaultValue` (uncontrolled) as sibling props on the same component (`components/accordion`, "API Reference"). The introduction states this as a named design goal: "Uncontrolled: Where applicable, components are uncontrolled by default but can also be controlled... without needing to create any local states" (`overview/introduction`). Headless UI's Disclosure mirrors the pattern with `defaultOpen` (uncontrolled) plus a `data-open`/`open` render prop for reading state back out, though (unlike Radix) it has no `onOpenChange`-style controlled input on the base component shown in the fetched docs.

**Applies to an Angular 22.2 library.** This is a closer match than most draft principles: Angular's `model()` *is* a controlled/uncontrolled pair in one declaration -- unbound, it behaves like `defaultValue` (internal signal, default value); bound with `[(expanded)]`, it behaves like `value` + `onValueChange` together, and Angular generates the `expandedChange` output itself. This repository already does this: `AccordionTrigger.expanded = model<boolean>(false)` (`research/di-and-composition-patterns.md` section 3e) and this effort's own `NfsAccordionItemDef.expanded = model(false)` (section 7) both follow it. No new API is needed to adopt this principle; `model()` already is Angular's answer to Radix's "controlled or uncontrolled."

**Strength.** Strong, and already in use, not merely proposed.

**Where it holds, needs a qualification, or conflicts.** Holds without qualification for any part with primary state (open/closed, selected value, expanded). Angular's `linkedSignal` is the tool for Radix's secondary case -- internal state that must track a controlled input but can also diverge locally (Aria's `TabList._selectedTabPattern`, cited in the same research file, section 8) -- which Radix and React Aria handle with a `useControllableState`-style hook; `linkedSignal` is the direct Angular counterpart and should be named as such in the guide.

## 5. Data attributes and render props for state, qualified against Foundation's class contract (draft P11)

**Principle.** Expose interactive state (pressed, hovered, selected, open) through a mechanism the styling layer can read without a parallel imperative API.

**Evidence.** React Aria: "Consistent default classes for each component... Style interactive states with data attributes: `&[data-pressed] { background: ... }`" (`react-aria/index.html`). Headless UI states the rationale directly: "Headless UI keeps track of a lot of state about each component... you can't see this information in your UI until you provide the styles you want for each state yourself... The easiest way... is using the `data-*` attributes that each component exposes" -- `data-open` on `DisclosureButton`, plus render props (`{ open }`) as the second mechanism for the same state (`headlessui.com/react/disclosure`, "Styling"). Base UI's Switch example exposes the identical pattern through its `render` function's second argument, `state` (`handbook/composition`, "Render function": `<Switch.Thumb render={(props, state) => ...}>`).

**Applies to an Angular 22.2 library.** The underlying need -- let CSS and consumer code read a part's interaction state -- is real and already answered here by a different, pre-existing mechanism: Foundation's own state classes. The map's standing preference is explicit that these classes *are* the styling contract ("Foundation CSS classes and state classes (`.is-active`, `.is-open`, and so on) are the styling contract... custom CSS only for what Foundation cannot express, as the smallest rule," `../map.md`). A directive already binds `[class.is-active]="item.expanded()"` (this repository's own accordion template, `research/di-and-composition-patterns.md` section 7); that binding is functionally the same feature as React Aria's `[data-selected]` or Headless UI's `[data-open]`, expressed through Foundation's existing vocabulary instead of a second, library-invented one. Introducing `data-nfs-*` attributes alongside Foundation's classes would duplicate the state signal Foundation's classes already carry, which the map's "smallest rule" preference and ADR 0039 ("directives manage every Foundation class") both argue against.

**Strength.** Moderate. The need is real and the evidence for it is strong across three libraries, but the specific mechanism (a parallel `data-*` attribute system) does not transfer; only the underlying requirement does, and it is already met.

**Where it holds, needs a qualification, or conflicts.** Conflicts with the map's Foundation-class-is-the-contract rule if implemented as `data-*` attributes. Qualification: adopt the requirement (state must be readable by the styling layer and by consumer code), reject the specific mechanism, and record that Foundation's own classes already satisfy it; a directive exposes state to *TypeScript* consumers (not CSS) as a `computed()` or the `model()`'s own signal, which the class binding does not.

## 6. Adherence to the WAI-ARIA APG as the one shared accessibility contract (draft P10)

**Principle.** Keyboard interaction, roles and ARIA state come from the APG pattern for the component, not from each library's own judgement.

**Evidence.** Radix: "Adheres to the WAI-ARIA design patterns where possible. We handle... aria and role attributes, focus management, and keyboard navigation" (`overview/introduction`); every component page states its specific pattern, for example Accordion's "Adheres to the Accordion WAI-ARIA design pattern" with a full keyboard interaction table (`components/accordion`, "Accessibility"). React Aria: "Components implement semantics and keyboard behavior according to the W3C ARIA Authoring Practices Guide. React Aria builds on this foundation with real-world testing and device support" (`react-aria/index.html`). Base UI: "Base UI components adhere to the WAI-ARIA Authoring Practices to provide basic keyboard accessibility out of the box" (`overview/accessibility`). Zag: "Focus on accessibility: Zag is built with accessibility in mind. We handle many details related to keyboard interactions, focus management, aria roles and attributes" (`overview/introduction`); Ark UI inherits this from Zag rather than restating it independently.

**Applies to an Angular 22.2 library.** This is already the map's own rule, stated independently of any of these libraries: "every directive and component complies with WCAG 2.2 AA, follows the matching WAI-ARIA APG pattern, and is axe-clean" (`../map.md`, Standing preferences). The five-library consensus is confirmation, not new information -- but it is useful confirmation, because it shows the rule is not this effort's own invention or an overreach: it is the default expectation of every serious component library surveyed, including the one (Base UI) built by a different vendor (MUI) than the other Adobe- and Vercel-adjacent libraries.

**Strength.** Strong; unanimous across every library fetched, and the map already enforces it.

**Where it holds, needs a qualification, or conflicts.** No conflict. One nuance worth recording: Radix's own accessibility pages cite the APG's *2018-era* URL pattern (`w3c.org/TR/wai-aria-practices-1.2`) in its introduction while individual component pages link the modern `w3.org/WAI/ARIA/apg/patterns/...` URLs, showing even libraries built specifically around APG conformance drift on which APG revision they track over time; this effort's rule of reading the APG from a pinned local clone (`d:/projects/github/w3c/aria-practices`) rather than "whichever page a library happened to cite" avoids that drift.

## 7. Explicit state machines as an internal model for multi-state interaction (new, qualified adoption)

**Principle.** Model a part's behaviour as a small number of named states with defined transitions, rather than a set of independent boolean flags that can combine into states nobody intended.

**Evidence.** Zag states this as its founding motivation: "In Chakra UI React, we've experienced too many hiccups and bugs in the past related to how we coordinate events, manage state, and side effects. Most of these bugs are associated with the orchestration within `useEffect`, `useMemo`, `useCallback`... We believe that most widgets should function the same way regardless of the framework they're built with... Zag is built on top of the latest ideas in Statecharts" (`overview/introduction`, "Motivation" and "Why Zag?"). Ark UI is Zag's component layer for React, Solid and Vue (confirmed by Ark's `asChild` composition doc importing from `@ark-ui/react`, `ark-ui.com/docs/guides/composition`, and by Zag's own framing of itself as "part of the next evolution of Chakra UI"). No other surveyed library (Radix, React Aria, Headless UI, Base UI) names an explicit state-machine model; they solve the same coordination problem with hooks, reducers and controllable-state helpers instead, without naming the underlying model.

**Applies to an Angular 22.2 library.** Zag's motivating complaint -- ad hoc `useEffect`/`useMemo` orchestration producing bugs -- is precisely the class of bug Angular signals and `computed()` are designed to remove by construction (a `computed()` cannot go stale the way a `useMemo` dependency array can be wrong). A full statechart runtime is not needed to get the benefit Zag describes; a directive whose internal state is a `computed()` deriving a named union type (for example a Combobox's `'idle' | 'open' | 'filtering' | 'no-results'`, rather than four independent booleans) gets the same "cannot combine into an impossible state" property Zag's machines provide, using only what this effort's Standing preferences already mandate (signals, `computed`, `linkedSignal`). This effort's own `NfsOpenable` contract (`../building-blocks.md` 1.8: `isOpen`, `triggerRole` as signals, `open()`/`close()`/`toggle()` as the only mutators) is already a small state machine in this lighter sense, expressed as a DI contract instead of a named library concept.

**Strength.** Moderate. Only one of the five libraries surveyed uses this model explicitly, and Zag's own reason for choosing it (cross-framework portability across React, Solid and Vue) does not apply to an Angular-only library, which weakens the case for adopting Zag's specific mechanism (a statechart interpreter) rather than its underlying discipline.

**Where it holds, needs a qualification, or conflicts.** No conflict with any recorded decision. Adopt with qualification: name multi-state interaction explicitly as computed union-typed state derived from signals, for any part with more than two meaningfully distinct states; do not add a state-machine library dependency, which neither the draft, the map's Implementation order (native, then `@angular/aria`, then `@angular/cdk`, then custom Angular), nor this effort's existing signal-only pattern calls for.

## 8. Copy-in distribution does not transfer; its composability rule already does (new, reject the mechanism)

**Principle (as shadcn/ui states it).** Ship component source code into the consumer's own repository instead of an installed package, so the "top layer" of every component stays open to edit.

**Evidence.** "This is not a component library. It is how you build your component library... shadcn/ui hands you the actual component code. You have full control to customize and extend the components to your needs" (`ui.shadcn.com/docs`, "Open Code"). shadcn/ui is built as a CLI-driven code generator over Radix (and, per the same page's component index, increasingly over Base UI) rather than as an npm dependency consumers install and upgrade.

**Applies to an Angular 22.2 library.** The distribution mechanism does not transfer: `ngx-foundation-sites` is destination-built as a published, versioned library (`../map.md`, Destination), which is exactly the model shadcn/ui's "Open Code" principle is written to replace ("this approach works well until you need to customize a component... you end up wrapping library components, writing workarounds to override styles"). Copying every directive's source into every consumer's repository would forfeit the versioning, security patching and single-source-of-truth properties a published library exists to provide, and nothing in the draft, the map, or this effort's recorded decisions asks for a code-distribution model.

**Strength.** Weak as a mechanism for this library; the one part of shadcn/ui's principle that does transfer -- "every component uses a common, composable interface, making them predictable... You are not learning different APIs for every new component" (`ui.shadcn.com/docs`, "Composition") -- restates section 2's compound-parts consensus and adds no new information beyond it.

**Where it holds, needs a qualification, or conflicts.** Reject the distribution mechanism outright; it conflicts with the map's Destination (one published library) and with npm as this repo's declared package manager. The composability half of the principle is already covered by section 2 and needs no separate adoption.

## 9. One DOM element per part, no incidental wrappers (draft P8, P12)

**Principle.** A part renders exactly the element the pattern needs, and nothing else; a directive is the more precise form of this than a component that happens to render one element.

**Evidence.** React Aria: "Each React Aria component renders a single DOM element" (`getting-started.html`), stated as a design constraint that shapes how compound parts are built, not an incidental fact. Radix: "reducing DOM wrappers" appears implicitly through the `asChild` feature (section 3) -- its entire purpose is to avoid Radix's own default element becoming an extra wrapper around the consumer's real one.

**Applies to an Angular 22.2 library.** An Angular attribute directive is a strictly tighter version of React Aria's "one element" rule: React Aria's one-element components still render *an* element (that a consumer might then wrap in yet another element for layout); an Angular directive renders *zero* additional elements, because it attaches to markup the consumer already wrote. Where a genuinely new element is required by the APG pattern itself -- a `tablist` container that does not otherwise exist in the consumer's markup, an off-canvas overlay pane -- the draft's own guidance (P3: components exist for coordination) already covers when a component, rather than a directive, is the right tool, and React Aria's rule confirms that even the component form should still render only the one element the pattern names, not extra structural wrappers around it.

**Strength.** Strong, and it strengthens rather than adds to the draft: P8 ("Preserve Native HTML... Reduce DOM wrappers") already states this, and React Aria's explicit design rule is independent confirmation from a library with no relationship to this effort.

**Where it holds, needs a qualification, or conflicts.** No conflict; extends P8 and P12 with a named source rather than changing them.

## 10. Open UI as a naming and anatomy cross-check, not a design source

**Principle.** Component and part names should follow the vocabulary the web platform community has already converged on across frameworks, not a name invented for one library.

**Evidence.** Open UI's charter states its research method directly: the group "focuses on capturing... commonly-used language for component names and parts, states, behaviors, and transition triggers," drawing on "documenting universal component patterns seen in popular 3rd-party web development frameworks," combined with "informal developer-facing user research" (`open-ui.org/charter`, read through WebFetch's isolated summary, quoted phrases as returned). The charter also states an explicit scope limit: the group "explicitly excludes novel design invention or platform-specific patterns, maintaining focus on standardizing widespread, proven interaction patterns already evident across the web development ecosystem," and its findings are delivered as draft proposals to WHATWG, CSSWG and W3C for adoption rather than treated as a standard on their own (same source).

**Applies to an Angular 22.2 library.** Open UI is a validation source for naming, not a design source for behaviour: it exists to answer "what does the web already call this part," which is exactly the question this effort's building-blocks and per-spec naming decisions already have to answer against Foundation's own vocabulary (`data-multi-expand`, `.accordion-item`) and the APG's vocabulary (`tab`, `tabpanel`). Where Foundation, the APG and Open UI's cross-framework research agree on a name, that is strong confirmation; where they disagree, Foundation's documented name wins per the map's Input naming rule ("Input names come from Foundation `data-*` options in camelCase," `../map.md`), since Open UI's own charter disclaims inventing new patterns and defers to existing, evident usage -- and Foundation's usage is exactly that kind of evidence.

**Strength.** Moderate. Open UI's own scope limit (no novel design invention) means it cannot resolve a genuine naming conflict; it can only report what already exists elsewhere, which this effort's other sources (Foundation, the APG, Angular Aria/CDK/Material) already supply directly.

**Where it holds, needs a qualification, or conflicts.** No conflict; treat as a secondary cross-check during naming decisions the building-blocks ticket already makes, not a required research step for every spec.

## 11. The web platform: Baseline status of the named features against the 2026-05-07 target (draft P9)

**Applies to an Angular 22.2 library.** Six of the eleven named features meet the target outright (`<dialog>`, `:focus-visible`, container size queries, ResizeObserver, IntersectionObserver, and -- already covered elsewhere in the same research file -- `position: sticky` and scroll-snap for the components that use them). The other five -- the Popover API, `:popover-open`, CSS anchor positioning, View Transitions, `:has()`, `:open`, and CSS nesting -- are each newer than at least one browser in the target table, several by a single version (Chrome 120 vs 119 for CSS nesting; Safari 17.2 vs 17 for the same; Firefox 121 vs 119 for `:has()`), which is the same "misses by one version" pattern `research/web-platform-features.md` already documents for `<details name>`. CSS nesting deserves particular note because it is a *tooling* feature (Sass already nests selectors) rather than a *component behaviour* feature: this library compiles Sass, so CSS nesting's Baseline status affects only whether this effort's own SCSS partials could someday drop the Sass compiler, not whether any directive or component can be built -- it does not belong in the same risk category as the Popover API or anchor positioning, which are unavailable component-behaviour building blocks, not optional tooling.

**Strength.** Strong; every verdict traces to a named engine version and a dated Baseline source, matching the ticket's own requirement.

**Where it holds, needs a qualification, or conflicts.** Directly qualifies draft P9 ("Browser capability > Light abstraction > Custom implementation"): the ordering is correct, but roughly half of the platform features the draft lists by name are not usable without a fallback on this map's own target, so P9 needs to be read as "prefer the browser capability once it is in the target set; until then, build the light abstraction (CDK Overlay, a measured positioner, a `keydown` Escape listener) and gate the browser path behind `@supports` or a feature check," which is exactly what `research/web-platform-features.md`'s per-plugin table already prescribes for Dropdown, DropdownMenu and Tooltip (all three "wait on popover and anchor positioning").

## 12. Translation summary: what stands in for `asChild`, context, and controlled/uncontrolled pairs

- **`asChild` / `render` / `as` (Radix, Base UI, Ark UI, Headless UI) -> nothing, in most cases; `hostDirectives` for the one case that remains.** Section 3 above: attribute directives already attach to the consumer's own element, so there is no default element to override. The residual case -- a coordinating *component* that must always carry another directive's behaviour on its own host -- uses `hostDirectives`, already in use in this repository (`../building-blocks.md` 1.9).
- **React context (every library's internal implementation of "the trigger knows about its panel") -> Angular DI**, specifically the token pattern this effort already follows: a lightweight `InjectionToken` on the parent (`useExisting`), optional or required injection in the child, `skipSelf` plus a `useValue: undefined` re-provide to stop nested instances registering upward (`research/di-and-composition-patterns.md` sections 1-3, and this effort's own `nfsOpenableToken` in `../building-blocks.md` 1.8). Where two parts are not DOM-nested (a trigger and a panel that live in different places, matching React Aria's Select `Button`/`Popover`/`ListBox` split), the same research file's section 3(d) pattern -- an `input.required<Target>()` template-reference link, with the target exposing `exportAs` -- is the Angular counterpart of passing a ref or an id between two React parts.
- **Controlled/uncontrolled pairs (`value`/`defaultValue`/`onValueChange` in Radix; `defaultOpen` plus a render prop in Headless UI) -> `model()`**, already in use (section 4 above). `linkedSignal` covers the secondary case of internal state that tracks a controlled input but can still diverge locally.
- **Data attributes and render props for state (React Aria, Headless UI, Base UI) -> Foundation's existing state classes, plus a `computed()` or the `model()` signal itself for TypeScript consumers.** Section 5 above: the requirement transfers, the specific `data-*` mechanism does not, because Foundation's class contract already serves the CSS half of the need.
- **Explicit state machines (Zag, and Ark UI through Zag) -> named union-typed `computed()` state**, not a state-machine library dependency (section 7 above).
