# Foundation 6.9's Sass, compiled one family at a time

Ticket: [Research: splitting Foundation 6.9's CSS per family](../issues/183-research-foundation-sass-per-family-split.md), for [Decide: how first-milestone directives load and unload their family styles](../issues/185-decide-lazy-family-styles.md). Model: Sonnet 5.5. Resolved 2026-10-01.

This file decides nothing. It reports what compiles alone, what each compile emits and weighs, which families need another family's rules or source order, which emit rules that apply with no directive on the page, what the full `foundation-everything` compile adds that per-family compiles do not, and how far the library's own Library mixins can follow.

Sources and path prefixes:

- `FDN/` = `d:/projects/github/foundation/foundation-sites`, Foundation for Sites 6.9.0 (`package.json:3`), commit `337be7a`.
- `Dart Sass` = 1.104.1 (`npx sass@1.104.1 --version` prints `1.104.1 compiled with dart2js 3.13.3`; the version `@angular/build` 22.2.0 pins, `adr/0012-sass-packaging.md:7`). The measured runs used its JavaScript API from the same release (`sass.info` printed `dart-sass 1.104.1`); one fixture was also compiled with the `npx sass@1.104.1` command line and produced the same bytes (9,725 plus the trailing newline the command line adds).
- `FX/` = `D:/tmp/f183`, a throwaway directory outside the repository holding the fixtures, the scripts, and the compiled CSS. It is not committed.
- Spec and ADR paths are relative to the effort directory (`.scratch/next-foundation-specs/`).

## 1. Findings in brief

1. **Every export mixin the first-milestone specs name compiles alone** after `@import 'settings'; @import 'foundation';`. The import itself emits no CSS (0 bytes). One export mixin outside the first-milestone set fails alone: `foundation-typography-base` (section 3.4).
2. **Rules do not repeat across families.** Every one of the 1,373 rules of `foundation-everything` also appears in the standalone compile of exactly one export mixin, and per-family compiles add no rule that `foundation-everything` lacks, apart from the 41 rules of `foundation-range-input`, `foundation-progress-element`, and `foundation-meter-element`, which `foundation-everything` does not include (`FDN/scss/foundation.scss:80-154`; the docs name them separately, `FDN/docs/pages/slider.md:174`, `progress-bar.md:110,131`). The only repeated rules are inside bundles (`foundation-forms` contains the `foundation-form-*` mixins; `foundation-grid` and `foundation-xy-grid-classes` share 1,428 bytes). The resets, `.foundation-mq`, `.is-visible`, and `.is-hidden` come from `foundation-global-styles` alone. Foundation's Sass has no `@keyframes` and no Motion UI class (zero matches for either in `FDN/scss/`). Note, 2026-10-01 (audit 0012): the 50 compiled mixins leave out three that `foundation-everything` can include: `foundation-float-classes` (always, `FDN/scss/foundation.scss:151`), `foundation-flex-grid` (`:107`), and `foundation-prototype-classes` (`:154`). The Float Classes' rules (`.float-left`, `.float-right`, `.float-center`, `.clearfix`) are in `foundation-everything.css` and in no standalone output (`rg -l '\.float-left' FX/out-default`), so the 1,373 rules are not all in one standalone compile. All three are later-milestone families.
3. **What does cost more is splitting the compressed bytes.** The 35 first-milestone mixins (31 components plus `foundation-forms`, `-range-input`, `-progress-element`, `-meter-element`) weigh 71,550 bytes minified and 11,271 gzipped in one compile. As 35 separate files they weigh 71,553 bytes (3 more: a second byte-order mark) and 17,755 gzipped in total, 6,484 bytes (57%) more, because each file compresses on its own. Brotli (quality 11): 9,637 bytes combined, 13,697 bytes as 35 files. Under the custom settings the same three figures are 79,214, 11,879, and 18,395 (section 3.5).
4. **Seven export mixins emit rules that apply with no directive on the page**: `foundation-global-styles` (45 of 49 rules are tag or attribute rules), `foundation-forms` (23 of 42), `foundation-range-input` (12 of 12), `foundation-meter-element` (9 of 9), `foundation-table` (9 of 21), `foundation-progress-element` (5 of 20), and, outside the first milestone, `foundation-typography`. Those rules cannot follow a directive's lifecycle. Every other export mixin, and the class-bearing parts of the form mixins, emits only class-scoped selectors. In the 35-mixin set the unscoped rules are 58 rules and about 5,725 bytes of 71,550 (serialised rule bytes; section 3.4).
5. **Three families need another family's rules in the page, and two need it earlier in source order.** `foundation-accordion-menu`, `foundation-drilldown-menu`, and `foundation-dropdown-menu` style markup that also carries `.menu`, and alone they leave the list bullets, block display, and unflexed items. `foundation-drilldown-menu` and `foundation-dropdown-menu` change the computed style of the nested submenu when they are emitted before `foundation-menu` (measured in Chromium; section 3.3). `foundation-button-group` and `foundation-slider` also need their companions (`foundation-button`, `foundation-range-input`) for their look, with no order effect measured.
6. **A full-page reading of `foundation-everything` differs from per-family includes in one setting**: `foundation-everything` assigns `$global-flexbox: true !global` and `$xy-grid: true !global` before it includes anything (`FDN/scss/foundation.scss:85-91`), so a consumer whose settings say `$global-flexbox: false` gets `display: flex` on `.menu` from `foundation-everything` and not from `@include foundation-menu` (measured, section 3.5).
7. **The Library mixins have no code.** From the specs' Sass subsections, nearly all are plain global mixins that read the consumer's settings and must follow their export mixin, several at equal specificity ("after it in source order"). `nfs-motion`, `nfs-breakpoint-properties`, `nfs-smooth-scroll`, and the `:root` Variant properties are not tied to one family (section 3.6).

"Needs from other families" names rules of another export mixin that the family's markup depends on to look right, or that the family overrides; "none" means the standalone output renders the family's own classes complete. "Source-order position" is set only where reversing the emit order of two mixins changed a computed style in the browser probe (section 3.3); "none measured" means a static candidate exists or the family overrides another family's rules by higher specificity, and the probe showed no change. "Splits per family" is a reading of the three columns before it, not a recommendation.

## 3. Evidence

### 3.1 Method and fixtures

- Settings, default: `FDN/scss/settings/_settings.scss` copied to `FX/_settings.scss` unchanged (it opens with `@import 'util/util'`, line 64, which resolves through the Foundation load path).
- Settings, custom: `FX/custom/_settings.scss`, the same file with three edits: `$global-radius: 8px` (default `0`, line 94), a `brand` palette entry (`#2b6e3f`) added to `$foundation-palette` and `primary` changed from `#1779ba` to `#a3001e` (lines 72-78), and `$breakpoint-classes: (small medium large xlarge)` (default without `xlarge`, line 126).
- Fixture: `@import 'settings'; @import 'foundation'; @include <mixin>;` with load paths `FX` (or `FX/custom`) and `FDN/scss`. Compiled with `--style=compressed`; the deprecations for `import`, `global-builtin`, `color-functions`, and `slash-div` were silenced to keep the output readable (the compile still prints Dart Sass's `if()` deprecation warnings and a "53 repetitive deprecation warnings omitted" line, the same for every fixture and not specific to a family).
- The import alone, with no include, emits 0 bytes (`FX/out-default/_import_only_.css`), so every byte below comes from the included mixin.
- Settings reach the per-family output. With the custom file, `foundation-button` alone emits 29 `brand` selectors (default: 0), `border-radius:8px` on `.button`, and the `#a3001e` primary in 10 places; `foundation-callout`, `-badge`, `-label`, `-progress-bar` each emit a `brand` selector; `foundation-button-group` emits 45; `foundation-xy-grid-classes` emits 12 distinct `xlarge-<n>` classes (default: 0). The `foundation-everything` compile grows from 117,513 to 138,811 bytes.
- Browser probes (3.3): Chromium through Playwright 1.63, one page per markup, the standalone CSS of the named mixins in a `<style>` element, every element's full computed style compared between the two orders.

### 3.2 Point 1: does each family compile alone, and what does it emit

- 49 of 50 mixins compile alone. `foundation-typography-base` does not (section 3.4).
- Sizes span 322 bytes (`foundation-thumbnail`) to 35,747 (`foundation-xy-grid-classes`). Among the 31 first-milestone component mixins the median is 1,070 bytes; the largest are `foundation-button-group` (15,294 min / 1,822 gz, because every palette colour and fill repeats under `.button-group`, `_button-group.scss:215-257`), `foundation-button` (8,643 / 1,581), `foundation-off-canvas` (7,443 / 1,046), `foundation-dropdown-menu` (5,581 / 766), `foundation-menu` (3,832 / 867).
- The custom settings leave some rows unchanged (`foundation-breadcrumbs`, `-media-object`, `-orbit`, `-responsive-embed`, `-sticky`, `-title-bar`, `-menu-icon`) and grow the rows that loop over palettes or breakpoint classes: `foundation-button-group` +14%, `foundation-xy-grid-classes` +36%, `foundation-off-canvas` +25%, `foundation-dropdown-menu` +24% (minified).
- What each standalone compile emits is in `FX/out-default/foundation-<mixin>.css`. Every first-milestone component mixin emits only rules that start with its own class names, plus modifier and state classes of the same component, `@media` blocks over the consumer's `$breakpoints`, and selectors that reach into another family's classes in the cases listed in 3.3.

So in this probe `foundation-menu` has to come before `foundation-dropdown-menu` and `foundation-drilldown-menu`, and nothing else measured depends on order. Foundation's own order (`FDN/scss/foundation.scss:137-141`) puts `foundation-menu` first.

**Limits of this reading.** A static scan of the standalone outputs for equal-specificity rules of different families that set the same property and can match one element (subject classes in a subset relation, `FX/order.mjs`) found 9 family pairs; its best-known hits were `.button-group.hollow .button.primary` against `.button.primary.disabled:hover` (both 0,4,0; probe: no difference), `.breadcrumbs .disabled`, `.pagination .disabled`, and `.button.disabled` (on one element only if a button carries all three classes), and `.menu.align-right .nested` against `.accordion-menu .nested.is-accordion-submenu` (probe: no difference). It missed the dropdown-menu case, where the subject class sets (`.menu` and `.is-dropdown-submenu`) are not in a subset relation. Loosening the scan to any two equal-specificity single-class rules sharing a property produced 546 pairs, almost all of components that never share an element (`.button` and `.callout`). The measured pairs above are therefore the evidence; whether a combination outside those 13 exists is open (section 4).

### 3.5 Point 4: `foundation-everything` against per-family compiles

- **Rules.** (Note, 2026-10-01 (audit 0012): not for the Float Classes, Flex Grid, or Prototyping Utilities, which were not compiled alone; see section 1, item 2.) All 1,373 distinct rules of `foundation-everything` (default settings) appear in a standalone compile of one export mixin, and 41 standalone rules do not appear in it (the three form-element mixins). So a per-family compile emits nothing that a full compile does not, and the resets (`foundation-normalize`), `.foundation-mq`, `.is-visible`, and `.is-hidden` appear only in `foundation-global-styles` (3,154 bytes, 1,215 gzipped), not in any component mixin. Across the 49 standalone outputs 78 rule texts repeat, all inside the `foundation-forms` bundle (4,866 bytes) or between `foundation-grid` and `foundation-xy-grid-classes` (1,428 bytes), which `foundation-everything` includes one at a time (`FDN/scss/foundation.scss:99-109`).
- **`foundation-mq` meta rule, keyframes, Motion UI.** `.foundation-mq { font-family: '<serialised breakpoints>' }` is emitted once, by `foundation-global-styles` (`FDN/scss/_global.scss:144-146`). Foundation's Sass defines no `@keyframes` and no Motion UI class; its docs treat Motion UI as a separate dependency (`FDN/docs/pages/orbit.md:241-244`, `starter-projects.md:101`). The Motion classes of this library are the Library mixin `nfs-motion` (`building-blocks.md:118-119`), which does not exist as code.
- **Bytes.** The 35 first-milestone mixins: one compile 71,550 min / 11,271 gz; 35 files 71,553 / 17,755 (+6,484 gz). The 31 component mixins alone: 63,950 / 9,411 against 63,953 / 15,136 (+5,725). The four forms parts (`foundation-forms`, `-range-input`, `-progress-element`, `-meter-element`): 7,600 / 2,221 against 7,600 / 2,619. The global families (`foundation-global-styles`, `-xy-grid-classes`, `-flex-classes`, `-visibility-classes`): 43,801 / 5,560 as one compile. Under the custom settings: 79,214 / 11,879 against 79,217 / 18,395 for the 35. `foundation-everything`: 117,513 / 17,141 (default), 138,811 / 18,753 (custom). The median separate gzip file is 382 bytes (default). Not measured: HTTP request cost, caching across pages, and the cost of the unused remainder when a page loads one big file.
- **Compile time.** Evaluating `@import 'settings'; @import 'foundation'` takes about 112 ms with no include (median of 5); `foundation-button` alone 261 ms; `foundation-everything` 1,316 ms. 35 separate compiles took 4.4 s in total (about 3.9 s of it the repeated import) against 0.97 s for one compile of the same 35 mixins. Machine: Windows 11 on ARM64.
- **Same output, different flags.** `foundation-everything($flex: true, $prototype: false, $xy-grid: $xy-grid)` assigns `$global-flexbox: true !global` when `$flex` is true and `$xy-grid: true !global` when `$xy-grid` is true (`FDN/scss/foundation.scss:80-91`). With `$global-flexbox: false` set after `@import 'settings'`, `.menu` came out as `padding:0;margin:0;list-style:none;position:relative` from `@include foundation-menu` and with `;display:flex;flex-wrap:wrap` from `@include foundation-everything` (`FX/flex.mjs`). A consumer who today sets `$global-flexbox: false` and includes `foundation-everything` gets flexbox anyway; the same consumer including families one at a time does not.

### 3.6 Point 5: can the Library mixins be compiled the same way

No Library mixin has code: the repository has the specs and [ADR 0012](../adr/0012-sass-packaging.md) only. This section is read from the first-milestone specs' Sass subsections (generated list in `FX/subs-full.txt`) and from one throwaway probe.

- **Shape.** `ngx-foundation-sites` ships `_index.scss`, which the consumer `@import`s after Foundation; it defines global mixins, emits nothing on import, and never imports Foundation (`adr/0012-sass-packaging.md:7`). A global mixin defined after `@import 'foundation'` is in the same compile as the export mixins, so `@include foundation-<x>; @include nfs-<x>;` in one per-family fixture has the same shape as the fixtures above. The probe below checks that.
- **Probe.** `FX/fx/nfs-stubs.scss` has two stubs written for this ticket from the specs' text (`specs/menu.md:503` rule 1: `.menu a[aria-current]...` with Foundation's `menu-state-active`; `specs/button.md:541` items 1 and 6: a 24 px floor and `--nfs-button-palette` / `--nfs-button-sizes` on `:root`). They are not the library's code. Compiled with `@include foundation-menu; @include nfs-menu; @include foundation-button; @include nfs-button;`: both settings compile; `menu-state-active` (a Foundation mixin, not an export mixin) is callable; the current-link rule comes out after the `.menu` rules; the current-link background follows the settings (`#1779ba` default, `#a3001e` custom); `--nfs-button-palette` lists `brand` under the custom settings. The stub joined the keys with commas; the spec says `space` (`specs/button.md:541`).
- **First-milestone Library mixins named in the specs** (include line or Sass subsection): `nfs-accordion`, `nfs-accordion-menu`, `nfs-badge`, `nfs-breadcrumbs`, `nfs-button`, `nfs-button-group`, `nfs-callout`, `nfs-card`, `nfs-close-button`, `nfs-drilldown`, `nfs-dropdown-menu`, `nfs-dropdown-pane` (a Variant property only, `specs/dropdown.md:730`), `nfs-label`, `nfs-menu`, `nfs-menu-icon`, `nfs-off-canvas`, `nfs-orbit`, `nfs-pagination`, `nfs-progress-bar`, `nfs-responsive-embed`, `nfs-responsive-toggle` (on request, `specs/responsive-toggle.md:584`), `nfs-reveal`, `nfs-slider`, `nfs-smooth-scroll`, `nfs-sticky`, `nfs-switch`, `nfs-table`, `nfs-tabs`, plus the shared `nfs-motion` and `nfs-breakpoint-properties`. Specs with no Library mixin: Abide, Anchored pane, Equalizer, Forms, Interchange, Magellan, Media Object, Nested Menu (uses three of the above), Responsive Accordion Tabs, Responsive Menu, Thumbnail, Toggler, Tooltip, Triggers, Variant declaration tooling.
- **What follows its export mixin cleanly.** Each `nfs-<x>` is documented as "included after `foundation-<x>`" and reads the consumer's settings and Foundation's functions and mixins. Several of its rules sit at equal specificity to Foundation's and win by coming later: `nfs-menu` rule 1 ("at the same specificity as Foundation's rule (0,2,1), after it in source order", `specs/menu.md:503`), `nfs-table`'s `table.stack tfoot` ("same specificity as Foundation's `display: none`, later in source order", `specs/table.md:453`), `nfs-switch`'s forced-colours rules ("equal specificity, so order decides", `specs/switch.md:533`). A per-family file that contains `foundation-<x>` then `nfs-<x>` keeps those orders; two files loaded in arbitrary order do not.
- **What does not follow one family.**
  - `nfs-button-group` is "included after `foundation-button-group` and after `nfs-button`" (`specs/button-group.md:447`), and `nfs-dropdown-menu` after `foundation-accordion-menu` when that is included (`specs/dropdown-menu.md:718`): cross-family order, on top of 3.3's.
  - `nfs-menu` is included by every menu Plugin's consumer (`specs/menu.md:503`), and `nfs-close-button` by the Callout, Reveal, Off-canvas, and Toggler specs; so the file that carries it is shared.
  - `nfs-smooth-scroll` emits `#{$scroller} { scroll-behavior: smooth }` with `$scroller` defaulting to `html`, "no ordering constraint against any Foundation include" (`specs/smooth-scroll.md:525`): an element selector.
  - `nfs-breakpoint-properties` writes `--nfs-breakpoint-classes` on `:root`, "included once anywhere in the global stylesheet" (`specs/breakpoint-service.md:570`).
  - The Variant properties (`--nfs-button-palette` and the like) are written on `:root` by each family's mixin, and the declaration-file generator reads them from a compile of "a project's global stylesheet" (`specs/variant-declaration-tooling.md:29`).
  - `nfs-motion` emits the `nfs-*` keyframe classes and one reduced-motion override for the whole library; the Dropdown, Tooltip, Reveal, Toggler, and Responsive Toggle specs name its classes, while the accordion and drilldown specs say "none from `nfs-motion`" (`building-blocks.md:118-119`). Several families use it.
  - `nfs-responsive-toggle` adds `.hide-for-<bp>` and `.show-for-<bp>` rules after `foundation-visibility-classes`, a later-milestone family (`specs/responsive-toggle.md:584`).

## 4. Open unknowns

1. **Completeness of the order list.** The probe covers 13 designed combinations in Chromium with default settings. It found two order-dependent pairs (menu with drilldown-menu, menu with dropdown-menu). It cannot show that no other pair exists, and the static scans have the blind spot described in 3.3. Not tested: the custom settings, Firefox and WebKit, the other nine menu-based variants (`.vertical`, `.icons`, `.is-active`), Orbit, Off-canvas open state, and combinations with the later-milestone grids.
2. **Where a family's file sits when its dependency loads later.** No fixture here loads two families at different times in a running page. How the compiled files would be ordered when a directive loads `foundation-dropdown-menu` before `foundation-menu` has loaded is outside this research.
3. **Settings reach.** (Note, 2026-10-01 (audit 0012): measured for one family in [research/lazy-style-loading.md](lazy-style-loading.md), 5.2: the application builder passes `stylePreprocessorOptions.includePaths` to every component stylesheet, and one `@import 'settings'` per family file applies the consumer's settings.) Each family compiles with a non-default settings file, but each compile evaluates Foundation again with the same file. Nothing here shows how the application's build would give every family file the same settings (one settings partial imported per file, or a shared Sass entry), or what `@angular/build` does with multiple extra stylesheets.
4. **Library mixins.** Their rules, their shared pieces (`nfs-motion`, `nfs-close-button`, `nfs-menu`, `:root` properties), and their sizes are unmeasured because no code exists. Whether the shared pieces repeat in several family files is open. The stubs cover two rules only.
5. **Variant properties on `:root`.** The generator reads them from a compile of the global stylesheet (`specs/variant-declaration-tooling.md:29`). Per-family files that are loaded lazily and are not in that compile would hide their properties from it; this research did not test the generator.
6. **`menu.md` and flex classes.** `specs/menu.md:503` says the Menu relies on `foundation-flex-classes` for `align` on a horizontal menu. `foundation-menu` alone emits `.menu.align-left`, `.menu.align-right`, and `.menu.align-center` (`FDN/scss/components/_menu.scss:489-505`); the generic `.align-*` classes come from `foundation-flex-classes` (`FDN/scss/components/_flex.scss:75`). Whether the spec means the second set is not settled here.
7. **Unscoped rules inside Library mixins.** The specs' rules for `nfs-table`, `nfs-slider`, and the form-element families that carry a tag or attribute selector were not read selector by selector, so the count of unscoped Library rules is unknown. `nfs-smooth-scroll`'s default `html` is one.
8. **Gzip and caching.** The extra 6.5 KB gzipped is for 35 separate files measured in one batch. Browser caching of files shared between pages, HTTP/2 multiplexing, and the share of a page that uses fewer than 35 families were not measured.
