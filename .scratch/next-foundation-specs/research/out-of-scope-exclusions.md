# Out-of-scope exclusions in the bundle

Written for [Triage the out-of-scope Foundation components and variants](../issues/79-triage-out-of-scope-components-and-variants.md). Every row below is a place the bundle rules a Foundation component, variant, modifier class, option, or behaviour out of scope, or declines to give it a directive, component, or input. Citations are bundle files relative to the effort root (`specs/button.md:353`) or the local Foundation clone (not needed here; every citation in this file is a bundle file). Tickets are linked by title relative to this file's own directory (`research/`).

The user's ruling (2026-09-27, quoted in the ticket): "being CSS-only must not exclude a Foundation for Sites component or variant from scope; an Angular component or directive is the Angular-native way to use a UI component in a website or web app, even when all it does is add a CSS class." Every row whose category is `css-only` is therefore a candidate the triage must bring back into scope and assign a directive or component. Every other category is presented for re-evaluation as the ticket asks, not pre-judged here.

## 1. Rules that exclude a whole class of things, not one item

These are stated once and then relied on by many rows below; the table cites the rule by name instead of repeating its text on every row that depends on it.

- **R1: the map's CSS-only line.** "CSS-only Foundation components with no JavaScript plugin other than Button (Button Group, Callout, Card, Badge, Label, Table, Grid, Top Bar markup, Menu markup, and so on). The destination covers the 21 JavaScript plugins plus Button; other CSS-only components need no Angular counterpart beyond markup." (`map.md:238`). This is the rule the user's ruling directly targets. Depends on it: G1 (and by extension every CSS-only Foundation component the bundle never names, excluded by omission).
- **R2: ADR 0010, Variant classes stay consumer-written classes.** "A directive does not mirror a Variant class as an input; the consumer writes it as a static or bound class... An input that sets a Variant class is allowed only when the directive's own behaviour depends on that state." (`adr/0010-button-variant-classes-stay-classes.md:7`, restated at `adr/0010-button-variant-classes-stay-classes.md:17`: "Other specs apply the same test to their Variant classes (Reveal sizes, Menu and Tabs orientation classes, Callout-like colors): purely visual stays a class; behaviour-changing becomes an input that binds the class."). Depends on it: B3, AC7, DP-size, RV-size, OC-position, TG-class-target, TB-variant, SL-vertical-partial (vertical is the one case where behaviour, not just look, changes, so it did become an input: `specs/slider.md:90`).
- **R3: building-blocks 1.4, class-name options dropped.** "Options that exist only because of jQuery or DOM strings are dropped and listed per spec under 'Dropped options': `data-options`... class-name options (`linkClass`, `panelClass`, `linkActiveClass`, `panelActiveClass`, `stickyClass`, `containerClass`, `verticalClass`, `rightClass`, `tooltipClass`, `triggerClass`, `activeClass`, `disabledClass`) because the classes are the contract." (`building-blocks.md:59`). Depends on it: AB1, AB2, ST-class-options, OR-class-options, DM-class-options, TB-class-options, MG-activeClass, TT-tooltipClass/triggerClass (triggerClass kept, see contradiction C4), SL-disabledClass.
- **R4: building-blocks 1.4, timing options dropped.** "Timing options that CSS or the browser now owns (`slideSpeed`, `moveTime`, `fadeInDuration`, `fadeOutDuration`, `showDelay`, `hideDelay` for Reveal, `animationDuration`, `animationEasing`..., `deepLinkSmudgeDelay`, `transitionTime`)." (`building-blocks.md:59`). Depends on it: AC8, AM-slideSpeed, RV-showDelay-hideDelay, MG-animationDuration, SS-animationDuration, SL-moveTime-changedDelay, DL-animationDuration, TT-fadeInDuration-fadeOutDuration, TB-deepLinkSmudgeDelay, OC-transitionTime.
- **R5: building-blocks 1.4, HTML-string options dropped.** "HTML-string options (`backButton`, `wrapper`, `container`, `template`, `allowHtml`)" (`building-blocks.md:59`). Depends on it: DL-backButton-wrapper, TT-template-allowHtml, ST-container.
- **R6: ADR 0004, menus use disclosure navigation, no menu/menubar/tree roles.** "Site navigation uses the disclosure navigation pattern, never `menu`/`menubar`/`tree`." (`building-blocks.md:121`; `adr/0004-menus-use-disclosure-navigation.md`). Restated in map.md's Out of scope: "Opt-in `role=\"menu\"` variants (DropdownMenu as an APG menubar, Drilldown as a vertical menu) for command menus. The building-blocks map put every menu on disclosure navigation and found no spec in the destination that needs a second role set." (`map.md:244`). Depends on it: AM4, DM-menubar-variant, DL-menu-tree-variant, RM-menu-tree-variant, NM-menu-tree-variant.
- **R7: the `@angular/aria` fallback confirmations.** Nine cases where an available Aria pattern is deliberately not used, already catalogued with their own evidence and reasons in `README.md:133-147` (evidence dossier: `issues/75-evidence-aria-fallback-confirmation.md`). These are not Foundation-feature exclusions but API-surface declines (a role set or a lazy-content form the bundle could have used and did not); not duplicated as rows here since README.md already gives each one its full reason, its file citation, and its judge's verdict.
- **R8: Motion UI and the jQuery plugin API surface.** "Foundation's jQuery plugin API surface (`$(el).foundation()`, `Foundation.Plugin` registration) and the Motion UI library as a dependency." (`map.md:241`). Depends on it: G4, G5, and every spec's "jQuery-only behaviour dropped" list (Accordion `:676` on, AccordionMenu, Reveal, Dropdown, Tooltip, Orbit, Toggler, Drilldown, all cite this rule for their own plugin's jQuery internals).
- **R9: runtime theming through custom properties is out of scope everywhere.** "Runtime theming through custom properties as a component contract... ruled runtime theming out." (`map.md:245`; `building-blocks.md:179` under 1.13). Every one of the 26 specs repeats a variant of "Runtime theming through custom properties" in its own Out of Scope section; listed once here (row G9) rather than 26 times.
- **R10: Foundation's own internal JavaScript utility modules never get a spec of their own.** "Which of Foundation's utilities become their own spec... A: Four: Breakpoint service, Triggers, Anchored pane (positioner plus Light dismiss), Nested menu. Motion, Keyboard, Box, Touch, Timer, ImageLoader, lifecycle, ids do not." (`issues/14-building-blocks-map.md:124`; restated at `building-blocks.md:287-294` under "Explicitly no spec of their own": "Motion... Keyboard... Box... Touch... Timer... ImageLoader... Plugin lifecycle, reflow, `data-options`... Id generation..."). These are Foundation's own internal plumbing, not consumer-facing components or variants, so the ruling does not reopen them; each is folded into the mechanics section of the spec that uses it instead of getting an entry point of its own.

## 3. Items where one location includes or treats something differently than another

- **C1, the central tension this triage exists to resolve.** `map.md:238` (R1) declares every CSS-only Foundation component other than Button out of scope with "no Angular counterpart beyond markup." The user's 2026-09-27 ruling (quoted in the ticket, `issues/79-triage-out-of-scope-components-and-variants.md:11`) directly overturns the premise of that line: "being CSS-only must not exclude a Foundation for Sites component or variant from scope." Every row in this file tagged `css-only` is a place the map's rule was applied; the triage's job is to bring each back into scope and say what it becomes.
- **C2, Top Bar and Menu markup.** `map.md:238` names "Top Bar markup, Menu markup" among the CSS-only components with "no Angular counterpart beyond markup." Yet the bundle gives both extensive directive-level treatment: the Dropdown Menu spec requires a specific `$topbar-background` Sass override for its own Top Bar story and documents `.top-bar`/`.top-bar-right` markup as a first-class input to its `alignment` resolution (`specs/dropdown-menu.md:91`, D9, Sass section); the Responsive Toggle spec's whole contract is a directive pair sitting on `.title-bar` and its target, with a required Sass mixin for the title bar's hamburger hit area and contrast (`specs/responsive-toggle.md:67-79`, Sass section); the Off-canvas spec requires the same `nfs-responsive-toggle` include for a bare `.title-bar .menu-icon` (`specs/off-canvas.md:642`); and the entire Nested menu utility, AccordionMenu, DropdownMenu, Drilldown, and ResponsiveMenu specs put directives directly on Foundation's plain `.menu`/`ul.menu`/`li` markup element by element. The map's blanket line and the specs' actual, detailed treatment of Top Bar and Menu markup disagree in practice, even though no spec calls itself a "Top Bar directive" or a "Menu directive" in name.
- **C3, Card.** `map.md:238` names Card as CSS-only and out of scope. The Equalizer spec's Usage examples give a full recipe for equalizing `.card` rows with CSS Grid `subgrid` (`specs/equalizer.md:424-439`), the only spec to treat Card markup in that much structural detail, though it stops short of a directive.
- **C4, `triggerClass` versus the general class-name-option rule.** Building-blocks 1.4 and R3 above state that class-name options are dropped everywhere ("the classes are the contract"). The Tooltip spec's Foundation contract table drops `triggerClass` under that same rule ("Dropped: `.has-tip` is the contract and is always added," `specs/tooltip.md:93`), but keeps its sibling `templateClasses` as an exception: "`templateClasses` kept... the only way to style one tip, because the consumer does not author the tip" (`specs/tooltip.md:90`, `:529` D7), and building-blocks 1.4 itself flags this as the one kept exception to the class-name-option rule (`building-blocks.md:59`: "Tooltip keeps `templateClasses`... it is the only per-tooltip class hook"). Not a contradiction once read together, but a rule with one documented exception that a reader of R3 alone would miss.
- **C5, ADR 0001's Tooltip exception widened after the fact.** ADR 0001 as originally accepted names one exception for generated structure: the Tooltip tip (`adr/0001-directive-first-with-named-exceptions.md:7`). Its own Consequences section records a 2026-09-27 amendment extending the same exception to a second, different element, the tip's hidden description: "the Tooltip exception also covers the tip's hidden description element, created in the first client render callback and never authored" (`adr/0001-directive-first-with-named-exceptions.md:16`). Not two documents disagreeing, but a rule whose scope changed after specs downstream (`specs/tooltip.md:523`, D1) had already relied on the narrower reading.
- **C6, `hoverPane`/hover-in-region across specs.** The Dropdown spec drops `hoverPane` because Foundation's `false` default fails WCAG 1.4.13 and makes the pane always part of the Hover region (`specs/dropdown.md:91`, `:316`). The Anchored pane spec states the same fact as a property of the shared utility, not of Dropdown alone (`specs/anchored-pane.md:316`). Consistent once cross-referenced, but a reader of only one file would think the exclusion belongs to that spec alone.
- **C7, `<dialog>` acceptance is not uniform across Openables.** Reveal adopts native `<dialog>` as its whole mechanism (ADR 0007, `adr/0007-reveal-on-native-dialog.md`), while Off-canvas rejects `<dialog>` (and `popover`) in every mode (OC6; ADR 0030, `adr/0030-off-canvas-no-dialog.md`). Not a contradiction once the structural difference is read: Reveal is always a dialog, while the same Off-canvas panel must also render as a permanent sidebar or an in-canvas page element at larger breakpoints, which a closed `<dialog>` cannot be. Worth cross-referencing so a reader does not take one plugin's `<dialog>` choice as evidence the other's rejection is inconsistent.
- **C8, Equalizer's own near-miss.** `specs/equalizer.md:368` (D1, row EQ10) records that shipping `nfsEqualizer`/`nfsEqualizerWatch` at all was nearly excluded on CSS-only-style grounds ("CSS guidance only, no directive... rejected at triage on 2026-09-26") one day before the user's 2026-09-27 ruling existed, for a different stated reason than Button Group's or Close Button's (real markup residue Foundation still ships: float grids, non-grid lists), not "CSS-only, so no Angular counterpart." Contrast with Button Group (B1) and Close Button (B2), which the map's CSS-only line excluded outright with no directive at all. Worth presenting alongside B1/B2 as a precedent for what a minimal directive looks like when CSS covers most, but not all, of a component's job.
- **C9, Interchange's image-mode exclusion (IC1) reads as CSS-only-adjacent but is not.** The stated reason throughout is a rendering-modes and performance argument (double download, delayed largest contentful paint, `hydrate never` residue: `specs/interchange.md:386`, `:402`), not "images are CSS-only, so they need no directive." Interchange itself is one of the 21 in-scope JavaScript plugins and still gets two directives for its other two modes (background, template). Flagged so the triage does not fold IC1 into the `css-only` bucket by category label alone without reading the reason: it is a platform/performance exclusion, not one the ruling's CSS-only premise touches.

## Notes for the triage

- Rows with category `css-only` are the ones the user's ruling most directly reopens: they were excluded, wholly or in part, because the underlying Foundation feature is CSS-only or because Foundation itself has no behaviour there. Under the ruling, each needs a stated Angular-native form (a directive that adds the class, at minimum), not a "markup only" note.
- Rows with category `variant-as-class` (the ADR 0010 pattern) are a distinct case from `css-only`: these are Foundation options or classes that already have a JavaScript-plugin-backed Angular directive on the same element (Button, Dropdown pane, Reveal, Off-canvas, Toggler, Tabs), and the question is only whether the variant itself should also become a typed input on that existing directive, not whether the component needs a directive at all.
- Rows with category `jquery-or-dom-plumbing` and `platform-or-a11y` are, on the bundle's own reasoning, unaffected by the CSS-only ruling (they were never excluded for being CSS-only) but are listed in full per the ticket's instruction to re-evaluate every reason, not only the CSS-only ones.
- Components the bundle never mentions at all (excluded by omission, per the ticket) are not separately enumerable from the bundle alone: the map's G1 line names Button Group, Callout, Card, Badge, Label, Table, Grid, Top Bar, and Menu explicitly, then says "and so on." The sibling research file `research/foundation-component-catalogue.md` (this ticket's other evidence file) is where the full Foundation 6.9 catalogue is checked against the bundle's coverage to find every component G1's "and so on" silently swept in.
