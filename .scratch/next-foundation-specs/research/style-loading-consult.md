## 2. Proposals

### 2.1 Proposal A: the family's CSS rides in the directive's chunk (static import through a build plugin)

**How it works.** Each family directive's module statically imports its family's CSS: `import calloutCss from 'nfs-family-css:callout'`. A library-shipped esbuild plugin resolves `nfs-family-css:<family>` to the library's own `<family>.scss` (`@import 'settings'; @import 'foundation-sites/scss/foundation'; @layer nfs.<family> { @include foundation-<family>; }`) compiled with Dart Sass and the consumer's `includePaths`, and returns the CSS as a string module. The module registers the string with the library's root style service at evaluation time. When the directive's constructor runs, the string is already in memory, so the service appends `<style data-nfs-family>` to `document.head` in the same task as the host element, on the server too. The client adopts the server `<style>` by attribute (188's `own-style`), holds server-rendered instances until a directive claims them (184's measurement 7 fix), and removes the element with 188's host timing. Because esbuild places a statically imported module in the chunk graph of whoever imports it, a family used only inside a `@defer` block or a lazy route ships in that block's or route's chunk, and a family used on the landing page ships in `main.js`; a module two chunks share becomes a common chunk. Ticket 189 built the same plugin with a dynamic `import()` per family and measured 17-20 unstyled frames at 300 ms, because the CSS chunk was fetched after the element existed (`P189/apps/fixture/src/lib/plugin-loaders.plugin.ts:3-8`). The change here is the static import and where it lives.

**Measured today** (`P192`, production SSR build of the `build-plugin` target, `P192/measure/probe-192.mjs`, raw output `P192/out/probe-192.json`), with 189's directives split into one module per family (`P192/apps/fixture/src/lib/directives/*.ts`), the routes made lazy with `loadComponent` so a page's families land in the page's chunk graph (`P192/apps/fixture/src/app/app.routes.ts`), and the client-defer and enter pages importing the callout module directly:

- **Chunking.** `main-*.js` (263.8 kB) holds no family rule. The callout CSS and directive are in `chunk-DE-ez8_g.js` (4,686 B raw, 1.78 kB transfer), the button's in an 8.6 kB chunk, the dropdown menu's in a 5.6 kB chunk, the menu's in a 3.9 kB chunk. The `@defer` block's dependency wrapper is a 91-byte chunk that imports the callout chunk. After the click on `/client-defer`, exactly those two chunks were requested in every engine, and no family element was in `<head>` before the click.
- **Requirement 3, client-only `@defer`**: **0 unstyled frames** out of 37-61 frames with the element present, chunk local and with the chunk delayed 300 ms, in Chromium, Firefox, and WebKit. The first three sampled frames read `44px` (the consumer's `$callout-sizes`, Foundation's default being 16px). 184's lazy carriers and 189's link and plugin variants measured 17-20 unstyled frames in the same scenario.
- **Requirement 3, server HTML and full hydration**: the server HTML of `/ssr` carries one `<style data-nfs-family>` per family; hydration shows 0 `<style>`/`<link>` insertions after the first 10 ms of parsing, 0 unstyled frames out of 58-74, and one element per family afterwards, in every engine. Incremental hydration and `hydrate on viewport`/`on interaction` were not rerun; 189 measured them passing for the plugin variant with the same service and the same owned `<style>` (189 README, point 2), and nothing in this change touches that path (inferred).
- **Requirement 5, enter animations** whose keyframes ship in the family CSS (189's `/enter` page): **on time** in 17 of 18 cases (click-inserted and client-only `@defer`, cold local, cold with a 300 ms chunk delay, and warm cache, in three engines), with 0 unstyled frames in all 18. The exception is Firefox, `@defer`, warm cache, where the animation started 24 ms after the element appeared and the harness's 20 ms threshold called it "late"; the same case in the cold runs started at 0-13 ms, so this is timing noise, not a skip. 189 measured the same page as "skipped" for every cold case of its link and plugin variants.
- **Requirement 2**: the six consumer settings read on `/ssr` (44px callout padding and the others) match 189's measurement 1; the plugin compiles with the consumer's `includePaths` (`P189/tools/nfs-esbuild-plugin.mjs:21-27`).
- **Requirement 6**: the chunk names are hashed by the application builder (above).
- **Requirement 4**: the `<style>` is library-owned, so Angular's `allLeavingAnimations` guard (`NG/packages/platform-browser/src/dom/dom_renderer.ts:683`) never applies; 188 measured `own-style` passing L1, L2, and L3 in three engines and 189 measured the same for the plugin variant (189 README, comparison table). The service's release path is unchanged in this probe (inferred carry-over).
- **Requirement 7**: esbuild's plugin API, Nx's `plugins` option on `@nx/angular:application` (189 point 2), `DOCUMENT`, `DestroyRef`, `ElementRef`. No `ɵ` import and no renderer hook: 188's `own-style` needed a `RendererFactory2` in a child injector only because a carrier component existed to intercept; here there is no component.
- **Requirements 8, 9, 10**: no custom property carries a theme value; the plugin compiles Foundation's export mixins from Foundation's own Sass with the consumer's settings and re-implements nothing; nothing newer than `@layer` is used.

**Requirement 1, what the consumer writes.** On Nx: the library's `global.scss` as the first `styles` entry, `stylePreprocessorOptions.includePaths` for the settings directory, and about 8 lines of `plugins` (189 point 2) in `project.json`; nothing per family, no TypeScript. A generator writes and reruns it. On Angular CLI without Nx, `@angular/build:application` has no `plugins` option (`BUILD/src/builders/application/schema.json` has `loader`, `externalDependencies`, and `statsJson` but no `plugins`), so the library would ship a thin builder: `createBuilder((options, context) => buildApplication(options, context, { codePlugins: [nfsFamilyCss(...)] }))`. `buildApplication` and the `ApplicationBuilderExtensions` type are public exports of `@angular/build` (`BUILD/src/index.d.ts:8-9`), and Nx's executor is built on exactly that call (189 point 2, `application.impl.js:31`). The consumer's `angular.json` then names `ngx-foundation-sites/build:application` instead of `@angular/build:application`, and the dev server needs the matching `buildTarget`. **Untested.** An alternative with no builder is to tell Angular CLI consumers to adopt `@nx/angular:application`, which is a documented Nx path.

**Main risk.** The library takes a position in the consumer's build pipeline. Three consequences follow: a plain Angular CLI consumer depends on a library builder or on Nx's executor; the plugin's Sass output bypasses Angular's stylesheet pipeline, so it misses the CSS optimiser (189 measured 1,011 B against 688 B for the same callout CSS, and `hsl()` where the builder writes `#fff`) unless the plugin runs `esbuild.transform(css, { loader: 'css', minify: true })` itself (untested); and the dev server, HMR after a settings edit (the plugin already returns `watchFiles` from `result.loadedUrls`, `P189/tools/nfs-esbuild-plugin.mjs:33`), prerendering, and `ng serve`'s Vite path are unmeasured. The CSS text is also duplicated at hydration (in the server HTML and in the chunk), as 184's carriers were; the chunk is fetched anyway for the directive, so the extra bytes are the CSS string (688-1,011 B minified per family here). Two Sass compiles per family per build (browser and server bundles) double 183's 4.4 s for 35 families; one compile of every family split by `@layer nfs.<family>` block with PostCSS would cut that to 183's 0.97 s (untested, and it fixes the import-time overhead 183 measured, `research/foundation-sass-per-family.md` 3.5).

**Smallest prototype that would settle what is open.** Three steps, each under a day, all in `P192`: (a) a 30-line Angular builder wrapping `buildApplication` with `codePlugins`, used from a plain Angular CLI `angular.json`, with `ng build` and `ng serve`; (b) `ng serve` with a settings edit, checking the family `<style>` updates; (c) rerun 188's `measure-188.mjs` L1-L3 and 189's `/hydrate-defer` against this build. The `esbuild.transform` minify step and the one-compile layer split are each a 20-line change to the plugin.

**Where it stands against the loading unit (185, point 8).** With a static import, the unit that loads together is the set of CSS modules a directive module imports, not "one export mixin". The dropdown menu's module imports the menu CSS and its own (`P192/apps/fixture/src/lib/directives/dropdown-menu.ts:4-9`), so a companion is a dependency the bundler enforces rather than a rule a consumer or a generator must remember, and the `@layer` statement still fixes the cascade order whatever the chunk order (184 measurement 4).

### 2.2 Proposal B: a Sass-computed settings fingerprint as the cache key for unhashed family bundles

**How it works.** 189's one failure is cache busting: non-injected global style bundles are named `[name]` by design (`BUILD/src/tools/esbuild/global-styles.js:42-47`: `outputNames` for `initial` bundles, and `{ ...outputNames, bundles: '[name]' }` otherwise), and Angular's generated `server.ts` serves them with a one-year `max-age`. The library already reads the global `styles-<hash>.css` link to find the bundle directory (189 point 3). If the global stylesheet's content changed whenever any Foundation setting changed, its hash would be a version key, and the library could append it to every family URL: `nfs-callout.css?v=NWRFCIUC`. Foundation's global styles do not read most settings (191 measured 12 of 487), so the library's `global.scss` emits one short rule carrying a checksum of every setting value, computed in Sass: `meta.inspect` of the list of all setting variables, then a djb2-style loop over its characters with `string.index` against a fixed alphabet and `%` arithmetic. Foundation itself serialises a setting into CSS for a reader to pick up: `.foundation-mq { font-family: '#{-zf-bp-serialize($breakpoints)}' }` (`FDN/scss/_global.scss:144-146`). The library ships the list of setting names for its Foundation peer range (489 top-level assignments in `FDN/scss/settings/_settings.scss`), and includes its own version string in the rule so a library upgrade changes the key too.

**Measured today** (`P192/probe-fingerprint.mjs`, Dart Sass 1.104.1 through its JavaScript API): with all 489 settings in the list, the rule compiles to `@layer nfs.global{.nfs-fingerprint{font-family:"nfs-1901472301"}}` (65 bytes, 83 gzipped). The number differs between Foundation's defaults, 189's consumer settings (six changed values), and 189's `cachebust` settings (only `$callout-sizes` changed from the consumer's). The compile took 205-311 ms against 68-89 ms for the import alone, so the loop costs about 150-220 ms once per global stylesheet compile.

**Requirements.** (6) is the one it addresses; it is **untested** at runtime, where the change is three lines in 189's `#href` (`P189/apps/fixture/src/lib/link-styles.ts`, the `#href` and `#bundlePrefix` methods). The server renders the same query string, so server links and client links agree. (1) holds: the rule lives in the library's `global.scss`, which the consumer already lists. (8): the value is a build fingerprint in a `font-family` string on a class nothing uses, as Foundation's `.foundation-mq` is; it is not a custom property and not a theme value. (7), (9), (10): nothing new.

**Main risk.** The key changes only with values in the list: a setting Foundation adds in a later 6.9.x patch is missed until the library's list follows, and a consumer who edits the library's own `<family>.scss` files (they ship as source) changes family output without changing the key. Query-string cache keys depend on the server and CDN keying by full URL; `express.static` ignores the query and serves the same file, which is what is wanted, while a CDN that strips query strings would keep serving the old file (untested per CDN). The 150-220 ms compile cost lands on every global stylesheet rebuild, including each dev-server rebuild.

**Smallest prototype.** In `P192`: add the rule to `src/lib/scss/global.scss` and the `?v=` suffix to `#href`; build 189's `production` and `cachebust` configurations; assert the two `styles-*.css` names differ and both family hrefs carry them; then load `production` in a browser, swap the served directory to `cachebust`, reload, and assert the callout padding changes. 189's build configurations and server already exist for this.

### 2.3 Proposal C: prune Beasties' copy through CSSOM instead of skipping Beasties

**How it works.** 189 found that Beasties copies a family's critical rules into its unmanaged first `<style>`, so the copy outlives the unload, and fixed it with `data-beasties-skip` on the family links. The price is that those links become render-blocking stylesheets in the server HTML (189 measurement 8; 190 measures the cost). The alternative keeps Beasties on: at unload, the library deletes every `CSSLayerBlockRule` named `nfs.<family>` from each `<style>` in `<head>` it does not own, with `sheet.deleteRule(i)`. The family's rules are inside `@layer nfs.<family> { ... }` blocks because the library's `.scss` wraps them, and Beasties preserves the blocks (189 `noskip` run: "inside the right `@layer` blocks"). `CSSLayerBlockRule` and `CSSLayerStatementRule` have the same support as `@layer` (Baseline high since 2024-09-14, `research/lazy-style-loading.md` section 6).

**Measured today** (`P192/measure/probe-beasties-prune.mjs` against 189's `noskip` build served from `P192`, three engines): Beasties' inline `<style>` holds one `CSSLayerStatementRule` first and one `CSSLayerBlockRule` per family in the page's layer order; the family links carry `media="all"` after Beasties' swap. After the hydrated callout and the hydrated-then-destroyed deferred callout were gone, a fresh `div.callout` still computed `44px` (189's leak). Deleting the one `nfs.callout` block brought it to `0px`, the layer statement stayed the first rule, and toggling the callout back in re-inserted the link and styled it at `44px`, in every engine.

**Requirements.** (3): the server HTML's first paint is styled by Beasties' inline copy and the family link loads without blocking, which is Beasties' purpose; (4): the unload now holds under critical-CSS inlining without `data-beasties-skip`; (7), (10): CSSOM, Baseline. **What it does not change**: the client-only `@defer` flash (section 2.4 or A), cache busting (B).

**Main risk.** The library edits a stylesheet it does not own, the same category of concern as 184's `repair` mode, though this sheet is written once by Beasties and never read back by Angular or Beasties. The deleted rules' text stays in the `<style>` element (only the CSSOM changes), so a `textContent` read would still show them. A family whose link Beasties rewrote but that the client never adopts (no `link[data-nfs-family]` because `<noscript>` and `media="print"` variants were emitted) must still be found by attribute; 189's adoption is by attribute and ignores `media`, so this holds (inferred). Beasties' `pruneSource` and `inlineFonts` options were not tried.

**Smallest prototype.** Add the pruning to 189's `#unload`, build `noskip`, rerun 189's measurement 8 and `/hydrate-defer`, and run 190's render-blocking measurement for `skip` against `noskip + prune`.

### 2.4 Proposal D: a paint gate and a listener-driven enter animation for fetch-on-construct loaders

**How it works.** When a family's CSS must be fetched after the element exists (189's `<link>`, E below, or any client-only first use without A), the directive marks its host `data-nfs-pending` from the constructor whenever the family's element is not yet loaded (`link.sheet === null`), and the library's `global.scss`, which is always present, carries `[data-nfs-pending] { visibility: hidden }` in `nfs.global`. The service clears the attribute on the link's `load` event. The unstyled interval becomes an invisible interval of the same length. For the enter animation, the directive binds the event form, `host: { '(animate.enter)': 'onEnter($event)' }`, waits for the family's `load`, then adds the typed Motion class and calls `event.animationComplete()` on `animationend`. Angular documents `animate.enter` and `animate.leave` as usable "directly on elements and also as a host binding" and as able to "call functions to apply animations from third party libraries" (`NG/adev/src/content/guide/animations/enter-and-leave.md:10`), and ADR 0003 and guide P19 already route enter and leave through those bindings. The class form cannot wait: `runEnterAnimation` removes the class one `requestAnimationFrame` after adding it when no animation is computed (189, read from `@angular/core` 22.2.0 `_debug_node-chunk.mjs:14385-14393`), which is why 189 measured "skipped" on every cold fetch.

**Requirements.** (3) in the weaker reading: no frame shows unstyled content, though content is invisible until the fetch completes; (5): the animation plays once the sheet applies, late by the fetch time rather than skipped. 190's accessibility measurement is where this matters most: a closed submenu or a `.show-for-sr` neighbour that Foundation hides is never exposed during the window, because the host is `visibility: hidden`. (1), (7), (8), (9), (10): a global rule, an attribute, a documented binding.

**Main risk.** Invisible content for the fetch duration is still a delay the user sees as a gap; focus moved into the inserted content (a Reveal, an off-canvas pane) fails while the host is `visibility: hidden`, so the directive must defer its focus move until styled; and whether a `visibility: hidden` element's later size change counts towards CLS is not established here. **Untested.**

**Smallest prototype.** 189's `/client-defer` and `/enter` at 300 ms with the gate and the listener, plus an axe run and an accessibility-tree snapshot during the window (190's harness has both).

### 2.5 Proposal E: the plugin's `file` loader variant

**How it works.** The same plugin as A, but `onLoad` returns `{ contents: css, loader: 'file' }`. esbuild then writes the CSS as a hashed asset under the application builder's `assetNames` (`media/[name]-[hash]`) and the import's default export is the asset's URL string. The library inserts `<link rel="stylesheet" href=url data-nfs-family>` as 189 does. This keeps CSS as CSS (HTTP cache shared across pages, no JavaScript parse, Beasties applies, with C), removes the per-family `styles` entries and the URL-prefix heuristic, and gives hashed names from the bundler.

**Requirements.** (6) by hashing; (1) as A; (3) and (5) as 189's `<link>` (the fetch starts at construct), so D applies. **Untested**, including: how the application builder's `publicPath`, `baseHref`, and `deployUrl` reach a `file`-loader URL; whether i18n builds place the asset per locale (189 measured that non-injected bundles are written per locale folder); and whether the server bundle emits a second copy under its own output directory.

**Smallest prototype.** Change the loader in `P189/tools/nfs-esbuild-plugin.mjs` (copied to `P192`), build, read the emitted path and the `href` in the server HTML, then build 189's `subpath`, `cdn`, and `i18n` configurations with the plugin target.

### 2.6 Proposal F: Angular's counted style host without a component, through `RendererFactory2.createRenderer`

**How it works.** 184 created a hidden carrier component with `createComponent` only to make Angular's `SharedStylesHost` count and serialise a `<style>`. The same effect is one public call: `inject(RendererFactory2).createRenderer(dummyElement, { id: 'nfs-callout', encapsulation: ViewEncapsulation.None, styles: [css], data: {} })`. **Read from source:** `DomRendererFactory2.createRenderer` returns the default renderer when either argument is falsy (`NG/packages/platform-browser/src/dom/dom_renderer.ts:193-195`), so the host element must be a real element (a detached `document.createElement('div')` suffices); it caches one renderer per `type.id` (`:221-222`) and calls `applyStyles()` on every call (`:212`), which is `sharedStylesHost.addStyles(this.styles, this.styleUrls)` (`:677`); `RendererType2` is a public interface whose `styles: string[]` is documented (`NG/packages/core/src/render/api_flags.ts:16-46`). The renderer's public `destroy()` runs `removeStyles` under the leave-animation guard (`:683`). The CSS string comes from A's plugin. What it buys over a library-owned `<style>`: Angular's `ng-app-id` serialisation and hydration reuse, the `CSP_NONCE` copy, dedupe by text, and shadow-root hosts, all of which 188's `own-style` had to take over itself.

**Requirements.** (7): public method and public types, though the behaviour that styles are applied on `createRenderer` is read from source, not documented. (4): the guard returns, so this needs 188's `retry` (call `destroy()` again until the guard passes) or 184's `repair`, and inherits their costs (polling while any `(animate.leave)` listener element exists). (3): as 184's carriers, including the dehydrated-instance hold. **Untested.**

**Main risk.** It trades 188's two undocumented behaviours for the guard leak, which is angular/angular#66244 with no fix planned (188 candidate 4). Lower rank for that reason; it is here because it removes the sham component and the consumer carrier from 184's design with one call.

**Smallest prototype.** In `P192`, replace the owned `<style>` insert with `createRenderer` and `retry`, and rerun 188's `measure-188.mjs` L1-L3 and the hydration scenarios.

### 2.7 Proposal G: hysteresis against churn

**How it works.** None of 184, 188, or 189 measured a family whose last instance comes and goes often: a tooltip, a dropdown pane, a Reveal, a toggled callout. Each cycle today inserts and removes the family's `<style>` or `<link>`, which forces a full style recalculation on insert and on remove and, for a `<link>`, a cache hit and re-parse. Two policies keep "unload when no instance remains" and cut the churn: a grace period (remove after an idle callback plus a fixed delay, or at the next navigation, if no instance returned), or `link.disabled = true` instead of removal, which drops the sheet from the cascade while keeping it parsed, so a return costs nothing. The ruling fixes that unloading happens, not how soon after the last instance.

**Requirements.** (4) still met, later; the grace period also absorbs L1-L3 timing in most cases, since a leave animation ends well inside any reasonable grace. **Untested.**

**Main risk.** A grace period keeps CSS a little longer than the ruling's plain reading; `disabled` is "unapplied", not "unloaded", so memory stays.

**Smallest prototype.** On 189's lifecycle page toggle one callout 20 times with and without a one-second grace, and record style-recalc time from the Performance API and the `<head>` mutation count; add the case to 190's INP scenario.

## 3. Critique of the current candidates

1. **Every leave-animation failure has one cause: letting `SharedStylesHost` own family CSS.** 184's carriers, 188's `retry`, `after-render`, and `repair`, and F above all run into the guard at `dom_renderer.ts:683`, and every passing public answer (188's `own-style`, `adopted`, and `own-link`; 189's `<link>`; A) is a way of not letting Angular own the element. 184's carrier component exists for one reason, to get Sass compiled by the consumer's build, and it drags Angular's count along: the guard leak, the uncounted dehydrated instances, and one hidden view per family. A build plugin compiles the same Sass with the same settings and no component.
2. **189's plugin variant was one `import()` away from the strongest result.** Its only reason for flashing was the dynamic import per family (`P189/apps/fixture/src/lib/plugin-loaders.plugin.ts:3-8`), which 189 chose so the CSS would be "a lazy chunk". Measured today, the static import gives 0 unstyled frames at 300 ms and enter animations on time with no family preloaded, because the chunk that carries the directive carries its CSS. 184's "eager carriers" result was the same mechanism applied to everything at once; the point is that the bundler, not a consumer map, should decide which chunk a family rides in.
3. **189's `<link>` loader is weaker than its table shows on three points and stronger on one.** The client-only `@defer` flash is structural: the fetch starts when the constructor runs, so preloading every family in `index.html` is the eager variant under another name (every family's CSS with the page), and 190's option D (prefetch at idle) narrows the window without closing it for a family first used before idle. `data-beasties-skip` trades a leak for render-blocking links (C removes the trade). The URL prefix depends on a global bundle named `styles` existing, which the library's `global.scss` entry ensures but a consumer can rename. Where it is stronger: its CSS stays CSS, cached by URL across pages, and nothing is fetched at hydration, which A does not match (A's chunk carries the CSS again).
4. **188's `own-style` is the right runtime and the wrong build.** Its runtime half (owned `<style>`, attribute adoption, host timing) is what 189's plugin variant and A reuse, and it passed every scenario. Its build half still needs the consumer's carrier files, and its `RendererFactory2` hook exists only to stop a component from applying styles. With no component there is nothing to intercept, and both undocumented dependencies disappear.
5. **gsd-pi has the right ownership instinct and gives up the settings.** A component-owned lifecycle with no consumer code is what every proposal above wants; its `@layer nfs-defaults` plus an unlayered consumer theme ships the family twice (189). 191 measured why a library default sheet cannot be rescued: only 25% of the first-milestone bytes are setting-independent, so under any custom settings most of a defaults sheet is wrong and overridden.
6. **The "family" unit was chosen for Sass, not for loading.** "One export mixin" is the right unit for compiling (183 measured every first-milestone mixin compiling alone), and the wrong unit for deciding what arrives together: `foundation-dropdown-menu` without `foundation-menu` looks wrong (183), so the dropdown-menu directive must load two families, and every consumer artifact or generator must know the pairing. With A, the pairing is a static import in the directive's module, enforced by the bundler, and the cascade order is the `@layer` statement's job (184 measurement 4). 185's point 8 could define the loading unit as "the CSS modules an entry point's directives import".
7. **The unload machinery is measured for correctness, not for cost.** 189's host timing attaches a `MutationObserver` with `childList: true, subtree: true` on `document` while any released host is still connected (`P189/apps/fixture/src/lib/link-styles.ts`, `#observe`), the hold scans every `[data-nfs-styles]` element at the first directive, and C or `data-beasties-skip` exists only for the unload. The benefit is removing a few hundred bytes to a few kilobytes of parsed CSS from the CSSOM. No ticket measured style-recalc time per insert and remove, or a family toggled repeatedly (G). 190 can.
8. **Requirement 1 is stricter than the bundle's own practice.** ADR 0040's Variant declaration file is generated TypeScript in the consumer's project, which the bundle accepts; 184's carriers are the same category. If 185 keeps the stricter reading, it should say why generated TypeScript is acceptable for Variant types and not for styles; A makes the question moot for styles.
9. **The `@layer` fix changes the cascade for every consumer in one way nobody measured.** 182 measured that any unlayered rule beats any layered rule. Consumer overrides winning is intended; a third-party unlayered stylesheet (a CMS theme, a reset) now beats Foundation's layered families regardless of source order, where today source order decides. One line in the decision's rendering-mode contract would state it.
10. **What no ticket measured, for every candidate**: the dev server (`ng serve` and Nx `serve` on Vite) and HMR after a settings edit, prerendering (`RenderMode.Prerender`), zone.js applications, CSP nonces on library-owned elements, several applications on one page, and client-side route navigation between pages that share a family. These are the same for A and for 189's loader, and the first two are where a build plugin is most likely to surprise.
