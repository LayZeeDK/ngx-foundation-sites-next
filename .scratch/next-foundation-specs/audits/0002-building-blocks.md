### H1. ADR 0003 permits JavaScript-timed animation, which the user ruled out, and the Motion UI prototype inherits the opening

- Files: `adr/0003-animation-mechanics.md`, Considered options bullet 1; `building-blocks.md` 1.6 rule 4; `issues/47-prototype-motion-ui-animate-enter.md`, Question.
- Rules: map Standing preferences, Animation (user decision): "No `@angular/animations`, no JavaScript-timed animation."; `/domain-modeling` (an ADR records the decision actually made).
- Evidence:
  - ADR 0003: "Web Animations API (`element.animate`) driven from `(animate.enter)` callbacks: rejected as the default because it is JavaScript-timed animation in all but name; allowed only if prototype P6 shows it is the sole way to honour consumer-supplied Motion UI transition classes." The ADR names the approach as JavaScript-timed and then allows it on a prototype result, which the user decision does not permit.
  - [Prototype: `animate.enter` and `animate.leave` with Motion UI transition classes](../issues/47-prototype-motion-ui-animate-enter.md) asks whether "the function form of those bindings rescue[s] them". A function-form rescue of the two-frame `mui-enter` / `mui-enter-active` protocol means sequencing classes across frames from script, the same timing the rule forbids. The prototype agent reads `adr/*.md` first and would treat that route as allowed.
  - Half of the prototype question is already settled by the Angular source: `adev/src/content/guide/animations/enter-and-leave.md:28` says that when transitions are used with `animate.enter`, "you would still need to pair it with `@starting-style` to have an appropriate _from_ state for your transition to work". `@starting-style` is out of the browser target (`building-blocks.md` 1.2 table). So Motion UI's transition classes cannot animate through the class form of `animate.enter` in the target browsers.
- Fix:
  1. ADR 0003, Considered options bullet 1: replace "allowed only if prototype P6 shows ..." with "rejected: it is JavaScript-timed animation, which the user ruled out; if a prototype finds no other way to honour a consumer-supplied Motion UI transition class, that class is unsupported and the case is recorded OPEN FOR HUMAN."
  2. `building-blocks.md` 1.6 rule 4: replace "whether they can be supported through the `(animate.enter)` callback form is prototype P6 (Part 4)" with "they are not supported: `animate.enter` with transitions needs `@starting-style` (`enter-and-leave.md:28`), which is out of target; consumers pass keyframe classes."
  3. Rewrite the Question of the Motion UI prototype ticket to: "Confirm that the library's `nfs-*` keyframe classes animate under `animate.enter` and `animate.leave` (inserted elements) and under a bound State class (persistent elements, completion on `animationend`/`transitionend` plus the duration-plus-100 ms fallback timer), with `prefers-reduced-motion` shortening them to 1 ms, in Chromium, Firefox, and WebKit. Motion UI transition classes are out (`enter-and-leave.md:28`); any route that sequences classes from script is recorded OPEN FOR HUMAN, not adopted."

### H2. `building-blocks.md` forbids `NgZone` in one section and requires running timers outside the zone in another

- File: `building-blocks.md` 1.5 bullet 1 versus 1.11 decision 4; `adr/0008-rendering-modes-contract.md` decision paragraph.
- Rules: rendering-modes rule 5 (`research/angular-rendering-modes.md` 7: "Focus, scroll and timers only in render callbacks; timers outside the Angular zone; nothing that keeps the app unstable"); audit brief item 2 (report every rendering-modes rule contradicted).
- Evidence: 1.5: "Anything driven by a timer, observer, or native listener writes into a signal; no `markForCheck`, no `NgZone`." 1.11 decision 4: timers start "on the client outside the Angular zone so a zone-based consumer still reaches stability and replays queued clicks promptly". Running outside the zone needs `NgZone.runOutsideAngular` (the research names it, section 1 Stability). The research also shows why it matters on the client: hydration cleanup and event replay wait for `appRef.whenStable()` (`packages/core/src/hydration/event_replay.ts:163`), so a timer inside the zone delays every replayed pre-hydration click. Timers are not rare here: every animated directive has the fallback timer of 1.6 rule 1, and Orbit, Dropdown, DropdownMenu, and Tooltip have autoplay or hover-intent timers. A spec or prototype following 1.5 breaks rule 5. ADR 0008 lists timers among what "lives in `afterNextRender`/`afterRenderEffect`" but does not say "outside the zone" at all.
- Fix: in 1.5 bullet 1 replace "no `markForCheck`, no `NgZone`" with "no `markForCheck`; `NgZone` is used only for `runOutsideAngular` around timers started in render callbacks or handlers (1.11 decision 4), which is harmless in zoneless apps". In ADR 0008's decision paragraph, after "lives in `afterNextRender`/`afterRenderEffect`", add "with timers started outside the Angular zone".

### H3. The Tooltip tip's lifecycle and its `aria-describedby` are stated three incompatible ways

- File: `building-blocks.md` 1.6 rules 1 and 2; Table A Tooltip row; Table B Tooltip row (animation, Material, and rendering cells); 1.11 decision 3.
- Rule: a decision lives in one place and agrees wherever it is restated (`/wayfinder` index-not-store; audit brief item 3).
- Evidence:

Table B's Material cell in the same row says "the tip stays in the DOM once created".
  - Table A: "`aria-describedby` set at first show". Table B rendering cell: "Server output: trigger with `.has-tip`, `aria-describedby` pointing at an id that exists only after first show". One says the server HTML has no `aria-describedby`; the other says it has one that references a missing id.
  - If the tip is removed on hide, `aria-describedby` points at nothing between shows; if it stays, `animate.leave` never runs. The [Prototype: Anchored pane positioning, measured Positionable port versus CDK Overlay](../issues/44-prototype-anchored-pane.md) positions `.tooltip` and the [Spec: Tooltip](../issues/27-spec-tooltip.md) reads both tables.

Edit: remove "the Tooltip tip component" from 1.6 rule 2 and from 1.6 rule 7's list; Table B Tooltip animation cell to "State class plus `nfs-fade-in`/`nfs-fade-out` keyframes on the kept tip; `opened`/`closed` after `animationend`"; Table B rendering cell to "Server output: trigger with `.has-tip` and no `aria-describedby`; the tip and the reference appear on first show". ### H4. Breakpoint-gated server state hides or disables content that Foundation's CSS shows at larger viewports

- File: `building-blocks.md` Table A ResponsiveToggle row; Table B ResponsiveToggle and OffCanvas rows (rendering cells).
- Rules: rendering-modes rule 9 ("Prefer CSS media queries and Foundation visibility classes for anything visible at first paint") and rule 11 (`hydrate never`); `building-blocks.md` 1.7 bullet "CSS first"; audit brief item 2.
- Evidence:
  - ResponsiveToggle, Table A: "below `hideFor` the menu carries `hidden` unless open"; Table B: "Server output: bar visible and menu `hidden` at `serverBreakpoint: 'small'`; above the breakpoint after hydration the bar hides by CSS and `hidden` is removed". A desktop visitor gets no navigation until hydration, and none at all inside `hydrate never`. Foundation documents the opposite approach for exactly this plugin: `docs/pages/responsive-navigation.md:286-320` ("Preventing FOUC") hides the title bar and shows the menu with a CSS media query before JavaScript runs.
  - OffCanvas, Table B: "Server output: panel `is-closed` with `inert` ... `revealOn`/`inCanvasOn` render the `serverBreakpoint` mode". With `.reveal-for-large`, Foundation's CSS makes the panel visible at large (`scss/components/_off-canvas.scss:387-396`, `off-canvas-reveal` sets `visibility: visible`), so the server paints a visible panel that `inert` makes unclickable and unfocusable until hydration, and permanently under `hydrate never`. The `inert` adds nothing for the closed state: Foundation already hides a closed panel with `.off-canvas.is-closed { visibility: hidden }` (`_off-canvas.scss:167-168`), which removes it from the tab order and the accessibility tree.
- Fix:
  1. ResponsiveToggle rows: replace the `hidden` binding with a State class plus documented library CSS inside a media query built from the Breakpoint map (below `hideFor`, `[nfsResponsiveToggleMenu]:not(.is-open)` is `display: none`; at and above it the title bar is hidden), so the server HTML is correct at every width; state that `hidden` is not used. Update the Table B rendering cell accordingly.
  2. OffCanvas rows: drop `inert` from the panel; rely on Foundation's `.is-closed` `visibility: hidden` and the `.reveal-for-<bp>`/`.in-canvas-for-<bp>` classes; keep `inert` only on `nfsOffCanvasContent` while a modal panel is open (as Table A already says).
  3. Add one line to 1.11 decision 8: "a breakpoint-gated hidden or inert state is expressed in CSS keyed on the Breakpoint map, never as a server-bound `hidden` or `inert`, whenever Foundation's CSS shows the element at a larger breakpoint."

### M9. AccordionMenu's height animation is placed on an element that cannot use the grid-row trick

- File: `building-blocks.md` Table A AccordionMenu ("Grid auto-height on `nfsSubmenu` (1.6)"), Table B AccordionMenu ("Grid-row auto-height per submenu"), 1.6 rule 3.
- Rule: internal consistency of the animation mechanics (ADR 0003).
- Evidence: 1.6 rule 3 requires "`grid-template-rows: 0fr -> 1fr` on the content host with a single wrapper child (`overflow: hidden`)". `nfsSubmenu` is a directive on `ul.menu.nested`, whose children are several `li` items, and ADR 0001 allows no wrapper there.
