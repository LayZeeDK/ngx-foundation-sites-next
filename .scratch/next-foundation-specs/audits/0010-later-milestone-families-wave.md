### Questions the sweeps left open

1. Can a Responsive Embed ratio named `'21by9'` compile (sweep 5, 5A)? No. Foundation's `scss/components/_responsive-embed.scss:51-55` prints each ratio as `&.#{$name}` inside `.responsive-embed, .flex-video`, so the name becomes a class selector, and a CSS identifier cannot start with a digit. Measured with Foundation's own partial, not a copy: `@import 'foundation';`, `$responsive-embed-ratios` with `'21by9': 21 by 9`, and `@include foundation-responsive-embed;` stops with `Error: Expected identifier.` at `&.21by9` (exit 65); the control with `'ultra-wide': 21 by 9` compiles (exit 0) and prints `.responsive-embed.ultra-wide, .flex-video.ultra-wide`. The rule is the selector grammar, so the Dart Sass version does not change it. Finding: M5.
2. Is the rule that `.show-for-sr` never goes on a focusable element (Visibility Classes D9, WCAG 2.4.7) kept where first-milestone specs now write the class? Yes. Building-blocks 1.10's Visibility Classes bullet (`building-blocks.md:193`) states it for the first milestone: "in the first milestone the same rules hold for Foundation's Visibility classes written as normal classes ... Visually hidden text (Foundation's `.show-for-sr`, written as a normal class in the first milestone) never holds a tab stop (... 2.4.7 ...)". Every element the first-milestone specs write the class on is a `span` inside a control or beside a glyph (Badge 12, Orbit 8, Drilldown Menu 8, Responsive Menu 7, Button Group 3, Button 3, Top Bar 2, Pagination 2, Label 2, Dropdown 1, Breadcrumbs 1, counted by tag), and the one other is the Abide's visually hidden Form alert, a `div` holding text (`specs/abide.md:707`). The one Foundation recipe that puts the class on a focusable element, the File Upload Button, is rejected for that reason in the Forms spec (`specs/forms.md:15`, `:117`, `:443`, D12) and in the Button spec (D11, and its Out of Scope at `specs/button.md:405`). The Switch spec drops Foundation's hidden paddle text for 3.3.2 and 2.5.3 (D4). No spec needs a restatement; no finding.
3. Should the Table spec require the four greys, which ticket 179 left open? Yes, by the same rule and the same measurements that put them in the Callout (D17) and the Card (D14). The requirement lived in the Typography Helpers spec for "a callout, a card divider, or a table" (its user story 29, and D23), which measured the table's backgrounds (`specs/typography-helpers.md:562-568`): `#737373` falls to 4.465:1 on the head, 4.198:1 on the stripes and footer, and 4.014:1 on those rows under the pointer, while `#666666` holds 4.860:1 at worst. The Table spec requires `$anchor-color` on the same eight backgrounds (D11) and says nothing of a `cite`, `blockquote`, `.subheader`, or heading `small` in a cell. Finding: M6.
4. Are the reading-order rules of the Flexbox Utilities and Float Classes restated where the Menu and Forms now write order and float classes? Not in the Menu, and not in building-blocks for the first milestone. Building-blocks 1.10's Flexbox Utilities and Float Classes bullets (`building-blocks.md:177`, `:190`) are marked "later milestone" with no clause for the classes written as normal classes, which the Visibility Classes bullet has. Finding: L3.

Groups a to c covered 33 specs, and the 11 others were never re-run; ticket 175's scan matched "the directives, entry points, and ticket links of the eight families", so a reliance written in words was missed.
