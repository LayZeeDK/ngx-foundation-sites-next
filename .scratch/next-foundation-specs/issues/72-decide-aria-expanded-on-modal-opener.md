# 72. Decide: `aria-expanded` on a modal dialog's opener

Type: grilling
Status: resolved
Blocked by: none
Labels: wayfinder:grilling
Map: ../map.md

## Question

Should a Trigger that opens a modal dialog (a modal Reveal, a modal Off-canvas panel, a Dropdown pane with `role="dialog"` and `trapFocus`) render `aria-expanded`? The [Spec: Triggers (shared utility)](54-spec-triggers.md) renders it on every `dialog`-role Trigger (its decision 18) and left the point OPEN FOR HUMAN in the trap quadrant (building-blocks Part 4, OPEN FOR HUMAN item 1): HIGH impact because the Trigger role union is a public contract every Openable inherits, NOT-HIGH confidence because the sources disagree. The alternative is a fifth role value (or a modal flag on the `dialog` role) that omits `aria-expanded` on modal openers, matching Foundation and the APG's modal dialog examples, while non-modal dialogs keep it.

Decide it with the panel the map's "Open-decision pass" note prescribes: an evidence dossier, four panelists (Opus and Fable, two adversarial), and a judge. The decision must say exactly what the Triggers spec, the three Openable specs, building-blocks 1.8 and Part 4, and the README open list change to.

## How to work it

The orchestrator runs the panel. The evidence dossier goes to `research/decision-aria-expanded-modal-opener.md`: WAI-ARIA 1.2 and 1.3 draft text on `aria-expanded` and `aria-haspopup="dialog"`; the APG modal dialog examples and any APG guidance on openers; ARIA in HTML; the Foundation 6.9 source for Reveal, Off-canvas, and Dropdown openers; what Angular Material, CDK Dialog, and other major design systems (for example GOV.UK, USWDS, Adobe Spectrum, GitHub Primer, Radix) render on modal openers; published screen-reader support data (a11ysupport.io, PowerMapper) and expert writing on announcing `aria-expanded` for a control whose popup takes focus and makes the rest inert; and the effort's own evidence (the Triggers spec decisions 16 to 20, the Reveal and Off-canvas specs, their prototypes). The judge writes the `## Answer` here.

## Answer

Judge's ruling, 2026-09-27, over the dossier (`research/decision-aria-expanded-modal-opener.md`, cited as "D n.n") and four panel arguments: the a11y lens (Opus), the api lens (Fable), the vsdefault lens (Opus, adversarial against the default), and the vsalt lens (Fable, adversarial against the alternatives). Every fact the ruling rests on was re-read at its source or re-run by the judge; those are marked "verified".

### Decision

The Trigger role union gains a fifth value, `modal-dialog`, whose Triggers render `aria-haspopup="dialog"` and `aria-controls` and no `aria-expanded`; an Openable reports it only when the platform makes every Trigger outside it inert for as long as it is open, which today means a Reveal with `overlay: true` (a `<dialog>` shown with `showModal()`). A Reveal with `overlay: false`, a Dropdown pane with `role="dialog"` (trapped or not; the Question mislabelled it as modal, its spec and the measurement say non-modal), and an Off-canvas panel in Modal mode keep `dialog` with `aria-expanded`; `aria-controls` stays on every dialog opener.

### Why

The deciding evidence, in the order it decides:

1. A `showModal()` dialog's opener never exposes an expanded value while the dialog is open. Verified in the dossier's raw outputs: Chromium's tree marks the opener `ignored=true (activeModalDialog)`, the Windows UI Automation trees of Chromium 153 and Firefox 155 omit it, and neither engine fires a state change on the opener when the flip and `showModal()` share a task (`D:/tmp/nfs-decision-aria-expanded/out-uia-chromium.txt`, `out-uia-firefox.txt`, `events-chromium.txt`, `events-firefox.txt`, case A; D 2.4.1 to 2.4.4). WHATWG 6.3.1 makes that normative for every engine in the Browser target, and `<dialog>` and `inert` are Baseline widely available on the target date (D 2.1.5, D 2.3). Under one `dialog` role the only value a user could ever meet on a modal Reveal's opener is "collapsed", which NVDA speaks on every focus and focus return: its state-presentation code drops "collapsed" only for `MENUITEM` with a popup (verified, `processAndLabelStates.py:88-91` at NVDA `f56b2e0`, the a11y and vsdefault lenses' shared finding).
2. Where the default's "true" is exposed for a modal Reveal, it is false. A Reveal with `[isOpen]="true"` is `true` on the server while the server HTML keeps the dialog closed (`specs/reveal.md:421`, D17 `:553`) and the Trigger's ARIA is a host binding on `isOpen` (`specs/triggers.md:315`). The a11y lens's case J, a button with `aria-expanded="true"` beside a closed `<dialog>`, reads `expanded=true` in Chromium's tree and `Expanded` in both UIA trees (verified, `D:/tmp/nfs-panel-72-a11y/out-measure.json`, `out-uia-*.txt`). The Reveal spec claims that server HTML is "identical for `[isOpen]="true"`" and shows `aria-expanded="false"` (`specs/reveal.md:355-358`); only an opener without the attribute makes that true for the modal example. The modal story also asserts `aria-expanded="true"` on a Trigger it calls inert in the same sentence (`:454`), which Playwright reports only because its role computation ignores inertness (D 2.4.5), against both specs' first testing sentence.
3. The modal value is defined by platform inertness, not by an Openable calling itself modal. The a11y lens's case I and the vsdefault lens's cases J and K (verified, `D:/tmp/nfs-panel-72-a11y/`, `D:/tmp/nfs-panel-72-vsdefault/`): while an Off-canvas Modal-mode panel is open, a Trigger outside `.off-canvas-content` stays in Chromium's tree with `expanded=true` and in both UIA trees as `Expanded`; `aria-modal="true"` alone removes nothing, only `inert` does; and the same Trigger without `aria-expanded` reads `Collapsed` in Firefox UIA while its panel is open, because Firefox infers collapsed from `aria-haspopup` (verified, `uiaRawElmProvider.cpp:54-60`). The Off-canvas spec makes only `.off-canvas-content` inert and sends fixed elements outside it (`specs/off-canvas.md:312`, `:505`; ADR 0030 Consequences), so a title-bar Trigger outside the content is a documented layout. A `modal-dialog` value there would trade a true state for a false one; a Reveal's opener can never be reached while its dialog is open, so the two Openables are different cases, not an inconsistency. The vsdefault lens's N2 (Angular's `synchronize()` runs render hooks and re-refreshes in one call, `application_ref.ts:594-686`) closes D 4.7: the content's `inert` lands in the same task as the focus move, so Off-canvas keeps `dialog` only because of Triggers outside the content, not because of timing.
4. Deciding now is the cheap direction. The api lens's five compile probes re-run by the judge with the repository's TypeScript (`tsc -p D:/tmp/nfs-panel-72-api/tsconfig.json`, strict): `widen.ts` (a four-value union shipped, a consumer's exhaustive `switch`, the value added later) fails with `TS2322: Type '"modal-dialog"' is not assignable to type 'never'`; `narrow.ts` (the value removed later) fails; `deprecate.ts` (the value kept as a deprecated alias rendered like `dialog`), `b2-silent.ts`, and `b1-forward.ts` compile. So adding the value after release breaks consumers and a later reversal breaks nobody, and the specs are unimplemented (D 2.9.13).
5. Every source that examined the modal opener on its own terms chose no expanded state, and the platform draws the line where this decision draws it: HTML-AAM 3.6.26, "A `command` attribute in the `close` and `show-modal` states provide no additional accessibility mappings to the `button` element", while the popover commands map `aria-expanded` (verified, `html-aam.html:9663`); Scott O'Hara's review on w3c/aria PR 2354, "being a button that opens a modal dialog and where focus will automatically be put into the dialog once it's opened, there's no need for any additional mappings" (verified, `aria2354.txt`); the APG Dialog (Modal) and Alert Dialog examples carry none of the three attributes on any opener (verified, `rg` over `patterns/dialog-modal` and `patterns/alertdialog` exits 1); Foundation's Reveal stamps `aria-controls` and `aria-haspopup: 'dialog'` and never `aria-expanded` (verified, `js/foundation.reveal.js:53-58`); and the effort's own first decision was the same shape ([Building-blocks map and cross-cutting architecture decisions](14-building-blocks-map.md), decision 38), which the Triggers spec's triage named as the reason its confidence was not high. The Triggers spec's upgrade path, `commandfor` with `show-modal` (`specs/triggers.md:555`), lands on that mapping; under the decision the upgrade changes no attribute.
6. B1 over B2, C, D, and E. The Triggers ticket's own rule is one role value per ARIA shape (decision 18); after this decision there are two dialog shapes. B2's optional member compiles when a wrapper forgets it and silently renders the non-modal output (`b2-silent.ts`, verified), and it would take the modal shape out of the pure derivation function, the data-driven browser test, and the mixed-roles check that all enumerate roles (`specs/triggers.md:191`, `:350`, `:361`). C (also dropping `aria-controls`) has no measured harm to fix, loses Foundation parity and the 1.3.1 relationship, and stays a one-row change later. D drops `aria-haspopup="dialog"`, which user story 13 promises and current JAWS, NVDA, and VoiceOver announce (D 2.8.4), and through `none` would merge a modal opener with Tooltip's meaning. E is outside the Question.

How each panelist's strongest argument was weighed:

- a11y lens (Opus): NVDA speaks "collapsed" before "opens dialog" on every focus of the default's modal opener (source, item 1), and Off-canvas Triggers outside the content stay exposed (case I, item 3). Adopted; its scope, Reveal only, is the decision's scope. Its option C variant is left unadopted (item 6).
- api lens (Fable): the reversibility probes and the platform upgrade path (items 4 and 5). Adopted for B1 over B2 and for deciding now. Its inclusion of Off-canvas Modal mode in `modal-dialog` is overridden by item 3. Its "no new ADR" is overridden: two modal Openables with different opener ARIA is exactly what a future reader will ask about.
- vsdefault lens (Opus): the false server state and the story that asserts what no assistive technology receives (item 2), plus N2 (item 3). Adopted. Its concession on Off-canvas is the decision's rule.
- vsalt lens (Fable): every source says "not needed", none says "wrong"; five libraries render it; Firefox UIA reports Collapsed under the alternative anyway; the alternative has no library precedent. Weighed as follows. (i) Item 2 is a place where the default is wrong, not redundant. (ii) The five libraries render the state from a generic trigger that never reads modality (Radix `dialog.tsx:121-139`; React Aria's `useOverlayTrigger` serves Modal, Popover, and Tray alike), and the one the lens examined itself, Material's datepicker toggle, stays reachable while its calendar is open because the page is not hidden; that places it with the Dropdown pane and Off-canvas on the keep-the-state side of the line this decision draws, not against the line. (iii) Firefox's inferred Collapsed reaches only its UIA provider; the MSAA and IA2 states that NVDA and JAWS read carry no `collapsed` for case B in either engine (verified, `events-chromium.txt` and `events-firefox.txt`, case B focus events), and a Collapsed on a reachable modal opener is true because the dialog is closed whenever the opener is reachable. So the alternative's benefit is partial on the Firefox-with-Narrator stack and never false. (iv) The lens's narrower point, that the same server mismatch remains for a non-modal open-by-default Reveal and is a Reveal-level defect, is accepted and routed (Changes to apply, follow-up 1).

### Dissent

Arguments the decision overrides, and what would reopen it:

- vsalt lens: the default is one value, WCAG 2.2 AA-conformant, axe-clean, rendered by Radix, React Aria, Ariakit, Zag, and Material's datepicker toggle, and no measured speech shows the extra word harmful; the alternative is an invention with no library precedent for a trigger whose attribute set switches with modality, adds a public union value for a distinction no engine exposes, and cannot remove the word on the Firefox UIA path. Overridden for the reasons in items 1, 2, 4, and 5. Reopens on: a measured or published announcement from a current JAWS, NVDA, or VoiceOver in which a button with `aria-haspopup="dialog"` and no `aria-expanded` is read worse than the same button with `aria-expanded="false"` (as a menu button, or with the popup type dropped); or HTML-AAM adding an `aria-expanded` mapping to `command="show-modal"` invokers.
- api lens: Off-canvas Modal mode should report `modal-dialog` too, since its `dialog` role occurs only in Modal mode and one value per Openable mode is simpler. Overridden by item 3. Reopens on: the Off-canvas spec making everything outside the panel inert (every body child but the panel, not only `.off-canvas-content`), at which point its opener meets the same guarantee as a `showModal()` dialog and the decision's rule assigns it `modal-dialog`.
- a11y and vsdefault lenses, option C: dropping `aria-controls` from modal openers as HTML-AAM and the Open UI explainer do. Not adopted (item 6). Reopens on: published data that `aria-controls` on a modal opener harms announcements.
- The whole Reveal half of the decision reopens on one fact: an engine in the Browser target, most likely WebKit with VoiceOver on Safari 17 or later, keeping a Trigger perceivable to assistive technology while its `showModal()` dialog is open. Then the opener's "expanded" would be perceivable and true, and Reveal would move to the keep-the-state side by the same rule that keeps Off-canvas there.

### Triage

- Impact: HIGH, unchanged. `NfsTriggerRole` is a public union that every library Openable and every consumer wrapper implements; the value is decided before any code exists, which is the only free moment (item 4).
- Confidence: HIGH after the panel. The map's rule rates confidence NOT HIGH for a bare default, a value carried from a prototype without deliberation, or a contradiction of the effort's own research or ADRs; this decision is deliberated over a dossier and four arguments, measured in two engines against normative HTML, and returns the modal case to the effort's own APG research (building-blocks decision 38) while keeping ADR 0007, 0013, and 0030 as written.
- Residual risk the decision accepts, and how the specs guard it: speech was never recorded (NVDA's output is derived from its source; JAWS, VoiceOver, and Narrator are unmeasured) and WebKit's platform tree was not read (D 4.1, 4.3). Guards: (a) README assistive-technology check 4 gains the modal Trigger's announcement on focus and focus return, worked by [Resolve the assistive-technology checks](77-evidence-assistive-technology-checks.md); (b) the reversal is one row of the pure ARIA-derivation function, keeping `modal-dialog` as a deprecated alias rendered like `dialog`, which compiles for every consumer (`deprecate.ts`, verified); (c) the `triggers--modal-dialog-role` story, the data-driven browser test, and the SSR smoke assert the attribute set per role, and an Openable that misreports a modal `<dialog>` as `dialog` renders the previous default's output, which conforms to 4.1.2.

#### Follow-ups outside this decision (the orchestrator routes them)

1. Non-modal open-by-default Reveal, false server state. Owner: [Spec: Reveal](18-spec-reveal.md), with the Triggers spec's rendering-modes rule 1 (`specs/triggers.md:315`, user story 31). A Reveal with `[overlay]="false"` and `[isOpen]="true"` ships its Trigger with `aria-expanded="true"` next to a dialog the server keeps closed (`specs/reveal.md:421`), until hydration and for good without JavaScript, so the claim at `:355` that the server HTML is "identical for `[isOpen]="true"`" is false for that case under every option, and the decision fixes only the modal (default) case by construction. Two fixes to choose between in the Reveal spec: the Reveal exposes to its Triggers an `isOpen` that reads `false` until the dialog has been shown (a separate signal from the model, so `isOpenChange` and the parent's state are untouched), or the spec documents the pre-hydration mismatch at `:355` and in the SSR smoke. Not decided here.
2. Off-canvas Modal mode, `aria-modal="true"` beside reachable content. Owner: [Spec: Off-canvas](25-spec-off-canvas.md). While a Modal-mode panel is open, content outside `.off-canvas-content` (a title bar, another panel) stays in the engines' accessibility trees although the panel claims `aria-modal="true"` (the a11y lens's case I, the vsdefault lens's case J, verified); ADR 0030 already records that such elements stay reachable except through the focus trap. Options for that spec: a development check for a registered Trigger, or any focusable element, outside both the panel and the linked content while Modal mode is on; or `inert` on every body child except the panel (which would also move Off-canvas to `modal-dialog` under this decision's rule). Not decided here.

### Amendment, 2026-09-27 (Resolve the assistive-technology checks)

From [Resolve the assistive-technology checks](77-evidence-assistive-technology-checks.md), check 5 (Off-canvas). That ruling closes one follow-up of this decision and changes its Off-canvas outcome under this decision's own rule; `specs/off-canvas.md` and `specs/triggers.md` were edited to match.

- Follow-up 2 (Off-canvas Modal mode, `aria-modal="true"` beside reachable content) is closed by the second of its two options: once focus is inside a Modal-mode panel, the panel sets `inert` on every element sibling of itself and of each of its ancestors up to `body` that is not already inert (the Modal inert set), except `.js-off-canvas-overlay` elements, the CDK focus-trap anchors, elements carrying `aria-live` or `popover`, and CDK's `.cdk-overlay-container` and `.cdk-describedby-message-container`, and removes it from exactly those elements at the close request.
- Outcome changed: Off-canvas Modal mode now reports `modal-dialog` (`aria-haspopup="dialog"` and `aria-controls`, no `aria-expanded`); non-modal Off-canvas configurations keep `disclosure`. Under the Modal inert set every Trigger outside the panel is inert while it is open, which is the condition the Decision gives for `modal-dialog` and the reopening fact the api lens's dissent names. Item 3 of Why, as it applies to Off-canvas, and the `specs/off-canvas.md` edits under Changes to apply are superseded by that ticket's Off-canvas and Triggers changes. The Reveal and Dropdown pane outcomes are unchanged.
- Edge cases in which a Trigger can still be reached while a Modal-mode panel is open, named by that ruling: a Trigger inside one of the exceptions (a popover or an overlay the page opened), a `nfsToggle` inside its own panel (the close control there is a bare `nfsClose`), an element added outside the panel after the set was taken, a modal panel open by default before hydration, and modal mode with `autoFocus: false` (the set waits for focus inside the panel). In each, MSAA and IA2 carry no state for a `modal-dialog` Trigger, and only Firefox's UI Automation infers "collapsed".
- Guard (a) of the Triage is worked: the modal Trigger's announcement on focus and focus return, and the non-modal Trigger's expanded state, are steps of the manual release tests in the Reveal and Off-canvas specs.
