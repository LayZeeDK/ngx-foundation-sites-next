# 109. Re-run: Toggler spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81, 83
Labels: wayfinder:grilling
Map: ../map.md

## Question

What does the [Spec: Toggler](17-spec-toggler.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/toggler.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

Also: the close-button rows follow the Close Button spec.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Toggler](17-spec-toggler.md) and the answer here. Model: Opus 5.5.

## Answer

Model: Opus 5.5. Worked AFK as a self-grilling (both sides) against the sources the ticket names, with `/domain-modeling` for vocabulary and `/to-spec` for the revision. Spec: [specs/toggler.md](../specs/toggler.md), revised in place; the dated amendment ("Amendment, 2026-09-28 (class rule)") is in the [Spec: Toggler](17-spec-toggler.md). No experiment was run: every point rests on ADR 0039, ADR 0040, building-blocks, a resolved spec, Foundation's source, or a measurement another ticket made. Four sibling tickets resolved while this one ran (Callout, Triggers, Reveal, and the Dropdown revision in progress); this Answer is aligned with each, and states the one place it adds to the Reveal's Motion shape.

Gist: the Toggler has no Structural or Variant class, so it gains no Variant input, and `.is-hidden` stays its host binding. Three things the consumer still wrote go. (1) Foundation's own class-mode example toggles a Menu Variant (`.expanded`), a Foundation class as an input value: class mode now names only the developer's own classes, and `toggler` written without a value selects class mode and switches no class, so the Variant is bound from `active` into its owner's input (`<ul nfsMenu nfsToggler toggler #menuBar="nfsToggler" [expanded]="menuBar.active()">`). (2) `animate` took library class names (`nfs-hinge-in-from-top`): it now takes the shared Motion names of the Reveal re-run (`NfsMotionIn`, `NfsMotionOut`, and the dot form `.my-class` for the developer's own keyframe classes) as a pair, `NfsMotionPair`, which also allows a leaving name alone, so Foundation's `data-animate` and `data-closable` values copy unchanged. (3) The static `is-hidden` seed goes (building-blocks 1.4); a copied one is stripped while shown and reported. Every example writes `nfsCallout`, `nfsMenu`, `nfsThumbnail`, `nfsButton`, and `nfsCloseButton` beside the Toggler; close buttons meet 2.5.8 through the Close Button's floor. Selectors, ARIA, keys, focus, animation phases, rendering modes, and Story ids are unchanged.

### Decision log

Sources: FS = the Foundation 6.9.0 clone (`docs/pages/toggler.md`, `js/foundation.toggler.js`); ADR 0039 with its follow-up decision on class names in input values; ADR 0040; BB = `building-blocks.md` as it stands; T = `research/out-of-scope-triage.md`; X = `research/out-of-scope-exclusions.md`; CAT = `research/foundation-component-catalogue.md`; CB = the [Spec: Close Button](83-spec-close-button.md) and its Answer; CO = the [Spec: Callout](89-spec-callout.md) and its Answer; TR = the [Re-run: Triggers (shared utility) spec under the class rule](130-rerun-triggers-class-rule.md) and the revised Triggers spec; RV = the [Re-run: Reveal spec under the class rule](110-rerun-reveal-class-rule.md) and the revised Reveal spec; DD = the Dropdown spec as the concurrent [Re-run: Dropdown spec under the class rule](118-rerun-dropdown-class-rule.md) is revising it; ACC = the [Re-run: Accordion spec under the class rule](107-rerun-accordion-class-rule.md); MG = the user's decision in the [Re-run: Magellan spec under the class rule](122-rerun-magellan-class-rule.md); "the spec" is the spec before this revision.

Round 1 (no prerequisites): which classes exist, and who owns them.

1. **Does the Toggler have a Foundation class of its own?** No Structural class and no Variant class: the plugin reads and writes only the class named by `data-toggler` (FS `foundation.toggler.js:46-64`), and Foundation ships no Toggler Sass; CAT's Toggler row records "none of its own". Its one State class is Foundation's global `.is-hidden`, already a host binding. So no Variant input, registry, alias, Variant property, or Runtime check request, and item (6) of the Sass subsection is "none". Source: FS; CAT; ADR 0039; ADR 0040.
2. **Which consumer-written classes did the spec carry?** Markup: `class="callout"`, `class="secondary callout"`, `class="menu"`, `class="menu expanded"`, `img class="thumbnail"`, `class="close-button"`, `nfsButton class="hollow"` and `class="secondary"`, and `class="is-hidden"` as the closed start (user story 7, the contract row, the `isOpen` default, D4, `toggler--initially-hidden`). Input values: `toggler=".expanded"` and `toggler="expanded"` (a Foundation Variant as a value), `animate="nfs-hinge-in-from-top nfs-spin-out"` and `nfs-fade-in nfs-fade-out` (library classes as values), and the Defaults token example. Prose: the 2.5.8 row's spacing exception and its consumer `min-width: 24px` recipe on `.close-button`, and the `@defer` hint to add `animate.enter` with an `nfs-` class. Source: the spec.
3. **Who binds them?** `.callout` and its colours: `nfsCallout` with `color` (CO decisions 1, 2). `.menu` and `.expanded`: `nfsMenu` with `expanded` ([Spec: Menu](85-spec-menu.md)). `.thumbnail`: `img[nfsThumbnail]` (T section 2, Responsive Embed and Thumbnail row; the [Spec: Thumbnail](97-spec-thumbnail.md) is open and fixes it). `.close-button`: `nfsCloseButton`, which closes nothing, so a bare `nfsClose` sits beside it (CB decisions 1, 2). `.hollow`, `.secondary` on buttons: `nfsButton` with `fill` and `color` ([Re-run: Button spec under the class rule](128-rerun-button-class-rule.md)). Each is placed beside the Toggler or its Trigger, never hosted: host directives are static, so hosting would give every Toggler another component's class (the map's composition preference; TR D16; CO D5). Source: those specs; T.

Round 2 (depends on 1-3): class mode and Foundation classes as values.

4. **What happens to `toggler="expanded"`, Foundation's own class-mode example?** ADR 0039's follow-up rules out a Foundation class as an input value, and `.expanded` already has an owner, the Menu's `expanded` input, so a Toggler binding it would make two owners of one class (BB 1.9, "the class and its Variants have one owner"). Options:
   - (a) keep `toggler="expanded"` with a warning: against the rule, and two directives fight over one class key;
   - (b) a placeholder application class kept only to select class mode (`toggler="menu-bar-full"` plus `[expanded]="menuBar.active()"`): no API change, but a class that exists only to satisfy a selector;
   - (c) no Toggler: the consumer binds `[attr.aria-pressed]` and a `(click)` handler itself, which TR's D6 already rejected for the toggle-button role, and ADR 0039's second rule gives the ARIA to the directive;
   - (d) `toggler` written without a value selects class mode and switches no class; `active` is bound into the owning directive's input. The selector partition of ADR 0016 is unchanged (Angular matches `[toggler]` on a bare attribute, whose static value initialises the input as `''`), the Toggler keeps its toggle-button role and `aria-pressed`, and the owning directive renders its class from the same state on the server.
   Settled: (d) (D17). It replaces the spec's development warning for an empty `toggler` (user story 19 rewritten): a forgotten value now reads as the state-only form, and the missing look shows at the first manual test, while `aria-pressed` still flips. Source: ADR 0039; ADR 0016; BB 1.9; TR D6.
5. **Does class mode keep toggling the developer's own class?** Yes: ADR 0039's follow-up names "the Toggler's class mode toggling an application class" among the inputs that stay, and BB 1.4 lets a directive read the consumer's own classes to seed state. The leading-dot and whitespace transform stays; the `active` seed from the static `class` stays, now defined as `false` for an empty `toggler`. Source: ADR 0039; BB 1.4.
6. **How does a developer learn that `toggler` names a Foundation class?** A development check (check 3), widened from the spec's visibility-class check: Foundation's hiding classes (`is-hidden`, `hide`, `invisible`) point to visibility mode; `expanded` and the `is-` and `nfs-` prefixes point to the owning directive's input. A complete list is out of reach (palette and size names are the consumer's Sass), so the check covers what Foundation's Toggler docs teach and the two prefixes that mark Foundation's State classes and the library's classes; the rule itself is ADR 0039's. A developer class starting `is-` gets a warning to rename it, which follows Foundation's own reservation of that prefix. Source: FS docs (`data-toggler=".expanded"`, `data-toggler="is-hidden"`); CONTEXT **State class**.

Round 3 (depends on 4-6): `animate` under the follow-up decision.

7. **What does `animate` take?** ADR 0039's follow-up: "a Motion input takes `'fade-in'`, never `'nfs-fade-in'`, and the directive maps it to its class", while inputs that apply the consumer's own classes stay. RV settled the shape for every Motion input and measured it with `ngc` 22.2.0 strict templates: closed name unions `NfsMotionInName` and `NfsMotionOutName` (the `nfs-motion` set without its prefix, `spin-in` added), the developer's own keyframe classes in Foundation's dot form `NfsMotionClassList` (`` `.${string}` ``, the notation Foundation's own `data-toggler=".class"` uses), `NfsMotionIn` and `NfsMotionOut` over them with `''`, and the pure mapping `nfsMotionClasses`, all in the primary entry point. RV's note for this ticket asks the Toggler to type its `"<in> <out>"` pair over `NfsMotionIn` and `NfsMotionOut`, "with the second half optional". Settled: the same names and types, with no Toggler-specific alias beside them. An earlier draft of this ticket used an object form `{in?, out?}` for the developer's classes; it is withdrawn in favour of RV's dot form, so one shape serves all four Motion inputs. Source: RV decisions 3, 10, its probe, and its note; ADR 0039.
8. **Where does the Toggler add to RV's pair note?** Foundation's `data-closable="slide-out-right"` has no entering value, and CO user story 12 and TR decision 4 write its counterpart as the Toggler's Motion name alone. Under "the second half optional", a lone value is the entering half, so `animate="slide-out-right"` would fail to compile. Motion UI's leaving names are disjoint from its entering ones (every name carries `-in` or `-out`, `research/foundation-utilities-conventions.md` 4.1), so a leaving name alone can tell its own direction. Settled: `NfsMotionPair` = `NfsMotionIn` (an entering value alone, or `''`) | `NfsMotionOutName` (a leaving name alone) | `` `${NfsMotionInName | NfsMotionClassList} ${NfsMotionOutName | NfsMotionClassList}` `` (Foundation's order). This is the one place the Toggler differs from RV's note: a superset that adds the lone leaving name, for the `data-closable` counterpart; a lone dot-form class stays the entering half, because a class's name tells no direction. A space separates the halves, so each half holds one class of the developer's own (RV's single-direction inputs accept several, `.a .b`). Rejected: a `none` keyword or a leading space for an empty entering half. Source: CO; TR; RV.
9. **Where do the types and the mapping live?** RV's types and `nfsMotionClasses` live in the primary entry point. The pair type and a pure `nfsMotionPairClasses` (split on whitespace, a lone leaving name to the leaving half, each half through `nfsMotionClasses`) join them there, because DD and the Responsive Toggle's `animate` hold both directions in one string too; DD's placeholder name `NfsMotionPair` is kept. The types add no runtime import (ADR 0040's measurement); the two functions are small runtime imports from the primary entry point, as RV's `nfsMotionClasses` and ADR 0040's `nfsVariantBoolean` already are. A node-level Sass compile case asserts one `nfs-` class per Motion name. Source: RV decision 10; DD; ADR 0040 Consequences.
10. **Which development checks change?** The spec's checks 1 (Motion UI transition names) and 2 (more than two tokens) give way to the type; a cast still reaches the mapping, so a new check 4, run in the `read` phase that measures a phase's animation, reports a value that starts no animation (a Motion name without the `nfs-motion` include, a class of the developer's own without `@keyframes`, a Motion UI transition class in the dot form), a value `nfsMotionPairClasses` cannot read, and a dot-form `nfs-` class: RV's check 3 in the Toggler's words, and DD's check 5. The phase completes as before. Source: the spec's completion rule; RV check 3; DD check 5.

Round 4 (depends on 7-10): State classes and the initial state.

11. **Does anything become a `Renderer2` write?** No. Every class the Toggler binds (`.is-hidden`, Motion classes, the developer's classes) sits on its own host, which carries the directive, so each is a host binding; MG's exception for elements without a library directive is not needed, and TR D18 (no Openable writes a class on its Triggers) holds. Source: MG; TR D18.
12. **What happens to the `is-hidden` seed?** BB 1.4's initial-state bullet names "the Toggler's `is-hidden`" among the seeds the re-runs remove. Settled: removed; a closed start is the `hidden` attribute or `[isOpen]="false"`. `hidden` stays a seed: it is a native attribute with the semantics the Toggler binds, not a class, and BB 1.4 forbids only seeding from a class. A copied `class="is-hidden"` is stripped while the element is shown, because the dynamic binding wins over a static class (ACC decision 6), so check 1 reads the static class through `HostAttributeToken('class')` in a development-only field initialiser and warns once, in ACC's dev check 7 shape (D19). Source: BB 1.4; ACC.
13. **The close-button rows?** They follow CB: `nfsCloseButton` with a bare `nfsClose` beside it (it closes nothing itself), no `type`, no class; the 2.5.8 row states that every close button is at least 24 by 24 px through the `nfs-close-button` floor, and the spacing-exception reasoning and the consumer `min-width` recipe go (CB's note for this ticket, reproduced). The glyph's 1.4.11 contrast is the Close Button's and the Callout's. Source: CB decisions 1, 2, 8, 9; CO decision 7.

Round 5 (depends on 11-13): examples, stories, tests.

14. **Examples and Rendered HTML?** Every consumer template writes directives only; the Rendered HTML shows the classes the directives bind, `toggler=""` for the state-only form, and the Menu's `.expanded` after a click. The dismissible callouts follow CO (focus moved in `closed`); the removal-with-a-library-Motion composition follows TR D17 (hide through the Toggler, remove in `closed`). The `data-closable` Dropped options sentence takes TR's wording. The spec's hint that a plain `@defer` block could add `animate.enter` with an `nfs-` class is replaced, because it put a library class in consumer code. Source: ADR 0039; CO; TR.
15. **Stories?** Story ids unchanged. `toggler--class-mode` is Foundation's menu example on `ul[nfsMenu]` with the state-only form; `toggler--class-mode-initially-active` shows the developer's own class seed; `toggler--initially-hidden` uses `hidden` and `[isOpen]="false"`; `toggler--visibility-animated` and `toggler--multiple-targets` use Foundation's `hinge-in-from-top spin-out`; `toggler--closable` animates with a leaving name alone and asserts the close button's 24 px box; `toggler--two-way-binding` feeds `[(active)]` into `[expanded]`. No story writes a Foundation or library class; the dot form has no story, because stories carry no CSS of their own, so browser-level tests cover it with a test stylesheet. Source: storybook-conventions sections 3, 8, and the checklist.
16. **Browser-level, SSR, pure logic?** Browser-level: the bare `toggler` in matching and seeding, the copied `is-hidden`, every `animate` shape including the dot form, class mode as a Variant source, and the four checks. SSR smoke: the class-free fixture asserts `class="menu"` without `expanded`, the developer's class, and no Motion class. Pure logic: `nfsMotionPairClasses` and the known-class check. Sass: the `nfs-motion` name-to-class case. The pair's two-half template-literal type was not compiled separately; RV measured its parts, and the first typings case confirms the pair. Source: BB 1.12; RV's probe.
17. **Glossary or ADR?** Glossary: **Class mode** is sharpened (the developer's own class, or the state-only form); **Motion class** and **Motion name** take TR's and RV's wording, which fits this spec. No new ADR: the Motion names apply ADR 0039's follow-up (RV's dated note on ADR 0003 records them), and the state-only form keeps ADR 0016's selector rule, recorded as a dated note on ADR 0016.

The frontier is empty.

### Decisions

1. The Toggler has no Structural or Variant class: no Variant input, registry, alias, Variant property, or Runtime check request.
2. `.is-hidden` stays a host binding of `NfsToggler`; Motion classes are host bindings during their phase; every class sits on the Toggler's own host, and none on its Triggers.
3. Class mode's `toggler` names only the developer's own classes; `toggler` written without a value selects class mode and switches no class, so a Foundation Variant is bound from `active` into the input of the directive that owns it (D17). The development warning for an empty `toggler` is removed.
4. `animate` is `NfsMotionPair`, declared with an explicit type argument: an entering value alone (a Motion name or a dot-form class) or `''`, a leaving Motion name alone, or both halves in Foundation's order; a Motion name binds `nfs-<name>`, a dot-form class binds without its dot, one per half (D14, D18).
5. `NfsMotionPair` and `nfsMotionPairClasses` join the Reveal re-run's `NfsMotionInName`, `NfsMotionOutName`, `NfsMotionClassList`, `NfsMotionIn`, `NfsMotionOut`, and `nfsMotionClasses` in the primary entry point, shared with the Dropdown pane and Responsive Toggle; a Sass compile case keeps the name lists and `nfs-motion` equal.
6. The `is-hidden` seed is removed; `hidden` and the developer's own class stay seeds; a copied `is-hidden` is stripped while shown and reported (D4, D19).
7. Development checks: (1) a copied `is-hidden`; (2) class mode with a static `animate`; (3) a Foundation or library class in `toggler`, over `is-hidden`, `hide`, `invisible`, `expanded`, and the `is-` and `nfs-` prefixes (D20); (4) an `animate` value that starts no animation, where the phase is measured.
8. Close buttons are `nfsCloseButton` with a bare `nfsClose`; 2.5.8 is the `nfs-close-button` floor, and the spec adds no rule.
9. The target and Trigger classes come from `nfsCallout`, `nfsMenu`, `nfsThumbnail`, `nfsButton`, and `nfsCloseButton`, placed beside, never hosted (D21).
10. Every example, story, fixture, and test host writes no Foundation or library class; Story ids unchanged; user stories 2 to 5, 7, 8, 14, 17 to 19 rewritten in place and 44 to 48 appended.
11. Behaviour, ARIA, keys, focus, animation phases and completion, and rendering modes are unchanged.
12. Glossary: **Class mode** amended; **Motion class** and **Motion name** as TR and RV propose; a dated note on ADR 0016; no new ADR.
