## Answer

Spec: [specs/responsive-accordion-tabs.md](../specs/responsive-accordion-tabs.md).

Gist: ResponsiveAccordionTabs is the one element-selector component, `nfs-responsive-accordion-tabs`, with a required `rules` input (Foundation's rule string or the typed object form, parsed by the shared `parseNfsBreakpointRules` and resolved by Breakpoint map order) and consumer sections as `ng-template[nfsResponsiveAccordionTabsPanel]` with `title`, `value`, and an optional `id`. It renders the library's Accordion directive set or its Tabs directive set, composed exactly as their specs define them (content key guard, replay guards, expansion policy, server-side tab stop, required Sass settings), and writes their `[panel]` links and `value`s itself. One `selected` model names the open item in both modes (the expanded accordion item or `undefined`; the selected tab, with the Tabs first-tab default), so a swap needs no mapping. Other inputs: `allowAllClosed`, `selectionMode`, `wrapOnKeys`, `headingLevel` (native `h1`-`h6`, default 3), `label`/`labelledBy`, and the deep-link options, which the component owns once for both modes. Outputs: `selectedChange`, `selectionChange` and `deepLinked` (`{value, panel}`); a read-only `mode` signal through `exportAs`. The Mode swap is the one accepted structural re-render: an `afterRenderEffect` reads focus in `earlyRead` and sets the displayed mode, and refocuses the equivalent control in `write`; every instance starts from the Server breakpoint's mode (the `instance` strategy), which needs a small Breakpoint service amendment. Consumer state inside sections resets on a swap, and a pre-hydration click on a control the first-render swap removes is lost, both documented. `multiExpand`, `autoFocus`, and vertical tabs are dropped or out of scope. No library CSS; three Foundation settings (the Accordion's and the Tabs spec's) make both modes pass WCAG 2.2 AA. Self-grilled against the sources below; nothing needs a prototype, and after triage only human-only items remain open.

### Decision log

Sources: RAT prototype = [Prototype: ResponsiveAccordionTabs as one component](51-prototype-responsive-accordion-tabs.md), its README, and its component and media-query source; Aria prototype = [Prototype: `@angular/aria` Accordion and Tabs under Foundation markup](43-prototype-aria-accordion-tabs.md); Accordion spec = [Spec: Accordion](../specs/accordion.md); Tabs spec = [Spec: Tabs](../specs/tabs.md); BP spec = [Spec: Breakpoint service (shared utility)](../specs/breakpoint-service.md); Foundation = `js/foundation.responsiveAccordionTabs.js`, `js/foundation.tabs.js`, `docs/pages/responsive-accordion-tabs.md` in the 6.9.0 clone; BB = `building-blocks.md`; R:x = the research files.

1. Q: Directive or component? A: One element-selector component, `nfs-responsive-accordion-tabs`, plus the `ng-template[nfsResponsiveAccordionTabsPanel]` directive. Source: ADR 0001 case 1; BB 1.1 and Table A; R:disclosure ResponsiveAccordionTabs "Behaviour that only jQuery makes easy"; RAT prototype verdict.
2. Q: Which option list? A: From Foundation's own source, not the ticket: `ResponsiveAccordionTabs.defaults = {}`, the `data-responsive-accordion-tabs` rules, the `reflow` constructor check, and every Accordion and Tabs option passed through (`_getAllOptions`, `this.options` handed to the child); events are the base lifecycle pair plus the live child's events; methods `open`, `close`, `toggle` (the last two accordion only), `destroy`. Source: Foundation plugin source lines 37-40, 104-127, 175, 249-289; docs page "All data-options ... can be passed through"; audit guard H6/M12.
3. Q: The `rules` input? A: `input.required<string | NfsBreakpointRules<'accordion' | 'tabs'>>()`, parsed by the shared parser against `mq.breakpoints`, resolved by map order through `resolve()`; a runtime change swaps like a resize. Source: BB 1.7 option-syntax bullet; BP spec API and rule grammar; Foundation docs "the accordion/tabs values can be in any order".
4. Q: What renders when no rule applies (rules with no Zero-breakpoint mode)? A: Accordion, with a once-per-instance dev warning. Foundation initialises no plugin ("No match? No dice"), which leaves hidden content; accordion is the mobile-first form and readable without JavaScript. Source: Foundation source lines 146-154; BP spec (`resolve` returns `undefined`, "left to the consuming spec"); RAT prototype fallback.
5. Q: Is the swap a structural re-render or a same-node class-and-role change? A: Structural: an `@if` branch, the one re-render ADR 0008 accepts. Source: RAT prototype verdict (static directive matching, panel placement, WAI-ARIA 1.3 tablist allowed children); R:rendering section 7 ResponsiveAccordionTabs row; ADR 0008 Consequences; R:apg ResponsiveAccordionTabs (heading semantics flip, so the elements must differ).
6. Q: Do container queries make the visual switch CSS-only? A: No. They are in the Browser target but cannot change roles, headings, or panel placement, and Foundation's rules are viewport breakpoints. Source: R:platform ResponsiveAccordionTabs row ("switching between two ARIA patterns is script"); ADR 0005 considered options; BB 1.7 "CSS first" bullet.
7. Q: Swap mechanics? A: The prototype's, as the spec's behaviour: the displayed mode is its own signal, following the viewport's mode in an `afterRenderEffect` `earlyRead` that first reads `document.activeElement` and records the section containing it; the `write` phase focuses the matching control once the new branch has rendered (it re-runs when the controls query changes in the same tick). The spec finds sections through view queries instead of the prototype's `data-nfs-value` attributes, so no test-only attributes reach server HTML. Source: RAT prototype source and "Decisions handed to the specs"; the angular-developer skill's `effects.md` on `afterRenderEffect` phases.
8. Q: The first render: service `current` or the Server breakpoint? A: The `instance` strategy: every instance starts from the Server breakpoint's mode and swaps in its own first `earlyRead`. Measured: deferred blocks hydrate as sent and keep focus; client-created instances never paint the wrong mode. Source: RAT prototype cases 4, 15, 19 to 21; proposed ADR below.
9. Q: How does the component read the Server breakpoint? A: The BP spec's API has no such member, so the spec proposes a read-only `serverBreakpoint` on `NfsMediaQuery` (the transferred or configured value the service started from) and an optional second argument `resolve(rules, breakpoint?)`, as the prototype added. Source: BP spec API table and handoff bullet; RAT prototype media-query source.
10. Q: Is the BP spec's consumer rule 1 ("nothing inside the widget can hold focus before the first render callback") true? A: No, for server-rendered pages: server-rendered titles are focusable, and a title focused before hydration is handed to the equivalent tab by the same mechanism. Amendment proposed below. Source: RAT prototype case 15.
11. Q: `multiExpand`? A: Dropped. Tabs show one panel (APG), so several open items have no tabs equivalent; Foundation's own switch copies every `is-active` from `li` to panel, and Foundation Tabs then marks each such tab `aria-selected="true"` with `tabindex="0"` and shows each panel (source reading), so Foundation has no working behaviour to keep. Adding `multiExpand` later (default `false`, with an array model) changes nothing already shipped. Source: Foundation RAT source lines 233-236 and Tabs `_init` lines 52-81; APG tabs; Tabs spec D15.
12. Q: `allowAllClosed`? A: Passed to `NfsAccordion`, default `false` (Foundation's), so the last open title is locked with `aria-disabled="true"` (ADR 0028). Source: Accordion spec; ADR 0028; R:apg ResponsiveAccordionTabs (the sole open header needs `aria-disabled`).
13. Q: `selectionMode` and `wrapOnKeys`? A: Both passed to `NfsTabs`, defaults `'follow'` and `true`. The component owns them, so its Defaults token can default them (unlike the Tabs token, which cannot change an Aria input's default). Source: Tabs spec API and D16; Foundation Tabs `wrapOnKeys`.
14. Q: `orientation` (vertical tabs)? A: Not exposed. Vertical tabs need Foundation's grid layout around strip and content, which the component does not own; Foundation's own switch inserts `.tabs-content` right after the element, so it did not support that layout either. Source: Tabs spec vertical example; Foundation RAT source lines 211-219.
15. Q: How does `selected` map between modes (single value versus multi-expand)? A: One `selected` model names the open item: the expanded accordion item or `undefined`, and the selected tab. In tabs mode the component binds `[selected]` two-way to `NfsTabs`, whose first-tab default writes the first value when `selected` is `undefined` or unknown, so `selected` always names what is on screen. The carry rules follow: tabs to accordion expands the selected tab's item; accordion to tabs selects the expanded item or the first tab. This departs from the prototype, which left `selected` unset while tabs showed the first panel; that was a side effect of binding a fallback value, not a deliberated contract, and it contradicts the Tabs spec's D6. The parent-model write during the child's content init is re-run by Angular's `detectChangesInViewWhileDirty` loop (`packages/core/src/render3/instructions/change_detection.ts` in the 22.2 clone), the same write the Tabs spec already makes into any consumer's `[(selected)]`. Source: Tabs spec D6 and first-tab default rule; RAT prototype cases 10 and 11; Angular source.
16. Q: Which changes emit `selectionChange` and write history? A: Every client change except the first-tab default (a move from `undefined` or an unknown value to the first section's value while tabs mode is displayed) and hash-driven changes; swaps change only `mode`, never `selected` directly, so they emit nothing. `selectedChange` fires for every model change. Source: Tabs spec `selectionChange` rule and D7; BB 1.4 aggregate outputs carry the item.
17. Q: Output payloads? A: `NfsResponsiveAccordionTabsChange {value, panel}` for `selectionChange` and `deepLinked`, with both `undefined` when the accordion closes its last section. Source: BB 1.4 ("container-level aggregate outputs carry the item"); Tabs spec `NfsTabChange`; the Accordion's item payload.
18. Q: Deep-link inputs? A: `deepLink`, `updateHistory`, `deepLinkSmudge`, `deepLinkSmudgeOffset` on the component, owned by it for both modes; the inner Accordion and Tabs always get `deepLink` false. Passing them through would re-read the hash, re-emit `deepLinked`, and smudge-scroll at every swap, because both specs apply deep links in each instance's first render callback (and Foundation re-inits the child at every switch). Hash rules: the union of the two specs (write on client changes except defaults and hash-driven ones; clear the fragment when the accordion's last section closes; an empty hash restores the first-render value; `history.state` passed through). Source: Accordion spec deep-link rule; Tabs spec deep-link rules 1 to 4; Foundation RAT source lines 168-175.
19. Q: Where do deep-link ids come from? A: The section's optional `id`, bound to Aria's `id` input on `[nfsAccordionContent]` or `[nfsTabsPanel]`; only one exists at a time, so no duplicate ids; a dev warning under `deepLink` when a section has none. Source: BB 1.5 ids rule; R:rendering rule 8; Foundation docs (content should have an id).
20. Q: `deepLinkSmudgeDelay`, `deepLinkSmudgeOffset`? A: Delay dropped (browser timing); offset kept as `scroll-margin-top` on the displayed list, the Tabs spec's rule (the Accordion spec dropped it for CSS; the component follows the Tabs form because the consumer cannot reach the internal list with a stable selector). Source: Tabs spec D13; Accordion spec contract table.
21. Q: `autoFocus`? A: Dropped. The Tabs directive focuses once per instance, which would fire again at every swap; the APG and the effort's focus rules avoid moving focus on load. Additive later. Source: Tabs spec `autoFocus` rule; BB 1.10 focus bullet.
22. Q: `slideSpeed`, `matchHeight`, `activeCollapse`, class options, `reflow`? A: Dropped with the Accordion and Tabs specs' reasons (`nfs-accordion($duration)`, the grid recipe on the component's `.tabs-content`, APG, classes as contract); `reflow` is Foundation's re-init mechanism. Source: Accordion spec; Tabs spec; BB 1.4 dropped options.
23. Q: Heading level? A: `headingLevel` input, default 3 (the APG example), native `h1`-`h6` through `@switch`, clamped to 1 to 6 with a dev warning. Not `role="heading"`: the `nfs-accordion` rules and the Accordion's dev check key on native headings. The title button is written inside each item because a template's DI follows its declaration site. Source: APG accordion; Accordion spec rules 1 and 3 and dev check 1; RAT prototype "does not prove" (heading fixed at `h3`).
24. Q: Naming the widget? A: `label` and `labelledBy` inputs applied to the rendered list in both modes; a dev warning when neither is set. `aria-label` on the host would sit on an element with no role. Source: BB 1.10 names bullet; Tabs spec dev check (tab list name); R:apg ResponsiveAccordionTabs (tabs mode needs `tablist` labelling).
25. Q: Methods? A: None; `selected` is the programmatic API (Foundation's `open`, `close`, `toggle` become writes; writes bypass the `allowAllClosed` lock, as ADR 0028 records for bindings). Source: Tabs spec "Methods: none"; ADR 0028 Consequences.
26. Q: Section query shape? A: `contentChildren(NfsResponsiveAccordionTabsPanel)` with direct children; sections inside `@for`/`@if` match because nodes in an embedded view created from a template directly in the content count as direct children. Source: Angular `query.ts` `isApplyingToNode` in the 22.2 clone; BB 1.9 (queries otherwise for validation; the Tabs spec's server-render exception applies).
27. Q: Focus continuity rules? A: Only when focus was inside the widget; title and tab of the same value swap; focus in content or on a tab panel goes to the section's control; the selection does not change; `focus()` without `preventScroll`. Source: R:apg ResponsiveAccordionTabs (persistence of focus); BP spec consumer rule 1 (amended); RAT prototype cases 7 to 13.
28. Q: What is lost on a swap? A: Stated plainly in the spec: state inside section content not held outside it (unbound input values, scroll inside panels, component instances and their init work, unbound nested widgets), and a pre-hydration click or key on a control the first-render swap removes. Kept: `selected`, focus, the URL, consumer-bound state. Source: RAT prototype cases 14, 16, 18.
29. Q: Incremental hydration triggers? A: `hydrate on viewport`, `on idle`, `on timer`, `on immediate` hydrate as sent, then swap; recommend them over `on interaction`, whose triggering click lands on a title the swap removes on wide viewports (the case 16 mechanism; replay runs after the render callbacks). `hydrate never` keeps the Server breakpoint's mode. Source: RAT prototype cases 16, 19 to 21; R:rendering section 3 replay order; BP spec Rendering modes.
30. Q: Animation? A: None added; accordion mode keeps `nfs-accordion`'s transition and reduced-motion rule; a branch created by a swap starts in its final state, so no transition runs (a CSS transition needs a before-change style) and the Accordion's phase starts settled; no `animate.enter`. Source: ADR 0003; Accordion spec Animation; [Prototype: `animate.enter` at hydration](52-prototype-animate-enter-hydration.md).
31. Q: Render hooks and `injectAsync`? A: `afterRenderEffect` (`earlyRead`, `write`) for the swap and refocus; `afterRenderEffect` for `selectionChange`, history, and the `hashchange` listener; `afterNextRender` for the initial hash, the smudge scroll, and dev checks; no `effect`, no `afterEveryRender`. `injectAsync` does not apply: both modes are needed at the first render callback, and on-demand loading would paint the wrong mode. Source: BB 1.5; [Spec: Anchored pane (shared utility)](../specs/anchored-pane.md) D20 and D21 (same reasoning); `effects.md`.
32. Q: Contrast settings? A: The Accordion's `$accordion-item-color: scale-color($primary-color, $lightness: -15%)` and the Tabs spec's `$tab-background-active: $primary-color; $tab-active-color: $white`, not the prototype's `$tab-active-color` darkening, which fixed the text (1.4.3) but left the selected look at 1.24:1 (1.4.11). Source: Tabs spec D17 and its WCAG table; Accordion spec 1.4.3 row; RAT prototype Custom CSS.
33. Q: Library CSS? A: None; no `nfs-responsive-accordion-tabs` mixin; `nfs-accordion` required, `nfs-tabs` not needed. Source: ADR 0012; RAT prototype Custom CSS; Accordion and Tabs Sass subsections.
34. Q: Material counterpart? A: None ("Material has no 'responsive component'"); compared with `mat-tab-group`, `mat-accordion`, and the navigation schematic's `BreakpointObserver` switch. Source: R:material 11.
35. Q: Defaults token? A: `nfsResponsiveAccordionTabsDefaultsToken` over every component-owned option; the Accordion and Tabs tokens do not reach the options the component binds. Source: BB 1.4 Defaults token bullet; the Tabs answer's building-blocks proposal 4.
36. Q: Testing seams, resize cases included? A: Play functions choose the mode through `rules` at the 414 px layer-1 viewport, with a story control that flips it; browser-level tests drive the service through a fake `MediaMatcher` and `TransferState`; the SSR smoke covers both Server breakpoints; Playwright covers real resizes, focus before hydration, pre-hydration clicks at both widths, client hints, and `hydrate on viewport` in three engines. The layer headings and the browser-level opening sentence are the [Decide the browser testing stack: Playwright component tests, Vitest Browser, or both](41-browser-testing-stack-decision.md) wording. Source: ADR 0018; `storybook-conventions.md` section 3 (414 px); RAT prototype test suite.
37. WCAG 2.2 AA criteria addressed, each a requirement in the spec: 1.3.1 (each mode's own elements), 1.3.4 (both modes carry the same content), 1.4.3 (three required settings), 1.4.11 (Tabs settings plus a play-function check), 1.4.10 (wrapping titles; accordion at the Zero breakpoint recommended), 1.4.12, 1.4.13 (no hover or focus content; automatic activation is selection state), 2.1.1 (native buttons, server-side tab stop, guards), 2.4.3 (swap refocus), 2.4.6 (heading level and title), 2.4.7 (Foundation's outline kept plus `:focus` backgrounds), 2.4.11 (no overlay, refocus scrolls into view, offset or `scroll-padding-top`), 2.5.3, 2.5.8 (about 52 px targets, axe `target-size`), 2.2.2, 3.2.1, 4.1.2. Source: ADR 0022; the Accordion and Tabs WCAG tables; RAT prototype cases 22 and 23.

### Proposed glossary terms

**Mode swap**:
A responsive Plugin's change of mode when its Breakpoint rule resolves to another mode: a class and key change on the same nodes for the menu Plugins, a structural re-render of its own template for ResponsiveAccordionTabs, the one ADR 0008 accepts.
_Avoid_: mode switch, re-init, re-render (bare), toggle

### Proposed ADR

- [`adr/0032-responsive-accordion-tabs-instance-first-render.md`](../adr/0032-responsive-accordion-tabs-instance-first-render.md): ResponsiveAccordionTabs starts every instance from the Server breakpoint's mode. Hard to reverse (every instance's first render and a service API), surprising against ADR 0014's rejected option, and the result of a measured trade-off.

### Proposed building-blocks changes

1. Table A, ResponsiveAccordionTabs row: the selector sketch becomes `nfs-responsive-accordion-tabs` with `rules`, a `selected` model, `allowAllClosed`, `selectionMode`, `wrapOnKeys`, `headingLevel`, `label`/`labelledBy`, and the deep-link options; sections as `ng-template[nfsResponsiveAccordionTabsPanel]` with `title`, `value`, optional `id`. "Switched by `NfsMediaQuery.atLeast` per rule" becomes "resolved by `NfsMediaQuery.resolve()`, starting from the Server breakpoint's mode". Reason: decision log 3, 8, 12 to 24.
2. Table B, ResponsiveAccordionTabs row: the DI cell becomes "composes the Accordion and Tabs directive sets as their specs define them, binds every option it owns (so their Defaults tokens do not reach them), `nfsResponsiveAccordionTabsDefaultsToken`"; the rendering cell adds "the swap runs in an `afterRenderEffect` `earlyRead` with a `write` refocus; every instance starts from the Server breakpoint's mode; pre-hydration input on a control the first-render swap removes is lost". Reason: decision log 7, 8, 28, 29, 35.
3. 1.7 Server value bullet and 1.10 focus bullet: add that the first-render swap moves focus like any other (server-rendered controls can hold focus before hydration). Reason: decision log 10.
4. 1.11 decision 8: "`@if` branch rebuild for ResponsiveAccordionTabs" becomes "an `@if` branch swap in the component's first render callback (the block hydrates as sent)". Reason: decision log 8.
