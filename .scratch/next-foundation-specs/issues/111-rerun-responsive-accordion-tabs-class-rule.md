# 111. Re-run: Responsive Accordion Tabs spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81, 107, 108
Labels: wayfinder:grilling

## Question

What does the [Spec: Responsive Accordion Tabs](19-spec-responsive-accordion-tabs.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/responsive-accordion-tabs.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

Also: RAT4 and RAT6 keep their exclusions with restated reasons (the triage file, section 3).

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Responsive Accordion Tabs](19-spec-responsive-accordion-tabs.md) and the answer here. Model: Opus 5.5.

## Answer

Model: Opus 5.5. Worked AFK as a self-grilling (both sides) against the sources the ticket names, with `/domain-modeling` for vocabulary and `/to-spec` for the revision. Spec: [specs/responsive-accordion-tabs.md](../specs/responsive-accordion-tabs.md), revised in place; the dated amendment is in the [Spec: Responsive Accordion Tabs](19-spec-responsive-accordion-tabs.md) under `### Amendment, 2026-09-27 (class rule)`.

Gist: the consumer already wrote no Foundation class here, because the host is the component and sections are `ng-template`s. The class rule still changed four things. The component's own template now writes no class either: `div[nfsTabsContent]` replaces the plain `div.tabs-content`, and the composed directives bind every class of both modes. Foundation's `.simple` and `.primary` looks, which Foundation's plugin keeps on its element across switches but which the consumer can no longer reach, become the boolean Variant inputs `simple` and `primary`, passed to `NfsTabs` in tabs mode. A Foundation class copied onto the host is reported in development, because the host binds no class and a copied `tabs` draws a border around the whole widget. The equal-heights recipe is restated without a Foundation class. RAT4 and RAT6 keep their exclusions with restated reasons. Two cheap measurements ran in Chromium, Firefox, and WebKit (Playwright 1.63 over Foundation 6.9's compiled CSS, under `D:/tmp/nfs-wave-111/`, no junction, nothing left running). Nothing is `OPEN FOR HUMAN`, and no prototype is needed.

### Decision log

Sources: ADR 0039; ADR 0040; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) ("81"); the Answers of [Re-run: Accordion spec under the class rule](107-rerun-accordion-class-rule.md) ("107") and [Re-run: Tabs spec under the class rule](108-rerun-tabs-class-rule.md) ("108"); `specs/accordion.md` and `specs/tabs.md` as revised; `research/out-of-scope-triage.md` section 3 ("triage"); `research/out-of-scope-exclusions.md` rows RAT1 to RAT10; BB = `building-blocks.md` as it stands; Foundation = `js/foundation.responsiveAccordionTabs.js`, `docs/pages/responsive-accordion-tabs.md`, `docs/pages/tabs.md`, and `scss/components/_tabs.scss` in the 6.9.0 clone; Measure = the two checks under `D:/tmp/nfs-wave-111/`.

1. Q: Which classes did the spec leave to the consumer? A: None in consumer markup: the host is `nfs-responsive-accordion-tabs`, and the sections are `ng-template`s, which render no element. The component's own template wrote `div.tabs-content`, a Structural class with no directive, and its hierarchy sketch spelled `ul[nfsTabs].tabs` and the like, which reads as if the template wrote the other classes too. Two consumer-facing losses were hidden behind that: Foundation's `.simple` and `.primary` looks, and Foundation's `is-active` initial state, which the spec covered through `selected` without saying so. Source: the spec before this revision; Foundation plugin `_checkMediaQueries` (removes only `MenuPlugins[*].cssClass`, `accordion` and `tabs`) and `_handleMarkup`.
2. Q: Does the component's template write classes? A: No. Every Foundation class of both modes is bound by the directive that owns it: `.accordion`, `.accordion-item`, `.accordion-title`, `.accordion-content`, `.tabs`, `.tabs-title`, `.tabs-content` (the new `[nfsTabsContent]`, which provides nothing and binds `.vertical` only for a vertical tab list, which never happens here), `.tabs-panel` as static `host` classes, and `.is-active` as host bindings. No class on the `nfsAccordionItem` hosts, as 107 asks, so its dev check 7 and the Tabs copied-class check stay silent. Rejected: redundant Structural classes in the template (a second spelling that can drift). Source: ADR 0039; 107 and 108, "What other specs need"; the Tabs spec's `NfsTabsContent` section.
3. Q: Initial state without `class="is-active"`? A: `selected` on the component (`selected="specs"`, a static string, which compiles for a `model<string | undefined>`, or a binding). Accordion mode applies it through each title's `[expanded]="selected() === value"`, the only initial-state path the Accordion spec keeps; tabs mode through `[selected]` on `ul[nfsTabs]`. The spec's phrase "as a title's `[expanded]` binding does in the Accordion spec" stays true. Source: 107 decision 5; BB 1.4 initial-state bullet; the spec's behaviour rules.
4. Q: Variant classes: which does the component render, and which become inputs? A: Foundation's accordion has none (Accordion D24). `.tabs` has three: `.vertical`, `.simple`, `.primary`. `.simple` and `.primary` become `simple` and `primary` on the component, booleans through `nfsVariantBoolean` (`input<boolean, NfsVariantBoolean>`), bound to `NfsTabs`' inputs of the same names in tabs mode and doing nothing in accordion mode. Why expose them: ADR 0039 has every Variant class set by a typed input, the consumer cannot reach the internal strip, and Foundation's plugin keeps these classes on its element across switches, so a Foundation consumer had both looks in tabs mode. Leaving them out would exclude a Foundation look only because it is a class, which the user's ruling of 2026-09-27 forbids. Two booleans, not an enum, because the classes combine; closed, so no registry, no Variant property, and no runtime-check case; not in the Defaults token. `.vertical` stays out (decision 9). Rejected: leaving them out as "additive later" (the ticket's narrow reading; see Dissent); one `look` enum; `booleanAttribute`. Source: ADR 0040; BB 1.4 naming rule 4 and the authoring bullet; 81, "What the 25 spec tickets and 26 re-run tickets need to know"; 108 decisions 5 and 12 and its note "If the re-run exposes either look, it passes it to `NfsTabs` and requires `nfs-tabs`"; Foundation plugin source.
5. Q: What do `simple` and `primary` cost in accessibility and Sass? A: The Tabs spec already made both looks pass WCAG 2.2 AA through `nfs-tabs`: the `simple` titles' 24 by 24 px minimum (2.5.8, Tabs D22) and the selected tab's colours on a `primary` bar with a compile-time check (1.4.3 and 1.4.11, Tabs D23). So `nfs-tabs` is required when either input is set and not otherwise, since plain strips do not depend on it and its compile-time check would stop a consumer who never uses `primary`. The WCAG rows, the Sass subsection items (1), (5), and (6), D20, and the consumer Sass example say so. A new story, `responsive-accordion-tabs--tabs-looks`, runs the gate on both looks and asserts the 3:1 bar ratio and the 24 px boxes; the three-engine geometry stays the Tabs spec's `tabs--simple` e2e case, because the same directive and rule draw it. Source: `specs/tabs.md` Sass subsection and WCAG table.
6. Q: What happens to a Foundation class copied onto the host? A: The host binds no class, so the class is not stripped, unlike a class copied onto a directive's host. It styles the host itself. Measured: a host with `class="tabs"` gets a 1 px solid border and Foundation's tab background around the whole widget in all three engines, where a class-free host has none. Foundation's own markup puts `accordion` or `tabs`, and on tab strips `vertical`, `simple`, or `primary`, exactly on that element, so a migration copies them. New dev check 7 reads the host's static `class` through `HostAttributeToken('class')` in a development-only field initialiser (the Accordion's dev check 7 mechanism) and warns once, naming the fix. It reports only those five whole tokens, never the consumer's own classes. Rejected: no check (a silent visual defect); binding each class to `false` to strip it (silent, and five bindings for a development concern). Source: Measure (`recipe.html`, cases "copied" and "plain"); 107 decision 6; BB 1.4.
7. Q: The equal-heights recipe (RAT9, "the Tabs spec's CSS grid recipe works on the component's `.tabs-content`")? A: Under the class rule the recipe may name no Foundation class (BB 1.1 consequence, Accordion D27), and the Tabs recipe's class goes on `[nfsTabsContent]`, which is inside this component. Restated: the consumer's class goes on the host, and the content box is selected as `.equal-heights > * > [role='tablist'] + *`, its panels as `... > [role='tabpanel']`, and hidden ones by `[inert]`. The child combinators keep a nested tab set out of it, and in accordion mode nothing matches. Measured in three engines against Foundation 6.9's CSS: the content box is a grid, all three panels take the tallest panel's height (531 px), the hidden ones are `visibility: hidden`, and a tab set nested in the shown panel keeps `display: block` on its content box and `display: none` on its hidden panel. It relies on the rendered structure the spec documents (the host's child is the tab group, the strip precedes the content box). `:has()` would remove that reliance and is listed for when the Browser target moves. Rejected: a `contentClass` input (new API for one recipe); a selector naming `.tabs-content`. Source: Measure (`recipe.html`, case "eq"); `specs/tabs.md` equal-heights recipe; BB 1.2 (`:has()` out of target).
8. Q: RAT4 and RAT6? A: Both keep their exclusions with the triage's restated reasons.
   - RAT4 (rich titles): a first-release limit. Foundation's titles are markup the consumer writes, so a plain-text `title` narrows them, and the upgrade is a title template on the section, rendered inside the accordion button or the tab, additive beside `title`. The Out of Scope line, the panel `title` API row, and the Material comparison say so.
   - RAT6 (`autoFocus`): D13 now leads with the refocus-at-swap reason. Passed through, the Tabs directive's once-per-instance focus fires at every Mode swap into tabs, because each swap creates the tab list again; a focus move at a swap belongs to the refocus rule (D9). A component-owned once-per-page option is additive later, as the deep links are owned once (D11). The APG's caution argues against a default, not an opt-in, so it is no longer the reason.
   - Source: triage section 3, rows RAT4 and RAT6 (LOW, HIGH).
9. Q: RAT2 (vertical tabs) under the class rule? A: Holds, reason unchanged, as 108 asks: `orientation` alone would now set both `.vertical` classes (Tabs D2), but Foundation's vertical tabs need the XY Grid to place strip and content side by side, and those cells would be the component's own elements, out of the consumer's reach. Foundation's own switch inserted `.tabs-content` straight after the strip, so it never supported that layout either. The class mapping lists `.vertical` with "none". Source: triage section 3 ("Foundation behaviour dropped for design reasons": RAT2); Foundation `docs/pages/tabs.md:85-109`; Foundation plugin `_handleMarkup`.
10. Q: Stories, tests, and the SSR smoke? A: No story, host, or fixture writes a class, except dev check 7's case. Stories add class assertions to `default` and `tabs-mode`, use `button[nfsButton]` controls (default size, no Variant input) in `mode-swap` and `bound-selection`, and gain `tabs-looks`. Browser level: a class-rule case (Structural classes of each mode, a class-free host, both composed copied-class checks silent, `selected="specs"` at first render, an application class kept), `simple` and `primary` pass-through, and dev check 7. SSR smoke: the fixtures write no class; the Structural classes of the displayed mode, `.simple` and `.primary` on that fixture's strip only, and a class-free host; a static `selected="specs"` fixture. Pure logic: dev check 7's whole-token test. Existing Story ids unchanged. Source: 107 decision 11; 108 decision 15; `storybook-conventions.md` section 3 and the checklist.
11. Q: User stories? A: 47 to 51 appended (every class set by the library, `selected` as initial state, the two looks with compile-time typo failure, the copied-class report, the equal-heights recipe); existing numbers kept, as 107 did.
12. Q: Rendering modes? A: Unchanged, apart from two sentences. Every Structural class and the two Variant classes are host bindings of the composed directives, so they are in the server HTML. Construction also reads, in development builds only, the host's static `class`.
13. Q: Glossary or ADR? A: Neither. No new term: Structural class, Variant class, State class, and Variant input carry it. No ADR: exposing `simple` and `primary` mirrors the Tabs spec's decided inputs and follows ADR 0039 and ADR 0040 without a fresh trade-off, dev check 7 is development-only, and the recipe is documentation; none meets all three bars.

### Dissent

- The lazier reading of the ticket: the spec left no Variant class consumer-written, so add no Variant input and record `.simple` and `.primary` as additive later. Not adopted, because the only honest reason to leave them out is that they are classes, which the user's ruling rules out, and the cost is two bindings that reuse the Tabs spec's types and `nfs-tabs` rules. Reopens if the consistency review finds a responsive widget with a look in one mode only confuses consumers more than the lost Foundation look costs.
