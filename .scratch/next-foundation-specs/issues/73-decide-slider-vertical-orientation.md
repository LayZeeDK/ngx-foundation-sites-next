# 73. Decide: Slider vertical orientation

Type: grilling
Status: resolved
Blocked by: none
Labels: wayfinder:grilling
Map: ../map.md

## Question

How should the vertical Slider (`.slider.vertical`) be built? The [Spec: Slider](32-spec-slider.md) uses one native `<input type="range">` per thumb, rotated inside Foundation's flipped `.slider.vertical` with `aria-orientation="vertical"` (its decision 29, from the [Prototype: Foundation-styled `<input type="range">` Slider](45-prototype-slider-range-input.md)), and left the vertical form OPEN FOR HUMAN in the trap quadrant because Chromium announces the rotated input as horizontal until vertical form controls reach the Browser target. The alternatives include: the same native input with CSS `writing-mode: vertical-lr` (or `direction`) where supported, falling back to rotation elsewhere; a custom `role="slider"` handle for the vertical form only; or dropping the vertical form until the platform catches up.

Decide it with the panel the map's "Open-decision pass" note prescribes: an evidence dossier, four panelists (Opus and Fable, two adversarial), and a judge. The decision must say exactly what the Slider spec, the `nfs-slider` mixin rules, building-blocks, and the README open list change to, and whether a prototype is needed first.

## How to work it

The orchestrator runs the panel. The evidence dossier goes to `research/decision-slider-vertical.md`: Baseline status and support dates for vertical form controls (`writing-mode` on `<input type="range">`) in the Browser target and in current engines (web-features, MDN browser-compat-data, caniuse); what each engine's accessibility tree exposes for a rotated input, a `writing-mode` input, and `aria-orientation` on a native range input (measured in Chromium, Firefox, and WebKit with Playwright's accessibility snapshot or the Chromium CDP accessibility tree, in a throwaway page under `D:/tmp/`); ARIA in HTML on `aria-orientation` for `input type=range`; the APG slider examples, including the vertical one; how Foundation 6.9's JavaScript Slider does vertical; how Angular Material's slider handles orientation; WCAG 2.2 AA implications (1.3.1, 4.1.2, 2.5.8); and the Slider spec's non-linear, two-handle, forced-colours, RTL, and hydration constraints any alternative must keep. The judge writes the `## Answer` here.

## Answer

Judge's ruling, 2026-09-27, on Opus 5.5: the judge runs on Opus because Fable credit ran out during the open-decision pass (map Notes, Model per ticket). It weighs the dossier (`research/decision-slider-vertical.md`, cited as "D n.n") and four panel arguments: the a11y lens (Opus), the api lens (Fable), the vsdefault lens (Opus, adversarial against the default), and the vsalt lens (Fable, adversarial against the alternatives). Every fact the ruling rests on was re-read at its source or re-run by the judge; those are marked "verified". Evidence capture: the key-mapping, engine-source, and feature-query files these marks cite are kept at [prototypes/slider-vertical-orientation/](../prototypes/slider-vertical-orientation/README.md); the full workspaces stayed under `D:/tmp/`.

### Decision

The vertical Slider stays as the spec has it for the whole Angular 22 Browser target: one native `<input type="range">` per Handle, rotated by `nfs-slider` rule 11 inside Foundation's flipped `.slider.vertical`, with `aria-orientation="vertical"` and native keys; no custom `role="slider"` Handle for any form, and no `writing-mode` path behind a feature query now. The `writing-mode` form is specified in advance as a Library-mixin and directive-internal change that lands, with no query and no second path, when vertical form controls enter the Browser target; no prototype is needed before the spec changes.

### Why

1. The harm the default carries is one engine's exposure of one property, and it changes no interaction.
   - Chromium's `AXSlider::Orientation()` returns vertical only for a vertical writing mode or a vertical `appearance` and never reads `aria-orientation` or a transform; the file is identical at tag `153.0.8010.55` and at `main` fetched 2026-09-27 (verified: `diff` of the vsdefault lens's two copies, `D:/tmp/nfs-panel-73-vsdefault/ax_slider-*.cc`, prints nothing; lines 46-78). Chromium therefore reports the rotated Handle as horizontal in CDP and UIA (D 2.4 table 1) and will keep doing so until the input's writing mode changes. WebKit's `AccessibilitySlider::explicitOrientation()` returns `orientationFromARIA()` first (verified, `D:/tmp/nfs-panel-73-a11y/AccessibilitySlider.cpp:60-63`), and Firefox carries the attribute as an object attribute and as `AXOrientation` on macOS (D 2.4, engine source).
   - Operation is identical in both orientations: the rotated rule 11 shape gives `Up=51 Down=49 Right=51 Left=49 Home=0 End=100` with the minimum at the bottom in Chromium 120, 141, and 153, Firefox 119, 142, and 155, and WebKit 17.4, 26.0, and 26.6 (verified, case `s-rot-fnd` in `D:/tmp/nfs-decision-slider-vertical/keys-pw140.txt`, `keys-pw156.txt`, `keys-pw163.txt`). A JAWS user in Chrome hears "left right slider" (D 2.8), and Left and Right move the rotated Handle the way the APG says; NVDA conveys no orientation for any slider, and VoiceOver on iOS, TalkBack, and UIA's RangeValue set a native range's value directly (D 2.8). What the user loses is layout information, not operability.
   - WCAG 2.2 AA does not require it. 4.1.2 asks that "the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set" (verified, `D:/tmp/nfs-decision-slider-vertical/data/wcag-guidelines_sc_20_name-role-value.html:8`); orientation is neither the name, the role, nor a value the user sets, and the word "orientation" occurs in none of 4.1.2, Understanding 4.1.2, or Understanding 1.3.1 (verified, `rg -c -i orientation` over the three dossier copies finds nothing). The author side conforms: the APG says a vertically oriented slider "has aria-orientation set to vertical" (APG `slider-pattern.html:82-83`), ARIA in HTML declares no conflict for it on `input type=range` (D 2.2), and ARIA-AT grades conveying orientation as a SHOULD (D 2.8). No panelist claims an AA failure: the a11y lens writes that the default "is not a clear 4.1.2 failure", the vsdefault lens that "the harm is mostly informational". So the user's accessibility preference (WCAG 2.2 AA and the matching APG pattern, map Notes) is met by the default and does not force a second code path.

2. The rule question the orchestrator put: a feature-query path whose fallback keeps today's behaviour is the forbidden kind. The two rules, verified:
   - Map, Browser support: "A platform feature counts as available only if it was Baseline widely available on that date; anything newer needs a fallback or is not used." and "A feature is usable without a fallback only if every browser in this table supports it from the listed version." (`map.md:44`, `:56`).
   - Building-blocks 1.2, Rules that follow: "No progressive enhancement onto a not-usable feature in the first specs: one code path per behaviour, because two paths double the test matrix and the not-usable features become usable only when the target moves with Angular. Each spec names the feature it would adopt then (for example anchor positioning for Dropdown) under Further Notes." (`building-blocks.md:36`), with "vertical form controls via `writing-mode`" in the Not usable column of the table above it (`:32`).

   Reading:
   - (a) Rotation where the query fails and `writing-mode` where it passes is progressive enhancement onto a Not-usable feature. Keeping the old behaviour where the feature is missing is what progressive enhancement means, so it cannot be an exempt kind, and the rule names none. Its reason applies in full: the a11y lens's own test plan needs a fixture stylesheet that forces the rotation, because every current CI engine passes the query and the fallback would otherwise go untested.
   - (b) The bundle has applied the rule to this exact shape twice. ADR 0002 rejected native `popover` plus anchor positioning "behind `@supports`" because "it would be a second code path" (verified, `adr/0002-in-place-measured-positioning-for-anchored-panes.md:12`). The Accordion spec kept Foundation's glyph in the title's accessible name rather than add CSS alternative text (`content: '+' / ''`; Chrome 77, Safari 17.4, Firefox 128), a CSS-only accessibility refinement whose fallback was the in-target behaviour, because "building-blocks 1.2 rules out a second path" (verified, `specs/accordion.md:301`, D18 at `:549`, the upgrade at `:673`). No spec puts an out-of-target feature behind a query (verified, `rg "@supports"` over `specs/` finds only the Accordion family's reasons for emitting none).
   - (c) The two rules agree. The map sets the outer bound ("needs a fallback or is not used"), and the building-blocks ticket's decision 12 chose the stricter branch for the first specs: "Not in the first specs; one code path each" (verified, `issues/14-building-blocks-map.md:71`). The Slider ticket's guard repeats the map's words "or behind a stated fallback" but defers to "as the building-blocks decision already ruled" (`issues/32-spec-slider.md:38`).
   - (d) The premise does not hold either. The Browser target is a floor, so Chrome 153, Firefox 155, and Safari 26 are in-target browsers, and the fallback keeps today's behaviour only for browsers that fail the query. Every Firefox that passes (119 and later under `sideways-lr`, 120 and later under the tighter query) takes the new path, gains no exposure (Firefox exposes only `aria-orientation`, in both paths: D 2.4 table 1, rows `wm-vlr` and `wm-vlr-rtl-aria`), and before hydration and in `hydrate never` its native Right decreases (verified, `keys-pw163.txt:13`, Firefox 155 `Right=49 Left=51`; `keys-pw140.txt:13`, Firefox 119 the same). WebKit's exposure does not change either. Only Chromium gains.

   So the a11y and vsdefault recommendations need building-blocks 1.2 amended, and the vsdefault lens proposes the amendment. It is not adopted: it is cross-cutting, it would reopen ADR 0002's and the Accordion D18's rejections for consistency, and item 1 shows the gain does not call for it.

3. On the merits the feature-query path costs more than it gains, even with the rule set aside.
   - It needs the directive to own Left and Right on vertical Handles, because no `writing-mode` configuration meets user story 10 natively across current engines (D 2.4 table 3; verified above). That takes over linear keys in every engine, which the spec declines for right-to-left ("that would mean taking over every linear key press on one engine's behalf", `specs/slider.md:305`; D9 at `:529`), rewrites the replay rule "A replayed `keydown` on a linear enabled handle does nothing" (`:420`), and extends to linear Handles the handler-writes-the-native-value mechanism that the spec lists as not yet run (`:427`); the vsdefault lens rates that part MEDIUM for the same reason.
   - A CSS feature query tests parsing, not the layout. Playwright's Windows WebKit 26.0 passes `@supports (writing-mode: sideways-lr)`, keeps `horizontal-tb`, and loses the rotation, leaving a slider that clicks do not move (verified, `D:/tmp/nfs-panel-73-api/probe-pw156.txt`: `b2.writingMode=horizontal-tb ... b2.clickTop=50 b2.clickBottom=50`). No target browser does this (Safari is a Cocoa port with the preference on, D 2.3), but it is how any proxy fails, and it constrains which WebKit build the e2e layer may run.
   - The gain is time-boxed. Vertical form controls are Baseline widely available on 2026-10-18 and in the 2027-05-07 set (D 2.3; re-run by the api and vsalt lenses); Angular 23 is "~ June 2027" with a Baseline date near its release (D 2.3); at that move the unconditional form arrives with no query. The default and the upgrade share one consumer contract (the api lens, step 1), so keeping the default costs no consumer change later.

4. Which query, if either: neither is adopted. If building-blocks 1.2 is ever relaxed, the vsdefault lens's `@supports (width: round(1px, 1px)) and (color: light-dark(red, red))` is the one that fits the map's availability rule. Its true set (Chrome and Edge 125, Firefox 120, Safari 17.5) lies inside BCD's full support for vertical range inputs (Chrome 124, Firefox 120, Safari 16.5) and for vertical form controls (Safari 17.4), while `@supports (writing-mode: sideways-lr)` (Chrome and Edge 132, Firefox 43, Safari 18.4) admits Firefox 119, which BCD records as partial and only engine source and a Playwright build clear (verified: `node D:/tmp/nfs-panel-73-vsdefault/bcd-query.mjs` over BCD 8.1.3; Firefox 119 `sideways-lr=true` in `D:/tmp/nfs-panel-73-api/probe-pw140.txt`). The tighter query's weaknesses go on record: it is a proxy of two unrelated functions whose meaning rests on release dates, and only Dart Sass 1.104.1 was checked not to fold `round(1px, 1px)` (the vsdefault lens's `round-check.mjs`); `sideways-lr` is simpler and ships in Fluent UI React v9 (D 2.7).

5. The other options fall on the dossier's facts, which no panelist contested. A custom `role="slider"` Handle (C) adds a second implementation path of 256 to 1,807 lines (`specs/slider.md:255`), changes consumer markup, brings back the APG touch caution, is inert before hydration and in `hydrate never`, and buys only the same Chromium announcement (D 3.C, D 2.8). Dropping the form (D) removes a documented Foundation feature (D 3.D). `appearance: slider-vertical` (E) replaces the Foundation thumb and is being removed (D 3.E). A hidden input with a positioned thumb (F) carries B's target problem and C's positioning code (D 3.F). `writing-mode` with no fallback (B1) breaks the map's rule (BCD Chrome 124 and Firefox 120 against a 119 target, D 2.3). A client-side switch (B3) changes the DOM after hydration (`specs/slider.md:24`).

How each panelist's strongest argument was weighed:

- a11y lens (Opus): JAWS with Chrome or Edge, 36.1 percent of primary screen-reader pairs in WebAIM survey 10 (verified: 24.7 and 11.4 percent in the lens's copy, `D:/tmp/nfs-panel-73-a11y/webaim10.md`), hears a vertical slider described as horizontal; a CSS path fixes Chromium 132 and later while engines that fail the query keep today's behaviour; measured in nine builds with the range form, a right-to-left page, and axe. Weighed: the exposure fact is right and is the residual this decision accepts; "never worse by construction" holds for engines that fail the query, not for the in-target Firefox that passes it (item 2, reading d); the argument does not address building-blocks 1.2 or its precedents; and the "left right" hint still leads to working keys on the rotated Handle (item 1). Its measurements go into the upgrade note (rule 3 on `inline-size`, the counter-flip on the input, the Left/Right handler), so the upgrade starts measured.
- vsdefault lens (Opus): Chromium's code is identical at `main`, so waiting does not fix the default and only CSS does; its tighter query stays inside BCD's support; it measured forced colours, drags, and axe on both paths. Weighed: agreed that only the writing mode fixes Chromium, which is what the scheduled upgrade does; its query is the right one if the rule changes (item 4); its proposed building-blocks rule is a cross-cutting change this ticket does not make (item 2); its own MEDIUM on the replay path is part of item 3.
- api lens (Fable): the default and the `writing-mode` form share one public contract, so the choice is rule compliance, cost, and timing; the one-code-path rule and the bundle-wide named-upgrade pattern; the impact re-rating. Adopted. Its point that the query path still leaves Chromium 119 to 131 horizontal is true but weighs little, since current Chromium would gain; the decision rests on items 1 to 3.
- vsalt lens (Fable): the rotated shape is the only one with identical keys, pointer, and thumb position in all nine builds; the harm is one engine, one property, one phrase; the query path needs a linear-key takeover that reopens the replay problem. Adopted. Two supporting points are weighed down. `css.properties.direction.vertical_slider_direction` being `baseline: false` does not count against sliders, since BCD's partial notes for Firefox and Safari read "Only supported for vertical range sliders" (D 2.3), and `vertical-lr; direction: rtl` puts the minimum at the bottom in every engine that applies it, Chromium 120 included (D 2.4 table 3; the Chromium 120 inversion it cites is for `direction: ltr`). The e2e verification gap it names is Playwright's Windows WebKit, not Safari.

### Dissent

Arguments the decision overrides, and what would reopen them:

- a11y and vsdefault lenses: ship `writing-mode: vertical-lr; direction: rtl` behind a feature query now, with the rotation as the fallback, `aria-orientation` kept, and the directive owning Left and Right. JAWS with Chrome or Edge is the largest desktop screen-reader group; Chromium will never read `aria-orientation` on a native range; the fix is CSS inside the library and changes no consumer markup; it is measured in nine builds with the range form, forced colours, right-to-left pages, drags, and axe; every engine that fails the query gets exactly today's behaviour; and waiting leaves the Angular 22 line, in long-term support until 2028-06, with the misreport for its whole life. Overridden by items 1 to 3. Reopens on either of:
  - the user relaxing building-blocks 1.2 to allow an enhancement whose fallback is the in-target technique; then the vsdefault lens's rule 11b with the `round()` and `light-dark()` query (item 4) plus the Left/Right handler becomes the vertical form with rule 11 as its fallback, and ADR 0002 and the Accordion's D18 are revisited under the same amendment;
  - a measured or published case of an assistive technology in a target browser that fails to change a native range's value because of its exposed orientation (for example a gesture or command that sends only Up and Down to a vertical slider and only Left and Right to a horizontal one, and one pair not reaching the Handle); orientation then becomes operational, 4.1.2 applies, and the user's accessibility preference outranks the one-code-path rule.
- a11y lens, on the query: `sideways-lr` as the proxy loses to the vsdefault lens's query if a query is ever used (item 4).
- If Chromium ever reads `aria-orientation` on a native range, the residual disappears; the e2e assertion below fails and the caveat text is dropped.

### Triage

- Impact: MEDIUM, re-rated from HIGH. The spec ticket rated it HIGH because moving the vertical form to a custom `role="slider"` Handle later would change the markup of every consumer and add a second implementation path (`issues/32-spec-slider.md:166`). This decision rejects that move; the one change left, the `writing-mode` upgrade, keeps consumer markup, inputs, host bindings, and the keyboard contract, and touches Library mixin rules 3, 5, 5a, and 11 and the directive's vertical key path at the target move, as every named upgrade in the bundle does. It re-touches shipped library code, so it is not LOW.
- Confidence: HIGH after the panel. The earlier NOT HIGH had three grounds (`issues/32-spec-slider.md:167`): a default carried from the prototype without deliberation (now deliberated over a dossier and four arguments); a reading of 4.1.2 that would require the orientation (4.1.2's text names name, role, and user-set values, and no panelist claims a failure, item 1); and unknown impact on assistive-technology users (now bounded from ARIA-AT, WebAIM, and the NVDA, Orca, TalkBack, and WebKit sources, D 2.8: JAWS, VoiceOver for macOS, and Orca convey orientation; NVDA, TalkBack, and VoiceOver on iOS do not; none operates a native range by it). The decision contradicts no research or ADR; it applies building-blocks 1.2 as ADR 0002 and the Accordion spec did.
- Residual risk the decision accepts: JAWS and Orca users of Chrome or Edge hear a vertical Slider described as horizontal for as long as the Angular 22 target holds; JAWS's actual speech for a rotated native range is not observed (expected "left right slider" from a 2020 report, D 2.8); Safari was not run on the rotated form (WebKit's reading of `aria-orientation` is source-verified and measured in Playwright's WebKit, D 2.4). Guards: (a) the e2e Chromium accessibility-tree case pins `orientation: horizontal` on the vertical stories, so a Chromium change or the upgrade cannot pass unnoticed; (b) `slider--vertical` and `slider--vertical-two-handles` assert `aria-orientation="vertical"` and all four arrow keys, the operational guarantee the decision rests on; (c) the upgrade is specified in advance with its measured shape and its remaining prototype questions; (d) README assistive-technology check 11 gains the one probe that would reopen the decision (Dissent, second reopening fact).
- Note (2026-09-27, audit 0006 M8): guard (d) now lives in the Slider spec's release test, not the README. The README's numbered checks were replaced by a summary when [Resolve the assistive-technology checks](77-evidence-assistive-technology-checks.md) resolved them, which removed check 11; the release test now runs the probe on `slider--vertical` and `slider--vertical-two-handles` with JAWS on Chrome and Edge, Orca on Chrome (added by audit 0007: the residual risk above names Orca users), and TalkBack on Chrome, and names this decision as the one to reopen ([Spec: Slider](32-spec-slider.md), amendment of this date).
