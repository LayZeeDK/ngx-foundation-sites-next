## Question

What does the [Spec: Breakpoint service (shared utility)](53-spec-breakpoint-service.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/breakpoint-service.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

## Answer

Model: Opus 5.5. Worked AFK as a self-grilling (both sides) against the sources below, with `/domain-modeling` for vocabulary and `/to-spec` for the revision. Spec: [specs/breakpoint-service.md](../specs/breakpoint-service.md), revised in place; the dated amendment is in the [Spec: Breakpoint service (shared utility)](53-spec-breakpoint-service.md). This re-run also carries every change the Answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) lists for this spec, and the requests of three tickets resolved while it ran: [Spec: Variant declaration tooling](136-spec-variant-declaration-tooling.md), [Spec: Close Button](83-spec-close-button.md), and [Re-run: Button spec under the class rule](128-rerun-button-class-rule.md), whose ADR 0040 dated note it re-measured.

Gist: the Breakpoint service has no class of its own and reads none, so the class rule changes its wording, not its behaviour: the Visibility and breakpoint classes it points consumers to are host bindings of their directives, set from Options or Variant inputs. The typing decision changes more. Variant inputs name Class breakpoints (`NfsClassBreakpoint`, closed, from the primary entry point), behaviour Options keep the open `NfsBreakpointName`, and `nfs-breakpoint-properties` also writes `--nfs-breakpoint-classes`. The drift check becomes `strictBreakpointSync`, one of three Runtime checks this entry point now hosts, configured by `provideNfsRuntimeChecks` (development overrides) and `provideNfsProductionRuntimeChecks` (production opt-in). Directives report through `nfsVariantCheck(directive)`, a handle with a presence request, `include()`, and a value report, `value()`. A production bundle that does not opt in carries none of the checker's code, measured under the real application builder.

Round 1 (no prerequisites): what classes the spec touches.

1. **Does the utility have a Structural, Variant, or State class?** No. It renders nothing; Foundation's MediaQuery utility used one class, `.foundation-mq`, on a `<meta>` it appended, which the spec already dropped (no computed style on the server). Its CSS is custom properties on `:root`, not classes. A "CSS class mapping" subsection now says so (BB 1.14 item 2). Source: the spec; FS `js/foundation.util.mediaQuery.js`; ADR 0039.
2. **Which consumer-written classes did the spec carry?** None in markup: its examples bind `mq.atLeast()` in `@if` and components. What remained were words that left classes to the consumer: the Solution's "stays in Foundation's CSS (`.show-for-*`, ...)", consumer rule 2's "expressed with Foundation's visibility and breakpoint classes", the consumer table's "first paint from Foundation's `.hide-for-<bp>` classes", user story 22, and the 1.4.4 e2e's `.show-for-medium`. Each now says the class is a host binding of the directive that owns it, set from its Option or Variant input, and in server HTML. Source: the spec; ADR 0039 Consequences; BB 1.7 "CSS first".
3. **Does "Initial state is bound, never read from a class" (BB 1.4) bear here?** Two ways. The service reads no class to learn a breakpoint or seed a state, and its checks read custom properties, which the rule does not concern; recorded in the class mapping. Consumer rule 2 adds that no directive learns its breakpoint from a static Visibility or breakpoint class on its host; a copied one is stripped where the directive binds it and reported by that directive's development check. Source: BB 1.4; the Accordion re-run's dev check 7.
4. **Do the exclusion rows for this spec change?** No. BP1 to BP8 (X `:84-91`) all sit under T's "Reasons that still hold" (section 3: BP3, BP6, BP7, BP8 not a Foundation feature; BP2 platform limits; BP1, BP4, BP5 dropped for design reasons), none rests on being CSS-only, and T names no dissent for this spec. RT7 (X `:224`, superseded) still points here and is now `strictBreakpointSync`. Source: X; T.
5. **Stories and fixtures?** Story ids unchanged. Demo components print into a plain `<table>`, which Foundation styles by tag and which has no Variant class and so no directive (ADR 0039, dated note), and `<output>`; no scaffolding class. The custom-map story's style block writes custom properties only. Source: storybook-conventions sections 3 and 8.

Round 2 (depends on 1-5): breakpoint names under ADR 0040.

6. **One breakpoint type or two?** Two, as ADR 0040 decides. `NfsBreakpointName` (open, the map's names) types behaviour Options and this API; `NfsClassBreakpoint` (closed over `$breakpoint-classes` through `NfsBreakpointClassesOverrides`, primary entry point) types Variant inputs and class-setting Options (`revealOn`, `inCanvasOn`). They differ by default (`xlarge`, `xxlarge` have no classes), so one type either lets `expanded="xlarge only"` compile with no class or rejects `stickyOn="xlarge"`. Source: ADR 0040 Consequences; FS `scss/util/_breakpoint.scss:48-50`, `scss/settings/_settings.scss:126`.
7. **How do the two relate?** Foundation requires every Class breakpoint to be a `$breakpoints` key ("Each value in this list must also be in the `$breakpoints` map", FS `_breakpoint.scss:48`; `breakpoint()` warns otherwise, `:95`), so `NfsClassBreakpoint` is assignable to `NfsBreakpointName` and a directive passes `revealOn()` to `atLeast()` directly; `strictBreakpointSync` reports a Class breakpoint the token lacks. `NfsBreakpointModifier` stays here; if the tooling ever declares the three words in the primary entry point, this entry point re-exports them. Source: FS; TOOL (its `NfsClassBreakpointQuery<M extends 'up' | 'only' | 'down'>`).
8. **How does a Variant directive find the Zero breakpoint?** `nfsBreakpointForWidth(inject(nfsBreakpointsToken).map, 0)`, the existing pure function, once at construction: the token's key whose value is 0, the same on server and client. Not `NfsMediaQuery`, whose construction registers a render callback and writes a `TransferState` entry into every server-rendered page (ADR 0014 Consequences). Not the literal `small` (a renamed map). No new export. Source: the spec's API; ADR 0014; the Button re-run's D20 and the Menu spec, which both read the token.
9. **A shared Breakpoint-query parser for Variant directives?** Weighed and not exported: each family maps its own words and Zero-breakpoint gaps to its own classes (Button `small down` to `.small-only-expanded`, Menu `up` only), and the grammar is two words. Recorded in Out of Scope. Source: the Button spec's class table; the Menu spec's `expanded` row.
10. **`--nfs-breakpoint-classes`?** Written by `nfs-breakpoint-properties` from `$breakpoint-classes`, joined with `space` (E1: `map-keys` and comma lists print with commas), whitespace only through `unquote('')` for an empty list (E1: `#{()}` is an error; TOOL's Variant property format); no flag gates it. It is the property of the `NfsBreakpointClassesOverrides` registry in TOOL's settings table and manifest. Source: ADR 0012 and ADR 0005 dated notes; TOOL.

Round 3 (depends on 6-10): the Runtime checks.

11. **API?** TYP's exactly: `NfsRuntimeChecks`, `NfsRuntimeCheckReport`, `provideNfsRuntimeChecks`, `provideNfsProductionRuntimeChecks`; all three on in development with no provider; none in production unless listed. Source: TYP "The runtime checks"; ADR 0040.
12. **Does the production provider act in development, and does `report` get development reports?** No to both: each function acts only in its own kind of build, and development reports always go to `console.warn`. For routing `report` in both builds: its integration becomes testable in TestBed. Against: a function named for production acting in development, and telemetry fed with development noise; the production path is testable on a production build, which the e2e now does. Decided: own build only. Source: NG `packages/core/src/change_detection/provide_check_no_changes_config.ts:41-56` (a provider that is empty outside its build); SYNC 8.2 to 8.4.
13. **Does a production bundle without the opt-in keep the checker?** No, measured (E2) under the real application builder with an ng-packagr FESM library and an `InjectionToken` with `makeEnvironmentProviders`, which SYNC 8.3 had measured only with a module variable and esbuild directly: absent without the production call, absent with only `provideNfsRuntimeChecks`, present with the production call (+3,976 B minified, about 1.2 kB transferred). The spec keeps the measurement as a regression test on production builds of the fixture app. Source: E2; SYNC unknown 8; the Angular CLI defines `ngDevMode` as `false` only with script optimization (SYNC 8.3).
14. **When and where do the checks run?** Only in render callbacks (`afterRenderEffect`, `afterNextRender`), which return a no-op on the server (NG `packages/core/src/render3/reactivity/after_render_effect.ts:419`, `packages/core/src/render3/after_render/hooks.ts:401`), so never on the server and never before hydration; they write no DOM and add no listener. A throwing `report` goes to `ErrorHandler` (NG `packages/core/src/render3/after_render/manager.ts:93-95`). Source: NG; BB 1.11 decision 3.
15. **Once per realm, for all three?** Yes: property reads and reports cached per realm, as TYP says and as the drift check already did, so a consumer test file without the Sass reports once per mixin; test files that need a first read of their own sit in their own file (Vitest's `isolate` defaults to `true`). Limit: a stylesheet added or hot-replaced after a first read is seen after the next page load. Source: TYP "Where and when they run"; the spec's decision 38 in its ticket; Vitest 4.1.11 config types.
16. **How does a directive report? Registration or a handle?** A handle: `nfsVariantCheck(directive)` returns `NfsVariantCheck | null` at construction, and the directive calls `include(mixin, settings)` and `value(input, value, needs)` from its own render callback, which it creates only when the handle exists. For a registration call that owns the callback: less directive code. Against: directives that already hold one development-only render callback would get a second (the Button's "one `afterRenderEffect` read phase exists only when a checker exists, and holds the development warnings too"); a handle lets them share it. Decided: the handle. Source: the Button re-run's decisions 16 and D19; the Menu spec ("through whatever reporting call that spec defines").
17. **A presence request with no bound value?** Yes, the Close Button's request: `include()` needs no value and runs at every run of the callback, so `strictVariantProperties` reports a missing include even where every Variant input is unset. Source: [Spec: Close Button](83-spec-close-button.md), decision 10 and its routed text.
18. **Missing include or empty list, when a property reads empty?** An empty and a missing property both read `""` (E1; ADR 0040, dated note). So `include()` lists only properties its mixin never leaves empty on Foundation's defaults (the Button's `button-palette` and `button-sizes`, never the gated `button-responsive-expanded`), and reports when all of them read empty; any other empty property is an empty list, so a flag-gated responsive value reports under `strictVariantNames`. A need whose property an `include()` found missing is skipped, so one missing include is one report. Rejected: a sentinel for the empty list (TOOL decision 7: `none` can be a name; whitespace only is the format). Source: E1; the Button re-run's D19; TOOL.
19. **What does a report carry?** TYP's fields; for `strictVariantNames` the directive, input, value, setting, and listed names; for `strictVariantProperties` the directive, the first setting, and all listed settings in `names`, with the include in the message; for `strictBreakpointSync` `setting: 'breakpoints'` and the names that disagree. Every message starts "ngx-foundation-sites [<check>]:", so the consumer knows which flag controls it. Source: TYP; user story 49.
20. **The property format?** TOOL's Variant property format: whitespace or commas between names, a bare count, whitespace only as the empty list. The checker trims, splits, and reads a count as one whole number. Source: TOOL "API: the Variant property format".

Round 4 (depends on 11-20): the drift check and what stays outside.

21. **What does `strictBreakpointSync` add with the class list?** It reads `--nfs-breakpoint-classes` and `--nfs-breakpoint-<name>` for each Class breakpoint the map lacks, and reports those in the same single report as value drift; the limit narrows to a Sass-only breakpoint that is not a Class breakpoint. A missing class list beside present map properties adds nothing here; directives that read the list report it through `include()`. It still runs in the service's go-live callback only, so an application that never constructs the service runs no sync; the docs say to rename a Zero breakpoint in Sass and token together. Rejected: also running it from the first Variant check (it would report a missing `nfs-breakpoint-properties` include to applications that use no breakpoint behaviour, and twice). Source: TYP "Changes to apply", item 3; the spec's Rendered output.
22. **The service's own development warnings (unknown names, rule tokens, invalid map)?** Outside the Runtime checks, unchanged: they report misuse of this API and read no CSS; the check set is ADR 0040's. Source: the spec's design decisions 14 and 21; decision 16 of the [Spec: Breakpoint service (shared utility)](53-spec-breakpoint-service.md) log.
23. **Out of Scope?** The names-list follow-up is decided (`--nfs-breakpoint-classes`); `@property` stays a follow-up; a list of every `$breakpoints` key stays out; new items: the tooling's scope, server-side checks, a declared-names check (ADR 0040's dissent), a development `report` callback, and the query-parsing helper. Source: TYP item 4.
24. **Tests?** Runtime-check cases at layer 2, one file per realm-sensitive case, with a probe directive using the handle; the SSR smoke gains a probe directive and a `getComputedStyle` spy; the Sass compile tests gain `--nfs-breakpoint-classes`; layer 4 gains the production-bundle measurement on two production builds of the fixture app and serves the opt-in build to test `report`. Source: BB 1.12; TYP item 3, third bullet.
25. **Glossary or ADR?** No new term: Class breakpoint, Runtime check, Variant properties, Breakpoint properties, and Zero breakpoint carry the revision. No new ADR: the typing and check decisions are ADR 0040's and ADR 0005's; the handle shape and the development `report` rule are reversible inside the library without touching consumer code, so they fail the hard-to-reverse condition.
