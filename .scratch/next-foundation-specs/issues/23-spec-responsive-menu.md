## Question

## WCAG 2.2 AA guard (user decision, 2026-09-26)

Every directive and component complies with WCAG 2.2 AA; see the map's Accessibility preference and [ADR 0022](../adr/0022-wcag-2-2-aa-enforcement.md). The spec carries a criteria subsection under Implementation Decisions naming the 2.2 AA criteria this plugin touches (at least 1.4.3, 1.4.11, 2.4.7, 2.4.11, 2.5.8, 4.1.2, and, for overlays and hover content, 1.4.13) and how each is met, as requirements, never recommendations. Where a Foundation default fails a criterion, the spec states the Sass settings the consumer must set or the smallest custom rule the `nfs-<plugin>` mixin adds, with the reason. The story axe gate runs with the WCAG 2.2 AA tags, and the decision log records each criterion addressed.

## Answer

Spec: [specs/responsive-menu.md](../specs/responsive-menu.md). Resolved 2026-09-26 by self-grilling (AFK), both sides played against the sources below, under the user's WCAG 2.2 AA rule, the Foundation Sass reuse rule, and the triage rule for human-only items.

Gist: one attribute directive, `ul[nfsResponsiveMenu]` (`NfsResponsiveMenu`, `exportAs: 'nfsResponsiveMenu'`, entry point `ngx-foundation-sites/responsive-menu`), whose required `rules` input is the directive attribute's value (Foundation's rule string or the typed object form), parsed by the shared `parseNfsBreakpointRules` against `dropdown`, `drilldown`, and `accordion` and resolved by Breakpoint map order; below the smallest rule breakpoint the smallest rule's mode applies with a development warning, and an empty rule set gives `accordion`. It provides the Nested menu root (`nfsMenuRootProviders`) and hosts `NfsAccordionMenu`, `NfsDrilldown`, and `NfsDropdownMenu` through `hostDirectives`, exposing all thirteen of their inputs under Foundation's names (`closeOnClick` reaches Drilldown and Dropdown Menu at once, each with its own default) and their `opened`/`closed` outputs, of which only the live mode's fire. Its own surface is a read-only `mode` signal (the displayed Menu mode) and `collapseAll()`; mode-specific members (`openPath()`, `expandAll()`) are reached through the hosted roots' `exportAs` on the same element. There are no roles to swap (disclosure navigation in every mode); a Mode swap changes classes and keys on the same nodes. The swap is committed in one Nested menu root render callback that reads focus while the old classes still apply and sets the displayed mode together with the pruning of the Open path (a proposed amendment to the Nested menu spec, with a proposed ADR), and entering dropdown with focus outside the menu closes every submenu; focus stays on the same control, and moves only off a drilldown back item the new mode hides. Every instance starts from the Server breakpoint's mode and follows the viewport from its first render callback, so server HTML and deferred blocks hydrate as sent and a pre-hydration click replays onto a node the swap kept. No library CSS; each mode's Library mixin styles its mode. One prototype is graduated to verify the swap commit and the first-render strategy in three engines; the only item left open is the screen-reader pass, human-only by kind.

Round 1: Foundation contract and what is already settled.

1. **Which options, events, and methods?** From Foundation's source, not the ticket's wording (audit guards H6, M12): `ResponsiveMenu.defaults = {}` (no Options), the rule string read from `data-responsive-menu` at setup, `MenuPlugins` with exactly `dropdown` (`.dropdown`), `drilldown` (`.drilldown`), and `accordion` (`.accordion-menu`), no event of its own (the base `init`/`destroyed` plus the live child's events and its `init`/`destroyed` at every swap), `destroy()` as the only public method, and a `data-mutate` attribute for Triggers' re-measure protocol. Source: FS `foundation.responsiveMenu.js` L11-24, L45-50, L63-90, L113-151; R:menus 4.2 to 4.5.
2. **The ticket's `-tabs` aliases?** None exist. `MenuPlugins` has three keys and no alias table; `tabs` is a mode of Responsive Accordion Tabs (its own `MenuPlugins`), and `accordion-menu` is the class of the `accordion` mode, not a mode name. Nothing is invented: a `tabs` or `accordion-menu` token is an unknown mode (or breakpoint), skipped with the shared parser's development warning, where Foundation stored `undefined` and threw later. Source: FS `foundation.responsiveMenu.js` L11-24, L73-79, `foundation.responsiveAccordionTabs.js` L11-16; BPS rule grammar.
3. **What do BB, the ADRs, NM, and P50 already settle?** BB Table A and B rows (a directive; the three roots as host directives with one live; the swap rule in `afterRenderEffect`; focus continuity); ADR 0004 (disclosure navigation in every mode, no directive swap); NM (the token, `nfsMenuRootProviders`, one `configure()` slot per mode, `drive()`, the swap rule, the consumer table, "always yield a mode" with the smallest-rule default); P50 rows 5 and 13 to 18 (three roots coexist, F1 to F4, server HTML, the first-paint layout cost); the root specs' asks (DD decisions 16 to 18 and 25 and its proposed change 4: expose `autoHeight`, `animateHeight`, `closeOnClick`, `scrollTop`, `scrollTopElement`, `scrollTopOffset`, `opened`, `closed`; DM decision 13 and DD decision 18: `closeOnClick` shared, each root with its own default). Reopened with reasons: when the swap is committed (decision 15) and which breakpoint an instance starts from (decision 21).

Round 2: shape, DI, and API.

4. **Directive or component?** One attribute directive on the consumer's `ul`: every mode is a set of directives on that same element, and Foundation's markup carries every element. Source: ADR 0001; BB 1.1 and Table A.
5. **How does one element carry three modes?** Through `hostDirectives`, which Angular applies statically at compile time ("You cannot dynamically add directives at runtime"); the hosting class's providers win on a shared token, so all three roots read one `NfsMenuRoot`, and the root's `mode` decides which root binds its class and handles keys. Rejected: creating directives per mode at runtime (no mechanism on an existing element), an `@switch` over three copies of the `ul` (re-renders consumer markup, drops focus, rebuilds at hydration), and one merged root host directive through 22.1 de-duplication (NM's alternative, unproven). Source: NG composition guide, "Adding directives to a component", "Dependency injection", "Host directive de-duplication"; NM decisions 6 and 7; P50 row 5; R:di 4.
6. **Names, selector, entry point, story ids?** `NfsResponsiveMenu` (the Plugin name, since ResponsiveMenu has no Structural class), selector `ul[nfsResponsiveMenu]`, `exportAs: 'nfsResponsiveMenu'`, entry point `ngx-foundation-sites/responsive-menu`, story ids `responsive-menu--<story>`. Source: BB 1.3; SC section 3; NM consumer table; DD decision 7 (the menu family's folders).
7. **The rules input?** `input.required<string | NfsBreakpointRules<NfsMenuMode>>({alias: 'nfsResponsiveMenu'})`, so Foundation's `data-responsive-menu="drilldown medium-dropdown"` becomes `nfsResponsiveMenu="drilldown medium-dropdown"`; parsed with `parseNfsBreakpointRules(rules, ['dropdown', 'drilldown', 'accordion'], mq.breakpoints)`; resolved by Breakpoint map order, a bare mode from the Zero breakpoint, tokens split at the last hyphen, the object form validated the same way; a runtime change swaps through the same callback as a resize. Source: BB 1.7 option syntax; BPS API, rule grammar, and deltas; NM usage sketch.
8. **What applies below the smallest rule breakpoint, and with no valid rule?** The smallest rule's mode, with a development warning (NM's default, kept); with no valid rule at all, `accordion` (the provider's mode), with a warning. Responsive Accordion Tabs renders `accordion` for its no-match case, but for menus the smallest rule's mode is better: its Library mixin is one the consumer included, while accordion mode's closed sections are hidden only by `nfs-accordion-menu`, which a consumer whose rules do not name accordion never includes (AM Sass item 5: without it every section shows while `inert`). Source: NM decision 44 and Triage 6; RAT D15; AM Sass subsection.
9. **The Zero-breakpoint mode and reflow?** BPS requires that the mode at the Zero breakpoint fit 320 CSS px, because zoom makes the service report the Zero breakpoint; drilldown and accordion always fit, dropdown only on a vertical root (DM's 1.4.10 row, with `$dropdownmenu-min-width: min(200px, 45vw)`). Enforced by e2e at 320 px and a development warning when the Zero-breakpoint mode is `dropdown` and the root's static class has no `vertical` (nor `<zero>-vertical`). Source: BPS WCAG 1.4.10 row; DM WCAG 1.4.10 row.
10. **Which inputs and outputs does the directive expose?** Every input of the three roots, thirteen in all (`multiOpen`; `autoHeight`, `animateHeight`, `closeOnClick`, `scrollTop`, `scrollTopElement`, `scrollTopOffset`; `alignment`, `disableHover`, `hoverDelay`, `closingTime`, `autoclose`, `closeOnClickInside`), because Foundation's child plugins read every `data-*` attribute of the same `ul`; NM's sketch listed three of Dropdown Menu's seven, which the proposed change corrects. `closeOnClick` is exposed by two host directives under one name, so one binding sets both and each keeps its own default when unbound. `opened`/`closed` are exposed from all three; only the live mode's completion function runs, so a consumer's handler fires once. Source: FS `foundation.responsiveMenu.js` L138; R:menus 0.3; NG composition guide, "Including inputs and outputs"; DD proposed change 4; DM decision 13; NM decision 8.
11. **Defaults tokens?** Each hosted root reads its own token, so per-mode application-wide defaults apply; the directive has no Options and no token (`ResponsiveMenu.defaults = {}`); a different `closeOnClick` per mode is set through the two roots' tokens with the input left unbound. Source: BB 1.4 last bullet and 1.9; FS L151.
12. **Members of the directive?** A read-only `mode` (the displayed Menu mode) and `collapseAll()` (mode-agnostic, delegating to the root). `openPath()`, `currentLevel`, and `expandAll()` stay on their roots and are reached through `#d="nfsDrilldown"` and `#a="nfsAccordionMenu"` on the responsive `ul`: Angular registers a host directive's `exportAs` in the element's export map. Source: NG acceptance test "should be able to reference exported host directives" and `saveNameToExportMap`; AM, DM D15 (one owner per symbol); BB 1.3 (Aria's `expandAll`/`collapseAll`).
13. **Tokens, Openable, and a second root on the same element?** No plugin token (nothing injects the responsive root); not an Openable (a bare `nfsClose` in the menu inside an off-canvas must close the panel). A root attribute written next to `nfsResponsiveMenu` is unsupported: Angular keeps that directive's selector match and drops its host directive match, and its own `nfsMenuRootProviders` then competes with this directive's provider; a development warning names it. Source: NM D22; AM D14; NG composition guide, "Template match takes precedence".

Round 3: the Mode swap.

14. **What state survives a swap?** Kept: each item's `expanded` (pruned by the swap rule), each root's inputs and `configure()` slot, focus on the same node, `data-nfs-shown` on settled open submenus, ids. Recomputed or reset: dropdown collision side classes (recomputed on open), hover-intent timers and Light dismiss entries (off while dropdown is not live), the Drilldown wrapper's heights (its observer disconnects outside drilldown and re-measures on re-entry). Drilldown's `scrollTop` must not read a swap into drilldown with a level open as a level change, or a resize would scroll the page (proposed DD change). Source: NM API tables and render hooks; DD wrapper section and `scrollTop` row; P50 rows 5 and 13 to 16.
15. **Where is the swap committed?** In the Nested menu root's own render callback, with the displayed mode kept separate from the driven one (proposed NM amendment and ADR): `earlyRead` compares the driven mode with the displayed one and reads `document.activeElement` and DOM order while the old classes still apply; `write` sets the displayed mode and applies the pruning together. Why: under NM as written, the mode follows the breakpoint in change detection, so the page renders the new mode before the swap rule's `earlyRead` reads focus, and in P50's F3 case that pass puts the focused toggle inside an `invisible` level (without pruning, focus fell to `body` in three engines); when an engine moves focus off a hidden control is not something to depend on; BB 1.5 names the render callback that commits the swap as a place to record focus; I67 asks the ResponsiveMenu spec to take one of its two patterns; RAT's displayed-mode split is the same shape, measured in three engines. `drive()`'s signature is unchanged. Source: NM swap rule and render hooks table; P50 row 15 and "Failures"; BB 1.5; I67 "The rule other specs inherit" and "Named specs"; RAT behaviour rules; P51.
16. **The swap rule's plan?** Entering accordion changes nothing. Entering drilldown or dropdown with focus inside the root keeps the submenus whose items contain the focused control and closes the rest; entering drilldown also closes the focused toggle's own submenu. With focus outside: entering drilldown keeps the first open submenu per level (NM's rule, which shows a pre-opened current section), entering dropdown closes every submenu (refinement). Why the refinement: Foundation's DropdownMenu never opened a submenu from a static `is-active` (its `_show` is the only opener), the APG disclosure navigation example starts collapsed, and an overlay nobody is using must not cover the page (1.4.13, 2.4.11); without it a desktop page whose markup marks the current section for the phone layout would load with a dropdown submenu open. Source: NM decision 31; FS `foundation.dropdownMenu.js` L302-328 and no `is-active` read at init; R:apg DropdownMenu; ADR 0024.
17. **Focus across a swap?** Never moved when outside the menu; kept on the same node otherwise, because the path holding it stays open; the one move is off a drilldown back item, which becomes `hidden` outside drilldown: an `afterNextRender` registered by the swap's `write` focuses the level's first control that is not inside the back item (where a drilldown puts focus when the level opens), after the render that applied the swap. The first-render swap follows the same rules. Source: NM drilldown key table and back-button definition; DD `NfsDrilldownBack`; BPS consumer rule 1; BB 1.5 (rendered state).
18. **Outputs at a swap?** None of its own. A submenu the swap closes emits its item's `expandedChange(false)`, so two-way bindings agree with the page, and the new live mode's `closed` once its close completes. RAT emits no selection output for a swap because its selection does not change; here a close is a real change of a two-way model. Source: BB 1.4 (model change outputs; Completion outputs); NM completion; RAT D16.
19. **A swap during an animation?** The interrupted phase completes through NM's fallback timer (measured duration plus 100 ms), or at once when the new mode has no transition, so outputs still fire once. Source: NM Animation.
20. **Does a swap animate?** Nothing slides except one case: entering drilldown with a level open moves that level to Foundation's `.is-drilldown-submenu.is-active` transform with `$drilldown-transition` in effect, a 150 ms slide (1 ms under reduced motion, none with `nfsAnimationsToken` disabled). Accepted: suppressing it needs a library attribute and a rule for a cosmetic case. Entering accordion takes `grid-template-rows` from `none` to `auto 1fr`, which does not interpolate. Source: FS `_drilldown.scss` (`.is-drilldown-submenu` transition and `.is-active` transform; R:menus 2.8); ADR 0003; NM Animation.

Round 4: first render and rendering modes.

21. **First render: the service's handoff or the Server breakpoint's mode per instance?** Per instance: the requested mode resolves at `mq.serverBreakpoint` until the directive's first render callback (a flag set in `afterNextRender`), then at the live breakpoint; the root's swap callback commits the change. For full hydration this equals the service's handoff; it differs for instances first rendered after the service went live (deferred blocks, routed layouts created after navigation, `@if`), which then hydrate as sent or, when client-created, swap in the same tick without painting. Why: every change of mode, the first included, then passes the swap rule, so a pre-opened section never opens a dropdown overlay on a desktop page and the F3 focus case is handled in deferred blocks too. ADR 0014 rejected a general per-directive gating helper in the service, and ADR 0032 kept the service's handoff for consumers that "change classes on the same nodes, so their focus survives a first-render change"; nothing is added to the service here (it already exposes `serverBreakpoint` and `resolve(rules, breakpoint?)`), and P50's F3 measurement shows a class swap can hide the focused node. Recorded in the proposed ADR. Source: ADR 0014 considered options and consequences; ADR 0032; P50 row 15; P51 cases 4, 15, 19 to 21; BPS API table.
22. **Server output and the handoff tick?** The server renders the Server breakpoint's mode with every class, ARIA attribute, `inert`, and the Drilldown pieces in their state; on the client the service goes live in its first `earlyRead`, the flag flips, and the root's swap callback, dirtied after its own `earlyRead` already ran in that batch, runs again in the same tick and commits before paint. A server-rendered page shows the Server breakpoint's layout until hydration (P50 row 18), which the client-hint recipe removes for Chromium visitors. Source: BPS "Going live"; ADR 0014; P60 verdict; I67 source reading (a phase node dirtied after its phase ran notifies the scheduler; `ApplicationRef.synchronize()` re-runs); P50 rows 17 and 18.
23. **Event replay?** Toggle and back item `click` and the root's `keydown` replay; Angular replays after `appRef.whenStable()`, which is after the first-render swap, and the swap keeps every node, so a pre-hydration click is applied once in the live mode (unlike RAT, whose swap removes the clicked control) and a pre-hydration key is handled by the live mode's table, logging the one accepted error. Hover and document listeners never replay. Source: R:rendering 4, "Mechanism" step 3, and 3, "What a directive inside a hydrate block may assume"; BB Part 4, Decided item 3; RAT rendering modes.
24. **Hydration boundary, `@defer`, hydrate triggers, `hydrate never`?** One boundary for the `nav`, the wrapper, the root, and every item, submenu, and back item. Deferred blocks hydrate as sent and then swap; `hydrate on interaction` replays onto a surviving toggle; `hydrate on hover` in dropdown mode only hydrates on the first hover (DM); `hydrate never` keeps the Server breakpoint's mode, so reachable sections need Hybrid items (DD). Source: R:rendering 3 and 7 rules 7 and 11; DM and DD rendering modes.
25. **Render hooks and `injectAsync`?** As the spec's table: `computed` for the parsed rules and the requested mode; the constructor for `drive()`; `afterNextRender` (`write`) for the first-render flag; the root's `afterRenderEffect` (`earlyRead`, `write`) for the swap; an `afterNextRender` from the swap's `write` for the back-item refocus; a development-only `afterNextRender`; no `effect`, no `afterEveryRender`. `injectAsync` does not apply: host directives are compiled into the directive, so no mode's code can load later, and the live mode is needed in the first render callback. Source: BB 1.5 and 1.9 (lazy services); NG composition guide; RAT D19; the Anchored pane spec (eager helpers).

Round 5: CSS and the platform.

26. **Does the CSS-only Menu markup plus container queries cover part of the job?** Foundation's CSS already covers the orientation part with viewport media queries (`.vertical.medium-horizontal`, `.<bp>-vertical`), which the library keeps as consumer classes. Container size queries are Baseline widely available (2025-08-14; Chromium 105, Gecko 110, WebKit 16) and so in the Browser target, but they change styles only: the key table, hover opening, Light dismiss, and the focus handoff need script; and Foundation documents the rules as viewport breakpoints, so container queries are not the switch. Source: R:platform 11 and the plugin table's ResponsiveMenu row; ADR 0005 considered options; BB 1.7 "CSS first"; FS docs "The Menu has some responsive CSS classes built in".
27. **Sass?** No library CSS and no `nfs-responsive-menu` mixin; each mode's mixin is keyed on its root class, so only the live mode's rules match; the consumer includes the mixin of every mode the rules name. Dropdown mode brings DM's two required settings, already in the library's Storybook overrides. Source: ADR 0012; NM Sass and D20; DM required settings; SC section 5.

Round 6: ARIA and WCAG 2.2 AA.

28. **ARIA pattern and keys?** Disclosure Navigation in every mode, the role set constant (R:apg ResponsiveMenu: "the role set is identical in every mode ... which removes most of the swap"); keys are the live mode's NM table, forwarded by the live root; Tab, Enter, and Space behave the same in every mode. A swap is not announced (BPS consumer rule 4). Source: ADR 0004; R:apg ResponsiveMenu; NM keyboard tables.
29. **Which WCAG 2.2 AA criteria, and how each is met?** 1.3.1 (constant role set, recomputed bindings), 1.3.4 (same content in every mode), 1.4.3 (passes except dropdown in the default Top Bar: `$topbar-background` setting, DM's warning), 1.4.4 (em queries), 1.4.10 (the Zero-breakpoint mode fits 320 px; dropdown's `$dropdownmenu-min-width` setting; development check), 1.4.11 (each mode mixin's unrounded compile check), 1.4.12 (each mode's rule, across a swap), 1.4.13 (dropdown hover rules; no overlay without the user after a swap), 2.1.1, 2.1.2, 2.4.3 (DOM order constant; a swap never drops focus to `body`), 2.4.6 (toggle and back names), 2.4.7 (each mode's ring, drilldown's inset ring), 2.4.11 (dropdown submenus close on focus leaving; a swap keeps only the focused submenu), 2.5.3, 2.5.8 (38 px rows, 40 px toggles, mixin checks), 3.2.1, 4.1.2 (a closed submenu reports `aria-expanded="false"` in the same pass). Each is a requirement with its check in the spec's table; no Foundation default fails in accordion or drilldown mode. Source: ADR 0022; BB 1.10; BPS WCAG table; AM, DM, DD WCAG tables.

3. **Entering dropdown with focus outside closes every submenu** (decision 16). Impact: medium (one branch of a shared rule). Confidence: HIGH (Foundation's DropdownMenu never opened from `is-active`; APG; 1.4.13 and 2.4.11). Decided.

## Prototype needed

**Prototype: ResponsiveMenu swap committed in the Nested menu root's render callback.** Question: with the real Breakpoint service and a Nested menu root amended as proposed (displayed mode separate from the driven one; `earlyRead` reads the driven mode, `document.activeElement`, and DOM order; `write` sets the displayed mode and prunes), hosting the three roots under `nfsResponsiveMenu="drilldown medium-dropdown large-accordion"`, in Chromium, Firefox, and WebKit, zoneless, on CSR, SSR, and prerendered routes:

1. Does every Mode swap (a resize across each threshold in both directions, a `rules` change, and the first-render handoff) render the new mode and the pruned Open path in the same change-detection pass, with no pass that shows the new root class over a submenu the swap closes (a `MutationObserver` record per pass)? Does focus stay on the same control in P50's F1 to F4, land on the level's first control when a back button held it and the swap leaves drilldown, and stay on a toggle focused before hydration at a 1280 px viewport while the main bundle is held back?
2. Does the root's swap callback, run first in the batch and dirtied again by the service going live and the directive's first-render flag, commit in the same tick, so a client-rendered route paints no frame of the Server breakpoint's mode (per-frame recorder), and does a menu inside `@defer (hydrate on viewport)` hydrate as sent (`componentsSkippedHydration === 0`, the Server breakpoint's classes in the hydration frame) before it swaps?
