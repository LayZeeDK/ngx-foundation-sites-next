## Question

This is a shared-utility spec graduated by the building-blocks decision: plugin specs depend on it, so its API must be settled before they are written. The result must be the best combination of the map's design criteria, applied to a utility: Foundation's own utility behaviour, the platform within the browser target, Angular CDK where it already solves the problem, Material-equivalent API shape, and the modern DI patterns in `research/di-and-composition-patterns.md`.

## Answer

Spec: [specs/nested-menu.md](../specs/nested-menu.md). Resolved 2026-09-26 by self-grilling (AFK), both sides played against the sources below, under the user's WCAG 2.2 AA rule, the Foundation Sass reuse rule, and the triage rule for human-only items.

Gist: one secondary entry point, `ngx-foundation-sites/nested-menu`. `li[nfsMenuItem]` (on every item, with an `expanded` model, `opened`/`closed` Completion outputs, `open()`/`close()`/`toggle()`), `ul[nfsSubmenu]` (id, `inert` while closed, slide phases), and `button[nfsSubmenuToggle]` (`aria-expanded`, `aria-controls`, a `hybrid` input for the link-plus-button form) read the Menu mode from `nfsMenuModeToken`, whose value is an `NfsMenuRoot` created by `nfsMenuRootProviders(mode)` in each plugin root's injector, and emit Foundation's whole Nest vocabulary and every mode's State classes as `computed` host class maps holding only the keys the utility owns in that mode. The root handle carries `mode`, `items`, `hasOpenItem`, per-mode behaviour slots set through `configure()`, `drive()` for ResponsiveMenu, the per-mode key tables behind `handleKeydown(event, mode)`, `handleClick` for dropdown leaf clicks, `expandAll()`/`collapseAll()`, and the swap rule. Roles are disclosure navigation in every mode; closed submenus are `inert`; hidden drilldown levels use Foundation's `invisible`. Dropdown mode uses the Anchored pane utility's Light dismiss (focus-out per submenu, Escape, outside press), hover intent, and horizontal `nfsOverlap` for `opens-*`. The accordion grid on the parent `li` keys on a library attribute, `data-nfs-expanded`, and releases its clip on `data-nfs-shown`. The plugin mixins `nfs-accordion-menu`, `nfs-drilldown`, and `nfs-dropdown-menu` hold every custom rule; there is no utility mixin.

### Decision log

Sources: FS = the Foundation 6.9.0 clone; NG = the Angular 22.2.x clone (`adev/src/content/guide/directives/directive-composition-api.md`, `guide/templates/binding.md`, `guide/components/host-elements.md`); NGC = the components 22.2.x clone (`src/aria/private/utils/collection.ts`); APG = the aria-practices clone (`content/patterns/disclosure/examples/disclosure-navigation-hybrid.html`, `js/disclosureMenu.js`); P50 = the [Prototype: Nested menu directive family with breakpoint mode switching](50-prototype-nested-menu.md) answer, the orchestrator's note at its end, and `prototypes/nested-menu/`; P43 = the [Prototype: `@angular/aria` Accordion and Tabs under Foundation markup](43-prototype-aria-accordion-tabs.md); BPS = [Spec: Breakpoint service (shared utility)](53-spec-breakpoint-service.md); AP = [Spec: Anchored pane (shared utility)](55-spec-anchored-pane.md); TRG = [Spec: Triggers (shared utility)](54-spec-triggers.md); ACC = `specs/accordion.md`; STK = `specs/sticky.md`; BB = `building-blocks.md`; R:x = research files by BB's short names; WCAG = the 2.2 AA criteria the user's rule names.

Round 1: what Foundation does and what is already settled.

1. **What does Nest add, and what do the three plugins share?** Nest's `Feather` adds roles (`menubar`, `menuitem`, `none`), `is-<type>-submenu-parent`, `submenu is-<type>-submenu` plus `data-submenu`, `is-submenu-item is-<type>-submenu-item`, `aria-haspopup` and copied `aria-label` on non-accordion parent links, and drilldown's `aria-expanded` on the `li` and `aria-hidden` on submenus; `Burn` removes the classes and leaves the roles. The three plugins share the markup, the open/close state, keyboard maps, and a slide or display mechanism. Source: FS `js/foundation.util.nest.js:4-63`; R:menus 0.2, 1 to 3.
2. **What do BB, the ADRs, and P50 already settle?** ADR 0004: disclosure navigation, one family, classes from a mode signal. P50: the three directives, the token, three roots as host directives with ResponsiveMenu's provider winning, `.submenu-toggle` in every mode, `invisible` not `inert` on hidden ancestor levels, `focus({preventScroll: true})`, `.is-drilldown { overflow: clip }`, per-item focus-out close, pruning on swap, focus moves in `afterNextRender`, and six custom rules. ADR 0024: Light dismiss holds "open Anchored panes and submenus". BPS: `parseNfsBreakpointRules` and `resolve()`, the first-render handoff. AP: the pure collision functions and the DropdownMenu mapping row. Reopened with reasons: the prototype's root `focusout` (decision 25), its `effect` swap (decision 31), its viewport collision bound (decision 27), and the `is-expanded` class (decision 34).

Round 2: shape and DI.

3. **Directives or a component?** Three attribute directives on the consumer's `li`, `ul`, and `button`, no component: Foundation's markup already has every element, and the toggle and back button are consumer-written single elements. Source: ADR 0001; BB 1.1 case 3.
4. **What does `nfsMenuModeToken` carry?** A root handle, `NfsMenuRoot`, not a bare mode signal, because items also need the root's per-mode Options and a place to register; the name is kept from BB and P50 (the ticket asks for it by name). The token file imports the class as a type only. Source: BB 1.9 parent handle; P50 decision 1 ("carries the mode signal plus the root's top-level items").
5. **How is the root handle created?** `nfsMenuRootProviders(mode)` returns a `useFactory` provider that constructs `NfsMenuRoot` in the root element's injector (so it can inject `ElementRef`, `Directionality`, `DOCUMENT`, `DestroyRef`, `HostAttributeToken`, and create render callbacks), plus `{provide: NfsSubmenu, useValue: null}`. Source: P50 `rootProvider`; R:di 3a.
6. **How do three roots coexist on one `ul` with one live?** ResponsiveMenu lists them in `hostDirectives` and provides the token; its provider takes precedence over its host directives' providers; every root binds its root class and forwards keys only while `root.mode()` equals its own mode. Measured in three engines (P50 row 5). Source: NG directive composition guide, "Dependency injection"; P50 verdict.
7. **One merged root host directive instead?** Not taken. Angular 22.1 merges a host directive reached twice (NG `directive-composition-api.md`, "Multiple host directive matches are merged"; the docs commit is in v22.1.0), which would give one listener, but P50 never exercised it and the three-listener shape is proven. Recorded as the alternative in the spec.
8. **How do the three roots pass their Options without overwriting each other?** `configure(mode, behaviour)` with one slot per mode; missing functions fall back to the frozen `nfsMenuBehaviourDefaults` (Foundation's defaults), which the plugin specs also use to seed their inputs. Two host directives exposing the same input name both receive a binding, which is Foundation's own behaviour (every child plugin read the same `data-*`), so `closeOnClick` keeps each mode's default. Source: R:menus 0.3 ("per-plugin `data-*` on the same `ul` still apply"); FS `foundation.responsiveMenu.js:138`.
9. **Parent discovery?** Items inject the nearest `NfsSubmenu` `{optional: true}`; roots re-provide it as `null` so a nested root starts a new tree (the `CdkAccordionItem` pattern); submenus and toggles inject their item, required. Source: BB 1.9.
10. **Registration and order?** Parent-owned registration at construction, unregistration in `DestroyRef.onDestroy`; order computed at event time or in a render callback with `compareDocumentPosition`, no `MutationObserver`, because no reader needs a reactive order (the arrow keys query visible controls at event time; the swap rule sorts in its `earlyRead`). Aria's `SortedCollection` keeps a `MutationObserver` only to keep `orderedItems` reactive. Source: NGC `src/aria/private/utils/collection.ts`; R:di 3c; BB 1.9 (proposed wording change).
11. **`nfsMenuItem` on leaves too?** Yes: Foundation gives every item inside a submenu `is-submenu-item is-<type>-submenu-item`, which a consumer may style, and the registry needs every item. Source: FS `foundation.util.nest.js:44-46`; P50 markup.
12. **Is an item an Openable?** No. A bare `nfsClose` on a link in a menu inside an off-canvas must close the off-canvas; the Triggers spec lists submenu toggles out of scope. Source: TRG Out of Scope; ADR 0013.
13. **An item without a root?** It toggles, emits no classes, binds `hidden` and `inert` on its closed submenu, and warns in development. Source: BB 1.9 ("menu item outside a menu root" warning).

Round 3: class emission.

14. **Class emission per mode?** As in the spec's API tables, from `computed` maps: item `is-<mode>-submenu-parent`, `is-submenu-item`, `is-<mode>-submenu-item`, `has-submenu-toggle`, dropdown `is-active` and `opens-*`; submenu `submenu`, `is-<mode>-submenu`, accordion `is-active`, drilldown `is-active`/`visible`/`invisible`/`is-closing`/`drilldown-submenu-cover-previous`, dropdown `js-dropdown-active`/`first-sub`; toggle `submenu-toggle`; drilldown root `invisible` from `hasOpenItem`. Source: FS `foundation.accordionMenu.js:227-290`, `foundation.drilldown.js:451-497`, `foundation.dropdownMenu.js:54-77, 302-377`; P50 rows 1 to 3.
15. **Which keys may a map hold?** Only those the utility owns in the current mode, so a consumer's `menu`, `nested`, `vertical`, and a leaf's current-page `is-active` are never removed. The one collision, `is-active` on a dropdown parent, is Foundation's own. Source: NG `guide/templates/binding.md` (static and bound classes combine); ACC D8 ("the binding would strip it"); R:menus 7.1.
16. **`visible` and `invisible` together?** Never: Foundation's `.visible` follows `.invisible` in `_visibility.scss`, so Foundation's own drilldown, which adds `invisible` to a level that still has `visible`, keeps that level visible. The library binds them exclusively. Source: FS `scss/components/_visibility.scss:69-74`, `js/foundation.drilldown.js:460-463`.
17. **`vertical` on dropdown submenus?** Consumer-written; `verticalClass` is a Dropped option (BB 1.4). Submenus are treated as vertical by the key tables, as Foundation's docs state. Source: FS `foundation.dropdownMenu.js:61`; `docs/pages/dropdown-menu.md` L92.
18. **Initial open state?** A static `is-active` on a submenu (Foundation's documented pre-open marker) seeds the item's `expanded` at construction through `HostAttributeToken`; a bound `[expanded]` wins. Source: R:menus 1.2 ("add the class `.is-active` to that sub-menu"); ACC D8.
19. **Ids?** A consumer `id` on the submenu wins (the `id` input); otherwise `_IdGenerator.getId('nfs-submenu-', true)`; server and client ids differ and `aria-controls` is a host binding, so hydration rewrites both. Source: BB 1.5.

Round 4: roles and keys.

20. **Roles and attributes constant across modes?** Native lists and items, `<button type="button" aria-expanded aria-controls>` parents, a link then a toggle in the Hybrid item named by Foundation's `.submenu-toggle-text` span, consumer-written `aria-current="page"` (Router: `ariaCurrentWhenActive="page"`), no `menu`/`menubar`/`menuitem`/`tree`/`group`/`none`, no `aria-haspopup`, no copied `aria-label`, `inert` on closed submenus. Source: APG disclosure navigation (R:apg AccordionMenu, DropdownMenu, ResponsiveMenu); ADR 0004; BB 1.10.
21. **Accordion keys?** Tab and native Enter/Space; APG optional keys in Foundation's set: Down/Up move across visible controls, Right opens a collapsed toggle with focus staying, Left closes an expanded toggle or the submenu containing focus and focuses its toggle, Escape closes the innermost submenu containing focus (Foundation closed all). Home/End not offered (Foundation never had them; APG optional). Source: FS `foundation.accordionMenu.js:30-38, 146-186`; APG hybrid keyboard table; P50 row 6.
22. **Drilldown keys and focus handoff?** Activating a toggle or Right opens and moves focus to the level's first non-back control with `preventScroll`; Left, Escape, and Back close and refocus the parent toggle; Down/Up move within the level. Focus moves on a mouse click too, because the toggle's level becomes `visibility: hidden`. Source: FS `foundation.drilldown.js:223-283`; P50 rows 6, 11.
23. **Dropdown keys?** Foundation's direction-dependent table (horizontal top level: forward/back move, Down opens and focuses; vertical top level: Down/Up move, forward opens; inside submenus: Down/Up move, forward opens nested, back closes and refocuses), RTL through `Directionality`, orientation from the root's computed `flex-direction` read in the handler (Foundation's `_isVertical()`). Up on a horizontal top level moves back, as the APG hybrid table says (Foundation closed). Source: FS `foundation.dropdownMenu.js:37-45, 168-263`; R:menus 3.6; APG hybrid table.
24. **Handler order and replay?** State, focus, `stopPropagation()`, `preventDefault()` last; modifier keys unhandled. A replayed key logs one `ErrorHandler` error, BB Part 4 item 3's accepted default; `stopPropagation()` before it keeps an enclosing widget from handling it again (P43 cases 24 and 25), and makes Escape close the innermost thing first. Source: BB 1.5, 1.11 decision 5; R:rendering 4.

Round 5: dropdown mechanics.

25. **Focus-out close: root `focusout` or Light dismiss?** Light dismiss, one entry per open dropdown submenu with `pane` = the submenu and `triggers` = the item's `li`, group `null`: ADR 0024 already names submenus, its focus rule closes per entry (the prototype's per-item scope, needed for 2.4.11 under `opens-inner`, P50 row 25), its Escape reaches hover-opened submenus with focus elsewhere (1.4.13), and its pointer rule is `closeOnClick`. One mechanism instead of two. Source: ADR 0024; AP Light dismiss rules and mapping table.
26. **Hover?** `nfsHoverIntent` per parent item, Hover region = the `li` (which contains its submenu), `enabled` = dropdown mode and not `disableHover`, delays `hoverDelay` (50) and `closingTime` (500), close on leave only with `autoclose` and not click-opened. `disableHoverOnTouch` dropped: the helper filters touch per event. A pointer click on a hover-opened submenu keeps it open (Foundation's `data-is-click`), a keyboard click toggles. Source: FS `foundation.dropdownMenu.js:100-166`; AP hover intent and mapping table.
27. **Collision bound?** Foundation's body box via `nfsDocumentRect`, `nfsBodyBounds`, horizontal `nfsOverlap`, in an `afterRenderEffect` per parent item (`earlyRead` measure, `write` flip), base to opposite to `opens-inner`, reset on close; the prototype's viewport width is replaced so Foundation's rule and the Anchored pane share one implementation. Source: FS `foundation.dropdownMenu.js:302-328`, `foundation.util.box.js`; AP D5 and mapping table.
28. **Alignment `auto`?** Right when the root's static class has `align-right`, when `Directionality` is `rtl`, or inside `.top-bar-right`; the last is read once in `afterNextRender` `earlyRead`, so it changes only closed submenus' classes after hydration. Source: FS `foundation.dropdownMenu.js:63-77`; BB Table B DropdownMenu risk.
29. **`clickOpen`, `forceFollow`, `closeOnClickInside`?** `clickOpen` dropped (buttons always toggle); `forceFollow` dropped (the Hybrid item's link navigates); `closeOnClickInside` kept through the root's `click` listener closing all on a leaf click. Source: FS `foundation.dropdownMenu.js:132-140`; BB 1.4.

Round 6: state, swap, and hooks.

30. **`multiOpen`, siblings, `expandAll`/`collapseAll`?** `open()` closes open siblings except in accordion mode with `multiOpen` on (Foundation's default `true`); closing siblings at the target's level equals Foundation's "outside the branch" because the invariant holds; `expandAll()` only in accordion with `multiOpen` on, `collapseAll()` everywhere. Source: FS `foundation.accordionMenu.js:194-204, 227-240`; BB 1.3 names.
31. **Swap rule?** In `NfsMenuRoot`, an `afterRenderEffect` keyed on `mode` with the previous mode in a closure: `earlyRead` reads `document.activeElement`, containment, and DOM order; `write` closes every open submenu off the focused path, also the focused toggle's own submenu when entering drilldown; with no focus inside, keeps the first open submenu per level; entering accordion changes nothing. Replaces P50's `effect` (BB 1.5 forbids DOM reads and state propagation there). Source: P50 rows 13 to 16 and ResponsiveMenu decision 2; BPS rule 1 (focus continuity).
32. **Focus after open or close?** In `afterNextRender` (`earlyRead` picks the target, `write` focuses), because `inert` is removed only by the next render (P50 F4 race); a focus-loss guard moves focus only when it was on a control the change hides; programmatic opens never take focus from outside. Source: P50 "Failures"; APG keyboard practice "persistence of focus".
33. **Render hooks?** As the spec's table: host bindings, constructor, `afterNextRender`, `afterRenderEffect` (collision, completion, swap), synchronous focus for moves between visible controls; no `effect`, no `afterEveryRender`. `injectAsync`: not applicable; nothing is loaded only after interaction. Source: BB 1.5; AP D20, D21.

Round 7: the accordion hook and animation.

34. **The expanded hook on the parent `li` (P50 OPEN FOR HUMAN 1, with the orchestrator's note).** The sources settle it. Foundation's contract for this state on this element is an attribute selector, `.is-accordion-submenu-parent[aria-expanded='true']` (FS `scss/components/_accordion-menu.scss:116-119`), set by JavaScript on the `li` (FS `foundation.accordionMenu.js:247-250, 277-280`); its `is-active` lives on the submenu `ul` (lines 243, 273), which cannot hold the grid because a multi-child `ul` sizes only its first row (BB 1.6 rule 3; audit 0002 M9), and a `:has()` selector from the `li` is out of target. `aria-expanded` on the `li` is invalid on `listitem`; `is-active` on the `li` paints a Hybrid item's link with `.menu .is-active > a` and would strip a consumer's `is-active`; an inline style needs `!important` to override and BB 1.13 keeps custom properties to measured values; an unprefixed `is-expanded` class passes for a Foundation State class, which CONTEXT.md reserves for Foundation. Decided: `data-nfs-expanded` on a parent `li`, bound in every mode while expanded, the attribute-keyed shape of Foundation's own selector with the library prefix, following STK's `data-nfs-sticky-on` on a consumer-written element (and ACC's `nfs-` classes only on library-owned elements). Proposed ADR below.
35. **Clip only while needed?** Yes: `data-nfs-shown` on the submenu when open and settled (at first render when open), removed at once on close, so focus rings and text spacing inside an open submenu are not clipped. Source: ACC decision 27 and rule 6; WCAG 2.4.7, 1.4.12.
36. **Accordion timing?** `nfs-accordion-menu($duration: 250ms)`, `ease-in-out`: Foundation's `slideSpeed` is a JavaScript Option with no Sass setting, and ACC uses the same parameter shape. No `@supports` guard (ACC D11). Source: FS `foundation.accordionMenu.js:324`; BB 1.13 (parameter only where Foundation has no setting).
37. **Drilldown slide and completion?** Foundation's `$drilldown-transition` on `is-active`/`is-closing`; completion by `transitionend` for `transform` on the submenu or a fallback of the measured computed total plus 100 ms, immediate for zero (Foundation hung on `none`). Source: FS `_drilldown.scss:95-113`; R:menus 2.8; ACC completion method.
38. **Dropdown animation?** None; `opened`/`closed` in the render callback after the change. Source: R:menus 3.8.
39. **Reduced motion?** `transition-duration: 1ms` for the accordion grid and Foundation's drilldown slide, in their mixins. Source: BB 1.6 rule 5; BB 1.13 item (4).

Round 8: CSS, WCAG, rendering modes, consumers, tests.

40. **Where does the custom CSS live?** In the three plugin mixins, each scoped to its root class, so a ResponsiveMenu matches only the live mode's rules; no `nfs-nested-menu` mixin (ADR 0012 pairs one mixin with each Foundation export mixin). Hybrid items in drilldown and dropdown mode also need the consumer's `foundation-accordion-menu`, which holds Foundation's only toggle rules. Source: ADR 0012; FS `_accordion-menu.scss:134-173` (unscoped `.submenu-toggle` rules).
41. **The custom CSS list?** Twelve rules in the spec's Sass subsection: the base parent-button rule per mode with padding and background twins from each mode's settings; button twins of every Foundation arrow (gated on the same Sass booleans); the accordion grid (three rules); the drilldown hybrid flex layout; link-arrow suppression in hybrid drilldown and dropdown items; `.is-drilldown { overflow: clip }`; the dropdown open-parent twin; reduced motion. P50 rule 1 is split per mode and gains the padding twins, because Foundation styles each mode's `a` padding separately. Source: P50 custom CSS list; FS `_menu.scss:72-78`, `_accordion-menu.scss`, `_drilldown.scss`, `_dropdown-menu.scss`.
42. **WCAG 2.2 AA?** 1.3.1, 1.4.3, 1.4.11, 1.4.12, 1.4.13, 2.1.1, 2.1.2, 2.4.3, 2.4.7, 2.4.11, 2.5.8, 3.2.1, 4.1.2, each with its requirement and check in the spec's criteria subsection. Foundation's defaults pass every one (arrows and link text 4.65:1; toggles 40 px; rows 38 px); the mixins add compile-time `@error` checks with Foundation's `color-contrast()` for arrow colours below 3:1 (axe has no 1.4.11 rule) and toggle settings below 24 px; no Storybook settings override is needed. The axe gate runs the six ADR 0018 tags in every mode. Source: P50 rows 19 to 23 and 25; ADR 0022; BB 1.10.
43. **Rendering modes?** Server HTML carries the mode's classes, ARIA, `inert`, and `data-nfs-*`; ResponsiveMenu renders the Server breakpoint's mode and re-classes in the first tick on other breakpoints; toggle `click` and root `keydown` replay; hover never replays; one hydration boundary for the whole menu; nothing structural is created. Source: ADR 0008, ADR 0014; R:rendering 7 (rules and the four menu checklist rows); P50 rows 17, 18.
44. **What does each consuming spec map?** The spec's table: root selector, `nfsMenuRootProviders(mode)`, root class and listener forwarding, the `configure()` slot, and the pieces each keeps (Defaults token, aggregate outputs, Drilldown's wrapper and back button, ResponsiveMenu's `rules`). ResponsiveMenu must always yield a mode; below a rule set's smallest breakpoint it uses that rule's mode, instead of Foundation's no-plugin state, which would leave button parents inert. Source: BB Tables A and B rows; BPS `resolve()` ("`undefined` when no rule applies yet ... left to the consuming spec"); FS `foundation.responsiveMenu.js:113-139`.
45. **Testing seams?** The four layers with ADR 0018's wording, story ids `nested-menu--*`, a test root directive in the tests only; layer 2 covers class maps, DI, registration under `@for` and `@defer`, completion with fake timers, alignment, replay-shaped keys; layer 3 the SSR smoke, pure tables, and the Sass compile checks; layer 4 real keys, geometry, swaps by viewport, and the fixture app's hydration, replay, and hydrate triggers. Source: BB 1.12; the [Decide the browser testing stack: Playwright component tests, Vitest Browser, or both](41-browser-testing-stack-decision.md) answer; P50 suite.

### Triage

Rule (map, Orchestration rules): impact HIGH when hard to reverse; confidence NOT HIGH when the default is bare, carried from a prototype without deliberation, or against the research or ADRs. Only HIGH with NOT-HIGH stays open.

1. **The accordion expanded hook** (P50 OPEN FOR HUMAN 1). Impact: HIGH (a styling hook consumers target; three specs inherit it). Confidence: HIGH now: derived from Foundation's own attribute-keyed selector for the same element and state, two in-effort precedents (STK's `data-nfs-sticky-on`, ACC's library classes only on library-owned elements), and the glossary's State class definition, which it leaves intact; every alternative is rejected by a named source (decision 34). Decided: `data-nfs-expanded`, with the proposed ADR.
2. **`data-nfs-shown` clip release.** Impact: medium (a second hook). Confidence: HIGH (ACC's measured rule for the same grid mechanism; WCAG 2.4.7 and 1.4.12). Decided.
3. **Light dismiss instead of the prototype's root `focusout`.** Impact: medium (DropdownMenu behaviour, one mechanism). Confidence: HIGH (ADR 0024 names submenus; the registry's focus rule is per entry, the scope P50 row 25 required). Decided; the e2e 2.4.11 case guards it.

### Proposed glossary terms

**Hybrid item**:
A menu item whose parent both navigates, through its link, and opens its submenu, through a separate toggle button beside it.
_Avoid_: split button, submenu toggle item, parent link

**Open path**:
The chain of open submenus from a menu root down to the innermost open one; Drilldown and DropdownMenu keep at most one per level, and a Menu mode swap keeps the one that holds focus.
_Avoid_: active branch, breadcrumb, trail
