## Answer

Gist: images get no directive: `<picture>` with `<source media>` for art direction and `NgOptimizedImage` (or `srcset`/`sizes`) for resolution switching, with a development-mode error on `img[nfsInterchange]`. Two directives share the `nfsInterchange` attribute through disjoint selectors: `NfsInterchange` (`[nfsInterchange]:not(ng-container)`) binds the host's `background-image` to the last matching Interchange rule and accepts Foundation's rule string or a typed `[content, query]` tuple array; `NfsInterchangeOutlet` (`ng-container[nfsInterchange]`) renders the `<ng-template>` of the last matching rule and replaces the dropped HTML-partial mode, with code splitting by a consumer `@defer` inside the template and data from `httpResource`/`resource`. Queries resolve as a breakpoint name (`atLeast`), then a Named query from `nfsInterchangeDefaultsToken` (default `nfsDefaultNamedQueries`, through `matches`), then a raw media query (through `matches`). Both expose a read-only `selected` signal and a `replaced` output. The server renders the Server breakpoint's rule and the client switches at the Breakpoint service's first render callback; `<picture>` is fully server-rendered, which is why it wins for images. No library CSS. Spec: [specs/interchange.md](../specs/interchange.md).

Source abbreviations: FS = `d:/projects/github/foundation/foundation-sites` (6.9.0), NG = `d:/projects/github/angular/angular` (22.2.x), NGC = `d:/projects/github/angular/components` (22.2.x), R: = this effort's `research/` files, BB = `building-blocks.md`, BP = the [Spec: Breakpoint service (shared utility)](53-spec-breakpoint-service.md) and `specs/breakpoint-service.md`.

### Decision log

Round 1 (no prerequisites: the Foundation contract and the upstream decisions).

1. Q: What are Interchange's real options, events, and methods (audit 0001 H6)? A: `Interchange.defaults` holds exactly `rules` (default `null`, programmatic `"[path, query]"` strings) and `type` (`'auto'`, `'src'`, `'background'`, `'html'`); `SPECIAL_QUERIES` holds `landscape`, `portrait`, `retina`, extended at init with every breakpoint as `only screen and (min-width: <em>)`; the one event is `replaced.zf.interchange`; the public method is `replace(path)`. The ticket's "named queries `small` ... `portrait`" are queries, not options. Source: FS `js/foundation.interchange.js:221-247` (read in full), `:109-116`; R:`foundation-inventory-forms-media.md` Interchange; audit 0001 H6.
2. Q: How does Foundation parse and evaluate rules? A: The string is matched with `/\[.*?, .*?\]/g`; each rule is split on `', '`, the last piece is the query and the rest are joined with `''` as the path; a query that is a `SPECIAL_QUERIES` key is replaced, anything else is used as a media query; every rule is tested with `window.matchMedia` on each `resizeme` and the last match wins; no match leaves the element unchanged. The docs say "`media_query` can be any CSS media query, or a Foundation breakpoint" and "the last rule to match will be used". Source: FS `foundation.interchange.js:70-86, 124-155`; FS `docs/pages/interchange.md` (Use with Images, callout).
3. Q: What do the three modes do? A: `src` sets the attribute and records `currentPath` on `load` (emitting `replaced` before load); `background` percent-encodes `(`/`)` and sets `background-image: url(...)`; `html` runs `$.get`, `.html(response)`, then `$(response).foundation()`. `auto` picks `src` for `<img>`, `background` for image extensions, `html` otherwise. Source: FS `foundation.interchange.js:163-207`.
4. Q: What is fixed upstream? A: BB Table A Interchange (`[nfsInterchange]` with a typed `rules` input for background and template modes; `<picture>` documented for images; HTML-partial mode dropped for `@defer`/`NgTemplateOutlet` driven by the breakpoint signal; `img` naming rule); BB Table B (`sizes="auto"` and `<iframe loading="lazy">` as future features; `nfsInterchangeDefaultsToken` with `namedQueries` defaulting to `nfsDefaultNamedQueries`; server renders the Server breakpoint's rule; template mode inside `@defer`); BB 1.3 (Plugin name when there is no Structural class), 1.4 (`replaced.zf.interchange` -> `replaced`; Defaults token Shape B), 1.11 decisions 3, 7, 8; BP (`matches(mediaQuery)`, `nfsDefaultNamedQueries`, Named query tokens, ADR 0014 handoff); ADR 0012 and the Sass subsection rule. Source: those documents.
5. Q: Is there a Material or Aria counterpart? A: No. Material 22.2 has no responsive-content component, and `BreakpointObserver`/`Breakpoints` are already compared and rejected in BP; Aria has no pattern; the APG has none either (only the `img` naming rules). Source: R:`angular-material-reference.md` (no Interchange section), R:`angular-aria-inventory.md` 10, R:`aria-apg-patterns.md` Interchange.

Round 2 (depends on 1-5: which modes survive).

6. Q: Does the library need an image mode? A: No. `<picture>`, `srcset`, `sizes`, and `<img loading="lazy">` are in the Browser target and pick the file at parse time; a `src` binding would render the Server breakpoint's file on the server and swap after hydration (double download, LCP after JavaScript, stuck inside `hydrate never`). Source: R:`web-platform-features.md` 12 ("Images: yes outright"); R:`angular-rendering-modes.md` 7 checklist row (`<picture>`/`srcset` "correct at every width with no JS"); BB 1.11 decision 7.
7. Q: Does the library wrap `NgOptimizedImage`? A: No. It already emits `srcset`, `sizes` (prefixed `auto, ` for lazy images), `loading`, `fetchpriority`, and a server preload link for `priority`; it does not support `<picture>` in 22.2 ("No, but this is on our roadmap"), so art direction uses a plain `<img>` inside `<picture>`. The spec documents both and compares them. Source: NG `packages/common/src/directives/ng_optimized_image/ng_optimized_image.ts:258` (selector `img[ngSrc]`), `:495-525`; NG `adev/src/content/guide/image-optimization.md:467-471`.
8. Q: What happens when a developer writes `nfsInterchange` on an `<img>` anyway? A: `NfsInterchange` matches it and throws a development-mode error naming `<picture>` and `srcset`/`sizes`; production does nothing. Rejected: excluding `img` from the selector (a static attribute would then do nothing silently). The `nodeName` read at construction is a read, safe on the server. Source: BP decision 21 (development errors for programming mistakes); BB 1.11 decision 3 (no DOM writes before hydration).
9. Q: Is the HTML-partial mode kept? A: No. Markup inserted with `innerHTML` is not compiled by Angular (no directives, sanitised), and `$(response).foundation()` has no counterpart; template mode plus a consumer `@defer` (code) and `httpResource`/`resource` (data) covers what partials were used for. A `PendingTasks`-backed loader is rejected as a data-fetching API inside a layout directive. Source: R:`web-platform-features.md` 12 Known gaps; R:`angular-22-api-survey.md` resource section (`httpResource` `@publicApi 22.0`), `@defer` section; R:`angular-rendering-modes.md` 1 (`PendingTasks`, "Interchange partial loading is the one candidate"). Proposed ADR below.
10. Q: Is `background-image` via CSS `image-set()` and media queries enough on its own? A: For URLs known at stylesheet compile time, yes: the consumer's stylesheet with Foundation's `breakpoint()` mixin and `image-set()` needs no directive and paints correctly at every width. `image-set()` is Baseline widely available, "available across browsers since September 2023" (Safari 17), so it is in target. For URLs that are data, no: inline styles cannot hold media queries, so background mode stays. Source: MDN `image-set()` (fetched 2026-09-26 through markdown.new); BB Table A.
11. Q: Does template mode earn a directive, or is `@if`/`@switch` over `NfsMediaQuery` enough? A: Kept as a directive, per BB Table A, because it brings Foundation's rule syntax, Named queries (including custom ones), and last-match-wins across mixed queries in one line; the `@if` form is documented as the equivalent for code that needs none of that. Also the answer for art direction whose meaning changes per breakpoint (one `alt` per template). Source: BB Table A; BP usage example (`@if (mq.atLeast('large'))`); R:`aria-apg-patterns.md` Interchange (`alt` truthful per source).

Round 3 (depends on 6-11: shape and API).

12. Q: One directive or two, and on which selectors? A: Two classes on one attribute with disjoint selectors: `NfsInterchange` on `[nfsInterchange]:not(ng-container)` and `NfsInterchangeOutlet` on `ng-container[nfsInterchange]`, both `exportAs: 'nfsInterchange'`. One class cannot serve both: its host style binding would target a comment node on `<ng-container>`. Two attribute names would split Foundation's single `data-interchange`. Precedent: Material's `MatButton`/`MatAnchor` on one `matButton` attribute. The compiler parses `:not(<element>)` and matches element-qualified selectors on `<ng-container>`. Source: NG `packages/compiler/src/directive_matching.ts:9-120`; NG `packages/core/test/acceptance/directive_spec.ts:160-190` (`ng-container[directiveA]`); BB 1.3 (names).
13. Q: Input name and forms? A: `rules` (Foundation's option name) as `input.required` with alias `nfsInterchange` (Foundation's attribute). Background: `string | readonly NfsInterchangeRule<string>[]`; template: `readonly NfsInterchangeRule<TemplateRef<unknown>>[]` (a string cannot name a template). `NfsInterchangeRule<T> = readonly [content: T, query: string]`, the tuple mirroring Foundation's `[path, media_query]`. This keeps the rule string as Foundation's contract, as BB 1.7 does for Breakpoint rules; BB 1.4's dropped-options wording is corrected below. Source: FS `interchange.md` rule format; BB 1.4, 1.7 bullet 5; angular-developer `inputs.md` (alias, required).
14. Q: How is a rule string parsed? A: A pure public `parseNfsInterchangeRules(rules)`: bracketed segments, each split at its first comma and trimmed; malformed segments warn in development and are skipped. Delta: Foundation splits on `', '` and takes the last piece, which breaks the `retina` query and any media query list and drops commas from paths. Source: FS `foundation.interchange.js:135-141, 246`.
15. Q: How is a query resolved? A: In order: a Breakpoint map name -> `mq.atLeast` (Foundation's `only screen and (min-width)` meaning); a `namedQueries` key -> `mq.matches(namedQueries[key])`; a token with whitespace or `(` -> `mq.matches(token)` (Foundation documents raw media queries); otherwise a development warning once per string and no match. A `namedQueries` key equal to a breakpoint name warns once and the breakpoint wins (Foundation added breakpoints after the special queries, so they overwrote them). BP's Named query paragraph says "anything else warns and answers false"; raw media queries are a documented Foundation feature, so this spec keeps them and proposes an amendment to that paragraph below. Source: FS `interchange.md` ("any CSS media query"); FS `foundation.interchange.js:109-116, 143-145`; BP Named query tokens.
16. Q: Where do custom Named queries live, and do they merge? A: `nfsInterchangeDefaultsToken` (`InjectionToken<NfsInterchangeDefaults>`, `{namedQueries?}`), Shape B, `inject(..., {optional: true})`, nearest provider wins; the map replaces `nfsDefaultNamedQueries`, and consumers spread the constant to extend it, as BP's binding usage example does. Source: BP decision 16 and its Interchange example; BB 1.4 (Defaults tokens), 1.9.
17. Q: What if no rule matches? A: The content is cleared (no inline `background-image`, empty outlet), so the result is a function of the media state. Delta: Foundation keeps the previous content, which depends on resize history and would make the server and `hydrate never` output unpredictable. The consumer's stylesheet background shows through when the inline property is absent. Source: FS `foundation.interchange.js:83-85`; BB 1.11 decision 1.
18. Q: `type`, `auto`, and `replace(path)`? A: Dropped: the host decides the mode; extension sniffing is fragile; `replace(path)` would fight the derived state (change `rules` instead). Source: FS `foundation.interchange.js:94-102, 163-176`; BB 1.4 dropped options.
19. Q: Outputs and public state? A: `replaced` (BB 1.4 mapping), emitted from a render callback once the DOM shows a rule different from the last reported one, starting with the first client render (Foundation emits at init), with the rule tuple, or `undefined` when cleared; a read-only `selected` signal. No `model()`: the viewport owns the state. Source: BB 1.4 (Completion output rule; `replaced.zf.interchange` -> `replaced`); angular-developer `outputs.md`; FS `foundation.interchange.js:180-196`.
20. Q: How is the background written? A: A `[style.background-image]` host binding on a `computed`: `url("<path>")` with the path escaped as a CSS string (`"`, `\`, newlines), `null` when cleared. Not `Renderer2` (not server-rendered, forbidden before hydration). Source: BB 1.5 (host bindings do the attribute work), 1.11 decision 1; FS `foundation.interchange.js:186` (only parentheses encoded).
21. Q: How does the outlet render templates? A: `ViewContainerRef.createEmbeddedView` from an `effect()`, which runs on the server too and so puts the Server breakpoint's view in the server HTML; hydration claims dehydrated embedded views by template id, as for `NgTemplateOutlet` and `@if`. Not `NgTemplateOutlet` as a host directive (its input cannot be set from the class, and it reacts only to `ngOnChanges`); not `afterRenderEffect` (no server content). Fallback: compare and swap in `ngDoCheck`. Whether the effect-driven view behaves under SSR, hydration, and the same-tick switch is under Prototype needed. Source: NG `packages/common/src/directives/ng_template_outlet.ts:76-93`; R:`angular-rendering-modes.md` 2 (Control flow: views reused by template id, else re-rendered); BB 1.5 (effects run on the server and never write the DOM), 1.9 (host directive input limit).
22. Q: Why not per-breakpoint `--nfs-interchange-*` custom properties with a Library mixin, which would paint correctly at every width? A: Rejected: it covers breakpoint names only, not Named queries, raw queries, or last-match-wins, so it is a second code path with different semantics; static URLs already have the stylesheet recipe. Source: BB 1.2 (one code path per behaviour), 1.13 (custom properties are an implementation channel, not theming).

Round 4 (depends on 12-21: accessibility and rendering modes).

23. Q: ARIA and keyboard? A: No pattern, no roles, no keys. Rules: one `alt` must be true for every `<picture>` source (meaning-changing art direction uses template mode with an `alt` per template); informative backgrounds put their information in the page text; template content carries its own semantics; swaps are not announced. Source: R:`aria-apg-patterns.md` Interchange (names practice, hiding-semantics practice); BP ARIA rule 4; MDN `image-set()` accessibility note.
24. Q: Focus when a swap removes the focused view? A: The outlet moves focus to the first tabbable element of the new view (CDK `InteractivityChecker.isTabbable`) in a render callback before emitting `replaced`, only when the live `activeElement` was inside the removed view; if the new view has none, focus is left alone and the consumer can act from `replaced`; never at the first-render switch. The target is a judgment call (OPEN FOR HUMAN below). Source: BP ARIA rule 1; BB 1.10 (focus persistence on re-render); R:`aria-apg-patterns.md` Interchange (do not remove the focused element without moving focus); NGC `src/cdk/a11y/interactivity-checker/interactivity-checker.ts:65`.
25. Q: Server output? A: `selected` from the Server breakpoint (names up to it match; Named and raw queries answer `false`); the background host binding and the outlet's view render; `<picture>` is as written. Source: BP Rendering modes; R:`angular-rendering-modes.md` 7 rules 1 and 9.
26. Q: Hydration? A: The hydration pass claims the server's style and view with the server's values (ADR 0014); the service then goes live in the same tick, rewriting the style and swapping the view if the live rule differs, which is a re-render, not an error. Source: ADR 0014; R:`angular-rendering-modes.md` 2.
27. Q: What does background mode cost at hydration? A: A server-rendered inline background downloads at parse time, so a viewport whose rule differs fetches a second file; accepted, with the stylesheet recipe and client-hint Server breakpoints as mitigations. Under a strict `style-src` CSP the server's `style` attribute is ignored until hydration writes the style through the CSSOM. Source: BB Table B Interchange ("may swap after hydration"); BP client-hint recipe.
28. Q: Event replay? A: Neither directive declares listeners, so no Interchange host has `jsaction` and nothing replays; consumer listeners inside templates replay as usual, except that a pre-hydration click inside a view the first client render swaps out is lost (replay runs after that render). Source: R:`angular-rendering-modes.md` 3-4; BP Event replay.
29. Q: `@defer`, incremental hydration, `hydrate never`, prerendering? A: Inside `hydrate on ...` the directive hydrates with live values (swap at the block's hydration); `hydrate never` keeps the Server breakpoint's choice while `<picture>` keeps working; plain `@defer` renders live with no swap; the recommended partial replacement is `@defer` inside each rule template (server content for the Server breakpoint's view, code split for the others); prerendering uses the default Server breakpoint and reads no request token. Source: ADR 0014 Consequences; BB 1.11 decisions 7 and 11; BB Table B Interchange.
30. Q: Animation? A: None: Foundation animates nothing, `background-image` does not interpolate, and the library adds no Motion class; consumer `animate.enter` inside a server-rendered template plays at hydration. Source: FS `foundation.interchange.js` (no Motion UI); the [Prototype: `animate.enter` at hydration](52-prototype-animate-enter-hydration.md) finding.

Round 5 (depends on all of the above: Sass, tests, future platform).

31. Q: Custom CSS and the Sass subsection? A: None; no `nfs-interchange` mixin; the subsection states the five items as "none", names `nfs-breakpoint-properties` as the token's CSS mirror, and notes the consumer-side `breakpoint()` recipe. Source: BB 1.13; ADR 0012; [Sass packaging for the new library](57-sass-packaging.md) answer (subsection template).
32. Q: Testing seams? A: The four layers with story ids `interchange--picture`, `--optimized-image`, `--background`, `--background-rule-forms`, `--named-queries`, `--custom-named-query`, `--raw-media-query`, `--no-match`, `--template`, `--template-deferred`, `--template-focus`; browser-level tests on a fake `MediaMatcher`; node-level parser tables and an SSR smoke; Playwright viewport, orientation, and `deviceScaleFactor` cases on the static Storybook build, and first paint without JavaScript, hydration, network counts (the accepted double fetch), hydrate triggers, and a pre-hydration click on the prerendered fixture app. Source: BB 1.12; BP Testing Decisions.
33. Q: Platform features for later? A: Bare `sizes="auto"` (not in target; `sizes="auto, <fallback>"` is valid today because WHATWG HTML says "fallback sizes can be specified" for engines without `auto`, and `NgOptimizedImage` emits it); `<iframe loading="lazy">` (Firefox 121); `NgOptimizedImage` support for `<picture>`. Source: R:`web-platform-features.md` 12; WHATWG HTML images section, fetched 2026-09-26 ("For better backwards-compatibility with legacy user agents that don't support the auto keyword, fallback sizes can be specified if desired."); NG `image-optimization.md:467-471`.

34. Q: Which WCAG 2.2 AA criteria apply, and does any Foundation default fail one (user rule restated 2026-09-26)? A: All treated as requirements: 1.1.1 (an `alt` true for every source a `<picture>` can show; meaning-changing art direction goes into template mode with an `alt` per `<img>`); 1.3.1 (background images are decoration only; any information is in the text for every rule's image, so a swap never carries information the text does not; no `role="img"` added); 1.4.3 (text over a background meets contrast against every rule's image or sits on a solid background; the story uses `.callout` so axe can decide); 1.4.5 (no text in swapped crops that could be real text); 1.4.10 (images fit 320 CSS px: Foundation's `foundation-global-styles` already sets `img { max-width: 100%; height: auto; }`, so no library rule is needed; consumers without it add those two declarations); 2.4.3 and 2.4.11 (the outlet's focus rule); 3.2.1 and 3.2.2 (swaps follow media state only; no listeners). No Foundation default fails; the story gate runs axe with the WCAG 2.2 AA rule set. Source: FS `scss/_global.scss:186-194`; WCAG 2.2 success criteria as named; BB 1.10 (axe gate); R:`aria-apg-patterns.md` Interchange; MDN `image-set()` accessibility note.

### OPEN FOR HUMAN

1. Focus target when a swap removes the view that holds focus (decision 24). Default applied: the first tabbable element of the new view, else leave focus to the browser and the consumer's `replaced` handler. Alternative: no library focus handling at all, leaving it entirely to `replaced`, which is simpler but lets focus fall to `<body>` on a device rotation unless every consumer handles it. Sources state that focus must not be lost, not which element of arbitrary consumer content should receive it.

### Proposed glossary terms

**Interchange rule**:
A `[content, query]` pair of Interchange, whose query is a breakpoint name, a Named query, or a media query; in a list of them the last matching one applies.
_Avoid_: breakpoint rule (which assigns modes), responsive source, interchange query

### Proposed ADR

- `adr/0015-interchange-no-image-or-partial-mode.md`: "Interchange has no image mode and no HTML-partial mode". Meets the bar: hard to reverse (public API and migration path), surprising to a Foundation migrant who expects `<img data-interchange>` to work, and a real trade-off (decisions 6 to 9).

### Re-run, 2026-09-26

Reopened by the [Prototype: Interchange template outlet under hydration](61-prototype-interchange-outlet-hydration.md): `replaced` fired before the DOM showed the rule it reported when the Breakpoint service's first-render handoff drove the swap, in both the `effect()` outlet and the `ngDoCheck` fallback, in three engines. Worked in the [Re-run: Interchange spec, the `replaced` timing and the outlet's focus rule](67-rerun-interchange-replaced-timing.md), which verified the chosen mechanism in a copy of the prototype workspace (evidence and numbers there). Decisions 19, 21, and 24 above are superseded by entries 35 to 40 below; the spec was edited in place.

35. Q: Why did `replaced` fire before the swap? A: `AfterRenderManager.execute()` runs every registered render callback phase by phase (`earlyRead`, `write`, `mixedReadWrite`, `read`) in one batch. The service writes `current` in an `earlyRead` callback; a later-phase `afterRenderEffect` that depends on `selected` is marked dirty while hooks are executing, and because its phase has not run yet it is reached in the same batch. The swap (a view `effect()`, or `ngDoCheck`) needs a change-detection pass, which `ApplicationRef.synchronize()` runs only in its next loop iteration. So any render callback that reads breakpoint-derived state directly runs ahead of a change-detection swap whenever the triggering write itself comes from a render callback. Source: NG `packages/core/src/render3/after_render/manager.ts` (`AFTER_RENDER_PHASES`, `execute`); NG `packages/core/src/render3/reactivity/after_render_effect.ts` (`consumerMarkedDirty`: "this node will be reached naturally"); NG `packages/core/src/application/application_ref.ts` (`synchronize`, `synchronizeOnce`); the [Prototype: Interchange template outlet under hydration](61-prototype-interchange-outlet-hydration.md) probe (`replaced:large` at 182.7 ms, `outlet-swap:large` at 184.8 ms).
36. Q: Which mechanism orders the emission after the swap? A: The rendered-rule handoff. The swap stays in change detection on both platforms (the outlet's `effect()`, which the [Prototype: Interchange template outlet under hydration](61-prototype-interchange-outlet-hydration.md) confirmed for server HTML, hydration, and first paint); the same effect writes the rule it rendered into a private signal; one `afterRenderEffect` (`mixedReadWrite` phase) depends on that signal and on `selected` and acts only when they are equal and the rule differs from the last one reported. In the handoff batch the two disagree and the callback does nothing; the swap's write re-dirties it; `synchronizeOnce()` runs render hooks only after a pass that leaves no view dirty, and a view's effects run before its embedded views are refreshed, so the new view's update pass is done when `replaced` fires. Background mode uses the same signal, written by an `effect()` that runs in the same pass as its host style binding. Verified: every emission's handler saw the view, its `@if` link, and its bound attribute (template) or the new `background-image` (background), in Chromium, Firefox, and WebKit, on client-rendered, server-rendered, and prerendered routes and inside `@defer (hydrate on viewport)`; the published form of background mode showed the same race (`NOT-SHOWN` on every run). Source: re-run evidence; NG `packages/core/src/render3/instructions/change_detection.ts` (`runEffectsInView` before `detectChangesInEmbeddedViews`); ADR 0014 Consequences (live values from the `write` phase on).
37. Q: Does the fix hold when the triggering write comes from another render callback, not only at the handoff? A: Yes. A later breakpoint change written inside an `afterNextRender({earlyRead})` callback and one written directly (the shape of a `MediaQueryList` listener) both produced exactly one `replaced` per swap, after the new view was in the DOM, in three engines. Source: re-run evidence.
38. Q: The prototype's candidate, swap and emit in the same `afterRenderEffect`? A: Rejected. A view created inside a render callback has had only its creation pass when the callback continues: the new view's `@if` link was absent at emission and the focus rule found nothing to focus (focus stayed on `<body>`), in three engines. An explicit `detectChanges()` on the new view fixes both (measured), but needs two swap paths (the effect for server HTML and the hydration pass, the render callback afterwards) and change detection inside a render callback, and it does not carry over to directives whose swap is an `@if` in their own template. Source: re-run evidence.
39. Q: Is the `ngDoCheck` fallback kept? A: No. In a zoneless app nothing re-checks the declaring view when `selected` changes, so `ngDoCheck` never ran again after the handoff and the fallback kept the Server breakpoint's view on every route, in three engines. In the [Prototype: Interchange template outlet under hydration](61-prototype-interchange-outlet-hydration.md) it appeared to swap only because the early `replaced` handler wrote a signal that the page template read. The `effect()` path is confirmed, so no fallback is needed. Source: re-run evidence; NG `packages/core/src/render3/instructions/change_detection.ts` (`ngDoCheck` runs only inside a refresh of the declaring view).
40. Q: Where does the focus rule detect "focus was inside the removed view", and does it apply at the handoff? A: In the swap effect, just before it clears the container, from the live `document.activeElement` (after a runtime swap the old view is already gone and the browser has moved focus to `<body>` by the time any render callback runs). The render callback then moves focus to the first tabbable element of the new view, only if focus is still on `<body>`, and emits `replaced` after that. It applies at the first-render handoff too: on a server-rendered page a keyboard user can focus a server-rendered link before hydration (Breakpoint service spec, consumer rule 1), which the published spec's "never at the first-render switch" wording contradicted. Verified for later swaps (both write paths) in three engines: focus on the new view's `@if` link, seen by the `replaced` handler; the pre-hydration case is a fixture e2e case in the spec, not measured here. WCAG 2.2 AA 2.4.3 (focus never stays on `<body>`), 3.2.1 (focus moves only when the swap removed the focused element). Source: re-run evidence; HTML focus fixup (a removed focused element leaves `document.activeElement` as `<body>`); BP consumer rule 1.
41. Q: What does `replaced` report at the first client render? A: Once, the live rule. When the handoff replaces the Server breakpoint's rule before the first paint, that rule is never reported, because it was never shown (measured: the handler log reads `large` only at 1300 px on every route). This keeps user story 29 ("fire once for the initial content"). Source: re-run evidence.
42. Q: Render hooks per building-blocks 1.5? A: One `afterRenderEffect` per directive with only a `mixedReadWrite` phase: the focus rule reads (`activeElement`, CDK `InteractivityChecker`, which reads layout) and then writes (`focus()`), and a `replaced` handler may read and write (the documented place for a consumer's own focus move), so the emission cannot sit in a `read` phase; not `earlyRead`, which shares the phase with the service's handoff write and is ordered by registration. Cost: one callback per swap. Source: BB 1.5; ADR 0014 Consequences; NG `after_render_effect.ts` phase documentation.

Side finding (low impact, no spec change): the "CSR double-construction" of the [Prototype: Interchange template outlet under hydration](61-prototype-interchange-outlet-hydration.md) is the `@defer (hydrate on viewport)` block's own outlet, which a client-rendered route creates on the client shortly after load (its `replaced` checks carry the block's test ids); it is not a second instance of the main outlet.
