# 116. Re-run: Responsive Toggle spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81, 86
Labels: wayfinder:grilling

## Question

What does the [Spec: Responsive Toggle](24-spec-responsive-toggle.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/responsive-toggle.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

Also: the Title Bar and Menu Icon (and the menu icon's hit area) now come from the Top Bar spec; RT6: the title directive returns, the generated id and the `aria-label` input stay out.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Responsive Toggle](24-spec-responsive-toggle.md) and the answer here. Model: Opus 5.5.

## Answer

Model: Opus 5.5. Worked AFK (map Notes, AFK override): a `/grill-with-docs` session in which the agent played both sides, with `/domain-modeling` for the vocabulary and `/to-spec` for the revision. Spec: [specs/responsive-toggle.md](../specs/responsive-toggle.md), revised in place; the change list is the `### Amendment, 2026-09-28 (class rule)` section of the [Spec: Responsive Toggle](24-spec-responsive-toggle.md). No experiment was run: every point rests on ADR 0039, ADR 0040, building-blocks as it stands, a resolved spec, Foundation's source, or a measurement another ticket made, and the contrast ratios quoted were recomputed with the exact WCAG relative-luminance formula (`#fefefe` on `#0a0a0a` 19.6304:1, `#cacaca` on `#0a0a0a` 12.0791:1, `#8a8a8a` on `#fefefe` 3.4230:1, `#1779ba` on `#e6e6e6` 3.7554:1, `#1779ba` on `#fefefe` 4.6473:1).

Gist: the Responsive Toggle has no Structural or Variant class of its own, so it gains no Variant input. Its Visibility classes, `.is-open`, and Motion classes stay host bindings, now as one class record per host that strips copied classes. What the consumer still wrote goes: `.title-bar`, `.menu-icon`, `.title-bar-title`, and `.top-bar` with its sections become the Top Bar spec's directives written beside this plugin's; `animate` takes the shared Motion names as `NfsMotionPair`, so Foundation's `hinge-in-from-top spin-out` copies unchanged. The menu icon's 24 px target and the title bar's contrast checks move to the Top Bar spec's mixins, leaving `nfs-responsive-toggle` with only the opt-in Visibility classes.

Sources, cited as: FS = the Foundation 6.9.0 clone (`docs/pages/responsive-navigation.md`, `scss/settings/_settings.scss`); NG = the Angular 22.2.x clone (`adev/src/content/guide/templates/binding.md`, class bindings); TB = the [Spec: Top Bar](86-spec-top-bar.md) and its Answer; TG = the [Re-run: Toggler spec under the class rule](109-rerun-toggler-class-rule.md) and the revised Toggler spec; RV = the [Re-run: Reveal spec under the class rule](110-rerun-reveal-class-rule.md); TR = the [Re-run: Triggers (shared utility) spec under the class rule](130-rerun-triggers-class-rule.md); BP = the [Re-run: Breakpoint service (shared utility) spec under the class rule](129-rerun-breakpoint-service-class-rule.md); TYP = the Answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md); T and X = `research/out-of-scope-triage.md` and `research/out-of-scope-exclusions.md`; BB = `building-blocks.md` as it stands; "the spec" = `specs/responsive-toggle.md` before this revision.

### Grilling record

Round 1 (no prerequisites): which classes the spec left to the consumer, and who owns them.

1. **Which Foundation or library classes did the spec leave to the consumer?** Markup: `class="title-bar"`, `class="menu-icon"`, `class="title-bar-title"`, `class="top-bar"`, `class="top-bar-left"`, `class="vertical medium-horizontal dropdown menu"`, `class="menu"`, `class="button"` on the second toggle, and the `.show-for-sr` naming alternative. Input values: `animate="nfs-hinge-in-from-top nfs-spin-out"` and `nfs-fade-in nfs-fade-out` in the Defaults example, library class names that ADR 0039's follow-up rules out. Prose: the class mapping's "the consumer writes `.title-bar`" and its "No directive" row for `.title-bar-title`, and the 2.5.8, 1.4.11, and 1.4.3 rows built on `nfs-responsive-toggle`'s hit area and warnings. Source: the spec; ADR 0039.
2. **Who binds them?** `.title-bar`, `.title-bar-title`, `.title-bar-left`, `.title-bar-right`, `.menu-icon` and `.dark`, `.top-bar`, `.top-bar-left`, `.top-bar-right`, `.stacked-for-<bp>`: the Top Bar spec's nine directives (TB decision 1). `.menu` and `.vertical`/`.<bp>-horizontal`: `nfsMenu` with `orientation` rules ([Spec: Menu](85-spec-menu.md)); the Dropdown Menu's classes: its root, which hosts `NfsMenu`. `.button`: `nfsButton`. `.show-for-sr`: the screen-reader-only directive of the [Spec: Visibility Classes](104-spec-visibility-classes.md), still open, so `nfsShowForSr` as TB writes it, a placeholder. Source: those specs; T section 2.
3. **Host the Top Bar directives, or sit beside them?** For hosting: one attribute on each element. Against: host directives are static, so `nfsResponsiveToggle` hosting `NfsTitleBar` would force `.title-bar` on a custom bar, and the spec's "any element will work" (Foundation's own docs sentence) would fall; BB 1.9 writes a behaviour that may sit on any element beside the class directive; TB D10 already decided beside. Settled: beside, and neither entry point imports the other (decision 1). Source: TB D10; BB 1.9; FS docs.

Round 2 (depends on 1-3): `hideFor` and the Visibility classes.

4. **Is `hideFor` a Variant input over Class breakpoints, or an Option?** For a Variant input: BB 1.4 naming rule 1 lists `hideFor` among the Options that name a Variant family, and it selects Visibility classes. Against: a Variant input defaults to setting no class and has no Defaults token default (ADR 0040; BB 1.4), while `hideFor`'s Foundation default `medium` sets `hide-for-medium` and `show-for-medium`, without which the bar shows at every width; it also selects the Breakpoint service query for the animation skip and the focus rule, which is behaviour. BB 1.7 already types it: "an Option whose spec emits the classes for every breakpoint keeps `NfsBreakpointName` (Responsive Toggle `hideFor`)", because `nfs-responsive-toggle(<bp>)` emits the pair for breakpoints outside `$breakpoint-classes`, which `NfsClassBreakpoint` would reject; TYP and BP left it to this re-run under the same condition, and the orchestrator's brief keeps it for now. Settled: an Option typed `NfsBreakpointName`, default `'medium'`, in the Defaults token, the Reveal's `overlay` precedent (RV decision 4); a clarifying clause for BB 1.4 is proposed (decision 2). Source: ADR 0040; BB 1.4, 1.7; TYP; BP; RV.
5. **Does `hideFor` request a Runtime check?** For: `strictVariantNames` could report a `hideFor` with no Visibility class. Against: its classes come from two sources, Foundation's `$breakpoint-classes` loop (listed in `--nfs-breakpoint-classes`) and this plugin's opt-in include (listed nowhere), so a check would need a second Variant property and the union of two lists; development check 5 already measures the rendered `display` of both hosts, which catches either missing source and a missing `foundation-visibility-classes`. BB 1.4 asks for `nfsVariantCheck` only from directives whose Variant inputs read a Variant property. Settled: no Runtime check request (decision 2). Source: BB 1.4, 1.13; the spec's check 5.
6. **How are the Visibility classes bound, and what happens to a copied one?** Options: (a) one dynamic key, `hide-for-<hideFor>`, as the spec had; (b) one class record per host over every non-zero breakpoint of `nfsBreakpointsToken`'s map, `true` only for `hideFor`, the Top Bar's `stackedFor` record and the Menu's (TB D2). (a) leaves a copied `hide-for-large` on a `medium` bar in place, where it hides the bar from `large` up regardless; (b) strips every copy of the family the directive binds, on server and client, because Angular's styling consults static classes only when every binding for the class is `undefined` (BB 1.4). Settled: (b), with `is-open` and the Motion classes in the menu's record; development check 1 widens from "the `hideFor` breakpoint's classes" to every copied Visibility class and `is-open`, reported through `HostAttributeToken('class')` in a development-only field initialiser, naming `hideFor` or `[(isOpen)]` (decision 3). A Visibility class of the other family (`show-for-*` on the bar) is not stripped, because the directive does not bind it there; the check reports it. Source: BB 1.4; TB D2; the Accordion re-run's dev check 7 shape.
7. **Can two directives' class records share one host?** NG's class binding guide: Angular combines static classes, `[class]` bindings, and single-class bindings, and resolves a collision for the same class by its precedence order; each binding must be a new object when it changes, which a `computed` gives, and no key may hold two class names. The Top Bar's records and this plugin's bind disjoint keys, and TB relies on the same composition (its Rendered HTML shows both on one element). Settled: no measurement needed. Source: NG; TB.

Round 3 (depends on 4-7): `animate`.

8. **What does `animate` take?** ADR 0039's follow-up: a Motion input takes `'fade-in'`, never `'nfs-fade-in'`. TG settled the one-string pair as `NfsMotionPair` over RV's `NfsMotionInName`, `NfsMotionOutName`, and dot-form `NfsMotionClassList`, mapped by `nfsMotionPairClasses`, and named this spec as a sharer. Foundation's own value, `hinge-in-from-top spin-out`, is in the set as written. Settled: `animate: NfsMotionPair` with an explicit type argument, default `''`, the Defaults token field typed the same (decision 4). The lone leaving name that TG added animates only the close here too; a lone entering value animates only the open, which Foundation's `anims[1] || null` also did. Source: TG decisions 4, 5; RV decisions 3, 10; FS `js/foundation.responsiveToggle.js`.
9. **What happens to development check 4 and the pure logic?** The check recognised Motion UI transition names; the type now rejects them. What still fails silently is a value that starts no animation (a Motion name without `nfs-motion`, a dot-form class without keyframes, a Motion UI class in the dot form), a cast value, or a dot-form `nfs-` class, which the completion effect's read phase already measures. Settled: check 4 reports those, TG's check 4 in this plugin's words; the `animate` parser and the recognition function leave this spec's pure-logic table, since `nfsMotionPairClasses` is the primary entry point's and TG's table covers it (decision 4). Source: TG check 4; RV check 3.

Round 4 (depends on 1-3): the menu icon, its target, and the contrast checks.

10. **Where do the menu icon's `type`, name, and 24 px target come from?** TB decisions 4 to 7: `button[nfsMenuIcon]` binds `.menu-icon` and `type="button"`, warns on a missing or symbol-only name and on a box under 24 px, and `nfs-menu-icon` gives every `.menu-icon` a transparent border on a content box, replacing this spec's `.title-bar .menu-icon::before`, which TB measured failing axe's `target-size` beside another target in three engines. Settled: the spec's 2.5.8 row points there, its `::before` rule, its hit-test e2e case, and its hit-area Sass test go; axe `target-size` stays in every story, and `responsive-toggle--below-breakpoint` asserts the icon's box, because its icon renders at every test viewport (decisions 5, 6). The Top Bar's `top-bar--responsive` e2e is the same layout, so nothing is written twice. Source: TB decisions 4-7, D6; BB 1.12.
11. **RT6?** The triage's "`[nfsTitleBarTitle]` returns; the generated id and `aria-label` input stay out" is TB decision 11. The consumer's static `id` on `nfsTitleBarTitle` names the icon through `aria-labelledby`; the Out of Scope line keeps the generated id and the input out. Source: T section 3, RT6; TB decision 11.
12. **The contrast checks?** TB decisions 7 and 8: `nfs-title-bar` stops the compile (`@error`) for the title and icon colours on `$titlebar-background`, with the exact formula; `nfs-top-bar` does the same for links on the bar and a differing submenu background; the consumer sets `$topbar-background: $white;` and, after the settings file, `$topbar-submenu-background: $topbar-background;`. The spec's `@warn` checks with Foundation's `color-luminance()` go (TB measured that function passing failing pairs, the reason this brief names). Settled: the rows point there, and the Sass subsection names both settings lines (decision 7). Source: TB decisions 7, 8, 12; TB probes 2 and 3.
13. **What is left of `nfs-responsive-toggle`, and should its argument stay optional?** Only the opt-in pair of Visibility classes. With `$hide-for: ()` as the default, an include without an argument would emit nothing, and a stylesheet copied from the published Off-canvas spec (`@include nfs-responsive-toggle;` for the hit area) would compile and silently lose its hit area. With the argument required, Sass's own missing-argument error names `$hide-for`, and no custom code is needed. Settled: required (decision 8); the Zero-breakpoint and unknown-name `@error`s stay. Source: TB decision 6; ADR 0012 (a parameter only for what Foundation has no setting for).

Round 5 (depends on all above): reflow, examples, stories, tests.

14. **The 1.4.10 reason?** TB measured Foundation's Top Bar docs example, which is this plugin's docs markup, at `scrollWidth` 320 at 320 px in three engines, so the spec's "which overflows at 320 px" is withdrawn. For keeping a stacked orientation in the story markup: a list of one link per row is the usual phone menu. Against requiring it: it is not what 1.4.10 needs, and a vertical Dropdown Menu opens its submenus beside the item (Foundation's `opens-right`), which the Dropdown Menu spec, not this one, must fit at 320 px. Settled: the requirement and its e2e stay; `responsive-toggle--default` holds Foundation's docs content as TB writes it, and one usage example shows `nfsMenu` with `[orientation]="{small: 'vertical', medium: 'horizontal'}"` as a layout choice; submenu widths are the menu Plugin's (decision 9). Source: TB Answer, "What other specs need"; FS docs; the Dropdown Menu spec's `$dropdownmenu-min-width`.
15. **Rendered HTML?** Consumer markup writes directives only; the resulting DOM names which spec binds each class; selector and static input attributes are left out, as TB's blocks do; a new block shows a bar and menu of the developer's own with a copied `hide-for-medium` stripped. Source: TB Rendered HTML; ADR 0039.
16. **Stories and tests?** Story ids unchanged. Stories write the Top Bar spec's directives as scaffolding; the default story asserts the Top Bar classes stay unchanged across a toggle and axe passes with a submenu open (the second settings line makes that true, TB probe 2). Browser-level: the class records and copies, every `animate` shape, the composition. SSR smoke: a class-free fixture plus one copied-class pair and one plain pair. Sass: the required argument. Source: BB 1.12; TG; TB layers.
17. **User stories?** 1, 3, 10, 15 to 17, 24, 29, 37, and 38 rewritten in place; 41 to 43 appended, keeping the numbers other records cite.
18. **Glossary or ADR?** No new term: Visibility class, State class, Motion class, Motion name (RV's proposal), Option, and Openable carry the revision. No ADR: every decision applies ADR 0039, ADR 0040, BB 1.7, or a resolved spec's decision (TB D6, D10; TG D18), and the one choice of this ticket's own, the required mixin argument, is easy to reverse.

### Decisions

1. The Responsive Toggle binds no Structural class. The bar is the Top Bar spec's `nfsTitleBar` (or any element), the icon `button[nfsMenuIcon]` with the bare `nfsToggle` beside it, the title `nfsTitleBarTitle` with a static `id`, and the menu `nfsTopBar` with its sections (or any element), all written beside `nfsResponsiveToggle` and `nfsResponsiveToggleMenu`, never hosted; the entry point imports nothing from the top-bar entry point.
2. `hideFor` stays an Option typed `NfsBreakpointName`, default `'medium'`, in the Defaults token; no Variant input, registry, alias, Variant property, or Runtime check request; development check 5 stays the missing-class signal.
3. The Visibility classes, `.is-open`, and the Motion classes stay host bindings, as one computed class record per host over every non-zero breakpoint of `nfsBreakpointsToken`'s map (plus `hideFor` itself), so a copied `hide-for-*` on the bar or `show-for-*` or `is-open` on the menu is stripped on server and client; development check 1 reports every copied Visibility class and `is-open`, naming `hideFor` or `[(isOpen)]`.
4. `animate` is `NfsMotionPair` (explicit type argument, default `''`, the Defaults token field typed the same), mapped by the primary entry point's `nfsMotionPairClasses`: Foundation's `hinge-in-from-top spin-out` copies unchanged; the developer's own classes take the dot form; a leaving name alone animates only the close. Development check 4 becomes the measured "started no animation" check; the parser and Motion UI name recognition leave the pure-logic table.
5. The menu icon's `type`, name checks, and box are `nfsMenuIcon`'s; the name is `aria-labelledby` to the `nfsTitleBarTitle` element's static `id` or visually hidden text (`nfsShowForSr`, a placeholder); no generated id, no `aria-label` input (RT6).
6. WCAG 2.5.8 is `nfs-menu-icon`'s border box on every `.menu-icon`; the `.title-bar .menu-icon::before` rule, its e2e hit test, and its Sass test are removed; axe `target-size` stays in every story, and `responsive-toggle--below-breakpoint` asserts the icon's 24 px box.
7. WCAG 1.4.11 and 1.4.3 are `nfs-title-bar`'s and `nfs-top-bar`'s `@error` checks with the exact formula; required settings `$topbar-background: $white;` and, after Foundation's settings file, `$topbar-submenu-background: $topbar-background;`.
8. `nfs-responsive-toggle` emits only the opt-in pair of Visibility classes, and its `$hide-for` argument is required.
9. The 1.4.10 overflow claim is withdrawn (TB's three-engine measurement); the requirement and its e2e stay; a stacked mobile menu is a documented layout choice, and submenu widths are the menu Plugin's.
10. Every example, story, fixture, and test host writes no Foundation or library class; Story ids unchanged; the Rendered HTML leaves out selector and static input attributes and adds a custom bar and menu.
11. Behaviour, the Openable contract, the state model, ARIA, keys, the focus rule, animation phases and completion, and rendering modes are unchanged.
12. No glossary term, no ADR.
