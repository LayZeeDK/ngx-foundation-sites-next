## Question

What replaces Foundation's Triggers utility (`data-open`, `data-close`, `data-toggle`, `data-toggle-focus`, `data-closable`), and what does its spec say?

## Answer

Spec: [specs/triggers.md](../specs/triggers.md). Resolved 2026-09-26 by self-grilling (AFK), both sides played against the sources below.

Gist: three attribute directives, `NfsOpen` (`[nfsOpen]`, target required), `NfsClose` (`[nfsClose]`, plus `nfsCloseResult`), and `NfsToggle` (`[nfsToggle]`), on the consumer's native `<button>` or link, each taking a typed template reference to an Openable or an array of them; a bare `nfsClose` or `nfsToggle` acts on the Nearest Openable, found with `inject(nfsOpenableToken, {optional: true, skipSelf: true})`. Every Openable implements `NfsOpenable` (`isOpen`, `id`, `triggerRole` as signals; `open(trigger?)`, `close(result?)`, `toggle(trigger?)`; optional `registerTrigger(trigger)`), provided under the lightweight `nfsOpenableToken`. The Trigger role (`disclosure`, `dialog`, `toggle-button`, `none`) decides the ARIA the Trigger renders as host bindings; `nfsClose` renders none. Activation is one `click` host listener that never calls `preventDefault()`, so replay is safe by construction. No service, no Defaults token, no CSS, no Foundation class, no `type` binding. `data-toggle-focus` and `data-closable` are dropped and replaced by template bindings, `@if` with `animate.leave`, or a Toggler with a bare `nfsClose`. Implementation level: custom Angular directives over native button activation (Invoker Commands and `popovertarget` are out of target).

### Decision log

Sources: FS = the Foundation 6.9.0 clone; NG = the Angular 22.2.x clone; NGC = the components 22.2.x clone; APG = the aria-practices clone; ARIA = the WAI-ARIA clone (`index.html`); R:x = the research files under `research/` by short name, as `building-blocks.md` cites them; BB = `building-blocks.md`.

Round 1 (no prerequisites): what Foundation does, and what is settled already.

1. **What exactly is Foundation's Triggers contract?** A document-level delegated `click` listener for `[data-open]`, `[data-close]`, `[data-toggle]`; the value is split on spaces and each `#id` receives `open.zf.trigger`/`toggle.zf.trigger` through non-bubbling `triggerHandler`, or `close.zf.trigger` through bubbling `trigger`; the trigger element is passed as an extra argument. Bare `data-close`/`data-toggle` fire on the trigger itself and bubble. `data-toggle-focus` toggles on both `focus` and `blur`. `data-closable` stops propagation and animates out with a Motion class or jQuery `fadeOut()`, then fires `closed.zf`. No `preventDefault()` anywhere. Source: FS `js/foundation.util.triggers.js:15-19, 29-67, 71-99`; `docs/pages/javascript-utilities.md:154-180`; `docs/pages/toggler.md` (Mark as Closable, Toggle on focus, Multiple Targets); R:utilities 2.1-2.5.
2. **Which plugins respond, and what ARIA does each stamp on its triggers?** Dropdown, OffCanvas, Reveal, Toggler, Tooltip respond. OffCanvas: `aria-expanded="false"` and `aria-controls` on every `data-open`/`data-close`/`data-toggle` trigger, flipped on open and close (FS `foundation.offcanvas.js:99-103, 421, 513`). Toggler: `aria-expanded` and appended `aria-controls` on `~=`-matched triggers at init, but updates only exact-match triggers (FS `foundation.toggler.js:42-77, 141-147`; R:disclosure Toggler). Reveal: `aria-controls`, `aria-haspopup="dialog"`, `tabindex="0"` on the first `data-open` anchor, else `data-toggle` (FS `foundation.reveal.js:53-58`). Dropdown: `aria-controls`, `aria-haspopup="true"`, `aria-expanded`, `data-is-focus`, `data-yeti-box` (FS `foundation.dropdown.js:52-61`). Tooltip: responds to `close.zf.trigger` only (FS `foundation.tooltip.js:245`).
3. **What does BB already settle, and what may this ticket reopen?** BB 1.8 and Table C: three directives, template references plus nearest-Openable DI, `nfsOpenableToken` with `open()`, `close()`, `toggle()`, `isOpen`, `id`, `triggerRole` (`'disclosure' | 'dialog' | 'none'`), dev warning on non-focusable hosts, Triggers do not bind `type`, Invoker Commands and `popovertarget` out of target, `data-closable` not a directive, `closeme` to Light dismiss. Audit 0002 L5: target resolution reopens only with a stated reason. Decisions 13, 16, 18, and 26 below reopen parts of 1.8, each with its reason; target resolution itself is not reopened (decision 5).
4. **Which consumers, and what does each need?** From BB Tables A and B: Reveal (`triggerRole: 'dialog'`, bare `nfsClose` inside, `[mat-dialog-close]`-style result, focus return); OffCanvas (disclosure, or modal dialog in trap-plus-overlay mode per R:apg OffCanvas; focus return to the trigger, Foundation's `$lastTrigger`, FS `foundation.offcanvas.js:404, 572`); Dropdown pane (disclosure, or dialog with its `role` input; its anchors are needed for `hover`, programmatic positioning against the first anchor, body-click exclusion, and `aria-labelledby`, FS `foundation.dropdown.js:52, 61, 72-76, 131, 166-195, 223-236`); Toggler (disclosure in visibility mode, `aria-pressed` in class mode, BB Table A and Table B Toggler rows; multi-target form); ResponsiveToggle (bare `nfsToggle` inside the bar resolves the bar's Openable, BB Table A); Tooltip (programmatic, BB Part 3).

Round 2 (depends on 1-4): targets and the contract.

5. **Target resolution: ids, template references, or DI?** Template references (and arrays) plus the Nearest Openable, as BB 1.8 chose; not reopened. Costs weighed: ids need a registry, consumer-supplied ids everywhere (generated ids differ between server and client, BB 1.5, R:rendering 7 rule 8), and a registry filled at construction is empty for an Openable in a dehydrated block, so a replayed click finds nothing (R:rendering 4 Worked cases, first bullet). References are compiler-checked and match Material `matMenuTriggerFor` (NGC `material/menu/menu-trigger.ts`), CDK `cdkMenuTriggerFor`, and Aria `AccordionTrigger.panel = input.required<AccordionPanel>()` (R:di 3d). The one gap, linking across components, is covered by passing the `NfsOpenable` through an input or by the wrapper providing the token. Recorded as the proposed ADR below.
6. **Template-reference form and typing?** `#x="nfsReveal"` through each Openable's `exportAs`, as Aria (`#panel1="ngAccordionPanel"`, R:di 3d) and Material require. The input is typed by the `NfsOpenable` interface, so under `strictTemplates` a reference to the element instead fails compilation (an element's `open` is a property, not a method, and `HTMLDialogElement.open` is a boolean). A dev-mode check covers non-strict templates.
7. **Array form?** `readonly NfsOpenable[]`, the typed counterpart of Foundation's space-separated list (FS `triggers.js:15-19`; `toggler.md` Multiple Targets). `aria-controls` lists every id.
8. **Bare form versus null?** Only the bare attribute (the empty string) selects the Nearest Openable; a bound `null` or `undefined` means no target (no ARIA, no-op click). Reason: a reference that is briefly `undefined` (a signal query before its first render) must not operate an ancestor. `nfsOpen` has no bare form: it is `input.required`, and Foundation's bare `data-open` targets nothing either (FS `triggers.js:30-32` always splits an id list).
9. **Nearest-Openable resolution?** `inject(nfsOpenableToken, {optional: true, skipSelf: true})` at construction, the AGENTS.md content-projection pattern and CDK's `CdkAccordionItem` shape (R:di 2 "inject() flags"). `skipSelf` matters because Tooltip provides the token on its host, which is a trigger element: `<button nfsClose nfsTooltip>` inside a Reveal must close the Reveal. Nearest wins, which also reproduces Reveal's guard that a closable callout inside a modal does not close the modal (FS `foundation.reveal.js:150-157`; R:disclosure Reveal "Listens"). Projected content resolves against its declaration site, so a wrapper component becomes the Nearest Openable only by providing the token itself (NG `adev/src/content/guide/di/hierarchical-dependency-injection.md:748-752`; R:di 2).
10. **Contract as abstract class or interface?** An interface behind `InjectionToken<NfsOpenable>` in a type-only token file. Consumers implement it in wrapper components without extending a library class; Material types `MAT_MENU_PANEL` by the `MatMenuPanel` interface for the same reason, while CDK and Aria use `InjectionToken` for retention (R:di 1). Token name per ADR 0009.
11. **Exact members and types?** `isOpen: Signal<boolean>` (the `isOpen` model, read-only here; BB 1.3), `id: Signal<string>`, `triggerRole: Signal<NfsTriggerRole>`, `open(trigger?: HTMLElement): void`, `close(result?: unknown): void`, `toggle(trigger?: HTMLElement): void`, `registerTrigger?(trigger: HTMLElement): () => void`. `triggerRole` is a signal because Toggler and Dropdown pane switch roles from inputs (BB Table B Toggler; Table A Dropdown). Methods return `void`: completion is the Completion outputs, not promises (BB 1.4; Material's `MatDrawer.open()` returns a promise, not borrowed).
12. **What is `id`?** The id of the controlled element, the one `aria-controls` must name: for ResponsiveToggle the menu, not the title bar that provides the token (FS `docs/pages/responsive-navigation.md` markup; R:apg ResponsiveToggle). Consumer-supplied or generated (BB 1.5).
13. **Why `open(trigger?)`, beyond BB 1.8's member list?** Focus return and anchoring need the invoking element: Reveal refocuses its active anchor (FS `foundation.reveal.js:236, 484`), OffCanvas its `$lastTrigger`, and Dropdown positions against `$currentAnchor` (FS `foundation.dropdown.js:119, 131`). Relying on `document.activeElement` alone fails where a mouse click does not focus the button. Material's `MatDrawer.open(openedVia?)` is the precedent for an optional argument (R:material 6). Without the argument the Openable falls back to its first registered Trigger for anchoring and to the element focused before opening for focus return (Material's dialog rule, R:material 3).
14. **Why `close(result?)`?** Material's `[mat-dialog-close]` hands its bound value to `close(result)` (NGC `material/dialog/dialog-content-directives.ts:29-49, 72-88`; R:material 3 "The `[mat-dialog-close]` directive shape"). The target already occupies `nfsClose`'s value, so the result gets its own input, `nfsCloseResult`.
15. **Why optional `registerTrigger`?** Dropdown needs its anchors before any click: `hover` listeners on the anchors, programmatic `open()` positioning against the first anchor, the body-click handler ignoring anchors, and `aria-labelledby` on the pane (FS `foundation.dropdown.js:52-76, 166-236`). The shape is Aria's reverse link, `effect(() => this.menu()?.parent.set(this))` (R:di 3e). An `effect` with cleanup registers and unregisters; it writes no DOM, so it is safe on the server (BB 1.5 "Effects"). Optional, because only Dropdown pane needs it today.

Round 3 (depends on 5-15): ARIA, keyboard, hosts.

16. **What does `triggerRole` render?** `disclosure`: `aria-expanded` plus `aria-controls` on `nfsOpen`/`nfsToggle` (APG disclosure pattern; R:apg Dropdown, OffCanvas, ResponsiveToggle, Toggler). `dialog`: `aria-haspopup="dialog"`, `aria-controls`, and `aria-expanded` (decision 18). `toggle-button`: `aria-pressed` on `nfsToggle` only (APG Button pattern; R:apg Toggler "aria-expanded would be wrong here because nothing is expanded"; ARIA `aria-pressed`, R:apg ARIA facts table). `none`: nothing (Tooltip; ARIA: "A tooltip is not considered to be a popup", ARIA `index.html:13953`). This adds `toggle-button` to BB 1.8's union. Reason: BB Table A Toggler ("toggle Button with `aria-pressed` (class mode)") and Table B Toggler ("`none` in class mode where the trigger binds `aria-pressed`") need a Trigger that renders `aria-pressed`, which `none` by definition cannot.
17. **`aria-haspopup="true"`?** Never. ARIA treats `true` as `menu` and requires the popup's role to match (ARIA `index.html:13953`; R:apg Dropdown "Foundation delta that matters most").
18. **`aria-expanded` on a dialog opener?** Rendered. A non-modal dialog (Dropdown pane with `role="dialog"`, BB Table A; Reveal with `overlay: false` through `show()`, ADR 0007) keeps its opener reachable, and R:apg Dropdown gives that opener `aria-haspopup="dialog"` and `aria-expanded`; for a modal Reveal the opener is inert while open, so only "collapsed" is ever announced. BB 1.8 lists only `aria-haspopup` plus `aria-controls` for Reveal, and the APG dialog example's opener carries neither (R:apg Reveal "`aria-controls` on the opener is not part of the pattern"). The sources allow both; the default here is one role value per ARIA shape. OPEN FOR HUMAN 1.
19. **`nfsClose` ARIA?** None. The APG dialog pattern's close button carries no state (R:apg Reveal: "a visible element with role `button` that closes the dialog"), and `aria-expanded` on a one-way control reports a state it cannot change back. Delta: Foundation's OffCanvas and Toggler stamp `aria-expanded` on `data-close` triggers (decision 2).
20. **Multi-target semantics?** `nfsOpen` opens each, `nfsClose` closes each; `nfsToggle` closes all when any is open, else opens all, so `aria-expanded` has one truthful value. Foundation toggles each independently (FS `triggers.js:42-49` per id), and its docs example ("Toggle All These" over three visible thumbnails, `toggler.md` Multiple Targets) behaves identically under both rules. Mixed Trigger roles in one array: the first target's role decides and dev mode warns.
21. **Keyboard?** Native only: Enter and Space activate a `<button>` through `click`; Enter follows and activates a link. No keydown listener, unlike Material's and CDK's menu triggers (NGC `material/menu/menu-trigger.ts:30-38`; `cdk/menu/menu-trigger.ts:59-66`), whose arrow keys belong to the menu pattern no Openable uses. Escape is the Openable's (BB 1.10).
22. **Which hosts, and the dev-mode warning?** `<button>`, `<a href>`, and `<input type="button|submit|reset">`. Anything else warns in dev mode ("cannot be operated from the keyboard"); an `<a>` without `href`, with an empty one, or with `#` warns "use a button". Foundation's docs use `<a data-toggle>` without `href`, which is not focusable (R:apg Toggler; BB 1.8, 1.10).
23. **Who owns `type`?** Not the Trigger, confirming the Button spec's rule (Button spec decision 17; BB 1.8): `nfsButton` or the consumer. A dev-mode warning fires for a `<button>` host without a `type` attribute whose `form` is not null, because the missing-value default submits (Button spec decision 9, HTML button element).
24. **Disabled hosts?** A natively disabled button dispatches no `click`. A focusable disabled `nfsButton` (`disabledInteractive`) renders `aria-disabled="true"` and still clicks, so the handler returns early on `aria-disabled="true"`, the check Material's `MatDialogClose._onButtonClick` makes for the same reason (NGC `dialog-content-directives.ts:72-76`).
25. **Focus return and `data-closable` focus?** The Openable returns focus to the `trigger` given to `open()`; a bare `nfsClose` inside the Openable does not become the return target. When a close button disappears with its content (the `data-closable` replacements), the consumer moves focus to a logical next element (R:apg Toggler: "the keyboard practice's persistence rule requires moving focus to a logical element"); Triggers move no focus.
26. **A Trigger on an `<a>` host?** Allowed for links that navigate and also act, the case BB 1.8 names (a menu link with `routerLink` and `nfsClose`). The Trigger never cancels navigation: it calls no `preventDefault()`, matching Foundation (FS `triggers.js` has none). A link that should not navigate is a button. Hazard, stated rather than engineered around: the host listener gives the link `jsaction`, so inside a still-dehydrated block Angular's dispatcher cancels the native navigation, hydrates, and replays; RouterLink then navigates on replay, a plain `href` does not (R:rendering 4 "Anchors"; Button spec decision 13; ADR 0011 Consequences). Exposure is small because an Openable is closed until its own boundary hydrates, so this needs a dehydrated block nested inside an open Openable. Rejected: attaching the listener in code only on links (no `jsaction`, so no cancellation, but two activation paths in one directive and no replay); a `preventNavigation` input (a button does that). ADR 0011's consequence line covers directives on `<a>` "whose navigation must stay native inside deferred regions"; a Trigger does not promise that (its whole job is a click listener), so the rule is met by documenting the exception rather than by dropping the listener, and no ADR change is proposed.
27. **`data-toggle-focus`?** Dropped (BB 1.4 already lists it): it toggles on both focus and blur, so a target that starts in the wrong state stays inverted (R:disclosure Triggers utility). Replacement: `(focus)="t.open()" (blur)="t.close()"` in the template; content shown on focus must also close on Escape (WCAG 1.4.13, R:apg Toggler), which the Openable provides.
28. **`data-closable` and its animation?** Not a directive (BB 1.8). Two documented replacements: `@if` with `animate.leave` and an `nfs-*` keyframe Motion class when the element should leave the DOM (ADR 0003 mechanic 2); a Toggler in visibility mode with a bare `nfsClose` inside when it should hide in place, which is what Foundation's `fadeOut()` does (`display: none`, FS `triggers.js:50-63`; ADR 0003 mechanic 1). An `nfsClosable` Openable would be a third way to hide an element.

Round 4 (depends on 5-28): rendering modes, implementation, tests.

29. **State model and zoneless?** Triggers own no state: `computed` for the resolved targets, the aggregate `isOpen`, and the ARIA values; host bindings read them; no timers, observers, or `NgZone` (BB 1.5).
30. **Server render and first paint?** The four ARIA attributes are host bindings on the Openable's signals, which exist on the server, so the server HTML is the final ARIA (R:rendering 7 rule 1). Generated `aria-controls` values differ between server and client and are rewritten at hydration because they are bindings (R:rendering 7 rule 8; BB 1.5).
31. **Event replay?** The `click` host listener is replayable and gives the host `jsaction="click:;"` (R:rendering 4 Mechanism and "Which events replay"). The replayed handler reads targets resolved at construction or in the first render, which exist before replay (R:rendering 3 "What a directive inside a hydrate block may assume"), and never calls `preventDefault()`, so replay cannot throw in it; BB Part 4 OPEN FOR HUMAN 3 (replay detection) does not affect Triggers. `showModal()` and `focus()` need no user activation (R:rendering 4).
32. **Hydration boundary and `@defer`?** A Trigger and its Openable share one boundary (ADR 0008; BB 1.11 decision 6). Template-variable scoping enforces half of it: a `@defer` block is a new view (NG `adev/src/content/guide/templates/variables.md:63, 200-230`), so a Trigger outside cannot reference an Openable inside. A Trigger inside a block referencing an Openable outside works: the click hydrates the block and its dehydrated ancestors top-down, then replays (R:rendering 3 "Nesting and order"). Inside `hydrate never` nothing is annotated, so a Trigger there is inert (R:rendering 3 Syntax). Library templates contain no `@defer`; the Triggers are the `ngx-foundation-sites/triggers` entry point (BB 1.3, 1.11 decision 7).
33. **Animation?** None (ADR 0003 has nothing to govern): a Trigger inserts nothing and binds no class; `aria-expanded` follows `isOpen`, which changes at request time.
34. **Implementation level and primitives?** Custom Angular over native button activation. Invoker Commands (Baseline newly available 2025-12-12, R:platform 20) and `popovertarget` (targets must be popovers, out of target, R:platform 2) are out; Aria 22.2 has no disclosure or dialog trigger (R:cdk Aria cross-reference); CDK's menu trigger renders `aria-haspopup="menu"` and creates overlays (R:cdk menu). Primitives: `input`, `input.required`, `computed`, one `effect`, `inject` with flags, `ElementRef`, host metadata, dev-only `afterRenderEffect`. No fallback needed.
35. **Service, provider function, Defaults token?** None: no shared state (BB 1.5), no Foundation defaults for Triggers (BB 1.4 Defaults token), and neither Aria nor CDK ships a provider function (BB 1.9).
36. **Material and CDK comparison?** Borrowed: typed-reference input with `exportAs` (`matMenuTriggerFor`), `[mat-dialog-close]`'s DI lookup, result, and `aria-disabled` check, Aria's reverse link. Not borrowed: `type` and `aria-label` inputs (native attributes; `nfsButton` owns `type`), keydown and mousedown handlers, overlay creation, `aria-haspopup="menu"`. `MatSidenav` has no trigger directive; consumers call `drawer.toggle()` through a reference, which Triggers keep working alongside (R:material 3, 5, 6).
37. **Testing seams?** Story ids `triggers--<story>` (ten stories) with a test Openable that lives with the tests and stories; browser-level tests (stack-neutral) for resolution, the ARIA table, contract calls, registration cleanup, the `aria-disabled` guard, wrapper components, the five dev warnings, and a replay-shaped click; node-level Vitest for the SSR smoke (ARIA and `jsaction` in server HTML) and the pure ARIA-derivation function; Playwright e2e for real keys across engines, first paint without JavaScript, hydration counters, a pre-hydration click, a dehydrated block, a nested boundary, the link hazard, and `hydrate never` (BB 1.12; the harness is the [Prototype: Rendering-mode test seam](59-prototype-rendering-mode-test-seam.md)).
38. **Sass?** Per [Sass packaging for the new library](57-sass-packaging.md), "What every plugin spec's Further Notes must say": Triggers use no Foundation export mixin and add no library CSS; "No library CSS; there is no `nfs-triggers` mixin", with items (1) to (5) stated as none.
39. **Platform features when the target moves?** Invoker Commands: render `commandfor` plus `show-modal`/`close`/`request-close` for Reveal and custom `--nfs-*` commands for the others; the dialog case then works before hydration and in `hydrate never`; needs consumer ids; `command` does not replay, so the click listener stays (R:platform 20; R:rendering 4 replay list). `popovertarget`: when Dropdown pane and Tooltip move to `popover`, the browser sets the invoker's `aria-expanded` and implicit anchor (R:platform 2). `<form method="dialog">` is in target today and documented as a Reveal-side alternative that skips the exit animation (R:platform 1; BB 1.8).

### OPEN FOR HUMAN

1. `aria-expanded` on a modal dialog's opener. Default applied: the `dialog` Trigger role renders `aria-haspopup="dialog"`, `aria-controls`, and `aria-expanded`, so one role value covers modal Reveals and non-modal dialogs (Dropdown pane `role="dialog"`, Reveal `overlay: false`). The alternative is a separate modal value (for example `modal-dialog`) that omits `aria-expanded`, matching BB 1.8's wording, Foundation's Reveal, and the APG dialog example's plain opener, at the cost of a fifth role value and an Openable that switches role with its modality. Sources permit both (ARIA `aria-haspopup` and `aria-expanded` definitions; R:apg Reveal and Dropdown); the choice is about announcement verbosity ("collapsed" on a dialog opener).

### Proposed glossary terms

**Nearest Openable**:
The closest Openable that encloses a Trigger in the template where the Trigger is declared, which a Trigger written without a target acts on; the replacement for Foundation's bubbling empty `data-close`.
_Avoid_: parent Openable, ancestor target, bubbling target

**Trigger role**:
What an Openable declares its Triggers to be (disclosure, dialog opener, toggle button, or plain command), which decides the ARIA each Trigger renders.
_Avoid_: trigger type, ARIA mode, popup type

### Proposed ADR

[adr/0013-triggers-target-resolution.md](../adr/0013-triggers-target-resolution.md): "Triggers reach Openables by typed reference or the Nearest Openable, through one interface token, never by id". It meets the bar. Hard to reverse: the public linking API every Openable spec and every consumer template depends on. Surprising: Foundation users expect id strings. A real trade-off: the id registry, custom events, `closest()`, and an abstract class were each weighed.
