# 41. Decide the browser testing stack: Playwright component tests, Vitest Browser, or both

## Question

Given the prototype results, does Playwright component testing replace Vitest Browser for browser-level tests in the next library, or do both stay, and what is the final test pyramid every spec's Testing Decisions must follow?

Decide, with `/grill-with-docs` self-grilling against `research/tooling-baseline.md`, `research/playwright-component-testing.md`, the prototype ticket's answer and `prototypes/playwright-ct/`, and `building-blocks.md`:

1. The layers: story play functions (Storybook with `@storybook/addon-vitest`), browser-level tests (Playwright CT, Vitest Browser, or both with a rule for which goes where), node-level Vitest for server-side rendering and pure logic, Playwright e2e for web-native APIs and the static Storybook build. Name the Nx target and command per layer.
2. CSF reuse rules: which stories are the single source for interaction tests, when a Playwright CT test may mount a story versus a bare host component, and what must never be duplicated between layers.
3. What each layer asserts (DOM and ARIA state, never instance fields), how axe runs in each, and how SSR, hydration, and event replay (per [Angular 22.2 @defer, SSR, prerendering, hydration, and event replay for DOM-touching directives](38-angular-rendering-modes.md)) are tested at which layer.
4. If no Playwright CT solution worked: record that, keep Vitest Browser, and state what would have to change upstream for the decision to be revisited.

Write the decision as an ADR under `adr/` (it is hard to reverse, surprising without context, and a real trade-off) and update the testing-seams section of `building-blocks.md` to match. The consistency review ticket then aligns every spec's Testing Decisions with this ticket. Mark anything unsettled as `OPEN FOR HUMAN`.

## Answer

Gist: **Playwright component tests do not replace Vitest Browser, and both stay, split by one rule.** Vitest browser mode under the Angular unit-test builder is the browser-level layer, because every case the published specs put there needs TestBed (DI overrides, `DeferBlockBehavior.Manual`, a `Directionality` double, a fake `MediaMatcher`, a replay-shaped event, dev-mode warnings), which a Playwright test cannot reach from Node. The working Playwright component-test solution (Playwright 1.63's built-in `mount(storyId, props?)` fixture over the static `@storybook/angular-vite` build) is adopted as the way the Playwright e2e layer opens stories, not as a fifth layer: what it adds over play functions (real engines, real input, a browser context) is what the e2e layer is for, and it costs a navigation plus a Storybook boot per mount. The node-level layer runs in the same `nx test` run as the browser-level layer, through the `<name>.ssr.spec.ts` files and one shared `renderServer()` helper; a `test-node` project is the fallback for adapter-dependent server paths. Interaction tests live once, as play functions. Story ids are shared by layers 1 and 4 only. Written as a self-grilling against the sources named in the question; every question and the answer settled on is in the decision log.

### Decision log

Each entry: the question asked, the decision, the source.

1. **Does Playwright CT replace Vitest Browser for the browser-level layer?** No. A Playwright test runs in Node and sees only the page: no TestBed, no DI override, no `ComponentRef.setInput`, no harness environment (CDK 22.2 ships `testbed`, `selenium-webdriver`, and `protractor` environments only), no coverage (`research/playwright-component-testing.md` section 6). Every browser-level case in `specs/button.md`, `specs/triggers.md`, and `specs/breakpoint-service.md` needs one of these: `provideRouter`, `skipSelf` resolution against a test Openable, a fake `MediaMatcher` in the environment injector, a seeded `TransferState`, console warning capture, an event dispatched with `eventPhase` 101 and a throwing `preventDefault`. Playwright's own docs call instance access "neither recommended nor supported" (same research, section 3).
2. **Does it become a layer of its own next to the four?** No. Its content would be a copy of a play function (layer 1 already runs the same story through the same Storybook build) or an engine-specific assertion (layer 4's job). The one thing it adds to the e2e layer is a nicer entry point, `mount(id, props)` with `update()` and rejection on story error, so it is adopted there (ADR, Considered options).
3. **The rule that splits the two stacks.** A case goes to the browser-level layer when it needs TestBed; to the e2e layer when it needs an engine other than Chromium, real input events, or a browser context (viewport, media emulation, history, storage, reload, network hold-back, JavaScript disabled); to a play function otherwise. Sources: the capability table in `research/playwright-component-testing.md` section 6 and `building-blocks.md` 1.12.
4. **Default realm of `nx test`.** `"browsers": ["chromiumHeadless"]` in the `test` target options, as `research/tooling-baseline.md` recommends: the directives are DOM, focus, and ARIA behaviour jsdom does not implement. The SSR smoke passes in browser mode as well (seam prototype cases 1 to 3), so one run covers layers 2 and 3.
5. **Is the browser-level layer Chromium only?** Yes by design. The builder normalises any browser name (`firefoxHeadless`, `webkitHeadless`) for the Playwright provider (`angular-cli/packages/angular/build/src/builders/unit-test/runners/vitest/browser-provider.ts:50-61`), but neither prototype ran it outside Chromium, and engine differences are what layer 4 exists for. Not added.
6. **Node-level layer: which target?** The library's `test` target, per the seam prototype's handed decision 1: `renderApplication` runs under the builder in jsdom and browser mode with no second project, no Analog plugin, no extra config. `test-node` (`nx:run-commands`, plain `node`, `DominoAdapter`) only for a spec whose server path depends on the DOM adapter (decision 4 of that prototype). The builder cannot run Vitest's `node` environment (`ReferenceError: document is not defined`, case 7).
7. **`ngServerMode` isolation.** Through the shared `renderServer()` helper, which builds `provideServerRendering()` and `provideClientHydration()` inside the bootstrap callback; the server platform then owns the flag and clears it on destroy (`NG/packages/platform-server/src/server.ts:130-146`; seam prototype cases 2, 4, 5). The "own file or process" wording in the published specs and in `research/angular-rendering-modes.md` section 6 is superseded; the note added to that section says so. Specs never import an application's `app.config.server.ts`.
8. **Which stories are the single source of interaction tests?** Every story in `<plugin>.stories.ts` with a play function. Layer 1 runs them all through addon-vitest. No other layer re-implements a play function: layer 4's Storybook half mounts with `embed=true`, which turns off autoplay (`shouldAutoplay = !shouldEmbed`, `storybook@10.6.0` preview runtime, research section 5), so Playwright owns the interaction there and asserts only what decision 3 assigns to it.
9. **When may a Playwright test mount a story rather than a bare host component?** Always a story: layer 4's Storybook half has no bare-component mount. Candidate 2 (an Angular-native gallery with `*.story.ts` files written twice) was rejected by the prototype for that reason, and the map's Testing rule asks for CSF reuse. Layer 2 is the reverse: always a bare test host component, never a story (next entry).
10. **May the browser-level layer compose stories (portable stories)?** Not as a rule. It works under the builder with three workarounds (`globalThis.STORYBOOK_ANGULAR_OPTIONS`, `*.css` module typings for TypeScript 6, a cast over the untyped `composeStory`; prototype failure 9), and a spec that only replays a play function duplicates layer 1. A spec that needs a story's decorators or `applicationConfig` providers is describing a play function.
11. **What must never be duplicated between layers.** A play function's steps; axe on a story's initial state (layer 1 owns it, layer 4 receives the same addon-a11y report through `storyFinished`); server-HTML assertions (layer 3 only; layer 4's fixture half asserts behaviour, not markup); and the two rendering-mode negative controls (once per suite, not per plugin, seam prototype decision 5).
12. **What each layer asserts.** DOM and ARIA state only (`building-blocks.md` 1.12, `R:material` 0.6): roles, accessible names, `aria-*`, State classes, `hidden`, `inert`, focus position, emitted outputs through a story `fn()` or a test host's bound handler. No layer reads a directive's fields; `@playwright-labs/selectors-angular` (instance access through `window.ng`, dev builds only) is not part of the stack (prototype result 6).
13. **How axe runs in each layer.** Layer 1: `@storybook/addon-a11y` with `parameters.a11y.test = 'error'` in `preview.ts`, `runOnly` widened to WCAG 2.2 AA (`research/tooling-baseline.md`, Accessibility checks in CI). Layer 2: none, the builder has no axe integration and the states it reaches are story states. Layer 3: none. Layer 4 Storybook half: the addon's own run (in the story's `afterEach`, in the browser) reaches Playwright through `storyFinished`, so a violation rejects `mount()` (prototype test "an axe violation in the story rejects mount()"); `@axe-core/playwright` 4.13 (peer `playwright-core >= 1.0.0`, works on 1.63) after Playwright-driven interactions that no play function performs. Layer 4 fixture half: `@axe-core/playwright` on the JavaScript-disabled page and after hydration.
14. **Where SSR, hydration, event replay, and hydrate triggers are tested.** Server HTML: layer 3 (`<name>.ssr.spec.ts`; assertions per seam prototype decision 3). Replay-safe handler logic: layer 2 (a real event with `eventPhase` redefined to 101 and `preventDefault` redefined to throw, mirroring `event_dispatcher.ts:121-138`, `research/angular-rendering-modes.md` section 6). Real hydration, replay of a pre-hydration click, hydrate triggers, `hydrate never`, and JavaScript-disabled first paint: layer 4 fixture half, one route per plugin, development build for `ngDevMode` stats (seam prototype decision 5, cases 10 to 16). Client-side `@defer` states: layer 2 with `DeferBlockBehavior.Manual` (`NG/packages/core/testing/src/defer.ts:25-66`).
15. **The gallery's dependence on Storybook preview internals.** Left OPEN FOR HUMAN as the prototype recorded it. Until answered: the gallery is adopted, confined to `.storybook/playwright-gallery.ts` plus the `previewHead` stub in `main.ts`, and layer 4 specs are written against Story ids and locators, so the fallback (`page.goto` on the public `/iframe.html?id=<story-id>&viewMode=story` URL, `&args=` for props, no `update()`) is one mechanical rewrite of the `mount` calls and deletes one file. Playwright's `mount` is stable public API since 1.62 (`research/playwright-component-testing.md` section 4); only the gallery's inside is at risk.
16. **Linux CI and real Safari.** Unproven on this machine (both prototypes, "what this does not prove"); every Playwright browser here is an x64 binary under Windows-on-Arm emulation, which is why Firefox and WebKit tests took 3 to 21 s each. The decision does not depend on either: layer 4 is the only three-engine layer, `-- --project=chromium` is the local default, and the new repository's first CI run on `mcr.microsoft.com/playwright:v1.63.0-noble` (or `npx playwright install --with-deps`) is where both get proven. Recorded under OPEN FOR HUMAN as an environment only the human can supply.
17. **How Story ids are shared across layers.** Storybook's own ids, `<plugin>--<story>` (`building-blocks.md` 1.3, CONTEXT.md Story id): layer 1 runs the story by id through addon-vitest, layer 4's Storybook half calls `mount('<plugin>--<story>')` with the same id (prototype fact "Story ids are Storybook ids"). Layer 2 uses no Story id. The typed `Stories` registry (`playwright` 1.63 `types/test.d.ts`) was not generated in the prototype and is not required; the [Storybook conventions for the new library](58-storybook-conventions.md) ticket may add it.
18. **Nx project shape.** Two e2e projects, as both prototypes ran them: `<lib>-e2e` with `webServer.command: 'npx nx run <lib>:static-storybook'` and `<fixture-app>-e2e` with `'npx nx run <fixture-app>:serve-static'`, both `reuseExistingServer: true`, so Nx runs the server target and its build as task dependencies and infers `e2e--wait-for-webserver` and `e2e-ci` (`research/tooling-baseline.md`, Playwright e2e setup; `@nx/playwright@23.2.1` plugin). One project with an array `webServer` was not tried and is not adopted.
19. **Question 4 of the ticket (no solution found).** Does not apply: candidate 1 works (23 of 23 in three engines). For the record, the upstream change that would make an adapter package viable again is a Playwright-blessed Angular gallery, which Playwright closed as "Not planned" (microsoft/playwright#39010), so the project-owned gallery is the durable route.
20. **The WCAG 2.2 AA rule set and the enforcing gate** (user rule restated 2026-09-26: every directive and component complies with WCAG 2.2 AA). Every layer that runs axe runs one rule set, `runOnly: {type: 'tag', values: ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa', 'best-practice']}`, and `parameters.a11y.test = 'error'` stays. Why the tags must be named: addon-a11y forwards `parameters.a11y.options` to `axe.run` and `parameters.a11y.config` to `axe.configure`, disabling only `region` (`@storybook/addon-a11y@10.6.0`, `dist/_browser-chunks/chunk-P5J2FJ2Z.js:42-95`); without `runOnly`, axe-core 4.13.0 runs every rule that is enabled by default, and its `target-size` rule (WCAG 2.2 SC 2.5.8, 24 by 24 CSS px, tags `wcag22aa`, `wcag258`) ships `enabled: false` (`axe-core/axe.js:33491-33496`). A tag-matched rule runs even when it ships disabled (`matchTags`, `axe.js:20558-20564`: `matching || include.length === 0 && rule.enabled !== false`), so naming `wcag22aa` is what turns target size on; `color-contrast` (SC 1.4.3, `wcag2aa`) is on either way. Layer 4 uses the same six tags through `AxeBuilder.withTags` (the prototype's call names four; `wcag22aa` and `best-practice` are added). The enforcing gate is layer 1, `npx nx test-storybook <lib>`, which runs every story's axe pass under Foundation's compiled CSS in Chromium and fails the Vitest run on a violation, in CI before merge; layer 4's Storybook half inherits the same report through `storyFinished`, so it cannot pass a story layer 1 fails. How a failing Foundation default is caught: every story renders Foundation's CSS as the consumer compiles it, so a default that fails 2.2 AA (a button colour below 4.5:1, a close button or Orbit bullet below 24 px) fails the story that shows it, on the pull request that adds the story. Silencing is not allowed: no story sets `parameters.a11y.test` to `'todo'` or `'off'` and no rule is disabled for a Foundation default; the two permitted responses are a Storybook settings override (consumer-side Sass in the preview's settings file, one variable per violation with the rule id in a comment, listed in the spec's Sass subsection) or, when the failing element is the directive's own markup, a library rule under the Styling Guidelines. Per-story exceptions exist only for documented anti-pattern demos, which the [Storybook conventions for the new library](58-storybook-conventions.md) ticket defines.
