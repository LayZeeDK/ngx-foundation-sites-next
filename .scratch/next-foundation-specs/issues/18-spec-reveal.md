## Question

What is the Angular design for Foundation's Reveal plugin in the next library, and what does its spec say?

The result must be the best combination of: Foundation for Sites SCSS and the plugin's features; the ARIA APG pattern and WAI-ARIA; WHATWG HTML and HTML5+ platform features; Angular Aria; Angular CDK; Angular Material-equivalent accessibility and Material-equivalent component API (inputs, outputs, public properties and methods, content and view projection) for the similar Material component; and the modern DI patterns recorded in `research/di-and-composition-patterns.md` (lightweight injection tokens, host-scoped providers, host directives, parent tokens, default-options tokens). One plugin may yield several related directives or components (for example a container plus items plus a lazy-content directive); the spec covers the whole set.

## WCAG 2.2 AA guard (user decision, 2026-09-26)

Every directive and component complies with WCAG 2.2 AA; see the map's Accessibility preference and [ADR 0022](../adr/0022-wcag-2-2-aa-enforcement.md). The spec carries a criteria subsection under Implementation Decisions naming the 2.2 AA criteria this plugin touches (at least 1.4.3, 1.4.11, 2.4.7, 2.4.11, 2.5.8, 4.1.2, and, for overlays and hover content, 1.4.13) and how each is met, as requirements, never recommendations. Where a Foundation default fails a criterion, the spec states the Sass settings the consumer must set or the smallest custom rule the `nfs-<plugin>` mixin adds, with the reason. The story axe gate runs with the WCAG 2.2 AA tags, and the decision log records each criterion addressed.

## Note from the research repairs (2026-09-25)

Audit 0001 finding H5 corrected the Foundation facts in `research/angular-material-reference.md` that this ticket reads. Take these as given:

- `closeme.zf.reveal` is not a close-lifecycle event: it fires just before this reveal opens so other open reveals close (`foundation.reveal.js:265-272`). The lifecycle events are `open.zf.reveal` (end of `open()`) and `closed.zf.reveal` (after the close animation). No Foundation event backs a Material-style `beforeClosed` output; if the spec wants one, it is synthesized at the start of the directive's own `close()` and the spec says so.

## Answer

Spec: [specs/reveal.md](../specs/reveal.md).

Gist: Reveal is one directive, `NfsReveal` on the consumer's `<dialog class="reveal">` (`dialog[nfsReveal]`, `exportAs: 'nfsReveal'`), on the native platform level: `showModal()` for the default modal, `show()` for `overlay: false`, `::backdrop` as Foundation's overlay; CDK Dialog is not needed. It is an Openable (`isOpen` model, `open(trigger?)`, `close(result?)`, `toggle(trigger?)`, `registerTrigger`, Trigger role `dialog`) and provides `nfsOpenableToken` and `nfsRevealToken`, with `nfsRevealDefaultsToken` for defaults. Foundation Options kept as inputs: `overlay`, `closeOnClick`, `closeOnEsc`, `multipleOpened`, `vOffset`, `hOffset`, `animationIn`, `animationOut`, `deepLink`, `updateHistory`; Material-derived additions: `role`, `autoFocus`, `restoreFocus`, `closePredicate`, `id`. Outputs `opened` (after the enter animation) and `closed(result)` (after `dialog.close()`); no `beforeClosed`. Dropped Options: `showDelay`, `hideDelay`, `fullScreen` (the `.full` class), `resetOnClose`, `appendTo`, `additionalOverlayClasses`. Three changes to the prototype's dismissal mechanics, recorded in a proposed ADR: modal Escape is intercepted at `window` so vetoes hold under repeated Escape, a Backdrop press needs both ends on the backdrop, and non-modal Reveals use the Light dismiss registry. Foundation's `'auto'` placement, which the prototype left OPEN FOR HUMAN, is decided: reproduced in CSS by one added rule, with a three-engine parity check graduated under Prototype needed. The Scroll lock is Foundation's own rule plus the directive's port of its offset and restore. No WCAG rule is added (Foundation's defaults pass); the mixin warns at compile time when a consumer's close-glyph or backdrop colours fall under 3:1. Self-grilled against the sources below; after triage only the screen-reader check and the upstream WebKit report stay human-only.

### Decision log

Sources are cited as: prototype = [Prototype: Reveal on native `<dialog>` under Foundation Sass](42-prototype-reveal-dialog.md), its README, `src/app/reveal.ts`, `src/_nfs-reveal.scss`, and `results.log`; Motion prototype = [Prototype: `animate.enter` and `animate.leave` with Motion UI transition classes](47-prototype-motion-ui-animate-enter.md); hydration prototype = [Prototype: `animate.enter` at hydration](52-prototype-animate-enter-hydration.md); seam prototype = [Prototype: Rendering-mode test seam](59-prototype-rendering-mode-test-seam.md); Triggers = [Spec: Triggers (shared utility)](54-spec-triggers.md) and its spec; Anchored pane = [Spec: Anchored pane (shared utility)](55-spec-anchored-pane.md) and its spec; Toggler = [Spec: Toggler](17-spec-toggler.md); Tabs = [Spec: Tabs](16-spec-tabs.md); Foundation = `js/foundation.reveal.js`, `scss/components/_reveal.scss`, `docs/pages/reveal.md` in the 6.9.0 clone; CDK = `src/cdk/dialog/dialog-config.ts` and `dialog-container.ts` in the 22.2.x components clone; BB = `building-blocks.md`; R:x = the research files.

1. Q: Directive, component, or service? A: One attribute directive on the consumer-written `<dialog class="reveal">`, placed where it belongs in the template; no service, no generated overlay. Source: ADR 0007, ADR 0001, BB 1.1 and Table A; R:material 3 "patterns that do not fit".
2. Q: Implementation level, and is ADR 0007's CDK Dialog fallback needed? A: Native platform; CDK Dialog is not needed for any case, because the prototype matched Foundation's sizes, full screen below medium, `::backdrop`, `show()`, nested modals, and the exit keyframe in three engines. CDK supplies only `InteractivityChecker` and `_IdGenerator`; Aria has no dialog pattern. Source: prototype verdict and "Decision handed to the Reveal and OffCanvas specs"; R:platform 1; R:cdk dialog; R:aria 10.
3. Q: Selector, `exportAs`, tokens? A: `dialog[nfsReveal]` (the selector enforces the element), `exportAs: 'nfsReveal'`, `nfsOpenableToken` and `nfsRevealToken` with `useExisting`, optional `nfsRevealDefaultsToken` (Material shape B). `nfsRevealToken` exists so content components can close their own Reveal with a result, the declarative counterpart of injecting `MatDialogRef`. Source: BB 1.3, 1.4, 1.9, Table B; ADR 0009, ADR 0013; R:material 3.
4. Q: State and Openable members? A: `isOpen` model (true from request to accepted close), `id` input with a generated `nfs-reveal-` default (Toggler's shape), `triggerRole` constant `'dialog'`, `open(trigger?)`, `close(result?)`, `toggle(trigger?)`, and `registerTrigger` (needed so the Light dismiss pointer rule counts Trigger presses as inside for non-modal Reveals). Source: Triggers API table; BB 1.3 `isX` rule; Toggler API; ADR 0024.
5. Q: Outputs, and `beforeClosed`? A: `opened` after the enter animation (or in the render callback after showing), `closed` with the result after `dialog.close()`, `isOpenChange` from the model. No `beforeClosed`: BB 1.4 allows no start events, and `isOpenChange(false)` already marks the accepted start of a close. Foundation's `closeme.zf.reveal` becomes the internal stack, not an output. Source: BB 1.4 output naming rule; the ticket's research-repair note (no Foundation event backs `beforeClosed`); R:disclosure Reveal events.
6. Q: `closePredicate` shape and reach? A: `(result: unknown) => boolean`, default `null`; it guards `close()` from code and Triggers, Escape, Backdrop press, Light dismiss reasons, and closes caused by another Reveal opening; a parent writing `isOpen` false and a native close are not vetoed (the parent owns its state; a native close cannot be stopped). Source: CDK `closePredicate` in `DialogConfig`; R:material 3.
7. Q: `overlay`? A: `true` opens with `showModal()` (modal, `::backdrop`), `false` with `show()` and Foundation's `.without-overlay` class; the APG treats the latter as non-modal. Source: prototype results; R:apg Reveal ("drop `aria-modal` and treat it as a non-modal dialog").
8. Q: How does a non-modal Reveal dismiss? A: Through the Light dismiss registry while open: group `null`, `outsidePress` from `closeOnClick`, its Triggers inside, Escape topmost-first from anywhere, and focus leaving closes it. This fixes the prototype's own-listener bug (an outside `pointerdown` closed the dialog before the Trigger's click reopened it) and meets 2.4.11 by closing on focus loss, a way of passing the Understanding document names for non-modal content. Every reason goes through `close()`, so `closeOnEsc` false ignores `'keydown'` and `closePredicate` applies. No Tab wrap, no Scroll lock. Known limit: a modal Reveal written inside a non-modal Reveal's element and opened with `multipleOpened` gets Escape only after the non-modal one closes. Source: ADR 0024 and the Anchored pane spec's registry API; WCAG 2.2 Understanding 2.4.11 (w3.org: "non-modal dialogs" can obscure focus, "closing on loss of focus" passes, Note 2); Triggers D7 (the non-modal Trigger stays reachable).
9. Q: Modal Escape: `cancel` as ADR 0007 and the prototype had it, or something reliable? A: The topmost modal Reveal handles Escape on `window` in the bubble phase, skipping `defaultPrevented` and `isComposing` events, closes when `closeOnEsc` and `closePredicate` allow, and calls `preventDefault()` last in every case. The WHATWG close request steps fire the Escape `keydown` first, and "If the web developer cancels the event by calling `preventDefault()`, then nothing further happens" (HTML Standard, User interaction, close requests; fetched through markdown.new); the Anchored pane spec measured the same in Chromium, Firefox, and WebKit. So `closeOnEsc: false` and vetoes hold under repeated Escape, which the prototype showed `cancel` cannot guarantee. `window` rather than the host, because the host `keydown` runs before the document-level Light dismiss handler of a pane inside the dialog. `cancel` stays as the fallback for other close requests; a non-cancelable one closes natively and the `close` event re-syncs. Source: HTML close request steps; prototype `closeOnEsc: false` row; Anchored pane spec Escape rule; proposed ADR below.
10. Q: Backdrop press: ADR 0007's `pointerdown`? A: `pointerdown` and `pointerup` both on the backdrop (target is the host and the point is outside the border box), `pointercancel` clears it; modal only. A touch swipe on the backdrop and drags between content and backdrop never close; the prototype's padding and drag-out cases still hold, and the click lands on the dialog. This is the HTML dialog light dismiss model and ADR 0024's. Source: prototype backdrop row; ADR 0024; R:platform 1 (`closedby` light dismiss).
11. Q: `closeOnClick`, `closeOnEsc` defaults? A: Foundation's `true` for both. `closeOnEsc` also covers the platform's other close requests on a modal, the Escape key's generalisation. Source: Foundation `Reveal.defaults`; BB 1.4.
12. Q: `fullScreen`? A: Dropped option in favour of the `.full` Variant class. Foundation's option only forced `overlay: false` and disabled the body click; a full-screen top-layer dialog stays modal with a covered backdrop, and Foundation's JavaScript did not even add `.full` for the option. Source: Foundation `_init`; ADR 0010's rule that classes stay classes.
13. Q: `multipleOpened`? A: `false` (default) calls `close()` on every other open Reveal before showing (each may veto through its predicate and then stays underneath); `true` stacks nested `showModal()` calls, and Escape, Backdrop press, and Tab wrap act on the topmost only. Foundation's Escape closed every open modal at once because every open Reveal bound the same `keydown.zf.reveal` on `window`; that bug is not copied. Source: ADR 0007 consequences; prototype nested rows; Foundation `_addGlobalListeners` and `close()`.
14. Q: Where does the shared state live? A: An internal root `@Service()`, `NfsRevealStack`: the open Reveals in order, the Scroll lock count, and one `window` `keydown` listener while a modal is open. BB 1.5 allows services only for state shared across instances, which this is; a module-level set (the prototype's) is shared between applications on one page. Source: BB 1.5; the prototype's note on the registry shape.
15. Q: `deepLink` and `updateHistory`? A: Kept, after hydration only, with a consumer-supplied id (dev warning otherwise). First render and every `hashchange` (a `window` listener in an `afterRenderEffect` keyed on `deepLink`): `#id` opens, any other hash closes an open Reveal (Foundation's `_handleState`). Open writes and close clears the hash with `replaceState(history.state, ...)`, or `pushState` under `updateHistory`, passing `history.state` through as the Tabs spec does. Source: Foundation `open()`, `close()`, `_handleState`; BB 1.5 ids, 1.11 decision 9; Tabs deep-linking rules.
16. Q: `resetOnClose`, `appendTo`, `additionalOverlayClasses`, `showDelay`, `hideDelay`? A: All dropped. `resetOnClose` re-parses `innerHTML`, which destroys Angular bindings; content that must reset is Lazy content under `@if (reveal.isOpen())`. `appendTo`: the top layer needs no move. `additionalOverlayClasses`: no overlay element exists; classes go on the dialog and style `.reveal.<class>::backdrop`. The delays: timing belongs to CSS. Source: BB 1.4 dropped list; R:disclosure "Behaviour that only jQuery makes easy".
17. Q: `vOffset`/`hOffset` `'auto'`, the prototype's OPEN FOR HUMAN item with options (a) CSS `top: 100px`, (b) a measured port, (c) drop both? A: A fourth option, Foundation's placement in CSS: at medium and up, `.reveal[open]:not(.full) { top: 25%; translate: 0 -25% }` is exactly Foundation's `(viewport height - modal height) / 4`, recomputed by the browser on resize and content change, with no measurement and nothing to hydrate. Numeric values are written by the directive as custom properties (`--nfs-reveal-top`, `--nfs-reveal-shift`, `--nfs-reveal-left`) that the same rule reads, and apply at medium and up only, so the full-screen box below medium is never pushed out of the viewport (Foundation's inline `top` did that, which a dialog that scrolls itself cannot tolerate). The tall-modal case differs from Foundation by design: the box is capped at `100% - 2 * min(100px, 10%)` (rule 4, Foundation's own tall offset mirrored) and so sits at half that offset from the top; Foundation let its overlay scroll instead. Why not (a): BB 1.4 keeps Foundation defaults, and `top: 100px` is not where Foundation 6.9 puts a modal. Why not (b): layout reads and two observers for what CSS computes. Why not (c): Foundation Options become inputs unless jQuery-only (BB 1.4). `translate` and `min()` are Baseline widely available well before 2026-05-07. The rendering of the rule in three engines (parity, text crispness at fractional offsets, composition with `transform` keyframes) is graduated under Prototype needed; the fallback is (b). Source: Foundation `_updatePosition`; R:disclosure Options; prototype OPEN FOR HUMAN 1 and its Triage row; BB 1.4, 1.13.
18. Q: `role`? A: `'dialog' | 'alertdialog'` input, default `'dialog'`; only `'alertdialog'` renders `role` (the element's implicit role covers `'dialog'`); an alert dialog without `aria-describedby` warns in dev mode. Source: ADR 0007; R:apg Reveal and Alert Dialog; CDK `DialogRole`.
19. Q: Accessible name and description inputs? A: None: the consumer writes `aria-labelledby`, `aria-label`, and `aria-describedby` on the `<dialog>` they own, as the Tabs spec does for its list; dev warning when the name is missing. `aria-modal` is never set (native modal state), `aria-hidden` never, `tabindex` never (HTML forbids it on `<dialog>`; dev warning). Source: BB 1.10; Tabs Material comparison; R:platform 1 known gaps.
20. Q: `autoFocus`? A: `'first-tabbable'` (default) | `'first-heading'` | selector | `false`; Material's `'dialog'` is not offered (APG: never focus the dialog element). `'first-tabbable'` honours a focusable descendant with `autofocus` first, the platform's own rule, then the first tabbable in sequential order by `InteractivityChecker`; a non-focusable heading or selector target gets a temporary `tabindex="-1"` removed on blur (CDK's mechanism); `false` leaves the browser's dialog focusing steps alone. The directive removes its host's `autofocus` attribute before every show, because a static `autoFocus="..."` is the HTML `autofocus` attribute and makes Firefox and WebKit focus the dialog itself. Source: CDK `_trapFocus`; R:apg Reveal focus rules; prototype static `autoFocus` rows and Triage.
21. Q: `restoreFocus`? A: CDK's `boolean | string | HTMLElement`, default `true`: the `trigger` from `open(trigger)` (WebKit does not focus a button on mouse click), else the element focused at open; moved only when focus is inside the dialog, on it, on `body`, or nowhere (CDK's guard, so a non-modal Reveal closed by focus moving away does not pull focus back); after the Scroll lock restored the page position. When the target is disconnected or unfocusable and sat inside a Reveal this one's opening closed, the target becomes that Reveal's restore target, up the chain (the prototype's unbuilt fallback; the `reveal--replace` story and a browser-level test check it). Source: CDK `_restoreFocus`; prototype restore and `multipleOpened: false` rows and Triage.
22. Q: Tab wrap? A: Modal only, on every Tab and Shift+Tab, through the tabbables in sequential focus order (positive `tabindex` first, then document order; one stop per radio group), wrapping; focus on the dialog or `body` goes to the first or last. The prototype's every-Tab rule is kept because WebKit puts the dialog element in its Tab order and skips links; the order and radio-group refinements match native sequential navigation. CDK `FocusTrap` does not fit: its sentinels are inserted outside the element, in the inert page. Source: prototype Tab rows and Triage; APG keyboard table; CDK `FocusTrap` anchors.
23. Q: Scroll lock? A: Ported: the first modal writes `top: -scrollTop` (when the document is taller than the viewport), `zf-has-scroll`, and `is-reveal-open` on the document element, and Foundation's Sass locks; the last modal to close removes them and scrolls back before focus is restored; destroy releases it. Modal only: Foundation also locked for non-modal Reveals, but a non-modal dialog leaves the page usable, so it stays scrollable. Source: prototype scroll rows and "Scroll lock" decision; audit 0002 M10 (settled: port it); Foundation `_disableScroll`, `_enableScroll`, `_addGlobalClasses`; BB 1.9 restore globals.
24. Q: Custom CSS? A: The prototype's six rules unchanged except rule 4's value (`calc(100% - 2 * var(--nfs-reveal-top, min(100px, 10%)))` instead of `calc(100% - 200px)`, following decision 17), plus rule 7 for the placement. Foundation's size classes, `.full`, full screen below medium, `.collapse`, `.without-overlay`, and the scroll-lock rules are reused. Source: prototype "Custom CSS"; BB 1.13; AGENTS.md Styling Guidelines.
25. Q: Animation mechanics? A: Motion classes from `animationIn`/`animationOut` (default empty, Foundation's default, so no animation unless set), bound with Foundation's own State class names `.is-opening`/`.is-closing` during a `linkedSignal` phase; the backdrop fades through `nfs-reveal-backdrop-in/out` keyframes keyed on those classes, which `nfs-motion` gains; completion is the Toggler's measured longest animation, then `animationend`/`animationcancel` filtered by target, empty `pseudoElement`, and the host's measured names (WebKit reports backdrop events with `pseudoElement: ''`), else measured length plus 100 ms outside the zone; `dialog.close()` is called inside the completion callback so nothing flashes; reduced motion is `nfs-motion`'s 1 ms; `nfsAnimationsToken` disables; the phase starts idle, so open-by-default appears without an enter animation. Source: ADR 0003; BB 1.6 rules 1, 4, 5; Toggler D8; prototype exit rows; Foundation `.is-opening` (Dropdown) and `.is-closing` (Drilldown); hydration prototype.
26. Q: Dev warning for Motion UI transition class names? A: Yes, once, class applied unchanged, the orchestrator's default. Source: Motion prototype orchestrator note and Triage 2.
27. Q: Motion UI `fast`/`slow` speed modifiers? A: Not supported (`nfs-motion` has one duration); consumers write their own keyframe class. Source: [Sass packaging for the new library](57-sass-packaging.md) decision 16; Foundation's `.fast`/`.slow` copy to the overlay.
28. Q: Reduced motion through the Breakpoint service? A: No: the CSS 1 ms override keeps `animationend` firing, so `reducedMotion()` is not read. Source: BB 1.6 rule 5; Motion prototype rule 5 confirmation.
29. Q: Rendering modes? A: Server HTML is the closed dialog with its content and nothing bound to `open`, whatever `isOpen` is; open-by-default calls `showModal()` in the first `afterRenderEffect` run after hydration; no JavaScript means closed. A pre-hydration Trigger click replays and opens with focus inside (no user activation needed). Pre-hydration Escape is lost and harmless. Trigger and Reveal share one hydration boundary; `hydrate never` leaves it closed; prerendering is identical. Rendering `open` on the server was rejected: it is non-modal, and `showModal()` cannot promote a dialog already open by attribute. Source: ADR 0008; R:rendering 7 and its Reveal checklist row; BB Table B; prototype server and open-by-default rows; seam prototype.
30. Q: Render hooks and effects? A: `afterRenderEffect` with `earlyRead` (focus and scroll snapshot), `write` (Scroll lock, `autofocus` removal, show or close, focus, history), `read` (measure animations, start the wait) for the open and close sync; another `afterRenderEffect` keyed on `deepLink` for the `hashchange` listener; `afterNextRender` for dev checks; `nfsLightDismiss` registers in its own render callback. No `effect` (everything touches the DOM or browser globals, and effects run on the server), no `afterEveryRender`. Source: BB 1.5; Angular `afterRenderEffect` phases in the 22.2 source; Anchored pane D21.
31. Q: `injectAsync`? A: Not used: nothing loads only after an interaction; the directive must be live at hydration to receive a replayed Trigger click, and `InteractivityChecker` is needed in the same callback that opens the dialog. The entry point lets a consumer `@defer` it. Source: Anchored pane D20; BB 1.11 decision 7.
32. Q: `<form method="dialog">`? A: The native `close` event re-syncs `isOpen`, the stack, the Scroll lock, focus, and history, and `closed` carries `returnValue`; this path has no exit animation and no predicate, documented, and `nfsClose` is the animated, vetoable close button. Intercepting `submit` was rejected because it collides with form libraries' own submit handling. Source: Triggers spec Further Notes (the question was left to this spec).
33. Q: WCAG 2.2 AA 1.3.1 and 4.1.2? A: Native role and modal state, required consumer name (and description for alert dialogs), dev checks 1 and 2, axe with the dialog open; the announcement itself is human-only. Source: R:apg Reveal; ADR 0022.
34. Q: WCAG 1.4.3? A: Rule 5 inherits the body colour; Foundation's defaults pass; axe `color-contrast` enforces. Source: prototype text-colour row.
35. Q: WCAG 1.4.11? A: The close glyph (`$closebutton-color`, `$closebutton-color-hover`) and the dialog's edge against the dimmed page (`$reveal-background` against `$reveal-overlay-background` over `$body-background`) at 3:1; defaults 3.45:1, 19.63:1, 3.17:1 (prototype); `@warn` at compile time through Foundation's `color-contrast()`, because axe has no 1.4.11 rule and the defaults pass (the Responsive Toggle spec's `@warn` precedent). Source: prototype contrast rows; ADR 0022; BB 1.10.

### Proposed glossary terms (CONTEXT-FORMAT; orchestrator applies)

**Scroll lock**:
Keeping the page behind an open modal Reveal from scrolling, through Foundation's `html.is-reveal-open` rule plus the scroll offset the library writes when the first modal opens and restores when the last one closes.
_Avoid_: body lock, scroll blocking, block scroll strategy (CDK's)

**Backdrop press**:
A pointer press that starts and ends on a modal Reveal's `::backdrop`, which closes it when `closeOnClick` is on; distinct from Light dismiss, which non-modal content uses.
_Avoid_: overlay click, outside click, backdrop click

Amended **Light dismiss**:
Closing an Anchored pane, an open submenu, or a non-modal Reveal on an outside pointer press, on Escape, when focus moves outside it, or when a sibling of the same kind opens; the replacement for Foundation's `closeme.zf.*` broadcast and body click handlers.
_Avoid_: click-outside, closeme, auto-close, Backdrop press (which is a modal Reveal's)
