## Question

## WCAG 2.2 AA guard (user decision, 2026-09-26)

Every directive and component complies with WCAG 2.2 AA; see the map's Accessibility preference and [ADR 0022](../adr/0022-wcag-2-2-aa-enforcement.md). The spec carries a criteria subsection under Implementation Decisions naming the 2.2 AA criteria this plugin touches (at least 1.4.3, 1.4.11, 2.4.7, 2.4.11, 2.5.8, 4.1.2, and, for overlays and hover content, 1.4.13) and how each is met, as requirements, never recommendations. Where a Foundation default fails a criterion, the spec states the Sass settings the consumer must set or the smallest custom rule the `nfs-<plugin>` mixin adds, with the reason. The story axe gate runs with the WCAG 2.2 AA tags, and the decision log records each criterion addressed.

## Note from the research repairs (2026-09-25)

Audit 0001 finding H5 corrected the Foundation facts in `research/angular-material-reference.md` that this ticket reads. Take these as given:

- Foundation appends the tip to `document.body` and positions it with inline offsets from Positionable (`foundation.tooltip.js:49-57`); the `.tooltip` CSS is not positioned relative to the trigger. The building-blocks decision creates the tip as a sibling of the trigger instead; the spec must reconcile that with ADR 0002 (in-place measured positioning) and state where the tip lives and what its containing block is, or raise it under `## Prototype needed` if sources cannot settle it.

## Answer

Spec: [specs/tooltip.md](../specs/tooltip.md). Resolved 2026-09-26 by self-grilling (AFK), both sides played against the sources below, under the user's WCAG 2.2 AA rule, the Foundation SCSS reuse rule, and the triage rule for human-only items.

Gist: one attribute directive, `[nfsTooltip]` (`NfsTooltip`, `exportAs: 'nfsTooltip'`), on an interactive host the consumer writes, with the text as its value or from the static `title`; it always adds `.has-tip`, keeps the text in `title` until the first show, and is an Openable with Trigger role `'none'`. On first show an `afterRenderEffect` creates the internal `nfs-tooltip-tip` component (`.tooltip`, `role="tooltip"`, generated `nfs-tooltip-` id) through the directive's `ViewContainerRef` as the host's next sibling and keeps it; the same pass removes `title` and adds the tip id to `aria-describedby` (after any static consumer value). The tip is placed by `nfsPositioner` (`autoPosition` from the host's legacy static class else `top`, `autoAlignment: 'center'`, pip 14 x 12, `allowBottomOverlap: false`), dismissed by `nfsLightDismiss` (group `'nfs-tooltip'`, pointer rule always on, external Triggers counted inside through `registerTrigger`), and hover-opened by `nfsHoverIntent` (`hoverDelay` 200, 100 ms close floor, tip in the Hover region). Keyboard focus opens at once through a replay-safe `focusin` host listener (`document.activeElement` plus `:focus-visible`); a pointer click opens and pins it through code-added `click`/`pointerdown` listeners (no `jsaction`, safe on links); `focusout` closes. Show and hide use `nfs-fade-in`/`nfs-fade-out` bound for the phase, completion from the measured computed animation, `hidden` when closed. Every Foundation option is kept with its default except `fadeInDuration`, `fadeOutDuration`, `tooltipClass`, `triggerClass`, `template`, `allowHtml`, and the dead `touchCloseText`; `templateClasses` is kept. No library CSS, loaded eagerly, nothing open for decision; one screen-reader check stays human-only by kind.

### Decision log

Sources: FS = the Foundation 6.9.0 clone (`js/foundation.tooltip.js`, `scss/components/_tooltip.scss`, `scss/components/_button-group.scss`, `docs/pages/tooltip.md`); NG = the Angular 22.2.x clone; NGC = the components 22.2.x clone (`src/material/tooltip/tooltip.ts`); APG = `aria-practices/content/patterns/tooltip/tooltip-pattern.html`; ARIA = the WAI-ARIA clone, `tooltip` role (`index.html:11278`); R:x = research files by building-blocks' short names; BB = `building-blocks.md`; AP = [Spec: Anchored pane (shared utility)](55-spec-anchored-pane.md) and `specs/anchored-pane.md`; TRG = [Spec: Triggers (shared utility)](54-spec-triggers.md); BP = [Spec: Breakpoint service (shared utility)](53-spec-breakpoint-service.md); BTN = [Spec: Button](37-spec-button.md); P44 = [Prototype: Anchored pane positioning, measured Positionable port versus CDK Overlay](44-prototype-anchored-pane.md); P47 = [Prototype: `animate.enter` and `animate.leave` with Motion UI transition classes](47-prototype-motion-ui-animate-enter.md); P52 = [Prototype: `animate.enter` at hydration](52-prototype-animate-enter-hydration.md); TOG = [Spec: Toggler](17-spec-toggler.md).

Round 1 (no prerequisites): Foundation's contract.

1. **What are the real options?** `Tooltip.defaults` (FS `foundation.tooltip.js:301-457`): `hoverDelay` 200, `fadeInDuration` 150, `fadeOutDuration` 150, `disableHover` false, `disableForTouch` false, `templateClasses` '', `tooltipClass` 'tooltip', `triggerClass` 'has-tip', `showOn` 'small', `template` '', `tipText` '', `touchCloseText` 'Tap to close.', `clickOpen` true, `position` 'auto', `alignment` 'auto', `allowOverlap` false, `allowBottomOverlap` false, `vOffset` 0, `hOffset` 0, `tooltipHeight` 14, `tooltipWidth` 12, `allowHtml` false. The charting ticket's `positionClass` does not exist (audit 0001 H6). R:positioned Tooltip 3 agrees.
2. **Events and methods?** `closeme.zf.tooltip`, `show.zf.tooltip` (synchronous, before the fade), `hide.zf.tooltip` (as the fade-out starts), `init`/`destroyed`; methods `show()`, `hide()`, `toggle()`, `destroy()` (FS `:132-185, 278-298`; R:positioned Tooltip 4, 5).
3. **Where does Foundation put the tip and how is it positioned?** Built at init, appended to `document.body`, hidden with jQuery, shown with a `visibility: hidden` measure then `fadeIn`, positioned with Positionable's inline offsets (FS `:47-57, 132-164`; audit 0001 H5). Default position resolves to `top` via `_getDefaultPosition` (legacy class, else `top`), alignment `center` (FS `:71-83`); the docs' "appears below" is wrong (R:positioned Tooltip 2).
4. **`title` and ARIA?** `title` emptied at init and restored on destroy; `aria-describedby` reuses an existing value as the tip id; tip `role="tooltip"`, `aria-hidden` toggled; no Escape, no keydown (FS `:44-65, 105-115, 291`; R:positioned Tooltip 6).
5. **Sass contract?** `.has-tip { position: relative; display: inline-block; border-bottom; font-weight; cursor: help }`; `.tooltip { position: absolute; top: calc(100% + pip); z-index: 1200; max-width: 10rem }` with pip classes `.top/.bottom/.left/.right` and `.align-*`; no hidden rule and no `display` (FS `_tooltip.scss:53-160`).
6. **What is settled upstream?** BB 1.1 case 3 and ADR 0001 (directive plus internal tip component created on first show and kept), BB 1.6 rule 1 after audit 0002 H3 (State class animation with `nfs-fade-in`/`nfs-fade-out`, `aria-describedby` only once the tip exists), ADR 0002, ADR 0003, ADR 0008, ADR 0013, ADR 0022, ADR 0024, AP (the three utility parts, the clip accepted), TRG (`triggerRole: 'none'`, `skipSelf`), BP (`is()`), BTN (`disabledInteractive`).

Round 2 (depends on 1-6): shape.

7. **Directive or component, and on which element?** A directive on the trigger plus an internal component for the tip (BB 1.1 case 3; Material's `matTooltip` shape, NGC `tooltip.ts:186-194, 958-967`). The Foundation class contract is honoured by `.has-tip` on the host and `.tooltip` plus pip classes on the tip.
8. **Selector, class, token names?** `[nfsTooltip]`, `NfsTooltip`, `exportAs: 'nfsTooltip'`; tip `nfs-tooltip-tip`, `NfsTooltipTip`; `nfsTooltipDefaultsToken`; internal `nfsTooltipToken` (ADR 0009, BB 1.3).
9. **Where does the tip live, and what is its containing block (the research-repair note)?** The host's next sibling, created by `ViewContainerRef.createComponent` on the directive's container, the mechanism P44 used (`prototypes/anchored-pane/src/app/anchored-pane.ts:256-268`). Its containing block is the host's containing block for absolute positioning, not `.has-tip` (whose `position: relative` applies only to the host); the Positioner measures that origin and writes inline `top`/`left`, Foundation's own mechanism. This reconciles with ADR 0002: the tip is created in place on the client and never moved (AP Rendered output, last paragraph; AP decision 24). Settled from sources; no prototype needed.
10. **Why not a child of the host, or `body`?** A child would join a `<button>`'s name from content and cannot exist in an `<input>`; `body` would put tips inside a modal `<dialog>` behind its top layer and is node creation outside the component tree (ADR 0008 Considered options; R:rendering 7 rule 4). Sibling it is, with documented limits (decision 43).
11. **Implementation level?** Custom Angular with platform measurement (ADR 0002): `popover="hint"` has no WebKit release, `popover` and anchor positioning are out of target (R:platform 2, 3, plugin table row Tooltip); Aria has no tooltip (BB 1.2; R:aria 10); CDK Overlay rejected by P44 (tip moved 209-254 px, `max-width` replaced). CDK used: `_IdGenerator`, `InteractivityChecker` (dev check), and through AP `Directionality`, `hasModifierKey`. Fallback: none.

Round 3 (depends on 7-11): text, title, ARIA.

12. **Text source?** One input, property `tipText` aliased `nfsTooltip` (Foundation's option name, Material's selector-named message, NGC `tooltip.ts:230-362`); a non-empty value wins, else the static `title` via `HostAttributeToken` (Foundation's fallback, FS `:46`). A dynamic `[title]` on the host is not supported (the directive owns `title`).
13. **When does `title` move off the host?** At first show, not at construction. Before that the host binds `title` to the text, so the accessible description exists in server HTML, before first focus, without JavaScript, and in `hydrate never` blocks (accname: `title` is the description when no `aria-describedby` exists and it is not the name). At first show the same render pass removes `title`, binds `aria-describedby`, and inserts the tip; afterwards the kept (hidden) tip is the description, which matches Material's always-present description (`AriaDescriber`, R:material 4) without its hidden copy, and meets ARIA's "referenced ... before or at the time the tooltip is displayed" (ARIA `tooltip`). BB Table B's "no `aria-describedby` in server HTML" holds. Costs, documented: before first show a mouse user may see the browser's own `title` tooltip where ours does not open (`disableHover`, below `showOn`, a `hoverDelay` longer than the browser's delay). Triage 3.
14. **Existing `aria-describedby`?** Kept first, the tip id appended (Material appends through `AriaDescriber`); Foundation's reuse of it as the tip id dropped. Dynamic consumer bindings lose to the directive's host binding (angular-developer `host-elements.md`, Binding Collisions) and are unsupported.
15. **Tip ARIA?** `role="tooltip"` static, generated id, `hidden` when closed; never `aria-hidden` (BB 1.10), never `aria-label` (ARIA prohibits naming a tooltip), never focusable (APG). Content is a text interpolation, never HTML.
16. **Trigger ARIA?** None beyond `aria-describedby`: `triggerRole: 'none'` (TRG ARIA section; ARIA says a tooltip is not a popup), so neither the host nor an external Trigger renders `aria-expanded`/`aria-haspopup`/`aria-controls`.
17. **Tip id?** `_IdGenerator` prefix `nfs-tooltip-`, generated once; it never appears in server HTML, so server and client cannot disagree (BB 1.5 ids). Not an input.
18. **Non-interactive hosts (BB Part 4 OPEN FOR HUMAN 2)?** Interactive hosts only: a native `button`, `a[href]`, `input` (not hidden), `select`, `textarea`, `summary`, or an element with an interactive ARIA role. Enforced as a development-mode warning, no production behaviour change; the defined-term recipe is a `button.has-tip` (Foundation's normalize resets buttons). Sources: APG (the pattern presumes a natively focusable trigger, R:apg Tooltip delta), Material's tooltip guidance, WCAG 2.1.1. Triage 1.
19. **Disabled hosts?** A natively disabled button cannot take focus, so the dev check says "use `disabledInteractive`" (BTN user story 15, API table).
20. **Name-versus-description guard?** A dev warning when the host has no name of its own (icon button without `aria-label`), because the tip is a description (WCAG 4.1.2); Foundation's init-time `title` blanking removed such names.

Round 4 (depends on 12-20): opening and closing.

21. **Hover?** `nfsHoverIntent` on the host with the tip as `pane`, `enabled = !disableHover && text`, `openDelay = hoverDelay` (200), `closeDelay` 0 (the helper's 100 ms floor applies), per-event touch filter (AP Hover intent, AP decision 37). The close callback is ignored while pinned or while the host matches `:focus-visible` (APG: a focus-opened tip closes on blur, not on mouse out).
22. **Keyboard focus?** A `focusin` host listener opens at once when `document.activeElement` is the host and it matches `:focus-visible` (Baseline since Safari 15.4). The live check makes replay safe (BB 1.11 decision 5; R:rendering 4 and checklist row Tooltip); `:focus-visible` stops a mouse-click focus from opening when `clickOpen` is off (Foundation's `isClick` bookkeeping, FS `:224-265`; Material's keyboard-origin rule, NGC `tooltip.ts:412-422`). CDK `FocusMonitor` rejected: a service for what one selector answers.
23. **`clickOpen`?** Kept, default true: a pointer click (`event.detail > 0`) opens and pins; a keyboard activation (`detail` 0) changes nothing because it is the host's own action; a click on an open tip pins it and never toggles it closed (Foundation's second `mousedown` does nothing, FS `:226-229`).
24. **Host `click` listener or code-added?** Code-added `click` plus `pointerdown` (for the pointer type) in `afterNextRender`. A host `click` listener would annotate link hosts with `jsaction`, and Angular's dispatcher cancels native navigation of such links inside dehydrated blocks (BB 1.11 decision 5; BTN D7 reasoning); a replayed stale click-open is not wanted for supplementary content. `pointerdown` alone rejected: a touch scroll over the host would open it (ADR 0024 reasoning).
25. **`disableForTouch`?** Kept with a per-press meaning: a touch press never opens the tip; mouse and keyboard keep working on touch-screen laptops. The iOS first-tap problem that motivated it is gone with the per-event touch filter (AP decision 36). `click` is not a `PointerEvent` in every target browser, hence the recorded `pointerdown` type.
26. **Light dismiss options?** `group: 'nfs-tooltip'` (replaces `closeme.zf.tooltip`), `pane` = the tip, `triggers` = host plus registered external Triggers, entry added only once the tip exists. `outsidePress` left at its default (always on): hover-opened and focus-opened tips close anyway when the pointer or focus leaves, so this equals AP's "on while click-opened" mapping with fewer states. Escape topmost, the focus rule, and the sibling rule unchanged (ADR 0024).
27. **Why a `focusout` host listener too?** Focus leaving for the page body (a click on plain text) or another window fires no `focusin`, which the Light dismiss focus rule needs (AP decision 30); APG: "dismissed when it no longer has focus".
28. **Pinned state?** Set by a press or `open()`/`toggle()`, cleared by every close; it only blocks the hover-leave close. Escape, outside press, and focus leaving still close: Foundation's "until you click somewhere else" (FS docs `:48`) plus WCAG 1.4.13 dismissible.
29. **`showOn`?** `NfsMediaQuery.is(showOn())` at open time (BP API table; `'all'` true), as Foundation checks only in `show()` (FS `:133-136`); a breakpoint change while open does not close. Live and replayed open requests happen after the service goes live (BP Rendering modes, replay bullet). A direct model write bypasses the gate.
30. **Programmatic and external Triggers?** `open(trigger?)`, `close(result?)`, `toggle(trigger?)` (BB 1.3); `registerTrigger` implemented so an info button with `[nfsToggle]="tip"` counts as inside and toggles rather than closing and reopening (AP rule 1; TRG consumers table row Tooltip). The anchor is always the host.
31. **Empty text?** The off switch (Material's no-message behaviour): open requests ignored; the shown state is `isOpen && text`, so clearing the text while open hides the tip and emits `closed` while `isOpen` keeps the requested value. A `disabled` input rejected as a second off switch.

Round 5 (depends on 21-31): API, defaults, dropped options.

32. **Inputs and defaults?** Every kept Option is an `input()` with Foundation's default and `numberAttribute`/`booleanAttribute` transforms, seeded from `nfsTooltipDefaultsToken` (Shape B, BB 1.4). `isOpen` is a `model(false)`; `opened`/`closed` are Completion outputs (BB 1.4 mapping of `show/hide.zf.tooltip`).
33. **Legacy position classes?** Kept as the `auto` default, read once from the static `class` with `HostAttributeToken` (FS `:71-79`; the docs examples use `class="top"`, `.right`, `.left`; AP decision 12 left it to this spec).
34. **Dropped options and why?** `fadeInDuration`/`fadeOutDuration` (CSS owns timing, BB 1.4; an inline `animation-duration` would override the reduced-motion rule), `tooltipClass` and `triggerClass` (the classes are the contract, BB 1.4), `template` and `allowHtml` (HTML strings, XSS per FS `:450-456`; rich content is a Dropdown pane per APG), `touchCloseText` (never read, R:positioned Tooltip 3).
35. **`templateClasses`?** Kept, against BB 1.4's list: the consumer does not author the tip, so this is the only per-tooltip styling hook; Material has `matTooltipClass`. Proposed building-blocks change 1.
36. **`.has-tip` always, or opt-out?** Always, as Foundation's default `triggerClass`; a `.button` host gets Foundation's dotted underline and help cursor exactly as on Foundation's docs page. Triage 2.
37. **`tooltipHeight`/`tooltipWidth`?** Kept (Positioner `pip`); they match `$tooltip-pip-*` by hand as in Foundation, best set once through the Defaults token. Deriving them from the pip's computed style rejected as cleverness Foundation never had.

Round 6 (depends on 32-37): animation, hooks, loading.

38. **Animation mechanics?** Kept tip, so State class animation (BB 1.6 rule 1, ADR 0003; never `animate.enter`, P52): `nfs-fade-in` while entering, `nfs-fade-out` while leaving, `hidden` when idle and closed, phases in a `linkedSignal` (TOG Animation). Keyframe classes confirmed in three engines with reduced motion (P47).
39. **Duration?** The `nfs-motion` `$duration` (500 ms default, [Sass packaging for the new library](57-sass-packaging.md) decision 16), not Foundation's 150 ms; no library CSS. A consumer recipe for 150 ms (with its own reduced-motion rule, because the higher specificity beats the mixin's) is in the Sass subsection. Triage 4.
40. **Completion?** Measured computed `animation-*` after the class is bound, longest finite animation, `animationend`/`animationcancel` filtered by target, fallback timer measured plus 100 ms outside the zone, measured zero completes at once (TOG's refinement of BB 1.6 rule 1; P47's note on missing stylesheets). `nfsAnimationsToken` disables the classes.
41. **Render hooks?** Tip creation in an `afterRenderEffect` `write` phase (one path for handlers, methods, and bound models; never on the server; `effect` rejected because it runs on the server). A view-bound after-render sequence is added when its view refreshes, not deferred to a later tick (NG `render3/after_render/manager.ts` `register`: sequences with a `view` go to `AFTER_RENDER_SEQUENCES_TO_ADD`; only view-less ones registered during execution are deferred), and `ApplicationRef.tick()` re-runs while views are dirty (AP decision 18), so the tip's Positioner places it before its first painted frame; Aria's `DeferredContent` also creates views from `afterRenderEffect` (BB 1.11 decision 2). Completion in an `afterRenderEffect` `read` phase; code-added listeners and dev checks in `afterNextRender`; `afterEveryRender` rejected (runs after every change detection for every tooltip); no `effect`.
42. **`injectAsync`?** Not applicable and not wanted: it resolves auto-provided service tokens (NG `di/inject_async.ts:19-58`), and the tip is a component (a bare dynamic `import()` would be the lazy route); a fetch after `hoverDelay`, or on a keyboard focus that shows at once, would delay the first tip and split the one-pass `title`/`aria-describedby` swap; the tip is a few lines; the entry point already splits under a consumer `@defer` (AP D20 for the utility).
43. **Documented limits of the sibling tip?** Clipping by a positioned `overflow` ancestor and `z-index` bounded by ancestor stacking contexts (P44 row "Long tooltip inside a positioned scroller"; decided in AP Triage 2); structural pseudo-classes and sibling combinators among the host's siblings see the tip once it exists: Foundation's `.button-group` `:last-child` margin and radius, `.no-gaps` `+` borders, float-mode `.expanded` `nth-last-child` widths (FS `_button-group.scss:55-140`), a 1 px margin change with Foundation's defaults (`$global-flexbox`, `$buttongroup-radius-on-each: true`, FS `settings/_settings.scss:327-330`); an ancestor named from content (`label`) includes the tip text while shown (dev warning). Inside a modal `<dialog>` the sibling tip is in the top layer with it, a benefit over `body`. Triage 5.

Round 7 (depends on everything above): WCAG, rendering modes, tests.

44. **WCAG 1.4.13?** Dismissible: Escape from anywhere (ADR 0024), no reopen until re-entry or refocus (AP hover intent). Hoverable: tip in the Hover region, 100 ms floor. Persistent: no auto-hide. The browser's `title` tooltip is exempt (user-agent controlled). Foundation fails all three (FS `:209-214`; R:positioned "Nothing is bound to the tip element itself").
45. **WCAG 1.4.3?** Foundation's defaults pass: `#fefefe` on `#0a0a0a`, about 19.6:1; consumer settings are gated by axe `color-contrast` in stories with the tip open (ADR 0018 rule set); no compile-time check, because ADR 0022 reserves those for criteria axe cannot check.
46. **WCAG 1.4.11?** Not applicable to the tip (not a UI component, no state); `.has-tip`'s border is about 3.4:1 on white anyway; the host's indicators are the host spec's.
47. **WCAG 2.4.7?** Passes with Foundation's defaults: `.has-tip` sets no outline; outlines are removed only under what-input attributes the library never loads (TOG WCAG table, same reasoning).
48. **WCAG 2.4.11?** The tip is placed beside the host for non-negative offsets (Positioner warning below 0); focus leaving closes it; the focus rule closes hover-opened tips when focus moves elsewhere; a hover tip over an earlier-focused control is dismissible with Escape without moving focus.
49. **WCAG 2.5.8?** Not applicable to the tip (not a target); the directive adds no target; `.button` hosts pass (BTN); inline links meet the inline exception; axe `target-size` runs in every story.

### Triage

Rule (map, Orchestration rules, "Triage of human-only items"): impact HIGH when hard to reverse; confidence NOT HIGH when the default is bare, carried from a prototype without deliberation, or against the research or ADRs. Only HIGH impact with NOT-HIGH confidence stays OPEN FOR HUMAN.

1. **Tooltips on non-interactive text (BB Part 4 OPEN FOR HUMAN 2).** Options: (a) interactive hosts only, development warning, no production change (applied); (b) refuse to open on non-interactive hosts; (c) support focusable `span[tabindex]` hosts as Foundation's docs do. Impact: not HIGH. Starting strict and relaxing later breaks no one (a warning can be removed or an opt-in added), while starting permissive and tightening later would be breaking; no public API depends on the choice. Confidence: HIGH. The APG pattern presumes a natively focusable trigger and the research recorded Foundation's focusable `span` as a role-less focusable element the APG never shows (R:apg Tooltip delta); WCAG 2.1.1 fails for a non-focusable span; Material's guidance agrees; BB's written default is the same. Decided: (a), with the `button.has-tip` recipe for defined terms.
2. **`.has-tip` on every host, no opt-out.** Impact: not HIGH (adding an opt-out input later breaks no one). Confidence: HIGH (Foundation's default `triggerClass`; BB 1.4 drops the Option; BB Table B server output shows `.has-tip`; Foundation's docs render buttons with it). Decided: always added; the look on buttons and inputs is Foundation's, and consumer CSS may override it.
3. **`title` kept until the first show.** Impact: not HIGH. It changes what server HTML carries, but reverting to blanking at construction is one host binding, and no API depends on it. Confidence: HIGH. It follows accname (description from `title`), ARIA's "before or at the time" rule, Material's always-present description, and BB's "no `aria-describedby` in server HTML"; the cost (a possible browser tooltip before first show in three named cases) is documented. Decided.
4. **Fade duration at the `nfs-motion` duration (500 ms default) instead of Foundation's 150 ms.** Impact: not HIGH (a CSS value; a library rule or a new keyframe pair can be added later without an API change). Confidence: HIGH. BB 1.4 drops `fadeInDuration`/`fadeOutDuration`, the Sass packaging decision owns one `$duration`, the brief rules out library CSS beyond the keyframes, and a consumer recipe restores 150 ms. Decided.
5. **Limits of the sibling tip (clip, stacking, sibling pseudo-classes, label names).** Impact: not HIGH (the tip's location is internal and can move to the top layer when `popover="hint"` is in target; AP Triage 2). Confidence: HIGH (the clip was decided in AP Triage 2 from P44 measurements; the pseudo-class and label effects follow from CSS selectors and accname and are small with Foundation's defaults). Decided: documented, with a dev warning for `label` ancestors and an e2e assertion for the clip.

### Proposed glossary terms

### Amendment, 2026-09-27 (Resolve the assistive-technology checks)

From [Resolve the assistive-technology checks](77-evidence-assistive-technology-checks.md), check 6: a spec defect in the description mechanism, fixed with a local description element (variant E). `specs/tooltip.md` was edited to match; spec decision D4 changes.

- OPEN FOR HUMAN item 1 (the screen-reader pass over the `title` to `aria-describedby` switch) is closed. The kept hidden tip did describe the host, but Firefox fired a description change on the focused host at the first show, at every re-show, and on Escape, which NVDA speaks by default, so the text was repeated on first focus, on every return, and on Escape; and a host with a static consumer `aria-describedby` had no tooltip text at first focus in either engine (HTML-AAM: `aria-describedby` is the first applicable description source), which JAWS, Narrator, TalkBack, and VoiceOver, which do not re-announce description changes, then never announce.

Measured by the judge in Chromium and Firefox, three runs: no description-change event in any step, the full description on every focus, the consumer's text first. The element shares its host's inertness and modal subtree, so it survives `showModal()` and the Off-canvas Modal inert set.
