# 122. Re-run: Magellan spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81, 121
Labels: wayfinder:grilling
Map: ../map.md

## Question

What does the [Spec: Magellan](30-spec-magellan.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/magellan.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Magellan](30-spec-magellan.md) and the answer here. Model: Opus 5.5.

## Answer

Model: Opus 5.5

Spec: [specs/magellan.md](../specs/magellan.md), revised in place. Resolved 2026-09-27 by self-grilling (AFK), both sides played against the sources below. The revision is recorded in the [Spec: Magellan](30-spec-magellan.md) as "Amendment, 2026-09-27 (class rule)".

Gist: Magellan has no Structural class and no Variant class, so `NfsMagellan` gains no Variant input and binds nothing on its host; its API, behaviour, ARIA, keyboard, rendering modes, and Story ids are unchanged. Foundation's Menu container becomes `<ul nfsMenu nfsMagellan>`, whose `.menu` and Variant classes (`orientation="vertical"`, `expanded`) the Menu directive binds, written beside `nfsMagellan` rather than hosted (D17, as the Smooth Scroll spec's D13). The marker (`.is-active` on the link and its `li`, `aria-current` on the link) stays a `Renderer2` write after render (D11 reaffirmed): the marked elements carry no library directive and no Structural class that would give them one, and no section is current in server HTML, so a host binding has neither a host nor a first-paint value; the consumer still writes no class. Magellan owns the marker on its tracked links and their list items, so a copied `class="is-active"` is removed by the first client marker write and reported in development (D18, building-blocks 1.4's initial-state rule). Every example and story writes directives only; the guide example's Sticky container moves to the grid cell, which fixes an example that never stuck.

### Decision log

Sources: FS = the Foundation 6.9.0 clone; NG = the Angular 22.2.x clone; ADR 0039, ADR 0040; T = `research/out-of-scope-triage.md`; X = `research/out-of-scope-exclusions.md`; CAT = `research/foundation-component-catalogue.md`; BB = `building-blocks.md` as amended through commit 46b7d0a; SBC = `storybook-conventions.md`; TYP = the Answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md); SS = the Smooth Scroll spec and the Answer of [Re-run: Smooth Scroll spec under the class rule](121-rerun-smooth-scroll-class-rule.md); ST = the Sticky spec; OC = the Off-canvas spec; the spec before this revision is "the spec".

Round 1 (no prerequisites): which classes exist, and who owns them.

1. **Does Magellan have a Foundation class of its own?** One State class, no Structural or Variant class. Its Plugin writes only `activeClass` (`is-active`) on the active link (FS `js/foundation.magellan.js:186-187`, `:220`); its other DOM write is the container's `id`, `data-resize`, and `data-scroll` attributes (`:44`), which the spec drops; Foundation ships no Magellan Sass, and CAT's Magellan row (`:89`) records "no dedicated structural class". So `NfsMagellan` binds no class on its host, has no Variant input, and declares no Variant registry and no Variant property (ADR 0040). Source: FS; CAT; ADR 0039.
2. **Which consumer-written classes did the spec carry?** Rendered HTML: `class="menu expanded"`, `class="menu vertical"`, and the docs' `div.sections` wrapper (FS `docs/pages/magellan.md:24`, `:31`; `.sections` is defined by no Foundation Sass). Usage examples: `grid-x grid-margin-x`, `cell large-3`, `cell large-9`, `sticky-container`, `sticky`, `vertical menu` (guide); `top-bar`, `top-bar-right`, `menu` (landing); `hide-for-large`, `show-for-large`, `vertical menu` (jump select); `vertical menu` (Router). Story `magellan--sticky-top-bar`: "a sticky `.top-bar`". Prose that left classes to the consumer: the class mapping ("stay the consumer's Variant classes (ADR 0010)"), the 2.5.8 recipe `.menu.simple.vertical a { ... }`, and Out of Scope's "style `.is-active` themselves". No example wrote a State class: the marker was already Magellan's. Source: the spec.
3. **Who binds them?** `.menu`: `ul[nfsMenu]` (T section 2, "Menu markup (G1)"; [Spec: Menu](85-spec-menu.md), resolved during this wave with the same names; the names SS uses). `.vertical`: the Menu's `orientation` (BB 1.4 naming rule 2; TYP: "`vertical medium-horizontal` becomes `[orientation]` rules"). `.expanded`, `.simple`: booleans named after their classes (BB 1.4 naming rule 4; ADR 0040 lists `.expanded` among single modifier classes). `.top-bar`, `.top-bar-right`: `[nfsTopBar]`, `[nfsTopBarRight]` (T section 2, Top Bar row). `.sticky`, `.sticky-container`: `nfsSticky`, `nfsStickyContainer` (ST `:100-101`, published). `.grid-x`, `.cell`, `.large-3`: `NfsGridX`, `NfsCell`, and `[size]="{large: 3}"` (BB 1.3's naming rule and alias `NfsCellSize`; BB 1.4: "`.medium-6` is `[size]="{medium: 6}"`"; [Spec: XY Grid](99-spec-xy-grid.md), open). The grid gutter is left out of the example rather than guessing its input. Visibility classes: removed from the example, which points to [Spec: Visibility Classes](104-spec-visibility-classes.md) for their directives, so this spec depends on no name that spec has not given. `.sections`: not a Foundation class; replaced by `<main>`. Source: T; BB 1.3, 1.4; ST; TYP.
4. **Do the exclusion rows for this spec change?** No. MG1 to MG10 (X `:159-168`) all sit under T's "Reasons that still hold" (T section 3: MG1 browser target; MG2 class-name Options; MG3 and MG10 replaced by a named mechanism; MG4, MG7, MG8, MG9 design reasons; MG5 and MG6 not a Foundation feature), and none rests on a class being CSS-only; T names no dissent for Magellan. MG2 (`activeClass` dropped) gains a reason, ADR 0039's follow-up that no class name is an input value; MG8 (styling the marker for custom navigations) holds, reworded to `a[aria-current]` (decision 12). Source: X; T; ADR 0039.
5. **What reaches server HTML for `<ul nfsMenu expanded nfsMagellan>`?** Static template attributes, directive selectors and static input values included, are set by `setUpAttributes` through `renderer.setAttribute` (NG `packages/core/src/render3/util/attrs_utils.ts:42-73`, re-read), serialised in lowercase, as SS decision 5 records from the Sticky CSS prototype's prerendered output. Host class bindings render on the server (BB 1.11 decision 1), so `class="menu expanded"` is in the server HTML, and Magellan adds only `jsaction`. The spec's Rendered HTML leaves the static attributes out and says so, as SS does. Source: NG; SS; BB 1.11.

Round 2 (depends on 1-5): the marker under the State-class clause, and the composition.

6. **Must the marker become a host binding, since ADR 0039 says "every State class is a host binding" and the ticket asks that every State class "stays or becomes a host binding"?** For: the literal clause; one mechanism across specs; a host binding would also strip a copied class on the server (BB 1.4). The only way to get it is a link directive and a list-item directive (`a[nfsMagellanLink]`, `li[nfsMagellanItem]`) reading `active` through a Parent token, since a host binding reaches only its own host. Against: two attributes on every item that Foundation never needed; a forgotten one silently loses the marker; a Parent token for links the spec finds by query (as Smooth Scroll does, and as `@for`-generated tables of contents need nothing for); the `li` of a Menu is the Menu spec's element; and no first-paint gain, since both would render nothing on the server, where no section is current. The clause's own reason (ADR 0039 Consequences: "Host bindings render on the server, so the server HTML still carries every Foundation class") does not apply to a class with no server value. The user's rule, verbatim, is that "All Foundation for Sites and NFS classes are managed by the Angular components/directives" (the Answer of [Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md), decision 1), which the `Renderer2` marker meets: the consumer writes none. ADR 0039 gives directives to Structural classes, and the marked links and list items carry none of Magellan's; BB 1.5 limits `Renderer2` writes to "values host bindings cannot express"; and the bundle already has the same case, OC's `is-off-canvas-open` on `body` ("A directive cannot bind `body`", OC `:119`). `RouterLinkActive` writes its classes and `aria-current` with `Renderer2` too (NG `packages/router/src/directives/router_link_active.ts:236-248`), though on its own host. **Decided: D11 stands**; the clause is read as applying where a library directive hosts the element, and a dated clarification is proposed for ADR 0039 and BB 1.1 so the other re-runs and the consistency review read it the same way. The [Spec: Menu](85-spec-menu.md), resolved while this ticket ran, gives link items no directive of their own (only `li[nfsMenuText]`, for items without a link) and marks a current page by `aria-current` alone, so no host exists there either and the list item keeps one writer. Source: ADR 0039; the triage Answer; BB 1.5; OC; NG.
7. **Should `NfsMagellan` host `NfsMenu`, as SS's Answer left to this ticket?** First a fact check, because SS D13 and the brief both rest part of the answer on a duplicate-directive error. Angular 22.0 de-duplicates host directives: a directive that the template matches and that is also a host directive applies once, as the template match, and the host-directive match is discarded (NG `packages/core/src/render3/features/host_directives_feature.ts:152-175`, `trackHostDirectiveDef`, line 171: `else if (!templateMatches.includes(hostDirectiveDef))`; commit 9c55fcb, "feat(core): de-duplicate host directives", first tagged v22.0.0-next.7 and in v22.0.0; its acceptance test "should de-duplicate a host directive that matches multiple times in a template", `packages/core/test/acceptance/host_directives_spec.ts:3502-3523`, all re-read). NG0309 (`DUPLICATE_DIRECTIVE`, `packages/core/src/errors.ts:60`) is still asserted (`packages/core/src/render3/view/directives.ts:84`, `:568-585`), but only after that de-duplication, so it no longer fires for a template match beside a host-directive match. The [Spec: Menu](85-spec-menu.md), resolved while this ticket ran (commit 51a4880), measured the same on Angular 22.2.0 (its Q13 and decision 5, Probe 1 `template-and-host`). So a consumer's `nfsMenu` beside a host of `NfsMenu` would not be an error. The answer is still no, for the reasons that do not depend on it: host directives are static, so every Magellan container, the spec's bare-link `nav` and step list included, would get `.menu` with no way to opt out; the Menu's Variant inputs would need a second exposure for consumers who do not also write `nfsMenu`; and the Magellan entry point would import the Menu's. **Decided: no; the consumer writes `nfsMenu` beside `nfsMagellan`** (D17). The same fact corrects two sentences the spec already had: "Writing `nfsSmoothScroll` on the same element as well is Angular's 'directive matches multiple times' error" (now: harmless, one instance, and Magellan's listener does not depend on the resulting listener order, since it neither reads `defaultPrevented` nor calls `preventDefault()`), and D3's rejected alternative ("Angular rejects a double match on one element"). Source: map Standing preferences (directives placed beside each other); SS D13; NG.
8. **Should the Menu directive host `NfsMagellan` (or `NfsSmoothScroll`)?** No: every Menu would track or handle in-page clicks, and the Menu entry point would import theirs, against per-plugin `@defer` splitting (BB 1.11 decision 7). The Menu spec writes Smooth Scroll and Magellan beside `nfsMenu` (its D6). Recorded as what this spec relies on and routed to the Menu spec. Source: BB 1.11; SS decision 7.
9. **What does a directive beside `nfsMagellan` have to avoid?** Two things: cancelling in-page link clicks (the composed Smooth Scroll yields to a `defaultPrevented` click, so nothing would scroll and the marker would snap back after the 100 ms idle; SS decision 8), and binding `.is-active` on the tracked links or their list items (decision 10). The spec's hierarchy section says so, and Comparison rule 2 extends from `routerLinkActive` to the Menu's own current-page marking. Source: the spec's click listener and transition; SS.
10. **Building-blocks 1.4's new rule (initial state is bound, never read from a class; a copied class is stripped and reported; commit 46b7d0a): does Magellan have such a seed?** It reads none: the Current section comes from the scroll position, a bound `active` (a consumer write scrolls there), or the deep link. But a copied `class="is-active"` (Foundation's Menu docs teach `li.is-active`) would have stayed forever under the spec's "remove from the previously marked links" write, leaving two current items. **Decided: Magellan owns the marker on its tracked links and their `li`s: each marker write removes `.is-active` and `aria-current` from every tracked link and item outside the Current section, and a development-mode check, read before that write (the first render callback's `earlyRead` phase, and the read phase that picks up later links), warns once per instance, naming `[(active)]`** (D18). Untracked links (to other pages) are never touched. Stripping on the server is not possible (nothing Magellan does runs there), so a copied class shows in the first paint until hydration; the warning is the signal. Source: BB 1.4; the Accordion spec's dev check 7 (the same rule for a host binding).
11. **Does ADR 0039's second rule (each directive owns the ARIA, `type` default, or check its documented markup lacks for WCAG 2.2 AA) add anything?** Magellan's own markup already gains `aria-current` and a development check for a missing `nav` landmark. The 2.5.8 failure of a `simple` vertical Menu and the Top Bar's 1.4.3 failure (`$anchor-color` on `$topbar-background`) belong to the Menu's and the Top Bar's documented markup, so their specs own the fix: the resolved Menu spec's `nfs-menu` gives simple-menu links a 24 px row and stops the compile when `$menu-item-background-active` is below 3:1 against `$body-background`, which the spec's 2.5.8 and 1.4.11 rows now cite; the Top Bar's 1.4.3 setting stays a consumer setting here until the Top Bar spec decides whether `nfs-top-bar` checks it. The spec adds no Library mixin (no library CSS, as before). Source: ADR 0039; ADR 0022; the spec's WCAG table.
12. **Options and consumer CSS recipes?** The four inputs are Options (and one ARIA token) and keep `booleanAttribute` and `numberAttribute`; ADR 0040's typed transform applies to Variant inputs only. The 2.5.8 fallback consumer rule, for a page without `nfs-menu`, becomes `[nfsMagellan] a { padding-block: 0.25rem; }`, and custom navigations style `a[aria-current]`, because a spec's consumer CSS recipe selects elements, attributes, or the consumer's own classes, never a Foundation or library class (BB 1.1). No Foundation rule styles `a.is-active` (FS `scss/`: only `.menu .is-active > a` at `scss/components/_menu.scss:478` and `li.is-active > a` at `scss/components/_dropdown-menu.scss:160`), so the link's class stays only as Magellan's own contract, for CSS migrated from Foundation. Source: BB 1.1, 1.4; ADR 0040; FS.

Round 3 (depends on 6-12): examples, stories, and tests.

13. **Usage examples and Rendered HTML?** Every class becomes a directive or a typed input, with the imports (`NfsMenu`, `NfsTopBar`, `NfsTopBarRight`, `NfsSticky`, `NfsStickyContainer`, `NfsGridX`, `NfsCell`). A static `orientation="vertical"` type-checks against the closed union, and a misspelt one fails (TYP round 1, cases S01 and S02, as SS decision 11). Source: ADR 0039; ADR 0040.
14. **The guide example's Sticky container?** The spec wrote Foundation's `nav.sticky-container > div.sticky`, but Foundation sets that range with `data-anchor="exampleId"` (FS `docs/pages/magellan.md:78-81`), an Option the library drops: the Sticky range is the sticky element's parent (ADR 0019; ST `:88`), and a `nav` wrapped around the sticky element is exactly as tall as it, so the navigation never stuck. **Decided: the grid cell is the container (`<div nfsCell [size]="{large: 3}" nfsStickyContainer>`) and the `nav` is the sticky element**, the shape of ST's sticky column (`:228`). A correction outside the class rule, found while rewriting the markup. Source: ST; ADR 0019; FS.
15. **Story scaffolding?** `ul[nfsMenu]` containers; the sticky bar is `[nfsTopBar]` with `nfsSticky` inside `[nfsStickyContainer]` spanning the story's scroller, with `stickyOn="all"` because play functions hold a 414 px viewport (SBC checklist) and Sticky's default `stickyOn` is `medium` (ST's title bar example uses `all`); the sidebar layout uses `[nfsGridX]` and `[nfsCell]`; story buttons are `button[nfsButton]`; inline styles only for heights, `overflow-y: auto`, and `scroll-margin-top` (SBC section 8). Keeping `nfsSticky` rather than SS's inline `position: sticky` is deliberate here: the story demonstrates Foundation's documented Magellan-plus-Sticky pairing (user story 34). Story ids are unchanged (SBC section 3). Source: SBC; ST; the spec.
16. **SSR smoke and fixture app?** The smoke's container is `<ul nfsMenu nfsMagellan>`; it asserts `class="menu"` from the Menu directive, that `NfsMagellan` adds no class and no attribute but `jsaction`, and that no link or list item carries the marker. The fixture app's containers are `ul[nfsMenu]`. Layer 2 gains the copied-marker case and its warning. Source: BB 1.12; TYP ("its SSR smoke asserts the class in server HTML"); SS decision 13.
17. **User stories?** Story 1 names `<ul nfsMenu nfsMagellan>`; story 5 styles custom navigations by `a[aria-current]`; story 36 ("server HTML to be my markup unchanged") no longer holds as written, since the Menu's class comes from a host binding, so it asks that Magellan add nothing but its event annotation; new stories 44 (no class written) and 45 (a copied marker reported and removed). Source: ADR 0039 Consequences.

### What other specs need from this one

- [Spec: Menu](85-spec-menu.md): Magellan's examples, stories, and SSR smoke write `<ul nfsMenu nfsMagellan>`, `orientation="vertical"`, `expanded`, and `simple`. Magellan relies on the Menu directive hosting neither `NfsMagellan` nor `NfsSmoothScroll`, not cancelling in-page link clicks, and binding no `.is-active` on the items of a Magellan navigation, which Magellan owns (Comparison rule 2). ### Gist for Decisions so far

- [Re-run: Magellan spec under the class rule](issues/122-rerun-magellan-class-rule.md) -- Magellan has no Structural or Variant class, so `NfsMagellan` keeps its API, gains no Variant input, and binds nothing on its host; Foundation's Menu container becomes `<ul nfsMenu nfsMagellan>`, with `.menu` and `orientation` set by the Menu directive written beside it rather than hosted (D17, as Smooth Scroll's D13, because host directives are static; the duplicate-directive reason both specs gave is corrected, since Angular 22.0 keeps a template match and discards the same directive's host-directive match); the marker stays a `Renderer2` write on the consumer's links and list items, which carry no library directive and have no server value (D11 reaffirmed, with a dated clarification proposed for ADR 0039's State-class clause), and Magellan now removes a copied `is-active` from every tracked item and reports it (D18); examples and stories write directives only, and the guide example's Sticky container moves to the grid cell so it sticks; impact HIGH, confidence HIGH. ### User decision, 2026-09-27

Asked about D11, the user chose to keep the `Renderer2` marker: when a directive manages a State class on an element that carries no library directive (the current-section marker on the consumer's links, the Off-canvas class on `body`), a `Renderer2` write satisfies the class rule, because the consumer writes no class and the directive manages it. ADR 0039's "every State class is a host binding" is clarified to apply where a library directive hosts the element (proposals 1 and 2 above).
