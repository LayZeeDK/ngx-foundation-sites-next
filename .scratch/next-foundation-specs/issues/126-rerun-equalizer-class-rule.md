# 126. Re-run: Equalizer spec under the class rule

Type: grilling

## Question

What does the [Spec: Equalizer](34-spec-equalizer.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/equalizer.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Equalizer](34-spec-equalizer.md) and the answer here. Model: Opus 5.5.

Gist: Equalizer has no Foundation class of its own, so the pair's API, the pass, DI, and every behaviour stay; what the developer still wrote were other components' classes. The CSS answer's `.grid-x`, `.cell`, sizes, block grid, flex helpers, `.callout`, and `.card`, and the residue's `.row` and `.column`, are now set by the XY Grid, Flexbox Utilities, Callout, Card, and Float Grid directives written beside the pair (placeholder names where those specs are unpublished); host classes render on the server, so CSS still comes first for the same reasons. The subgrid recipe selects the developer's own class and element, the host-directive example hosts `NfsCallout` (and gets the `display: block` it always needed), the three Options stay Options, no copied-class check is added, and every exclusion and rejected alternative carries a category (EQ1 `scope-boundary`, EQ10 `platform-or-a11y`).

### Decisions

1. **Which classes did the published spec leave to the consumer?** None of Equalizer's own, because it has none. Other components' classes, in five places: the CSS answer's markup (`.grid-x`, `.grid-margin-x`, `.cell`, `.medium-4`, `.small-up-1 .medium-up-2 .large-up-4`, `.flex-container`, `.flex-dir-column`, `.flex-child-grow`, `.callout`, `.card`), in the Solution, user stories 2 and 3, the class mapping ("Plain markup" rows), the first Delta, the Rendered HTML, and the usage examples; the residue's markup (`.row`, `.medium-6`/`.medium-4`, `.columns`, `.callout`) in the Rendered HTML and three examples; `host: { class: 'callout' }` in the `ProductTile` example; the `> .card` selector of the subgrid recipe; and the stories, whose layouts the spec described by Foundation's classes (`small-*` cells, `.row`/`.columns`). Source: the spec before this revision.
2. **Does the pair change?** No. FS `js/foundation.equalizer.js` writes only an inline `height` and FS ships no Equalizer Sass (the spec's decision 1), so there is no Structural class to bind, no Variant class to type, and no State class to host. The class mapping says so in its first row, as the Magellan spec does for a Plugin with no class. No Variant registry, alias, Variant property, `nfsVariantCheck` call, or manifest entry; the Sass subsection's item (6) reads "none". Source: ADR 0039; ADR 0040; building-blocks 1.3, 1.4, 1.13.
3. **Who sets the CSS answer's and the residue's classes?** The directives of their own specs, placed beside the pair and never hosted, so each class has one owner (building-blocks 1.9 hosts a class directive only where the element is always that component's): `nfsGridX` and `nfsCell` with `size` and `up` (XY Grid), a flex container directive with a column direction and a grow-child directive (Flexbox Utilities), `nfsCallout` with `color` and `size` (Callout, published), `nfsCard`, `nfsCardDivider`, `nfsCardSection` (Card), `nfsRow` and `nfsColumn` with `size` (Float Grid), and, in stories, `nfsToggler` and `button[nfsButton]`. Names: `nfsGridX`, `nfsCell`, `size`, and `up` follow building-blocks 1.3 and 1.4 (rule 3 names `up` for the grid families), as the Forms, Tabs, Abide, Magellan, and Slider re-runs wrote them; the Card names are the triage's (section 2, Card row); `nfsFlexContainer direction="column"`, `nfsFlexChild="grow"`, `nfsRow`, and `nfsColumn` are placeholders built by the same rules (`direction`, because `dir` is the HTML global attribute). All unpublished names are flagged in the spec's class mapping. The gutters (`.grid-margin-x`, `.grid-padding-x`) are left out of the examples until the XY Grid spec names its input, as the Slider and Magellan re-runs did; they change spacing, not equalization. Source: the specs named; `research/out-of-scope-triage.md` section 2; FS `scss/components/_flex.scss:17-40` (the three helper families); FS `docs/pages/flexbox-utilities.md` (the Vanilla helpers example uses the column container with growing children).
4. **Does the CSS answer still come first?** Yes, for unchanged reasons. The class directives bind static host classes or host bindings, which render on the server (building-blocks 1.11 decision 1; ADR 0039, Consequences), so the server HTML carries every class and the CSS answer is equal at first paint, with JavaScript off, and inside `hydrate never`, where the Equalizer directive never runs. The "no directive" wording becomes "no Equalizer directive", and the first-paint, full-hydration, and `hydrate never` bullets say why the classes are there. The SSR smoke now asserts those classes in the server HTML of a class-free fixture, because the claim depends on them. Story ids stay (`css-*` still names the answer in which CSS equalizes).
5. **EQ10, the directive as the primary answer (D1's rejected alternative): what is its real reason?** Not CSS-only. A measuring directive leaves the server HTML and `hydrate never` blocks unequal, shifts the layout at hydration, and runs a measurement loop for a layout job; the directive itself ships (D2). Category `platform-or-a11y` (rendering modes). The triage already found it holds "because its directive ships" (section 3). Source: the spec's decisions 21 and 23; `research/out-of-scope-triage.md` section 3 and C8.
6. **EQ1, library CSS for equal heights: does it hold?** Yes, with its real reason, which the scope lens named. For a library rule: the map's standing preference allows custom CSS for what Foundation cannot express, and equal rows across wrapped lines is such a thing. Against: (a) Foundation has no class or rule for it, so a library class would add a class family Foundation lacks, and ADR 0039 gives directives to Foundation's classes, not to new ones; (b) doing it for the block grid means laying the grid out in CSS grid, which re-implements Foundation's XY grid layout (`grid-template-columns` mirroring `.medium-up-<n>`), against the rule never to re-implement Foundation's styles; (c) Foundation's own feature, one height across every row, is fully covered: it is `nfsEqualizer` with `equalizeByRow` off. The recipes without JavaScript stay as the developer's own rules on the developer's own classes. Category `scope-boundary` (not a Foundation feature), in Out of Scope and D14. Source: `map.md` Standing preferences; ADR 0039; FS `scss/xy-grid/_classes.scss` (block grid); `research/out-of-scope-triage.md` section 3.
7. **What do the developer's CSS recipes select?** Only the developer's own classes and elements (building-blocks 1.1's sentence from the Accordion re-run). `.equal-rows` needed no change. The subgrid rule becomes `.card-row > article`, with the cards written `<article nfsCard>`: `.card-row > *` would tie Foundation's `.card` at (0,1,0) and depend on stylesheet order, while the element selector (0,1,1) outranks it, as the old `.card-row > .card` (0,2,0) did. A developer class on each card also works; the element is shorter and semantic. Source: FS `scss/components/_card.scss:56-60` (`display: flex` under `$global-flexbox`).
8. **The host-directive example?** `ProductTile` hosts `NfsCallout` beside `NfsEqualizerWatch` (`hostDirectives: [NfsCallout, NfsEqualizerWatch]`) instead of `host: { class: 'callout' }`. The callout's close-button content query still works on a host directive, because Angular runs `contentQueries` for every directive in the node's directive range, host directives included (NG `packages/core/src/render3/queries/query_execution.ts:55-75`). A correction found while rewriting it, outside the class rule: the host is a custom element, inline by default, and `.callout` sets no `display` (the Callout spec says so), so `min-height` had no effect on it and `offsetHeight` measured line boxes; the example now gives its host `display: block` in the component's own `styles`, and the browser-level host-directive case uses such a host. A development warning for an inline watched element was considered and not added (new behaviour the ticket does not ask for; the example and the docs line cover it).
9. **A development check for copied classes?** No. Neither directive owns a class, so there is nothing of its own to strip or report; a copied `callout`, `row`, or `grid-x` belongs to the directive that binds it, which is building-blocks 1.4's rule and the Triggers spec's Out of Scope item for its class-free hosts. Building-blocks 1.4's "component whose host binds no class reports Foundation's classes on the plugin's element" is about a Foundation class that styles the plugin's own element (a copied `tabs`); Foundation's Equalizer markup puts on its elements only other components' classes, whose directives the class rule already places there. Added to Out of Scope (`scope-boundary`) and D16.
10. **Do the three Options become Variant inputs?** No. They set no class; building-blocks 1.4 keeps `booleanAttribute` for Options and `nfsVariantBoolean` for Variant inputs, and 1.7 and the Breakpoint service spec keep behaviour Options open (`equalizeOn` is listed there under `NfsBreakpointName`; its values are Breakpoint query strings that `is()` takes). Stated under the API table and in D16. Source: building-blocks 1.4, 1.7; the Breakpoint service spec's type table.
11. **Stories?** Ids unchanged. A story-markup paragraph: no written class; scaffolding from each spec's entry point; breakpoint-independent layouts written as `size="4"`, `up="2"`, and `size="6"` (a bare value is the Zero breakpoint, building-blocks 1.4); the two CSS grid stories carry the recipe's declarations in inline `style`, values Foundation has no class for (Storybook conventions section 8). `equalizer--hidden-then-shown` now uses the published Toggler (`nfsToggler` in Visibility mode with a `button[nfsButton]` Trigger) instead of "a plain `[hidden]` binding until Toggler exists". A correction outside the class rule: the spec (and the Storybook conventions' comment) said `foundation-grid` has no class overlap with the XY grid, but both emit the size classes (`.medium-6`, FS `scss/grid/_classes.scss:101-104`); the overlap is harmless, because the XY grid's size rules are `.grid-x > .medium-6` (FS `scss/xy-grid/_classes.scss:92`) and outrank the float grid's, so the sentence now says that.
12. **Tests?** Browser-level: a class-rule case (class-free hosts; the pair adds no class, attribute, or listener; beside `nfsCallout` the host carries only `.callout` and the pass's `min-height`) and the host-directive case with `NfsCallout` hosted. SSR smoke: a class-free fixture whose server HTML carries the grid, flex, callout, row, and column classes from their directives. Playwright: the gated variant's cells are `[size]="{medium: 4}"` and the by-row resize names `up`. Every other case unchanged.
13. **Rendering modes?** Unchanged in behaviour. The Equalizer directives still bind nothing and run nothing on the server; the class directives beside them bind the same classes on both platforms, so hydration claims the nodes unchanged. Only the wording of three bullets changes (decision 4).
14. **Categories.** Every Out of Scope item, every "Dropped" row of the Foundation contract table (written "Dropped (`<id>`)" or "Replaced (`<id>`)", the Tooltip re-run's form), the Dropped options line, and every rejected alternative of D1 to D16 carries a one-line reason and one category of `research/out-of-scope-exclusions.md`. Changes in kind: EQ1 from `css-only` to `scope-boundary`, EQ10 from `css-only` to `platform-or-a11y`; EQ2, EQ3, EQ4, and EQ6 stay `scope-boundary`, EQ5 `superseded`, EQ7 and EQ11 `jquery-or-dom-plumbing`, EQ8 and EQ9 `superseded`; runtime theming is `other` (design choice), as the research tags G9; new: the copied-class check (`scope-boundary`). Being CSS-only is the reason for none, and no Foundation class is left to the developer. Nothing returns to scope.
15. **User stories?** 1, 2, 3, 9, and 28 rewritten in place; 43 (the CSS answer's classes set by their own directives, still in the server HTML) and 44 (recipes that select only the developer's own classes and elements) appended; numbering kept.
16. **Glossary or ADR?** Neither. "Watched element" already carries the vocabulary, and "CSS answer" is this spec's own phrase, not a domain term. No ADR: everything follows from ADR 0039 and ADR 0040, ADR 0021 is untouched (it concerns the directive's writes), and the one choice with alternatives (`> article` over a developer class on each card) is an example, reversible at no cost.
