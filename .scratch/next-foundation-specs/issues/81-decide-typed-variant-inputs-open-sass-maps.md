# 81. Decide: typed Variant inputs over open Sass maps

Type: grilling
Status: claimed
Blocked by: 80, 135
Labels: wayfinder:grilling
Map: ../map.md

## Question

How is a Variant input typed under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010), both for closed sets Foundation's Sass fixes (`stacked`, `vertical`, `hollow`) and for open Sass maps the consumer extends (palette colours, button sizes, breakpoints)? The user vetoed consumer-side TypeScript `namespace` or `module` augmentation. The user settled the veto's reach on 2026-09-27: it rules out every way of changing the library's types from outside the consumer's own code, namely declaration merging (`declare module`, `declare namespace`), a tsconfig `paths` entry that remaps a library type module (O7), and a generator that overwrites a type file inside the installed package (Chakra's `typegen` approach). Consumer-local code stays: a subclass (O4), a narrowing directive (O5), a typed factory (O6), a closed or open union (O1, O2), a development-mode check (O10), and a generator that writes into the consumer's own source tree (O9 feeding O4 to O6). The answer is the ADR every spec and re-run ticket in this wave types its Variant inputs by, including the input naming (`color`, `size`, `fill`, boolean modifiers or enums), how a responsive Variant (`.small-expanded`, `.medium-horizontal`) is expressed, and what development-mode check catches a value the consumer's Sass does not generate.

## How to work it

Decided by a panel under the map's Open-decision pass note: the dossier is [Research: typed Variant inputs over open Sass maps](80-research-typed-variant-inputs-open-sass-maps.md)'s `research/typed-variant-inputs.md`; four lenses (API design; consumer ergonomics and migration; adversarial against every option that asks the consumer for code per directive; adversarial against every option that lets a typo compile or blocks a custom name), all on Opus 5.5 because Fable credit ran out on 2026-09-27 and the user's rule is that Opus, never Sonnet, takes Fable's seats; then an Opus 5.5 judge who weighs the arguments, records the dissent, writes the ADR (proposed as `adr/proposed-<slug>.md` in the ADR-FORMAT shape), and lists the changes to ADR 0039, building-blocks, and the glossary.

## User input, 2026-09-27

- Code generation ships as an Nx generator, wrapped and exposed as an Angular CLI schematic (the user). Where the research says "generator" (O9) it meant a step that turns the consumer's Sass settings into TypeScript; if the decision uses one, the one-off setup (writing the typed file into the consumer's source tree and the consumer-local code that type feeds) is that Nx generator and schematic.
- Orchestrator's proposal for the judge to weigh, not a user decision: keeping the generated types in step with later Sass edits needs a step that runs on every build, which a generator or schematic does not; that would be an Nx executor (run before build, serve, and test through `dependsOn`) and an Angular CLI builder (which runs the type step and then calls `@angular/build:application`, since the Angular CLI cannot chain targets), with a `--check` mode for CI. `@angular/build` 22.2 has no hook inside its own Sass compile (`research/typed-variant-inputs.md`, O9).
- The user, relayed by the orchestrator while the judge worked: "Ideally, a misspelt palette or size name fails to compile." Stated as the ideal, not an absolute requirement, after the orchestrator explained the measured costs of the subclass option (O4) and the narrowing-directive option (O5). The orchestrator's own recommendation, again a proposal to weigh, not a user decision: library default O2 plus O10, and for compile-time failure an opt-in O5 whose types, narrowing directives, and one exported import list per entry point (so components cannot forget the checker) are generated from the consumer's Sass by that generator and schematic, and regenerated by an Nx executor and Angular CLI builder with a `--check` mode for CI.
- The user ruled a general rule for the library: directive composition is preferred over subclassing. The user called subclassing a poor API, especially when many components must be extended just to add one colour. O4 is out on that ground.
- The user narrowed the veto:
  - Option A, consumer-side declaration merging, is now allowed on the condition that a probe confirms it works. It means module augmentation of library-declared registry interfaces in a consumer `.d.ts`, the MUI and Mantine pattern, for example `declare module 'ngx-foundation-sites' { interface NfsButtonPaletteOverrides { brand: true; warning: false } }`.
  - Option B, a tsconfig `paths` remapping of a library type module (O7), stays vetoed.
  - Option C, anything that writes into or overwrites files in `node_modules`, is vetoed under all circumstances, permanently.
- The user proposed a change of plan: option A plus a generator that writes the consumer's `.d.ts` from the consumer's Sass (the `.d.ts` may also be hand-written), combined with an Nx sync generator, so that a Sass change synchronises the consumer's TypeScript automatically (`syncGenerators` on targets, `nx sync`, and `nx sync:check` in CI). The user also asked for a research round on alternatives not yet considered that do not rely on the vetoed options: [Research: further typing and synchronisation options for Variant inputs](135-research-further-variant-typing-options.md). This ticket waits on it, and the judge's provisional ruling is below.
- The user: "Having a development mode (or optionally production mode) runtime check and a CI check sounds like a good idea."
- The user: "Development/production mode runtime check opt-in could be inspired by @ngrx/store's runtime configuration." The research ticket's sync-tooling researcher is verifying NgRx's `runtimeChecks` shape from source.
- The user: "Development mode runtime check should default to on but opting out should be possible." So the development-mode check is on by default with a per-check opt-out, and the production-mode check stays opt-in.
- The user, on the ESLint template rule the second research round found (N5 in `research/variant-typing-alternatives.md`): "An ESLint plugin is a good idea but would add to the library's API surface and maintenance burden and I struggle to see how it could be fed its options from SCSS or provided values." The orchestrator's note for the judge: with declaration merging, such a rule checks only literal values the compiler already rejects, so it adds cost and no check; the same holds for a shipped stand-alone type-checker check (N6).

Verdict: declaration merging works as the user's condition requires. It reaches Angular's template type-check for static and bound values, fails typos with the compiler's suggestion, accepts declared names, and rejects removed ones. It works across a real ng-packagr package boundary, for registries declared in the primary entry point, in a secondary entry point, or re-exported through a secondary. It keeps a separate set of names per application program in one workspace, and it fails closed in a program that leaves the declaration file out.

### Provisional decision

These rules stand from the first draft; the probes and sources behind them are unchanged:
- Closed sets Foundation's Sass fixes (the fills; Reveal and Switch sizes; Menu `horizontal` and `vertical`; Button Group `stacked-for-small` and `-medium`; single modifier classes) are a literal union, or a boolean through the library transform `nfsVariantBoolean`, whose parameter is `NfsVariantBoolean`, `boolean | '' | 'true' | 'false' | null | undefined`. Never `booleanAttribute`, which lets `arrowOnly="flase"` compile and set the class (J09; verified, `NG/packages/core/src/util/coercion.ts:23-25`).
- A responsive Variant takes the breakpoint in the value of the family's own input. An on or off family takes `true` or a Breakpoint query (`expanded="medium only"`, `showFor="large only"`); a valued family takes a bare value (the Zero breakpoint) or a Breakpoint rules object (`[size]="{small: 12, medium: 6}"`, `[orientation]="{small: 'vertical', medium: 'horizontal'}"`). A `<words>-for-<bp>` class keeps Foundation's words (`stackedFor`). The directive maps each value to the class with its meaning and fills Foundation's Zero-breakpoint gaps: `expanded="small down"` sets `.small-only-expanded` (verified, `FDN/scss/components/_button.scss:345-365`), and a Menu rule for the Zero breakpoint sets `.vertical` (verified, `FDN/scss/components/_menu.scss:413-429`). There is no input per breakpoint, and no class-name or rule string as a value (verified, `adr/0039-directives-manage-every-foundation-class.md:25`).
- Input names, in this order:
  1. A Foundation `data-*` Option that names the family (`revealOn`, `inCanvasOn`, `hideFor`, Slider `vertical`).
  2. The hosted `@angular/aria` directive's name for the concept (`orientation`).
  3. One enum input per set of mutually exclusive names, named for its dimension (`color`, `size`, `fill`, `ratio`, `offset`, `up`, `order`).
  4. A boolean named with the camelCase of its class (`expanded`, `dropdown`, `arrowOnly`, `noGaps`).
  5. A responsive form never gets its own input.
  6. Aliases are `Nfs` + component + dimension.
- Every Variant input defaults to `undefined` (`false` for a boolean), which sets no class, so the consumer's Sass default is the look. With `$button-fill: hollow`, a `fill` defaulting to `'solid'` would set `.solid` and fight the setting (D 2.8, 2.9; verified, `_button.scss:368-381`). The value `'default'` sets no class, no Defaults token holds a Variant default, an explicit value always sets its class, and a value that is not one class token binds nothing.
- The Variant check channel: each Library mixin of an entry point with an open family writes Variant properties, `--nfs-<setting>` lists on `:root` of the names the consumer's compile generates, and `nfs-breakpoint-properties` also writes `--nfs-breakpoint-classes`. This is ADR 0005's verification channel (`adr/0005-breakpoint-source-of-truth.md:7`, `:13`), and it answers the Breakpoint service spec's recorded follow-up (verified, `specs/breakpoint-service.md:378`).
- An element Foundation styles by tag gets a directive once Foundation gives it a Variant class. Native `<progress>` takes the palette classes (verified, `FDN/scss/forms/_progress.scss:70-71`, documented on `FDN/docs/pages/progress-bar.md:113-119`), and `<table>` takes `.unstriped`, `.striped`, `.stack`, `.scroll`, and `.hover` (verified, `FDN/scss/components/_table.scss:168-321`); `<meter>` has no class. This corrects ADR 0039's list of tag-styled elements with no directive (the vsloose lens's finding).
- Library directives are not extension points: a subclass inherits neither `providers` nor its selector nor `exportAs`. The providers feature carries no `ngInherit` (verified, `NG/packages/core/src/render3/features/providers_feature.ts:44-58`; the host-directives feature does, `host_directives_feature.ts:61`), and class-token injection matches the exact type (verified, `NG/packages/core/src/render3/di.ts:705-712`). The user's rule of composition over subclassing now makes this a library rule.

What option A changes:
- **Open palettes, size and ratio maps, and Prototyping lists** become closed by default and extended by the consumer.
  - Each Sass setting gets one library-declared, empty registry interface, `Nfs<Setting>Overrides`, and each directive family an alias `NfsOverridableStringUnion<defaults, registry>`. The aliases chain where Foundation's defaults chain: `$button-palette`, `$badge-palette`, and `$label-palette` default to `$foundation-palette`, and `NfsButtonColor` builds on `NfsFoundationPaletteColor` (B01).
  - For every consumer with no setup, a misspelt name fails to compile with the compiler's suggestion (A02) and a Foundation class name fails (A06). With the consumer's own declaration file, a name its Sass adds compiles (A01), a removed name fails (A03), and the editor offers the consumer's names (K01).
  - The `(string & {})` escape is dropped from these families. A consumer who wants open typing for one setting declares an index signature in that registry (O01), and the docs give that as the opt-out.
- **Class breakpoints**: the registry `NfsClassBreakpointOverrides` makes `NfsClassBreakpoint`, `NfsClassBreakpointQuery<M>`, and rules-object keys closed. A misspelt query (A10) and a misspelt key (A13) now fail at compile time, which closes the first draft's gap on keys, and an added `xlarge` compiles once declared (A09, A12). Behaviour Options keep `NfsBreakpointName` (`specs/breakpoint-service.md:145`) unless the final Answer extends a registry to `$breakpoints`.
- **Counts**: a registry holds the count (`{columns: 16}`), the type is a range over it, and a template literal over the alias gives the static-attribute strings (A14, A15, B05).
- **A library authoring rule** comes from the A19 trap. Every Variant input declares explicit type arguments that name exported aliases, and the library's build asserts that each Variant input's emitted write type names its registry-derived alias. Declaration emit can print an alias's resolved union, which freezes Foundation's defaults into the typings, where no consumer declaration can reach them.
- **Where the registries live** is settled in the final Answer; all three placements measured merge correctly (A07, B03, B04, R01). The provisional choice is to declare all Variant registries once, in the primary entry point `ngx-foundation-sites`, so a consumer's declaration file augments one module. Type-only use adds no runtime import, so per-plugin `@defer` splitting is untouched.
- **The runtime check** is on by default in development builds and opt-in for production, configured by providers in the direction of NgRx's `runtimeChecks` (per-check options, on in development, off in production). The exact shape waits for the research ticket's source reading.
  - Under A its job moves. The compiler now reports typos. The check reports drift between the consumer's declaration file and its compiled Sass: a declared name the CSS lacks, a removed key still declared, a class a Sass flag leaves out, or a missing Library mixin include. It also reports values that bypass the type (`$any()`, or a string cast from data).
  - What production opt-in costs: the check's code stays in the bundle, not stripped by `ngDevMode` (small, not measured). It adds one `getComputedStyle(document.documentElement)` property read per family per realm after the first render, cheaper than the stylesheet scan D 4.4 timed at 2 to 17 ms (not measured separately), and one report per distinct value. The Variant properties ship in production CSS in any case.
  - It runs only in the browser. The server has no computed style (`research/angular-rendering-modes.md:31`, `:51`), so server HTML carries whatever class the value produced.
  - The one reason to opt in for production is Variant values that come from runtime data, such as a colour name from a CMS.
- **The CI check** fails when the consumer's declarations and its Sass settings disagree: `nx sync:check` when the generator runs as an Nx sync generator, or the generator executor's `--check` mode otherwise.
- **The generator, the user's proposal, is adopted provisionally.** It compiles the application's global stylesheet with that project's Sass options and reads the Variant properties, the same source the runtime check reads. It then writes `src/nfs-variants.d.ts` into the application's own source tree, never into `node_modules` (veto C). A hand-written declaration file is equally supported, and the CI check compares either with the Sass.
  - **Nx**: it is an Nx sync generator attached through `syncGenerators` to the application's `build`, `serve`, `test`, and `typecheck` targets. `nx sync` applies it, `sync.applyChanges: true` applies it without a prompt, and `nx sync:check` fails CI when it is out of step. All of these were verified in nx 23.2.1:
    - a target's `syncGenerators?: string[]`, "List of generators to run before the target to ensure the workspace is up to date" (`dist/src/config/workspace-json-project-json.d.ts:262`);
    - `sync.globalGenerators` and `sync.applyChanges` (`dist/src/config/nx-json.d.ts:690-709`);
    - `SyncGenerator = (tree: Tree) => SyncGeneratorResult`, with `outOfSyncMessage` (`dist/src/utils/sync-generators.d.ts:7-12`);
    - `nx sync:check`, "Check that no changes are required after running all sync generators" (`dist/src/command-line/sync/command-object.js:15-16`).

    The earlier `dependsOn` executor proposal is replaced by this for Nx workspaces, because sync generators are Nx's own mechanism for keeping generated workspace files in step before tasks, and they carry the CI check.
  - **An Angular CLI project without Nx** has no sync generators and no target dependencies. In their place it gets:
    - the same generator as a schematic through `convertNxGenerator` (`ng g ngx-foundation-sites:variant-types`) to write or rewrite the file;
    - an Architect builder through `convertNxExecutor` whose `--check` mode runs in CI (both converters verified in `@nx/devkit` 23.2.1, `dist/src/utils/convert-nx-executor.d.ts`, `invoke-nx-generator.d.ts`);
    - optionally, npm `prebuild`, `prestart`, and `pretest` scripts that run the builder in write mode. npm runs them for `npm run build`, `npm start`, and `npm test`, not for a bare `ng build`, and nothing reruns during `ng serve` watch;
    - the runtime check in development as the backstop.

    The Angular CLI builder that wraps `@angular/build:application` stays not adopted: a committed file needs a drift check, not regeneration inside the build, and a wrapper would carry every option of the application builder across its releases. `@angular/build` 22.2.0's application schema has only three deprecation options under `stylePreprocessorOptions.sass` and no plugin option (verified).
  - Not measured, for the research ticket or the tooling spec: the Sass compile per sync (D 4.3: about 1.5 s with `foundation-everything`; an entry that emits only the Variant properties would be cheaper); whether Nx reruns a sync generator during `nx serve` watch; and reading a project's Sass options from its target configuration.
- **Dropped by the rulings**:
  - O4 (composition over subclassing).
  - The open default for open families (O2): the user's ideal can now be met without a subclass.
  - The generated narrowing directives with import lists (O5). A reaches every component in the program, offers completion of the consumer's names, and fails closed. O5 fails open outside its lists (L05) and offers only Foundation's names (D 4.2).
- **Still rejected**: O3 (inference gives every string), O6 (brands force bindings everywhere), O8 (DI never reaches the type check), O7 (veto B), and every form that writes into `node_modules` (veto C, which also rules out Chakra's typegen shape).

### Why, provisionally

1. A meets the user's ideal for every consumer by default. A misspelt palette, size, breakpoint, or count fails to compile with no consumer step (A02, A10, A13, A15). The consumer's own names compile once declared (A01, A09, A12, A14) and are offered by the editor (K01, K04). A removed key fails (A03), which answers ADR 0010's objection that a union type would lie about an open Sass map. A Foundation class name passed as a value fails (A06), which answers the vsloose lens's point that the open type let `hide`, `disabled`, and `is-active` through against ADR 0039:25.
2. A fails closed where the declaration is missing (C01), and the default CLI and Nx templates put a `src/` declaration file in both the application and the test programs. The generated narrowing lists failed open wherever a component bypassed them (L05).
3. A asks the consumer for code per Sass setting, not per directive: one line per changed name in one file per application, generated or hand-written. That answers the vsdirective lens's case against per-directive consumer code, and composition over subclassing holds, since nothing is subclassed.
4. Several applications with different Sass keep separate names in separate programs (shop against admin: B02). A Nx library compiled inside an application's program sees that application's names; its own test and lint programs need a declaration file of their own or fail closed (the C01 behaviour).
5. The Sass stays the source of truth and TypeScript stays its mirror, verified twice. The CI check catches drift before merge; the development runtime check catches drift, a missing include, and values that bypass the type, in the browser. This is ADR 0005's shape for breakpoints (a TypeScript mirror verified through `:root` custom properties), applied to names.
6. The library carries a real authoring risk: the A19 trap would silently freeze the defaults. It is guarded by explicit alias type arguments and a build assertion on the emitted typings.

The panel's arguments after the rulings:
- **vsloose lens**: its central demand, that a name the consumer's Sass does not generate fails to compile by default, is met by A without its subclass route. Its closed rule-object keys are adopted through the registry. Its typed boolean transform and its native `<progress>` finding stand.
- **api lens**: its reversibility table now favours A. The library's default is the narrow type, and widening is the consumer's own declaration, never a breaking library change. Its naming order, outer-escape measurement (still relevant to behaviour Options), and Zero-breakpoint mapping stand.
- **ergo lens**: its day-two cost changes from none to one declaration line per changed name, or one generator run, and its multi-application Nx case is measured (shop and admin). Its Storybook measurement now helps: closed unions in library source get a radio or select control from `@storybook/angular-vite`'s docgen, so the library's own stories need no `argTypes` line for Variant inputs (its 2.5).
- **vsdirective lens**: its Step 3 failures (providers, selectors, `exportAs`, class-token injection, composed inputs) apply only to subclassing, which is out. Its preference for no consumer code at all is outweighed by the user's ideal; the price is one declaration file per application.

### Provisional dissent

- **api, ergo, and vsdirective lenses (argued before the rulings)**: the open type by default, with no consumer step. Overridden by the user's ideal and the narrowed veto, which make a closed default extensible without subclassing. Reopens if the research ticket or the tooling spec finds that a consumer declaration file breaks in a supported toolchain, where the CI check cannot catch it. The candidates are Vitest under `@angular/build:unit-test`, `@storybook/angular-vite`'s own compile, and a buildable Nx library's programs.
- **The orchestrator's generated narrowing lists**: superseded by A (point 2).
- **The orchestrator's executor-on-every-build proposal**: replaced by the sync generator for Nx; the application-builder wrapper for the Angular CLI stays not adopted.
- **api, ergo, and vsdirective lenses**: `booleanAttribute` for pure boolean Variant inputs, the Angular-native shape. Overridden by J05 and J09, as in the first draft.
