# 115. Re-run: Responsive Menu spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81, 132
Labels: wayfinder:grilling

## Question

What does the [Spec: Responsive Menu](23-spec-responsive-menu.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/responsive-menu.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Responsive Menu](23-spec-responsive-menu.md) and the answer here. Model: Opus 5.5.

Spec: [specs/responsive-menu.md](../specs/responsive-menu.md), revised in place; the dated amendment is in [Spec: Responsive Menu](23-spec-responsive-menu.md) under `### Amendment, 2026-09-28 (class rule)`.

Gist: the consumer's markup keeps Foundation's element structure and carries no class. The responsive `ul` gets one `NfsMenu` through its three roots, and the Menu's five Variant inputs bind on that `ul` without being listed in `hostDirectives`, so `class="vertical medium-horizontal menu"` becomes `[orientation]="{small: 'vertical', medium: 'horizontal'}"` and `align="right"` turns dropdown mode's submenus left in server HTML; submenus are bare `ul[nfsSubmenu]`; the current page's section open at first paint is `[expanded]="true"`; `span[nfsSubmenuToggleText]` and the screen-reader-only directive replace the last two consumer-written spans; the Advanced Layout example uses the Top Bar spec's directives and `nfs-top-bar`; development check 3 reads the Menu's `orientation()`, and the check for a copied mode class is removed, in line with the Accordion Menu and Drilldown Menu re-runs. Behaviour, ARIA, keyboard, the swap rule, rendering modes, and Story ids are otherwise unchanged. Nothing is `OPEN FOR HUMAN`; no prototype is needed.

### Decisions

1. One `NfsMenu` for the responsive `ul`, through the three roots; this directive's `hostDirectives` list no Menu input; `orientation`, `expanded`, `simple`, `align`, and `iconPosition` bind on the `ul` (D19).
2. `[orientation]="{small: 'vertical', medium: 'horizontal'}"` replaces Foundation's orientation classes in every example; the consumer pairs it with the rules; the orientation is not derived from the rules (D20).
3. Development check 3 reads the hosted Menu's `orientation()` and the Zero breakpoint from `nfsBreakpointsToken`, in development builds only; never a class.
4. The current page's section open at first paint is `[expanded]="true"` or `[(expanded)]` on its item; a copied `is-active` opens nothing in any mode and is reported by the Nested menu naming `[expanded]`; D10 is unchanged (D21).
5. The class mapping table gains the Kind column and a row for every class on the menu's elements; copied Foundation classes are stripped in every mode; the published check 4 (a mode class on the root) is removed, because a copy changes nothing, as the three roots decided for themselves; the former check 5 is check 4 (D22).
6. `span[nfsSubmenuToggleText]` names a Hybrid toggle; the back suffix uses the Visibility Classes spec's screen-reader-only directive, written `nfsShowForSr` until that spec names it (D23).
7. The Advanced Layout example uses the Top Bar spec's directives; a menu in a Top Bar needs `nfs-top-bar` with `$topbar-background` and `$topbar-submenu-background`, in any mode; the Base side inside a right-hand section comes through the Nested menu root (D24).
8. The current link's look is `nfs-menu`'s, which the consumer includes; a 1.4.1 row names the per-mode fill checks; every quoted ratio is exact (D25).
9. Stories, tests, and the SSR smoke write no class except the copied-class cases; Story ids unchanged; user stories 44 to 52 appended, 18 and 19 revised; a Hybrid item's Router link matches exactly, with a browser-level case; the per-mode 1.4.1 compile cases stay the mode mixins' own.
10. No glossary term and no ADR.
