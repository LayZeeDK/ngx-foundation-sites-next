# 113. Re-run: Dropdown Menu spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81, 86, 132
Labels: wayfinder:grilling
Map: ../map.md

## Question

What does the [Spec: Dropdown Menu](21-spec-dropdown-menu.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/dropdown-menu.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

Also: its `.top-bar-right` ancestry read follows the Top Bar spec.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Dropdown Menu](21-spec-dropdown-menu.md) and the answer here. Model: Opus 5.5.

Contract: the "What other tickets need from this one" section of the [Re-run: Nested menu (shared utility) spec under the class rule](132-rerun-nested-menu-class-rule.md), applied, not reopened, including that every read of `align-right` becomes `align()` and that this spec owns the current top-level link's look and its contrast pair. Gist: the consumer's markup keeps Foundation's element structure and carries no class. `ul[nfsDropdownMenu]` hosts `NfsMenu` with the five Menu inputs, so `orientation` and `align="right"` replace `vertical` and `align-right`; submenus are bare `ul[nfsSubmenu]`, the Hybrid name `span[nfsSubmenuToggleText]`, a submenu open at first paint a bound `expanded`, the current page `aria-current` only, the Top Bar sections the Top Bar spec's directives. The Top Bar question is settled by combining both answers: the Nested menu root reads `nfsTopBarRightToken` at construction, so a menu declared in the right-hand section opens left in the server HTML, and walks the DOM once after hydration only when it found no token, for a menu projected into the section, with a development warning; measured under hydration in three engines. The current top-level link keeps the Menu's current look through one new rule, measured necessary. Nothing is `OPEN FOR HUMAN`; no prototype is needed.

Round 2 (the Top Bar conflict, which the orchestrator asked this ticket to settle, and the current look, which the Nested menu contract left here):
- Q5. How does a menu root learn it sits in a Top Bar's right-hand section? Three options, argued both ways.
  - (a) The DOM walk after hydration (the Nested menu re-run's D33, and the published D9). For: it reads exactly what Foundation's CSS and JavaScript read (DOM ancestry), so a menu projected into the section from another template is found; DI follows the declaration site and cannot see it. Against: building-blocks 1.11 decision 1, server output is the first paint: every right-hand menu, including the Top Bar docs layout, renders `opens-right` on the server and flips at hydration, which shows on a vertical root (its side arrows) and on any submenu open at first paint, and the common case needs a development warning and a redundant `alignment="right"` to be right.
  - (b) The token alone (the Top Bar spec's decision 9). For: server-correct wherever the menu is declared inside the section, which is the documented layout; no DOM read; the triage's reason for rejecting DI (a consumer-written `.top-bar-right`) no longer holds under the class rule. Against: a menu projected into the section keeps opening right in production, not only at first paint; its only signal is a development warning, and the Top Bar spec's second remedy, providing the token "on an element of its own", has no good value to provide (the token's value is the `NfsTopBarRight` instance, and writing `nfsTopBarRight` again inside the section binds a second `.top-bar-right`, which Foundation's `.top-bar .top-bar-right` rules style too).
  - (c) Both, with precedence: the token at construction, and the walk after hydration only when no token was found. For: the server HTML is right in every case DI can reach, and the projected case still reaches Foundation's side in production. The Top Bar spec rejected "both" as "two sources for one decision"; that objection was the triage's, where a consumer-written class and a token could disagree. With precedence they cannot: the walk runs only when DI found nothing and can only add the section. The one case where the two facts would differ, a template declared inside the section and rendered elsewhere, keeps the token's answer, deterministically. Cost over (b): one `closest()` call in a render callback that (b) already needed for its development warning, now acting in production too.
  - Settled: (c), measured (Probe A) with Angular 22.2.0 in a server render and under full hydration in Chromium, Firefox, and WebKit. It meets the rendering-modes rule wherever the rule can be met, and a projected menu, which cannot be server-correct without the consumer's help, is correct after hydration and reported in development, naming `alignment="right"` as the fix. The proposed ADR changes accordingly (change 5).

### Decisions

1. `NfsDropdownMenu` hosts `NfsMenu` with `inputs: ['orientation', 'expanded', 'simple', 'align', 'iconPosition']` and binds only `.dropdown` itself; the consumer writes no class: bare submenus, `span[nfsSubmenuToggleText]`, `[expanded]` for first-paint state, `aria-current` for the current page, the Top Bar spec's section directives; the class mapping table gains a Kind column (D1, D20).
2. The Base side's Top Bar source: the Nested menu root injects `nfsTopBarRightToken` optionally at construction (no `skipSelf`), and walks the DOM (`closest('.top-bar-right')`) once in its first render callback only when it found none, writing a signal the Base side reads; the walk changes only closed submenus' side classes; a development warning, naming `alignment="right"`, fires once when the walk changes the Base side (D9).
3. The root has no development check of its own and reports no copied `dropdown` (D22).
4. The current top-level link keeps the Menu's fill: `nfs-dropdown-menu` rule (e) at (0,3,2) (Nested menu rule 14), and a 1.4.1 `@error` for `$menu-item-background-active` against a set `$dropdownmenu-background` (D21).
5. Top Bar checks: `nfs-top-bar` owns `$anchor-color` and the fill against the bar; `nfs-dropdown-menu` warns for `$dropdown-menu-item-color-active`, `$dropdownmenu-arrow-color`, and `$accordionmenu-arrow-color` against the bar; the required settings and the Storybook overrides carry both Top Bar lines (D14).
6. Every ratio is the exact WCAG formula through the library's exact-luminance helper; no quoted ratio moves; new compile cases isolate the 1.4.1 check and prove the helper.
7. The entrance-animation recipe keys on `data-nfs-expanded`; Hybrid links in Router examples match exactly (D12).
8. Stories, tests, fixtures, and examples as listed in Q17; Story ids unchanged.

5. New ADR (the orchestrator numbers it), in place of the [Spec: Top Bar](86-spec-top-bar.md)'s proposal 12, which does not stand as written (it decided the token "in place of" the walk and rejected the combination adopted here), `status: accepted`:

   > # A menu root learns it sits in a Top Bar's right-hand section through dependency injection, and from the DOM only when projection hides it
   >
   > Foundation's Dropdown Menu opens its submenus to the left when its root sits inside `.top-bar-right`, which Foundation's JavaScript reads from the DOM; the published Dropdown Menu spec read the same ancestry in the first render callback, so the server HTML carried the wrong side and the side changed at hydration, with a development warning in every such layout. Under the class rule ([ADR 0039](0039-directives-manage-every-foundation-class.md)) the right-hand section is always the `nfsTopBarRight` directive, which dependency injection can find on the server. We decided that `NfsTopBarRight` provides the lightweight `nfsTopBarRightToken`, that the Nested menu root injects it optionally at construction and gives `opens-left` for `alignment: 'auto'` when it is present, so the side is in the server HTML and hydration changes nothing, and that only when no token is found does the root walk the DOM once after hydration, because DI follows the declaration site and misses a menu projected into the section from another template ([Spec: Top Bar](../issues/86-spec-top-bar.md); [Re-run: Dropdown Menu spec under the class rule](../issues/113-rerun-dropdown-menu-class-rule.md), measured with Angular 22.2.0 under hydration in three engines).
   >
   > ## Considered options
   >
   > - The DOM walk alone (the published Dropdown Menu spec's D9 and the Nested menu re-run's D33): it sees a projected menu, but the server HTML is wrong in every Top Bar layout, and the common case needs a warning and a redundant `alignment="right"`.
   > - The token alone (the Top Bar spec's first proposal): right in the server HTML wherever the menu is declared inside the section, but a projected menu keeps the wrong preferred side in production, with only a development warning.
   > - Injecting `NfsTopBarRight` by class: every menu bundle would keep the Top Bar's directive class.
   >
   > ## Consequences
   >
   > - The walk runs only when the token is absent and can only add the section, so the two never disagree; a template declared inside the section and rendered elsewhere keeps the token's answer.
   > - A projected menu's closed submenus change side at hydration; the menu root warns in development builds, naming `alignment="right"`, which puts the side in the server HTML.
   > - A root that is itself the right-hand section counts as inside it, where Foundation's `parents()` skipped the root.
   > - The Nested menu entry point imports the token from the top-bar entry point, as the Openables import `nfsOpenableToken` from the Triggers entry point.
