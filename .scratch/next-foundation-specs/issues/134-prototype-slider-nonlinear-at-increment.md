# 134. Prototype: a non-linear Slider Handle that assistive-technology increments move

Type: prototype
Status: resolved
Blocked by: none
Labels: wayfinder:prototype
Map: ../map.md

## Question

Graduated on 2026-09-27 from the re-judgement of [Resolve the assistive-technology checks](77-evidence-assistive-technology-checks.md) (its "Prototype needed"). A non-linear Slider Handle uses `step="any"`, which WebKit counts as 0, so VoiceOver's increment and decrement change nothing, and Chromium's increment adds one native unit of a thousand, which maps back to the same value; keys, drags, and track presses are unaffected. The [Spec: Slider](32-spec-slider.md) records it as a documented limitation (D22). Can a numeric `step` and an `input` rule make assistive-technology increments move the Handle one value step?

## How to work it

A non-linear Slider Handle operable by assistive-technology increment and decrement: on the Slider's non-linear stories, give the native input a numeric `step` (for example `1`, one thousandth of the track) instead of `any`, and add an `input` rule: a native value change with no pointer pressed and no key handled by the directive, whose mapped value equals the current value, moves one value step in the direction of the change and writes the native value. Measure in Chromium, Firefox, and WebKit: the dependent bounds in position units (a bound such as `585.93` off the step grid), the pre-hydration key and drag replay cases of the Slider spec, drags that end between steps, and a value set from outside (UIA `RangeValue.SetValue` in Chromium and Firefox; the increment actions themselves only on real devices, through the Slider's release test). If it holds, the limitation text and D22 below give way to the rule and ADR 0020 gains a second dated note; if not, the limitation stands.

Run AFK under the map's AFK override with `/mattpocock-skills:prototype` on Opus 5.5; capture the decisive files under `prototypes/`. The [Re-run: Slider spec under the class rule](124-rerun-slider-class-rule.md) waits on this ticket.

### Verdict

The rule holds with conditions. A non-linear Handle with `step="1"`, its value and both dependent bounds rounded to integers, a native range in which every value step spans at least two native units, and the `input` rule guarded by the Handle's own pointer events moved exactly one value step per increment and per decrement, in the right direction, in Chromium 153, Firefox 155, and WebKit 26.6: from 50 and from 5 on `log`, on `pow`, at both dependent bounds of a two-Handle slider, after a drag that ended between steps, on a 1000-step scale with the derived range, and through the real UI Automation `SetValue` path in Chromium and Firefox. The pre-hydration key and drag replay cases of the Slider spec all pass with it. Each condition is required: dropping any one fails a measured case (table 3). D22's limitation gives way to the rule, and ADR 0020 gains a second dated note.

The rule, as measured: on a non-linear Handle's `input` event that the directive did not dispatch itself, when no pointer is pressed on the Handle (set by its `pointerdown`, cleared by its `pointerup`, `pointercancel`, and `change`), the live native value differs from the last native value the Handle read or wrote, and the value it maps to (clamped against the sibling) equals the current value, the Handle moves one value step in the direction of that difference, clamped against the sibling and the scale, sets the model, and writes the new value's native position. Otherwise the listener sets the model from the mapped value, as today. The last native value is updated on every `input` and every write. The ticket's "no key handled by the directive" needs no flag of its own: the key handler's write (D18) makes the companion `input` read a native value equal to the last one.

### 1. How the actions were exercised

Only a device runs VoiceOver's or TalkBack's action, so the prototype reproduced each engine's arithmetic and number-to-string conversion from source, and ran the real platform set where Windows exposes one. Sources: Chromium `cdf7131c` and WebKit `c39e3bbd` through their GitHub mirrors (the re-judgement's commits), Firefox `mozilla-firefox/firefox` at `cdc95c93`.

- Chromium (TalkBack's scroll actions through `AdjustSlider`, `content/browser/accessibility/web_contents_accessibility_android.cc` 2453-2474; VoiceOver on Chrome for macOS; Orca): `AXNodeObject::AlterSliderOrSpinButtonValue` (`ax_node_object.cc` 710-747, synthesized keys off by default) adds the exposed step, and `StepValueForRange` (4710-4750) exposes none for `any` or for 40 or more stops (`kNumStopsForFivePercentRule`, 4727), so the step is a default `StepRange`'s 1. The float result is printed by `String::Number(float)`, which is `%.6g` (`wtf_string.cc` 268-270, `wtf_string.h` 124), and set by `AXSlider::OnNativeSetValueAction` (`ax_slider.cc` 80-99), which returns when the string equals the live value and otherwise sets it with `input` and `change`. TalkBack's set-progress action is an absolute set (`SetRangeValue`, 2903-2929).
- WebKit (VoiceOver on iOS and macOS): `alterRangeValue` (`AccessibilityNodeObject.cpp` 1785-1811) calls `changeValueByStep` (1917-1924) when a `step` attribute exists, adding its `toFloat()` (1440-1443; `any` is 0) to the float value; `setNodeValue` (1906-1914) prints it as the shortest float (`WTFString.cpp` 251-255), and `AccessibilitySlider::setValue` (`AccessibilitySlider.cpp` 144-153) sets it with `input` and `change` whenever the string differs.
- Firefox for Android (TalkBack): `ACTION_SCROLL_FORWARD`/`BACKWARD` on a node call `changeValueBySteps(id, +-1)` (`SessionAccessibility.java` 233-257), which sets `CurValue() + Step() * steps` (`accessible/android/SessionAccessibility.cpp` 157-164); `HTMLRangeAccessible::Step()` is the input's step (`any` is 0) and `SetCurValue` prints 15 significant digits and calls `SetUserInput` (`accessible/html/HTMLFormControlAccessible.cpp` 618-638).
- Real platform path: UI Automation `RangeValuePattern.SetValue` in headed Chromium and Firefox on Windows 11 ARM64. Chromium's reaches the same `AXSlider::OnNativeSetValueAction` as its increment, and Firefox's the same `SetCurValue` as Firefox for Android's increment, so `SetValue(Value + 1)` is the increment's final call with its arithmetic. Chromium's CDP tree confirmed the exposed values (its `valuetext` property is the native value string, the known trap; the DOM `aria-valuetext` carried the value).

### 4. Costs of the candidate

- Before hydration and in `@defer (hydrate never)`, a native arrow key moves one native unit in every engine (a thousandth of the track at the default range; Chromium and WebKit moved a hundredth with `any`, Firefox a thousandth already); Page Up and Page Down still move a tenth, Home and End reach the ends. Replayed keys still count one value step after hydration.
- An outside set that lands inside the current value's step (a UIA `SetValue` three native units away) moves one value step; that is the rule's defined behaviour and matches a UIA client stepping by `SmallChange`.
- TalkBack may use set-progress about 5 percent further instead of the scroll actions (Chromium's comment in `StepValueForRange` expects it when no step is exposed); that is an absolute set of several value steps, which the rule leaves alone. Which action TalkBack sends stays unread; the release test records it.
- The Handle gains four host listeners (`pointerdown`, `pointerup`, `pointercancel`, `change`), all in the replay set; `aria-valuenow` stays a position, now an integer.
- The derived range is capped at 100000, because Chromium prints the incremented float with six significant digits; a scale that needs more (over about 20000 value steps at base 5) is documented as not guaranteed one value step per increment at its dense end.

### 5. Questions settled (AFK override)

1. Is the numeric step needed, or does the rule alone fix it? Needed: the rule alone fixes Chromium, but with `any` WebKit's zero-step set still fires `input` with a rounding drift, so the rule would step in the drift's direction (measured: decrements went up).
2. Which step value? `1` on an integer grid: integers are exact in the float arithmetic Chromium and WebKit use and in every engine's number printing, so a set is exactly one unit and a same-value set is exactly equal.
3. Do the dependent bounds stay off the grid (`585.93`)? No: rounding the bounds to integers makes each bound the sibling's native value exactly; unrounded bounds shift the maximum's grid (measured).
4. Is 0..1000 always enough? No: the round trip and the one-unit step need every value step to span two native units, so the range is derived from the scale; 1000 covers Foundation's defaults and every usage example in the spec.
5. How does the rule know a pointer is pressed, before and after hydration? The Handle's own `pointerdown`, `pointerup`, `pointercancel`, and `change`, which the early event contract replays in order; a CSS `:active` read was not used, because at replay time it reads the pointer as released, and a replayed short drag then gains a step (the no-guard case measured exactly that).
6. How does it know the direction? From the last native value the Handle read or wrote, which also makes it idempotent: Firefox fires `input` on a same-value UIA set, and replayed companion `input` events read the key handler's write.
7. Does it disturb absolute sets? No: a set that maps to another value sets that value (UIA far sets measured in both engines).
8. Does it change linear Handles? No: the rule runs on non-linear Handles only; the linear UIA sets moved as native (measured).

Nothing is left `OPEN FOR HUMAN`.
