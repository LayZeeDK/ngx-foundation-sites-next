# 127. Re-run: Interchange spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81

## Question

What does the [Spec: Interchange](35-spec-interchange.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/interchange.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Interchange](35-spec-interchange.md) and the answer here. Model: Opus 5.5.

## Answer

Model: Opus 5.5. Worked AFK as a self-grilling (both sides) against the sources below, with `/domain-modeling` for vocabulary and `/to-spec` for the revision. Spec: [specs/interchange.md](../specs/interchange.md), revised in place; the dated amendment is in the [Spec: Interchange](35-spec-interchange.md). No experiment was run: every point is settled by the bundle's decisions or by source.

Gist: Interchange has no Foundation class, so the class rule removes what the consumer still wrote around it rather than adding bindings: the story's and the data example's `.callout` become `nfsCallout`, a table's `.hover` goes, and a Foundation look on a background host comes from the directive that owns that class, placed beside or inside it. The project's image rule is applied: `NgOptimizedImage` for every static `<img>`, except the `<img>` of an art-directed `<picture>` and `data:` or `blob:` URLs. An Interchange rule's breakpoint names are behaviour, so they stay the Breakpoint map's (`NfsBreakpointName`), never Class breakpoints. The image-mode exclusion is re-checked (contradiction C9) and stays out as `platform-or-a11y`. Every exclusion now carries a reason and a category.

### Decision log

Sources: FS = the Foundation 6.9.0 clone; NG = the angular 22.2.x clone; X = `research/out-of-scope-exclusions.md`; T = `research/out-of-scope-triage.md`; BB = `building-blocks.md` as it stands during the wave; BP = `specs/breakpoint-service.md` after the [Re-run: Breakpoint service (shared utility) spec under the class rule](129-rerun-breakpoint-service-class-rule.md); "the spec" = `specs/interchange.md` before this revision.

Round 1 (no prerequisites): which classes the spec touches.

1. **Does Interchange have a Structural, Variant, or State class?** No. FS has no Interchange Sass (no file under `scss/` names it), and `js/foundation.interchange.js` never calls `addClass` or `removeClass` (searched; the same search finds its `SPECIAL_QUERIES` lines, the positive control): it writes `src`, an inline `background-image`, or fetched markup. So no host class binding, no Variant input, registry, alias, or Variant property, and no `nfsVariantCheck` report. The class mapping becomes a Kind table (BB 1.14 item 2). Source: FS; ADR 0039; ADR 0040.
2. **Which consumer-written Foundation classes did the spec carry?** Four: the `interchange--background` story's headline on a Foundation `.callout`; the data-bound usage example `<section class="callout" [nfsInterchange]>`; `<table class="hover">` in the `httpResource` example; and the mapping prose naming `.thumbnail` and "a grid cell" as classes the consumer writes on the host. `.hero` is the application's own class (FS `scss/` defines no `.hero` or `.banner`), which ADR 0039 leaves alone. Source: the spec.
3. **What replaces them?** The story's headline sits inside an `nfsCallout` element ([Spec: Callout](89-spec-callout.md), `[nfsCallout]` binds `.callout` as a static host class), so axe still decides 1.4.3 against a solid background. The data example becomes `<section class="banner" [nfsInterchange]>` with an `<div nfsCallout>` child for the text: an `nfsCallout` on the Interchange host itself would put the text straight on the image, which fails 1.4.3 for some rule's image, so the child form is both class-free and accessible. The table becomes a plain `<table>` (Foundation styles it by tag; the [Spec: Table](92-spec-table.md) is not written, so no Variant input is named here). The mapping prose says that the classes on a background host come from the directive that owns them, written beside or inside, and the application's own classes stay. Rejected: keeping `class="callout"` (against ADR 0039); `nfsCallout` on the Interchange host (text over the image, 1.4.3). Source: ADR 0039; the Callout spec; WCAG 2.2 1.4.3.
4. **Does "Initial state is bound, never read from a class" (BB 1.4) bear here?** Only as a confirmation: no part of Interchange reads a class to seed state or choose a rule; the initial rule comes from `rules` and the media state (the Server breakpoint on the server). There is no copied-class hazard and no development check to add, because neither directive binds a class a copy could collide with. Recorded in the Kind table. Source: BB 1.4; the spec.
5. **Should Interchange host a class directive, or offer an input that sets a Foundation class?** No. BB 1.9 ("Hosting a class directive") says a behaviour that may sit on any element is written beside the class directive; `NfsInterchange` binds only `[style.background-image]`, so it composes with `nfsCallout` or a grid cell's directive by placement, and each class keeps one owner. Recorded as design decision 17 and an Out of Scope item (`scope-boundary`). Source: BB 1.9; ADR 0039.

Round 2 (depends on 1-5): typing under ADR 0040.

6. **Is an Interchange rule's breakpoint name a Variant value?** No: it selects content, which is behaviour, as the [Re-run: Breakpoint service (shared utility) spec under the class rule](129-rerun-breakpoint-service-class-rule.md) records (behaviour Options keep `NfsBreakpointName`; Variant inputs take `NfsClassBreakpoint`). And it must not be a Class breakpoint in meaning either: Foundation's `SPECIAL_QUERIES` gain every entry of `MediaQuery.queries` (FS `js/foundation.interchange.js:110-113`), which the MediaQuery utility reads from `.foundation-mq`, whose font-family serialises the whole `$breakpoints` map (FS `scss/_global.scss:144-146`), so `xlarge` and `xxlarge` are queries although they have no classes by default. Resolution step 1 and the Solution now say "any breakpoint of the Breakpoint map". No Runtime check reads the query. Source: FS; ADR 0040 Consequences; BP (`breakpoints`, `atLeast(name)`, `NfsBreakpointName`).
7. **Does the query's `string` type become a union?** No. A template-literal union of breakpoint names, Named query keys, and media-query shapes cannot list the Named queries, which come from `nfsInterchangeDefaultsToken` at run time, and media queries are free text; the development warning for an unknown bare word already catches `meduim`. Recorded as design decision 19 with both rejected forms. Source: the spec's query resolution; ADR 0040 (closed types apply to Variant inputs, which this is not).

Round 3 (depends on 1-7): the project's image rule.

8. **Does the repository's `NgOptimizedImage` rule apply to this spec's images?** Yes: AGENTS.md says to use it for all static images. The spec had four plain `<img src>`: the Rendered HTML `<picture>`, two `<picture>` usage examples, and the two images of the meaning-changing chart example. The chart images become `ngSrc` (they already had `width` and `height`). Source: AGENTS.md (Angular Best Practices); the spec.
9. **What about the `<img>` inside an art-directed `<picture>`?** It stays plain, the rule's one exception here. NG's guide says `<picture>` is not supported ("No, but this is on our roadmap", `adev/src/content/guide/image-optimization.md:467-471`), and its source shows why it would misfire there: `assertNoImageDistortion` compares the chosen file's `naturalWidth`/`naturalHeight` (the `<source>` the browser picked) with the `<img>`'s `width` and `height` and warns when they differ by more than 0.1 (`packages/common/src/directives/ng_optimized_image/ng_optimized_image.ts:1080-1125`), which an art-directed crop of another shape always does; and its server preload for `priority` passes the `<img>`'s own rewritten `src` and `srcset` (`:525-532`), a file a viewport that matches a `<source>` never shows. Source: NG.
10. **What about resolution switching with no image CDN?** `NgOptimizedImage` generates `srcset` only with a configured loader (`shouldGenerateAutomaticSrcset` requires `imageLoader !== noopImageLoader`, `:710-721`), throws when a hand-written `srcset` sits beside `ngSrc` (`assertNoConflictingSrcset`, `:817-827`), and rejects `data:` and `blob:` URLs (`:941-955` and the base64 check before it). So the guidance names a loader (a built-in CDN loader or an `IMAGE_LOADER` function mapping widths to files), plain `srcset`/`sizes` is kept only for `data:` and `blob:` URLs and inside `<picture>`, and the `interchange--optimized-image` story provides an `IMAGE_LOADER`, without which its `srcset` assertion could not pass (a real gap in the spec). The `auto, ` prefix on `sizes` for lazy images does not depend on the loader (`:508-512`). The development error on `img[nfsInterchange]` now names `NgOptimizedImage (ngSrc with sizes)` in place of `srcset/sizes (NgOptimizedImage)`. Recorded as design decision 18. Source: NG.
11. **Does `ngSrc` inside a rule template change the rendering-modes story?** It adds one sentence, not a behaviour: an `<img>` in the Server breakpoint's template that the first client render swaps out can start downloading at parse time, the same accepted cost as a background, and `priority` on it would emit a server preload for the Server breakpoint's file on every viewport, so such images take no `priority`; `<picture>` avoids both when one `alt` fits. Source: the spec's Double fetch bullet; NG `:525-532`.

Round 4 (depends on 1-11): exclusions and their categories.

12. **Does the image mode (IC1) come back under the CSS-only ruling?** No. Contradiction C9 of X flagged that IC1 reads as CSS-only-adjacent but is not: the reason throughout is that the server cannot know the viewport, so a `src` binding renders one fixed file and swaps it after hydration (a second download on another viewport, the largest contentful paint after JavaScript, the wrong file kept inside `hydrate never`), while `<picture>` and `srcset` let the browser's preload scanner choose at parse time (ADR 0015; BB 1.11 decision 7). The ruling's premise, that an Angular directive is the Angular-native way to use a UI component, is met for images by Angular's own `NgOptimizedImage`, and art direction is a platform element. The reason is the platform, so the category is `platform-or-a11y`, not the `superseded` of the exclusion table of the [Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md) (X row IC1; T section 3 groups it under "Replaced by a named mechanism"). Source: X C9 and IC1; ADR 0015; the spec's design decision 1.
13. **The other exclusions?** Re-checked, none rests on being CSS-only, and each now carries a one-line reason and a category in the spec: IC2 HTML partials `jquery-or-dom-plumbing`; IC3 `type` and `auto` `superseded`; IC4 `replace(path)` `superseded`; IC5 the `<picture>`-generating component `scope-boundary`; IC6 custom-property backgrounds `other` (one code path per behaviour); IC7 container queries `scope-boundary`; IC8 waiting for image load `platform-or-a11y`; the consumer-specific focus rule `scope-boundary`; the new item (a class bound or hosted by Interchange) `scope-boundary`. Dropped options: `type`, the string-array `rules` form, and `replace(path)` `superseded`; the generated `id` and `data-resize` `jquery-or-dom-plumbing`; the lifecycle events `superseded`. Every rejected alternative in Design decisions 1 to 19 carries a category, with `other` plus a parenthetical where the reason is an Angular limit or a design choice (the Slider re-run's form). These match X's categories for IC2 to IC8. Source: X rows IC1 to IC8; T section 3; the spec.

Round 5 (depends on 1-13): tests, stories, and the rest.

14. **Can the `interchange--no-match` story's default background be an inline `style` on the host, now that stories declare no styles?** No. NG's `findStylingValue` consults the static `style` attribute only when every binding for the property is `undefined`, and `isStylingValuePresent` counts `null` as a value (`packages/core/src/render3/instructions/styling.ts`, `findStylingValue` and `isStylingValuePresent`, `:1009-1015`), so the host's `null` binding removes a static inline `background-image` as surely as a matching rule replaces it. The default therefore comes from a stylesheet, as user story 22 already said: a recipe class `hero-default` in the Storybook stylesheet's recipe block (storybook-conventions section 5, "Recipe CSS"), beside the `hero` recipe (a `min-height` and `background-size: cover`, so an empty host shows its background). The API's host-binding row documents the fact, and a browser-level case asserts it. Rejected: switching the cleared value to `undefined` so an inline default survives (a behaviour change this ticket does not make; recorded for [Triage: out-of-scope items across the specs](138-triage-out-of-scope-across-specs.md) only if it proves wanted). Source: NG; storybook-conventions sections 5 and 8.
15. **Tests?** Layer 1: the intro states that no story writes a Foundation or NFS class and names the recipe classes; `interchange--optimized-image` gains its `IMAGE_LOADER`; `interchange--background` uses `nfsCallout`; `interchange--no-match` uses `hero-default`. Layer 2: one class case (no class added on a class-free host; composition with a class-binding test directive; the static inline style is absent while matching and after clearing). Layer 3: the SSR fixture writes no Foundation or NFS class, and the background host's `class` attribute is exactly `hero`. Layer 4 unchanged. Story ids unchanged. Source: BB 1.12; the Callout spec's composition case.
16. **Rendered HTML?** The picture example is labelled as the `NgOptimizedImage` exception; the background example labels `hero` as the application's class; a new composition example shows `<div nfsCallout>` inside the host and its server HTML with `class="callout"` from the host binding. Template mode unchanged. Source: BB 1.11 decision 1; ADR 0039 Consequences (server HTML still carries every Foundation class).
17. **Sass?** Still no library CSS and no `nfs-interchange` mixin; item (5) names `strictBreakpointSync` in place of "the development drift check"; item (6), Variant properties, is "none"; the recipe classes and the Storybook `nfs-callout` include are noted, with no settings override needed (the callout's text is not a link, so the Callout spec's `$anchor-color` override does not bear on it). Source: BB 1.13; the Callout spec's Sass subsection; BP.
18. **Foundation's docs markup and WCAG (ADR 0039's "each directive owns the check its documented markup lacks")?** Foundation's `<img data-interchange>` example has no `alt` (FS `docs/pages/interchange.md:24-27`, an axe `image-alt` failure); the existing development error on `img[nfsInterchange]` already sends that markup to `<picture>` or `NgOptimizedImage`, and every image in the spec has a true `alt`, so no new check is needed. The background `<div>` lacks nothing, because a background is decoration (1.3.1 row). Recorded under Foundation behaviour changed or dropped. Source: FS; ADR 0039; ADR 0022.
19. **Glossary or ADR?** No new term: Structural class, Variant class, State class, Class breakpoint, Named query, and Interchange rule carry the revision. One sharpening is proposed for **Interchange rule**, whose "a breakpoint name" is ambiguous now that Class breakpoint exists (proposal 3). No new ADR: the decisions follow from ADR 0039, ADR 0040, ADR 0015, and the project's image rule, and none is hard to reverse (examples, stories, and a type that stays `string`); a dated note on ADR 0015 records the C9 re-check (proposal 4).
