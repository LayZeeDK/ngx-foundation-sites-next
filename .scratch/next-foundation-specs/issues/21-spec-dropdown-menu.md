## Question

What is the Angular design for Foundation's Dropdown Menu plugin in the next library, and what does its spec say?

The result must be the best combination of: Foundation for Sites SCSS and the plugin's features; the ARIA APG pattern and WAI-ARIA; WHATWG HTML and HTML5+ platform features; Angular Aria; Angular CDK; Angular Material-equivalent accessibility and Material-equivalent component API (inputs, outputs, public properties and methods, content and view projection) for the similar Material component; and the modern DI patterns recorded in `research/di-and-composition-patterns.md` (lightweight injection tokens, host-scoped providers, host directives, parent tokens, default-options tokens). One plugin may yield several related directives or components (for example a container plus items plus a lazy-content directive); the spec covers the whole set.

## WCAG 2.2 AA guard (user decision, 2026-09-26)

Every directive and component complies with WCAG 2.2 AA; see the map's Accessibility preference and [ADR 0022](../adr/0022-wcag-2-2-aa-enforcement.md). The spec carries a criteria subsection under Implementation Decisions naming the 2.2 AA criteria this plugin touches (at least 1.4.3, 1.4.11, 2.4.7, 2.4.11, 2.5.8, 4.1.2, and, for overlays and hover content, 1.4.13) and how each is met, as requirements, never recommendations. Where a Foundation default fails a criterion, the spec states the Sass settings the consumer must set or the smallest custom rule the `nfs-<plugin>` mixin adds, with the reason. The story axe gate runs with the WCAG 2.2 AA tags, and the decision log records each criterion addressed.

## Answer

Spec: [specs/dropdown-menu.md](../specs/dropdown-menu.md). Resolved 2026-09-26 by self-grilling (AFK), both sides played against the sources below, under the user's WCAG 2.2 AA rule, the Foundation Sass reuse rule, and the triage rule for human-only items. The [Spec: Nested menu (shared utility)](56-spec-nested-menu.md) is binding and is used as defined, including its 2026-09-26 amendments (disabled animations, `open()` not opening ancestors, unrounded contrast ratios).

Gist: one attribute directive, `ul[nfsDropdownMenu]` (`exportAs: 'nfsDropdownMenu'`, entry point `ngx-foundation-sites/dropdown-menu`), provides the Nested menu root in Menu mode `dropdown` through `nfsMenuRootProviders('dropdown')`, binds `.dropdown` from the mode, forwards `keydown` and `click` to the root, and hands Foundation's seven behaviour Options (`alignment` `'auto'`, `disableHover` `false`, `hoverDelay` 50, `closingTime` 500, `autoclose` `true`, `closeOnClick` `true`, `closeOnClickInside` `true`) to it through `configure('dropdown', ...)`, seeded from `nfsDropdownMenuDefaultsToken`. It re-emits submenu completions as `opened`/`closed` carrying the `NfsMenuItem` and offers `collapseAll()`. Disclosure navigation, not a menubar. `disableHoverOnTouch`, `clickOpen`, `verticalClass`, `rightClass`, and `forceFollow` are Dropped options. No animation (Foundation has none). WCAG 2.2 AA needs two consumer settings Foundation's defaults fail: `$dropdownmenu-min-width: min(200px, 45vw)` (1.4.10) and, for menus in a Top Bar, a bar background on which `$anchor-color` reaches 4.5:1 (1.4.3); the `nfs-dropdown-menu` mixin warns for both. One amendment to the Nested menu's dropdown key table is proposed: the open and close keys follow the Base side.

### Decision log

Sources: FS = the Foundation 6.9.0 clone (`js/foundation.dropdownMenu.js` with `DropdownMenu.defaults` at lines 394-480, `scss/components/_dropdown-menu.scss`, `_menu.scss`, `_accordion-menu.scss`, `_top-bar.scss`, `docs/pages/dropdown-menu.md`); APG = the aria-practices clone (`content/patterns/disclosure/examples/disclosure-navigation.html`, `js/disclosureMenu.js`); NG = the Angular 22.2.x clone (`adev/src/content/guide/aria/menu.md`); NGC = the components 22.2.x clone (`src/aria/menu/menu-bar.ts`); NM = [Spec: Nested menu (shared utility)](56-spec-nested-menu.md) and its answer; P50 = [Prototype: Nested menu directive family with breakpoint mode switching](50-prototype-nested-menu.md); AP = [Spec: Anchored pane (shared utility)](55-spec-anchored-pane.md); DD = [Spec: Dropdown](26-spec-dropdown.md); STK = the Storybook conventions; BB = `building-blocks.md`; R:x = research files by BB's short names; ST = [Decide the browser testing stack: Playwright component tests, Vitest Browser, or both](41-browser-testing-stack-decision.md).

Round 1: Foundation's contract.

1. **Which Options, events, and methods does DropdownMenu really have?** Twelve Options in `DropdownMenu.defaults`: `disableHover` (false), `disableHoverOnTouch` (true), `autoclose` (true), `hoverDelay` (50), `clickOpen` (false), `closingTime` (500), `alignment` (`'auto'`), `closeOnClick` (true), `closeOnClickInside` (true), `verticalClass` (`'vertical'`), `rightClass` (`'align-right'`), `forceFollow` (true); none is on the docs page. Events `show.zf.dropdownMenu [$sub]` and `hide.zf.dropdownMenu [$toClose]`, plus the lifecycle pair. No public method but `destroy()`. The ticket's list omitted `disableHoverOnTouch` (audit guard H6). Source: FS `foundation.dropdownMenu.js:394-480, 327, 375`; R:menus 3.3 to 3.5.
2. **What JavaScript remains once Foundation's CSS positions submenus?** Open state (classes, `aria-expanded`, `inert`), sibling closing, the keyboard, hover timers, outside-press and focus-out dismissal, the collision flip, and the alignment decision; all of it is the Nested menu's dropdown mode plus the Anchored pane helpers. Foundation's CSS already places `.is-dropdown-submenu` absolutely with `top`/`left` per side and shows it with `.js-dropdown-active`. Source: FS `_dropdown-menu.scss:82-143, 208-278`; NM API; AP.
3. **Which Options survive?** `alignment`, `disableHover`, `hoverDelay`, `closingTime`, `autoclose`, `closeOnClick`, `closeOnClickInside`, with Foundation's names and defaults (BB 1.4). Dropped: `disableHoverOnTouch` (hover intent filters `pointerType: 'touch'` per event), `clickOpen` (a parent is a button, so a click always toggles; a parent that ignores clicks would leave pointer users who cannot hover with no way in), `verticalClass` and `rightClass` (class-name Options; the classes are the contract), `forceFollow` (the Hybrid item's link navigates), `data-options`. Source: BB 1.4 dropped list; NM Foundation contract; AP hover intent.
4. **Does dropping `verticalClass` break Foundation's docs markup?** No: the docs' submenus are `<ul class="menu">` with no `vertical`, and `.is-dropdown-submenu > li { width: 100% }` stacks their items; the key table treats submenus as vertical regardless. Consumers may still write `vertical`, as the vertical docs example does. Source: FS `_dropdown-menu.scss:269-271`, `dropdown-menu.md` L35-47, L92; NM decision 17.
5. **Events?** `show` -> `opened`, `hide` -> `closed`, Completion outputs on the root carrying the `NfsMenuItem` (BB 1.4: container aggregates carry the item; NM's `NfsMenuCompletion` passes the item). One `closed` per submenu, where Foundation fired one `hide` per group. No reason on `closed`: the Light dismiss reason is internal to the utility's focus rule and not in the completion API. Source: BB 1.4; NM `NfsMenuCompletion`; R:menus 3.4.
6. **Methods?** `collapseAll()` delegating to the root (Foundation's private `_hide()` with no argument). No `expandAll()`: dropdown mode keeps one open submenu per level, and NM warns when it is called outside accordion mode. Item-level `open()`/`close()`/`toggle()` and `expanded` are NM's. Source: NM API; FS `foundation.dropdownMenu.js:338-377`.

Round 2: shape, level, pattern, DI.

7. **Directive or component, and on what?** One attribute directive on the consumer's `ul.dropdown.menu`, `ul[nfsDropdownMenu]`, class `NfsDropdownMenu`, binding `.dropdown` while the mode is `dropdown`; `menu`, `vertical`, `.<bp>-horizontal`, and `align-right` stay consumer-written. Source: ADR 0001; BB 1.3 plugin mapping; NM consumer table.
8. **ARIA pattern: disclosure navigation or menubar?** Disclosure navigation, overlaying form. The APG's menubar navigation example opens with "Caution! ... The `menubar` pattern requires complex functionality that is unnecessary for typical site navigation", and the disclosure example says Escape and focus-out close are needed for 1.4.13; the Angular Aria guide lists "Building site navigation" under "Avoid menus when"; a menubar would pull every link but one out of the tab sequence; Foundation's items are links. Source: APG `disclosure-navigation.html` L164-167 and the menubar example's caution (R:apg DropdownMenu); NG `guide/aria/menu.md` L51-53; ADR 0004; BB 1.10 "a role is a promise".
9. **Why not `@angular/aria` `ngMenuBar`?** Besides the roles: its orientation is fixed horizontal (a `.vertical` Dropdown Menu has no counterpart), submenus are separate `ngMenu` elements referenced by `[submenu]` with `ng-template` content (breaks the nested `ul` and server HTML for open submenus), and hover opens only after a first interaction. Source: NGC `src/aria/menu/menu-bar.ts:117`; R:aria 6.1 to 6.4.
10. **Implementation level?** Custom Angular directive over the Nested menu. Native `popover` and anchor positioning are out of the Browser target (Baseline 2024 with Firefox 125 and iOS 18.3; Baseline 2026); `<details>` has no separate link and `<details name>` is out of target; CDK Menu has the menu roles and overlays. No fallback needed: P50 ran dropdown mode on this level in three engines. Source: R:platform 2, 3; BB 1.2; P50 verdict.
11. **Nesting discovery and open state?** DI registration through NM (items inject the nearest `NfsSubmenu`, register at construction), open state as each item's `expanded` model; no `contentChildren`. Source: NM hierarchy; BB 1.9.
12. **DI shape?** `nfsMenuRootProviders('dropdown')` on the root; `inject(nfsMenuModeToken, {self: true})`; `nfsDropdownMenuDefaultsToken` Shape B, `{optional: true}`, falling back to `nfsMenuBehaviourDefaults.dropdown`; no plugin token (nothing injects the root; DD D2); not an Openable (NM D22). Source: NM; BB 1.4, 1.9; DD.
13. **`closeOnClick` under ResponsiveMenu?** Kept compatible with Drilldown's same-named Option: one binding on the ResponsiveMenu reaches both host directives (Foundation's shared `data-*` reading), and when unbound each keeps its own default (`true` here, `false` for Drilldown) from its own Defaults token. The outputs share the names `opened`/`closed` with the other roots; only the live mode emits. Source: R:menus 0.3; NM decision 8 and the consumer table; the Nested menu author's note in this ticket's brief.

Round 3: the Options' behaviour.

14. **`alignment` and the side rule?** NM's base-side rule: `'left'` -> `opens-right`, `'right'` -> `opens-left`, `'auto'` -> `opens-left` for a static `align-right`, an RTL `Directionality`, or a `.top-bar-right` ancestor (after hydration), else `opens-right`. Resolves BB Table B's DropdownMenu risk. A development warning names a `.top-bar-right` root without a server-known side, because a vertical root's side arrows flip at hydration there. Source: FS `foundation.dropdownMenu.js:63-77`; NM API; BB Table B.
15. **Hover (`disableHover`, `hoverDelay`, `closingTime`, `autoclose`)?** `nfsHoverIntent` per parent item with the item as the Hover region, `enabled` = dropdown mode and not `disableHover`, `openDelay` = `hoverDelay`, `closeDelay` = `closingTime` with hover intent's 100 ms floor, close on leave only while `autoclose` is on and not click-opened. A pointer click on a hover-opened parent keeps it open (Foundation's `data-is-click`); a keyboard click always toggles. Source: FS `foundation.dropdownMenu.js:100-166`; AP hover intent and mapping table; NM toggle rule.
16. **`closeOnClick`?** Light dismiss's pointer rule per open submenu (both `pointerdown` and `pointerup` outside, never a touch scroll); Escape and focus leaving close regardless; a second click on an open parent always closes it (Foundation gated that on `closeOnClick`). With it off, a press that moves focus outside still closes through the focus rule, in engines that focus buttons on click (DD D11). Source: ADR 0024; AP Light dismiss rules; FS `foundation.dropdownMenu.js:109, 274-293`.
17. **`closeOnClickInside`?** The root's `click` listener into NM's `handleClick`: a click inside a leaf item closes every open submenu; a Hybrid link is inside a parent item and closes nothing, Foundation's `hasSub` test; the focus-loss guard moves focus off a closing submenu. Source: FS `foundation.dropdownMenu.js:132-140`; NM API.

Round 4: keyboard, RTL, and the amendment.

18. **Key table?** NM's dropdown table: horizontal top level Down opens and focuses, Up and the reading-direction keys move; vertical top level Down/Up move, the open key opens; inside submenus Down/Up move, open opens nested, close closes and refocuses; Escape closes the innermost submenu containing focus or, with focus outside, the topmost one; Tab out closes per submenu. Deltas from Foundation are listed in the spec (Enter/Space keep focus, Escape one level, Up moves back, no top-level reversal under `align-right`). Source: NM ARIA and keyboard; FS `foundation.dropdownMenu.js:37-45, 168-263`; APG hybrid keyboard table.
19. **Should the open and close keys follow `Directionality` or the side submenus open to?** The side: Open and Close follow the Base side (`opens-right` -> Right opens, `opens-left` -> Left opens), while Next and Previous along a horizontal top level keep the reading direction. Under `align-right` in LTR, NM's current rule makes Right open a submenu that appears on the left; Foundation's `_isRtl()` counted `align-right` and turned the keys, but it also reversed the top level, which is wrong for flex menus whose items keep DOM order on screen (`menu-align(right)` only justifies). Proposed as an NM amendment (below). A collision flip does not change the keys, as in Foundation. Source: FS `foundation.dropdownMenu.js:86-88, 213-263`; FS `_menu.scss` `menu-align` (lines 112-142).
20. **Vertical detection?** NM reads the root's computed `flex-direction`; Foundation's `_isVertical()` also treats a top-level `li` with computed `display: block` as vertical, which is how `$global-flexbox: false` builds express `.vertical` (`menu-direction(vertical)` sets `li { display: block }`). Proposed as a second NM amendment. Source: FS `foundation.dropdownMenu.js:82-84`; FS `_menu.scss:178-204`.
21. **RTL?** `Directionality` gives `opens-left` by default and turns the reading-direction keys; Foundation's `$global-left`/`$global-right` are the consumer's compile-time RTL build for arrow placement, which the mixin reuses. Source: NM; BB 1.5 RTL; FS `_dropdown-menu.scss`.

Round 5: WCAG 2.2 AA, each criterion.

22. **1.3.1, 1.3.2, 4.1.2, 2.4.6, 2.5.3**: native lists, buttons named by their text or `.submenu-toggle-text`, `aria-expanded`/`aria-controls` as host bindings in server HTML, no roles or `aria-haspopup`, submenus after their buttons in the DOM. Source: NM WCAG table; APG.
23. **1.4.3 Contrast**: passes on the page (4.65:1 for `$anchor-color` and `$dropdown-menu-item-color-active`); fails in Foundation's default Top Bar (`$light-gray`, 3.76:1, WCAG formula, unrounded), which is Foundation's documented placement and the source of the `.top-bar-right` rule. Required: a bar background on which both reach 4.5:1 (`$topbar-background: $white` in Storybook); the mixin `@warn`s (not `@error`, since it cannot know a Top Bar is used). Source: FS `_top-bar.scss:15-19, 49-57`; FS settings `$light-gray: #e6e6e6`, `$primary-color: #1779ba`; ADR 0022; the Off-canvas spec's `@warn` precedent for an anchor-colour pair.
24. **1.4.10 Reflow**: Foundation's 200 px `$dropdownmenu-min-width` fails at 320 CSS px for a narrow item about 120 to 200 px from the left (it fits neither side, and `opens-inner` keeps the left edge). A submenu at most half the page wide always fits one of Foundation's three sides: from an item starting in the left half, opening rightwards; from one ending in the right half, opening leftwards; a nested submenu that fits neither side fits `opens-inner` under its parent. Required: `$dropdownmenu-min-width: min(200px, 45vw)`, with a compile-time `@warn` for a fixed width over 160 px; e2e sweeps item offsets at 320 px. Source: FS `_dropdown-menu.scss:82-98, 219-251`; DD 1.4.10 row and D22 (the same half-page argument and 45vw margin).
25. **1.4.11 Non-text Contrast**: NM's compile-time `@error` for `$dropdownmenu-arrow-color` against the dropdown backgrounds and for the Hybrid toggle arrow against a set `$accordionmenu-submenu-toggle-background`, with unrounded ratios from `color-luminance()` (NM amendment of 2026-09-26); this spec adds the Hybrid toggle arrow (`$accordionmenu-arrow-color`) against the dropdown backgrounds when the toggle background is `null`, because the arrow then sits on the row's background. Source: NM Sass checks; FS `_accordion-menu.scss:139-163`.
26. **1.4.12 Text Spacing**: passes; `.is-dropdown-submenu` has a `min-width` and no fixed height or `overflow`. Source: FS `_dropdown-menu.scss:241-278`.
27. **1.4.13 Content on Hover or Focus**: dismissible (Light dismiss Escape from anywhere, no reopen until the pointer re-enters), hoverable (the item contains its submenu, so it is the Hover region), persistent (no hide timer while hovered; `closingTime` at least 100 ms after leaving; never while `autoclose` is off or after a click); nothing opens on focus. Source: AP hover intent; ADR 0024; APG disclosure navigation note.
28. **2.1.1, 2.1.2, 2.4.3, 3.2.1, 2.5.2**: Tab, Enter, and Space reach everything; hover has the click equivalent; nothing traps focus; closed submenus are `inert` and `display: none`; focus opens nothing; toggles act on `click`, Light dismiss needs both pointer ends outside. Source: NM; ADR 0024.
29. **2.4.7 Focus Visible**: the library removes no outline; Foundation's `disable-mouse-outline` acts only under what-input's mouse attribute, which the library never sets; submenus do not clip. Source: FS `_dropdown-menu.scss:149-151`; P50 row 22.
30. **2.4.11 Focus Not Obscured**: per-submenu focus-out close (P50 row 25 under `opens-inner`); a hover-opened submenu over a focused control elsewhere is dismissed with Escape without moving focus. Source: P50 row 25; ADR 0024.
31. **2.5.8 Target Size**: 38 px rows, 40 px Hybrid toggles; NM's `@error` below 24 px for the toggle settings. Source: P50 row 20; NM.
32. **Open nested parents' highlight?** Not twinned: Foundation paints an open nested parent's link through Menu's current-link style `.menu .is-active > a` (`$menu-item-background-active`, `$primary-color`), and a button twin would put the side arrow (`$primary-color`) on that background at 1:1, failing 1.4.11; the open state shows through the visible submenu and `aria-expanded`. The top-level twin (NM rule 11) stays because Foundation has dedicated dropdown settings for it. Source: FS `_menu.scss:382-385, 477-479`; FS `_dropdown-menu.scss:160-163`; R:menus 7.1.

Round 6: animation, hooks, rendering modes.

33. **Animation?** None, as in Foundation (`display` through `.js-dropdown-active`); completion in the render callback after the change; no `animate` input, although BB Table B suggested one: Foundation has no such Option, an exit needs a leaving phase NM's dropdown mode lacks, and a consumer can put an entrance keyframe on `.js-dropdown-active` in their own CSS. `nfsAnimationsToken` changes nothing here. Source: R:menus 3.8; NM Animation; BB 1.6 rule 1; ADR 0003.
34. **Render hooks?** Host bindings and host listeners for `.dropdown` and `jsaction`; the constructor for `configure()` and the Defaults token; one `afterNextRender` under `ngDevMode` for the `.top-bar-right` check; everything else is NM's and AP's (`afterNextRender` for focus and the ancestry walk, `afterRenderEffect` for collision, completion, Light dismiss, and hover). No `effect`, no own `afterRenderEffect`, no `afterEveryRender`. `injectAsync` not applicable: nothing loads after an interaction, AP decided eager loading, and the entry point already splits. Source: BB 1.5, 1.9; NM render hooks; AP loading.
35. **Rendering modes?** Server HTML carries the root class, Nest classes, `first-sub`, the Base side from `alignment`/`align-right`/`Directionality`, ARIA, and `inert`; nothing measured; `.top-bar-right` applies after hydration. Replay: toggle `click` and root `keydown` and `click` replay; the root carries `jsaction`, so links (action element not an `<a>`) navigate natively; hover never replays. One hydration boundary for the whole menu. `hydrate on hover` hydrates on the first hover without opening; `hydrate never` keeps links working and toggles inert. Source: ADR 0008; R:rendering 4, 7 (DropdownMenu row); NM Rendering modes; DD (the `hydrate on hover` case).

Round 7: CSS and tests.

36. **The `nfs-dropdown-menu` rules?** NM's dropdown assignments restated with reasons: the parent-button base rule with dropdown padding and background (rule 1), Hybrid link-arrow suppression (rule 8), button arrow twins (rule 10), the open top-level parent twin (rule 11); plus the checks of decisions 23 to 25 and 31. No custom property, no reduced-motion rule. Source: NM Sass (1) table; ADR 0012; BB 1.13.
37. **Testing seams?** The four layers with ST's wording; story ids `dropdown-menu--*`; this suite covers what the root adds and leaves NM's own stories to NM; layer 4 sweeps 1.4.10 at 320 px, a real mouse for 1.4.13, and the fixture route's `.top-bar-right` change, replay, and hydrate triggers. Source: BB 1.12; ST; STK sections 3, 5, 10; ADR 0018.

### Triage

Rule (map, Orchestration rules): impact HIGH when hard to reverse; confidence NOT HIGH when the default is bare, carried from a prototype without deliberation, or against the research or ADRs. Only HIGH with NOT-HIGH stays open.

1. **`opened`/`closed` carry the `NfsMenuItem`, no reason** (decision 5). Impact: HIGH (public output payload). Confidence: HIGH (BB 1.4's aggregate rule; NM's completion API passes only the item; the Accordion Menu spec uses the same shape). Decided.
2. **`closeOnClick` shared with Drilldown, each with its own default** (decision 13). Impact: HIGH (public input under ResponsiveMenu). Confidence: HIGH (Foundation's own behaviour; NM decision 8). Decided.
3. **Base-side open and close keys** (decision 19). Impact: medium (a behaviour of a shared utility's table, reversible in one handler; no API). Confidence: HIGH (Foundation's `_isRtl()` counts `align-right` for opening; the Base side is state the root already computes; the top level keeps NM's rule). Decided; proposed NM amendment 1.
4. **`$dropdownmenu-min-width: min(200px, 45vw)` required, with `@warn`** (decision 24). Impact: medium (a consumer settings contract, reversible). Confidence: HIGH (a geometric argument from Foundation's three placements; DD D22 precedent; e2e sweep). Decided.
5. **Top Bar contrast `@warn` and a Storybook `$topbar-background: $white`** (decision 23). Impact: medium (the Storybook override is shared by every story with a Top Bar). Confidence: HIGH (3.76:1 computed with the WCAG formula; the gate fails any story that shows Foundation's default Top Bar with links). Decided; cross-spec note below.

### Proposed glossary terms

**Base side**:
The side, left or right, toward which a dropdown-mode submenu opens before the collision check moves it; set by `alignment`, Foundation's `align-right`, a `.top-bar-right` ancestor, and the reading direction.
_Avoid_: alignment (the Option), default side, opening direction
