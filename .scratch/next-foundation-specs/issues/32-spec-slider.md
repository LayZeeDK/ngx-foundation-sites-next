## Answer

Spec: [specs/slider.md](../specs/slider.md). Resolved 2026-09-26 by self-grilling (AFK), both sides played against the sources below, with the [Prototype: Foundation-styled `<input type="range">` Slider](45-prototype-slider-range-input.md) as a binding input (its verdict, custom CSS list, hydration finding, and four OPEN FOR HUMAN items).

Gist: two attribute directives on consumer-written Foundation markup. `NfsSlider` (`[nfsSlider]`, the `.slider` container) takes Foundation's Options `start`, `end`, `step`, `vertical`, `disabled`, `clickSelect`, `decimal`, `nonLinearBase`, `positionValueFunction`, plus `disabledInteractive` and Material's `displayWith`; it binds `.slider`, `.vertical`, `.disabled`, and the `--nfs-slider-lo`/`--nfs-slider-hi` fill channel, exposes read-only `doubleSided` and `values`, and provides `nfsSliderToken`. `NfsSliderHandle` (`input[type=range][nfsSliderHandle]`, one or two) has a `value` model, `disabled` and `readonly` inputs, and a `touch` output, implementing `FormValueControl<number>` so `[formField]` binds it; Reactive and template-driven forms bind it with Angular's `ngNoCva` attribute. Foundation's `.slider-fill` span stays plain markup. Implementation level: native platform, no Aria, no CDK. The native `input`/`change` events replace `moved`/`changed.zf.slider`; the directives dispatch them for the changes they make themselves. `nfsSliderDefaultsToken` covers `step`, `decimal`, `nonLinearBase`, `positionValueFunction`. No animation; the `nfs-slider` Library mixin carries the prototype's rules plus two refinements and four additions, two of them for WCAG 2.2 AA: a 24 by 24 CSS px minimum thumb (2.5.8) and a compile-time `@error` when the fill or thumb colour is below 3:1 against the track (1.4.11), which Foundation's default fill (about 1.3:1) fails.

### Decision log

Sources: FS = the Foundation 6.9.0 clone (`js/foundation.slider.js`, `scss/components/_slider.scss`, `scss/forms/_range.scss`, `scss/util/_unit.scss`, `docs/pages/slider.md`); NG = the Angular 22.2.x clone (`packages/forms/signals/src/**`, `packages/forms/src/directives/**`, `packages/core/src/render3/instructions/control.ts`, `adev/src/content/guide/forms/signals/{custom-controls,migration}.md`, `CHANGELOG.md`); NGC = the components 22.2.x clone (`src/material/slider/**`); APG = the aria-practices clone (`content/patterns/slider/`, `slider-multithumb/`); P45 = the prototype ticket answer and `prototypes/slider-range-input/`; R:x = the research files by short name as `building-blocks.md` cites them; BB = `building-blocks.md`.

Round 1: what Foundation offers and what is settled already.

1. Q: Which Options exist? A: Exactly the 18 keys of `Slider.defaults` (FS `foundation.slider.js:571-706`; R:forms-media Slider Options); the ticket's list is right except that it omits `disabledClass` (audit 0001 H6). `invertVertical` is declared and never read (dead).
2. Q: Which events and methods? A: `moved.zf.slider` after the `Move` animation, `changed.zf.slider` `changedDelay` ms after the last change; public `setHandles()`/`_reflow()` only (FS `:106-118`, `:287-302`).
3. Q: Implementation level? A: Native `<input type="range">` for every form, settled by P45 (17 cases, axe WCAG 2.2 AA, three engines at current and target-era versions); no Aria slider exists (R:aria 10); the custom `role="slider"` fallback is not needed (BB Table A, corrected).
4. Q: Directive or component, and which markup? A: Directives: `[nfsSlider]` on `.slider`, `input[type=range][nfsSliderHandle]` per handle, `span.slider-fill` as plain markup; the hidden inputs go (P45 decision 2; ADR 0001; the repo skill's one-directive-per-Structural-class rule, with the fill having no behaviour).
5. Q: CDK drag-drop for pointer handling? A: No: the native input owns the pointer; `DragRef` would fight Foundation's percentage positioning (R:cdk drag-drop "Slider handles only").

Round 2: API.

6. Q: Where does the value live? A: A `value` model per handle (BB 1.4; NGC `slider-input.ts:94-127` value plus `valueChange`); the container has no model, only read-only `values`, so each value has one writer. `initialStart`/`initialEnd` become the handles' model values; an unbound handle starts at `0` clamped to its bounds (delta from Foundation's `initialEnd: 100`).
7. Q: Container aggregate event? A: None of its own: native `input`/`change` bubble to the container (WHATWG event dispatch), which is the aggregate; BB 1.4's `{item, value}` payload rule has nothing to add over `$event.target`.
8. Q: Outputs? A: Native `input` for `moved`, native `change` for `changed` (BB 1.4 mapping; R:material 7 "MatSliderChange is deprecated in favour of them"), `valueChange` from the model. `changedDelay` dropped: `change` already fires once per committed change; Signal Forms `debounce()` covers the rest. Material's `dragStart`/`dragEnd` not borrowed: Foundation has no drag events and native pointer events give the same moments.
9. Q: Do native events fire for changes the directive makes (track presses in the range form, non-linear keys)? A: Not by themselves (the native control did not change its value), so the directive dispatches bubbling `input` and `change` after it sets the model and the native value, and its own listener ignores them. Consumer-side model writes dispatch nothing, like a native `value` write.
10. Q: Names of the scale inputs? A: Foundation's `start`/`end`/`step` (map rule; AGENTS.md Input Naming), not Material's `min`/`max`.
11. Q: `vertical` input or class? A: An input that binds `.vertical`, because orientation changes directive behaviour (ADR 0010's exception); default read from the static class list, so Foundation's class alone works (FS docs require both class and option; the Button spec reads `.submit` the same way).
12. Q: `disabled` default mode? A: Native `disabled` by default, `disabledInteractive` opt-in, deviating from P45 decision 5. BB 1.10 gives native disabled to standalone native controls (Button D6), and it is the only mode enforced before hydration and in `hydrate never`: a focusable disabled range input's keys move the native value before hydration, which the adoption step would then take into the model. Default read from a static `.disabled` class, as Foundation's `_init` does (FS `:75-78`).
13. Q: `disabledClass`, `moveTime`, `invertVertical`, `binding`, `draggable`, `doubleSided`? A: Dropped: class-name option, timing option (BB 1.4), dead, replaced by binding one signal or field to several controls, the native control's own behaviour with no accessibility value (keeping it would need a CSS switch on the thumb pseudo-elements), and derived (read-only `doubleSided` signal).
14. Q: `displayWith` on the handle (P45) or the container? A: The container, Material's placement (NGC `slider.ts:366`), because both handles share one scale.
15. Q: `decimal`? A: Kept; rounds values the directive computes (track presses, non-linear mapping); native linear values are already exact.
16. Q: Defaults token keys? A: BB Table B's four: `step`, `decimal`, `nonLinearBase`, `positionValueFunction` (BB 1.4 shape B).
17. Q: Methods? A: None. `setHandles`/`_reflow` are unnecessary (CSS positions); `focus()` is native.
18. Q: DI shape? A: `nfsSliderToken` provided by the container with `useExisting`, injected by handles without `optional` (a lone range needs no directive; BB 1.9); registration in the constructor, unregistration on destroy; order is registration order on the server and first pass, re-sorted with `compareDocumentPosition` after a registration change on the client. No `MutationObserver` (BB 1.9's general form): two sibling inputs only reorder by being recreated. A third handle is a dev error.

Round 3: forms.

19. Q: Signal Forms? A: The handle implements `FormValueControl<number>`. NG `control.ts:349-366` marks any directive with a `value` model as the custom control, and `form_field.ts:382-397` takes the custom path ahead of the native one, so `[formField]` on the native input binds the directive. `control_custom.ts` then writes native `disabled`, `readonly`, `min`, `max`, `name`, `required` only for inputs the control does not declare, so the handle declares `disabled` and `readonly` (else Signal Forms would set native `disabled` against the `disabledInteractive` policy, and native `readonly`, which a range input ignores) and a `touch` output on blur (the custom path does not listen to `blur`, NG `control_custom.ts:25`).
20. Q: `readonly` semantics? A: `aria-readonly="true"` (WAI-ARIA 1.2 lists it for `slider`), keys and pointer blocked like the focusable disabled mode, no fade; otherwise a readonly field would stay editable.
21. Q: Schema `min()`/`max()` on a slider field? A: Not supported: Signal Forms would write the native `min`/`max` that carry the dependent bounds (NG `forms/src/directives/native.ts:51-81`). The scale is `start`/`end`; dev check 3 reports an overwrite.
22. Q: Reactive and template-driven forms? A: A `FormValueControl` works with them as is (NG `migration.md:453-515`), but on `input[type=range]` the built-in `RangeValueAccessor` matches `formControlName`/`formControl`/`ngModel` and wins (NG `ng_control.ts:215-225`), writing the native value past the model. The public `ngNoCva` attribute (NG `CHANGELOG.md`, commit 3983080236; `range_value_accessor.ts:49`) opts out; the docs require it and dev check 3 catches its absence.
23. Q: ControlValueAccessor as well? A: No; the forms guide says implement one contract, not both.
24. Q: Foundation's data binding? A: Bind the same signal or field to a `type="number"` input or an `<output>` (which `foundation-range-input` already styles, FS `_range.scss` `output`); `inputmode="decimal"` only for a `type="text"` input.

Round 4: keyboard, pointer, orientation, direction.

25. Q: Keys? A: Native for linear handles: arrows, Home, End, Page Up/Down at ten percent of the range in every engine (P45 "APG slider keys"); APG lists Page keys as optional larger steps. Foundation's `Shift+Arrow` fast step dropped (P45 decision 9).
26. Q: Two handles? A: Dependent native `min`/`max` (APG Multi-Thumb; ARIA in HTML forbids `aria-valuemin`/`max` on range), equal values allowed (APG; Foundation kept a one-step gap, FS `:208-216`), same-frame clamp in the input handler, the free thumb on top when they meet (P45 decisions 3, meeting-thumbs case).
27. Q: Track presses? A: Native for one handle; for the range form a container `click` listener (not `pointerdown`, P45 failure text) ignoring presses that began on an input, moving the nearest handle that can reach the press without crossing, focusing it. `clickSelect=false` on a range removes the only single-pointer alternative to dragging (WCAG 2.5.7); documented.
28. Q: Thumb length for track-press geometry? A: The Library mixin emits `--nfs-slider-thumb: rem-calc($slider-handle-width)` (FS `_unit.scss:30-104`, converting px, em, and unitless to rem), and the directive multiplies by the root font size; this replaces P45's rem-only parser note.
29. Q: Vertical? A: Rotated inputs inside Foundation's flipped `.slider.vertical`, `direction: ltr`, `aria-orientation="vertical"` (P45 decision 4); keys identical in both orientations. Chromium reports horizontal: OPEN FOR HUMAN 1.
30. Q: RTL source: `Directionality` (BB 1.5) or computed direction? A: Computed `direction` of the host, read in client event handlers only. The native input and the logical-property fill follow CSS direction; `Directionality` can disagree when a subtree sets `dir` without CDK's `Dir`. Documented exception to BB 1.5; no CDK dependency remains.
31. Q: Foundation compiled with `$global-text-direction: rtl`? A: Foundation mirrors `.slider:not(.vertical)` with `scale(-1, 1)` (FS `_slider.scss:134-139`) to pair with its JavaScript; with native inputs that mirror reverses them a second time, so the Library mixin cancels it under the same condition (new rule 12). P45 tested `dir="rtl"` with an LTR compile only; see Prototype needed.
32. Q: Non-linear scales? A: The native input carries the Bar position (0..1000, `step="any"`), the model the value mapped with Foundation's formulas (FS `:124-182`), `aria-valuetext` the value, and a keydown handler one value step per key, ten per Page key, the ends for Home/End (P45 decision 6). Dependent bounds for a non-linear range are in position units, generalising P45 (which gave non-linear inputs the full 0..1000 and no sibling clamp); see Prototype needed. Proposed ADR because the native value and form submission carry the position.
33. Q: Step snapping? A: From `start` (native rule); Foundation snaps from `0` (FS `_adjustValue`, `:412-435`); listed as a delta.

Round 5: rendering modes, animation, CSS, tests.

34. Q: Value channel and hydration? A: `[attr.value]` plus the live property in `afterRenderEffect`, adopting a pre-hydration value in the first client render (P45 decision 7 and its failure text). Refinement: adopt only when the native value differs numerically from the handle's own clamped native value (so a clamp or float formatting is not taken as user input), and never on a disabled or readonly handle, which restores its value instead.
35. Q: Replay? A: `input`, `keydown` on handles and `pointerdown`, `click` on the container replay; a replayed range-track press moves a handle after hydration; soft-disabled and non-linear keydown paths set state then call `preventDefault()`, which throws during replay (accepted default, BB Part 4 OPEN FOR HUMAN 3). `blur` is not replayed (R:rendering 4).
36. Q: `hydrate never` residue? A: The native control (BB 1.11 decision 7 lists Slider); no fill tracking, range-track presses, dependent bound updates, or non-linear value steps; a non-linear native submission sends the position.
37. Q: Animation? A: None. `$slider-transition` is documented by Foundation as not applying to the native slider and `foundation-range-input` has none (FS `_slider.scss:16-18`, `_range.scss`); the fill's transition is switched off (P45 rule 10). BB Table B's "`$slider-transition` on the thumb through the `foundation-range-input` mixin" is wrong; see proposed changes. No reduced-motion override needed.
38. Q: Custom CSS? A: P45's rules 1 to 11, binding, with two refinements (rule 5 `max(24px, $slider-handle-height)` so a larger thumb stays inside the box; rule 7 scoped to `.slider.disabled` so a disabled handle in an enabled slider keeps Foundation's fade) and four additions (rule 8 fade for a handle soft-disabled on its own, from `$slider-opacity-disabled`; rule 12 above; rules 0a and 5a for WCAG 2.2 AA, decisions 43 to 45). Rule 0 declares the lengths.
39. Q: Foundation mixin gaps? A: Focus outline (rule 6, WCAG 2.4.7), Firefox thumb border and radius (rule 9), target size (rules 5 and 5a, WCAG 2.5.8; decision 43).
40. Q: `foundation-everything`? A: Does not include `foundation-range-input` (FS `foundation.scss`; P45); the spec's Sass subsection requires the explicit include; proposed for the Sass packaging docs.
41. Q: Testing seams? A: The four BB 1.12 layers, with the prototype's pixel, drag, and AX-tree checks moved to e2e, the value maths and a Sass compile test in node-level Vitest, and the pre-hydration cases on the prerendered fixture app.

Round 6: WCAG 2.2 AA (user rule, restated 2026-09-26: every directive and component complies with WCAG 2.2 AA, so no AA criterion may be left as a recommendation).

42. Q: 2.1.1 Keyboard? A: Met by the native keys for linear handles (P45 "APG slider keys"), the directive's keydown handler for non-linear ones (one value step per key), and focusable-but-blocked keys for `disabledInteractive` and readonly handles; asserted in stories and e2e (spec, WCAG table).
43. Q: 2.5.8 Target Size (Minimum)? A: Guaranteed by default, replacing the earlier OPEN FOR HUMAN 3 default (a docs recommendation). The Library mixin sizes each thumb `max(24px, $slider-handle-width)` by `max(24px, $slider-handle-height)` and re-centres it with `margin-top: calc(($slider-height - max(24px, $slider-handle-height)) / 2)` (new rule 5a), and keeps the input box at `max(24px, $slider-handle-height)` (rule 5). Why Foundation cannot supply it: its default thumb is 1.4rem, 22.4 px at a 16 px root (FS `_range.scss` `$slider-handle-width`/`height`), `foundation-range-input` sizes the thumb from the settings with no floor, and it leaves the input box at the 0.5rem track height (P45 axe failure text). Meeting thumbs: the movable one is on top and is itself a full-size target (2.5.8's equivalent-control exception). The track-press geometry applies the same floor (`--nfs-slider-handle-width` plus the 24 px maximum). Enforced by axe `target-size` in every story (input box) and an e2e measurement of each painted thumb.
44. Q: 1.4.11 Non-text Contrast? A: A requirement, replacing the earlier OPEN FOR HUMAN 4 default (a docs recommendation): `$slider-fill-background` against `$slider-background`, and `$slider-handle-background` against `$slider-background`, at 3:1 or better. Foundation's defaults, `$medium-gray` #cacaca on `$light-gray` #e6e6e6, reach about 1.3:1 and fail; the default thumb `$primary-color` #1779ba reaches about 3.8:1 against the track and passes (ratios by the WCAG relative-luminance formula). A passing example fill is `$primary-color` (about 3.8:1 on the default track).
45. Q: How is 1.4.11 enforced: the story axe gate or a dev-mode check? A: Neither. axe-core 4.11 has no 1.4.11 rule: its contrast rules are `color-contrast` and `color-contrast-enhanced` (text, tags `wcag143` and above), and no rule carries a `wcag1411` tag (checked in this repo's `node_modules/axe-core/axe.js`), so the story gate cannot catch a failing fill. A reliable computation does exist in source: Foundation's own `color-contrast()` and `color-luminance()` (FS `scss/util/_color.scss:26-68`) implement the WCAG formula on Sass colours, and the settings are solid Sass colours, so the Library mixin checks both ratios at compile time and stops with `@error` naming the setting to change (new rule 0a). That compile-time check is the check; no runtime dev check is added, because reading computed colours at runtime is weaker than the exact compile-time value. The story Sass uses a passing fill, and the node-level Sass compile test asserts the `@error` with Foundation's defaults.
46. Q: 2.4.7 Focus Visible? A: `foundation-range-input` sets `:focus { outline: 0 }` and adds nothing (FS `_range.scss`), so the Library mixin's rule 6 draws a 2 px `$black` outline offset 2 px on the focused thumb (P45 "keyboard focus is visible on the thumb"); asserted by an e2e pixel check in three engines.
47. Q: 4.1.2 Name, Role, Value? A: Role, value, and bounds from the native input (WHATWG range state; dependent bounds on native `min`/`max`, never `aria-valuemin`/`max`, per ARIA in HTML); the name from `<label for>` or `aria-label`/`aria-labelledby` on the input, with dev check 2 for a missing one; human-readable values from `aria-valuetext` (`displayWith`, always on non-linear handles, where `aria-valuenow` is the Bar position); states from `disabled`, `aria-disabled`, `aria-readonly`. The announcement of `aria-valuetext` by screen readers stays OPEN FOR HUMAN 2.
48. Q: 2.5.7 Dragging Movements? A: A single press on the track moves a handle (native for one handle, the container's `click` handler for two); `clickSelect` defaults to `true`, and turning it off on a range slider is documented as a 2.5.7 failure (decision 27).

### OPEN FOR HUMAN

1. Vertical orientation: Chromium exposes a native range as horizontal whatever `aria-orientation` says, and the only fix inside the Browser target is a custom `role="slider"`. Default applied (P45's): native rotated inputs with `aria-orientation="vertical"`, accepted until `writing-mode` vertical controls are in target; keys behave identically in both orientations.
2. `aria-valuetext` on native range inputs needs a screen-reader check (NVDA with Chrome and Firefox, VoiceOver on macOS and iOS, TalkBack). Default applied: bind it from `displayWith`, and always on non-linear handles; the DOM attribute is asserted, the announcement is not.
The prototype's items 3 (thumb size) and 4 (fill contrast) are no longer open: WCAG 2.2 AA 2.5.8 and 1.4.11 are requirements for every directive, so the spec guarantees the 24 px thumb in the Library mixin and requires 3:1 fill and thumb colours, checked at compile time (decisions 43 to 45).

## Prototype needed

### Proposed glossary terms

**Handle**:
A native `<input type="range">` inside a Slider that carries one of its values; the library's replacement for Foundation's `.slider-handle` span.
_Avoid_: thumb (the draggable part a Handle draws), slider input, knob

**Bar position**:
Where a value sits along a Slider's track, as a fraction from its start; equal to the value's share of the range except on a non-linear Slider, whose Handles carry it natively.
_Avoid_: percentage, pctOfBar, offset

### Proposed ADR

[adr/0020-slider-non-linear-bar-position.md](../adr/0020-slider-non-linear-bar-position.md): "A non-linear Slider handle's native input carries the Bar position, not the value". It meets the bar. Hard to reverse: the native value, `aria-valuenow`, and native form submissions of every non-linear slider depend on it. Surprising: a native form posts 0..1000 instead of the value. A real trade-off: a custom `role="slider"` for non-linear scales, or dropping them.

### Proposed building-blocks changes

1. 49. Q: Where does a pre-hydration native change enter the model: the write phase's first pass (the P45 design, decision 34) or the replayed native `input`? A: The replayed `input`. The first pass leaves an enabled handle's differing native value alone and only marks itself done; a disabled or readonly handle still restores its value there. Why: the early contract queues every native `input` a drag or a key's default action fires, and the handle's `input` listener reads the live native value, so replaying it is idempotent. Adopting in the write phase turns the engine's native drift into the model before the replayed `keydown` adds its step on top (P64's double-step finding). Decision 34's numeric-comparison refinement is dropped, because nothing adopts in the write phase any more. Replaces decision 34's adoption clause.
50. Q: Is deferring to the replayed `input` enough to make a replayed non-linear key count once? A: No, and that is the real cause of P64's Firefox failure. `ecrd` replays the queue synchronously in arrival order after `whenStable()`, so the `keydown` replays before its companion `input`, with no `afterRenderEffect` between them. P64's key handler set the model and left the native write for later, so the companion `input` read the native drift and overwrote the step. Checked against P64's own numbers (`log`, base 5, at 50 = position 309.02): Chromium and WebKit drift by 10 to 319.02, which maps to 51 by coincidence; Firefox drifts by 1 to 310.02, which maps to 50, and its native value stays at 310.02 because the model's native value never changed. At 5 on the same scale, a drift of 10 maps to 7, so Chromium would take two steps there. Decision: the non-linear key handler writes the live native value inside the handler (the spec already said directive-made changes write it) before `preventDefault()`, so the companion `input` reads the directive's position and maps it back to the same value (value to position to value round-trips for every step, checked for 0..100). Accepted edge case: a key and then a drag on the same non-linear handle, both before hydration, ends at the key's step. Rejected: skipping replayed `input` by reading `eventPhase === 101` (internal constant; building-blocks Part 4 item 3). Replaces P64 decision 6's "known Firefox limitation" with a fix; the limitation text is the documented fallback if the e2e case still fails in Firefox.
51. Q: Does the design depend on event replay being on? A: Yes. It is on by default in Angular 22: `provideClientHydration()` adds incremental hydration unless `withNoIncrementalHydration()` is given, and incremental hydration provides `withEventReplay()`. An app that opts out of both keeps the pre-hydration value on screen, but the model does not learn it until the next change; the docs say so. Rejected: detecting replay from the `jsaction` attribute (internal).
52. Q: Non-linear range dependent bounds? A: In Bar-position units on both handles (`fraction(siblingValue) * 1000`) for native `min`/`max`, the `input` clamp, and `--nfs-slider-span` (divided by 1000); the key handler clamps in value units. P64 case 2 passed in three engines. A two-handle non-linear example is added to Rendered HTML (values 25 and 75: positions 123.84 and 585.93, spans 0.586 and 0.876). Confirms decision 32's generalisation.
53. Q: Home and End on a non-linear range handle? A: The dependent bound (End on the minimum to the maximum's value, Home on the maximum to the minimum's value), as on a linear handle, whose native `min`/`max` already do this; the scale ends only on the free side. APG Multi-Thumb; P64 case 2d. The keyboard table states it per scale type.
54. Q: Rule 12 and right-to-left keys? A: Rule 12 unchanged, confirmed under a real `$global-text-direction: rtl` compile (P64 case 3a); P45's right-to-left fixture never exercised it. Keys: Chromium and Firefox reverse Left and Right on a native range under `dir="rtl"`, WebKit does not (P64 case 3b). The non-linear handler keeps reversing in every engine; linear keys stay native, so on WebKit alone the two scale types disagree in right-to-left. Documented, not overridden (that would take over every linear key on one engine). Impact LOW, confidence HIGH: decided.
55. Q: Forced colours? A: New rule 13. `foundation-range-input`'s `appearance: none` takes the thumb out of the system-colour treatment, so the forced `Canvas` background paints the thumb and fill invisible (P64 case 3c, Chromium and Firefox). Colours checked against CSS Color 4: thumb `CanvasText` instead of P64's `ButtonText`, because `CanvasText` on `Canvas` (the track) is the pair CSS Color 4 guarantees and `ButtonText` belongs on `ButtonFace`. Fill `Highlight` (a selection). Focused thumb outline `CanvasText`, because rule 6's `$black` is no longer forced once `forced-color-adjust: none` applies. Disabled thumbs `GrayText`. Track edge a `CanvasText` outline, not P64's border, so the track box and the track-press geometry keep their size. `forced-color-adjust: none` goes on the input and the fill, not on `.slider` as in P64, because the property is inherited. The WCAG table gains a forced-colours 1.4.11 row and a 1.4.1 row, and 2.4.7 names the forced outline. WebKit: Playwright cannot emulate forced colours there, and Safari has no forced-colours mode, so this is not a gap. The `CanvasText` and outline changes from P64's measured rule are unmeasured; the forced-colours e2e case in Chromium and Firefox covers them.
