## Question

What Angular directives (preferred) or components give Foundation for Sites 6.9's Flexbox Utilities to the next, from-scratch ngx-foundation-sites repo, under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Foundation's docs page is `docs/pages/flexbox-utilities.md` and its Sass is `scss/components/_flex.scss` in the 6.9.0 clone. Publish `specs/flexbox-utilities.md`.

Known from the triage: Alignment, direction, and order Variants, responsive forms included; ordering must not break reading and focus order (1.3.2, 2.4.3).

### Measurements made for this ticket

Several questions needed facts the bundle did not have, so the ticket measured them in a throwaway workspace (`D:/tmp/nfs-wave-103/`, not committed; no server and no port; the repository's `node_modules` linked in through a junction that was removed at the end; Playwright 1.63 read from the existing `D:/tmp/nfs-ct-prototype` install). Foundation 6.9.0 Sass from the repository's `foundation-sites` package, compiled with Dart Sass 1.93.2 (the repository's install; the effort's pin is 1.104.1, and nothing measured depends on the difference); Chromium, Firefox, and WebKit through Playwright 1.63.

- E1, the generated class set (`compile.mjs`): `@include foundation-flex-classes` over Foundation's defaults emits 56 classes of the family (plus `.vertical` and `.menu` inside the vertical-menu rule): `.align-left`, `-right`, `-center`, `-justify`, `-spaced`; `.align-top`, `-middle`, `-bottom`, `-stretch` and their `.align-self-*`; `.align-center-middle`; `.small-order-1` to `.large-order-6` (the Zero breakpoint prefixed, each breakpoint above it in its media query); `.flex-container`, the three `.flex-child-*`, the four `.flex-dir-*`; and their `medium-` and `large-` forms, with no `small-` form. `$flexbox-responsive-breakpoints: false` removes exactly those 16 responsive helpers and keeps the order classes; `$flex-source-ordering-count: 12` adds `.large-order-12`; `$breakpoint-classes: (small medium large xlarge)` adds `xlarge-` forms of both; a right-to-left compile emits the same set. `.align-center-middle` is emitted after the axis classes and sets `align-content: center` beside both axes; the vertical-menu rule covers only `left`, `right`, and `center`.
- E2, central alignment against the pair (`probe.mjs`): in a 300 px high XY grid of four third-width cells (two lines), the first line starts 63 px down under `.align-center.align-middle` and 126 px down under `.align-center-middle`, in all three engines.
- E3, visual, DOM, and Tab order (`probe.mjs`), at 400, 800, and 1100 px in three engines: Foundation's Source Ordering example with a link in each cell shows the second DOM cell first at 400 px and in DOM order from 800 px; a `.flex-container.flex-dir-row-reverse` of three links shows them reversed; `.flex-dir-column.large-flex-dir-column-reverse` reverses only at 1100 px; three items with orders 3, 3, 1 show as 3, 1, 2. A prediction from computed style alone (element children that are not `display: none` or absolutely positioned, stably sorted by computed `order`, reversed for a `-reverse` computed `flex-direction`) equals the rendered sequence (sorted by rectangle) in every case, engine, and width. Tab follows the DOM order in Chromium and Firefox; WebKit's default Tab does not reach links, as Safari's.
- E4, physical names in a right-to-left region (`probe.mjs`): `.flex-container.align-right` inside `dir="rtl"` in a left-to-right compile puts its item at the left edge in three engines.
- E5, the `hidden` attribute (`hidden.mjs`), with `foundation-everything` on defaults: `<div class="flex-container" hidden>` and `<div class="grid-x" hidden>` compute `display: flex` in three engines; `.flex-container.is-hidden` and a plain `div[hidden]` compute `none`.
- E6, the candidate Library mixin (`_nfs-flexbox-utilities.scss`, `mixin.mjs`): over Foundation's defaults it emits exactly `:root { --nfs-flex-source-ordering-count: 6; --nfs-flexbox-responsive-breakpoints: medium large; }`; with the flag off the second property is empty (`unquote('')`); a count of 12 writes 12; an added `xlarge` writes `medium large xlarge`; `$breakpoint-classes: (medium large)` writes `medium large`.
- E7, prior art (`flex-layout.json`, the unpacked tarball): `@angular/flex-layout`'s last release, 15.0.0-beta.42 (2023-01-24), is marked deprecated by the registry ("This package has been deprecated. Please see https://blog.angular.io/modern-css-in-angular-layouts-4a259dca9127"); its flex entry point declares `fxLayout`, `fxLayoutGap`, `fxFlex`, `fxFlexOrder`, `fxFlexOffset`, `fxFlexAlign`, and `fxLayoutAlign`, each with inputs per breakpoint and range (`fxLayout.xs`, `fxLayout.gt-sm`), applied as inline styles from a media marshaller, with a `FlexLayoutServerModule` for server rendering.
- E8, CSS Flexbox Level 1 (fetched from w3.org; markdown.new returned a Cloudflare challenge page), section 5: "The reordering capabilities of flex layout intentionally affect only the visual rendering, leaving speech order and navigation based on the source order", and "Authors must not use order or the *-reverse values of flex-flow/flex-direction as a substitute for correct source ordering, as that can ruin the accessibility of the document."
- Sources read: Foundation's flexbox utilities docs page, flex Sass partial, flex utility mixins, global settings, menu partial (`menu-align`), flex grid partial, and breakpoint iterator; the docs pages that use the classes (Button Group, Flex Grid, Media Object, Menu, Abide, Forms, Smooth Scroll); CDK 22.2's `InteractivityChecker`; ADR 0001, 0012, 0022, 0039, and 0040; building-blocks 1.1 to 1.14 and Table D; `CONTEXT.md`; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md); `research/out-of-scope-triage.md` (section 4 and the grids' paragraph that names the source-ordering hazard), `research/foundation-component-catalogue.md` (the Flexbox Utilities row), and `research/out-of-scope-exclusions.md` (no row names this family); the [Spec: Menu](../specs/menu.md), [Spec: Button Group](../specs/button-group.md), [Spec: Equalizer](../specs/equalizer.md), [Spec: Card](../specs/card.md), [Spec: Label](../specs/label.md), [Spec: Breakpoint service (shared utility)](../specs/breakpoint-service.md) (the Variant check), and [Spec: Variant declaration tooling](../specs/variant-declaration-tooling.md), and the tickets of the Menu, Button Group, and Sticky re-run.

### Grilling record

Round 1 (nothing settled yet).

- Q1, how many directives, and what each owns. For one directive per class family (seven attributes): one attribute per Foundation class family, a one-to-one map. Against: seven selectors for one docs page, and ADR 0040 puts families as inputs on the directive that owns them. For one `nfsFlex` directive with every input: one attribute. Against: a Flex parent would carry child inputs and a child parent inputs, and alignment must also sit on flex parents that are not `.flex-container`. For the docs' own roles: Foundation's page is written around the flex parent and the flex child, and parent alignment works on Foundation's own flex parents (grid, Button Group, Media Object, Card, Menu) without `.flex-container`. Settled: three directives, `NfsFlexContainer` (the vanilla container and direction, hosting `NfsFlexAlign`), `NfsFlexAlign` (parent alignment on any Flex parent), `NfsFlexChild` (child size, self alignment, order) (decision 1).
- Q2, who owns `.align-*` on Foundation's other flex parents. For each component's own inputs: `<div nfsGridX alignX="center">` reads well. Against: one class family with five owners, which ADR 0039's one-owner reading and the Button Group spec's D9 reject. Settled: this family's directives are the one owner; other specs write them beside their directives or host them under the same input names, never declare their own (decision 8).
- Q3, input names for parent alignment. For `align` plus `alignY`: the Menu names its horizontal family `align`. Against: an asymmetric pair, and the Menu's `align` is its own three-name family from `menu-align`. For `justify` and `alignItems`: the CSS properties. Against: building-blocks 1.4 rule 3 names by Foundation's dimension, not CSS's. For one two-axis string (`fxLayoutAlign`): Foundation's two name sets are disjoint. Against: two sets that do not exclude each other are two inputs (rule 3), and a pair string invites confusing `'center middle'` with central alignment. Settled: `alignX` and `alignY`, from Foundation's `flex-align($x, $y)`; `alignSelf` from the class template `align-self-` and `flex-align-self($y)` (decisions 2, 3).
- Q4, `.align-center-middle`. For mapping `alignX="center" alignY="middle"` to it: one spelling. Against: measured (E2), it looks different in a wrapping parent, so the pair and the central class are two Variants. Settled: the boolean `alignCenterMiddle` (rule 4) and a development warning when it is combined with an axis input, which it overrides (decision 4).
- Q5, the vanilla container's own class and its responsive form. For a static class and a `from` input: the directive binds its class like a Structural-class directive. Against: `.medium-flex-container` is the same family, and ADR 0040 gives an on-or-off responsive family one input taking `true` or a query. Settled: `nfsFlexContainer` itself is that input, the bare attribute `true`, a query with `up` (the only forms Foundation generates) selecting the responsive class, the Zero breakpoint filling Foundation's gap; `direction` a bare value or rules (decision 5).
- Q6, the child's size input. For a `flex` input: explicit. Against: `size` means columns in the grids, `flex` is a CSS word, and the Equalizer spec already writes `nfsFlexChild="grow"`. Settled: `nfsFlexChild` itself, a name or rules, the bare attribute a marker that sets no class, for a child that takes only `alignSelf` or `order` (decision 6).

Round 2 (Q1 to Q6 settled).

- Q7, `order`'s type and mapping. Building-blocks 1.4 names it `order`; ADR 0040 types a count through `NfsOverridableCount` and a transform that adds the static-attribute strings; the registry and property already exist in the tooling spec's table. Foundation prefixes the Zero breakpoint in this family (E1), so a bare value sets `.small-order-<n>` and there is no gap. Settled (decision 7).
- Q8, the ordering hazard (1.3.2, 2.4.3). For documentation only (the triage's first recommendation): the directives cannot judge meaning. Against: the user ruled typed ordering in, and ADR 0022 wants a signal where axe has none. For refusing `order` where focusable content exists: against ADR 0039's every-class rule, and the directive cannot know content at compile time. For a development check: the part the directives can see is focusable content shown out of DOM order, and computed style predicts the rendered order exactly (E3). For CSS `reading-flow`: out of the Browser target. Settled: the DOM order is the reading and focus order, a requirement shown in every recipe and asserted by every story; `NfsFlexChild` (with `order`) and `NfsFlexContainer` (with a reverse direction) report a Flex parent whose focusable items are shown out of DOM order at the current breakpoint, re-run on `NfsMediaQuery.current()` in development builds (decisions 9, 10).
- Q9, class binding: a record that strips copied classes, or a list. For the record (the Menu, the Switch): copied classes vanish. Against: `NfsMenu`'s record binds `align-left`, `align-right`, and `align-center` as `true` or `false`, and a second record on a menu would fight it; the order and responsive families depend on the consumer's count and Class breakpoints, which a record cannot enumerate at compile time. Settled: one `computed` list per directive, the Button and Label rule, with a development report for copied classes (decision 12).
- Q10, the menu. For forbidding `nfsFlexAlign` on menus (the Menu ticket's note): no key conflict. Against: `.align-justify`, `.align-spaced`, and vertical alignment on a menu would have no home, and the Menu spec's Out of Scope already points them here. Settled: allowed, with a warning for the Menu's own three names (decision 11).
- Q11, the Library mixin. An Open Variant family (the count) needs one (ADR 0012, ADR 0040); the flag-gated responsive helpers need a property of their own (the tooling spec's rule), listing exactly the breakpoints Foundation generates them for (E6). Settled: properties-only `nfs-flexbox-utilities`, included after `foundation-flex-classes` (decision 13).
- Q12, the Runtime check calls. Settled from the Breakpoint service spec's rules: `include()` only while a value that reads a property is bound (the mixin holds nothing the directives need otherwise), needs from the class mapping, and no call from `NfsFlexAlign`, whose families are closed (decision 14).

Round 3 (Q7 to Q12 settled).

- Q13, the other development checks. Copied classes (building-blocks 1.4); an alignment or a child outside a Flex parent, which does nothing silently, sparing hosts that are Flex parents only from a breakpoint up and accepting grid parents for the child's `order` and `alignSelf`; central alignment combined with an axis. Settled (decisions 4, 12, 15).
- Q14, physical names, column parents, and `hidden`. For mapping `left` and `right` through `Directionality`: logical intent. Against: Foundation compiles them against `$global-text-direction` (E4), and a JavaScript swap would fight a right-to-left compile; the Menu documents the same behaviour. Settled: documented, as the Menu's are; the column-axis note and the measured `hidden` finding (E5) go in the spec's Notes, and the `hidden` finding is proposed for building-blocks 1.10 because it holds for every Foundation class that sets `display` (decision 16).
- Q15, rendering modes. Host bindings only, no listener, breakpoint-dependent classes as Foundation's media queries, the Zero breakpoint from the token on both sides; development checks and Runtime check requests in render callbacks only. Settled (decision 17).
- Q16, reflow (1.4.10). For a check on the host's overflow: it would catch a row that scrolls the page. Against: a width against the viewport has no stable first-render answer (the Label spec's D13), and Foundation's responsive example already stacks at the Zero breakpoint. Settled: a requirement, followed by every row story and asserted by an e2e at 320 px (decision 18).
- Q17, entry point, names, stories, and the title group. Settled: `ngx-foundation-sites/flexbox-utilities`, `NfsFlexContainer`, `NfsFlexAlign`, `NfsFlexChild`, no `exportAs`, story ids `flexbox-utilities--<story>`, title `Utilities/Flexbox Utilities`, a group the Storybook conventions do not have yet (decision 19).
- Q18, the Material comparison. Material and the CDK have no layout directives; `@angular/flex-layout` (deprecated upstream, E7) is the nearest Angular prior art. Settled: compared, its parent-child split and child order borrowed, its inline styles, per-breakpoint inputs, and pair string not (decision 20).
- Q19, glossary. Foundation's docs name the roles "flex parent" and "flex child" and the feature "source ordering", and other specs use the ideas; "flex container" is also a Foundation class. Settled: three terms (decision 21).

The frontier is empty: every branch above was visited, and nothing was left to a bare default.

### Decisions

1. Three attribute directives in `ngx-foundation-sites/flexbox-utilities`, by the docs' roles, on any element: `[nfsFlexContainer]` (`NfsFlexContainer`: `.flex-container` and its responsive form, `direction`; hosts `NfsFlexAlign`), `[nfsFlexAlign]` (`NfsFlexAlign`: `alignX`, `alignY`, `alignCenterMiddle`), `[nfsFlexChild]` (`NfsFlexChild`: its own size value, `alignSelf`, `order`). No token, no providers, no Defaults token, no outputs, methods, models, or `exportAs`.
2. `alignX: NfsFlexAlignX` (`left`, `right`, `center`, `justify`, `spaced`; `.align-left` included because the Sass generates it) and `alignY: NfsFlexAlignY` (`top`, `middle`, `bottom`, `stretch`), closed, named for Foundation's `flex-align($x, $y)`.
3. `alignSelf: NfsFlexAlignY` on `NfsFlexChild`, closed, one alias with `alignY`.
4. `alignCenterMiddle`, a boolean through `nfsVariantBoolean`, distinct from the pair (measured, E2); a development warning when it is combined with `alignX` or `alignY`.
5. `nfsFlexContainer`, the selector-named input: `NfsVariantBoolean | NfsClassBreakpointQuery<'up'>`, default `false`, the bare attribute `true`; the Zero breakpoint and `true` set `.flex-container`, a higher breakpoint `.<bp>-flex-container`. `direction: NfsFlexDirection | NfsClassBreakpointRules<NfsFlexDirection>`, the Zero-breakpoint key setting the unprefixed class.
6. `nfsFlexChild`, the selector-named input: `'' | NfsFlexChildSize | NfsClassBreakpointRules<NfsFlexChildSize>`; the bare attribute sets none.
7. `order: NfsFlexOrderInput` over `NfsFlexOrder = NfsOverridableCount<6, NfsFlexSourceOrderingCountOverrides>`, a count or rules of counts, static strings `'1'` to `'6'` through its transform; a bare value sets `.<zero>-order-<n>`.
8. One owner for every class of the family, on every element: other specs write these directives beside their own or host them through `hostDirectives` exposing `alignX`, `alignY`, `alignCenterMiddle`, `alignSelf`, and `order` under those names, and declare no inputs for these classes. The spec documents the beside form; hosting is each Flex parent's or Flex child's own spec to choose.
9. The DOM order is the reading and focus order: a requirement (1.3.2) shown in every recipe and asserted by every story; no reordered story item holds focusable content.
10. A development visual-order check (2.4.3): `NfsFlexChild` while `order` is bound checks its parent, `NfsFlexContainer` while `direction` holds a reverse value checks its host; flex parents only; the sequence predicted from computed `order` and `flex-direction` (E3); items holding CDK-tabbable content compared with the DOM order; one warning per container and distinct sequence, re-run on `NfsMediaQuery.current()`; one or no focusable item never warns.
11. `nfsFlexAlign` on a menu offers `justify`, `spaced`, `alignY`, and `alignCenterMiddle`, and warns in development for `left`, `right`, and `center`, which the Menu's `align` owns there; the check reads the host's `.menu` class after render, with no import of the Menu entry point.
12. One `computed` `[class]` list per directive; copied Foundation classes are not stripped and are reported in development, naming the inputs.
13. `nfs-flexbox-utilities`, a properties-only Library mixin included after `foundation-flex-classes`: `--nfs-flex-source-ordering-count` (never empty) and the flag-gated `--nfs-flexbox-responsive-breakpoints` (the Class breakpoints above the Zero breakpoint, empty while `$flexbox-responsive-breakpoints` is off; not in the manifest). No required setting and no layout rule.
14. Runtime checks: `NfsFlexContainer` and `NfsFlexChild` call `include('nfs-flexbox-utilities', ['flex-source-ordering-count'])` and `include('nfs-breakpoint-properties', ['breakpoint-classes'])` only while a value that reads a property is bound, and `value()` with needs from the class mapping (`flex-source-ordering-count`, `breakpoint-classes`, `flexbox-responsive-breakpoints`); `NfsFlexAlign` makes no call.
15. Development warnings for an `nfsFlexAlign` host, or an `nfsFlexChild` parent, that is not a Flex parent at the first render (a responsive container class counts as one; a grid parent counts for the child).
16. Physical names stay physical (no `Directionality` mapping); the column-axis note and the `hidden` finding (E5) are documented.
17. Rendering modes: host bindings only, no listener and no `jsaction`, server HTML equal to the hydrated DOM, breakpoint forms as Foundation's media queries, the Zero breakpoint from `nfsBreakpointsToken`; checks in render callbacks only.
18. Reflow: a row that cannot shrink to 320 CSS px stacks at the Zero breakpoint through `direction` rules; required, followed by every row story, asserted by an e2e; no check.
19. Stories `flexbox-utilities--horizontal-alignment`, `--vertical-alignment`, `--align-self`, `--central-alignment`, `--flex-container`, `--responsive`, `--source-ordering`, `--button-group`, `--fixture`; title `Utilities/Flexbox Utilities`; `component: NfsFlexContainer`; e2e for breakpoint geometry, reflow at 320 px, and the fixture app's first paint and hydration; no Anti-pattern story and no manual assistive-technology test.
20. Native implementation level; no Aria; CDK's `InteractivityChecker` and the Breakpoint service only in development builds. `@angular/flex-layout` is the Material-comparison prior art (deprecated upstream).
21. Glossary: **Flex parent**, **Flex child**, **Source ordering**.

5. `CONTEXT.md`, Foundation side, after **Utility class**, new terms:

   ```markdown
   **Flex parent**:
   An element laid out with `display: flex` whose children the Flexbox Utilities' alignment classes place: a Foundation grid, Button Group, Media Object, Card, or Menu, or any element the `.flex-container` class makes one.
   _Avoid_: flex container (CSS's term, and the name of the one Foundation class that makes any element a flex parent), flexbox parent, row

   **Flex child**:
   An immediate child of a Flex parent, which can align itself, take a share of the space, or take another place in the visual order.
   _Avoid_: flex item (CSS's term), cell (the XY Grid's element), column

   **Source ordering**:
   Foundation's per-breakpoint change of the visual order of Flex children through its order classes, which leaves the DOM order, the reading and focus order, as written.
   _Avoid_: reordering (bare), push and pull (the Float Grid's own mechanism), sort order
   ```
