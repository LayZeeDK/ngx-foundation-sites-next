# 75. Decide the `@angular/aria` fallback confirmation

Type: grilling
Status: resolved
Blocked by: none

## Question

The README open list's confirmation item names nine places where a spec does not use an available `@angular/aria` building block; the repository's `AGENTS.md` asks for confirmation before such a fallback, and the user has ruled that this pass resolves it autonomously (map, "Open-decision pass"). For each of the nine fallbacks, decide: confirm the fallback, overrule it (the spec adopts the Aria building block), or confirm it with a condition. Each decision rests on whether the spec's stated reason is true in `@angular/aria` 22.2 (source file and line in the components clone), whether anything on Aria's `main` branch or in a newer prerelease changes it, and what using the Aria building block would cost (API, server HTML, WCAG 2.2 AA, Foundation markup).

## How to work it

The orchestrator runs it: an evidence dossier at `research/aria-fallback-evidence.md` (one section per fallback, facts only, cited), then two adversarial reviewers (one on Opus arguing to overrule each fallback, one on Fable attacking the Aria alternative), then a judge who decides each fallback and writes the `## Answer` here with one decision per fallback, its evidence, and the dissent. Any overruled fallback lists the exact spec changes.

### 1. Orbit slides do not host Aria's `TabPanel`: overruled, with two conditions

Decision. `NfsOrbitSlide` hosts Aria's `TabPanel` (exposing `value` and `id`) and binds `[attr.inert]` itself, computed from `inject(TabPanel).visible()` and the Orbit's `live` signal: `live ? (visible ? null : true) : (visible ? null : undefined)`. ADR 0025's decision stands; ADR 0037 supersedes ADR 0034. Condition 1: the Orbit writes Aria's `selectedTab` synchronously at the points where mechanic 8 records a handoff (the `selected` model's change notification, `ngOnChanges` for a parent binding, and so the live flip's reconciliation). Condition 2: every spec test about `inert` before live asserts presence (`hasAttribute('inert')` at each observation), never the absence of mutation records.

Why. The stated reason (README item 1; `specs/orbit.md` "Why custom for the slides"; ADR 0034's last consequence; the re-run's triage "no binding-based variant can pass") is a universal claim, and one counterexample defeats it. The counterexample is measured three ways: in the server renderer (probe G `g5`, `g6`: Foundation's order, `@for`, a selection changing in a later server pass); end to end in the prototype that produced ADR 0034's measurement, whose failing `inert` gate passes in Chromium, Firefox, and WebKit (27 of 27 cases, re-run by the judge); and in server HTML with a bound non-first slide (read by the judge; not captured). The mechanism is read from source (above) and reproduced in the same run as the failure it replaces (`g1` fails beside `g5`): Aria's `inert` changes only when `visible()` changes, the derived value changes in exactly those passes (between `null` and `undefined` before live, both rendered as no attribute), and the slide's binding is applied after its host directive's. `g1` against `g4` closes the dossier's 1.4 unknowns: the plain override lost because slides inside `@for` bind before the bullets' `@for` views register a tab, and document order is no fix (`g7`). With the misfit gone, `AGENTS.md` applies ("Always use Angular ARIA building blocks first. Ask before falling back to alternatives"): Aria renders the slide's `role`, `id`, `tabindex`, `aria-labelledby`, and the bullet's `aria-controls`, which removes the custom contract's static role and four bindings, the slide id generator, the pairing lookup, the bullet's `aria-controls` override, and two of the three halves of dev check 6 (Aria reports a slide without a bullet and a bullet without a slide). The Orbit then uses the same primitive as the Tabs spec. Nothing on `main` or in a newer prerelease changes `TabPanel` (dossier, "What is on `main` or newer").

Why the two conditions. Once live, a slide's `inert` and `tabindex` follow Aria's selected tab, not the Orbit's model. The spec's first render callback reconciles the selection and flips `live` in one write phase (mechanic 4), so that a slide in view, and a focus inside it, never meets `inert`. If Aria's `selectedTab` were written a pass later, the adopted slide's override would turn from `undefined` to `true` in the live-flip pass while Aria still reads the old selection, and that slide would become `inert` with focus inside it; the focus handoff (mechanic 8) needs the new slide's `inert` lifted in the pass that renders the change for the same reason. The spec's Selection link bullet says only "whenever its own selection changes", so it must name the synchronous points. The keyboard prototype met this by a template binding (`[selectedTab]="selectedValue()"`), which the library's directives cannot use. Condition 2 follows from the judge's probe: the transient is harmless (never rendered; focus unchanged in three engines), but the spec's browser-level and e2e cases worded as "a `MutationObserver` ... records no `inert` at any point" would fail on its two writes while testing nothing a user can observe.

Weighing. The confirm-side reviewer's strongest argument was that the measurement (two binding forms, three engines) stands whatever its explanation, and that any repair would rest on document order, the opposite of Foundation's markup and uncheckable at compile time. The new measurement is in Foundation's order with `@for`, survives a late selection change, and depends on no order, so both halves fall; their rule, which explained both the failure and the bullets' `tabindex` success, is kept with the third clause it lacked. Their second argument, that Aria-first is an order of preference and `TabPanel` is attributes only, meets `AGENTS.md`'s wording, which requires confirmation before any fallback and so treats Aria-first as a rule with an exception process; the exception needs a true reason, and the stated one is false. The overrule-side reviewer's own counterpoint, that the override rests on an unwritten Angular detail (`Object.is` in `bindingUpdated`) and on Aria keeping `inert` a function of `visible()`, is real; it is priced in as the SSR fixtures, the live-gate test, and a code comment, and the judge adds the two conditions the reviewer left optional or unseen (the reviewer offered the selection link "synchronously ... or through a binding evaluated in that pass", and did not look at the client transient).

Dissent. (1) The custom contract depended on no comparison detail of Angular's binding instruction; the override does, and a future Angular that treated `null` and `undefined` as one binding value, or an Aria whose `inert` depended on more than `visible()`, would break it silently in server HTML. Answer: the late-selection SSR fixture fails on the first such update. (2) A `computed` that returns `undefined` in one branch and `null` in another for the same rendered result invites a "simplification"; the ADR, the spec's binding precedence paragraph, and the code comment carry the reason. (3) The override adds a set-and-remove write pair on every unselected slide at hydration, which a `MutationObserver`-based consumer tool would see; measured unobservable to rendering and focus in three engines, not measured with a screen reader (the assistive-technology decision covers slides entering and leaving `inert`). (4) The library's own directives are not built yet; the prototype's `SlideGate` and a probe wrapper carry the evidence, and the spec's tests are the first run of the real code. Reopening facts: a `TabPanel` whose `inert` is an input or absent on the server by itself (the override then goes too); a change to `bindingUpdated`'s comparison; either SSR fixture, the live-gate test, or an initial-position or handoff test failing.

### 2. Orbit offers no Aria `TabContent` for lazy slides: confirmed, reason restated

Decision: confirmed; the README item and the Orbit spec state the reason that survives fallback 1's overrule.

Why. With `TabPanel` hosted, a `TabContent` in a slide would render, so the dossier's first fact (no `DeferredContentAware` without `TabPanel`, `NGC/src/aria/private/deferred-content/deferred-content.ts:47,58`) no longer decides it. What decides it is specific to a scroll-snap carousel: `DeferredContent` renders only while `contentVisible()` is true (`deferred-content.ts:58`), which `TabPanel` sets from `visible()` in a render callback (`tabs/tab-panel.ts:96-100`), true only for the selected slide (`private/tabs/tabs.ts:98`). In this Orbit every slide can be on screen before it is selected (mechanic 1 selects at half visibility), so a lazy slide is a visible blank while the user scrolls it in, and the container, as tall as its tallest slide with no measurement (user story 3), changes height when a taller lazy slide fills in; in server HTML and inside `hydrate never` every lazy slide is `<!--container-->` (probe E's mechanism), against user story 24. Foundation's Orbit has no lazy option (`FS/js/foundation.orbit.js`). `@defer (on viewport)` inside a slide, whose observer sees the container's clipping, loads by visibility, the trigger a carousel needs (story `orbit--defer-in-slide`).

Weighing. Both reviewers confirm. The overrule-side reviewer's counterpoint (consistency with the Tabs opt-in; `[preserveContent]="true"` renders each slide once) fixes only the second showing, not the blank first swipe or the height jump. The confirm-side reviewer's "forced by fallback 1" argument falls with fallback 1 and is replaced by the carousel-specific reason, which they also gave.

Dissent: a consumer with expensive live state per slide might want "rendered while selected"; `@defer (when slide.isActive())` through the exported `isActive` signal gives that, with a server-rendered placeholder. Reopening fact: an Aria `TabContent` that renders the selected panel on the server, or a visibility-keyed variant.

### 3. Accordion does not use Aria's `AccordionContent`, even for Lazy content: confirmed, with a corrected reason and a dated pointer on ADR 0008

Decision: confirmed. The library's own lazy template (`@if` plus `NgTemplateOutlet` in the wrapper's template, Accordion D12) stays. The third stated reason is reworded (below), and ADR 0008 gets a dated bullet recording that the Accordion's opt-in lazy mode is the library's renderer while the Tabs opt-in is Aria's `TabContent`.

Why. First reason, measured: an open lazy panel under Aria's `AccordionContent` is `<!--container-->` in server HTML (probe E, `ap-1`; probe H, the open panel inside a component host), because `AccordionPanel` sets `contentVisible` in a render callback (`NGC/src/aria/accordion/accordion-panel.ts:85-89`) and `DeferredContent` creates the view in one (`deferred-content.ts:56-69`). User story 19 (an open lazy panel in server HTML) matters whenever `expanded` is bound from server state and the consumer does not know statically which panel is open; the library's template renders it during change detection (`research/angular-rendering-modes.md` section 5). Second reason, unconditional source: on collapse `DeferredContent` destroys the view unless `preserveContent()` is true (`deferred-content.ts:64-66`), at the start of the `grid-template-rows` close transition (ADR 0003), so a lazy panel would shrink over an empty box; the library keeps the view while `expanded() || !settled()`. Third reason, corrected: `preserveContent` cannot be exposed through the wrapper's own `hostDirectives` inputs (NG2017, probes A and B; `NG/packages/compiler-cli/src/ngtsc/annotations/common/src/diagnostics.ts:267-297`), but a consumer can bind it on the content element through `AccordionPanel`'s own exposure (probes D, E, and H), in bound form only (`strictTemplates` rejects the bare attribute, probe C); library code reading it would depend on Aria's private-prefixed re-export (`NGC/src/aria/accordion/public-api.ts:15-20`). Probe H closes the dossier's unknown 3.4 (discovery through a component host works) without changing the cost.

Weighing. The overrule-side reviewer's strongest argument: ADR 0008 kept Aria's content directives "as an opt-in lazy mode", the Tabs spec follows it (D19), and two lazy mechanisms diverge. ADR 0008 allowed the opt-in; it did not require Aria's directive for it, and building-blocks 1.11 decision 2 states the minimum ("consumers who accept client-only panel content"), which the Accordion's renderer exceeds. The divergence is real and is recorded where it belongs: a dated pointer on ADR 0008 and Tabs D19's corrected rationale (fallback 4), rather than levelling the Accordion down to the mechanism that is empty in server HTML and destroys content mid-transition. Their point that "laziness buys nothing for a panel open at first render" misses the bound-from-server-state case. The confirm-side reviewer's concession on the third reason is adopted.

Dissent: one lazy mechanism would be less code (no `@if`, `NgTemplateOutlet`, `linkedSignal`, or lazy branch in the settled logic) and one story; a consumer reading Aria's guide expects `preserveContent` on the panel element. Reopening fact: a `DeferredContent` that creates its view during change detection when the container is initially visible (Aria's directive then serves story 19 and the library renderer can go).

### 4. Tabs uses Aria's `TabContent` only behind the opt-in lazy template: confirmed with a condition

Decision: confirmed; projection stays the default. Condition: `specs/tabs.md` D19's rationale and the class mapping's "counterpart" phrase are corrected.

Why. The selected lazy panel is empty in server HTML (probe E: both tab panels `<!--container-->`), while projected content is present (the [Prototype: `@angular/aria` Accordion and Tabs under Foundation markup](43-prototype-aria-accordion-tabs.md), case 9) and paints without JavaScript (case 11); `TabPanel` works without `TabContent` apart from a development warning (`tabs/tab-panel.ts:108-110`), so projection is a shape Aria supports. ADR 0008 and building-blocks 1.11 decision 2 make projection the rule; under `hydrate never` a default-lazy tab set would show an empty selected panel for good. The condition: D19 says "Consistent with Accordion", which is false while the Accordion keeps its own renderer (fallback 3).

Weighing. Both reviewers confirm. The overrule-side reviewer's counterpoint (Aria's examples treat `TabContent` as the normal case and the panel warns without it) meets the guide's own wrong default statement (`NG/adev/src/content/guide/aria/tabs.md:193` against `deferred-content.ts:27`): the guide is no authority on intended defaults, and the server-HTML cost is measured.

Dissent: every consumer following Aria's guide gets a development warning per panel from this library's default. Reopening fact: the same as fallback 3.

### 5. Responsive Accordion Tabs exposes neither lazy form: confirmed, reason restated as scope

Decision: confirmed, with the README reason rewritten: sections are created again on every Mode swap, including the first-render swap on a client whose breakpoint differs from the server's (ADR 0032), so `preserveContent` cannot hold; and the tabs-mode lazy form (Aria's `TabContent`) is empty in server HTML while the accordion-mode form (the Accordion's template) is not, so one lazy input would be server-rendered in one mode only, depending on the Server breakpoint; deferred as additive scope, not a misfit of an Aria building block.

Why. The [Prototype: ResponsiveAccordionTabs as one component](51-prototype-responsive-accordion-tabs.md) case 14 measured state loss across a swap (`prototypes/responsive-accordion-tabs/results.log:26`); `DeferredContent.ngOnDestroy` destroys a preserved view with its branch (`deferred-content.ts:72-74`); ADR 0032 starts every instance in the Server breakpoint's mode and swaps in the first render callback, so lazy content on any off-breakpoint client would be created and destroyed once before the user does anything. The asymmetry between the two lazy forms is from source (fallbacks 3 and 4). The [Spec: Responsive Accordion Tabs](19-spec-responsive-accordion-tabs.md) triage already rates the omission "Not HIGH: each is additive", and `@defer` inside a section gives code splitting in both modes with one meaning.

Weighing. The overrule-side reviewer's strongest argument: "created again on every swap" applies to projected content too, so it argues for laziness, and the cost is a boolean and two template wrappers. Re-creation is not the reason; `preserveContent` is: it is the one thing that distinguishes Lazy content from `@if`, and the component cannot keep it across any swap. The asymmetric server rendering is behaviour keyed on a configuration value invisible at the call site, which the confirm-side reviewer rightly called a trap. The overrule-side reviewer's fallback request (restate as scope, additive) is adopted.

Dissent: a heavy section has only `@defer` today, and with `rules="accordion"` the accordion's lazy form would be safe. Reopening facts: a consumer need for lazy sections; or fallback 3 overruled later, which makes both forms client-only and symmetric, so a `lazy` input becomes a plain addition.

### 6. The menus use neither `ngMenuBar`/`ngMenu` nor `ngTree`: confirmed with a condition

Decision: confirmed. Condition: the stated reason is corrected where it overstates and extended where it understates, in README item 6, `specs/nested-menu.md`, `specs/dropdown-menu.md`, `specs/drilldown-menu.md`, and a dated bullet on ADR 0004.

Why. Roles: `menubar` (`NGC/src/aria/menu/menu-bar.ts:59`), `menu` (`menu.ts:61`), `menuitem` (`menu-item.ts:47,77`), `tree` (`tree/tree.ts:73`), `treeitem` (`tree-item.ts:46`), all in probe F's server HTML. Tab stop: all three containers use roving focus and set their first active item only in a render callback (`menu-bar.ts:116,124`, `menu.ts:158,191`, `tree.ts:119,189`), so every item is `tabindex="-1"` in server HTML (probe F): before hydration and inside `hydrate never` the Tab key reaches no navigation link (WCAG 2.1.1). A wrapper override of the kind fallback 1 uses might be derivable from a public Aria signal, but a menu item's `tabIndex` also depends on submenu state (`private/menu/menu.ts:799-804`), and it is unmeasured; the reasons below decide the fallback without it. The APG's three cautions (`APG/content/patterns/disclosure/examples/disclosure-navigation.html:35-37`, `menubar/examples/menubar-navigation.html:34-39`, `treeview/examples/treeview-navigation.html:32-38`) and building-blocks 1.10's rule ("never `menu`/`menubar`/`tree`", ADR 0004). Enter on a link item is cancelled: `MenuPattern` maps Enter to `trigger()`, which calls `submit()` on a leaf, `MenuBarPattern` maps Enter to `open()` (`private/menu/menu.ts:181,396-401,532`), and `KeyboardEventManager` defaults to `preventDefault: true, stopPropagation: true` (`private/behaviors/event-manager/keyboard-event-manager.ts:32-36`), so navigation would come from `itemSelected`, not the link; the tree's `nav` mode fixes it for the tree only (`private/tree/tree.ts:263,269`). Tree child levels always sit in `ng-template[ngTreeItemGroup]` hosting `DeferredContent` (`tree-item-group.ts:42-45`), absent from server HTML even when expanded (probe F); the tree forces `multiExpandable` (`private/tree/tree.ts:373`). The menubar is horizontal only (`menu-bar.ts:117`); Drilldown has no pattern (`NGC/src/aria/config.bzl`); ResponsiveMenu cannot swap directive sets on one element (ADR 0004, ADR 0035). The chosen design is measured: no roles in any mode, server HTML with classes and `aria-expanded`, axe clean in every mode and engine (the [Prototype: Nested menu directive family with breakpoint mode switching](50-prototype-nested-menu.md), cases 4, 17, 19). What the stated reason overstates: the Angular Aria guide advises against `ngMenu` for site navigation (`NG/adev/src/content/guide/aria/menu.md:53`) but lists site navigation as a use for `ngTree` (`tree.md:27,30,52-66`); `ng-template` is required only by the tree (a menu needs `[submenu]` references, and `ngMenuContent` is optional, `menu-content.ts:31`); menubar submenu items are missing from server HTML only when placed in `ngMenuContent`, Aria's own reference shape (probe F, `sub1` against `sub2`).

Weighing. Both reviewers confirm. The overrule-side reviewer's strongest case, a DropdownMenu on `ngMenuBar` with direct submenu items (Foundation's nested `ul`, server-rendered, Foundation's own roles, typeahead for free), is closed by the cancelled Enter on links, the missing pre-hydration tab stop, and the one-family requirement; Foundation's own roles are the ones its inventory records as wrong (`research/foundation-inventory-menus.md`). The confirm-side reviewer's case is adopted, with their two concessions (direct items are server-rendered; the tree guide lists navigation) written into the reason.

Dissent: Aria's menu and tree are stable, RTL-aware, typeahead-equipped patterns with APG navigation examples; the roles are heavier than needed, not wrong. Reopening facts: an Aria disclosure-navigation pattern; menu and tree directives whose first tab stop is a host binding and whose Enter follows a link; or the map admitting opt-in `role="menu"` variants.

### 7. Accordion Menu does not use Aria's accordion: confirmed with a condition

Decision: confirmed. Condition: "one roving tab stop over the triggers" is false and is struck from README item 7, `specs/accordion-menu.md` (Implementation level), `research/angular-aria-inventory.md` 2.1, and the [Spec: Accordion Menu](20-spec-accordion-menu.md) decision that introduced it; the reason rests on the facts below instead.

Why. Every enabled trigger is a tab stop: `tabIndex = isFocusable(this) ? 0 : -1` (`NGC/src/aria/private/accordion/accordion.ts:196-198`), `isFocusable = !item.disabled() || softDisabled()` (`private/behaviors/list-focus/list-focus.ts:115-117`), not the roving `getItemTabIndex` rule (`:86-94`); measured `0,0,0,0,0,0,0` (the Aria prototype's case 10), probe E, probe H. That matches the APG accordion pattern itself (`APG/content/patterns/accordion/accordion-pattern.html:62`). What stands: the group's host `(keydown)` listener (`accordion/accordion-group.ts:65`) hands every keydown that reaches it to one key map without checking the target (`private/accordion/accordion.ts:73-81,95-96`), whose arrow keys move among triggers only and whose Enter and Space toggle the active trigger's panel (`:79-80,114-118`) and are cancelled (`keyboard-event-manager.ts:32-36`), so a menu would have to guard Aria's keys off on every level (else Enter on a link inside an open section toggles a section and does not follow the link; source reading) and re-add Foundation's cross-link arrows beside them; `region` is static (`accordion-panel.ts:52`) but removable through the Accordion's `region` input (Accordion D17); `[panel]` is required (`accordion-trigger.ts:73`) and accepted in the Accordion (D4); ResponsiveMenu needs one directive family across modes (ADR 0004, ADR 0035), so a standalone Accordion Menu on Aria's accordion would fork the plugin into two implementations with different keys and ids; the Aria guide says "Avoid accordions when: Building navigation menus" (`NG/adev/src/content/guide/aria/accordion.md:32`).

Weighing. Both reviewers confirm, and both found the roving claim false. The overrule-side reviewer's strongest counterpoint (the standalone Accordion Menu composing the library's `NfsAccordion` pieces, which already carry the region switch and the guards) is two implementations of one Foundation plugin whose behaviour differs by context, and the arrow keys would regress from Foundation's link walking. The confirm-side reviewer's corrected reason set is adopted.

Dissent: with `region` removed and every trigger a tab stop, Aria's accordion is a disclosure with arrow keys, and the APG accordion is a legitimate pattern for stacked expandable sections. Reopening facts: an Aria accordion whose group listener checks its target and whose arrows can walk links; or ResponsiveMenu dropping accordion mode.

### 8. The Dropdown pane does not use Aria's menu: confirmed

Decision: confirmed; no change.

Why. `ngMenu` renders `role="menu"` (`NGC/src/aria/menu/menu.ts:61`), whose allowed owned elements are `menuitem`, `menuitemcheckbox`, `menuitemradio`, a `group` of those, and `separator` (`ARIA/index.html:6229-6238`); axe-core 4.13.0's `aria-required-children` fails other owned children, and ADR 0022 makes that run the gate. Its keyboard manager treats every printable character as typeahead on any keydown that reaches the menu, with `preventDefault()` and `stopPropagation()` by default (`private/menu/menu.ts:149,175-186,233-236`; `keyboard-event-manager.ts:32-36`), so a text field in a pane would lose Space, Home, End, and every typed character (source reading; the code path is unconditional). Foundation's first documented pane is a form (`FS/docs/pages/dropdown.md:30-42`). `MenuTrigger.menu` accepts only a `Menu` (`menu-trigger.ts:68`). Aria 22.2 has no disclosure or dialog pattern (`config.bzl`).

Weighing. Both reviewers confirm (0.95 and high). The one counterpoint, a pane that is purely a command list, is the Menu Button pattern, a different component the map keeps out of scope.

Dissent: none that changes the default. Reopening facts: the map admitting opt-in `role="menu"` variants, or an Aria disclosure or dialog pattern.

### 9. Triggers do not use Aria's `MenuTrigger`: confirmed with a condition

Decision: confirmed. Condition (text): README item 9 and `specs/triggers.md` state the literal value Aria renders.

Why. `MenuTrigger` binds `'[attr.aria-haspopup]': 'hasPopup()'` (`NGC/src/aria/menu/menu-trigger.ts:48,74`) with `hasPopup = () => true` (`private/menu/menu.ts:664`); probe F renders `aria-haspopup="true"`, which WAI-ARIA requires user agents to treat as `menu` (`ARIA/index.html:13968-13969`), wrong for a disclosure or dialog opener (4.1.2). Aria has no disclosure, dialog, or toggle trigger (`config.bzl`).

Weighing. Both reviewers confirm (0.95 and high). The counterpoint (server-safe; the reverse link is the shape the Triggers spec borrows) is borrowing a shape, not using the building block.

Dissent: none that changes the default. Reopening fact: an Aria disclosure or dialog trigger.
