## Question

The README open list names thirteen checks that were left for a person with a screen reader. The user has ruled that this pass resolves them autonomously (map, "Open-decision pass"). For each check, decide whether the spec's markup and behaviour are right, from evidence that does not need a person: what each engine exposes to assistive technology for the markup the spec produces (computed role, name, description, states, live-region properties, and what changes across the interaction), measured from the prototype captures or a minimal page under `D:/tmp/` with Playwright's ARIA snapshot, the Chromium CDP accessibility tree, and, on this Windows machine, the UI Automation tree that Narrator and NVDA consume (read-only inspection of the browser window); what published support data says about NVDA, JAWS, VoiceOver, and TalkBack for those roles and states (a11ysupport.io, PowerMapper screen reader reliability, the APG's own notes); and the WAI-ARIA and HTML-AAM mappings. Where the evidence shows the spec is wrong, the decision is the fix. Where it shows the spec is right, the check is resolved, and any manual confirmation still worth doing becomes a release-test step in the spec's Testing Decisions rather than an open decision.

## How to work it

Evidence agents (the thirteen checks may be split) write `research/assistive-technology-evidence.md`; an adversarial reviewer on Fable attacks each verdict; the orchestrator's judge writes the `## Answer` here with one line per check (verdict, evidence, spec change if any) and the exact spec edits. Do not install screen readers or other software system-wide.

### Checks 5 and 6 decided together

The review found that the Off-canvas fix (check 5, the Modal inert set up to `body`) and the Tooltip fix as E1 drafted it (check 6, CDK `AriaDescriber`, whose container is a `body` child) meet at one element. J1 and J2 show the meeting is harmless in Chromium and Firefox today, but only because Chromium follows a reference into a `visibility: hidden` node whatever its inertness, and CDK keeps its container `visibility: hidden`; a rendered target outside the panel does lose its text in Chromium (J1 A and D), and WebKit was not measured. The Tooltip spec had already rejected `body`-appended structure (D23) and relies on tips inside modal dialogs (`tooltip--in-modal-dialog`). So:

- Tooltip does not use `AriaDescriber`. It keeps its description in a hidden `role="tooltip"` element beside the host (J3, variant E), which is inert, top-layered, or pruned exactly when the host is, in every engine and under any `inert` the library or a consumer applies. That removes the collision at its source and keeps D23.
- Off-canvas's Modal inert set skips what the page's services put at `body` level for the benefit of whatever holds focus, following CDK Dialog's own background hiding: `aria-live` and `popover` elements, and CDK's two `body` containers, `.cdk-overlay-container` (a Material select or datepicker opened from inside the panel lives there, and would otherwise be inert and unclickable) and `.cdk-describedby-message-container` (a consumer's Material tooltips; never navigable, because it is `visibility: hidden`). The second exception is not needed in Chromium or Firefox (J2) and is kept because WebKit is unmeasured and it costs nothing.

### 5. Off-canvas

Verdict: spec defect, with the fix below; the fix also changes the Off-canvas Trigger role.

Deciding evidence: E1 section 5, 3 of 3 runs. For Foundation's sibling markup the modal panel is a named modal dialog with focus inside and the content inert, the disclosure Trigger reports its state, and the revealed sidebar is plain page content under its `nav`. Two cases break the modal promise, measured: a modal panel nested inside `.off-canvas-content`, a form the spec supports (user story 6), is made inert with its enclosing content, so focus falls to `body` and the dialog leaves the tree in all three engines (2.1.1, 2.4.3, 4.1.2); and content outside `.off-canvas-content` stays in Chromium's and Firefox's trees while the panel claims `aria-modal="true"`, which Narrator, TalkBack, and Orca then reach (a11ysupport.io APG modal test, E1 section 5). `inert` is honoured by every tested screen reader (a11ysupport.io, 2023-07-08), so it is the one mechanism a reader that ignores `aria-modal` cannot also ignore. Inerting every sibling along the panel's ancestor chain fixes both, measured in the three engines (E1 `?walk`); J2 re-applied the same set.

The fix: the Modal inert set. Once focus is inside the panel, the panel sets `inert` on every element sibling of itself and of each of its ancestors up to `body` that is not already inert, except `.js-off-canvas-overlay` elements, the CDK focus-trap anchors, elements carrying `aria-live` or `popover`, and `.cdk-overlay-container` and `.cdk-describedby-message-container`; it records what it changed and removes `inert` from exactly those at the close request, before focus returns. A breakpoint crossing already runs the close path (Breakpoint reactions; the existing 800 to 1300 px e2e case), so no set outlives an open panel.

Ticket-level consequence 1: this closes follow-up 2 of [Decide: `aria-expanded` on a modal dialog's opener](72-decide-aria-expanded-on-modal-opener.md) ("Off-canvas Modal mode, `aria-modal="true"` beside reachable content"), by the second of the two options that follow-up named.

Ticket-level consequence 2, a change to that decision's outcome: its reasoning for keeping Off-canvas Modal mode on the `dialog` role no longer holds. It kept `dialog` only because a Trigger outside `.off-canvas-content` stayed exposed with a true expanded state (its item 3). Under the Modal inert set every Trigger outside the panel (in a title bar outside the content, in another panel, in the content itself) is inert for as long as the panel is open, so no expanded state can ever be read as true there, which is exactly the condition its rule gives for `modal-dialog`; its api-lens dissent and ADR 0036 ("Reopened if the Off-canvas spec makes everything outside the panel inert") name this change as the reopening fact. Ruling: Off-canvas Modal mode's Trigger role becomes `modal-dialog` (`aria-haspopup="dialog"` and `aria-controls`, no `aria-expanded`); non-modal configurations keep `disclosure`. Flagged for the orchestrator as a change to that ticket's outcome, ADR 0036, the Triggers spec, and building-blocks 1.8 and Part 4 (Changes). The edge cases where a Trigger could still be reached while the panel is open are named, not hidden: a Trigger inside one of the six exceptions (a popover or an overlay the page opened), a `nfsToggle` inside its own panel (the close control there is a bare `nfsClose`, which renders nothing), an element added outside the panel after the set was taken, a modal panel open by default before hydration, and modal mode with `autoFocus: false` (development check 4 already warns; the set waits for focus inside the panel). In each, MSAA and IA2 carry no state for a `modal-dialog` Trigger, and only Firefox's UI Automation infers "collapsed".

Review weighed: TalkBack joins the release test (accepted: it is one of the readers the fix is for). The toast argument and the WebKit argument hold as the review concluded. The container exception is adopted in the wider form above; its measured necessity is less than the review said (J1, J2).

Residual risk: a reference from inside the panel to a rendered element outside it (a consumer's `aria-describedby` to a visible paragraph) resolves to nothing in Chromium while the set is applied (J1 A), documented in the spec; elements added after the open are not made inert. Release-test step, verbatim: "Before each release, with NVDA on Firefox, Narrator on Edge, TalkBack on Chrome, and VoiceOver on Safari (macOS and iOS), open `off-canvas--modal` and `off-canvas--modal-nested` from their Triggers and confirm each Trigger is announced as a button that opens a dialog with no expanded state, that the dialog's name is spoken with focus on its first control, and that browse, swipe, or virtual cursor navigation cannot leave the panel, the header outside the wrapper included; open `off-canvas--default` and confirm its Trigger is announced as expanded and collapsed; at the large breakpoint confirm `off-canvas--reveal-for-large` is read as the 'Main' navigation with no dialog."

### 6. Tooltip

Verdict: spec defect, with the fix below (variant E), replacing E1's `AriaDescriber` fix (variant D).

Deciding evidence: E1 section 6, 3 of 3 runs. The kept hidden tip does describe the host, but Firefox fires a description change on the focused host at the first show, at every re-show, and on Escape, which NVDA speaks by default (`event_descriptionChange`, verified in `release-2026.2`), so the tooltip text is repeated on first focus, on every return, and on Escape; and a host with a static consumer `aria-describedby` has no tooltip text at first focus in either engine, which HTML-AAM makes normative (`aria-describedby` is "the first applicable description source") and which JAWS, Narrator, TalkBack, and VoiceOver iOS then never announce (a11ysupport.io, description changes are not re-announced). The fix removes every such event and the gap: J3, 3 of 3, both engines. It keeps the spec's `title` behaviour for no-JavaScript users, for mouse users before the first show, and for hosts below `showOn` (E1 variant B removed `title` at the first render callback and lost that).

Why a local element and not `AriaDescriber`: see "Checks 5 and 6 decided together". The local element shares the host's inertness and modal subtree by construction (J2: survives `showModal()` and the Modal inert set in both engines); `AriaDescriber` depends on each engine's handling of a reference across a modal boundary (holds in Chromium and Firefox, J1 E and J2; unmeasured in WebKit) and on a CDK implementation detail, and D23 already ruled out `body`-appended structure.

Review weighed: the diagnosis and the direction hold; the review's option (b), the evidence's local element, is adopted. The review's measured collision is corrected by J1 and J2 (its probe used a rendered inert target), and its option (a) is kept only as insurance inside the Off-canvas exception list. `AriaDescriber`'s dedup and ordering conveniences (verified by the review) are not needed: one element per host, consumer ids first by the host binding.

Costs the fix accepts: one hidden element per tooltip from the first client render (D4's rejected "second element per tooltip", now justified by measurement); D23's sibling pseudo-class limit applies from hydration instead of from the first show (with Foundation's defaults, a 1 px right margin on a button group's last button); a host that holds focus from before hydration gains the reference while focused, so Firefox reports one description change with the same text.

Residual risk: VoiceOver's WebKit path for the local element and the modal case. Release-test step, verbatim: "Before each release, with NVDA on Firefox and on Chrome, JAWS on Chrome, and VoiceOver on Safari (macOS and iOS), Tab to the hosts of `tooltip--defined-term`, `tooltip--described-by-merge`, `tooltip--disabled-interactive`, and `tooltip--in-modal-dialog` and confirm the tooltip text is spoken once as the description on the first focus (after the consumer's own description), is not repeated when the tip appears or when Escape dismisses it, and is spoken again on the next focus."

### 8. Dropdown Menu

Verdict: spec defect (low impact) in one unmeasured interaction, with the fix below; the rest is correct.

Deciding evidence: E2 check 8. `aria-expanded` on parent buttons and Hybrid toggles is exposed and its change fires on the focused control (measured, both engines; ARIA-AT JAWS and NVDA pass); the open submenu is the next sibling of its button in every tree; a hover opening with focus elsewhere fires a state change on a button that is neither the focus nor a focus ancestor, plus show and text-inserted events outside any live region, none of which NVDA speaks (`event_stateChange`, `ia2LiveRegions.cpp`, verified). The defect: with keyboard focus inside Item 2's open submenu and the pointer resting on Item 1, hover opens Item 1, the sibling rule closes Item 2, and the Nested menu's focus-loss guard moves focus to Item 2's toggle (`specs/dropdown-menu.md` Hover rule; `specs/nested-menu.md` focus-loss guard, verified): a pointer that merely rests over the menu takes keyboard focus away, and the screen reader speaks the move. Fix: hover opens nothing while focus is inside an open submenu of a sibling item.

Touch: Chromium's accessibility click dispatches `pointerdown`, `mousedown`, `pointerup`, `mouseup`, `click` and no `pointerenter` (E2, `event_dispatcher.cc`), so TalkBack toggles. E2's WebKit sentence is wrong (the helper, verified): pointer events are `TouchRelated`, the item's `pointerenter`/`pointerleave` make `hasTouchEventListener()` true, and `press()` dispatches touch events and returns before `dispatchSimulatedClick`; whether that yields exactly one click is closed source. ### 10. Abide

Verdict: spec defect in the placement of Form errors of native controls inside a wrapping label, with the fix below; several alerts at once and the on-blur order are correct.

Deciding evidence: E2 check 10. Inside a wrapping label, a shown Form error joins the field's accessible name in Firefox (accname "Name From Content" covers descendants of a `label`), so the error is read twice on focus and the field fires a name change whenever an error appears or clears; Chromium keeps it out of the name but fires no `EVENT_SYSTEM_ALERT` for an alert inside a `label` (measured, `probe-alert` cases A and C). After the label, neither effect occurs in either engine (cases B and D, "Work email"). Several alerts at once and an alert on blur are exposed in DOM order right after the focus move, and NVDA queues `NOW`-priority alerts without cutting earlier ones off (`priorities.py`, `event_alert`, verified by E2). Foundation's `.form-error` and `.is-invalid-label` rules do not depend on nesting (`scss/forms/_error.scss`, the review and helper), so moving the error changes no style.

Review weighed: the fix is extended to the terms checkbox and the Reactive Forms example (accepted; both keep an error inside a wrapping label, verified); the migration cost against user story 14 and Foundation's docs markup is recorded (accepted); the automated guard is a DOM structural assertion (no visible Form error of a native control inside its `label`) plus the development check, and the Firefox name reading goes to the release test (partly accepted: Playwright has no Firefox accessibility-tree reader and its own names are not the engine's, E2 tooling finding 2); "each Form error once with NVDA on Chrome" stays its own release gate (accepted: Chromium's alert path and live-region path both reach NVDA, with no de-duplication found in its source). The custom `FormValueControl` exception stays, because its typed reference crashes the compiler (measured by the Abide prototype) and a custom element is not labelable, so the Firefox name effect does not arise; the missing system alert there is the documented limitation.

Residual risk: the double path in NVDA with Chrome; VoiceOver's description reading (a11ysupport.io data from 2021). Release-test step, verbatim: "Before each release, with NVDA and JAWS on Chrome and Firefox and VoiceOver on macOS and iOS, on `abide--submit`, `abide--validate-on-blur`, and `abide--checkbox`: a failed submit announces the Form alert and each Form error once, in DOM order, without an error cutting off the one before it (with NVDA on Chrome, each error once although Chromium reports it both as an alert and as a live-region insertion); leaving an empty required field announces its error and the next field, the error interrupting the field's announcement and the field then resuming; focusing an invalid field announces its label, invalid state, and error once, with no error text in the name (Firefox included); on VoiceOver, the error is read as the field's description."

### 12. Orbit

Verdict: spec correct; D22 confirmed.

Deciding evidence: E2 check 12: the "carousel" and "slide" role descriptions are exposed (IA2 `roledescription` in both engines, UIA localized control type in Chromium); without "slide", NVDA would call each slide "property page" (`ia2Web.py` `_get_roleText`, `role.py`, verified), so D22's "slide" reads better; text inserted into the container is ignored while `aria-live="off"` and reported while `polite` (`ia2LiveRegions.cpp`, measured events); `inert` slides are absent from both trees; the handoff fires one focus event on the new slide with its name and role description and never on `body`.
