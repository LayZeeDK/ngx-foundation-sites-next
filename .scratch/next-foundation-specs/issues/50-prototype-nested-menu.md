## Question

Three sub-questions, worked in this order:

1. Can one item and submenu directive family emit the `is-<mode>-submenu*` classes from a mode signal, with the accordion, drilldown, and dropdown root behaviours coexisting as host directives on one `ul` and only one active, constant disclosure navigation roles, and per-mode keyboard handling? This sub-question decides the verdict. Include the accordion-mode height animation, which is documented custom CSS because Foundation's `foundation-accordion-menu` Sass has no height rule (its JavaScript used `slideDown`): a grid on the parent `li` (`nfsMenuItem`, rows `auto 0fr` to `auto 1fr`) with the submenu `ul` as the clipped row (`min-height: 0; overflow: hidden`), since a grid on the multi-child `ul.menu.nested` would size only its first row (`building-blocks.md` 1.6 rule 3).
2. What must the Drilldown mode render (wrapper, back button) and measure, and what does the server render for each mode?
3. Does focus stay on the equivalent control when a breakpoint swaps the mode?

A session that runs out of room records the unanswered sub-questions under "what the prototype does not prove" rather than guessing.

Read first: `building-blocks.md` (the matrix row and the open risk this prototype settles), `adr/*.md`, `research/foundation-inventory-menus.md`, `research/aria-apg-patterns.md`, `research/di-and-composition-patterns.md`, `research/angular-rendering-modes.md`.

### Verdict

Yes: one item and submenu directive family carries all three Menu modes. `li[nfsMenuItem]`, `ul[nfsSubmenu]`, and `button[nfsSubmenuToggle]` read the Menu mode from `nfsMenuModeToken` and emit Foundation's whole Nest vocabulary (`is-<mode>-submenu-parent`, `is-<mode>-submenu`, `is-<mode>-submenu-item`, `submenu`, `is-submenu-item`) plus each mode's State classes (`is-active`, `js-dropdown-active`, `first-sub`, `opens-left|right|inner`, `is-closing`, `visible`/`invisible`, and `is-drilldown` on the wrapper) as host class bindings, in server HTML and after every client swap. `NfsResponsiveMenu` lists `NfsAccordionMenu`, `NfsDrilldown`, and `NfsDropdownMenu` in `hostDirectives` on one `ul`. Each root provides `nfsMenuModeToken`, and the hosting directive's own provider wins on that element injector, so all three roots and every item read one mode signal, only the active root adds its root class (`accordion-menu`, `drilldown`, `dropdown`), and only the active root's key handler acts. The Angular runtime merges the three roots' host listeners into one `jsaction="keydown:;focusout:;"` on the `ul`. No `role` attribute is emitted in any mode; parents are `<button aria-expanded aria-controls>` or, in the hybrid form, a link plus a toggle button. axe with the WCAG 2.2 AA tags plus best-practice reports no violations for any mode, open or closed, in any engine. The parent-`li` grid (`auto 0fr` to `auto 1fr`) animates height in all three engines. Two results correct `building-blocks.md`. First, a hidden Drilldown ancestor level cannot be `inert`, because the open level is its descendant and `inert` cannot be undone inside a subtree, so hidden ancestor levels use Foundation's `invisible` and only closed submenus are `inert`. Second, the programmatic focus into a sliding Drilldown level must pass `preventScroll`, or the `overflow: hidden` wrapper scrolls sideways and the whole menu vanishes (seen in all three engines before the fix). Focus stays on the same control across every breakpoint swap tested, provided the swap prunes the open submenus to the focused path and, when drilldown is entered, closes the focused toggle's own submenu; without that pruning, focus drops to `body` in all three engines.

### Failures and exact error text

- Drilldown focus handoff, before `preventScroll` (row 11): there was no thrown error, only a wrong layout. Probe of the ancestor chain after opening Item 1 at 1280 px in Chromium: Item 1A `"rect":[-912,177,928,38]`, root `ul` `"rect":[-912,139,928,117]`, wrapper `div.is-drilldown` `"rect":[16,139,928,231]`, `"ov":"hidden"`. Screenshots of the open Drilldown in WebKit and Firefox were blank below the status line.
- `opens-inner`, before per-item focus-out (row 25), Chromium: `Error: expect(received).toBe(expected) // Object.is equality` / `Expected: true` / `Received: false`, logged state `{"control":"Item 1B","rect":[17,217,198,38],"visible":false}`.
- Hybrid toggle target size, before `.submenu-toggle` applied in every mode (row 20), Chromium: `[axe] drilldown closed: ... target-size [button[hybrid=""]]`, and the same in dropdown mode.
- WebKit Tab order (row 10), before the assertion was made engine-aware: `Expected: ["BUTTON:Item 1A", "A:Item 1B", "A:Link after the menu"]` / `Received: ["BUTTON:Item 1A", "BODY", "BUTTON:Back"]`. This is the engine's default (Safari's "Press Tab to highlight each item" is off), not a menu defect.
- Harness race in F4 (1 of 336 runs, Chromium): `Error: expect(locator).toBeFocused() failed` / `Received: inactive`. The test called `focus()` on a link straight after the click that opened its submenu, before zoneless change detection had removed `inert`, so the focus was a no-op. The fix waits for `inert` to go. Library fact: `inert` changes land on the next change detection pass, so any focus move after an open must run in a render callback (the prototype uses `afterNextRender`), never synchronously after `expanded.set(true)`.
- Harness-only axe findings in the first run (fixed in the page, not the menu): `page-has-heading-one [html]` and `color-contrast [.status]`.

### What the prototype does not prove

- DropdownMenu hover opening, hover intent timers, `closingTime`, touch, and Light dismiss by an outside pointer press. Only click, keyboard, and focus-out close were built.
- RTL: `Directionality` feeds `opens-left` and the dropdown arrow keys in code, but no RTL case ran.
- Vertical DropdownMenu roots, `.<bp>-vertical` direction changes, and `alignment: auto` with `.top-bar-right` ancestry.
- Drilldown `autoHeight`, `animateHeight`, `scrollTop`, `closeOnClick`, `backButtonPosition: 'bottom'`, and `parentLink` (dropped per `building-blocks.md` 1.4). More than three levels.
- Event replay (clicks and keys before hydration), incremental hydration and `@defer` hydrate triggers, and prerendering. Only SSR per request with full hydration ran. Hydration was checked only through a clean console (a production build prints no hydration statistics); `componentsSkippedHydration` was not read.
- The real Breakpoint service and its client-hint `serverBreakpoint`: the simulation reads `matchMedia` in `afterNextRender`. The first-paint layout change at non-small widths (row 18) is left to the [Prototype: Breakpoint handoff under hydration](60-prototype-breakpoint-handoff-hydration.md).
- Parent-owned registration with DOM-order sorting (`building-blocks.md` 1.9): the prototype registers items in construction order and finds items by element through a `WeakMap`. Order under `@for` and `@defer` was not exercised.
- Screen reader output. Accessibility evidence is axe, DOM state, focus, and geometry only (see Triage, item 9).
- Cost at scale: the prototype runs one `afterRenderEffect` per item for the collision check.
- The `overflow: clip` rule for a Tab during the Drilldown slide ran in Chromium only, in one run at the unsafe timing (row 12).

### Decisions handed to the blocked specs

To the [Spec: Nested menu (shared utility)](56-spec-nested-menu.md):

1. The family is `li[nfsMenuItem]` (owns `expanded`, the parent and item classes, `open()`/`close()`/`toggle()`), `ul[nfsSubmenu]` (injects the owning `NfsMenuItem`, owns its generated id, the submenu classes, `inert` while closed, and the `is-closing` wait), and `button[nfsSubmenuToggle]` (`type="button"`, `aria-expanded`, `aria-controls`, and a `hybrid` boolean input for the link-plus-button form). The mode comes from `nfsMenuModeToken`, which carries the mode signal plus the root's top-level items. Every mode-specific class is a `computed` class map on the host.
2. The hybrid toggle gets Foundation's `.submenu-toggle` and its item `.has-submenu-toggle` in every mode, not only in accordion mode: that is what gives it the 40 x 40 target (WCAG 2.5.8) and its arrow. Drilldown mode needs custom rule 3 (below) for the layout.
3. Roles: none. Native lists, buttons, and links; `aria-current="page"` is consumer-written; closed submenus are `inert`. The Foundation arrow rules keyed on `a` and on `li[aria-expanded]` need `<button>` twins (custom rules 1 and 2), because `aria-expanded` sits on the button and never on the `li`.
4. Any focus move that follows a state change runs in `afterNextRender` (the F4 harness race under "Failures" shows why).

To the [Spec: Accordion Menu](20-spec-accordion-menu.md):

1. The height animation is the parent-`li` grid exactly as `building-blocks.md` 1.6 rule 3 states. It works in all three engines, including the hybrid form, because an absolutely positioned toggle takes no grid track. The `li` needs an "expanded" hook that Foundation lacks; how that hook is named or expressed is left `OPEN FOR HUMAN` (Triage, item 1). The prototype used a class named `is-expanded`.
2. The keys stay the ones in row 6, with Right, Left, Up, Down, and Escape as the APG's optional keys; every control stays in the Tab sequence. `multiOpen` keeps Foundation's default `true`.

To the [Spec: Drilldown Menu](22-spec-drilldown-menu.md):

1. The wrapper is a consumer-written `div[nfsDrilldownWrapper]` that gets `is-drilldown` and `min-height` only while the menu is in drilldown mode. `min-height` is the tallest level, read in `afterRenderEffect` `earlyRead` and written in `write`, plus a `ResizeObserver` created in `afterNextRender`; the server renders no `min-height`, and the layout settles after hydration. The back button is a consumer-written `li.js-drilldown-back > button` with `nfsDrilldownBack`, `hidden` outside drilldown mode, so one markup serves ResponsiveMenu.
2. Correction to `building-blocks.md` Table A and Table B ("`inert` on the hidden parent level") and to the APG research's "ancestor levels hidden with `hidden`": both are impossible, because the open level is a descendant of every hidden level (row 9). Closed submenus are `inert` and `invisible`; hidden ancestor levels (the root `ul` included) get Foundation's `invisible`; the open level gets `visible`.
3. Opening moves focus to the first non-back control of the new level with `focus({preventScroll: true})` (row 11), and the library adds `.is-drilldown { overflow: clip }` (Baseline widely available: Chrome 90, Firefox 81, Safari 16), because a user's own Tab during the 150 ms slide can still scroll the wrapper (row 12) and `preventScroll` does not reach that case (Triage, item 4).
4. `is-closing` is set on close and cleared on the submenu's own `transitionend` for `transform`, with a 250 ms fallback (`$drilldown-transition` 150 ms plus 100 ms).

To the [Spec: Dropdown Menu](21-spec-dropdown-menu.md):

1. Classes: `js-dropdown-active` on the open submenu, `is-active` on the open parent, `first-sub` on top-level submenus, and `opens-right`/`opens-left` from `Directionality`. The collision check runs after open in `afterRenderEffect` (`earlyRead` measures the submenu against the viewport, `write` flips), going from the base side to the opposite side to `opens-inner`, and the base side is restored on close (rows 24, 25). Only left and right are checked, as in Foundation.
2. Focus-out closes per item, not only per menu: a submenu closes when focus leaves its own `li`. This goes beyond the APG example, which closes only when focus leaves the whole navigation, and it is required for WCAG 2.4.11 whenever `opens-inner` drops a submenu over later siblings (row 25).
3. Escape closes and refocuses the parent button (WCAG 1.4.13). Hover opening is still unproven (see above).

To the [Spec: Responsive Menu](23-spec-responsive-menu.md):

1. `ul[nfsResponsiveMenu]` hosts the three roots through `hostDirectives` and provides `nfsMenuModeToken` itself; its provider wins, so the three roots and every item share one mode signal computed from `rules` and the Breakpoint service. There is no directive swap and no re-render; a swap changes classes and key handling only (row 5).
2. The swap rule (rows 13 to 16): keep open exactly the submenus that contain the focused control. Entering drilldown also closes the submenu whose own toggle has focus, because an open level hides its toggle (F3 without this: focus lost to `body` in all three engines). With no focus inside the menu, keep the first open submenu per level. Entering accordion changes nothing. The prototype runs this in an `effect` that writes `expanded` signals and reads `document.activeElement`. That breaks `building-blocks.md` 1.5 (no `effect` that propagates state between signals; DOM reads only in render callbacks), so the spec moves it into an `afterRenderEffect` keyed on the mode: `earlyRead` reads `activeElement`, `write` prunes.
3. Server output is the `serverBreakpoint` mode's classes and ARIA (row 17). A client on another breakpoint re-classes at hydration with no hydration error, and the first paint shows the server mode's layout until then (row 18).

### Custom CSS (every rule in `_nested-menu.scss`)

1. `.menu li > button:not(.submenu-toggle)`: `display: block; width: 100%; padding: $menu-items-padding; line-height: 1; text-align: start; color: $anchor-color; cursor: pointer`. Why: disclosure parents are buttons (ADR 0004); Foundation's `menu-base` styles only `a` and `.button`.
2. Button arrows: `.accordion-menu .is-accordion-submenu-parent:not(.has-submenu-toggle) > button::after` (plus its `[aria-expanded='true']` rotation), `.drilldown .is-drilldown-submenu-parent > button:not(.submenu-toggle)::after`, `.drilldown .js-drilldown-back > button::before`, and `.dropdown.menu > li.is-dropdown-submenu-parent > button:not(.submenu-toggle)::after` (with the arrow padding). Why: Foundation draws every arrow on `> a` and reads `aria-expanded` from the `li`. Each rule copies Foundation's geometry through `css-triangle` and Foundation's arrow settings.
3. `.drilldown .is-drilldown-submenu-parent.has-submenu-toggle { display: flex }`, with `> a { flex: 1 1 auto; margin-inline-end: 0 }` and `> .submenu-toggle { position: static; flex: none }`. Why: Foundation's only toggle styles are AccordionMenu's, which position the toggle absolutely against a positioned `li`; a drilldown `li` must stay unpositioned because the submenu slides against the root `ul`.
4. `.drilldown .has-submenu-toggle > a::after, .dropdown.menu li.has-submenu-toggle > a::after { content: none }`. Why: in drilldown and dropdown mode Foundation's link arrows have no `.has-submenu-toggle` exclusion (AccordionMenu's has one), so the hybrid form would draw two arrows.
5. `.accordion-menu .is-accordion-submenu-parent { display: grid; grid-template-rows: auto 0fr; transition: grid-template-rows 250ms ease }`, with `> .is-accordion-submenu { min-height: 0; overflow: hidden }`, `&.is-expanded { grid-template-rows: auto 1fr }`, and `transition-duration: 1ms` under `prefers-reduced-motion: reduce`. Why: this replaces jQuery `slideDown`/`slideUp`; Foundation's Sass has no height rule, and 250 ms is Foundation's `slideSpeed` default. The `@supports not (grid-template-rows: 0fr)` guard from 1.6 rule 3 was not added: every engine tested interpolates `fr`.
6. Decided for the Drilldown spec but not in the prototype stylesheet: `.is-drilldown { overflow: clip }` (Drilldown decision 3). Why: it overrides Foundation's `overflow: hidden` so that no focus, programmatic or by Tab, can scroll the wrapper sideways mid-slide.

### OPEN FOR HUMAN

1. How the accordion-mode parent `li` exposes "expanded" to the grid rule (Triage, item 1). Foundation has no open class on the `li` in accordion mode: its JavaScript put `aria-expanded` on the `li` and animated with `slideDown`. Options:
   - (a) A library class on the `li`, such as `is-expanded` (what the prototype did). It is easy for consumers to theme, but it adds a non-Foundation class to the styling contract, so `CONTEXT.md`'s State class definition would have to admit library classes.
   - (b) Foundation's `is-active` on the `li`. Rejected by the prototype's reading of Foundation: `.menu .is-active > a` then paints the parent link in the active-link style.
   - (c) A host style binding on the `li` (`[style.grid-template-rows]`, or a `--nfs-*` custom property that the rule reads). This adds no class vocabulary, but it moves state into inline style, which consumers can only override with `!important` (or, for the custom property, through the property itself).
   - (d) `aria-expanded` on the `li`, mirroring Foundation's own selector. Rejected: the attribute is not allowed on `listitem` (axe `aria-allowed-attr`), and `building-blocks.md` 1.10 puts `aria-expanded` on the button.
   - A selector keyed on the submenu (`:has()`) is out of target.
   Confidence is low because the prototype chose (a) without weighing the alternatives, and (a) contradicts the glossary.
2. A screen reader pass over a breakpoint swap with a submenu open (Triage, item 9): axe and DOM checks cannot confirm what NVDA, JAWS, or VoiceOver announce when a mode swap moves layout under focus.

Orchestrator, 2026-09-26: on OPEN FOR HUMAN item 1, Foundation's own contract gives the [Spec: Nested menu (shared utility)](56-spec-nested-menu.md) its sources: `foundation.accordionMenu.js` puts `is-active` on the open submenu `ul` (lines 243 and 273), and `_accordion-menu.scss` keys the parent's arrow on the `li`'s `aria-expanded` attribute. The spec settles from those which hook the parent `li` gets for the grid rows (a documented library class, the attribute the button carries, or the submenu's `is-active` with the grid moved to it), applying the triage rule; it stays open only if the sources cannot settle it. The two `building-blocks.md` corrections (hidden Drilldown parent levels use Foundation's `invisible`, never `inert`; the ResponsiveMenu swap runs in `afterRenderEffect`) are carried into the map with that spec's shared-file changes.
