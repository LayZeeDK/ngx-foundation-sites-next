## Question

What is the API of the library's breakpoint utility, the one source of truth every breakpoint-gated plugin reads, and what does its spec say?

This is a shared-utility spec graduated by the building-blocks decision: plugin specs depend on it, so its API must be settled before they are written. The result must be the best combination of the map's design criteria, applied to a utility: Foundation's own utility behaviour, the platform within the browser target, Angular CDK where it already solves the problem, Material-equivalent API shape, and the modern DI patterns in `research/di-and-composition-patterns.md`.

Read first: `building-blocks.md` (the shared-utilities section and every matrix row that uses this utility), `CONTEXT.md`, `adr/*.md`, `research/foundation-utilities-conventions.md`, `research/angular-cdk-inventory.md`, `research/angular-rendering-modes.md`, `research/web-platform-features.md`, and the resolved answers of the tickets this one is blocked by. Run `/grill-with-docs` (self-grilling, both sides) over these questions, then publish the spec with `/to-spec` to `specs/breakpoint-service.md`. The spec is a `/to-spec` spec: its top-level sections are exactly the to-spec template (Problem Statement, Solution, User Stories, Implementation Decisions, Testing Decisions, Out of Scope, Further Notes). The foundation-api-design material lives inside those sections as subsections: under Implementation Decisions put the directive or service hierarchy, the proposed API (inputs, outputs, model signals, public methods, DI tokens and providers), the ARIA requirements it imposes on its consumers where any, and the comparison with the nearest Angular Material or CDK counterpart; under Further Notes put usage examples and the design decisions table. Prose describes the API; short type-level signatures are allowed where prose would be less precise, and no file paths.

2. Which plugin specs consume it and exactly what each needs from it; read the building-blocks matrix rows for those plugins.

Utility-specific questions:

- `NfsMediaQuery` as a signal service, `nfsBreakpointsToken` with Foundation's default map, `atLeast`, `upTo`, `only`, `is`, and the current breakpoint as signals.
- The rule-string parser shared by ResponsiveMenu, ResponsiveAccordionTabs, ResponsiveToggle `hideFor`, Tooltip `showOn`, Sticky `stickyOn`, OffCanvas `revealOn` and `inCanvasOn`, and Interchange named queries (`landscape`, `portrait`, `retina`).
- `reducedMotion()` as a signal.
- The server answer (the building-blocks decision says `small`) and the client-hint `useFactory` recipe reading `REQUEST`.
- The `nfsBreakpointsToken` shape and the dev-mode drift check against the `--nfs-breakpoint-*` properties the Sass packaging decision emits.

## Answer

Gist: one root service, `NfsMediaQuery` (`@Service()`), over CDK `MediaMatcher`, configured by `nfsBreakpointsToken` (`{map, serverBreakpoint?}`, px, root factory with Foundation's defaults). `current` and `reducedMotion` are signals; `atLeast`, `upTo`, `only`, `is`, `resolve`, and `matches` are reactive reads; `get` returns Foundation's em query. The service answers with the Server breakpoint on the server and, on the client, until its first `afterNextRender` `earlyRead` callback, where it goes live inside the same tick; a per-request Server breakpoint reaches the client through `TransferState`. One pure parser reads Breakpoint rules by map order. A development-mode check compares the map with the Breakpoint properties and warns once, naming the include when they are missing. Spec: [specs/breakpoint-service.md](../specs/breakpoint-service.md).

### Decision log

Round 1 (no prerequisites: the Foundation contract and the upstream decisions).

1. Q: What exactly does Foundation's MediaQuery utility do? A: It serialises `$breakpoints` into `.foundation-mq { font-family }`, appends `<meta class="foundation-mq">`, builds `only screen and (min-width: <em>)` per breakpoint in map order, and offers `current`, `atLeast`, `upTo`, `only`, `is` (`up`/`only`/`down`, throwing on other modifiers), `get`, `next` (throwing on unknown names), `_reInit`, a `matchMedia` polyfill, and `changed.zf.mediaquery` from a window `resize` watcher. Source: FS `js/foundation.util.mediaQuery.js` (read in full: `_init`, `atLeast`, `upTo`, `is`, `next`, `_getCurrentSize`, `_watcher`); FS `docs/pages/media-queries.md:187-236`; R:`foundation-utilities-conventions.md` 3.1-3.3.
2. Q: Which values does the em query use? A: `-zf-bp-to-em` converts px and unitless values through `rem-calc($value, $base: 16px)` and then to em, so the query value is px / 16 (`640px` -> `40em`), serialised as `small=0em&medium=40em&...`. Source: FS `scss/util/_unit.scss:62-70`, `scss/util/_breakpoint.scss:201-209`.
3. Q: Which plugins consume it, with which calls? A: Equalizer `is(equalizeOn)` (default `''`, skipped by the plugin), Interchange iterates `queries`, OffCanvas `atLeast(revealOn|inCanvasOn)`, ResponsiveAccordionTabs and ResponsiveMenu `atLeast` per rule key, ResponsiveToggle `atLeast(hideFor)` (default `medium`), Sticky `is(stickyOn)` (default `medium`), Tooltip `is(showOn)` (default `small`, `'all'` bypass). Source: R:`foundation-utilities-conventions.md` 3.3; FS `foundation.tooltip.js:133, 366`, `foundation.sticky.js:305, 473`, `foundation.equalizer.js:55, 119, 312`, `foundation.responsiveToggle.js:82, 100, 141`, `foundation.offcanvas.js:198, 204, 217, 672, 680`.
4. Q: What is fixed upstream? A: ADR 0005 (token source of truth, service over `MediaMatcher`, signals, `serverBreakpoint: 'small'`, drift check, `REQUEST` recipe); BB 1.7 (queries built from the token, CSS first, rule syntax kept with an object form); BB 1.11 decisions 3, 8, 11 (no `matchMedia` before render callbacks; breakpoint-gated hidden state in Foundation CSS; no request tokens read by the library); ADR 0012 and the Sass packaging decisions 13-15 (the consumer's `@include nfs-breakpoint-properties;` emits `--nfs-breakpoint-<name>` px values; this spec owns the token shape, the drift check, and the missing-include behaviour). Source: those documents.
5. Q: What does CDK offer? A: `MediaMatcher.matchMedia` (WebKit/Blink empty style rule so `change` fires, `CSP_NONCE`; a server stub whose `matches` is true only for `''` and `all`, with `addListener`/`removeListener` and no `addEventListener`), `BreakpointObserver` (`isMatched`, `observe` with `debounceTime(0)` after the first value, `NgZone.run`, deprecated `addListener`), and Material's `Breakpoints` constants, unrelated to Foundation's map. Source: NGC `src/cdk/layout/media-matcher.ts:19-99`, `breakpoints-observer.ts`, `breakpoints.ts`; R:`angular-cdk-inventory.md` layout; R:`angular-material-reference.md` 11.

Round 2 (depends on 1-5: shape, token, primitive).

6. Q: Service, directive family, or per-plugin code? A: One `@Service()` root singleton plus a token plus pure functions; breakpoint state is shared (BB 1.5) and there is no element to attach a directive to. `@Service()` is stable in v22 and the skill's recommended form. Source: BB 1.5, Table C; R:`angular-22-api-survey.md` Dependency injection; angular-developer `creating-services.md`.
7. Q: Token shape? A: `InjectionToken<NfsBreakpoints>`, `NfsBreakpoints = {map: NfsBreakpointMap; serverBreakpoint?: NfsBreakpointName}`, map values in px, root factory `{map: nfsDefaultBreakpointMap}`. A nested `map` avoids a breakpoint named `serverBreakpoint` colliding with the setting; px is the unit of Foundation's default settings and of the Breakpoint properties (Sass decision 13). Source: ADR 0005; Sass packaging decision 13; FS `scss/util/_breakpoint.scss:14-20`.
8. Q: Map order and validation? A: The service sorts by value, so key order does not matter (JavaScript orders integer-like keys first, which would break a map-order assumption). Valid: finite, non-negative, unique values, exactly one `0`, `serverBreakpoint` a key. Development builds throw at construction; production skips validation. Source: FS `_breakpoint.scss:41-46` (first value must be `0`); ECMAScript property order for integer-like keys.
9. Q: Server breakpoint default? A: The Zero breakpoint (the key with value `0`; `small` in Foundation's map), Foundation's `$-zf-zero-breakpoint`, so a renamed map keeps working. Source: FS `_breakpoint.scss:39-47`; ADR 0005 (`small`).
10. Q: Shape A or a Defaults token? A: Shape A (required configuration, root factory), not the per-Plugin Shape B Defaults token of BB 1.4: the service always needs a map. No `provideNfsBreakpoints()`: one token needs no wrapper. Source: R:`di-and-composition-patterns.md` 5; BB 1.9.
11. Q: Where may the token be provided? A: Application level only (the application and server configurations): the root service reads it once, so route and element providers are never seen. Source: angular-developer `defining-providers.md` (scopes); `@Service()` root semantics.
12. Q: Primitive? A: `MediaMatcher.matchMedia` for every query with `addEventListener('change')`; not `BreakpointObserver` (RxJS, debounce, `NgZone.run`), not raw `matchMedia` (loses CDK's engine workaround, nonce, and test seam). `MediaQueryList` `change` and `prefers-reduced-motion` are Baseline widely available. Source: decision 5; R:`web-platform-features.md` Feature summary, 11 Known gaps, 18; BB 1.2.
13. Q: How is `current` computed? A: One list per breakpoint query; on any `change`, `current` is the largest matching breakpoint. The queries are nested min-width ranges, so this equals Foundation's per-query `atLeast`. Source: FS `_getCurrentSize`.

Round 3 (depends on 6-13: API, reactivity, parser).

14. Q: Signals or signal-returning functions, and memoisation? A: `current` and `reducedMotion` are signals (private writable, exposed read-only); `atLeast`, `upTo`, `only`, `is`, `resolve` are reactive reads of `current` returning plain values, reactive in any reactive context and a snapshot elsewhere (Foundation's behaviour). No service cache: each is a map lookup and an index comparison; consumers memoise with `computed`. Rejected: `atLeast(name): Signal<boolean>` (double calls in templates, and a per-argument cache to avoid a new `computed` per pass). This refines ADR 0005's "as signals"; proposed wording change below. Source: angular-developer `signals-overview.md` (reactive contexts, `computed` memoisation); R:`angular-22-api-survey.md` Signals.
15. Q: Which Foundation members survive? A: `current`, `atLeast`, `upTo`, `only`, `is`, `get`; new `resolve`, `matches`, `breakpoints`, `reducedMotion`. Dropped: `next` (no consumer), `queries`, `_init`, `_reInit`, the polyfill; `changed.zf.mediaquery` becomes the `current` signal (derive with `computed`, `linkedSignal`, `effect`, or `toObservable`). Source: decisions 1, 3; BB 1.4 (lifecycle events have no counterpart).
16. Q: Unknown names and bad modifiers? A: Development warning once per distinct string, answer `false`; never throw (a template typo must not crash the app). `upTo` of the largest breakpoint is `true`. Source: FS `atLeast` (`false` for unknown), `is`/`next` (throw); the Button spec's development-warning convention.
17. Q: Breakpoint query grammar? A: `'all' | '' | <name> | <name> (up|only|down)`, trimmed; `all` (Tooltip) and `''` (Equalizer's "no gate") are `true`, so consuming specs need no special case. Source: FS `is()`; `foundation.tooltip.js:133`; `foundation.equalizer.js:55`.
18. Q: Breakpoint rule grammar and typed result? A: Whitespace-separated tokens, `mode` or `<breakpoint>-<mode>` split at the last hyphen, modes supplied by the consuming Plugin; result `NfsBreakpointRules<M> = Readonly<Partial<Record<NfsBreakpointName, M>>>`; the object form is validated the same way; a bare mode maps to the Zero breakpoint; a repeated breakpoint keeps the last token and warns; unknown modes and breakpoints warn and are skipped. Pure function `parseNfsBreakpointRules(rules, modes, breakpoints)` so Node tests reach it. Source: FS `foundation.responsiveMenu.js` L65-83 (split on `-`, bare means `small`, `MenuPlugins[x] !== null` lets `undefined` through), `foundation.responsiveAccordionTabs.js:77-95`; R:`foundation-inventory-menus.md` 4.2; BB 1.7 bullet 5.
19. Q: Rule resolution order? A: The largest rule breakpoint at or below `current` (map order), exposed as `resolve(rules)`, `undefined` when none applies (Foundation's "No match? No dice", left to the consuming spec). Foundation takes the last matching rule in written order, but its docs say the ResponsiveAccordionTabs values "can be in any order", which only map order makes true, and every documented ResponsiveMenu example is written smallest first, where both agree. Source: FS `foundation.responsiveMenu.js` `_checkMediaQueries` (L113-139); FS `docs/pages/responsive-accordion-tabs.md:22`; R:`foundation-inventory-menus.md` 4.5.
20. Q: Interchange named queries? A: `nfsDefaultNamedQueries` holds Foundation's `landscape`, `portrait`, `retina` strings verbatim; `matches(mediaQuery)` tracks any query with one lazily created signal and list per distinct string (queued until the service goes live); custom named queries are the `namedQueries` field of Interchange's Defaults token, defaulting to the constant; a token is a breakpoint name (`atLeast`) or a named-query key (`matches`), else warn and `false`. Interchange keeps its own last-matching-rule order. Named queries stay off `nfsBreakpointsToken` because only Interchange uses them and BB Table B already places them in its Defaults token. Source: R:`foundation-inventory-forms-media.md` Interchange (named media queries, `interchange.js:109-116, 243-247`; docs `interchange.md:300-304` for custom names); BB Table B Interchange.
21. Q: Keep the `retina` string verbatim? A: Yes: parity, and unsupported parts of a media query list evaluate to false harmlessly. A shorter `(min-resolution: 2dppx)` would be a behaviour change for no gain. Source: FS `foundation.interchange.js:246`.
22. Q: `get()` output format? A: `only screen and (min-width: <px / 16>em)` with JavaScript's shortest number formatting (`0em`, `40em`, `68.75em`), matching Foundation's serialisation; range syntax and px are rejected to stay equal to Foundation's CSS under a changed default font size. Source: decisions 1-2; FS `docs/pages/media-queries.md` (`get('medium')`).
23. Q: `reducedMotion`? A: A signal over `(prefers-reduced-motion: reduce)`, live in both directions; `false` on the server and before going live (nothing at first paint depends on it: autoplay starts in render callbacks, smooth scrolling in handlers). Material's cached `_getAnimationsState()` read is not borrowed because Orbit must restart autoplay when the setting changes back. Source: BB 1.6 rule 5; NGC `src/material/core/animation/animation.ts:27-36`; R:`web-platform-features.md` 18.
24. Q: What happens while printing? A: When no breakpoint query matches (`only screen` fails for print media), `current` keeps its previous value, so menus and tabs keep their screen modes in the printout; Foundation recomputed only on `resize`, so it behaved the same in practice. Source: FS `_watcher` (resize only), `_getCurrentSize` (`undefined` with no match).

Round 4 (depends on 12-14: rendering modes and the handoff).

25. Q: Server answer? A: `current` is the Server breakpoint for the request, predicates derive from it (the Zero breakpoint is `true`, unlike CDK's stub), `matches()` and `reducedMotion` are `false`; no `MediaMatcher`, `window`, or computed-style call. Source: R:`angular-rendering-modes.md` 7 rule 9; decision 5 (the stub answers `false`).
26. Q: When does the client read the viewport? A: Only in the service's first `afterNextRender({earlyRead})` callback, registered without a view at construction; before that, the Server breakpoint. `afterNextRender` is a no-op on the server, so no platform check is needed. Source: BB 1.11 decision 3; NG `packages/core/src/render3/after_render/hooks.ts:384-407` (injector from context, `ngServerMode` no-op), `:443-470` (registration without a `ViewContext`).
27. Q: Does the switch paint an intermediate state? A: No, by source reading: after-render hooks run at the end of each synchronisation pass and `ApplicationRef.synchronize` loops while views are dirty (up to 10 passes), so signals set in `earlyRead` re-render before the tick returns. Phases run across all sequences in the order `earlyRead`, `write`, `mixedReadWrite`, `read`, so consumer callbacks in the later phases of that pass already see live values. Source: NG `packages/core/src/application/application_ref.ts:588-610, 617-680`; NG `packages/core/src/render3/after_render/manager.ts:40-45, 79-100`. Confirmation by running code is listed under Prototype needed.
28. Q: What happens at hydration when the client breakpoint differs? A: The hydration pass claims server nodes with exactly the server's values; the live values then rewrite class and attribute bindings and rebuild a differing `@if`/`@switch` branch, which hydration treats as a re-render, not an error. Source: R:`angular-rendering-modes.md` 2 (Structure rules: only node type and tag are compared; Control flow: a non-matching template id removes the dehydrated branch); BB 1.11 decision 8.
29. Q: How does the client learn a per-request Server breakpoint? A: `TransferState`: the constructor reads key `nfsServerBreakpoint` with the token value as default, uses it as the initial `current`, and writes it back; the server's copy is serialised into `ng-state` by `provideServerRendering()`, the client's is never serialised. A name missing from the client map warns and falls back. Rejected: the client token alone (a server rendering `large` from client hints would hydrate against a client assuming `small`). Source: NG `packages/core/src/transfer_state.ts:60-140` (public API; the client reads the script at first injection); NG `packages/platform-server/src/transfer_state.ts:31-110`. Proposed as an ADR (it meets the bar: hard to reverse as a behaviour every gated spec relies on, surprising, real alternatives).
30. Q: Per-instance gating for directives that hydrate later? A: Not needed: once the app has rendered, the service is live, so a directive in a later-hydrated block renders live values in its hydration render (a rewrite or branch rebuild, as in decision 28), and a directive created later in a plain `@defer` block has no swap at all. Source: R:`angular-rendering-modes.md` 3 (per block: load, one render, resolve, then replay).
31. Q: Event replay? A: The service declares no template or host listeners, so no `jsaction`; replay runs after the hydrating render's `afterNextRender` callbacks, so replayed handlers see live values. Source: R:`angular-rendering-modes.md` 3 ("What a directive inside a hydrate block may assume"), 4.
32. Q: `hydrate never`? A: The Server breakpoint's state forever, which is why first-paint visibility per breakpoint uses Foundation's classes (audit 0002 H4; ADR 0008 Consequences). Source: R:`angular-rendering-modes.md` 7 rule 11.
33. Q: Prerendering? A: SSR at build time, `REQUEST` is `null`, so a per-request factory falls back to the default and the page carries it in `TransferState`. Source: NG `adev/src/content/guide/ssr.md:358-391`.
34. Q: Zoneless and zone-based behaviour? A: Every update is a signal write, which schedules zoneless change detection when a template reads it; no `NgZone.run` (CDK needs it only for RxJS plus patched `addListener`). Zone apps get the same scheduling, and zone.js runs the `change` callback in the zone. Listeners are removed through `DestroyRef`. Source: NG `adev/src/content/guide/zoneless.md:45-60`; NGC `breakpoints-observer.ts` (`_zone.run`).

Round 5 (depends on 7 and 25-29: the client-hint recipe and the drift check).

35. Q: Client-hint recipe? A: Consumer code in the server configuration: a `useFactory` provider of `nfsBreakpointsToken` that reads `inject(REQUEST)?.headers.get('Sec-CH-Viewport-Width')` and maps it with the exported pure `nfsBreakpointForWidth(map, widthPx)`; `useFactory`, not `useValue`, because top-level server values persist across requests. The server entry sends `Accept-CH: Sec-CH-Viewport-Width` (the hint arrives only on later requests) and `Vary`. Chromium only; Firefox and Safari get the default. The library reads no request token. Source: NG `adev/src/content/guide/ssr.md:266-271, 358-391`; MDN `Sec-CH-Viewport-Width` (opt-in through `Accept-CH`, `Vary` advised, experimental) and `Sec-CH-UA-Mobile` (low-entropy, not Baseline), fetched 2026-09-26 through markdown.new; BB 1.11 decision 11.
36. Q: Drift check mechanics? A: Development only (`ngDevMode`), in the first `earlyRead` callback, once per JavaScript realm: for each map name read `getComputedStyle(documentElement).getPropertyValue('--nfs-breakpoint-<name>')`, trim, parse px, compare within 0.01 px. Unregistered custom properties compute to their specified text. Source: Sass packaging decisions 13 and 15; BB 1.7 bullet 1.
37. Q: What if the properties are missing? A: One warning that names `@include nfs-breakpoint-properties;` (the Sass ticket's recommended default); a partial mismatch lists each name with both values. Source: Sass packaging decision 15.
38. Q: Once per realm or once per application? A: Per realm: consumer unit tests without the Sass would otherwise warn in every test; per realm is one line per test file. No opt-out field (more API for a warning). Material removed its own presence check. Source: Sass packaging decision 11 (Material removed its theme-presence check).
39. Q: Can the check find breakpoints that exist only in Sass? A: No: computed style cannot list custom properties by prefix. Documented limit; any Plugin Option naming such a breakpoint gets the unknown-name warning. A names-list property or `@property` registration would need a change to the Sass decision; recorded as a follow-up, not decided. Source: CSSOM `getPropertyValue` needs the property name.

Round 6 (depends on all of the above: consumers' obligations, entry point, tests).

40. Q: ARIA requirements on consumers? A: None of its own; four rules for consumers: focus continuity on swaps (never on the first-render switch, where nothing holds focus yet), no server-bound `hidden`/`inert` for content Foundation shows at larger breakpoints, reduced motion for JavaScript-driven motion (WCAG 2.2.2 for Orbit), no live-region announcements of breakpoint changes. Source: BB 1.10 (focus persistence, reduced motion), 1.11 decision 8; audit 0002 H4.
41. Q: Entry point and naming? A: `ngx-foundation-sites/media-query`, class `NfsMediaQuery` (Foundation's utility name; there is no structural class), token `nfsBreakpointsToken`, constants `nfsDefaultBreakpointMap`, `nfsDefaultNamedQueries`, pure functions `parseNfsBreakpointRules`, `nfsBreakpointForWidth`. Source: BB 1.3; ADR 0009.
42. Q: Implementation level and fallback? A: Custom Angular service over CDK `MediaMatcher` (platform queries underneath, no Aria counterpart). Fallback only if a target engine misbehaved with `change`: a `ResizeObserver` on the document element recomputing from `matches`, same API. Source: BB 1.2, Table C; ADR 0005.
43. Q: Testing seams? A: Story ids `media-query--<story>` (six stories); play functions assert width-independent relationships; browser-level tests fake `MediaMatcher` (CDK's documented seam) for the handoff, changes, the print hold, `matches`, cleanup, validation, drift warnings in their own file, and the transfer fallback; node-level Vitest for the pure parser, the query grammar, width mapping, the query builder, and the SSR smoke (Server breakpoint, the `TransferState` script, the `REQUEST` factory with and without a request, no `MediaMatcher` call); Playwright e2e for viewport thresholds in three engines, reduced motion and print emulation, and the prerendered fixture (no-JavaScript first paint, hydration at 1300 px without NG05xx, a `hydrate on viewport` block). Source: BB 1.12; R:`angular-material-reference.md` 11 ("MediaMatcher ... is the thing to fake in tests"); R:`tooling-baseline.md`.
44. Q: Platform features to adopt later? A: Cross-browser viewport client hints; `@property` registration of the Breakpoint properties (not Baseline widely available by 2026-05-07, and it needs a Sass decision change); `@custom-media` for consumers' own CSS. None replaces the token, because the server has no CSS. Source: the MDN client hint pages (decision 35); R:`web-platform-features.md` Feature summary.
45. Q: Does the spec reuse Foundation's SCSS without re-implementing it (the user's standing rule)? A: Yes: the only CSS is the `nfs-breakpoint-properties` Library mixin decided by the Sass packaging ticket, which reads the consumer's `$breakpoints` and calls Foundation's `-zf-bp-to-em`; the service adds no CSS, and breakpoint-gated first-paint visibility stays in Foundation's `.show-for-*`/`.hide-for-*`/`.reveal-for-*`/`.in-canvas-for-*` classes. Source: ADR 0012; BB 1.7 "CSS first".

### OPEN FOR HUMAN

None. Two judgment calls are recorded rather than left open, because sources support either side and the choice is cheap to revisit before implementation: predicates as reactive reads instead of signal-returning methods (decision 14, refining ADR 0005's wording), and the drift warning once per JavaScript realm with no opt-out (decision 38).

### WCAG 2.2 AA revision, 2026-09-26

Revision for the user's rule that every directive and component complies with WCAG 2.2 AA, with a criteria subsection per spec ([map](../map.md), Standing preferences; ADR 0022). The spec gains `### WCAG 2.2 AA` under Implementation Decisions (after the ARIA requirements imposed on consumers), an amended consumer rule 1, and the test-layer wording of the [Decide the browser testing stack: Playwright component tests, Vitest Browser, or both](41-browser-testing-stack-decision.md) answer. The service renders nothing, so every criterion is one it imposes on consumers, each with the test the consuming spec inherits. No Sass setting or library rule is required.

46. **1.4.10 Reflow?** Imposed: at 320 CSS px no consumer scrolls horizontally. 400 percent zoom of a 1280 px window is a 320 CSS px viewport, which the em queries answer with the Zero breakpoint through `change` events (decision 13), so the Zero breakpoint's mode (a bare rule mode, the Zero-breakpoint state of a query) must fit 320 px: ResponsiveMenu's bare mode is `drilldown` or `accordion`, never a horizontal `dropdown`. Foundation's documented rule examples pass. Inherited test: e2e at 320 by 640 px, `scrollWidth <= 320`, three engines.
47. **1.4.4 Resize Text?** Imposed: breakpoint behaviour follows the user's default font size because queries are em (decisions 2, 22); consumers never build px queries or compare `window.innerWidth` with the map. Foundation's own queries are em (FS `scss/util/_breakpoint.scss:201-209`). Inherited test: node-level query builder cases, and e2e in Firefox with `font.size.variable.x-western` at 20 (`medium` at 800 px, not 640). Firefox only, because it is the engine whose default font size Playwright can set through a documented user preference.
48. **2.4.3 Focus Order: consumer rule 1 amended.** The old sentence "A swap at the first render (Server breakpoint to live) never moves focus, because nothing inside the widget can hold focus before the first render callback" is false for server-rendered and prerendered pages: a server-rendered control can hold focus before hydration ([Prototype: ResponsiveAccordionTabs as one component](51-prototype-responsive-accordion-tabs.md), case 15, three engines). The rule now requires a consumer that swaps structure at the handoff to read the live `document.activeElement` in its `earlyRead` callback before the swap and focus the equivalent control once the new nodes exist, the prototype's mechanism; in a client-rendered app the same path finds nothing to move. Inherited tests: browser-level with the fake `MediaMatcher`, e2e real resize, and the fixture case "focus before hydration". The prototype's other hand-off (the service exposing the Server breakpoint for the `instance` strategy) is an API question for the [Spec: Responsive Accordion Tabs](19-spec-responsive-accordion-tabs.md) and ADR 0014, not part of this revision.
49. **2.2.2 Pause, Stop, Hide?** Imposed: motion that a breakpoint or `reducedMotion` change starts and that runs over 5 s has a visible pause or stop control in every mode where it runs; a breakpoint change never restarts motion the user paused; nothing starts while `reducedMotion` is `true` (decision 23; consumer rule 3). Foundation's Orbit has no reduced-motion check (FS `js/foundation.orbit.js`, no `matchMedia` or reduced-motion read). Inherited tests: browser-level with the fake `MediaMatcher` (pause survives a threshold crossing), e2e with `emulateMedia({reducedMotion: 'reduce'})`.
50. **1.3.4 Orientation?** Added because the service tracks the `landscape` and `portrait` named queries: a consumer branch on orientation may change layout but never restrict content or function to one orientation. Inherited test: e2e at 640 by 360 and 360 by 640 px, same controls and text.
51. **4.1.3 Status Messages?** Not applicable: breakpoint changes are layout, not status, and consumer rule 4 forbids announcing them.
52. **Test layers.** Wording from the [Decide the browser testing stack: Playwright component tests, Vitest Browser, or both](41-browser-testing-stack-decision.md) answer: layer 1 through `npx nx test-storybook <lib>` with the six axe tags named; layer 2 renamed to Vitest browser mode with the verbatim opening sentence; layer 3's "own file or process" sentence replaced by `<name>.ssr.spec.ts` through `renderServer()`; layer 4 headed with both e2e commands, plus a 320 px reflow case and the Firefox resize-text case, and `@axe-core/playwright` with the six tags on the fixture app.

Settings and rules required by this revision: none. Requirements imposed on consumers: the Zero breakpoint's mode fits 320 px; em queries through the service only; focus carried on every swap including the hydration handoff; a pause control and no restart for breakpoint-started motion; no orientation lock.

### Proposed glossary terms

**Breakpoint service**:
The shared piece that answers which breakpoint of the Breakpoint map the viewport is at, and whether the user asked for reduced motion; the replacement for Foundation's MediaQuery utility.
_Avoid_: MediaQuery (Foundation's name), breakpoint observer, media service

**Zero breakpoint**:
The breakpoint of the Breakpoint map whose minimum width is 0 (`small` in Foundation's defaults); a Breakpoint rule mode written without a breakpoint applies from it, and it is the default Server breakpoint.
_Avoid_: base breakpoint, mobile breakpoint, default breakpoint

**Breakpoint query**:
An Option value that names a breakpoint with an optional `up`, `only`, or `down` modifier (`medium`, `large only`, `medium down`), as in Tooltip `showOn` or Sticky `stickyOn`; distinct from a Breakpoint rule, which assigns modes.
_Avoid_: media query (for this), breakpoint string, size

**Named query**:
A media query addressed by a name that is not a breakpoint (`landscape`, `portrait`, `retina`, or the consumer's own), used in Interchange rules.
_Avoid_: special query (Foundation's code name), custom breakpoint

Amendment to the existing term (the default now follows the map, and the client keeps it until its first render):

**Server breakpoint**:
The breakpoint the library assumes while rendering on the server or prerendering, and on the client until its first render completes (the Zero breakpoint by default), so server HTML is deterministic and hydrates unchanged.
_Avoid_: SSR default, fallback breakpoint, mobile default

### Proposed ADR

[The Breakpoint service keeps the Server breakpoint until its first render callback, and the server hands its choice to the client through `TransferState`](../adr/0014-breakpoint-service-first-render-handoff.md) (decisions 26-30). Hard to reverse: every breakpoint-gated spec's rendering-modes section relies on it. Surprising: a reader expects the client to read the viewport immediately and would not expect `TransferState` in a breakpoint utility. Real trade-off: live-at-construction, per-instance gating, and a client-token-only start were each considered.
