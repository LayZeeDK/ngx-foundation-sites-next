## Question

What is the Angular design for Foundation's Button component in the next library, and what does its spec say? Button has no Foundation JavaScript plugin; it is a CSS component the user added to the destination, so the spec must earn its directive with something beyond applying a class.

The result must be the best combination of: Foundation for Sites SCSS and the component's features; the ARIA APG button pattern and WAI-ARIA; WHATWG HTML (`<button>`, `<a>`, `<input type="submit">`, the `disabled` attribute, `aria-disabled`, form-associated behaviour); Angular Aria and Angular CDK where they apply; Angular Material-equivalent accessibility and Material-equivalent component API (Material's button is a directive family on native `button` and `a` elements with appearance variants); and the modern DI patterns recorded in `research/di-and-composition-patterns.md`. One component may yield several related directives (for example button, button group, close button); the spec covers the set it decides on.

## Answer

Spec: [specs/button.md](../specs/button.md).

Gist: one attribute directive, `NfsButton` on `button[nfsButton], a[nfsButton]`, with three inputs (`disabled`, `disabledInteractive`, `type`) and no outputs, models, methods, tokens, or listeners. It adds `.button`, defaults `<button>` to `type="button"` (explicit types and Foundation's `.submit` marker win), and owns the disabled contract: native `disabled` on buttons; an opt-in focusable disabled mode that renders `aria-disabled="true"`, `.disabled`, and `type="button"`; and a disabled link rendered as an HTML placeholder link (the consumer binds `href` or `routerLink` to `null`) with `role="link"`, `aria-disabled="true"`, `.disabled`, and dev-mode checks. Size, color, fill, `.expanded`, `.dropdown`, and `.arrow-only` stay consumer-written Variant classes; Button Group and Close Button stay markup. Implementation level: native platform. The directive earns its place with the `type` default and a disabled state that holds in every rendering mode, not with the classes.

### Decision log

Sources are cited by name: FS = the Foundation 6.9.0 clone (docs pages and Sass partials), NG = the Angular 22.2.x clone, NGC = the components 22.2.x clone, APG = the aria-practices clone, ARIA = the WAI-ARIA clone, HTML = WHATWG HTML (multipage `form-elements`, `form-control-infrastructure`, `text-level-semantics`, fetched 2026-09-25 through markdown.new).

1. **What is Foundation's Button contract, and which of the ticket's names are real?** Classes only: `.button`; sizes from `$button-sizes` with the `default` key removed from the class loop (`.tiny`, `.small`, `.large`); colors from `$button-palette` (defaults to `$foundation-palette`: primary, secondary, success, warning, alert; consumer-configurable); fills from `@each $filling in (solid hollow clear)` skipping the class equal to `$button-fill` (so `.solid` exists when the default fill is changed); `.expanded` plus responsive `-expanded` classes behind `$button-responsive-expanded`; `.disabled` and `[disabled]`; `.dropdown`; `.arrow-only`. No Plugin, no `defaults`, no Options, no events (FS `_button.scss` lines 58-94, 332-427; `button.md`). Per audit 0001 H6, none of the ticket's input names are Foundation Options: they are classes, `default` has no class, and `arrowOnly` is `.arrow-only`.
2. **Directive or component; which elements?** Attribute directive on native `<button>` and `<a>`, Material's shape (NGC `button.ts` selector `button[matButton], a[matButton]`, `MatAnchor = MatButton`), per ADR 0001. `<input type="submit|button|reset">` is not a host: it cannot hold `.show-for-sr` text, icons, or the `.dropdown` `::after` arrow, Foundation's docs never show it, and native `disabled` already works there (FS `button.md`; HTML button content model).
3. **One class or two?** One class for both hosts, so a consumer cannot import one and silently lose the other selector. Two classes were considered only to give `<button>` a listener the anchor must not have; decision 13 removes every listener, so the reason disappears.
4. **How does it honour the `.button` contract?** A static host `class: 'button'`, merged with the consumer's static classes (the way Material's host `class: 'mdc-button'` works, NGC `button.ts:36-38`). Consumer-written `class="button"` stays harmless.
5. **Does the directive earn its place beyond applying a class?** Honest answer: the classes alone do not earn it, since a consumer can write every Foundation class. It earns its place with the `type` default (decisions 9 to 11), a disabled state that disables in every rendering mode for buttons and links (decisions 12, 13, 15, 16), and a focusable disabled state Foundation's CSS can style (decision 14). That is the smallest thing that earns it; typed appearance inputs, a defaults token, a toggle model, a close-button directive, and a group directive were each rejected (decisions 6, 7, 18, 20, 21).
6. **Which appearance names become `input()`s, which are enums?** None. Variant classes stay consumer-written, static or bound with `[class.x]`. Reasons: the repo's API-design skill says "CSS class is purely for styling (no behavior): apply class directly, no directive needed"; the map makes Foundation classes the styling contract; the value sets are open (custom palette names, custom sizes, `.solid` only with a non-solid `$button-fill`, responsive `-expanded` classes), so typed inputs would either lie or collapse to `string`; Material's appearance input exists because its classes are private (NGC `button.ts` `APPEARANCE_CLASSES`). This departs from building-blocks Table A's sketched `size`, `color`, `fill`, `expanded`, `dropdown`, `arrowOnly` inputs; see the proposed ADR and building-blocks changes below.
7. **A default-options token library-wide?** No. The glossary's Defaults token replaces a Plugin's `Foundation.X.defaults`, and Button has none; appearance defaults are Sass settings (`$button-fill`, `$button-background`, the `default` size); Material's `MAT_BUTTON_CONFIG.disabledInteractive` (NGC `button-base.ts:34-46`) is the one runtime default worth copying, and it waits for a real need. Matches building-blocks Table B ("None (no token)").
8. **Outputs?** None; native events are the API. No models, no methods (Material's `focus(origin)` exists for `FocusMonitor`, which buttons here do not use). `exportAs: 'nfsButton'` for template references to the input signals.
9. **Default `type`?** Yes, `button`. HTML's missing-value default for `<button type>` is the Auto state, which is a submit button inside a form (HTML `form-elements`, the button element, lines on "missing value default ... Auto state" and "said to be a submit button"); Foundation's docs callout asks for `type="button"` on every non-submit button (FS `button.md`). Aria's accordion trigger and Material's dialog close do the same (NGC `accordion-trigger.ts` constructor; `dialog-content-directives.ts` `type = 'button'`).
10. **How is `type` set without clobbering the consumer?** As a `type` input (`'button' | 'submit' | 'reset'`) bound to `[attr.type]` on button hosts, MatDialogClose's shape. A static `type` feeds the input and `[type]` binds it; a consumer `[attr.type]` loses (Angular collision rule: dynamic vs dynamic, the host binding wins; NG `adev/.../components/host-elements.md` "Binding collisions"). Rejected: a static host attribute (one class serves `<a>`, where `type` is a MIME hint), and Aria's constructor `setAttribute` (a construction-time DOM write, which building-blocks 1.11 decision 3 forbids).
11. **Foundation's `.submit` marker?** Honoured: when the static class list contains `submit` and no `type` is given, the default is `submit`, so Foundation's docs markup `<button class="submit success button">` still submits. `.submit` has no CSS (no hit in FS `scss/` outside normalize's `[type="submit"]`); it is a docs convention. Read once through `HostAttributeToken('class')`, which returns the static classes (NG `render3/di.ts` `injectAttributeImpl`).
12. **`disabled` versus `aria-disabled` on buttons: which is the default?** Native `disabled`. The APG keyboard practice ("Focusability of disabled controls") removes disabled controls from the tab order when their presence can be inferred and keeps `aria-disabled` for elements that must stay discoverable (its examples are toolbar buttons and composite items); HTML makes a disabled control drop queued clicks (HTML `form-control-infrastructure`: "A form control that is disabled must prevent any click events ... from being dispatched on the element") and blocks implicit submission through a disabled default button. It is the only disabled mode the platform enforces before hydration and in `hydrate never`. This narrows building-blocks 1.10's `aria-disabled` default to composite items (proposed change below).
13. **Does the directive declare listeners (to block clicks)?** No listeners at all. Sources: the JSAction dispatcher calls `preventDefault()` on a `click` whose action element is an `<a>` carrying `jsaction` (NG `primitives/event-dispatch/src/dispatcher.ts` `shouldPreventDefaultBeforeDispatching`), which applies to live clicks inside dehydrated blocks (rendering-modes research, section 4), so a host `click` listener would stop every plain-`href` link-button there from navigating; during replay `invokeListeners` calls every stashed listener on the element and `stopImmediatePropagation` is patched to `stopPropagation` (NG `event_delegation_utils.ts` `invokeListeners`; `event_dispatcher.ts` `prepareEventForBubbling`), so a blocker cannot stop the consumer's own listener; and `hydrate never` blocks are never annotated with `jsaction` (NG `hydration/annotate.ts`, `isHydrateNeverBlock`), so no listener ever runs there.
14. **`disabledInteractive`: name and behaviour?** Material's name (`disabledInteractive`, NGC `button-base.ts:126-140`; the ticket names it) rather than Aria's container-level `softDisabled`. While `disabled`: `aria-disabled="true"`, `.disabled` (Foundation styles `.disabled` and `[disabled]`, not `[aria-disabled]`, FS `_button.scss:384-387`), focusable, and `type="button"`, so the platform performs no submit or reset (HTML button activation behaviour). Consumer handlers still receive clicks and guard themselves, as Material documents ("you should guard against such cases in your component", NGC `button.md`). No effect on `<a>` hosts. Edge: a single-text-field form can still submit implicitly, because HTML then treats the form as having no submit button (HTML `form-control-infrastructure`, implicit submission); a natively disabled button has no such gap.
15. **`a.button` disabled and `a.button` without `href`?** A disabled link is an HTML placeholder link: the consumer binds `href` or `routerLink` to `null`; the directive adds `role="link"`, `aria-disabled="true"`, `.disabled`. HTML: an `a` without `href` "represents a placeholder for where a link might otherwise have been placed" (HTML `text-level-semantics`); WAI-ARIA advises against `aria-disabled` on elements the host language cannot disable and says `aria-disabled` with scripting can disable an element with role `link` (ARIA `aria-disabled` definition); `link` supports `aria-disabled` (ARIA link role). Foundation's docs markup `aria-disabled` without a value is `false` (ARIA true/false value type: the empty string takes the default). Dev-mode checks warn on a disabled link that still has `href` and on an enabled `nfsButton` link without `href` (not focusable).
16. **Why can the directive not remove `href` itself?** RouterLink owns `href` through its own host binding `'[attr.href]': 'reactiveHref()'`, and `[routerLink]="null"` yields `href` null (NG `router_link.ts:185-199, 451-458, 578-582`); two directives binding one attribute resolve by directive order. The Router's documented disabling (`null`) is the consumer's second binding.
17. **Attribute ownership and collisions?** The directive owns `type`, `disabled`, `aria-disabled`, `role`. The static `role` is echoed through `HostAttributeToken('role')` so a consumer `role="switch"` survives; `.disabled` binds `true` or `undefined`, never `false`, because Angular's styling treats only `undefined` as "no opinion" (NG `render3/instructions/styling.ts` `isStylingValuePresent`), so a consumer's static `.disabled` is left alone. Not combined with Aria item directives that own the same attributes (NGC `aria/toolbar/toolbar-widget.ts` host binds `[attr.disabled]` and `[attr.aria-disabled]`; `aria/tabs/tab.ts` binds `aria-disabled` and static `role="tab"`).
18. **Toggle buttons (`aria-pressed`)?** The consumer's, as building-blocks Table A decided: bind `[attr.aria-pressed]` and keep the label constant (APG Button pattern). Foundation has no pressed class or style; Toggler's class mode covers class toggling with `aria-pressed` (building-blocks Table A, Toggler).
19. **Icon-only buttons and accessible names?** Guidance, not code: `.show-for-sr` text plus an `aria-hidden="true"` icon (FS `button.md` Accessibility; `button-group.md` Split Buttons); `aria-label` only without visible or screen-reader text (APG naming research: button and link are named from content). Axe's `button-name` and `link-name` rules in every story cover it; no runtime name check.
20. **The `.close-button` case?** Plain markup plus the Triggers utility's `nfsClose`; never `nfsButton` on it, because `.close-button` is a separate class contract (`position: absolute`, its own sizes `.small`/`.medium`, FS `_close-button.scss`) and `.button` padding and background would collide. Foundation's markup already carries `type="button"` and `aria-label` (FS `close-button.md`).
21. **Button group: directive with a Parent token, or markup?** Markup. The map lists Button Group as CSS-only and out of scope; Foundation's group rules are descendant selectors (`.button-group.small .button`, color and fill rules on `.button-group.<color> .button`, FS `_button-group.scss:215-259`), so the cascade already delivers sizes, colors, and fills to children. Guidance: optional `role="group"` with a name when the grouping carries meaning (split button); a single-tab-stop toolbar is Aria's toolbar, where the consumer writes `.button` classes directly (decision 17).
22. **Implementation level?** Native platform; stopped at the first level. Aria 22.2 has no button pattern (NGC `src/aria` holds accordion, combobox, grid, listbox, menu, tabs, toolbar, tree); CDK `FocusMonitor` and `InteractivityChecker` add nothing a button needs. No prototype risk was flagged by the map (building-blocks Table B: "None"), and none was found.
23. **State model, signals, zoneless?** Three signal inputs with `booleanAttribute` where boolean; host bindings compute everything; no `effect`, no timers, no `NgZone`. The only DOM read is the dev-mode link check inside `afterRenderEffect` (building-blocks 1.5).
24. **Server render and first paint?** The server HTML equals the hydrated DOM: `.button`, Variant classes, `type`, `disabled`, `aria-disabled`, `role`, `.disabled` are host bindings on inputs and static attributes; no platform branch, breakpoint, or generated id (rendering-modes research section 7 rules 1, 3, 8). Nothing runs before hydration outside host bindings.
25. **Full and incremental hydration, `@defer`, prerendering?** Hydration-clean by construction (no structure, identical values, no `ngSkipHydration`). No hydration boundary of its own (no parent or children); a Trigger on the button brings the Trigger's rule. No `@defer` in library templates (there is no template); its own entry point lets consumers defer it. In `hydrate never` the native elements keep working and disabled states hold. Prerendering is SSR at build time; no request tokens are read (ADR 0008).
26. **Event replay: which listeners replay; `preventDefault()` ordering?** The directive has none, so nothing of its own replays and the open question on replay detection does not touch it. Consumer listeners replay normally; natively disabled buttons queue nothing (no click is dispatched); `disabledInteractive` clicks replay to consumer listeners, which guard themselves. Stated consumer hazards, both Angular behaviour: a consumer `(click)` on an `a[nfsButton]` inside a dehydrated block cancels its native navigation (decision 13), and so does being a root node of a `hydrate on interaction` block, whose trigger annotates root nodes with `click` and `keydown` (NG `hydration/annotate.ts` `annotateDeferBlockRootNodesWithJsAction`; NG `primitives/defer/src/triggers.ts` `interactionEventNames`), so such links are wrapped in an element. The e2e regression test therefore uses `hydrate when`, which annotates no root nodes.
27. **Animation and reduced motion?** Only Foundation's `$button-transition` (background-color and color, 0.25 s). WCAG 2.2's motion-animation definition excludes changes of color or opacity that do not change perceived size, shape, position, or depth (w3c/wcag `guidelines/terms/21/motion-animation.html`), so no reduced-motion handling is needed; no Completion output waits on it; ADR 0003 has nothing to govern.
28. **Focus visibility?** Foundation's `disable-mouse-outline` matches only `[data-whatinput='mouse']`, set by the what-input library that Foundation's JavaScript depends on (FS `util/_mixins.scss:206-210`, `package.json`); the library never loads it, so the browser's `:focus-visible` heuristic governs the ring. No custom CSS.
29. **Foundation behaviours dropped or changed?** Disabled links become placeholder links with `aria-disabled="true"` and `role="link"` (was: `href` kept, valueless `aria-disabled`); `.submit` gains its documented meaning as the `type` default; `disable-mouse-outline` has nothing to port; `.close-button` closes through `nfsClose`; `data-closable` belongs to the Triggers spec. No custom CSS ships (Foundation's `.disabled` and `[disabled]` rules cover every state).
30. **Naming?** Class `NfsButton` (`Nfs` plus the Structural class), selector attribute `nfsButton`, entry point `ngx-foundation-sites/button` (building-blocks 1.3).
31. **Testing seams?** Story ids `button--<story>` (13 stories); story play functions for rendering, names, Tab, submit behaviour, and axe; browser-level tests (stack-neutral) for the host binding table, `type` sources, echoing, RouterLink, and dev-mode warnings; node-level Vitest for the SSR smoke (including no `jsaction` from the directive); Playwright e2e for real Tab order across engines, implicit submission with real keys, first paint without JavaScript, hydration counters, pre-hydration clicks, a dehydrated-block link navigation regression test, and `hydrate never`. No pure logic worth a node-level unit test.
32. **Material comparison?** Borrowed: directive on native elements, one class for both hosts, `disabledInteractive`. Not borrowed: the component template (ripple, label, focus indicator), appearance and color inputs, `MAT_BUTTON_CONFIG`, the anchor click blocker, `focus(origin)`, the harness (building-blocks 1.12 asserts the DOM).
33. **Platform features beyond the target?** Invoker Commands (`command`/`commandfor`, Baseline newly available December 2025, out of target): explicit `type="button"` keeps them working inside a form, since HTML's button activation behaviour returns early for an Auto-state button with a form owner (HTML `form-elements`, button activation behaviour). Nothing else applies.
34. **Target size?** Checked, no change: Foundation's `.tiny` and `.tiny.arrow-only` buttons measure about 27 to 28 CSS pixels tall with default settings (0.6rem font, `0.85em 1em` padding, 1px borders), above WCAG 2.2 2.5.8's 24 pixels; a small `.close-button` relies on the spacing exception.
35. **Does the spec reuse Foundation's SCSS without re-implementing it (coordinator's restatement of the user's standing rule)?** Yes. The consumer includes `foundation-button`, `foundation-button-group`, and `foundation-close-button` and configures them through the `$button-*` variables; every class in play is one Foundation's partials already style; the directive maps its inputs onto Foundation's `[disabled]` and `.disabled` rules; no library CSS is proposed (D15, and the spec's "Sass and custom CSS" subsection records "none" with the one rejected candidate). The directive has no appearance inputs (decision 6), so the Variant classes are applied as Foundation's own classes rather than through an input mapping; this still reuses `_button.scss` unchanged.
36. **Research gaps met on the way.** `research/angular-material-reference.md` has no Button section (sections 1 to 12 cover the plugin counterparts only), so the Material facts come straight from NGC `src/material/button/**`. Audit 0002 findings that name Button: M2 (the Sass packaging ticket's claim on every spec's Sass note; the spec's Sass note lists the mixins and settings only and leaves packaging to that ticket) and L4 (the `hydrate never` wording, which this spec states as "native elements keep working").

### WCAG 2.2 AA revision, 2026-09-26

Revision for the user's rule that every directive and component complies with WCAG 2.2 AA, with a criteria subsection per spec ([map](../map.md), Standing preferences; ADR 0022). The spec gains `### WCAG 2.2 AA` under Implementation Decisions (after ARIA and keyboard), user stories 40 to 42, design decisions D15 (revised), D16, and D17, and the test-layer wording of the [Decide the browser testing stack: Playwright component tests, Vitest Browser, or both](41-browser-testing-stack-decision.md) answer. Ratios come from a Sass probe compiling Foundation 6.9.0's settings with Dart Sass 1.93.2 and Foundation's own `color-luminance()` and `color-pick-contrast()`, unrounded. Decisions 34 and 35 are superseded where they say "no change" and "no library CSS".

37. **2.5.8 Target Size: does `.tiny` pass?** Height yes at a 16 px root: `.tiny` 27.92 px (0.6rem x (1 + 2 x 0.85) + 2 px border), `.small` 34.4, default 40.88, `.large` 56; `.tiny.arrow-only` 27.92 by 28.88 px. Width no in general: `.tiny` is 21.2 px plus its label, so a single narrow glyph (`I`, about 2.7 px) gives about 23.9 px, and a root font size under about 13.6 px takes every `.tiny` button under 24 px tall. Foundation has no minimum-size setting. Rule required: the `nfs-button` Library mixin emits `.button { min-width: 24px; min-height: 24px; }` (border box, since Foundation sets `box-sizing: border-box`), which changes nothing at the default sizes. Source: FS `scss/components/_button.scss:97-124, 332-341`, `scss/settings/_settings.scss:300, 310-315`, `scss/_global.scss:149-157`; building-blocks 1.10 (a `max(24px, <setting>)` floor where settings can fail).
38. **`.close-button` target size?** Not a `.button`, so the floor does not reach it; it passes through the spacing exception in its absolute corner position, and the consumer adds `min-width: 24px` where a layout breaks it, the rule the [Spec: Toggler](17-spec-toggler.md) already records. Its 2em and 1.5em glyph is large text, so `$closebutton-color` at 3.42:1 on white meets 3:1 (as the [Prototype: Reveal on native `<dialog>` under Foundation Sass](42-prototype-reveal-dialog.md) measured).
39. **1.4.3 Contrast: which defaults fail?** Pass: `.button` `#fefefe` on `#1779ba` 4.587:1 (hover 5.899), `.primary` 4.587, `.secondary` 4.504, solid `.success` 10.912 (hover 7.879) and `.warning` 10.659 (hover 6.845) with the black label. Fail: solid, hollow, and clear `.alert` 4.498:1; hollow and clear `.success` 1.799:1 and `.warning` 1.842:1. No button label is large text, so 4.5:1 applies everywhere; disabled buttons are exempt. Source: the probe; FS `_button.scss:183-279, 369-382` (palette fills use `color-pick-contrast()` for the label and `$button-background-hover-lightness` for hover).
40. **Required setting for 1.4.3.** `$button-palette: map-merge($foundation-palette, ('alert': #bf3f2c, 'success': #177a3d, 'warning': #8a5a00));`: 5.252, 5.275, and 5.877:1 on `$body-background`, each with the `$button-color` label (Foundation's pick flips to white) and hover 7.316, 7.211, 8.040:1. ### Proposed glossary terms

**Variant class**:
A Foundation CSS class that selects a static look for a Structural class (`.small`, `.alert`, `.hollow`, `.expanded`, `.dropdown` on `.button`), as distinct from a State class, which expresses runtime state.
_Avoid_: modifier, appearance class, style class

**CSS-only component**:
A Foundation component that ships Sass and classes but no Plugin, such as Button, Button Group, Close Button, or Callout.
_Avoid_: static component, plain component, pure-CSS widget

Amendment to the existing term, because `.button` is not part of a Plugin's markup:

**Structural class**:
A Foundation CSS class that names an element of a Plugin's or a CSS-only component's markup (`.accordion-item`, `.dropdown-pane`, `.orbit-slide`, `.button`).
_Avoid_: layout class, block class, container class

### Proposed ADRs

- [Variant classes stay consumer-written classes](../adr/0010-button-variant-classes-stay-classes.md): hard to reverse (public API shape every spec copies), surprising for Material users, and a real trade-off against typed inputs.
- [Button declares no event listeners](../adr/0011-button-listener-free-disabled-contract.md): a deliberate deviation from Material's listener-based anchor disabling, justified by Angular's dispatcher cancelling anchor clicks inside dehydrated blocks; recorded so nobody adds a click blocker back.

### Proposed building-blocks changes

1. Table A, Button row: inputs become `disabled`, `disabledInteractive`, `type` (Variant classes are consumer-written, per the proposed ADR); the level cell becomes "Platform: native `<button>` and `<a>`; the directive adds `.button`, defaults `type`, and owns the disabled contract (native `disabled`; `disabledInteractive` renders `aria-disabled`, `.disabled`, `type="button"`; disabled links are placeholder links with `role="link"` and `aria-disabled`)"; primitives become "Host bindings, `HostAttributeToken('class')` and `('role')`; no listeners". Reason: decisions 6, 13 to 16; "prevented navigation" is not achievable without a listener, and a listener breaks dehydrated links.
2. Table B, Button row: replace "`type="button"` is a static host attribute" with "`type` is a host binding from the `type` input (a static host attribute would also land on `<a>`)"; rendering-mode cell adds "no listeners, so no `jsaction` from the directive; plain links keep native navigation inside dehydrated blocks"; Material cell becomes "`disabledInteractive` name and behaviour borrowed; appearance inputs, config token, and anchor click blocker not borrowed". Reason: decisions 10, 13, 32.
3. 1.10 Disabled bullet: "Composite items (Aria-hosted and disclosure menus): `aria-disabled` and still focusable by default (Aria `softDisabled: true`). Standalone native controls (Button): native `disabled` by default, `aria-disabled` on opt-in." Reason: the APG keyboard practice's convention (decision 12); the current wording reads as a rule for every control.
