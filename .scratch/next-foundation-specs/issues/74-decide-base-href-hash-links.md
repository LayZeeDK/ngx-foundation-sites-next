# 74. Decide: `#`-only links that `<base href>` resolves to another document

Type: grilling
Status: resolved
Blocked by: none
Labels: wayfinder:grilling
Map: ../map.md

## Question

In an Angular application with `<base href="/">`, a bare `href="#section"` on any route other than the root resolves to `/#section`, a different document, so the browser treats it as a cross-document navigation (confirmed by the [Prototype: Smooth Scroll under Router scroll restoration and replay](62-prototype-smooth-scroll-router-restoration.md)). The [Spec: Smooth Scroll](29-spec-smooth-scroll.md) treats a `#`-only `href` as in-page after hydration (Foundation's `a[href^="#"]`), with a development warning, and left it OPEN FOR HUMAN in the trap quadrant; the [Spec: Magellan](30-spec-magellan.md) inherits it. The alternative is to handle only links the browser itself treats as same-document (the resolved URL equals the document URL apart from the fragment), leaving bare `#` links to the browser, and to document the base-href-safe `href` recipe.

Decide it with the panel the map's "Open-decision pass" note prescribes: an evidence dossier, four panelists (Opus and Fable, two adversarial), and a judge. The decision must say exactly what the Smooth Scroll and Magellan specs, ADR 0017 (by a dated pointer or a new ADR), building-blocks, and the README open list change to.

## How to work it

The orchestrator runs the panel. The evidence dossier goes to `research/decision-base-href-hash-links.md`: the HTML standard's URL resolution against `<base>` and the "navigate to a fragment" rule; Angular's guidance on `<base href>`, `RouterLink` with `fragment`, `anchorScrolling`, and `withInMemoryScrolling`; how Angular apps in practice write in-page links (angular.dev's own markup, Angular Material docs, community guidance), and how often a bare `#id` appears in Angular templates; what happens before hydration and with JavaScript disabled for each option (a pre-hydration click is a native navigation either way); Foundation 6.9's Smooth Scroll and Magellan selectors; the prototype's measured behaviour; and the accessibility and progressive-enhancement consequences (focus, history entries, reloads). The judge writes the `## Answer` here.

## Answer

Judge's ruling, 2026-09-27, over the dossier (`research/decision-base-href-hash-links.md`, cited as "D n.n", its experiment rows as "EXP H1" and so on) and four panel arguments: the a11y lens (Opus 5.5), the api lens (Sonnet 5, standing in for Fable 5.1 after Fable credit ran out), the vsdefault lens (Opus 5.5, adversarial against the current default), and the vsalt lens (Sonnet 5, standing in for Fable 5.1, adversarial against the alternatives). The judge ran on Opus 5.5. Facts the ruling rests on were re-read by the judge at their source or in the raw experiment logs; those are marked "verified". Evidence capture: the experiment logs these marks cite are kept at [prototypes/base-href-hash-links/](../prototypes/base-href-hash-links/README.md); the full workspaces stayed under `D:/tmp/`.

### Decision

Option B. `NfsSmoothScroll`, and `NfsMagellan` through it, treats a link as in-page exactly when a click on it would be a same-document fragment navigation for the browser (resolved URL equal to the document URL with fragments excluded, fragment non-null), so a `#`-only `href` that `<base href>` resolves to another document is left to the browser, named by a development-mode warning at first render and at click time; the documented current-path `href` in both specs is replaced by one that follows `Location.onUrlChange`, because the read-once version goes stale under component reuse.

### Why

The deciding evidence, in the order it decides:

1. The current default changes the outcome of a bare link in one state only. Verified in `D:/tmp/nfs-decision-base-href/app/annotations.log`: rules A and B give the same result in all three engines before hydration (EXP P1, P2: the document unloads to `/#s2`, `/#s4`), without JavaScript (J1), in `hydrate never` (H9), for a container host inside a dehydrated block with the app hydrated (H7, `reloaded: true` under A too), and on Ctrl, Meta, and middle clicks (M1, M2: the new page opens at `/#s2`). They differ only for an unmodified click after hydration (H1, H2: A scrolls in place, B reloads the application at `/`) and for a link host inside a dehydrated block (H8: A scrolls after the block hydrates, B does nothing). User story 17's promise, that copied Foundation markup "does not send users to the home page from a deep route" (`specs/smooth-scroll.md:50`), holds under A for one gesture in one rendering state.
2. The links A adds are exactly the links for which the effort's accepted documents are false, and B carries no such contradiction. User stories 27 (a link clicked before hydration jumps natively), 29 (a link inside a dehydrated block scrolls to its target), and 30 (links in `hydrate never` keep working) (verified, `specs/smooth-scroll.md:60`, `:62`, `:63`) are false for a bare link under A (P1, H7, H9); so is building-blocks 1.11 decision 7's "SmoothScroll ... keep working" in `hydrate never` (verified, `building-blocks.md:156`), and ADR 0008's reason for its contract, "server HTML is the consumer's markup plus host bindings, which keeps crawlers, no-JS users, and dehydrated blocks correct" (verified, `adr/0008-rendering-modes-contract.md:11`). Under B every link the directive calls in-page works natively in each of those states: EXP J1 `c-safe`, P3, H3, H5, and the vsdefault lens's build without `<base>` (verified, `D:/tmp/nfs-panel-74-vsdefault/app/summary-e.log`: every bare link in every row lands on the current page). The map's triage rule rates confidence NOT HIGH for a default that contradicts the effort's own research or ADRs (`map.md`, Orchestration rules, "Triage of human-only items"); A met that condition by construction.
3. The two directions of a later change are not symmetric. Narrowing A to B later turns links that scroll in place into reloads of the base route, the reason the [Spec: Smooth Scroll](29-spec-smooth-scroll.md) triage rated the item HIGH impact; widening B to A later turns reloads into in-page jumps and breaks no consumer who wrote a link on purpose (the one exception, a shared header's bare `href="#pricing"` meant for the home page whose id also exists on the current page, is a link A would already hijack). The library is unreleased (root `package.json` `"version": "0.0.0"`), so this is about which rule its own first release freezes (api lens).
4. The platform and assistive technology already use B's test. HTML takes the fragment path only when the URL "equals navigable's active session history entry's URL with exclude fragments set to true" and the fragment is non-null (D 2.1 fact 3). WebKit's `AccessibilityNodeObject::internalLinkElement()` returns an in-page target only when `equalIgnoringFragmentIdentifier(document->url(), linkURL)` with `linkURL = anchor->href()` (verified with a read-only `gh api` read of `Source/WebCore/accessibility/AccessibilityNodeObject.cpp:1556-1576` on `main`); the a11y lens read the same rule in Chromium's `AXNodeObject::InPageLinkTarget()` and in NVDA's `isSamePageURL`, and the vsdefault lens read NVDA's independently (not re-read by the judge). Under A, after hydration, a bare link stays on the page while each of these layers describes it as a link to another page, and its context-menu actions (open in new tab, copy link) use the base URL (EXP I1, AX). Under B the handled set and the announced set are the same.
5. Angular's own teams fix the `href`, never the click. angular.dev rewrites bare anchors "because relative hrefs are relative to the base URL, which is '/'" (verified, `adev/shared-docs/components/viewers/docs-viewer/docs-viewer.component.ts:114`), and the Material docs site does it before insertion because "these fragment links would redirect to "/#my-section"" (verified, `docs/src/app/shared/doc-viewer/doc-viewer.ts:158`). Under B the library's documented markup is the same kind of fix, and it works in every row of point 1 (EXP J1 `c-safe`, P3, H3).
6. Under B a broken bare link fails on the first click in development, and Magellan's existing "no in-page links" warning fires (`specs/magellan.md:213`); under A the only signal is a console warning from a check that runs once at first render (`specs/smooth-scroll.md:147`), so links a `@for` adds later are handled and never warned about (vsdefault lens).

How each panelist's strongest argument was weighed:

- a11y lens (Opus): the state table in which a same-document `href` works in every row and a bare one in one row under A only, the accessibility layers' same-page rule, and the measured staleness of the spec's read-once recipe (verified, `D:/tmp/nfs-panel-74-a11y/results-check.log`: every read-once link reloads after a `routerLink` to a new parameter or query, in three engines; the re-read link stays same-document). Adopted. Its recipe, re-read on `NavigationEnd`, is replaced by the vsdefault lens's `Location.onUrlChange` version with the same measured outcome, because it needs only `Location`, which the recipe already injects, no Router and no RxJS, and it also follows `popstate` (verified, NG `packages/common/src/location/location.ts:171-193`, `:232-248`: `go()` and `replaceState()` notify the listeners, and the listener subscribes to `popstate`; the Router writes the URL through `location.go`/`location.replaceState`, `packages/router/src/statemanager/state_manager.ts:257`, `:263`).
- api lens (Sonnet, replacing Fable): the asymmetric reversibility and the observation that the spec's only Router example already uses the recipe, so B changes no documented Router code. Adopted (points 3 and 5). Two of its change notes are overridden: building-blocks Table A's "container of `a[href^="#"]`" would now describe links the directive does not handle, so it changes; and the warning text cannot stay as written, because "leaves the page before hydration, in `hydrate never`, and on middle-click" implies the link works after hydration.
- vsdefault lens (Opus): the contradictions with user stories 27, 29, 30, building-blocks decision 7, and ADR 0008 (point 2), the measurement without `<base>` together with its caveat that the 22.2 dev server drops `deployUrl` (verified, `@angular/build/src/builders/dev-server/vite/index.js:68-69`, "Deploy url is not used in the dev-server."), the click-time warning, and the `onUrlChange` recipe (verified in `D:/tmp/nfs-panel-74-vsdefault/app/src/app/pages/docs.ts`). Adopted. Its B plus an opt-in browser-side rewrite is recorded as the reopen path, not adopted now.
- vsalt lens (Sonnet, replacing Fable): its strongest point is that the unmodified click after hydration is the most common click on a hydrated page, and there A is strictly better: in place, focus on the target, the next Tab inside it, no lost state, where B reloads the application with focus on the body of another page (EXP H1, WCAG 2.4.3). Weighed, not dismissed: A's benefit reaches only links a consumer leaves unfixed, B makes those links fail visibly in the first development click and every audit, while A hides them and still fails the same users before hydration, without JavaScript, from a context menu, and in dehydrated containers. Its H8 point (a dead click under B for a link host in a dehydrated block) is real and is accepted with guards: it is the existing hazard of any link host whose `href` leaves the page (ADR 0017), Foundation's primary placement, the container host, is not affected, and the click-time warning names it exactly there, where the page does not unload. Its Foundation-parity point is answered by Foundation's own meaning: its pages have no `<base href>`, where `a[href^="#"]` and B select the same links, and Foundation calls the plugin "internal links smooth scrolling" (FS `docs/pages/smooth-scroll.md:3`); the effort already accepts docs-markup deltas where the platform meaning of `href="#..."` conflicts (ADR 0023, verified `adr/0023-tabs-anchor-tab-hosts.md:16`). Its reading that NVDA's "not same page" for an A-handled link errs on the safe side is accepted as not a conformance failure; point 4 rests on predictability, not on phrasing. Its rejections of options C, D, E, F, and G stand and are adopted.

### Dissent

- vsalt lens: A is the only option under which Foundation's documented markup works on a deep route without the consumer rewriting anything, it is better on the most common click, and B adds a dead click inside dehydrated blocks and a full reload with lost state for every link a consumer does not fix. Overridden by points 1 to 3 and 6. Reopens on a measured corpus showing that bare `#id` links in Router applications are mostly clicked after hydration and mostly left unfixed after a visible failure, or on a screen-reader run showing a harm specific to B's reload that A avoids.
- a11y lens and vsdefault lens, their own flip fact: if most bare `#id` links inside in-page navigation come from run-time HTML (Markdown or CMS content) that the developer neither writes nor tests, B's visible-failure advantage does not reach them. The answer then is a browser-side rewrite of bare `href`s inside the host as an opt-in layered on B (option C), which also fixes modified clicks, copy link, and the announced destination, not a return to A. The corpus count (D 4 unknown 1) is the fact that reopens this.
- vsdefault lens: plain B rather than B plus the opt-in rewrite as the final shape (its MEDIUM). Not adopted now: the rewrite's interplay with consumer `[href]` bindings, `@for` updates, and deferred blocks is unmeasured (D 4 unknown 8), and it can be added later without breaking anyone.
- A future fact that changes the docs but not the rule: Angular making its Navigation API integration (`withExperimentalPlatformNavigation()`) the default inside the Browser target would turn a bare link that B leaves to the browser into a Router navigation to the base route instead of a reload (D 4 unknown 5). The same-document rule and the recipe stand either way.

### Triage

- Impact: HIGH, unchanged. The [Spec: Magellan](30-spec-magellan.md) inherits the in-page rule through `hostDirectives`, and the rule fixes what consumer markup must look like on routed pages.
- Confidence: HIGH after the panel. The rule is HTML's own fragment-navigation condition and the same-page test of the engines' accessibility layers; the state table is measured in three engines by the dossier and re-checked by two panelists; the decision removes the contradiction with the effort's own user stories, building-blocks decision 7, and ADR 0008 that kept the earlier default NOT HIGH under the map's rule; and the one unmeasured prediction, that a failure visible on the first click gets fixed more often than a console warning, does not carry the decision, because the correction it would call for (widening, or the opt-in rewrite) breaks nobody.
- Outcome: DECIDED. The item leaves the README's trap-quadrant list.
- Residual risk the decision accepts, and how the specs guard it: (a) a bare link a consumer does not fix reloads the application at the base route after hydration, where the earlier default scrolled in place, most likely in run-time HTML; guarded by the development warning at first render and at click time, the Router example's recipe, the fixture e2e that asserts both the bare link's navigation and the recipe link's in-page handling after parameter and query changes, and the non-breaking opt-in path above. (b) A link host with a non-in-page `href` inside a dehydrated block gives a dead click; guarded by the click-time warning, the spec text in Rendering modes, and a browser-level case asserting "not handled, warned once". (c) No screen reader was run (D 4 unknown 3); the decision does not rest on how a screen reader phrases a link, only on the rule each layer implements, so no new assistive-technology check is added.
