# 128. Re-run: Button spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81
Labels: wayfinder:grilling
Map: ../map.md

## Question

What does the [Spec: Button](37-spec-button.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/button.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

Also: Button Group and Close Button move to their own specs; B4: Foundation's Forms page shows `input[type=submit].button` and a `label.button` file upload, so D11's "never shown" is wrong (the label host waits on a 2.4.7 focus fix); D10 and the Out of Scope list are rewritten.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Button](37-spec-button.md) and the answer here. Model: Opus 5.5.

### Decisions

1. **Which Variant inputs, named how?** Six, by the building-blocks 1.4 name order: `size`, `color`, and `fill` (rule 3, one enum per set of mutually exclusive names), and `expanded`, `dropdown`, and `arrowOnly` (rule 4, booleans named after their classes; the responsive `-expanded` forms fold into `expanded` by rule 5). The input the Accordion re-run's example writes, `<button nfsButton size="small">`, is valid as written: the input is `size`, typed `NfsButtonSize`, and `small` is one of Foundation's default names. (Spec D3.)
2. **`size` type.** `NfsOverridableStringUnion<'tiny' | 'small' | 'large', NfsButtonSizesOverrides> | 'default'`. `'default'` sets no class (building-blocks 1.4) and sits outside the registry: FS `_button.scss:337` removes the `default` key from the class loop, so `--nfs-button-sizes` never lists it, and a registry default the property lacks would be written as removed (`default: false`) by the generator.
3. **`color` type.** `NfsOverridableStringUnion<NfsFoundationPaletteColor, NfsButtonPaletteOverrides>`, chained because `$button-palette` defaults to `$foundation-palette` (FS `_button.scss:69`). The required WCAG palette changes values, not names, so it needs no declaration.
4. **`fill`.** Closed, `'solid' | 'hollow' | 'clear'`. Each value sets its class whatever `$button-fill` is; the class equal to `$button-fill` has no rule and the bare `.button` already has that fill (FS `_button.scss:369-381`; the probe found `.button.solid` rules only under `$button-fill: hollow` and `.button.hollow` rules only under `solid`).
5. **`expanded`.** `true` (or the bare attribute) or `NfsClassBreakpointQuery<'up' | 'only' | 'down'>`, through a transform that maps `NfsVariantBoolean` with `nfsVariantBoolean` and passes a query through. Mapping: `'<bp>'` and `'<bp> up'` set `.<bp>-expanded`, `'<bp> only'` sets `.<bp>-only-expanded`, `'<bp> down'` sets `.<bp>-down-expanded`; for the Zero breakpoint, where Foundation generates neither `-expanded` nor `-down-expanded` (FS `_button.scss:345-365`), `'<zero>'` and `'<zero> up'` set `.expanded` and `'<zero> down'` sets `.<zero>-only-expanded`. The Zero breakpoint is read from `nfsBreakpointsToken` (the key whose value is 0), not hard-coded as `small`, because a consumer can rename it (spec D20).
6. **`dropdown` and `arrowOnly`.** Booleans through `nfsVariantBoolean`. `arrowOnly` sets only `.arrow-only`, which draws nothing without `.dropdown` (FS `_button.scss:415-419`); a development warning reports `arrowOnly` without `dropdown`, and either on an `<input>` host, which draws no `::after` (D21). Rejected: `arrowOnly` also setting `.dropdown` (one input, two classes).
7. **Defaults.** Every Variant input unset sets no class; no Defaults token (D4 stands, ADR 0040).
8. **How the classes are bound.** One `[class]` host binding from a `computed` list, at most one class per input, nothing for a value that is not one class token. `.disabled` becomes a plain boolean binding (D14): the first version's `true`-or-`undefined` form existed only to keep a consumer-written `.disabled`, which the class rule removes.
9. **Copied Foundation classes (building-blocks 1.4, initial-state rule).** A copied `class="disabled"` is stripped by the boolean binding; a copied Variant class survives, because a `[class]` list sets only its own classes; a copied `submit` does nothing. All three are reported once in development builds, through `HostAttributeToken('class')` read only there, naming the input to bind (D22). The check knows the closed names, the `-expanded` pattern, and Foundation's default size and palette names; a redundant `button` merges with the static host class and is not reported.
10. **The `.submit` marker.** Dropped (D5): it is a consumer-written Foundation class, and building-blocks 1.4 now forbids reading a static class to seed state. A submit button says `type="submit"`. This removes the first version's `HostAttributeToken('class')` injection from production code.
11. **B4, `<input>` hosts.** Join: `input[type=submit][nfsButton]`, `input[type=button][nfsButton]`, `input[type=reset][nfsButton]` (FS `docs/pages/forms.md:298-304`, the Input Group; `kitchen-sink.md:579`). Same contract as `<button>`: native `disabled`, `disabledInteractive` with `type="button"` while disabled, `aria-disabled`, `.disabled`. The static `type` in the selector keeps text fields out. The name comes from `value`. A static `size` attribute stays in the DOM, where HTML ignores it for these types (spec Notes).
12. **B4, `<label>` hosts.** Not a host until a 2.4.7 fix exists: the Forms page's file upload focuses a file input that `.show-for-sr` clips to 1 px (FS `scss/util/_mixins.scss:212-230`), so the label that looks like a button shows no focus indicator. The [Spec: Forms](98-spec-forms.md), written in the same wave, replaces the recipe with the native file input (its D12) and leaves label hosts to this spec; the label joins the selector only together with a focus fix, and both specs name a `:has()` rule as that route once `:has()` is in the Browser target.
13. **Button Group and Close Button.** Moved out (D10). `NfsButton` declares no group token; the [Spec: Button Group](82-spec-button-group.md), which waits on this ticket, decides whether its buttons read one and proposes the amendment if so. `nfsButton` never shares an element with the Close Button's directive, since both bind `type` and the two class contracts collide.
14. **Solid arrow under `$button-fill: hollow` (new, D18).** Measured: FS `_button.scss:393-397` recolours every `.dropdown` arrow to `$button-background` under `$button-fill: hollow`, `.solid` included, so `fill="solid" dropdown` draws its arrow in its own fill colour (1:1) and an arrow-only button fails 1.4.11. `nfs-button` emits `.button.dropdown.solid::after { border-top-color: $white; }` only under that setting, restoring Foundation's own solid arrow. The compile-time arrow check computes arrow colours under the consumer's `$button-fill` (D16). This makes ADR 0040's statement that each fill renders its own fill whatever `$button-fill` is hold for dropdown buttons too.
15. **Variant properties (D19).** `--nfs-button-palette`, `--nfs-button-sizes`, and `--nfs-button-responsive-expanded`, space-separated on `:root`; the last lists `$breakpoint-classes` while `$button-responsive-expanded` is true and is empty otherwise. Measured: Sass interpolates `map-keys()` with commas (`primary, secondary, ...`), so the mixin joins with `space`; `#{''}` writes an empty property (`--x: ;`); and an empty property reads as `""` through `getPropertyValue`, exactly like a missing one, in all three engines. So `strictVariantProperties` reports a missing `nfs-button` include only when `--nfs-button-palette` and `--nfs-button-sizes` both read empty, never from the gated property.
16. **Variant check.** `NfsButton` reports its bound values to the Runtime checks after the first render in development builds, and in production only under `provideNfsProductionRuntimeChecks`; a responsive `expanded` value whose Breakpoint the gated property does not list is reported naming `$button-responsive-expanded`. The directive's one `afterRenderEffect` read phase exists only when a checker exists, and holds the development warnings too.
17. **Stories.** Eleven ids; `button--button-group` and `button--split-button` go to the Button Group spec. Stories set inputs, use only Foundation's default names (so the library's Storybook program needs no Variant declaration file), and leave out the responsive `expanded` forms, whose classes the preview settings do not generate; layer 2 covers their mapping.
18. **Tests.** Layer 2 adds a data-driven Variant mapping (with a renamed Zero breakpoint), `<input>` hosts, the copied-class and arrow warnings, and the Variant check; the SSR smoke adds an `<input>` host and a fully set Variant button and asserts no Runtime check runs on the server; the Sass compile test adds the Variant properties and `$button-fill: hollow`.
19. **Examples.** No consumer-written Foundation class remains. `.show-for-sr` spans take the Visibility Classes directive, written `nfsShowForSr` here until the [Spec: Visibility Classes](104-spec-visibility-classes.md) names it; the icon-font class `fi-trash` became an inline SVG and the `.help-text` paragraphs plain paragraphs, so the examples depend on no unwritten spec beyond that one name. A generated Variant declaration file for a `purple` palette entry is shown without its path.
20. **Solution and user stories.** Under the class rule the class alone earns the directive (the triage's section 5 note), and the Solution says so; the type default and disabled contract stay as the other reasons. User stories 1 to 4, 6, 12 to 23, 25, 26, and 30 to 42 keep their numbers and subjects, so outside references (the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) cites user story 8) still hold; 5, 7 to 11, 24, and 27 to 29 are rewritten and 43 to 46 added.
21. **Aria composite items.** Unchanged in substance, restated: `nfsButton` on an Aria toolbar widget, accordion trigger, or tab would fight their `disabled`, `aria-disabled`, and `role` bindings. No spec in the destination needs `.button` there; one that does decides the composition. (The first version's "the consumer writes `.button` directly inside an Aria toolbar" is no longer available under the class rule.)
