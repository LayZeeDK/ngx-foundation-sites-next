## Answer

Spec: [specs/orbit.md](../specs/orbit.md). Resolved 2026-09-26 by self-grilling (AFK), both sides played against the sources below, with the [Prototype: Orbit on CSS scroll snap](46-prototype-orbit-scroll-snap.md) as the binding input (verdict, custom CSS list, `div` slides, container `tabindex="-1"`, the three gaps, the `scrollIntoView` finding, the rewind, the scrollbar question, the touch harness limit) and the orchestrator's note on it (item 1 stays open; items 2 and 3 are settled here).

Gist: eight attribute directives on Foundation's Orbit markup. `NfsOrbit` (`div[nfsOrbit]`, hosts Aria `Tabs`) takes `autoPlay`, `timerDelay`, `infiniteWrap`, has a `selected` model keyed by slide `value` (`selectedChange` replaces `slidechange`), a read-only `playing` signal, and `next()`, `previous()`, `play()`, `stop()`, and provides `nfsOrbitToken`. `NfsOrbitContainer` (`div[nfsOrbitContainer]`) is the scroll-snap row, the live region, and the IntersectionObserver root; `NfsOrbitSlide` (`div[nfsOrbitSlide]`, hosts `TabPanel`); `NfsOrbitBullets` (`[nfsOrbitBullets]` on `nav.orbit-bullets`, hosts `TabList`); `NfsOrbitBullet` (`button[nfsOrbitBullet]`, hosts `Tab`); `NfsOrbitPrevious`, `NfsOrbitNext`; `NfsOrbitRotation` (the APG rotation control). Implementation level: native platform (scroll snap, `scrollBy` on the container, IntersectionObserver, `inert`, `prefers-reduced-motion`) with Aria Tabs for the bullets; no Motion UI and no `@if` fallback. `nfsOrbitDefaultsToken` covers `autoPlay`, `timerDelay`, `infiniteWrap`. The `nfs-orbit` Library mixin carries the prototype's eight layout rules plus a 24 px bullet floor, an arrow background, an inward focus ring on the slide, a hidden scrollbar, and compile-time contrast checks that Foundation's default bullet and caption colours fail.

### Decision log

Sources: FS = the Foundation 6.9.0 clone (`js/foundation.orbit.js`, `scss/components/_orbit.scss`, `docs/pages/orbit.md`); NGC = the components 22.2.x clone (`src/aria/tabs/*.ts`, `src/aria/private/tabs/tabs.ts`); APG = the aria-practices clone (`content/patterns/carousel/`, `examples/carousel-2-tablist.html`, `examples/js/carousel-tablist.js`); AXE = axe-core 4.13.0 `axe.js` in the prototype workspace; P46 = the scroll-snap prototype ticket and `prototypes/orbit-scroll-snap/`; P43 = the Aria Accordion and Tabs prototype; P52, P47 = the `animate.enter` prototypes; BS = [Spec: Breakpoint service (shared utility)](53-spec-breakpoint-service.md); R:x = research files by short name as `building-blocks.md` cites them; BB = `building-blocks.md`; W = WCAG 2.2.

Round 1: contract and level.

1. Q: Which Options, events, and methods exist? A: The 18 keys of `Orbit.defaults` (FS `foundation.orbit.js:424-552`; R:forms-media Orbit), events `slidechange`, `beforeslidechange`, the Timer's `timerstart`/`timerpaused`, methods `geoSync`, `changeSlide`, `_reset`, `_destroy`. There is no `data-orbit-container` or `data-orbit-slide` option and the ticket's `boxOfClass` is `boxOfBullets` (audit 0001 H6).
2. Q: Scroll snap or the `@if` fallback? A: Scroll snap; P46 passed every case in three engines from server HTML, axe clean. The fallback is retired from BB 1.6 rule 2, rule 7, Table B, and ADR 0003 (proposed changes below).
3. Q: Motion UI classes, `animate.enter`, or View Transitions? A: None: the browser's scrolling is the movement, `scroll-behavior: smooth` gated by reduced motion. Motion UI transition classes never animate under `animate.enter` (P47); `animate.enter` would replay on server-rendered slides at hydration (P52); View Transitions are out of target (R:platform 17) and there is no non-scrolling change to animate. The four `animIn*`/`animOut*` options are dropped.
4. Q: Directive set and markup? A: `[nfsOrbit]`, `div[nfsOrbitContainer]`, `div[nfsOrbitSlide]`, `[nfsOrbitBullets]`, `button[nfsOrbitBullet]`, `button[nfsOrbitPrevious]`, `button[nfsOrbitNext]`, `button[nfsOrbitRotation]` (ADR 0001; BB Table A). Markup delta: `ul`/`li` become `div` because `tabpanel` is not allowed on `li` and the APG's `li[role=group]` alternative is not allowed either (P46 axe `aria-allowed-role`, `list`); the rotation control is added first; arrow glyphs get `aria-hidden` spans (Foundation's glyph text would join the accessible name).
5. Q: Basic, tabbed, or grouped carousel? A: Tabbed (BB Table A; APG recommends it over grouped). Bullets are required, so `bullets` is dropped; a basic style would need slides with a second role set, which static `hostDirectives` cannot switch (NGC `tab-panel.ts:46`: `role="tabpanel"` always; without a tab every panel is visible, `tabs.ts:98`).
6. Q: Material counterpart? A: None in Material, CDK, cdk-experimental, or Aria (R:material 10).

Round 2: options.

7. Q: `navButtons`, `swipe`, `accessible`, `useMUI`, class-name options? A: Dropped: arrows exist when written; native scrolling is the swipe (a consumer wanting none writes `overflow-x: hidden`, which keeps `scrollBy` working); `accessible` and `useMUI` per BB 1.4; `containerClass`, `slideClass`, `boxOfBullets`, `nextClass`, `prevClass` are class-name options (BB 1.4).
8. Q: `pauseOnHover`? A: Dropped, always on: the APG's "Features needed to provide sufficient rotation control" include stopping while hovered (R:apg Orbit), so an off switch would be a switch to fail the pattern. BB Table B's defaults token list loses it.
9. Q: `autoPlay`, `timerDelay`, `infiniteWrap`? A: `input()` with `booleanAttribute`/`numberAttribute` and Foundation's defaults, seeded by `nfsOrbitDefaultsToken` (BB 1.4). Rotation needs more than one slide, as in Foundation (FS `:91-93`).
10. Q: `infiniteWrap` and the bullets' arrow keys? A: Independent: APG Tabs wraps arrow keys, and a host-directive wrapper cannot set Aria's `wrap` input from code (P43 case 4), so Aria's default `true` stays; `infiniteWrap` governs the arrows and the rotation. Deviates from P46's `[wrap]="infiniteWrap"`, which bound Aria directly in a template.
11. Q: Rewind or forward wrap (orchestrator: settle)? A: Rewind, settled: FS wraps forward only because slides were absolutely positioned and Motion UI slid the first one in from the right (`changeSlide`, `:309-374`); the APG says nothing about wrap direction; a forward loop needs cloned slides, which duplicate content for assistive technology, find-in-page, and crawlers; the rewind keeps one copy and matches native swiping, which stops at the ends. `infiniteWrap`'s meaning (last to first) is kept; only the path changes. Documented as a behaviour change.

Round 3: state, outputs, methods, DI.

12. Q: Selection model? A: `selected = model<string | undefined>()` keyed by `value` (BB 1.4, 1.9 value-keyed pairing); `undefined` shows the first slide through an internal effective value, so no write happens at init and `selectedChange` never fires then. `slidechange` becomes `selectedChange`; `beforeslidechange` dropped (BB 1.4).
13. Q: Rotation state and methods? A: Read-only `playing`, a `linkedSignal` of `autoPlay` and `reducedMotion` (recomputes when either changes; BS user story 11 and its Orbit example), written by `play()`, `stop()`, and the focus rule; the effective rotation also needs no hover and more than one slide. `timerstart`/`timerpaused` dropped (Timer internals). `next()`/`previous()` replace `changeSlide(isLTR)`; `geoSync()` becomes `play()`. Not a model: Foundation exposes no rotation method and event pair (BB 1.4 rule for `model()`), and `autoPlay` already carries the initial value.
14. Q: How are slides registered? A: Through `nfsOrbitToken` (required inject, BB 1.9), `register()` in `ngOnInit`, sorted by `compareDocumentPosition`, re-sorted by a `MutationObserver` started in `afterNextRender`; not `contentChildren`. Bullets, the bullets directive, the container, and the rotation control register too (the Orbit needs the container for scrolling, the bullets for the tab stop and Aria's model, the rotation control for dev checks).
15. Q: Aria composition? A: Root hosts `Tabs`; bullets host `TabList` (no inputs exposed); bullet hosts `Tab`, slide hosts `TabPanel`, each exposing `value` (required, NG2019 otherwise, P43) and `id` (so a consumer's static id is not overwritten by Aria's host binding). Content projected, no `ngTabContent` (BB 1.11 decision 2; P46).
16. Q: Keeping Aria's `selectedTab` in step? A: The Orbit's `selected` is the source of truth; `NfsOrbitBullets` writes the effective value into Aria's model in `ngAfterContentInit` (after slides register; P43 case 6 proved no NG0100 and a selected tab in server HTML) and subscribes to Aria's model to forward user choices; the Orbit writes Aria's model on later changes; equal values are ignored.
17. Q: Localised strings? A: Consumer markup (`role`, `aria-label`, `aria-roledescription` on root and slides, tablist label, rotation text via `orbit.playing()`), checked in dev mode; APG notes the role descriptions must be localised, and Foundation's docs already have the consumer write `aria-label`.
18. Q: `Directionality`? A: Not injected: `scrollBy(slideRect.left - containerRect.left)` is correct in RTL (P46 RTL case), and Aria injects `Directionality` itself; a subtree `dir` needs CDK `Dir` in the consumer's imports (P46).

Round 4: movement and the observer.

19. Q: `scrollIntoView` or scrolling only the container? A: Only the container, for every move: `scrollIntoView` moved the page by 120 px (P46 finding; R:platform 9 known gap); APG arrows must not move the page.
20. Q: One movement path? A: Every move changes the selection first; one `afterRenderEffect` scrolls the container (rects in `earlyRead`, `scrollBy` in `write`) when the selected slide is not the one in view, which also covers consumer writes to `selected`.
21. Q: Active slide from native scrolling? A: IntersectionObserver rooted on the container, `threshold: 0.5`, with the pending-target guard and passive `wheel`/`touchstart`/`pointerdown`/`keydown` listeners added in code that cancel it (P46 decision 2). `scrollend` is out of target (R:platform 9).
22. Q: A bound non-first `selected` at first paint? A: The server cannot scroll; in the first render callback a container still at `scrollLeft` 0 is aligned instantly by one `scrollLeft` write with an inline `scroll-behavior: auto` override (BB 1.5 allows `Renderer2` for scroll writes); a container the user already scrolled is adopted by the observer. `behavior: 'instant'` is avoided because its support in the Browser target is not documented in BCD (checked `api/Element.json`: no `instant` subfeature). New; see Prototype needed 2.
23. Q: The visible scrollbar (orchestrator: settle)? A: Hide it, settled: `scrollbar-width: none` (Firefox 64+, Chromium 121+) plus `::-webkit-scrollbar { display: none }` (every Chromium and Safari in target) together cover the whole Browser target, contrary to P46's reading of `scrollbar-width` alone; Foundation's Orbit never showed a scrollbar; the bullets are required, so hiding it never removes the only single-pointer alternative to swiping (W 2.5.1, 2.5.7).

Round 5: rotation.

24. Q: Timer placement? A: `setTimeout` scheduled from an `afterRenderEffect` tracking the effective rotation and the selection, inside `NgZone.runOutsideAngular`, restarting the full delay on each change (P46 decision 4; BB 1.11 decision 4; audit 0002 H2). A timer in the zone blocked stability and replay in P46's zone build.
25. Q: Focus stop? A: On `focusin` at the root when the target matches `:focus-visible` and is not the rotation control. APG text says keyboard focus stops rotation until an explicit restart; the APG tabbed example exempts the rotation button (APG `carousel-tablist.js`, `hasUserActivatedPlay`). The `:focus-visible` check refines P46 (which stopped on any `focusin`): Chromium focuses a clicked button and Safari does not, so a mouse click would stop rotation in one engine only; hover covers the pointer. A replayed `focusin` re-checks live focus (BB 1.11 decision 5).
26. Q: Hover pause? A: `pointerover` (target outside the rotation control) and `pointerleave`, added in code in `afterNextRender`, so a stale pre-hydration hover is never replayed into a stuck pause (APG example `handleMouseOver` excludes the rotation button; P46 decision 4). After leaving, the full delay restarts (Foundation resumed the remaining time; delta).
27. Q: Reduced motion? A: `scroll-behavior` stays `auto` by CSS alone; `playing` starts `false` from the live `reducedMotion` signal (BS; APG examples start paused); the label and `aria-live` switch in the first client tick.
28. Q: Live region? A: `aria-live="off"` on the container only while the effective rotation runs, `polite` otherwise, `aria-atomic="false"` (APG; P46).

Round 6: the three gaps, focus, keyboard.

29. Q: Aria's roving tab-stop drift (P46 OPEN 1)? A: Decided by triage (below): accept the drift and document it; no public Aria API moves the active item (NGC private `tabs.ts:227-273`: `setDefaultStateEffect` stops after the first interaction and `onFocusIn` only records interaction); the directive's `tabindex` binding equals Aria's value whenever Aria has an active item, so the directive never fights Aria. Filing upstream stays human-only.
30. Q: Pre-hydration bullet tab stop (P46 gap 2)? A: `NfsOrbitBullet` binds `tabindex`: `0` on the selected bullet while no bullet is Aria's active item (server HTML and the first client pass), Aria's own roving value (`active ? 0 : -1`, from the public `Tab.active`) afterwards. Two attribute bindings on one element are not merged, so the wrapper's value is defined to equal Aria's whenever Aria has one.
31. Q: `inert` on slides native scrolling can reach (P46 gap 3), and is `inert` right at all? A: With JavaScript, yes: the observer selects whatever slide the user lands on, so no visible slide stays `inert` after a scroll settles, and out-of-view slides are hidden, not off-screen (APG). Without JavaScript or in `hydrate never`, no: a visible `inert` slide fails W 1.3.1 and its links do nothing. So `NfsOrbitSlide` overrides Aria's `inert` and applies it only once live; server HTML hides no slide. Proposed ADR.
32. Q: Focus on a slide that becomes `inert`? A: Focus would fall back to `body` (HTML focus fixup), so when the observer changes the selection while focus is inside the old slide, the new slide receives focus with `preventScroll` first. New; Prototype needed 1.
33. Q: Keyboard table? A: APG: Tab order rotation, previous, next, visible slide, bullet tab stop; Enter/Space on buttons without moving focus; Aria's arrow keys, Home, End on bullets; Foundation's container arrow keys survive as native scrolling of the container from the focused slide (the container is no longer focusable, `tabindex="-1"`, P46 Firefox fix).
34. Q: Replay guard? A: `NfsOrbitBullets` re-applies `stopPropagation()` for Aria's keys in a host `keydown`, as `nfsAccordion` does (P43 case 25), so a replayed Home or End inside an accordion panel does not reach the accordion.

Round 7: WCAG 2.2 AA (user rule: requirements, never recommendations).

35. Q: 2.2.2? A: Rotation control first (dev check when missing with `autoPlay`), focus stop, hover pause, reduced-motion start state.
36. Q: 2.5.8 on bullets? A: Foundation's bullets are `1.2rem` (19.2 px) with `0.1rem` margins (FS `_orbit.scss`), centres 22.4 px apart, so the circles of the spacing exception intersect: fail. AXE cannot fail it: `widget-not-inline-matches` and `targetOffsetEvaluate` return incomplete when neighbours are outside the tab order, which roving `tabindex` makes every other bullet (AXE `axe.js:28289-28310`, `25822-25890`); that is why P46's axe run passed. Library rule 10 floors the bullet at `max(24px, $orbit-bullet-diameter)` (Slider D16 approach); e2e measures the boxes. Arrows (1rem padding) and `.button.small` (about 32 px) pass.
37. Q: 1.4.11 and 1.4.1 on bullets? A: `$medium-gray` #cacaca on white is about 1.6:1 (fail); the active `$dark-gray` #8a8a8a 3.4:1, but only 2.1:1 against the inactive bullet, and the state is shown by colour alone. Compile-time `@error` (rule 0a) with Foundation's `color-contrast()` against `$body-background` and between the two states (Slider decision 45 approach; axe has no 1.4.11 rule). Passing example: `$dark-gray` with `$black` (about 5.7:1 between them).
38. Q: 1.4.11 on arrows? A: The white glyph sits on arbitrary images and Foundation shades it only on hover and focus; rule 9 applies `$orbit-control-background-hover` at rest (3.7:1 for white over that band composited on white), checked at compile time (rule 0b).
39. Q: 1.4.3 on captions? A: `rgba($black, 0.5)` behind white text over a white image area is 3.7:1 (fail; P46's `color-contrast` failure was the stretched-slide variant); axe marks text over images incomplete. Compile-time `@error` compositing the band over white and black (rule 0b); `rgba($black, 0.6)` gives 5.2:1.
40. Q: 2.4.7 and 2.4.11? A: Buttons and bullets keep the UA ring (Foundation's `disable-mouse-outline` acts only under what-input's attribute, which the library does not set); the focused slide's ring is clipped by the container, so rule 11 draws it inside (`outline-offset: -0.25rem`); no control is covered by the arrows. Prototype needed 1 checks the pixels.
41. Q: 4.1.2, 1.3.1, 2.1.1, 2.4.3, 2.5.1, 2.5.7? A: Aria roles and states plus consumer names (dev checks); no visible slide hidden from assistive technology (decision 31); bullets reachable by Tab from server HTML (decision 30); rotation control before the slides; bullets required as single-pointer alternatives. 2.3.3 (AAA) is honoured through reduced motion. Each is recorded in the spec's WCAG table.

Round 8: rendering modes and tests.

42. Q: Server output? A: All slides, the first or bound one `.is-active`, none `inert`, Aria roles and `aria-selected` from the model written at content init, the selected bullet `tabindex="0"`, the rotation label and `aria-live` from `playing`; `jsaction` on the arrows, the rotation control, the tablist, and the root (BB Table B; P46 server HTML case, amended by decisions 30 and 31).
43. Q: Replay? A: Arrow, rotation, and bullet clicks replay and act once (P46 replay case); replayed bullet keys act and Aria's `preventDefault()` logs (BB Part 4 item 3, P43 OPEN 2); scrolls and hovers do not replay; a pre-hydration scroll is adopted.
44. Q: Hydrate triggers and boundary? A: One Hydration boundary for the whole carousel (BB 1.11 decision 6); `hydrate on viewport` recommended (BB Table B); `hydrate never` leaves a native scroll-snap gallery with every slide usable (decision 31).
45. Q: Lazy slides? A: `@defer (on viewport)` inside a slide (the viewport observer respects the container's clip) and `loading="lazy"` on later images; no `ngTabContent`, which would empty slides in server HTML (BB 1.11 decision 2).
46. Q: Testing seams? A: The four BB 1.12 layers: story play functions (interaction and axe; settings overridden to pass the compile checks), browser-level tests (state, timer, pending target, focus handoff, live gate, tab stop, dev checks, replay-safe handlers), node-level Vitest (SSR smoke, pure logic, Sass compile test), Playwright e2e (scroll positions, page scroll, timing, reduced motion, tab order, geometry, and the fixture app's no-JS, hydration, replay, zone, `hydrate on viewport`, and `hydrate never` cases).

A: Case 1 passed in three engines, headless and headed: keyboard scrolling from a focused slide never drops focus to `body`, the inward ring shows (`outline-offset: -4px`, `:focus-visible`), and rule 12 hides the scrollbar. 48. Q: Why did the `inert` override lose, and does the cause reach beyond `TabPanel`? A: Source reading, which P65 left open. Every attribute binding keeps its own slot and writes only when its value differs from that slot (`bindingUpdated`). Host directives apply their bindings before the host (adev, "Directive execution order"), so the host's binding wins only in a pass where Aria's value does not change afterwards. NGC `TabPanel` binds `inert` to `!visible()`, and `TabPanelPattern.hidden` is `tab()?.expanded() === false`. In the first server pass the bullets, which follow the slides in the document, have not registered, so `tab()` is undefined and Aria renders no `inert`. In a later server pass it renders `true` on every unselected panel while the wrapper's value is still `null` and unchanged, so only Aria's binding writes. This fits every P65 number: `beforeInert` `false, true, true, true` beside `data-diag-override="null"`; the template binding losing too (template bindings run before host bindings); the isolated repro passing (its inner value never changed after the first pass); and the bullet `tabindex` override winning (Aria's `getItemTabIndex` is a constant `-1` until an active item exists, which happens only in a browser render callback, and equal to the wrapper's afterwards). The rule is general: a wrapper overrides an Aria host binding only when Aria's value never changes after the wrapper's last write, or equals the wrapper's whenever it changes (building-blocks 1.9 change proposed in the re-run ticket). Confidence HIGH from source; not re-measured, and the SSR smoke and prerendered fixture cases assert the outcome.
49. Q: How does the slide get its ARIA contract? A: P65 decision 1, adopted. `NfsOrbitSlide` hosts no Aria directive and binds the contract itself: static `role="tabpanel"`; `[attr.id]` from its own `id` input (the consumer's `id` wins, otherwise `nfs-orbit-slide-` from `_IdGenerator`, the library prefix rule of building-blocks 1.5); `[attr.tabindex]` `0` on the selected slide and `-1` on the others (no roving, because a slide's tab stop follows the selection); `[attr.aria-labelledby]` the paired bullet's id from the Orbit's registry; `[attr.inert]` `true` while live and not selected, the only `inert` binding on the element. Its own required `value` input. The API shape is unchanged; only the member comments change. Rejected: a `Renderer2` correction in a render callback (never runs on the server, and a later Aria change overwrites it); giving `TabPanel` its `value` only once live (a wrapper cannot set Aria's input from code, P43, and the slide would lose `aria-labelledby` before hydration); Aria's private panel collection; dropping Aria for the bullets (their overrides hold). Replaces decision 15's slide half and decision 31's mechanism ("overrides Aria's `inert`"); decision 31's outcome stands.

Dev check 6 now also warns on two slides with one `value`, since the library's registry pairs the slides (Aria checks duplicate tab values only, `tab-list.ts`).

52. Q: How does the focus handoff run? A: P65 decision 2, generalised. Two steps: at the change, before any render, the Orbit reads live focus (`DOCUMENT.activeElement` inside a slide other than the newly selected one) and writes the new slide into a pending-handoff signal; an `afterRenderEffect` `write` phase, which runs after the change-detection pass that lifts the new slide's `inert`, focuses it with `preventScroll` while it is still the selected one, and clears the signal. Record points: the `selected` model's own change notification (`model_signal.ts`: `set()` emits to subscribers synchronously), which every library write and a consumer's direct `selected.set()` reach; `ngOnChanges`, for a parent binding (`write_to_directive_input.ts`: signal inputs go through `setInput`, so the `NgOnChanges` feature sees them; it runs before the slides' host bindings in that pass); and the live flip (54). Rejected: a synchronous `focus()` in the observer callback (P65: silent no-op in three engines, the new slide still `inert`); reading live focus inside the render callback (the old slide is `inert` by then, and an engine may already have moved focus to `body`; P65 saw the blur a frame later in its trace, which is no guarantee, and a layout read in an earlier phase can force it); keeping the losing slide out of `inert` while it holds focus (unmeasured, needs focus listeners and a third input to `inert`); `ngDoCheck` (skipped when only a `@for` embedded view refreshes, the lesson of the [Re-run: Interchange spec, the `replaced` timing and the outlet's focus rule](67-rerun-interchange-replaced-timing.md)).
53. Q: Which selection changes need the handoff? A: Every change while focus is inside a slide that stops being selected, not only the observer's. A control inside a slide that calls `next()` or writes `selected` would otherwise drop focus to `body` when its slide becomes `inert` (W 2.4.3), and so would a rotation step after a pointer focused a slide and left. The arrows and the bullets hold focus themselves and never trigger it. Rendered-state rule (BB 1.5): the target is written outside render callbacks, except at the live flip, where no slide is `inert` yet; Aria's `selectedTab` forwarding runs in Aria's `write` phase but never records, because focus is on the bullet. So no rendered-state signal is needed.
54. Q: What happens at the live flip after interaction before hydration? A: New, found while grilling the gate. In P65's design `live` turned on in the first render callback and the observer adopted a pre-hydration scroll one report later, so for at least a frame the slide in view was `inert`, and a focus inside it (a keyboard user who tabbed into a later slide's link before hydration, which scrolls that slide into view; likely under `hydrate on viewport`) would fall to `body`. Decision: mechanic 4 reconciles in the first render callback (`earlyRead` reads `scrollLeft` and the slide rectangles, `write` acts) before `live` turns on: a bound non-first slide at `scrollLeft` 0 is aligned instantly (unchanged); otherwise the slide at least half visible is adopted there, with one `selectedChange` (cause scroll); then a focus inside another slide records a handoff. The observer's first report agrees and changes nothing. P65's adoption case still holds (one change, cause scroll). Replaces "adopted by the observer's first report" in decision 22 and the rendering-modes subsection. Impact MEDIUM, confidence HIGH (a geometry read in a render callback, the observer's own threshold): decided; e2e cases assert that the slide in view never carries `inert` and that the focus stays.

The APG carousel pattern gives them no role, and a later `keydown` handler would be additive. Keyboard table row, 2.1.1 row, D21; the e2e case asserts focus and records `scrollY`.

### Amendment, 2026-09-27 (Decide the `@angular/aria` fallback confirmation)

The [Decide the `@angular/aria` fallback confirmation](75-evidence-aria-fallback-confirmation.md) overruled this spec's fallback from Aria's `TabPanel` (its fallback 1) and confirmed the lazy-slides fallback with a restated reason (its fallback 2); `specs/orbit.md` was edited to match. 1. Decision 45 (lazy slides), reason restated: with `TabPanel` hosted, an Aria `TabContent` in a slide would render, so the missing panel no longer decides it. 2. Decisions 48 to 51 and 57 are superseded by ADR 0037:
