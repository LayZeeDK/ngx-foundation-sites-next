## Answer

Spec: [specs/responsive-toggle.md](../specs/responsive-toggle.md). Resolved 2026-09-26 by self-grilling (AFK), both sides played against the sources below.

Gist: two directives. `[nfsResponsiveToggle]="menu"` on the consumer's `.title-bar` (required typed reference to the menu, `hideFor` default `medium`) is the Openable: `isOpen` model, `open(trigger?)`/`close()`/`toggle(trigger?)`, `opened`/`closed` Completion outputs, `triggerRole` `disclosure`, `id` = the menu's id, and it provides `nfsOpenableToken`, so the bare `nfsToggle` on the hamburger toggles it. `[nfsResponsiveToggleMenu]` on the toggled element carries `animate` (`"<in> <out>"`, where Foundation's docs put `data-animate`) and the menu's `id`. The building-blocks decision is confirmed, not reopened: the bar always carries Foundation's `.hide-for-<hideFor>`, the menu carries `.show-for-<hideFor>` while closed and not animating out, plus `.is-open` while open, so the server HTML is correct at every width, hydration changes no class at any width, and `hidden` is never used. Motion classes are bound only during the enter or exit phase (a `linkedSignal` of `isOpen`), completing on `animationend` or a 1100 ms fallback, and are skipped before the first client render, under reduced motion, with animations disabled, and at or above `hideFor`. The Breakpoint service is read only after the first render (animation skip, focus rule). WCAG 2.2 AA is met as requirements: the `nfs-responsive-toggle` Library mixin adds a 24 by 24 px hit area to Foundation's 20 by 16 px hamburger (2.5.8) and compile-time contrast warnings (1.4.11, 1.4.3), and, only on request, the two Visibility classes for a `hideFor` outside `$breakpoint-classes`. Implementation level: native platform CSS through Foundation's Visibility classes plus custom Angular directives; no Aria pattern; CDK `_IdGenerator` and `InteractivityChecker` only.

### Decision log

Sources: FS = the Foundation 6.9.0 clone; NG = the Angular 22.2.x clone; NGC = the components 22.2.x clone; APG = the aria-practices clone; R:x = the research files under `research/` (R:menus = `foundation-inventory-menus.md`, R:utilities = `foundation-utilities-conventions.md`, R:apg = `aria-apg-patterns.md`, R:platform = `web-platform-features.md`, R:rendering = `angular-rendering-modes.md`, R:material = `angular-material-reference.md`, R:aria = `angular-aria-inventory.md`); BB = `building-blocks.md`; the Breakpoint spec, Triggers spec, and Motion UI prototype are [Spec: Breakpoint service (shared utility)](53-spec-breakpoint-service.md), [Spec: Triggers (shared utility)](54-spec-triggers.md), and [Prototype: `animate.enter` and `animate.leave` with Motion UI transition classes](47-prototype-motion-ui-animate-enter.md).

Round 1 (no prerequisites): the Foundation contract and what is fixed upstream.

1. **What exactly does Foundation's plugin do?** Reads `data-responsive-toggle="<id>"` (logging a stale `data-tab-bar` error when missing), finds `[data-toggle]` descendants of the bar whose value is the id or empty, merges options from the bar and then from the target, `_update()`s on every `changed.zf.mediaquery` (bar shown and target hidden below `hideFor`, the reverse at and above, inline `display`), `toggleMenu()` only below `hideFor` (Motion UI `animateIn`/`animateOut` chosen by `:hidden`, else `toggle(0)`), fires `toggled.zf.responsiveToggle` after the animation and `mutateme.zf.trigger` on `[data-mutate]` descendants. No ARIA. Defaults: `hideFor: 'medium'`, `animate: false`. Source: FS `js/foundation.responsiveToggle.js` (read in full); R:menus 5.1-5.9, 0.3; FS `docs/pages/responsive-navigation.md` (title bar example, animated example with `data-animate` on the target, "Preventing FOUC").
2. **Which option names are real (audit 0001 H6 guard)?** Only `hideFor` and `animate` (the `defaults` object); the ticket's `data-responsive-toggle` is the target reference, not an option. Source: FS `ResponsiveToggle.defaults`.
3. **What is fixed upstream?** BB Table A and Table B ResponsiveToggle rows (two directives; Foundation's `.hide-for-<bp>`/`.show-for-<bp>` bound from `hideFor`; `.is-open`; no `hidden`; a custom rule only outside `$breakpoint-classes`; keyframes as a State class; disclosure; button named by `aria-labelledby`); BB 1.11 decision 8 and ADR 0008 Consequences (as amended by audit 0002 H4); BB 1.3 (`isOpen`, `open`/`close`/`toggle`, `opened`/`closed`); BB 1.6 rule 1 and ADR 0003; ADR 0013 and the Triggers spec (Openable interface, `disclosure` role, bare `nfsToggle` resolving the bar); ADR 0014 and the Breakpoint spec (`atLeast`, `reducedMotion`, live after the first render). Reopened only where stated below (decisions 13, 22, 36). Source: those documents.
4. **What do Foundation's Visibility classes actually emit?** `.hide-for-<bp>`: `display: none !important` from `breakpoint(<bp>)` up; `.show-for-<bp>`: `display: none !important` below the breakpoint (0.00125em under it); both only for `$breakpoint-classes` (default `small medium large`) and never for the Zero breakpoint. The `!important` is why the directive must remove `.show-for-<bp>` to show the open menu. Source: FS `scss/components/_visibility.scss` (`show-for`, `hide-for`, `foundation-visibility-classes`); FS `scss/settings/_settings.scss:126`; FS `scss/util/_breakpoint.scss:37-50`.
5. **Does any Foundation rule style `.is-open` on a menu or top bar?** No: only `.dropdown-pane.is-open` and `.off-canvas.is-open`. So `.is-open` on the menu is a harmless hook. Source: `rg "is-open" FS/scss`.

Round 2 (depends on 1-5): shape and linking.

6. **Toggler variant with a breakpoint input, or its own directive?** Own directive. The title bar must provide the Openable (bare `nfsToggle` inside it), the bar needs its own breakpoint class, and Toggler hides with `hidden` (BB Table A Toggler), which would hide the desktop menu in server HTML. Source: BB Table A; audit 0002 H4.
7. **Which elements get a directive?** The bar (`[nfsResponsiveToggle]`) and the menu (`[nfsResponsiveToggleMenu]`); both need host bindings present in server HTML (ADR 0001; R:rendering 7 rule 1). No directive on `.title-bar-title` (decision 26) or the button (the Trigger covers it). Source: BB 1.1, 1.3 (plugin name when no structural class).
8. **Does the bar directive add `.title-bar`?** No; the consumer writes it, so a custom bar works, and ResponsiveToggle is behaviour, not a look. Source: BB Table A ("on `.title-bar`"); FS docs ("Any element will work" for the target).
9. **Link direction and form?** The bar's main input holds a typed template reference to the menu, `[nfsResponsiveToggle]="menu"` with `#menu="nfsResponsiveToggleMenu"`, the counterpart of `data-responsive-toggle="<id>"` (this supersedes the Triggers spec's `[menu]` sketch, which that spec marked as owned here). Template references are hoisted in a template, so the menu may follow the bar. Source: ADR 0013; NG `adev/src/content/guide/templates/variables.md`.
10. **How does the menu's host read the bar's state?** The bar registers with the menu from an `effect` with cleanup (Aria's reverse link, as the Triggers spec's `registerTrigger`). View effects run in `refreshView` after the template's input bindings and preorder hooks and before `processHostBindingOpCodes`, and embedded and child views refresh after that, so the menu's classes are right in the first pass whenever the bar is in the same, an enclosing, or an embedded view; only a bar in a child component with the menu in the parent renders the menu once without it, repaired within the same tick by the synchronisation loop. The effect writes no DOM, so it is server-safe. Source: NG `packages/core/src/render3/instructions/change_detection.ts` (`refreshView`: `executeTemplate`, preorder hooks, `runEffectsInView`, `detectChangesInEmbeddedViews`, `processHostBindingOpCodes`, child components); Triggers spec decision 15; BB 1.5.
11. **Plugin token?** None: nothing injects the bar by class; `nfsOpenableToken` serves descendants, `exportAs` serves templates. BB Table B lists `nfsResponsiveToggleToken`; proposed change below. Source: BB 1.9 (tokens for parent handles that children need); YAGNI.
12. **Defaults token?** `nfsResponsiveToggleDefaultsToken` (Shape B, `hideFor`, `animate`). Source: BB 1.4 last bullet, Table B.
13. **Where do `hideFor` and `animate` live?** One home each: `hideFor` on the bar (Foundation's docs and defaults), `animate` on the menu (Foundation's animated example puts `data-animate` on the target, the element that animates). Foundation's read-from-both-elements merge is dropped. BB Table A lists both on the bar implicitly; proposed change below. Source: R:menus 5.3; FS docs animated example.

Round 3 (depends on 6-13): state, API, and the breakpoint.

14. **Inputs and model?** `menu` (required), `hideFor: NfsBreakpointName` (default `'medium'` or the Defaults token), `isOpen = model(false)`; on the menu `animate: string` (default `''`), `id` from a static attribute or `_IdGenerator` (`nfs-responsive-toggle-menu-`). Source: BB 1.4; Breakpoint spec types; BB 1.5 (ids).
15. **Outputs?** `isOpenChange` (model, at request time) and `opened`/`closed` (Completion outputs after the animation). Foundation's `toggled` fires after the Motion callback, which is the Completion outputs' timing, so BB 1.4's mapping "`toggled` -> `isOpenChange`" is refined to both. Source: FS `toggleMenu` (event inside the `animateIn`/`animateOut` callbacks); BB 1.4 output rule; CONTEXT Completion output.
16. **Methods and the Openable members?** `open(trigger?)`, `close(result?)` (result ignored, no veto), `toggle(trigger?)`, `registerTrigger` (for focus return), `id` = the menu's id, `triggerRole` = `disclosure`. Source: Triggers spec API table and "Consumers" table.
17. **Keep `toggleMenu()`'s no-op at and above `hideFor`?** No. The desktop menu is shown by CSS whatever the state, so the guard protects nothing; the methods work at every width. Source: decision 4; FS `toggleMenu`.
18. **What happens to the state at a breakpoint crossing?** Nothing is written; `isOpen` persists. Foundation's reset to hidden came from rewriting inline `display` on every breakpoint change (even between two breakpoints below `hideFor`). Writing the model from a breakpoint change would need an `effect` that propagates state, which BB 1.5 and Angular's effect guide rule out, and the menu looks the same at and above `hideFor` in either state. Open state after a round trip is kept, which also keeps focus from being dropped. Sources cannot settle whether consumers prefer Foundation's reset: OPEN FOR HUMAN 1. Source: FS `_update`; NG `adev/src/content/guide/signals/effect.md` ("Avoid using effects for propagation of state changes"); BB 1.5.
19. **How are server HTML and first paint correct at every width?** The bar always carries `.hide-for-<hideFor>`; the menu carries `.show-for-<hideFor>` when `!isOpen && transition !== 'exiting'`; both follow the `hideFor` input, not a breakpoint evaluation; Foundation's media queries do the rest before any JavaScript. Source: BB Table A/B; audit 0002 H4; R:rendering 7 rules 1, 9, 11.
20. **What happens at the first-render handoff when the client is at or above `hideFor`?** Nothing re-renders and no class changes, because no binding reads the breakpoint; the live value reaches only the animation skip and the focus rule, whose first run records values without acting. So the [Prototype: Breakpoint handoff under hydration](60-prototype-breakpoint-handoff-hydration.md) does not affect this spec's first paint. Source: ADR 0014; Breakpoint spec decisions 26-32.
21. **Consumer-written `.show-for-*`/`.hide-for-*` (Foundation's FOUC habit)?** Not allowed on the bar or the menu for the `hideFor` breakpoint; a static class would fight the binding. Development-mode warning through `HostAttributeToken('class')`. Source: angular-developer `host-elements.md` (binding collisions); Button spec (`HostAttributeToken('class')`).
22. **`hideFor` outside `$breakpoint-classes`?** BB offered "the smallest custom rule, or ask the consumer to add the breakpoint to `$breakpoint-classes`". Decided: an opt-in `@include nfs-responsive-toggle(<bp>...)` that emits `.hide-for-<bp>` and `.show-for-<bp>` through Foundation's `hide-for()`/`show-for()` mixins for the named breakpoints only, because `$breakpoint-classes` also drives the grid, alignment, and other responsive classes of every component. Same class names, so the directive's binding rule stays one rule. Names already in `$breakpoint-classes` are skipped; the Zero breakpoint and unknown names are a compile `@error`. Source: FS `_visibility.scss`; FS `scss/grid/*`, `scss/util/_breakpoint.scss` (`$breakpoint-classes` users); ADR 0012 (mixin parameters only for values Foundation has no setting for).
23. **`hideFor` equal to the Zero breakpoint?** Meaningless (the bar would never show; Foundation emits no `hide-for-small`); development-mode warning, no special mapping. Source: decision 4.
24. **Missing Visibility class detection?** A development-mode render callback checks once: below `hideFor` with the menu closed, the menu computes `display: none`; at and above, the bar does. It names both fixes and also catches a missing `foundation-visibility-classes` include. Source: Sass packaging decision 11 (a forgotten include must be caught or named); Breakpoint spec drift check (same mechanism).

Round 4 (depends on 14-24): ARIA, keyboard, WCAG 2.2 AA.

25. **Pattern and roles?** APG Disclosure, the mobile navigation button of the disclosure-navigation example: native `button` with `aria-expanded` and `aria-controls` (rendered by `nfsToggle` in the `disclosure` role); the menu is the consumer's element, a named `nav` landmark recommended. Source: R:apg ResponsiveToggle; APG `content/patterns/disclosure/`; Triggers spec ARIA table.
26. **How is the icon-only button named?** Consumer markup: `aria-labelledby` pointing at the `.title-bar-title` element's static `id` (visible text beats `aria-label`; the name matches the visible label for 2.5.3), or a `.show-for-sr` span. No directive and no generated id: static ids are hydration-safe, and a directive would only copy an id. Source: R:apg ResponsiveToggle ("aria-labelledby pointing at .title-bar-title beats an aria-label"); BB 1.10 names rule.
27. **Hiding mechanism for ARIA?** `display: none` from Foundation's Visibility class; no `hidden`, no `aria-hidden`, no `inert` on the closed menu (it is the visible desktop menu); `inert` only while animating out. Source: BB 1.10, 1.11 decision 8; R:platform 15 ("inert the collapsed menu while ... animating").
28. **Escape?** None: the title-bar menu is in the page flow; BB 1.10 reserves Escape for overlays; the APG disclosure pattern requires none; Foundation has none. Overlay-styled consumers add `(keydown.escape)`. Source: BB 1.10; APG disclosure pattern keyboard section; R:platform 21 (`CloseWatcher` only for in-flow custom overlays).
29. **Focus management?** Focus stays on the button (disclosure). One rule for focus that would be lost: when the menu stops being operable (exiting, or a crossing hides a closed menu) while it holds focus, focus moves to the `trigger` from `open()`, else the first registered Trigger; when a crossing to `hideFor` hides the bar while it holds focus, focus moves to the first tabbable menu element (`InteractivityChecker`); never on the first render. Source: BB 1.10 focus persistence; Breakpoint spec decision 40; Triggers spec "Requirements every Openable spec inherits" (focus returns to the `trigger`).
30. **WCAG 2.2 AA 4.1.2 Name, Role, Value?** Requirement met by decisions 25-26: native button, name from the title, `aria-expanded`, `aria-controls`; Foundation fails it (no name, no state). Tested by axe `button-name` and ARIA rules and the SSR smoke. Source: WCAG 2.2 4.1.2; R:menus 5.6 (no ARIA in Foundation).
31. **WCAG 2.2 AA 2.5.8 Target Size (Minimum)?** Foundation's `.menu-icon` is `hamburger()` at a fixed 20 by 16 px with no size setting (`foundation-menu-icon` passes only colours); it passes only through the spacing exception, which a nearby `.title-bar-right` button breaks. Requirement met by the smallest custom rule: `.title-bar .menu-icon::before`, a transparent 24 by 24 px box centred with `transform` (Foundation's bars are `::after`, and `hamburger()` sets `position: relative`), so the look and the icon box are unchanged and no Foundation literal is copied. Emitted by default by `nfs-responsive-toggle`. Tested by `elementFromPoint` outside the icon edges in three engines and axe `target-size`. Source: FS `scss/components/_menu-icon.scss`; FS `scss/util/_mixins.scss:83-143` (`hamburger`); WCAG 2.2 2.5.8 (24 by 24 CSS px or spacing).
32. **WCAG 2.2 AA 1.4.11 Non-text Contrast and 1.4.3 Contrast (Minimum)?** Foundation's defaults pass (`#fefefe` bars on `#0a0a0a` about 19.6:1; `#cacaca` hover about 12:1; `.menu-icon.dark` hover `#8a8a8a` on white about 3.4:1; title text about 19.6:1, computed with the WCAG relative-luminance formula). A consumer theme can fail silently, so `nfs-responsive-toggle` emits compile-time `@warn` through Foundation's own `color-contrast()` for the icon colours (under 3) and the title colour (under 4.5); no CSS. Source: FS `scss/settings/_settings.scss:80-83, 852-858`; FS `scss/util/_color.scss:54-70` (`color-contrast`); WCAG 2.2 1.4.11, 1.4.3.
33. **WCAG 2.2 AA 2.4.7 Focus Visible?** The library removes no outline; Foundation's global button reset removes it only under `[data-whatinput='mouse']`, which needs the what-input script the next library never loads, and then only for mouse input; the user agent's indicator stays. Tested by an e2e screenshot comparison. Source: FS `scss/_global.scss:222-224`; FS `scss/util/_mixins.scss:206-210` (`disable-mouse-outline`).
34. **WCAG 2.2 AA 2.4.11 Focus Not Obscured (Minimum)?** In Foundation's in-flow layout nothing overlays focused content; the closed menu is `display: none` and the exiting menu `inert`, so neither holds focus, and decision 29 moves focus out of anything hidden. A sticky title bar (consumer layout) requires `scroll-padding-top` equal to its height, stated as a requirement of that layout and tested in an e2e story variant. Source: WCAG 2.2 2.4.11; R:platform 9 (`scroll-padding` in target).
35. **WCAG 2.2 AA 1.4.10 Reflow?** At 320 CSS px the page must not scroll horizontally. The flex title bar fits; the menu below `hideFor` must stack: the spec's markup uses `vertical medium-horizontal` menus (Foundation's docs example uses a horizontal `.dropdown.menu`, which overflows), and consumers keep `$topbar-unstack-breakpoint` at or above `hideFor`. Tested at 320 by 640 px with the menu open. Also 2.1.1 and 2.4.3: native activation and bar-then-menu DOM order. Source: WCAG 2.2 1.4.10; FS `scss/components/_title-bar.scss` (`$global-flexbox`); R:menus 5.8 (`$topbar-unstack-breakpoint`).
36. **Axe gate?** WCAG 2.2 AA rule set (tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`) with `parameters.a11y.test = 'error'` in every story. Source: BB 1.10 last bullet; user rule restated 2026-09-26.

Round 5 (depends on 14-29): animation and reduced motion.

37. **Mechanism?** BB 1.6 rule 1 (persistent element, State-class keyframes); `animate.enter`/`animate.leave` do not apply because the menu is never inserted or removed. Source: BB 1.6 rules 1-2; ADR 0003; BB Table B.
38. **How does a change through `[(isOpen)]` animate without an effect?** `#phase` is a `linkedSignal` of `isOpen` returning `'idle'` for the first value and while `#live` (untracked) is false, else `'entering'`/`'exiting'`; completion writes `'idle'`. Bindings, Triggers, and methods share one path; the initial state and any change before the first client render (server included) never animate. Source: NG `adev/src/content/guide/signals/linked-signal.md` (previous-value computation, writable); BB 1.4 (`linkedSignal` for derived-but-writable state).
39. **When is the Motion class bound?** Only during the phase; `#transition` is `'idle'` (skip) when not live, no class for that direction, `reducedMotion()`, `nfsAnimationsToken.disabled`, or `atLeast(hideFor)` (nothing to animate while the menu is shown throughout). No Motion class in server HTML, so hydration plays nothing. Source: [Prototype: `animate.enter` at hydration](52-prototype-animate-enter-hydration.md) (signal-gated classes); Breakpoint spec (live values after the first render).
40. **Completion and the fallback timer?** `animationend` whose `target` is the menu, else a timer of 1100 ms (BB 1.6 rule 6 ceiling of 1 s plus 100 ms), a design-time value because it must work when the stylesheet is missing; started in an `afterRenderEffect` outside the zone, cleared by its cleanup; skipped phases complete in that effect at once. A consumer class longer than 1 s is cut, documented. Source: BB 1.6 rules 1, 6; BB 1.11 decision 4; Motion UI prototype ("a value the directive already knows at design time"); NG `adev/src/content/guide/animations/enter-and-leave.md:106` (some test environments emit no animation events).
41. **Reduced motion?** No Motion class is bound under `reducedMotion()`, so consumer classes without a reduced-motion rule are covered too; `nfs-motion`'s 1 ms override remains the backstop for its classes. This follows BB 1.6 rule 1's "reduced motion resolves the wait synchronously". Source: BB 1.6 rules 1 and 5; Breakpoint spec decision 23.
42. **Motion UI transition class names?** Unsupported (Motion UI prototype); a recognised name (`hinge-in-from-top`, `spin-out`, the rest of Motion UI's transition set) warns once in development mode, names the `nfs-` class when `nfs-motion` has one, and is applied unchanged (the orchestrator's default in that ticket). Foundation's docs example maps to `nfs-hinge-in-from-top nfs-spin-out`, both in the `nfs-motion` set. Source: Motion UI prototype answer and orchestrator note; BB 1.6 rule 4.
43. **Interruption?** The opposite request swaps the class and restarts the timer; the interrupted direction emits no Completion output. Source: BB 1.4 (Completion outputs only for committed changes).

Round 6 (depends on all above): rendering modes, level, tests, extras.

44. **Rendering modes?** SSR and prerendering: first paint from bindings only; nothing reads the viewport before render callbacks; the reverse-link effect is server-safe. Full hydration changes nothing but generated ids. Event replay: only the Trigger's `click` host listener replays (`jsaction="click:;"`); `afterNextRender` runs before replay, so a replayed tap animates; the menu's `(animationend)` is not a replayable type. One hydration boundary for bar, Triggers, and menu. `hydrate never`: desktop menu usable, mobile toggle inert (documented residue). No `@defer` in library templates. Zoneless: signal writes only. Source: ADR 0008; R:rendering 3, 4, 7 rules 1-11; BB 1.11 decisions 1-8, 10-11; [Prototype: Rendering-mode test seam](59-prototype-rendering-mode-test-seam.md) (`jsaction`, replay after hydration).
45. **Implementation level and fallback?** Native platform CSS (Foundation's Visibility classes, keyframes, `inert`) plus custom Angular directives; Aria has no disclosure pattern; CDK only `_IdGenerator` and `InteractivityChecker`. Fallback: none needed, every feature is Baseline widely available on 2026-05-07. Source: BB 1.2; R:aria (eight patterns, none a disclosure); R:platform Feature summary.
46. **Material counterpart?** None; the navigation schematic's `BreakpointObserver` plus `mat-sidenav` recipe decides visibility in JavaScript, so it is right at one width only. Borrowed only through the Openable contract. Source: R:material 11.

Invoker Commands through the Triggers utility. Source: R:platform 2, 20, 21.

Source: BB 1.12; Breakpoint spec decision 43 (MediaMatcher fake, width-independent play functions); rendering-mode test seam prototype.

### OPEN FOR HUMAN

1. State at a breakpoint crossing. Default applied: `isOpen` persists (nothing is written on a crossing), so a menu opened on a phone, rotated to a desktop width and back, is still open. The alternative is Foundation's behaviour, closing the menu on a crossing, which in Angular needs either an `effect` that writes the model from a breakpoint change (against BB 1.5 and Angular's effect guidance) or an `isOpen` whose read value is derived from the breakpoint (so the model and the visible state disagree). Sources establish Foundation's reset as a side effect of its inline-`display` rewriting (FS `_update`, which even resets between two breakpoints below `hideFor`), not a documented feature, so they cannot settle what consumers expect.

## Prototype needed

None. The reverse-link ordering is read from NG `refreshView`, the animation path is confirmed by the Motion UI prototype, first paint depends on no breakpoint evaluation (so the Breakpoint handoff prototype does not gate it), and the hit area relies on pseudo-elements taking part in hit testing, which the e2e `elementFromPoint` case asserts in three engines.

### Proposed glossary terms

**Visibility class**:
A Foundation CSS class that shows or hides an element by breakpoint of the Breakpoint map (`.show-for-medium`, `.hide-for-large`, `.show-for-small-only`), generated only for the breakpoints in `$breakpoint-classes`; distinct from a State class, which expresses runtime state.
_Avoid_: responsive class, breakpoint class, visibility helper

Reason: BB 1.7 and 1.11 decision 8, ADR 0008 Consequences, the Breakpoint spec, and this spec all rely on "Foundation's visibility classes" as a category that is neither a Structural, State, nor Variant class; OffCanvas will too.

### Proposed ADR

None. The Visibility-class first paint is already ADR 0008's consequence; the persistence of `isOpen`, the opt-in mixin, and the hit-area rule are each easy to reverse.
