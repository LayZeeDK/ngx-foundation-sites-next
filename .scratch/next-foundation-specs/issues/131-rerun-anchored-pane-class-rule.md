# 131. Re-run: Anchored pane (shared utility) spec under the class rule

## Question

What does the [Spec: Anchored pane (shared utility)](55-spec-anchored-pane.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/anchored-pane.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Anchored pane (shared utility)](55-spec-anchored-pane.md) and the answer here. Model: Opus 5.5.

### Grilling record

Round 1 (nothing settled yet): what classes does the spec touch, and who writes them?

1. **Which Foundation or library classes does the published spec leave to the consumer?** Found: `class="dropdown-pane"` in the Dropdown pane's consumer markup (DRP asks it gone); the 1.4.10 advice "Foundation's `.tiny`/`.small` classes"; the e2e reflow case's "`.small` (200 px) pane"; the test pane "on a `.dropdown-pane`", which reads as a class written in the stories; the usage sentence "a Foundation-styled `position: absolute` element" for a developer's own anchored element; the Tooltip block, which shows only rendered output and no class-free consumer line. The contract's `position` row still said "the Tooltip spec reads its trigger's legacy class for `auto`", which TT has now dropped. Settled: all go (decisions 1, 4, 6, 7).
2. **Does the utility itself bind or read any class?** Read the spec against FS: the Positioner writes inline `top`/`left` with `Renderer2` and exposes `placement`; Light dismiss and hover intent touch no class; Foundation's own Positionable reads options only, and only its Dropdown (`:89-106`) and Tooltip (`:71-79`) subclasses read legacy position and `.float-*` classes, both now dropped (DRP D5 and D27, TT decision 2). So nothing changes in the mechanism; what was implicit becomes a stated invariant: the utility reads no class and writes none (decision 1, D22), which also meets building-blocks 1.4's rule that no directive reads a static Foundation class to seed state.
3. **Who binds the Placement classes, and is that a State class?** The consuming directive, in its own `[class]` list: the Dropdown pane's `has-position-*`/`has-alignment-*` and the tip's pip classes (DRP decision 3, TT decision 1: State classes of the resolved Placement, which a collision can change). The utility writing them would be a second writer beside that binding. Settled: D9 revised (decision 2).

Round 2 (depends on 1 to 3): vocabulary, the public API for developers' own panes, and the consuming specs' decisions.

4. **"Consumer" means two things in this spec.** In most of the spec it named the Dropdown pane, Tooltip, and Nested menu ("the consumer binds its classes", "Their consumers", "What each consumer maps"); ADR 0039 uses it for the application ("consumers write no Foundation or NFS class"). Read together, "Placement classes are bound by the consumers" says the application writes them, the opposite of the rule. Options: (a) keep the word and add a definition; (b) "consuming directive" for the library side and "consumer" for the application, as ADR 0039 has it; (c) a glossary term. (a) keeps the collision in every table. (c) fails the `/domain-modeling` bar: "consuming directive" names no domain concept beyond this spec's relation to its callers. Settled: (b), with a two-sentence definition in the Solution; two headings and one column are renamed, and the amendment records the old names so earlier citations stay traceable (decision 3).
5. **A developer's own anchored element (the spec's public API).** The spec told such a developer to use "a Foundation-styled `position: absolute` element", which under ADR 0039 means writing `.dropdown-pane` or `.tooltip` on an element no library directive owns. Options: (a) an application class that sets `position: absolute`, and `nfsDropdownPane` itself for Foundation's pane look; (b) a class-only directive that binds `.dropdown-pane` for such panes; (c) allow the class there. (c) breaks ADR 0039. (b) gives one Structural class two owners, one of them without the pane's State classes (`.is-open`, the Placement classes) that `NfsDropdownPane` binds, and ADR 0039 and building-blocks 1.1 give each Structural class one directive. Settled: (a) (decision 5, D23). The development `position` check covers both routes; its message now names the missing export mixin and the application-class case. Its three checks stand, which TT's Tooltip relies on ("The Positioner adds its own three").
6. **`parentClass`.** DRP D6: it names an application class, never a Foundation or library class, with no check. The contract and mapping rows say so (decision 6).
7. **The legacy position classes (X AP3).** Both consuming specs now drop them and report a copied class in development (DRP D5, D27; TT decision 2, `auto` is `top` for the Tooltip). The contract rows, the mapping's not-read row, and Out of Scope state it. AP3's reason ("decided by the consumer specs") is decided; its category becomes `superseded` (the typed `position` and `alignment` replace them), the category TT gave its own dropped read (decision 4).
8. **The Nested menu's Top Bar source (DM, the Positioner's consumers may meet it).** The Base side now comes from `alignment`, the Menu's `align`, the direction, and `nfsTopBarRightToken` at construction, with a DOM walk after hydration only when the token is absent. The utility's collision functions are pure and measure a submenu wherever that side put it, so nothing changes here; the DropdownMenu mapping cell names the Base side instead of `alignment` alone. Does the utility itself have an ancestry that projection could hide (building-blocks 1.9, DM's proposed "Ancestry that projection can hide" bullet)? No: Light dismiss nesting is DOM containment of a pane or a Trigger at event time, which follows where projected content renders, so no token is needed; stated in a Hierarchy bullet (decision 8).

Round 3 (depends on 4 to 8): tests, stories, rendering modes, exclusions.

9. **Stories and tests.** The Storybook conventions forbid a Foundation class written in a story. The test pane and test tip bind their own classes as host bindings (the Nested menu's test root does the same); Triggers are `nfsButton` buttons with `nfsToggle`; scaffolding that has no directive yet is inline style, as DRP decision 12 does, until the [Spec: Prototyping Utilities](102-spec-prototyping-utilities.md) gives it directives. The reflow case needed a 200 px pane: `.small` cannot be written, and the library Storybook compiles the Dropdown spec's required `$dropdown-sizes`, which caps `.small` at `min(200px, 45vw)`, 144 px at 320 px wide, so the published "`.small` (200 px)" was already wrong there. Options: a `size` input on the test pane (a second copy of the Dropdown's Variant input in test code, and still not 200 px) or a `paneWidth` arg as an inline width (a value no class gives under those settings). Settled: `paneWidth`. Layer 2 gains a Classes case (the utility adds nothing to the class list; a copied legacy class changes no placement); the SSR fixture writes no `class`; Story ids are unchanged (decision 7, D24). Using the real `NfsDropdownPane` in the utility's own stories was weighed and rejected: they would test the Dropdown's Options, and the Tooltip tip is internal to its entry point.
10. **Rendering modes.** Unchanged: the utility writes nothing on the server. The text now says the pane's server class comes from its directive, that open at first paint is a bound `[isOpen]="true"`, never a copied `.is-open` (building-blocks 1.4), and that the Placement classes appear after hydration from the consuming directive's binding (decision 9).
11. **Exclusion categories (the brief).** Every Out of Scope item gets "Category: `<id>`": AP1, AP2, AP5, runtime theming `scope-boundary` (DP17's reading of G9), AP3 `superseded`, AP4 `platform-or-a11y`, AP6 `other` (as X). "Library CSS" leaves Out of Scope, as TT did for the Tooltip: the utility has none, which D18 and the Sass subsection state. The "Not ported" list and the "Foundation behaviour changed or dropped" list carry one category per item; `hoverPane` (AP7) is marked `platform-or-a11y` where the spec names it. Design-decisions rows are read as TT read them: the rows whose rejected alternative is a Foundation feature (D4, D7, D8, D10, D12, D13, D14, D16, D19, D22) name its "Exclusion category" in the Rationale; alternatives that are not Foundation items (CDK, viewport bounds, render hooks) carry none. Nothing comes back into scope: no item was excluded for being CSS-only, and no Foundation class is left for the consumer (decision 10).
12. **Glossary or ADR?** No ADR: nothing is hard to reverse or surprising; every change applies ADR 0039. Glossary: the **Anchored pane** definition lists only "the Dropdown pane and the Tooltip tip", while the spec's public API speaks of developers' own Anchored panes; a one-clause widening is proposed (change 2). TT's proposed **Application class** term is used as written.

The frontier is empty.

### Decisions

1. The utility reads no class and writes none: its only DOM output is inline `top`/`left`, and `auto` resolves from `autoPosition`, `autoAlignment`, and `Directionality`, never from a class (new D22). Every class on a placed or measured element is its consuming directive's host binding; the class mapping gains a Kind column with the Structural rows (`.dropdown-pane`, `.tooltip`), the Nested menu's `is-dropdown-submenu`, the State rows, and not-read rows (legacy position classes, `.float-*`, `.is-opening`). No Variant class, Variant property, or Runtime check request.
2. The consuming directive binds the Placement classes from `placement` as State classes in its own `[class]` list (D9 revised).
3. Vocabulary: "consuming directive" for a directive built on the utility, "consumer" for the application, as ADR 0039 uses it; the headings "What each consuming directive maps" and "ARIA requirements it imposes on consuming directives" and the column "Consuming directive's part" replace their "consumer" forms.
4. Legacy position and `.float-*` classes are read nowhere: the contract rows state that both the Tooltip and the Dropdown pane drop them and report a copied one in development (TT's request, verbatim in substance); Out of Scope's AP3 item is `superseded`.
5. A developer's own anchored element is styled by an application class that sets `position: absolute`, never by `.dropdown-pane` or `.tooltip`; `nfsDropdownPane` gives Foundation's pane look (new D23, a usage example); the development `position` check's message names both the missing export mixin and this case; the three checks stand.
6. `parentClass` names an application class (DRP D6); WCAG 1.4.10's consuming-directive part cites the Dropdown spec's required `min(<width>, 45vw)` widths and its `size` input.
7. Examples, stories, tests: `class="dropdown-pane"` leaves the Dropdown pane's consumer markup, and the Tooltip block gains its class-free consumer line; the test consumers bind their own classes; no story, test host, or fixture writes a Foundation or library class, except the layer 2 case that feeds a copied legacy class; Triggers are `nfsButton` with `nfsToggle`; scaffolding is inline style; the fixture story gains `paneWidth`, and the reflow case uses a 200 px inline width; layer 2 adds a Classes case; the SSR fixture writes no `class` and asserts `.dropdown-pane` from the test pane (new D24). Story ids unchanged.
8. The DropdownMenu mapping cell names the Base side, a Top Bar's right-hand section included; Light dismiss nesting stays DOM containment, so the utility needs no ancestry token.
9. Rendering modes, behaviour, ARIA, keyboard, and every API signature unchanged; the text names the directive-bound server class and the bound open-at-first-paint state.
10. Out of Scope, the "Not ported" and "changed or dropped" lists, and the Foundation-excluding Design-decisions rows carry exclusion categories in TT's format; "Library CSS" leaves Out of Scope; the Sass subsection gains item (6), "Variant properties: none".
11. User stories 43 to 46 appended; D1, D9, D20 reworded; D22 to D24 added.
