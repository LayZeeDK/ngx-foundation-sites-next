# 114. Re-run: Drilldown Menu spec under the class rule

Type: grilling
Status: resolved
Blocked by: 81, 132
Labels: wayfinder:grilling
Map: ../map.md

## Question

What does the [Spec: Drilldown Menu](22-spec-drilldown-menu.md) become under the class rule of the user's ruling on 2026-09-27 ([Triage the out-of-scope Foundation components and variants](79-triage-out-of-scope-components-and-variants.md)): consumers write no Foundation or NFS class; every Structural class is bound by its directive, every Variant class is set by a typed input, every State class is a host binding, and layout systems and utility families get directives too (ADR 0039, which supersedes ADR 0010)? Revise `specs/drilldown-menu.md` in place so that no consumer-written Foundation or NFS class remains: every Structural class the spec leaves to the consumer gets its directive binding, every Variant class the spec leaves consumer-written becomes a typed input by the decision above, and every State class stays or becomes a host binding. Behaviour, ARIA, keyboard, rendering modes, and tests otherwise stay as decided.

## How to work it

Read first: ADR 0039; the answer of [Decide: typed Variant inputs over open Sass maps](81-decide-typed-variant-inputs-open-sass-maps.md) (how a Variant input is typed, including over open Sass maps); `research/out-of-scope-triage.md` (every row and dissent that names this spec); `research/foundation-component-catalogue.md` and `research/out-of-scope-exclusions.md` (its rows and ids); `map.md` Notes (standing preferences, target platform, spec shape, rendering modes, the triage rule, the Out-of-scope triage note); `building-blocks.md`; `CONTEXT.md`; ADR 0001, ADR 0012, and ADR 0022. Then revise the spec's Solution, class mapping, API tables, Rendered HTML (server and hydrated), stories and their play functions, tests, SSR smoke, and Design decisions, and remove every consumer-written class from its examples. Where the change reaches another spec, a shared utility, building-blocks, or an ADR, propose the edit for the orchestrator instead of making it. Record the revision as a dated `### Amendment, <date> (class rule)` section in the [Spec: Drilldown Menu](22-spec-drilldown-menu.md) and the answer here. Model: Opus 5.5.

## Answer

Model: Opus 5.5. Resolved 2026-09-28, AFK under the map's override: self-grilled on both sides with `/grill-with-docs` (the `/grilling` rounds plus `/domain-modeling` for vocabulary), then the spec revised in place in the `/to-spec` shape. Sources: ADR 0039, ADR 0040, ADR 0041, ADR 0042, building-blocks 1.3, 1.4 (the Option and Variant rules, the initial-state rule), 1.9, 1.10, 1.13, and 1.14, the answers of [Re-run: Nested menu (shared utility) spec under the class rule](132-rerun-nested-menu-class-rule.md) (its "What the four menu re-runs must follow" section is the contract applied here), [Spec: Menu](85-spec-menu.md), [Re-run: Reveal spec under the class rule](110-rerun-reveal-class-rule.md) (the Option-class precedent), [Re-run: Button spec under the class rule](128-rerun-button-class-rule.md) (the `nfsShowForSr` placeholder), and [Spec: Top Bar](86-spec-top-bar.md) (the exact-luminance finding, relayed by the orchestrator mid-ticket), the revised `specs/nested-menu.md` and `specs/menu.md`, `research/out-of-scope-triage.md`, `research/out-of-scope-exclusions.md` (DL1 to DL11), `research/foundation-component-catalogue.md` (the Drilldown Menu row), `map.md` Notes, the Foundation 6.9.0 clone (`js/foundation.drilldown.js`, `scss/components/_drilldown.scss`, `docs/pages/drilldown-menu.md`), and the Angular 22.2.x clone (`packages/core/src/render3/instructions/styling.ts`). No experiment was run. Spec: [specs/drilldown-menu.md](../specs/drilldown-menu.md), revised in place; the dated amendment is in [Spec: Drilldown Menu](22-spec-drilldown-menu.md) under `### Amendment, 2026-09-28 (class rule)`.

Gist: the consumer's markup keeps Foundation's element structure and carries no class. `ul[nfsDrilldown]` hosts `NfsMenu` with the five Menu inputs every plugin root exposes, so `orientation="vertical"` replaces Foundation's `vertical` and `align` turns the drilldown arrows; submenus are bare `ul[nfsSubmenu]`, the Hybrid name `span[nfsSubmenuToggleText]`, the back item `li[nfsDrilldownBack]` (binding `js-drilldown-back`), the wrapper `[nfsDrilldownWrapper]`, and the back suffix the Visibility Classes directive (placeholder `nfsShowForSr`); a level open at first paint is `[expanded]` on each item of its Open path; the current page is `aria-current` only, styled by `nfs-menu`; the Options stay Options; copied State and Option classes are stripped and reported, redundant Structural ones are not; `nfs-drilldown` uses the exact WCAG formula for every ratio and checks the current link's fill (1.4.1). Behaviour, ARIA, keyboard, animation, rendering modes, and Story ids are otherwise unchanged. Nothing is `OPEN FOR HUMAN`; no prototype is needed.

### Grilling record

Round 1 (the frontier: ADR 0039, ADR 0040, ADR 0041, ADR 0042, the Menu spec's decisions 4 and 5, and the Nested menu re-run's contract settle every prerequisite):
- Q1. Which classes did the published spec leave to the consumer? `vertical menu` on every root, with `drilldown` "may also be written statically, as in Foundation's docs"; `menu vertical nested` on every submenu; the `submenu-toggle-text` span; `show-for-sr` around every back button's suffix; a static `is-active` path to open a level at first paint (user story 16, Rendered HTML, `drilldown-menu--open-path`, the SSR fixture, the fixture e2e case, the usage example); `li.js-drilldown-back` in the `backButton` Option row and the Solution. Source: the spec before this revision.
- Q2. Who binds `.menu` and the root's Variants? The hosted `NfsMenu`, exposing `orientation`, `expanded`, `simple`, `align`, and `iconPosition` (contract item 1; the Menu spec, D5; ADR 0041). `NfsDrilldown` binds no `.menu` and declares none of those inputs; the `NfsMenuRoot` factory's required `inject(NfsMenu, {self: true})` is satisfied. Applied, not reopened.
- Q3. Should the Drilldown root bind `vertical` itself in drilldown mode, as `NfsSubmenu` binds it on submenus? For: every Foundation drilldown example writes `vertical`, and a horizontal root level is unusual. Against: Foundation's Drilldown never adds it (`foundation.drilldown.js:49-50` adds only `drilldown`; `rg vertical` finds nothing in the plugin or Nest); a Variant input's default sets no class (building-blocks 1.4); a second writer beside `orientation` would override a consumer's horizontal root level and fight a ResponsiveMenu's `orientation` rules, which set `vertical` only at `small`. The submenu case differs: Foundation's DropdownMenu adds `verticalClass` to every submenu, and a horizontal submenu breaks every mode's layout (Nested menu D27). Settled: no default; the examples bind `orientation="vertical"` (D25).
- Q4. How does a level open at first paint without `is-active`? `[expanded]="true"`, or a route-data binding, on each item of its Open path (contract item 3; building-blocks 1.4). Found while working it: the published user story 16 ("as Foundation documents") and usage example ("Foundation's documented marker") were wrong for this plugin. Foundation's Drilldown never reads `is-active` at load: its `_init` adds `invisible` to every submenu (`foundation.drilldown.js:117`), and the drilldown docs page has no such marker; the marker is the AccordionMenu docs', which the Nested menu's former seed applied to every mode. So nothing Foundation's Drilldown did is dropped here (D26).
- Q5. The current page? `aria-current` on its link, never a class (contract item 4; ADR 0042). The spec's examples already used it; the class mapping, ARIA table, and 1.3.1 row now say it is the only source and that a copied `is-active` is stripped and reported.
- Q6. The back item and the wrapper? `<li nfsDrilldownBack>` and `<div nfsDrilldownWrapper>`, with no class (the contract's Drilldown line); their directives already bind `js-drilldown-back` (static) and `is-drilldown` (per mode).

Round 2:
- Q7. The back suffix's `show-for-sr`? The Visibility Classes directive for `.show-for-sr`, written `nfsShowForSr` until [Spec: Visibility Classes](104-spec-visibility-classes.md) names it: the placeholder the Button, Button Group, Dropdown, Abide, and Top Bar specs already use. Rejected: a Drilldown-owned span directive (`.show-for-sr` is a Utility class of a family ADR 0039 gives its own directives, unlike `.submenu-toggle-text`, Foundation's own class for the toggle's name element); an `aria-label` on the button (D8 rejected it: it replaces the visible label) (D29).
- Q8. `animateHeight`: a Variant input through `nfsVariantBoolean`, since it sets a class, or an Option? An Option: it is Foundation's `data-animate-height`, Foundation's JavaScript added `animate-height` from it (`foundation.drilldown.js:125`) and its markup never carried the class, and a Variant input cannot keep the decided `NfsDrilldownDefaults.animateHeight` slot (ADR 0040). The Reveal re-run decided `.without-overlay` from `overlay` the same way. `autoHeight`, `closeOnClick`, and `scrollTop` are Options for the same reason (D27).
- Q9. Which copied classes are reported? Building-blocks 1.4 has two rules: a class a directive binds from state is stripped and reported; a Structural class written redundantly merges and is not. Reported: `invisible` on the root (State), `animate-height` on the wrapper (the Option's class, naming `animateHeight`), `is-hidden` on a back item (State). Not reported: `drilldown`, `is-drilldown`, and `js-drilldown-back`, each the directive's Structural class, bound whenever drilldown is live (so redundant there) and stripped by the `false` binding in the other modes of a ResponsiveMenu (Angular consults a static class only when every binding for it is `undefined`, `isStylingValuePresent`, `styling.ts:1009-1015`), so a copy can change nothing; and Foundation's docs write `drilldown` on every root (`docs/pages/drilldown-menu.md:26, 46, 105, 110, 183, 188`), which would warn on every migrated example. The root's Menu classes are the Menu directive's check; the item, submenu, and toggle classes the Nested menu's (D28).
- Q10. A Foundation `li.js-drilldown-back` copied without the directive? The utility's focus rule reads the class, so focus skips it, but it neither closes its level nor hides outside drilldown mode. No new check: the existing check 2 (a submenu without a back item) fires, and its message now names `li[nfsDrilldownBack]`.

Round 3:
- Q11. Sass under the class rule and the Top Bar finding? The consumer includes `@include nfs-menu;` after `foundation-menu` (contract item 6). `nfs-drilldown` gains the 1.4.1 check of `$menu-item-background-active` against `$drilldown-background` and `$drilldown-submenu-background` where not `null` (the Nested menu's D32), and every ratio it checks now uses the library's exact-luminance helper, not Foundation's `color-luminance()`, which the [Spec: Top Bar](86-spec-top-bar.md) ticket measured passing 26 failing pairs. Which ratios change: none of this spec's quoted figures. Every default pair it checks is `$primary-color` on `$white`, `#1779ba` on `#fefefe`, 4.6473:1 exactly (the Top Bar's Probe 3), which the spec already gave as 4.65:1; Foundation's function gives 4.5865:1. The only quoted default that moves is in the Nested menu spec's 1.4.1 row, 4.59:1, which is Foundation's figure (proposed change 3) (D30).
- Q12. Which compile cases prove the two changes? `$drilldown-arrow-color: #116666` on `$drilldown-background: #0a0a0a` stops the compile (2.94:1 exactly; Foundation's function gives 3.01:1; the Top Bar's measured pair); every other check passes there (the fill and the dropdown twin arrow are `#1779ba`, 4.22:1 on `#0a0a0a`; the arrow on the white submenu is 6.68:1). `$menu-item-background-active: #f0f0f0` stops it naming the 1.4.1 check (1.13:1 on `#fefefe`, the value the Menu ticket measured). The published "background of `$primary-color`" form is not used, because every default arrow is also `$primary-color`, so an arrow check would fail first and the case would not isolate the 1.4.1 check.
- Q13. Does the current link's look reach Drilldown levels, or does the Drilldown need a rule as the dropdown top level does? It reaches them: `nfs-menu`'s `.menu a[aria-current]:where(...)` is specificity (0,2,1), and Foundation's only drilldown link background, `.drilldown a { background: $drilldown-background }`, is (0,1,1) (`_drilldown.scss:88-93`); `.is-drilldown-submenu a` sets only padding. No Drilldown rule.
- Q14. The aligned arrows? Foundation's `zf-drilldown-left-right-arrows` keys on `&.align-left` and `&.align-right` of `.drilldown` (`_drilldown.scss:58-69`), so `align` on the root, bound by the hosted Menu, reaches them and `nfs-drilldown` rule 2's twins alike; user story 41, the API row, and rule 2's reason say so.
- Q15. Stories and tests? No story, test host, or fixture writes a class except the copied-class cases; controls outside the menu are `nfsButton`; the default story asserts the directive-bound classes; the hybrid story finds the current link by `getByRole('link', {current: 'page'})`; new browser-level cases for Hosting, Initial state, and Copied classes; the SSR fixture writes no class attribute and asserts the Menu, submenu, toggle-text, back, and suffix classes; the Sass test gains the two cases of Q12. Story ids unchanged.
- Q16. Rendering modes? Unchanged: the hosted Menu's classes and the bound Open path are host bindings the first update pass reads, so they are in the server HTML; the only new construction-time work is the development-only static `class` read, whose warning waits for the client.
- Q17. Glossary or ADR? No new term: Drilldown level and Drilldown wrapper still read true (the wrapper element is consumer-written; its class is bound). No ADR: hosting is ADR 0041, the current page ADR 0042, the initial state building-blocks 1.4, and the rest is local and reversible (D24).

The frontier is empty.

### Decisions

1. `NfsDrilldown` hosts `NfsMenu` with `inputs: ['orientation', 'expanded', 'simple', 'align', 'iconPosition']`, binds no `.menu` or Menu Variant itself, and sets no orientation of its own; the examples bind `orientation="vertical"`, and `align="left"` or `align="right"` turns Foundation's drilldown arrows (D25).
2. The markup carries no class: `ul[nfsSubmenu]` for every submenu, `span[nfsSubmenuToggleText]` in a Hybrid toggle, `li[nfsDrilldownBack]` (static `js-drilldown-back`), `[nfsDrilldownWrapper]`, and the back button's hidden suffix in the Visibility Classes directive, written `nfsShowForSr` until that spec names it (D29).
3. A level open at first paint is `[expanded]="true"`, or a route-data binding, on each item of its Open path; the static `is-active` path is gone, and the published claim that Foundation documents it for the Drilldown is corrected; development check 6 also names `[expanded]` (D26).
4. The current page is `aria-current` on its link, never a class; `nfs-menu` gives it Foundation's active look inside every level with no Drilldown rule, and the consumer includes `nfs-menu`.
5. `autoHeight`, `animateHeight`, `closeOnClick`, and `scrollTop` stay Options with `booleanAttribute` and their Defaults token slots; `animate-height` stays the wrapper's host binding (D27).
6. Development check 7 reports a copied `invisible` (root), `animate-height` (wrapper, naming `animateHeight`), and `is-hidden` (back item), and not `drilldown`, `is-drilldown`, or `js-drilldown-back`; check 2 names `li[nfsDrilldownBack]` (D28).
7. `nfs-drilldown` computes every ratio with the library's exact-luminance helper and adds the 1.4.1 check of `$menu-item-background-active` against `$drilldown-background` and `$drilldown-submenu-background`; two compile cases; the Sass subsection gains item (6) (no Variant properties); the spec's quoted 4.65:1 figures stand (D30).
8. The class mapping table gains a Kind column and rows for every class on the Drilldown's elements; the entry point declares no Variant input, registry, or property; Out of Scope names the Menu directive and the Visibility Classes directive.
9. Stories, tests, fixtures, and examples write no class (except the copied-class cases); new browser-level Hosting, Initial state, and Copied classes cases; the SSR smoke's fixture writes no class attribute; Story ids unchanged.
