# next-foundation-specs: bundle index

The planning bundle for the next, from-scratch ngx-foundation-sites: an Angular 22.2 directive library that keeps Foundation for Sites 6.9's Sass and CSS class contract and gives every Foundation UI component, layout system, and utility family Angular directives, which set every Foundation and library class so the consumer writes none (the class rule, [ADR 0039](adr/0039-directives-manage-every-foundation-class.md)). This file is the index the [Consistency review and bundle index](issues/36-consistency-review.md) wrote on 2026-09-26, after checking the whole bundle against itself, brought up to date on 2026-09-27 with the ruling of [Triage the out-of-scope Foundation components and variants](issues/79-triage-out-of-scope-components-and-variants.md); [Consistency review: the class-rule wave](issues/133-consistency-review-class-rule-wave.md) checks it again. The map is [map.md](map.md); every decision lives in one ticket under `issues/`, and this index only points at them. `issues/` holds 133 tickets: the 79 before the class-rule wave are resolved, and the wave's 54 are open (Open list).

## Destination

One published spec per Foundation docs page for every UI component, layout system, and utility family in Foundation for Sites 6.9, JavaScript plugin or CSS-only, plus one shared-utility spec for the Variant typing tooling: 52 specs. 34 are published under [specs/](specs/): the 21 JavaScript plugins, Button, the five shared utilities (the four the building-blocks decision added, plus [Spec: Variant declaration tooling](issues/136-spec-variant-declaration-tooling.md), the fifth shared utility that [Decide: typed Variant inputs over open Sass maps](issues/81-decide-typed-variant-inputs-open-sass-maps.md) added), and seven of the 25 new docs-page specs the 2026-09-27 ruling added ([Spec: Button Group](issues/82-spec-button-group.md), [Spec: Callout](issues/89-spec-callout.md), [Spec: Close Button](issues/83-spec-close-button.md), [Spec: Forms](issues/98-spec-forms.md), [Spec: Menu](issues/85-spec-menu.md), [Spec: Top Bar](issues/86-spec-top-bar.md), [Spec: Breadcrumbs](issues/88-spec-breadcrumbs.md)). The other 18 are open spec tickets, the rest of the 25 docs-page specs the 2026-09-27 ruling added; each of the 26 specs published before that ruling is re-run under the class rule by a ticket of its own (Open list). Each spec describes the Angular directives (preferred) or component that give the component to the next repository, and [building-blocks.md](building-blocks.md) records the Angular, Aria, CDK, or native platform primitive each one is built on. The map also required a working Playwright component test solution (found: [Prototype: Playwright component tests mounting CSF stories from @storybook/angular-vite](issues/40-playwright-component-testing-prototype.md)), a decided browser testing stack ([ADR 0018](adr/0018-browser-testing-stack.md)), and a passed consistency review: the [Consistency review and bundle index](issues/36-consistency-review.md) passed the 26 published specs, and [Consistency review: the class-rule wave](issues/133-consistency-review-class-rule-wave.md) is the gate for all 52. The full statement is the map's Destination section.

Target platform: Angular 22.2 (core, forms, cdk, aria, material), Nx 23.2, Storybook 10.6 with `@storybook/angular-vite`, Vitest 4.1 browser mode, TypeScript 6.0, Foundation for Sites 6.9.0; browsers are the Baseline widely available set of 2026-05-07 (Chrome, Edge, and Firefox 119, Safari 17). Moving the bundle into the new repository is that repository's first task and is out of scope here.

## How to read the bundle

Read in this order. Each step assumes the ones before it.

1. [map.md](map.md): the Destination, the standing preferences every spec follows (directive first, implementation order, Foundation Sass reused and never re-implemented, WCAG 2.2 AA as requirements, animation through `animate.enter`/`animate.leave` or State classes, every rendering mode, the Browser target, the four test layers), the orchestration and triage rules, and Decisions so far (one line per resolved ticket).
2. [building-blocks.md](building-blocks.md): Part 1 holds the cross-cutting rules every spec inherits (1.1 directive or component to 1.14 spec shape); Part 2 is the matrix (Table A structure, Table B mechanics) with one row per plugin, and Table D, one row per spec the 2026-09-27 ruling added, filled by its spec ticket; Part 3 the four shared utilities (Table C); Part 4 the graduated tickets, now with no open item left.
3. [architecture-guide.md](architecture-guide.md): the directive and component architecture principles: 26 testable rules over eight kinds of building block, an 11-question decision framework, an idioms table for authors who know React's headless libraries, and the conflicts the research raised, each principle restating a map ruling, an ADR, or building-blocks (which outrank it) or marked New; [Audit: the specs against the architecture guide](issues/142-audit-specs-against-architecture-guide.md) audits every spec against it, and its provisional parts (the import array, the release policy) are not audited until the user decides them.
4. [CONTEXT.md](CONTEXT.md): the glossary. Specs use its terms as written (Trigger, Openable, Light dismiss, Anchored pane, Nested menu, Mode swap, Server breakpoint, Library mixin, and so on) and avoid the words it lists under `_Avoid_`.
5. [adr/](adr/): 44 decision records, indexed below (42 accepted, two superseded). Later findings are dated bullets beside the part they qualify, and a changed decision gets a new record; audit 0004's fixes corrected the wording of ADRs 0008, 0017, 0022, 0024, and 0025 in place (its Resolution log).
6. [specs/](specs/): 34 published specs; the 26 published before the 2026-09-27 ruling, in the plugin and utility tables below, are each revised under the class rule by their own re-run ticket, and the eight published since ([Spec: Button Group](issues/82-spec-button-group.md), [Spec: Callout](issues/89-spec-callout.md), [Spec: Close Button](issues/83-spec-close-button.md), [Spec: Forms](issues/98-spec-forms.md), [Spec: Menu](issues/85-spec-menu.md), [Spec: Top Bar](issues/86-spec-top-bar.md), [Spec: Breadcrumbs](issues/88-spec-breadcrumbs.md), [Spec: Variant declaration tooling](issues/136-spec-variant-declaration-tooling.md)) are already written under it. Every spec has the seven `/to-spec` sections in order (Problem Statement, Solution, User Stories, Implementation Decisions, Testing Decisions, Out of Scope, Further Notes), with the API-design material placed as building-blocks 1.14 says, a WCAG 2.2 AA criteria subsection (ADR 0022), and a Sass subsection in the form of [Sass packaging for the new library](issues/57-sass-packaging.md). Each spec's ticket under `issues/` holds its decision log, triage, and amendments.
7. [storybook-conventions.md](storybook-conventions.md): how every spec's stories are written, named, styled, and gated, including the full `_settings-overrides.scss` list the specs require.
8. [research/](research/): the twenty-five research files: the fifteen the specs cite by title and section (the four Foundation plugin inventories ([disclosure](research/foundation-inventory-disclosure.md), [menus](research/foundation-inventory-menus.md), [positioned](research/foundation-inventory-positioned.md), [forms and media](research/foundation-inventory-forms-media.md)), [Foundation core conventions and utilities](research/foundation-utilities-conventions.md), the [Angular 22.2 API survey](research/angular-22-api-survey.md), the [Aria inventory](research/angular-aria-inventory.md), the [CDK inventory](research/angular-cdk-inventory.md), the [Material reference](research/angular-material-reference.md), the [APG patterns](research/aria-apg-patterns.md), the [web platform features](research/web-platform-features.md), the [tooling baseline](research/tooling-baseline.md), the [DI and composition patterns](research/di-and-composition-patterns.md), the [rendering modes](research/angular-rendering-modes.md), and [Playwright component testing](research/playwright-component-testing.md)), and the six evidence files of the open-decision pass: the three decision dossiers ([the modal-opener decision](research/decision-aria-expanded-modal-opener.md), [the Slider vertical decision](research/decision-slider-vertical.md), [the base-href decision](research/decision-base-href-hash-links.md)), the [fallback confirmation dossier](research/aria-fallback-evidence.md), and the two assistive-technology evidence files ([evidence 1](research/assistive-technology-evidence.md), [evidence 2](research/assistive-technology-evidence-2.md)); and the three evidence files of the out-of-scope triage: the [exclusions sweep](research/out-of-scope-exclusions.md), the [Foundation component catalogue](research/foundation-component-catalogue.md), and the [judge's triage](research/out-of-scope-triage.md).
9. [prototypes/](prototypes/): the captured decisive files of 23 prototypes and re-runs, plus the evidence captures of five open-decision-pass tickets: [Decide the `@angular/aria` fallback confirmation](issues/75-evidence-aria-fallback-confirmation.md) (`prototypes/orbit-slide-derived-inert/`), [Decide: `aria-expanded` on a modal dialog's opener](issues/72-decide-aria-expanded-on-modal-opener.md) (`prototypes/modal-opener-aria/`), [Decide: Slider vertical orientation](issues/73-decide-slider-vertical-orientation.md) (`prototypes/slider-vertical-orientation/`), [Decide: `#`-only links that `<base href>` resolves to another document](issues/74-decide-base-href-hash-links.md) (`prototypes/base-href-hash-links/`), and [Decide: the server state of an open-by-default non-modal Reveal's Trigger](issues/78-decide-open-by-default-non-modal-reveal-server-state.md) (`prototypes/reveal-open-first-paint/`), each with a README that states the question, how to run it, and the verdict; the matching ticket holds the results table and triage. The runnable workspaces stayed under `D:/tmp/`.
10. [audits/](audits/): seven compliance audits (research wave, building blocks, prototypes and first specs, second spec wave, final bundle, open-decision pass, and the fixes of audit 0006), each ending with a resolution log.

### `@angular/aria` building blocks not used (decided 2026-09-27)

The repository's `AGENTS.md` asks for confirmation before falling back from an `@angular/aria` building block. The user ruled that this pass decides the list from evidence (map, Open-decision pass); the [Decide the `@angular/aria` fallback confirmation](issues/75-evidence-aria-fallback-confirmation.md) did, from the dossier `research/aria-fallback-evidence.md` and two adversarial reviews. One fallback was overruled; eight stand, with corrected reasons where the original overstated.

1. Overruled: Orbit slides host Aria's `TabPanel` again and override only `inert`, with a binding derived from `TabPanel.visible()` that changes in every pass in which Aria's does and so keeps `inert` out of server HTML (measured in the server renderer and in three engines); the Orbit writes Aria's selection synchronously. [ADR 0037](adr/0037-orbit-slide-hosts-tab-panel.md) supersedes ADR 0034; [Spec: Orbit](issues/33-spec-orbit.md).
2. Orbit offers no Aria `TabContent` for lazy slides: Aria's lazy content renders only for the selected slide, and in a scroll-snap carousel a slide is on screen before it is selected, so a lazy slide would be blank while scrolled in and the container's height would jump when it fills; empty in server HTML too. `@defer (on viewport)` inside a slide is the supported form. [Spec: Orbit](issues/33-spec-orbit.md).
3. Accordion does not use Aria's `AccordionContent`, even for Lazy content: Aria creates the view in a render callback, so an open panel would be empty in server HTML (ADR 0008); it removes content at the start of the close transition unless preserved; and its `preserveContent` cannot be exposed through the wrapper's own `hostDirectives` inputs (a consumer can still bind it on the content element, in bound form only, through `AccordionPanel`'s own exposure, and library code reading it would depend on Aria's private-prefixed re-export). [Spec: Accordion](issues/15-spec-accordion.md).
4. Tabs uses Aria's `TabContent` only behind the opt-in lazy template; by default panel content is projected, for the same server-HTML reason. [Spec: Tabs](issues/16-spec-tabs.md).
5. Responsive Accordion Tabs exposes neither lazy form (additive scope, not a misfit): sections are created again on every Mode swap, including the first-render swap on a client whose breakpoint differs from the server's, so `preserveContent` cannot hold; and the tabs-mode lazy form is empty in server HTML while the accordion-mode form is not, so one lazy input would be server-rendered in one mode only. [Spec: Responsive Accordion Tabs](issues/19-spec-responsive-accordion-tabs.md).
6. The menus (the Nested menu family behind AccordionMenu, Drilldown, DropdownMenu, and ResponsiveMenu) use neither `ngMenuBar`/`ngMenu` nor `ngTree`: they apply the `menubar`, `menu`, `menuitem`, and `tree` roles that the APG advises against for site navigation (the Angular Aria guide agrees for `ngMenu` and lists navigation as a use for `ngTree`), set no tab stop in server HTML, cancel Enter on a link item (the menu), keep tree child levels out of server HTML and force multi-expansion (the tree), need `[submenu]` references or `ng-template` groups with `[parent]` inputs on Foundation's nested `ul`, fit Drilldown not at all, and the menubar is horizontal only ([ADR 0004](adr/0004-menus-use-disclosure-navigation.md)). [Spec: Nested menu (shared utility)](issues/56-spec-nested-menu.md), [Spec: Accordion Menu](issues/20-spec-accordion-menu.md), [Spec: Dropdown Menu](issues/21-spec-dropdown-menu.md), [Spec: Drilldown Menu](issues/22-spec-drilldown-menu.md), [Spec: Responsive Menu](issues/23-spec-responsive-menu.md).
7. Accordion Menu does not use Aria's accordion: every enabled trigger is a tab stop (not one roving stop), but its group listener handles keys from inside open sections without checking the target (arrows move among triggers only; Enter and Space toggle a section), so a menu would guard Aria's keys off and re-add Foundation's cross-link arrows; the `region` per panel is removable; each trigger needs a required `[panel]` binding; and ResponsiveMenu needs one directive family across modes. [Spec: Accordion Menu](issues/20-spec-accordion-menu.md).
8. The Dropdown pane does not use Aria's menu: a pane holds arbitrary content, so `role="menu"` would promise menu keys it does not have and fail axe's required-children rule; it is a disclosure or a non-modal dialog. [Spec: Dropdown](issues/26-spec-dropdown.md).
9. Triggers do not use Aria's `MenuTrigger`: it renders `aria-haspopup="true"`, which WAI-ARIA treats as `menu`, targets `ngMenu` only, and keeps the open state in the trigger, wrong for every Openable. [Spec: Triggers (shared utility)](issues/54-spec-triggers.md).

No available Aria pattern was declined elsewhere: `@angular/aria` 22.2 ships accordion, combobox, grid, listbox, menu, tabs, toolbar, and tree, and has nothing for Button, the Breakpoint service, the Anchored pane, Reveal, Off-canvas, Tooltip, Toggler, Responsive Toggle, Slider, Abide, Interchange, Equalizer, Sticky, Smooth Scroll, or Magellan.
